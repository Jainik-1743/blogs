> **In one line:** a **transaction** groups several statements so they all happen or none do, and an **isolation level** decides what a transaction can see while others run at the same time. Most real bugs here are races (two sessions touching the same rows), and the fixes are a short list: atomic updates, `SELECT ... FOR UPDATE`, a higher isolation level plus a retry loop, and keeping transactions short.

In lessons 0 to 5 one person ran one query at a time. A real shop has many sessions writing at once: two buyers for the last pair of headphones, a transfer that crashes halfway, a job queue with ten workers. This lesson reproduces each problem with **two real `psql` sessions** so you can see it happen, and then shows the fix. For the theory of ACID (atomicity, consistency, isolation, durability) and the full list of anomalies, read [System Design, Lesson 21](/system-design/lesson-21); for how an API uses transactions see [Backend, Lesson 07](/backend/lesson-7); for the Prisma side see [Full-Stack Q&A, Lesson 08](/fullstack-qa/lesson-8). The tables are the shop of [lesson 4](/sql-postgres/lesson-4), plus an `accounts` table for money moves.

## Words used in this lesson

- **A transaction** is a group of statements treated as one unit. It ends with `COMMIT` (keep the changes) or `ROLLBACK` (throw them away).
- **Atomic** means all-or-nothing. **Durable** means that after `COMMIT` returns, the data survives a crash.
- **A session** (or connection) is one client talking to the database. Every session has its own transaction at a time.
- **An isolation level** is a rule for how much one transaction sees of the changes of others running at the same time.
- **A snapshot** is a frozen view of which rows are visible. PostgreSQL keeps old row versions (**MVCC**, multi-version concurrency control), so readers do not block writers and writers do not block readers.
- **An anomaly** is a wrong result caused by concurrency. Names used below: **non-repeatable read**, **lost update**, **write skew**.
- **A lock** is a claim on a row or table. Others who want a conflicting claim must wait.
- **A deadlock** is a cycle: A waits for B and B waits for A. Nobody can move.
- **A serialization failure** is an error that PostgreSQL raises to stop an anomaly. The right response is to **retry** the whole transaction.
- **Idempotent** means doing it twice has the same effect as doing it once.
- **Dead rows** are old versions of updated or deleted rows. **`VACUUM`** cleans them up.

## BEGIN, COMMIT, ROLLBACK: all or nothing

Take two accounts: Asha has 10,000 cents (100.00) and Ben has 5,000.

```sql
CREATE TABLE accounts (
  id            integer PRIMARY KEY,
  owner         text NOT NULL,
  balance_cents integer NOT NULL CHECK (balance_cents >= 0)
);
INSERT INTO accounts VALUES (1, 'Asha', 10000), (2, 'Ben', 5000);
```

A transfer of 3,000 is two updates. Without `BEGIN`, psql is in **autocommit** mode: each statement is its own tiny transaction, committed at once. So if the program dies between the two statements:

```sql
UPDATE accounts SET balance_cents = balance_cents - 3000 WHERE id = 1;
-- the app crashes here, the second statement never runs
SELECT * FROM accounts ORDER BY id;
```

```text
 id | owner | balance_cents 
----+-------+---------------
  1 | Asha  |          7000
  2 | Ben   |          5000
(2 rows)
```

Three thousand cents have vanished. This is the atomicity problem. Wrap both updates in a transaction:

```sql
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 3000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 3000 WHERE id = 2;
SELECT * FROM accounts ORDER BY id;
ROLLBACK;
SELECT * FROM accounts ORDER BY id;
```

```text
 id | owner | balance_cents 
----+-------+---------------
  1 | Asha  |          7000
  2 | Ben   |          8000
(2 rows)

 id | owner | balance_cents 
----+-------+---------------
  1 | Asha  |         10000
  2 | Ben   |          5000
(2 rows)
```

Inside the transaction you see your own changes. After `ROLLBACK` nothing happened. If the connection dies before `COMMIT`, PostgreSQL rolls back for you, so the half-done state is never visible to anyone else. Replace `ROLLBACK` with `COMMIT` and both changes become permanent together.

### An error aborts the whole transaction

A constraint (lesson 4) is a good safety net. Try to move 20,000 from Asha, who only has 10,000:

```sql
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 20000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 20000 WHERE id = 2;
COMMIT;
```

```text
BEGIN
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_cents_check"
DETAIL:  Failing row contains (1, Asha, -10000).
ERROR:  current transaction is aborted, commands ignored until end of transaction block
```

After the first error, PostgreSQL puts the transaction in an **aborted** state. Every later statement is refused, and a `COMMIT` is turned into a `ROLLBACK` (psql printed `ROLLBACK` for my `COMMIT`; I hid it with `-q`). Balances were unchanged afterwards. This is a difference from some other databases: you cannot "ignore the error and carry on" in PostgreSQL, unless you use a savepoint.

> [!warn] **Never swallow a database error inside a transaction.** If your code catches the exception and keeps running statements, they all fail with `current transaction is aborted`. Catch it, `ROLLBACK`, and decide whether to retry.

## Savepoints: undo part of a transaction

A **savepoint** is a bookmark inside a transaction. `ROLLBACK TO SAVEPOINT name` undoes everything after the bookmark and keeps the transaction alive. Example: build order 1, then try to add 5 headphones when only 1 is in stock (the `CHECK (stock >= 0)` from lesson 4 will refuse):

```sql
BEGIN;
INSERT INTO orders (customer_id) VALUES (1) RETURNING id;
INSERT INTO order_items VALUES (1, 1, 2, 350);
SAVEPOINT try_headphones;
INSERT INTO order_items VALUES (1, 3, 5, 5900);
UPDATE products SET stock = stock - 5 WHERE id = 3;
ROLLBACK TO SAVEPOINT try_headphones;
SELECT * FROM order_items;
COMMIT;
```

```text
 id 
----
  1
(1 row)

ERROR:  new row for relation "products" violates check constraint "products_stock_check"
DETAIL:  Failing row contains (3, Headphones, audio, 5900, -4).

 order_id | product_id | quantity | unit_price_cents 
----------+------------+----------+------------------
        1 |          1 |        2 |              350
(1 row)
```

The headphone row and the stock change are gone, the notebook line stays, and the order commits. Savepoints are also what ORMs use for "nested transactions". Do not use them in a tight loop for every row: each one costs a little, and a huge number of them slows a transaction down.

## Isolation levels in one table

PostgreSQL has four names, but three behaviours:

| Level | What each statement sees | Prevents | Still allows |
|---|---|---|---|
| **Read Committed** (the default) | a new snapshot at the start of **each statement** | dirty reads | non-repeatable reads, lost updates (if you read then write), write skew |
| **Repeatable Read** | one snapshot taken at the **first statement** of the transaction | the above, plus phantom reads in PostgreSQL | write skew |
| **Serializable** | like Repeatable Read, plus conflict tracking | everything: the result is as if transactions ran one at a time | nothing, but it may fail with an error you must retry |

`READ UNCOMMITTED` is accepted but behaves as Read Committed in PostgreSQL, so a **dirty read** (seeing another transaction's uncommitted data) never happens. You set the level per transaction with `BEGIN ISOLATION LEVEL REPEATABLE READ;`, or per session with `SET default_transaction_isolation`. Check yours with `SHOW transaction_isolation;`.

The sections below show each behaviour with two sessions, **A** and **B**, side by side. Lines are in the order they ran.

### Read Committed: a non-repeatable read

A **non-repeatable read** means the same query, twice in one transaction, gives two answers because someone else committed in between.

```text
A| SHOW transaction_isolation;
A|  read committed
A| BEGIN;
A| SELECT balance_cents FROM accounts WHERE id = 1;
A|          10000
B| UPDATE accounts SET balance_cents = balance_cents - 2500 WHERE id = 1;
B| UPDATE 1
A| SELECT balance_cents FROM accounts WHERE id = 1;
A|           7500
A| COMMIT;
```

Session B's update was committed at once (autocommit). Session A, still inside its transaction, saw 10,000 and then 7,500. For a single report this can be a bug: a total at the top of a page that does not match the rows below it, because the numbers came from different moments. It is fine for many simple requests, and it is the default because it is the cheapest.

### Repeatable Read: one frozen view

Same steps, but A starts with `BEGIN ISOLATION LEVEL REPEATABLE READ;`:

```text
A| BEGIN ISOLATION LEVEL REPEATABLE READ;
A| SELECT balance_cents FROM accounts WHERE id = 1;
A|          10000
B| UPDATE accounts SET balance_cents = balance_cents - 2500 WHERE id = 1;
B| UPDATE 1
A| SELECT balance_cents FROM accounts WHERE id = 1;
A|          10000
A| UPDATE accounts SET balance_cents = balance_cents - 1000 WHERE id = 1;
A| ERROR:  could not serialize access due to concurrent update
A| ROLLBACK;
A| SELECT balance_cents FROM accounts WHERE id = 1;
A|           7500
```

Two things happened. First, A's second read still says 10,000: it sees the snapshot from its first statement, not B's commit. Second, when A then tried to **update** the row that B changed after A's snapshot, PostgreSQL refused with a serialization failure instead of silently building on stale data. Under Read Committed the same update would simply have run on the new value. So with Repeatable Read your code **must be ready to retry** (see below).

### Lost update, and the fix with FOR UPDATE

A **lost update** is the classic race. Two buyers both read `stock = 10`. The app computes the new value itself (`10 - 3` and `10 - 4`) and writes it back:

```text
A| BEGIN;
B| BEGIN;
A| SELECT stock FROM products WHERE id = 1;
A|     10
B| SELECT stock FROM products WHERE id = 1;
B|     10
A| UPDATE products SET stock = 10 - 3 WHERE id = 1;
B| UPDATE products SET stock = 10 - 4 WHERE id = 1;     -- waits for A
A| COMMIT;
B| UPDATE 1                                             -- B's update ran after A committed
B| COMMIT;
B| SELECT stock FROM products WHERE id = 1;
B|      6
```

Seven were sold (3 + 4) and stock should be 3, but it is 6. A's sale was **lost**: B overwrote it with a number computed from a stale read. There are two good fixes.

**Fix 1: let the database do the arithmetic.** `UPDATE products SET stock = stock - 4 WHERE id = 1 AND stock >= 4` is atomic. The row is locked while it runs, and under Read Committed the second session re-reads the latest value after waiting. Check `rowcount`: 0 rows means "not enough stock". This is the best fix whenever the new value is a simple function of the old one.

**Fix 2: lock the row when you read it.** `SELECT ... FOR UPDATE` locks the rows it returns until the end of the transaction:

```text
A| BEGIN;
B| BEGIN;
A| SELECT stock FROM products WHERE id = 1 FOR UPDATE;
A|     10
B| SELECT stock FROM products WHERE id = 1 FOR UPDATE;      -- B waits here
A| UPDATE products SET stock = stock - 3 WHERE id = 1;
A| COMMIT;
B|      7                                                  -- B's SELECT returns only now, with the new value
B| UPDATE products SET stock = stock - 4 WHERE id = 1 RETURNING stock;
B|      3
B| COMMIT;
```

B was held at its `SELECT ... FOR UPDATE` until A committed, then read the fresh value 7, and the final stock is 3. Use this when the app must read, think, and then write (for example, check a business rule in code). Keep the locked section short.

> [!note] **Lock modes you will meet.** `FOR UPDATE` blocks other writers and other lockers. `FOR NO KEY UPDATE` is weaker (it lets foreign key checks through), and `FOR SHARE` and `FOR KEY SHARE` only block writers. A plain `SELECT` takes no row lock at all. I ran only `FOR UPDATE`, `NOWAIT` and `SKIP LOCKED` here; the weaker modes are from the documentation.

### Write skew: Repeatable Read is not enough

**Write skew** is subtler. Two transactions each read the same set of rows, each decide "it is safe", and each update a **different** row. Each update alone is fine; together they break a rule. The standard story: a hospital needs at least one doctor on call. Both doctors are on call and both ask to go off.

```sql
CREATE TABLE oncall (doctor text PRIMARY KEY, on_call boolean NOT NULL);
INSERT INTO oncall VALUES ('Asha', true), ('Ben', true);
```

Under **Repeatable Read** (both sessions run `BEGIN ISOLATION LEVEL REPEATABLE READ;` first):

```text
A| SELECT count(*) FROM oncall WHERE on_call;
A|      2
B| SELECT count(*) FROM oncall WHERE on_call;
B|      2
A| UPDATE oncall SET on_call = false WHERE doctor = 'Asha';
B| UPDATE oncall SET on_call = false WHERE doctor = 'Ben';
A| COMMIT;
B| COMMIT;
A| SELECT * FROM oncall ORDER BY doctor;
    Asha | f
    Ben  | f
```

Both committed. Nobody is on call. There was no error because the two updates touched **different rows**, so no row-level conflict exists. Repeatable Read cannot see the rule that links them. The same steps with `ISOLATION LEVEL SERIALIZABLE`:

```text
A| UPDATE oncall SET on_call = false WHERE doctor = 'Asha';
B| UPDATE oncall SET on_call = false WHERE doctor = 'Ben';
A| COMMIT;
A| COMMIT
B| COMMIT;
B| ERROR:  could not serialize access due to read/write dependencies among transactions
B| DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
B| HINT:  The transaction might succeed if retried.
A| SELECT * FROM oncall ORDER BY doctor;
    Asha | f
    Ben  | t
```

PostgreSQL's Serializable level (called **SSI**, serializable snapshot isolation) watches which transactions read what others wrote. It saw that A and B each read data the other changed, a pattern that cannot happen in any one-at-a-time order, and cancelled B. If B retries now, it sees the truth:

```text
B| BEGIN ISOLATION LEVEL SERIALIZABLE;
B| SELECT count(*) FROM oncall WHERE on_call;
B|      1
B| ROLLBACK;
```

Only one doctor is left, so B's code takes the "refuse" branch. That is the whole point: B ran again against the new state and the rule held.

> [!warn] **Serializable does not mean "no errors". It means "no wrong answers, but sometimes an error".** If you turn it on and do not retry on error `40001`, you have just moved the bug from silent wrong data to visible failed requests.

### The retry loop

Retry the **whole transaction**, from `BEGIN`, when the error code is `40001` (`serialization_failure`) or `40P01` (`deadlock_detected`). Do not retry the single statement; the snapshot it ran in is gone. Here is the helper I ran with Node and `pg`, plus the two doctors going off call at the same time:

```js
async function withTransaction(fn, { isolation = 'SERIALIZABLE', maxTries = 5 } = {}) {
  for (let attempt = 1; ; attempt++) {
    const client = await pool.connect();
    try {
      await client.query(`BEGIN ISOLATION LEVEL ${isolation}`);
      const result = await fn(client, attempt);
      await client.query('COMMIT');
      return result;
    } catch (err) {
      try { await client.query('ROLLBACK'); } catch {}
      const retryable = err.code === '40001' || err.code === '40P01';
      if (!retryable || attempt >= maxTries) throw err;
      console.log(`  attempt ${attempt} failed with ${err.code}, retrying`);
      await new Promise(r => setTimeout(r, 20 * attempt + Math.random() * 20));  // small random backoff
    } finally {
      client.release();
    }
  }
}
```

The business function reads the count, and goes off call only if at least two are on. I added a 100 ms pause after the read to make the race certain. Output:

```text
  attempt 1 failed with 40001, retrying
Asha: now off call, attempt 1
Ben: refused (only 1 on call), attempt 2
[ { doctor: 'Asha', on_call: false }, { doctor: 'Ben', on_call: true } ]
```

Ben's first attempt failed, the second attempt saw one doctor and refused. Three rules for the loop: **limit the tries**, **add a small random delay** (so two retries do not collide again), and make sure the function inside has **no side effects outside the database** (an email sent inside a retried function is sent twice). Many ORMs do not retry for you.

### Which level should I use?

- **Read Committed** for most web requests, with atomic `UPDATE`s and `FOR UPDATE` where a race matters.
- **Repeatable Read** for reports and exports that must see one consistent picture (a read-only transaction costs almost nothing).
- **Serializable** when the rule spans several rows and you cannot easily lock them (like "at least one on call", "no overlapping bookings"), and you are willing to add a retry loop. Test it under load: it has a cost.

Alternatives to Serializable for write skew: lock the rows you read (`SELECT ... FOR UPDATE` on all the `oncall` rows), or turn the rule into a **constraint** (a unique index or an exclusion constraint), so the database enforces it for every session.

## Row locks, table locks, and what waits for what

An `UPDATE` or `DELETE` takes a **row lock** on each row it changes. A second writer to the same row waits until the first commits or rolls back. Plain reads never wait. Besides rows, every statement takes a lock on the **table**. I looked at what session A held after one `UPDATE` inside a transaction:

```sql
SELECT locktype, relation::regclass AS rel, mode, granted
FROM pg_locks WHERE pid = pg_backend_pid() AND locktype IN ('relation','transactionid');
```

```text
   locktype    |      rel      |       mode       | granted 
---------------+---------------+------------------+---------
 relation      | pg_locks      | AccessShareLock  | t
 relation      | accounts      | RowExclusiveLock | t
 relation      | accounts_pkey | RowExclusiveLock | t
 transactionid |               | ExclusiveLock    | t
(4 rows)
```

An `UPDATE` takes `RowExclusiveLock` on the table and each index. That sounds scary but it is a **weak** table lock: many sessions can hold it at once, so many updates can run in parallel. The row lock itself is not listed in `pg_locks` (it is stored in the row; waiters queue on the `transactionid` of the transaction that owns it). A plain `SELECT` takes `AccessShareLock`, the weakest of all.

| Table lock | Taken by | Conflicts with |
|---|---|---|
| `ACCESS SHARE` | `SELECT` | only `ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE` | `SHARE` and stronger |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`, `CREATE INDEX CONCURRENTLY` | itself and stronger |
| `SHARE` | `CREATE INDEX` (not concurrent) | writers: blocks inserts and updates |
| `ACCESS EXCLUSIVE` | most `ALTER TABLE`, `DROP`, `TRUNCATE`, `VACUUM FULL` | **everything**, even `SELECT` |

(The table is from the PostgreSQL documentation; I observed `AccessShare` and `RowExclusive` above and the `ACCESS EXCLUSIVE` wait below, not each mode.)

### The lock queue: why a small `ALTER TABLE` can freeze a table

`ACCESS EXCLUSIVE` conflicts with everything, and lock requests are served **in line**. So a waiting `ALTER TABLE` blocks everyone behind it, even plain reads. I reproduced this with three sessions. A opened a transaction and ran a harmless `SELECT count(*)` (holding `AccessShareLock`, and not committing). B ran `ALTER TABLE accounts ADD COLUMN note text`. Then C, a third psql, ran a plain `SELECT count(*) FROM accounts`:

```text
  pid  | wait_event_type | wait_event |                   query                    
-------+-----------------+------------+--------------------------------------------
 18254 | Lock            | relation   | ALTER TABLE accounts ADD COLUMN note text;
 18360 | Lock            | relation   | SELECT count(*) FROM accounts
(2 rows)
```

```text
C|  count = 2
C| Time: 2241.485 ms (00:02.241)
```

C's innocent `SELECT` waited **2.2 seconds**, only because it stood behind B's waiting `ALTER`, and B waited for A. When A committed, B ran, then C. On a busy production table, one forgotten open transaction plus one `ALTER TABLE` stops every query on that table. This is the main reason lesson 7 uses `lock_timeout` for migrations.

You can also fail fast instead of waiting: `SET lock_timeout = '2s'` makes a statement give up with `ERROR: canceling statement due to lock timeout`. I confirmed the setting is accepted but did not paste that exact message from a run, so treat the wording as from the docs.

## SKIP LOCKED: a job queue in one query

A common job: many workers must each take a different queued job. If all use `SELECT ... FOR UPDATE`, they queue up behind the first job. `SKIP LOCKED` says "skip rows that are locked by someone else":

```sql
CREATE TABLE jobs (
  id      int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payload text NOT NULL,
  status  text NOT NULL DEFAULT 'queued'
);
INSERT INTO jobs (payload) SELECT 'email-' || g FROM generate_series(1, 5) g;
```

Two workers, each in a transaction, each asking for two jobs:

```text
A| BEGIN;
B| BEGIN;
A| SELECT id, payload FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 2 FOR UPDATE SKIP LOCKED;
A|   1 | email-1
A|   2 | email-2
B| SELECT id, payload FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 2 FOR UPDATE SKIP LOCKED;
B|   3 | email-3
B|   4 | email-4
B| SELECT id FROM jobs WHERE id = 1 FOR UPDATE NOWAIT;
B| ERROR:  could not obtain lock on row in relation "jobs"
```

B did not wait: it took jobs 3 and 4. The last line shows `NOWAIT`, which raises an error at once instead of waiting for a locked row. The usual one-statement worker claims a job and marks it running:

```sql
WITH next AS (
  SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET status = 'running' FROM next WHERE jobs.id = next.id
RETURNING jobs.id, jobs.payload;
```

```text
 id | payload 
----+---------
  3 | email-3
(1 row)
```

(Jobs 1 and 2 were already marked done and 3 was next in the queue.) If a worker crashes, its transaction rolls back and the job returns to `queued` automatically, as long as the work happens inside the same transaction. If the work takes minutes, mark the job `running` with a timestamp and have a sweeper requeue stale ones instead of holding a transaction open. `SKIP LOCKED` gives an inconsistent view on purpose, so use it for queues, not for reports.

## Deadlocks

A **deadlock** happens when two transactions take the same locks in opposite order. Here two transfers run at once: A moves money from account 1 to 2, B from 2 to 1.

```text
A| BEGIN;
B| BEGIN;
A| UPDATE accounts SET balance_cents = balance_cents - 100 WHERE id = 1;   -- A locks row 1
B| UPDATE accounts SET balance_cents = balance_cents - 100 WHERE id = 2;   -- B locks row 2
A| UPDATE accounts SET balance_cents = balance_cents + 100 WHERE id = 2;   -- A waits for B
B| UPDATE accounts SET balance_cents = balance_cents + 100 WHERE id = 1;   -- B waits for A: a cycle
A| ERROR:  deadlock detected
A| DETAIL:  Process 18549 waits for ShareLock on transaction 793; blocked by process 18548.
A| Process 18548 waits for ShareLock on transaction 792; blocked by process 18549.
A| HINT:  See server log for query details.
A| CONTEXT:  while updating tuple (0,17) in relation "accounts"
B| UPDATE 1
```

Nobody can proceed, so after `deadlock_timeout` (default **1 second**; I checked `SHOW deadlock_timeout`) PostgreSQL checks for a cycle, picks one victim (here A), and cancels it. B then continued. The error code is `40P01`, and the retry loop above handles it. Two ways to avoid deadlocks:

1. **Always lock in the same order.** For a transfer, lock the lower account id first. I ran this: both sessions did `SELECT id FROM accounts WHERE id IN (1,2) ORDER BY id FOR UPDATE`. B simply waited for A's `COMMIT` and then got both rows. No deadlock.
2. **Keep transactions short** and touch as few rows as possible, so the window is small.

The `DETAIL` shows transaction numbers and process ids. The real statements are in the server log, which is where you look in production.

## Advisory locks, briefly

An **advisory lock** is a lock on a number you choose, with no table or row behind it. PostgreSQL only keeps the book; your code gives it meaning. Use it for "only one instance runs this cron job" or "only one process migrates tenant 42":

```text
A| SELECT pg_try_advisory_lock(42) AS got_it;      -- t
B| SELECT pg_try_advisory_lock(42) AS got_it;      -- f
A| SELECT pg_advisory_unlock(42);                  -- t
B| SELECT pg_try_advisory_lock(42) AS got_it;      -- t
```

The `pg_try_` version returns at once with true or false. There are two lifetimes: **session level** (`pg_advisory_lock`, held until you unlock or the connection ends) and **transaction level** (`pg_advisory_xact_lock`, released at commit or rollback, which I prefer because you cannot forget it). Warning: with a connection pool in transaction mode, session-level locks stick to a connection that is handed to someone else. Use the transaction-level ones.

## Long transactions hurt

An open transaction is cheap to start and expensive to forget. Three costs:

1. **It blocks cleanup (vacuum).** When rows are updated, the old versions stay as dead rows until no transaction could still need them. `VACUUM` removes dead rows, but only those older than the oldest open snapshot. I tested: a table `hot` of 1,000 rows, session A open in `REPEATABLE READ` after one read, then 20 rounds of `UPDATE hot SET n = n + 1` on all rows (autovacuum off for the test). `VACUUM (VERBOSE) hot` said:

```text
tuples: 0 removed, 21000 remain, 20000 are dead but not yet removable
removable cutoff: 799, which was 20 XIDs old when operation ended
```

   Twenty thousand dead rows, none removable, because A's old snapshot might still want them. After A rolled back, the same command said:

```text
tuples: 20000 removed, 1000 remain, 0 are dead but not yet removable
```

   Tables grow (the table was 93 pages for 1,000 live rows), scans slow down, and indexes bloat. In production this is the classic reason a table is "suddenly slow and huge": one forgotten transaction from days ago.
2. **It holds locks.** Locks are released only at the end. An open transaction that wrote a row keeps others waiting on it, and it keeps the `ALTER TABLE` queue problem above alive.
3. **It occupies a connection** from a small pool (lesson 5 and [Backend, Lesson 07](/backend/lesson-7)). A pool of 20 with 20 idle-in-transaction sessions is an outage.

The worst form is `idle in transaction`: the app did `BEGIN`, ran something, then went off to call an HTTP API and left the transaction open. Never do network calls inside a transaction. To find culprits, and to set a safety net:

```sql
SELECT pid, state, now() - xact_start AS xact_age, left(query, 30) AS last_query
FROM pg_stat_activity WHERE xact_start IS NOT NULL AND pid <> pg_backend_pid()
ORDER BY xact_start;
```

```text
  pid  |        state        |    xact_age     | last_query 
-------+---------------------+-----------------+------------
 18909 | idle in transaction | 00:00:03.214152 | SELECT 1;
```

```sql
SET idle_in_transaction_session_timeout = '1s';   -- test value; use something like 30s to a few minutes in real life
```

I tested it: after `BEGIN; SELECT 1;` and two seconds of silence, the next statement got `FATAL: terminating connection due to idle-in-transaction timeout`. Set it per role or database (`ALTER ROLE app SET idle_in_transaction_session_timeout = '60s'`), and also consider `statement_timeout` and `transaction_timeout` (the latter exists in PostgreSQL 17; I read this and did not test it on 16).

## Idempotency and retries from the app

Retries are everywhere: your retry loop, the HTTP client, the load balancer, the user double-clicking "Pay". The network can also lose the answer: the server committed, but the client never heard, so it sends again. If the operation is not **idempotent**, the money moves twice.

The fix is an **idempotency key**: the client generates a unique id for the intent and sends the same id on every retry. The database stores it with a `UNIQUE` constraint, so the second attempt cannot succeed. The first insert and the money move are in one transaction:

```sql
CREATE TABLE payments (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  idempotency_key text NOT NULL UNIQUE,
  from_account    int NOT NULL, to_account int NOT NULL,
  amount_cents    int NOT NULL CHECK (amount_cents > 0),
  created_at      timestamptz NOT NULL DEFAULT now()
);
```

The core of the Node function (full flow: `BEGIN`, insert, two updates, `COMMIT`):

```js
const ins = await c.query(
  `INSERT INTO payments (idempotency_key, from_account, to_account, amount_cents)
   VALUES ($1,$2,$3,$4) ON CONFLICT (idempotency_key) DO NOTHING RETURNING id`,
  [key, from, to, cents]);
if (ins.rowCount === 0) { await c.query('ROLLBACK'); return 'duplicate, nothing done'; }
// ...otherwise move the money in this same transaction, then COMMIT
```

I sent the same request `req-123` twice at the same time, then a third time:

```text
before [{"id":1,"balance_cents":10000},{"id":2,"balance_cents":5000}]
[ 'moved 3000, payment 1', 'duplicate, nothing done' ]
duplicate, nothing done
after  [{"id":1,"balance_cents":7000},{"id":2,"balance_cents":8000}]
```

Three requests, one transfer. The two simultaneous requests were safe too: the second insert waited for the first one's transaction (the unique index makes it wait), then saw the conflict and did nothing. `ON CONFLICT` is explained fully in lesson 7. In a real API you also return the **original response** on a duplicate, so the client sees the same answer. For HTTP-level idempotency and exactly-once ideas see [System Design, Lesson 21](/system-design/lesson-21) and the messaging lessons it links to.

The same thinking applies to the retry loop: anything inside a retried transaction must be safe to run again, so do not send emails or call payment providers there. Write an "outbox" row in the transaction and let a worker send it after the commit.

## Try it

Use the `accounts` table (balances 10,000 and 5,000) and two psql windows.

1. In window A run `BEGIN;` and `SELECT balance_cents FROM accounts WHERE id = 2;`. In window B run `UPDATE accounts SET balance_cents = balance_cents + 100 WHERE id = 2;`. Read again in A. Repeat with `BEGIN ISOLATION LEVEL REPEATABLE READ;`. What differs?
2. In both windows run `BEGIN;` then `SELECT * FROM accounts WHERE id = 1 FOR UPDATE;`. What does the second window do, and how do you make it fail instead of wait?
3. Reproduce a deadlock between two transfers, then change the order of the updates so it cannot happen.
4. Write a transfer that never lets an account go below zero without relying on the `CHECK`: one statement, no `SELECT` first. How does the app know it failed?
5. A teammate says "I set everything to SERIALIZABLE, so we are safe". What do you ask?

**Answers**

1. With Read Committed, the second read in A shows the new balance (the data changed between two reads). With Repeatable Read, A keeps seeing the old balance until it commits or rolls back.
2. The second window hangs on its `SELECT ... FOR UPDATE` until the first commits or rolls back. Use `FOR UPDATE NOWAIT` (error at once) or `SET lock_timeout = '2s'` (error after 2 seconds).
3. Window A: update account 1 then 2. Window B: update 2 then 1, with both sessions open. After about a second one gets `ERROR: deadlock detected`. Fix: both always update the lower id first, or lock both rows first with `ORDER BY id FOR UPDATE`.
4. `UPDATE accounts SET balance_cents = balance_cents - 3000 WHERE id = 1 AND balance_cents >= 3000;` The app checks the affected row count. If it is 0, the balance was too low, so it rolls back the whole transfer. (The idea is from the stock example above; I did not run this exact statement.)
5. "Do you retry on `40001`?" and "what is the throughput under contention?" Serializable gives correct results but raises serialization errors, so without a retry loop the failures reach users, and heavy contention can cause many retries.

## Interview questions

### Q1. What is a transaction, and what does ACID mean in practice? (Must know)

A transaction groups statements so they succeed or fail together. Atomicity: all or nothing, as with my transfer where a crash between two updates would otherwise lose money. Consistency: constraints hold at commit. Isolation: concurrent transactions do not see each other's half-done work, to a degree set by the isolation level. Durability: after `COMMIT` returns, the data survives a crash because the log is flushed. I use autocommit only for single statements.

### Q2. What isolation levels does PostgreSQL have, and what is the default? (Must know)

Read Committed (the default), Repeatable Read and Serializable. Read Uncommitted exists as a name but behaves like Read Committed, so there are no dirty reads. Read Committed takes a new snapshot per statement. Repeatable Read keeps one snapshot for the whole transaction. Serializable adds conflict tracking so results match some one-at-a-time order.

**Follow-up:** Does Repeatable Read allow phantom reads? In PostgreSQL, no, because the snapshot is fixed. The SQL standard would allow them.

### Q3. Show me a non-repeatable read. (Must know)

Under Read Committed, session A selects a balance and sees 10,000. Session B updates and commits. A selects again inside the same transaction and sees 7,500. With Repeatable Read, A would still see 10,000. I reproduced both with two psql windows.

### Q4. What is a lost update, and how do you prevent it? (Must know)

Two transactions read the same value, compute a new one in the app, and write it back; the second write overwrites the first. In my test stock ended at 6 instead of 3. Best fix: do the arithmetic in SQL (`SET stock = stock - 4 WHERE stock >= 4`). Otherwise `SELECT ... FOR UPDATE` to lock the row, or Repeatable Read/Serializable and a retry on `40001`. A version column with optimistic checking also works.

### Q5. What is write skew, and why does Repeatable Read not stop it? (Senior signal)

Two transactions read the same set of rows, each updates a different row based on that read, and together they break a rule, such as the on-call example where both doctors went off. Repeatable Read only detects conflicts on the same row, and here the rows differ. Serializable detects the read/write dependency and cancels one transaction with `40001`. Other fixes are locking all the rows read, or turning the rule into a constraint.

### Q6. Serializable raised an error. What do I do? (Must know)

Retry the whole transaction from `BEGIN`, with a limit and a small random delay. The error `could not serialize access` and its hint say it may succeed on retry. The code inside must be safe to repeat, so no emails or external calls until after the commit. If errors are frequent, I look at contention and shrink the transaction.

### Q7. Explain SELECT ... FOR UPDATE, NOWAIT and SKIP LOCKED. (Senior signal)

`FOR UPDATE` locks the returned rows until the transaction ends, so other writers and lockers wait. `NOWAIT` errors at once if a row is locked. `SKIP LOCKED` leaves locked rows out of the result, which makes a job queue: each worker claims different jobs. In my test two workers got jobs 1-2 and 3-4 without waiting. I use `SKIP LOCKED` for queues only, because the result is deliberately incomplete.

### Q8. How do deadlocks happen and how do you avoid them? (Must know)

Two transactions lock the same rows in opposite order, each waits for the other. PostgreSQL waits `deadlock_timeout` (1 s), detects the cycle and aborts one transaction with `40P01`. I avoid them by locking in a consistent order (for example by id), keeping transactions short, and retrying on `40P01` as a safety net.

### Q9. Why can an ALTER TABLE take a site down even if it is fast? (Trap)

It needs `ACCESS EXCLUSIVE`, which conflicts with every lock, and lock requests queue in order. If one long transaction holds a lock on the table, the `ALTER` waits, and every later query, even a plain `SELECT`, waits behind the `ALTER`. In my test a `SELECT` waited 2.2 s for that reason. The fix is `SET lock_timeout` for migrations, no long transactions, and retrying the migration.

### Q10. Why are long transactions bad for the database? (Senior signal)

They keep an old snapshot, so `VACUUM` cannot remove dead rows newer than it: I saw 20,000 dead rows "not yet removable" until I ended the transaction. Tables and indexes bloat. They also hold locks longer and tie up connections from the pool. `idle in transaction` is the worst case. I set `idle_in_transaction_session_timeout`, never call external services inside a transaction, and monitor `pg_stat_activity` for old `xact_start`.

### Q11. How do you make a payment endpoint safe against retries? (Senior signal)

The client sends an idempotency key. The server inserts it into a table with a `UNIQUE` constraint in the same transaction as the money move, using `ON CONFLICT DO NOTHING`. If the insert affected no row, the request is a duplicate, so I return the stored result and do nothing else. My test sent the same key three times (two at once) and moved the money once. I also never retry non-idempotent work blindly.

### Q12. What is an advisory lock? (Senior signal)

An application-defined lock on a number or a pair of numbers, managed by PostgreSQL but not tied to any table or row. I use `pg_try_advisory_xact_lock` for things like "one instance runs this job". The transaction-level version is released automatically at commit, which is safer than session-level locks, especially behind a transaction-mode connection pool.

### Q13. When would you not use a higher isolation level but a constraint instead? (Trap)

When the rule can be expressed in the schema: a `UNIQUE` index for "one active booking per room", or an exclusion constraint for overlapping time ranges. The database then enforces it for every session, with no retry loop and no dependence on every code path using the right level. Isolation levels are the tool for rules you cannot write as a constraint.

## Key takeaways

- A transaction is all-or-nothing. After any error inside it, you must roll back (or roll back to a savepoint).
- Read Committed (the default) sees new data at every statement. Repeatable Read freezes the view. Serializable also stops write skew, by raising errors you must retry.
- Do arithmetic in SQL (`SET stock = stock - 1 WHERE stock >= 1`), or lock with `FOR UPDATE`, never "read, compute in the app, write".
- Retry the whole transaction on `40001` and `40P01`, with a limit, a short random wait, and no outside side effects inside.
- `SKIP LOCKED` makes a queue. Lock rows in a fixed order to avoid deadlocks.
- `ACCESS EXCLUSIVE` locks queue everything behind them. Use `lock_timeout` for DDL.
- Keep transactions short. Long ones block vacuum, hold locks and eat connections. Set `idle_in_transaction_session_timeout`.
- Use idempotency keys with a `UNIQUE` constraint so retries cannot repeat money moves.
