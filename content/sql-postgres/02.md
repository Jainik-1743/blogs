> **In one line:** an **aggregate** function (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) turns many rows into one value, `GROUP BY` does that once per group, `WHERE` filters rows **before** grouping, and `HAVING` filters groups **after**. Most mistakes come from not knowing the order in which a `SELECT` is evaluated, and from how aggregates treat `NULL`.

Until now every query returned one result row for each input row. A report is different: "how many orders per customer", "revenue per month", "average price per category". You are not listing rows, you are summarising them. That is what this lesson teaches. It uses the shop from [lesson 0](/sql-postgres/lesson-0) and the joins from [lesson 1](/sql-postgres/lesson-1).

> [!note] **What I ran / checked.** Every query below was run on a real **PostgreSQL 16.15** with the exact shop data from lesson 0 (run `setup.sql` for a fresh copy). The result tables are pasted from `psql`. Rows without `ORDER BY` can come back in any order; I always add it when order matters. Two months in the revenue report have the same total (132.40). I checked: that is a real coincidence in the data, not a bug.

## Words used in this lesson

- **An aggregate function** takes many values and returns one: a count, a sum, an average, a minimum, a maximum.
- **A group** is the set of rows that share the same value in the `GROUP BY` columns.
- **`GROUP BY`** splits the rows into groups and runs the aggregates once per group.
- **`HAVING`** is a filter that runs on groups, after the aggregates are computed.
- **`FILTER`** is a condition attached to one aggregate, so it counts or sums only some rows.
- **A grouping set** is one particular way of grouping. `GROUPING SETS`, `ROLLUP` and `CUBE` compute several groupings in one query.
- **`date_trunc`** cuts a date or timestamp down to a unit (day, week, month, year), which makes it a good group key.
- **A report** here just means a query that summarises data.

## Aggregates without GROUP BY

With no `GROUP BY`, all rows form one group, so you get exactly one result row.

```sql
SELECT count(*) AS products, sum(price) AS sum_price, avg(price) AS avg_price,
       min(price) AS cheapest, max(price) AS dearest
FROM products;
```

```text
 products | sum_price |      avg_price      | cheapest | dearest 
----------+-----------+---------------------+----------+---------
        6 |    143.60 | 23.9333333333333333 |     1.20 |   59.00
(1 row)
```

`avg` of a `numeric` column gives a long decimal. Use `round(avg(price), 2)` for display. `min` and `max` also work on text and dates. `sum` of the whole order lines (`quantity * unit_price`) gives total revenue:

```sql
SELECT sum(quantity * unit_price) AS total_revenue FROM order_items;
```

```text
 total_revenue 
---------------
        277.80
```

## COUNT(*) versus COUNT(column), and NULL

This is the most asked aggregate question. Our `customers` table has 6 rows, and Fay has no city:

```sql
SELECT count(*) AS all_rows, count(city) AS cities_known,
       count(DISTINCT city) AS distinct_cities
FROM customers;
```

```text
 all_rows | cities_known | distinct_cities 
----------+--------------+-----------------
        6 |            5 |               3
```

- `count(*)` counts **rows**. It never looks at values.
- `count(city)` counts rows where `city` is **not NULL**.
- `count(DISTINCT city)` counts different non-NULL values: Pune, London, Lagos.

The same rule holds for the other aggregates: **they ignore NULL.** `sum`, `avg`, `min` and `max` skip NULL values, so `avg` is the sum of the non-NULL values divided by their count, not by the row count. If *all* values are NULL, or there are no rows, `sum` and `avg` return NULL, not 0. But `count` returns 0:

```sql
SELECT sum(quantity) FROM order_items WHERE order_id = 999;
SELECT count(*) FROM order_items WHERE order_id = 999;
SELECT coalesce(sum(quantity), 0) FROM order_items WHERE order_id = 999;
```

```text
 sum 
-----
    
(1 row)

 count 
-------
     0
(1 row)

 coalesce 
----------
        0
(1 row)
```

Wrap a `sum` in `coalesce(..., 0)` when you want a number in a report.

## GROUP BY

"How many orders in each status?"

```sql
SELECT status, count(*) AS orders
FROM orders
GROUP BY status
ORDER BY status;
```

```text
  status   | orders 
-----------+--------
 cancelled |      1
 new       |      1
 paid      |      3
 shipped   |      2
(4 rows)
```

How to picture it: the database sorts the 7 order rows into four piles by `status`, then runs `count(*)` on each pile and writes one row per pile.

**The rule:** every column in `SELECT` must be either in `GROUP BY` or inside an aggregate function. Otherwise the database does not know which value of the pile to show:

```sql
SELECT customer_id, status FROM orders GROUP BY customer_id;
```

```text
ERROR:  column "orders.status" must appear in the GROUP BY clause or be used in an aggregate function
```

Customer 1 has three orders with two different statuses. There is no single `status` to print. (One exception: if you group by a table's primary key, PostgreSQL lets you select other columns of that same table, because the key decides them.)

You can group by several columns, by an expression, or by position (`GROUP BY 1`), and `GROUP BY` accepts an output alias (a PostgreSQL extension; `HAVING` does not, as you will see):

```sql
SELECT customer_id AS cust, count(*) AS n
FROM orders GROUP BY cust ORDER BY n DESC, cust;
```

```text
 cust | n 
------+---
    1 | 3
    3 | 2
    2 | 1
    4 | 1
```

### Group by a joined table, and keep the empty groups

Customer names live in `customers`, so join first, then group. To include customers with no orders (Eli, Fay), use a `LEFT JOIN`, and count a column from the **right** table:

```sql
SELECT c.name, count(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY c.id;
```

```text
 name | orders 
------+--------
 Asha |      3
 Ben  |      1
 Chen |      2
 Dara |      1
 Eli  |      0
 Fay  |      0
(6 rows)
```

`count(o.id)` skips the NULL that the left join made for Eli and Fay, so they get 0. With `count(*)` they would get **1**, because the row exists even though it holds no order. Group by `c.id` as well as `c.name`, because two customers could share a name.

> [!warn] **`count(*)` after a `LEFT JOIN` counts the empty row.** Count a column from the right table instead. I ran `count(*)` here and Eli and Fay both showed 1.

## WHERE versus HAVING

- `WHERE` filters **rows**, before grouping. It cannot use aggregates.
- `HAVING` filters **groups**, after grouping. It is where you use aggregates.

```sql
SELECT status, count(*) FROM orders WHERE count(*) > 1 GROUP BY status;
```

```text
ERROR:  aggregate functions are not allowed in WHERE
```

The row filter does not know the group size yet. Use `HAVING` for that. Customers with at least two orders:

```sql
SELECT customer_id, count(*) AS n
FROM orders
GROUP BY customer_id
HAVING count(*) >= 2
ORDER BY customer_id;
```

```text
 customer_id | n 
-------------+---
           1 | 3
           3 | 2
```

You can use both in one query. Here `WHERE` first removes cancelled orders, then `HAVING` keeps customers with at least two of the rest:

```sql
SELECT customer_id, count(*) AS n
FROM orders
WHERE status <> 'cancelled'
GROUP BY customer_id
HAVING count(*) >= 2;
```

```text
 customer_id | n 
-------------+---
           1 | 3
```

Chen dropped out: of Chen's two orders, one was cancelled. **Rule of thumb:** if a condition does not need an aggregate, put it in `WHERE`. It is cleaner and lets the database throw rows away early. Also, `HAVING` cannot use an output alias: `HAVING n >= 2` fails with `column "n" does not exist`. Repeat the expression.

## FILTER: many counts in one pass

Often you want several conditional counts side by side. `FILTER (WHERE ...)` applies a condition to one aggregate:

```sql
SELECT customer_id,
       count(*)                                  AS orders,
       count(*) FILTER (WHERE status = 'paid')      AS paid,
       count(*) FILTER (WHERE status = 'cancelled') AS cancelled
FROM orders
GROUP BY customer_id
ORDER BY customer_id;
```

```text
 customer_id | orders | paid | cancelled 
-------------+--------+------+-----------
           1 |      3 |    2 |         0
           2 |      1 |    1 |         0
           3 |      2 |    0 |         1
           4 |      1 |    0 |         0
```

One pass over the table gives three numbers per customer. `FILTER` is standard SQL and PostgreSQL has had it since 9.4. The older way, `sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END)`, does the same and works everywhere. `FILTER` also gives a share: `count(*) FILTER (WHERE status = 'paid')::numeric / count(*)` gave `0.4285...` (3 of 7).

## DISTINCT inside aggregates

`count(DISTINCT x)` counts different values. It answers "how many different customers ordered" and not "how many orders":

```sql
SELECT count(DISTINCT customer_id) AS buyers, count(customer_id) AS orders FROM orders;
```

```text
 buyers | orders 
--------+--------
      4 |      7
```

It also fixes the join fan-out problem from lesson 1. If you join customers to orders to order lines, `count(*)` counts lines, not orders:

```sql
SELECT c.name, count(*) AS rows_joined, count(DISTINCT o.id) AS orders
FROM customers c
JOIN orders o ON o.customer_id = c.id
JOIN order_items oi ON oi.order_id = o.id
GROUP BY c.name ORDER BY c.name;
```

```text
 name | rows_joined | orders 
------+-------------+--------
 Asha |           6 |      3
 Ben  |           2 |      1
 Chen |           3 |      2
 Dara |           1 |      1
```

> [!warn] **`sum(DISTINCT x)` and `avg(DISTINCT x)` are almost never what you want.** They remove repeated *values*, not repeated rows. `avg` of 10, 10, 40 is 20, but `avg(DISTINCT ...)` gives 25. Two different order lines with the same quantity would count once. If a join multiplied your rows, fix the join (aggregate first), do not hide it with `DISTINCT`.

Other handy aggregates: `string_agg(name, ', ' ORDER BY name)` joins text (the Pune customers gave `Asha, Chen`), `array_agg(id ORDER BY id)` collects values into an array (`{1,3}`), and `bool_or`, `bool_and` work on booleans.

## Reports: revenue per category and per month

Revenue per category joins the order lines to products:

```sql
SELECT p.category, sum(oi.quantity * oi.unit_price) AS revenue
FROM order_items oi
JOIN products p ON p.id = oi.product_id
GROUP BY p.category
ORDER BY revenue DESC;
```

```text
  category  | revenue 
------------+---------
 audio      |  118.00
 bags       |   90.00
 stationery |   44.90
 home       |   24.90
```

(Gift card sold nothing, so its category does not appear. An inner join drops empty groups.) For time reports use `date_trunc`, which rounds a timestamp down to the start of a unit:

```sql
SELECT date_trunc('week', timestamp '2025-03-15 20:10') AS week_start,
       date_trunc('month', timestamp '2025-03-15 20:10') AS month_start;
```

```text
     week_start      |     month_start     
---------------------+---------------------
 2025-03-10 00:00:00 | 2025-03-01 00:00:00
```

(Weeks start on Monday, and 10 March 2025 is a Monday.) Group by it for a monthly report. Because each order has several lines, count the order id with `DISTINCT`:

```sql
SELECT date_trunc('month', o.ordered_at)::date AS month,
       count(DISTINCT o.id)                    AS orders,
       sum(oi.quantity * oi.unit_price)        AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY 1
ORDER BY 1;
```

```text
   month    | orders | revenue 
------------+--------+---------
 2025-01-01 |      1 |   13.00
 2025-02-01 |      3 |  132.40
 2025-03-01 |      3 |  132.40
```

`GROUP BY 1` means "the first column of the select list". `::date` casts the month to a plain date for cleaner output. A month with no orders is simply missing. To show it as zero, generate the months and left join:

```sql
SELECT gs::date AS month, coalesce(x.n, 0) AS orders
FROM generate_series('2025-01-01'::date, '2025-04-01'::date, interval '1 month') gs
LEFT JOIN (SELECT date_trunc('month', ordered_at) AS m, count(*) AS n
           FROM orders GROUP BY 1) x ON x.m = gs
ORDER BY 1;
```

```text
   month    | orders 
------------+--------
 2025-01-01 |      1
 2025-02-01 |      3
 2025-03-01 |      3
 2025-04-01 |      0
```

> [!note] With `timestamptz` columns, `date_trunc` uses the session time zone to decide where midnight is. Two people in different zones can get different monthly totals. Pick one zone for reports, for example `date_trunc('month', ts AT TIME ZONE 'UTC')`.

## GROUPING SETS and ROLLUP, briefly

A report often needs details **and** subtotals **and** a grand total. Instead of three queries and a `UNION`, ask for several groupings at once. `ROLLUP (a, b)` gives the groups `(a, b)`, `(a)` and `()`, i.e. detail, subtotal per `a`, and the grand total:

```sql
SELECT p.category, p.name, sum(oi.quantity) AS units
FROM order_items oi
JOIN products p ON p.id = oi.product_id
GROUP BY ROLLUP (p.category, p.name)
ORDER BY p.category NULLS LAST, p.name NULLS LAST;
```

```text
  category  |    name    | units 
------------+------------+-------
 audio      | Headphones |     2
 audio      |            |     2
 bags       | Backpack   |     2
 bags       |            |     2
 home       | Desk lamp  |     1
 home       |            |     1
 stationery | Notebook   |     7
 stationery | Pen        |    17
 stationery |            |    24
            |            |    29
(10 rows)
```

The row `stationery | (blank) | 24` is the subtotal for the category, and the last row is the grand total (29 units). The blanks are NULLs made by the rollup. The same result comes from `GROUP BY GROUPING SETS ((p.category, p.name), (p.category), ())`, which lets you pick any combinations. `CUBE (a, b)` gives all four combinations. If your data has real NULLs in a group column, use the `grouping()` function to tell "subtotal NULL" from "real NULL": `grouping(p.category, p.name)` returned 0 on detail rows, 1 on a category subtotal and 3 on the grand total.

## Order of evaluation of a SELECT

You write `SELECT` first, but the database does not run it first. The logical order is:

```text
1. FROM / JOIN      build the rows (apply ON)
2. WHERE            keep rows
3. GROUP BY         make groups
4. aggregates       compute count, sum, ...
5. HAVING           keep groups
6. SELECT           compute the output columns (and their aliases)
7. DISTINCT         remove duplicate output rows
8. ORDER BY         sort
9. LIMIT / OFFSET   cut
```

(This is the logical order. The planner may run things in another order if the result is the same.) It explains most of the errors in this lesson:

- `WHERE count(*) > 1` fails because aggregates (step 4) do not exist yet at `WHERE` (step 2).
- `HAVING n >= 2` fails because the alias `n` is created in step 6, after `HAVING`.
- `ORDER BY n DESC` works because sorting (step 8) happens after `SELECT`. `GROUP BY cust` works because PostgreSQL makes a special exception for output aliases there.
- `LIMIT` cuts after sorting, which is why "top 3" needs `ORDER BY` first.

## Common mistakes

1. `count(*)` after a `LEFT JOIN` when you mean "count the matches".
2. Counting or summing after a join that multiplied rows. Use `count(DISTINCT o.id)` or aggregate first.
3. Using `HAVING` for a plain row filter that belongs in `WHERE`.
4. Forgetting that `sum` and `avg` return NULL for no rows.
5. Grouping by a name instead of a key, so two people with the same name are merged.
6. `avg` of integers expecting a rounded integer. `avg` returns a `numeric`; cast or round as you need.

## Try it

1. Total quantity sold per product, with the product name, biggest first.
2. How many customers have a city, how many do not, and how many different cities are there? (One query.)
3. Customers who spent more than 50 in total on non-cancelled orders.
4. For each order status, the number of orders and the average order total. (Hint: total per order first, in a subquery.)
5. Number of orders per month, with a column for how many were `paid`.

**Answers**

1. `SELECT p.name, sum(oi.quantity) AS units FROM order_items oi JOIN products p ON p.id = oi.product_id GROUP BY p.name ORDER BY units DESC;` gives Pen 17, Notebook 7, Backpack 2, Headphones 2, Desk lamp 1.
2. `SELECT count(city) AS with_city, count(*) - count(city) AS without_city, count(DISTINCT city) AS cities FROM customers;` gives 5, 1, 3.
3. Same shape as the `HAVING` example above, with `> 50`: it gives customer 1 with 178.40 (Asha). Customers 2 and 3 have 48.50 and 22.50.
4. `SELECT o.status, count(*) AS orders, round(avg(t.total), 2) AS avg_total FROM orders o JOIN (SELECT order_id, sum(quantity * unit_price) AS total FROM order_items GROUP BY order_id) t ON t.order_id = o.id GROUP BY o.status;` Summing in the subquery first avoids the fan-out.
5. `SELECT date_trunc('month', ordered_at)::date AS month, count(*) AS orders, count(*) FILTER (WHERE status = 'paid') AS paid FROM orders GROUP BY 1 ORDER BY 1;` gives January 1 and 1, February 3 and 1, March 3 and 1.

## Interview questions

### Q1. What is the difference between `COUNT(*)`, `COUNT(col)` and `COUNT(DISTINCT col)`? (must know)

`count(*)` counts rows. `count(col)` counts rows where col is not NULL. `count(DISTINCT col)` counts different non-NULL values. In our customers table that was 6, 5 and 3 for the city column.

### Q2. What is the difference between `WHERE` and `HAVING`? (must know)

`WHERE` filters rows before grouping and cannot use aggregates. `HAVING` filters groups after the aggregates are computed. If the condition does not need an aggregate, I put it in `WHERE`, so fewer rows reach the grouping step.

### Q3. Why does `SELECT customer_id, status FROM orders GROUP BY customer_id` fail? (must know)

Each group has many different `status` values, and the query does not say which to show. Every selected column must be in `GROUP BY` or inside an aggregate. I can add `status` to the `GROUP BY`, or aggregate it, for example `max(status)` or `string_agg`.

### Q4. How do aggregates treat NULL? (trap)

They ignore NULLs, except `count(*)`. `avg` divides by the number of non-NULL values. With no rows or only NULLs, `sum` and `avg` return NULL while `count` returns 0. I use `coalesce(sum(x), 0)` when I need a number.

### Q5. I want every customer with their order count, including customers with none. How? (must know)

`customers LEFT JOIN orders`, then `GROUP BY c.id`, and `count(o.id)`. I count a column of the right table because `count(*)` would count the NULL-filled row as 1.

### Q6. A revenue report doubled after joining a table. Why, and how do you fix it? (how would you debug)

A one-to-many join repeated rows, so values from the "one" side were summed more than once. I compare row counts before and after the join. The fix is to aggregate the many side in a subquery or CTE and join the result, or to sum only columns from the many side. `DISTINCT` inside `sum` is not a safe fix.

### Q7. What does `FILTER` do, and when do you use it? (senior signal)

`FILTER (WHERE ...)` limits one aggregate to some rows, so I can compute several conditional counts or sums in one pass over the table, such as paid, cancelled and total orders per customer. It is easier to read than `sum(CASE WHEN ...)`.

### Q8. Explain the logical order of a SELECT. Why can't `HAVING` use a column alias? (senior signal)

FROM and JOIN, then WHERE, GROUP BY, aggregates, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT. The alias is created in the SELECT step, which comes after HAVING, so HAVING cannot see it, but ORDER BY can. PostgreSQL allows aliases in GROUP BY as an extension.

### Q9. How would you build a monthly report that also shows months with no sales? (senior signal)

Aggregate with `date_trunc('month', ts)`, then `LEFT JOIN` that result onto `generate_series` of months, and use `coalesce(n, 0)`. A plain `GROUP BY` only creates groups for months that have rows. I also fix the time zone for the truncation, so the totals do not depend on where the query runs.

### Q10. What are `ROLLUP` and `GROUPING SETS`? (senior signal)

They compute several groupings in one query: `ROLLUP (a, b)` returns detail rows, a subtotal per `a`, and a grand total. `GROUPING SETS` lets me list the exact combinations. The subtotal rows show NULL in the rolled-up columns, so I use `grouping()` to tell them apart from real NULLs.

## Key takeaways

- Aggregates turn many rows into one value. They ignore NULL, except `count(*)`.
- `GROUP BY` makes groups. Every selected column must be grouped or aggregated.
- `WHERE` filters rows before grouping; `HAVING` filters groups after.
- After a `LEFT JOIN`, count a right-table column, not `*`. After a one-to-many join, beware of double counting.
- `FILTER` gives conditional aggregates in one pass; `date_trunc` makes time groups; `ROLLUP` adds subtotals.
- Know the evaluation order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.
