> **In one line:** "sales rank by category" means showing the best-selling products in each category for a time window (say the last 7 days). Sales are written once and read about 100 times more, so the design splits into a **write path** (a sales event stream and a windowed aggregation) and a **read path** (a precomputed top-N list per category in a **Redis sorted set**), with a clear choice about how fresh the list must be and what that freshness costs.

This is lesson 9 of **System Design Case Studies, Part 2**. Lesson 5 ([trending topics and top-K](/design-cases/lesson-5)) ranked items in a huge stream and accepted approximate counts. This case is the calmer sibling: the data is smaller and **exact**, because a sales number is money and units, and a seller will check it. Lesson 10 ([Mint-style data pipeline](/design-cases/lesson-10)) covers the event pipeline that feeds a system like this, and Lesson 11 ([scaling on AWS](/design-cases/lesson-11)) covers where such a service would run. The problem comes from the [system-design-primer](https://github.com/donnemartin/system-design-primer) (folder `solutions/system_design/sales_rank`).

> [!note] **What I ran / checked.** I wrote four TypeScript files and ran them on Node 22.22.0 (type stripping, no build step): `sortedset.ts` (a small in-memory sorted set with Redis-style `ZINCRBY`, `ZREM`, `ZREVRANGE`, `ZREVRANK`), `ranker.ts` (hourly buckets, one sorted set per category, a sliding window, duplicate and late-event handling, and a slow "batch" recompute used as a check), `ranker.test.ts` (7 tests with `node:test`), and two demo scripts. All outputs below are real. The sales data is **made up** (random generator with a fixed seed, skewed on purpose), so the numbers show behaviour, not any real shop. Timings are from this one sandbox machine, in one process, with no network. I did **not** run a real Redis; my sorted set follows the Redis behaviour I know (score then member order, `ZREVRANGE`), but the real server uses a different structure (a skip list), and Redis memory per member in section 2 is an **assumption**. I read the primer's `sales_rank` README (it uses MapReduce over log files, an hourly refresh, and a SQL table); I did not run its code (`mrjob`).

## Words used in this lesson

- **Sale event** is one record: time, product, category, quantity, price. We only need a few fields to rank.
- **Window** is the time range we count in. "Last 7 days" is a **sliding window**: it moves forward with time.
- **Bucket** is a small slice of time (here one hour) with its own counts. A window is the sum of its buckets. When a bucket falls out of the window we subtract it.
- **Aggregation** means combining many records into one number, here "units sold per product per category".
- **Sorted set** (Redis `ZSET`) is a collection of unique members, each with a numeric **score**, kept ordered by score. We use the product as the member and units sold as the score.
- **ZINCRBY** adds to a member's score. **ZREVRANGE** reads members from the highest score down. **ZREVRANK** returns a member's position from the top (0 is first).
- **Top-N** is the N best items, for example the top 100.
- **Write path / read path** are the two halves of the system: how data gets in, and how it gets out.
- **Hot category** is a category that gets a large share of all traffic (for example "Electronics" on a sale day).
- **Backfill** means rebuilding results from the raw history, for example after a bug or a new ranking rule.
- **Idempotent** means doing the same operation twice has the same effect as once. We need it because event streams deliver some events twice.
- **Late event** is an event that arrives after its time slice has already been counted.

## 1. Requirements

**Functional**

- A user opens a category page and sees the **top N products** by units sold (or revenue) for a window: last day, last 7 days, last 30 days.
- A product page can show "rank #12 in Toys". That is a **rank lookup**.
- A product may belong to **more than one category**. A product does not change category (the primer's assumption).
- Results are refreshed about **every hour** at least; popular categories could be fresher.

**Non-functional**

- **Read heavy**: the primer assumes 100 reads for each write.
- **Fast reads**: single-digit milliseconds, from a cache or an in-memory store.
- **Highly available** reads: a slightly old list is better than an error page.
- **Accurate**: counts are exact (no sampling), and a sale is never counted twice.
- **Cheap**: do not recompute the whole world every time a sale arrives.

**Out of scope here**: the rest of the shop (cart, payments, search), personalised ranking, and sub-categories (the primer also skips them).

## 2. Back-of-envelope numbers

The first block uses the primer's assumptions. The second block is mine; every number is an **assumption**.

```text
Products                    10 million
Categories                  1,000
Sales transactions          1 billion / month  = 1e9 / 2.5e6 s = ~400 sales/s on average
Reads                       100 billion / month = ~40,000 reads/s on average (100:1)
Sale record                 ~40 bytes -> 40 GB per month of raw sales, ~1.4 TB in 3 years

My assumptions
Peak                        5x average: ~2,000 sales/s, ~200,000 reads/s
Each product in             ~2 categories on average -> ~4,000 category-updates/s at peak
Window                      7 days = 168 hourly buckets
Sorted-set size             10M products x 2 categories = 20M members per window
Redis memory per member     ~64 bytes (guess; check with MEMORY USAGE) -> 20M x 64 B = ~1.3 GB per window
3 windows (1d, 7d, 30d)     ~4 GB total; fits in one big node or a few small ones
```

What this shows:

- **Writes are small.** 400 sales per second is a modest stream. Even 2,000 per second is easy for one stream partition.
- **Reads are the load.** 40,000 to 200,000 reads per second means the read path must be a lookup in memory, not a query on sales data.
- **The ranked state fits in memory.** A few GB for all the windows. We do not need an expensive big-data job just to hold the answer.
- A list of the **top 100 per category** is tiny: 1,000 categories x 100 entries x ~50 bytes = 5 MB. We can cache that on every API server.

## 3. API

```http
GET /v1/categories/{categoryId}/top?window=7d&limit=50&offset=0
-> 200 OK
{ "category": "toys", "window": "7d", "asOf": "2026-10-11T10:00:00Z",
  "items": [ { "rank": 1, "productId": "p0", "units": 3884 },
             { "rank": 2, "productId": "p15", "units": 498 }, ... ] }

GET /v1/products/{productId}/rank?category=toys&window=7d
-> 200 OK   { "category": "toys", "window": "7d", "rank": 12, "units": 211 }

# Internal: the sales service publishes events (not HTTP, usually a stream)
{ "id": "ord-91-line-2", "ts": 1760000000, "productId": "p15", "categories": ["toys", "gifts"], "qty": 2 }
```

Notes:

- `asOf` tells the reader how fresh the list is. Honest and cheap.
- The event has a unique `id` (an order line id). It is what makes counting **idempotent** (section 6.5).
- Pagination: top 50 comes from one `ZREVRANGE`. Deep pages (rank 5,000) are rare; cap the depth.

## 4. Data model

```text
Raw sales (object store, e.g. Parquet files by day, or a table partitioned by day)
    event id | ts | product id | category ids | qty | price | ...        <- the source of truth, kept for backfill

Stream (Kafka-style)   topic "sales", partitioned by product id        <- same product -> same partition

Aggregator state (memory + checkpoint)
    hourly buckets:  hour -> category -> product -> units               <- so an hour can be subtracted later
    seen event ids per hour                                              <- dedupe

Serving store (Redis)
    key  rank:{category}:{window}     type ZSET   member = product id   score = units in the window
    optional  top:{category}:{window} type STRING a JSON blob of the top 100 (for a CDN or app cache)

Product catalogue (SQL)   product id -> name, image, price     <- joined by the API when it builds the page
```

Why the sorted set is the right structure: one `ZREVRANGE rank:toys:7d 0 49` gives the top 50, one `ZREVRANK` gives a product's position, and `ZINCRBY` updates a score and moves the member in `O(log n)`. A SQL `GROUP BY` plus `ORDER BY` would have to scan and sort.

## 5. High-level architecture

```text
 Sales service ---> Stream "sales" (partition by product id) ---> Aggregator workers (stateful)
 (orders)                  |                                        1. dedupe by event id
                           |                                        2. add to hourly bucket (hour, category, product)
                           v                                        3. every few seconds: apply the batch as ZINCRBY
                  Raw sales archive                                 4. every hour: subtract buckets that left the window
                  (object store, Parquet)                                         |
                           |                                                      v
                           |                                          Redis ZSET  rank:{category}:{window}
                           v                                                      |
                  Backfill / batch job  ------ rebuilds the ZSETs --------------->+
                  (replay raw sales)                                              |
                                                                                  v
 Users ---> CDN / API cache (5-60 s) ---> Rank API (reads ZREVRANGE / ZREVRANK) --+
                                              + product details from catalogue
```

Two paths, kept apart on purpose:

- **Write path**: events flow in one direction through the stream and the aggregator. Nothing here is on a user's page load.
- **Read path**: the API reads a ready-made sorted set. The cost of a read does not depend on how many sales happened.

## 6. Deep dives

### 6.1 Two ways to build the ranking: batch and incremental

| | Batch (the primer's approach) | Incremental (stream) |
|---|---|---|
| How | Every hour, a job reads the last 7 days of sales, groups by (category, product), sums, sorts, writes a table | Each sale (or small batch) adds to a counter; hours that leave the window are subtracted |
| Freshness | As old as the last job (an hour or more) | Seconds |
| Cost | Reads 7 days of data every run (all of it, every hour) | Touches only the new sales and the expired hour |
| Complexity | Low: one job, easy to reason about | Higher: state, dedupe, late events, a clock |
| Correctness check | It is the definition of "correct" | Must be compared against the batch result |

The primer uses MapReduce: step 1 maps each log line to `(category, product) -> quantity` and reduces by sum, step 2 sorts, and the output goes into a `sales_rank` SQL table that a Rank API reads. That is a good first answer and fits the "update hourly" requirement.

In an interview I would say: **start with the hourly batch**, because it is simple and the requirement allows it. Then say the incremental path as the improvement for freshness and for cost, **and keep the batch job anyway** as the backfill and as the checker. This lesson's code builds the incremental version and uses the batch version to prove it right.

### 6.2 The sorted set

I wrote a small sorted set (`sortedset.ts`) with the same behaviour as the Redis commands we need: order by score, ties broken by member, `ZREVRANGE` walks from the top. Real Redis uses a skip list plus a hash table. Mine uses a sorted array plus a map, which is simpler and fine to show the idea (insert is `O(n)` in the array, where Redis is `O(log n)`).

```ts
export class SortedSet {
  private score = new Map<string, number>();
  private arr: Array<[number, string]> = [];            // ascending by (score, member)
  zincrby(member: string, delta: number): number {
    const next = (this.score.get(member) ?? 0) + delta;
    if (next <= 0) { this.zrem(member); return 0; }       // sales never stay at zero or below
    this.zadd(member, next);
    return next;
  }
  zrevrange(start: number, stop: number)  // highest score first
  zrevrank(member: string)                // position from the top, 0 = best
}
```

Test 1 checks the ordering rules: after increments the order is `b 9, a 6, c 5`, `zrevrank("c")` is 2, a member whose score returns to zero is removed, and two members with the same score come out in reverse member order (Redis returns equal scores in lexical order, so `ZREVRANGE` gives the reverse). **Ties** matter in a ranking page: decide a rule (here by member id) so that the list does not shuffle between refreshes.

### 6.3 The write path: windowed aggregation

The aggregator (`ranker.ts`) keeps two things:

1. **Hourly buckets**: `hour -> category -> product -> units`. These are the pieces of the window.
2. **One sorted set per category** holding the sum over the buckets still in the window.

```ts
// A batch of sales arrives
for (const s of sales) {
  const h = Math.floor(s.ts / 3600);
  if (h > this.nowHour) { flush(); this.advance(h); }     // time moves forward with the data
  if (!this.inWindow(h)) { this.dropped.tooOld++; continue; }
  if (seenInThisHour.has(s.id)) { this.dropped.duplicate++; continue; }
  for (const c of s.categories) { bucket[h][c][s.product] += s.qty; delta[c][s.product] += s.qty; }
}
flush();    // ONE zincrby per (category, product) in this batch

// When the clock moves to hour H, every bucket at or before H - 168 leaves the window:
for each expired bucket: zincrby(product, -units) for each (category, product); delete the bucket
```

The sliding window is therefore "add the new, subtract the expired". It is the same idea as the ring of buckets in [Lesson 5](/design-cases/lesson-5), with exact counters instead of sketches. A sale is touched twice in its life: once when it arrives and once when its hour leaves the window.

**A bug I hit, and what it taught me.** My first version of `applyBatch` collected the changes for the whole batch and wrote them to the sorted sets at the end. When one batch contained events that moved the clock forward by many hours, the old buckets were subtracted **before** the changes from those old hours were written. The sorted sets then ended up with sales that should have expired. Test 7 (the backfill test) failed. The fix is the `flush()` call right before `advance()`: apply pending changes first, then expire old hours. The rule: **in a windowed aggregator, the order of "add" and "expire" matters, and a test against a plain recompute finds this class of bug fast.**

### 6.4 Is the incremental result correct?

Never trust incremental state without a check. `batchTop()` is the simple version: scan all raw events, keep the ones inside the window and in the category, sum, sort. I ran this demo (`demo2.ts`): 200,000 sales over 14 days, 50 categories (40% of sales in one hot category, `cat0`), 20,000 products with a skewed popularity, 20% of sales in two categories, a 7-day window, applied in batches of 1,000.

```text
sales: 200000 over 14 days; window 7 days; now hour 335 dropped {"tooOld":0,"duplicate":0}
cat0 (hot) top 5: [["p0",3884],["p15",498],["p17",460],["p1",457],["p12",405]]
cat7 top 3     : [["p0",184],["p9439",138],["p8541",138]]
all 50 categories: incremental top-10 equals batch recompute? true
ZSET members: cat0 778 | median category 34 | total 2427
```

All 50 top-10 lists matched the recompute exactly (same products, same units, same order). `p0` appears in both lists because the data has many sales for product `p0` and it sits in several categories. Note `cat7`'s second and third place both have 138 units: a tie, resolved by member order, the same on both sides.

The tests (`ranker.test.ts`, run with `node --test ranker.test.ts`):

```text

ok 2 - top-N per category, a product can be in two categories
ok 3 - window slides: old hours are subtracted
ok 4 - duplicates are ignored, sales older than the window are dropped
ok 5 - a late sale that is still inside the window is counted

```

### 6.5 Duplicates, late events and exactness

Streams usually give **at-least-once** delivery: after a crash or a retry an event can arrive twice. If every event is added to a counter twice, the rank is wrong and nobody notices. So the aggregator keeps the set of event ids it has seen **per hour bucket** and drops repeats (test 4). When an hour leaves the window its id set is deleted too, so memory stays bounded. For very high volume you can keep the ids in a shared store with an expiry, or let the stream give exactly-once effects through transactions (more complex).

**Late events.** A sale can arrive hours after it happened (a phone was offline, a queue was backed up). Because we bucket by **event time**, a late sale simply goes into its old hour's bucket and is added to the sorted set (test 5, 10 hours late). It will also be subtracted when that hour expires, which is correct. A sale older than the whole window is dropped and counted (`dropped.tooOld`) so you can see how often it happens. If the rank must include very late sales, that is a case for the backfill path.

**Returns and cancellations.** A refund is a negative sale event. It can use the same path (a negative `qty`). My code removes a member whose score drops to zero; a real design must also decide whether a return after the window counts. I did not implement this.

### 6.6 Freshness versus cost

How often should the sorted set change? Every sale, or every few seconds? Each `ZINCRBY` is a write to Redis. **Coalescing**, adding up the sales for the same (category, product) in a short batch and writing once, cuts the writes. I measured it two ways.

The ordinary mixed workload above (200,000 sales over 14 days) counting how many sorted-set writes (including the expiry subtractions) each batch size caused:

```text
batch size     1: ZSET writes 352660
batch size   100: ZSET writes 349861
batch size  5000: ZSET writes 344434
```

Barely any saving: 2.3% at the largest batch. In this data the sales in one batch mostly belong to different products, so there is little to add together. Honest result: **batching does not always help**.

A **flash sale** is different: 100,000 sales in one hour, all in one category, spread over 20 products (`flash.ts`):

```text
batch     1 sales: ZSET writes 100000
batch  1000 sales: ZSET writes 2000
batch 10000 sales: ZSET writes 200
```

Here batching cuts writes by 50 times with batches of 1,000 and by 500 times with batches of 10,000, because the same 20 products repeat in every batch. The cost of waiting is freshness: a batch window of a few seconds means the list is a few seconds old.

What freshness do you need? The primer says hourly is acceptable. A useful way to think about it:

| Refresh | Cost | Fits |
|---|---|---|
| Hourly batch | Lowest write load, reads all raw data each run | The stated requirement; most categories |
| Every 1 to 5 minutes (micro-batch) | Few writes, small state | Big categories; "best sellers right now" |
| Per sale | Many writes, a hot sorted set | Rarely worth it; the human cannot tell |
| Read-time cache of 5 to 60 s | Free | Always add on top, in the API or CDN ([Lesson 4](/design-cases/lesson-4)) |

Nobody sees a difference between "updated 3 seconds ago" and "updated 30 seconds ago" on a best-sellers page. Spend freshness only where users notice it (a flash sale page).

### 6.7 Hot categories

Traffic is not even (a primer assumption). In my data, `cat0` gets 40% of sales. Three different things get hot, and each has a different fix:

| What is hot | Symptom | Fix |
|---|---|---|
| **Writes to one sorted set** | One Redis key takes a large share of `ZINCRBY` | Coalesce in micro-batches (6.6); shard the key by product hash into `rank:cat0:7d:{0..3}` and merge the top lists on read (a product is always in one shard, so merging the shards' top-N lists is exact, as in [Lesson 5](/design-cases/lesson-5), 6.4) |
| **Reads of one key** | 100,000 reads per second hit the same sorted set | Cache the top-100 JSON in the API process for a few seconds, and on the CDN; add read replicas |
| **One product** with huge sales | One member updated constantly | Coalescing again; the cost per update is `O(log n)`, so one member is rarely the real problem |

My numbers show the shape of it: for the hot category the sorted set had only 778 members while the median category had 34, but the hot category got a large share of the **writes**. Size is not the issue; update rate is. Redis can do very many simple operations per second on one core, but one key lives on one node (in a cluster), so one key cannot be spread without splitting it yourself.

Reading cost, for scale: in my process, a top-10 read from the in-memory sorted set took about 0.25 microseconds. That is a local array slice and says nothing about the network, serialisation or a real Redis. The point is only that the work is a lookup, not a computation.

### 6.8 The read path and capacity

- The Rank API calls `ZREVRANGE rank:{category}:{window} 0 N-1` and joins product names and images from the catalogue (cache these too).
- Top-100 per (category, window) as one JSON string in Redis or in an API process cache. 1,000 categories x 3 windows x ~5 KB = ~15 MB. Everything that is read a lot fits in memory on every API server. (Assumed sizes.)
- For `rank` of one product, `ZREVRANK` is `O(log n)`. For products that are not in the sorted set, the answer is "unranked", not an error.
- Reads must survive a Redis failure: keep the last top-100 blobs in the API process or a second store, and serve them with the `asOf` time. A stale list is better than a 500.

**Memory trimming.** Do we need the whole sorted set of 20 million members, or only the top 1,000 per category? Keeping all is simple and lets you answer "rank of any product" and lets expiry subtract exactly. Keeping only the top K saves memory, but then a product just below the cut cannot move up when the products above it expire (you do not know its score). The usual compromise is: keep the full set for the exact window, **or** keep a bounded list and rebuild it from buckets every so often. I kept the full sets; I did not test the bounded variant.

### 6.9 Backfill and fixing mistakes

Sooner or later you must rebuild: a bug in the aggregator, a new rule (exclude returned items), a new category tree, or a lost Redis. This is why the **raw sales are kept** in cheap storage and why the batch job exists.

```text
Backfill procedure
1. Replay raw sales for the window into a NEW sorted set key (rank:cat:7d:v2). Never write over the live key.
2. When it has caught up, compare it with the live one (sample categories, check top-N equality).
3. Switch the API to the new key (a version number in the key name or in a config value).
4. Delete the old key after a safe period.
```

Test 7 does the small version: it builds a ranker from a stream in small batches, builds a second one by applying **all** events in one go, and checks that the top-10 is identical. In the demo:

```text
batch recompute for ONE category: 21.5 ms
backfill all 200k raw events into a fresh ranker: 762 ms; same cat0 top-10? true
```

200,000 raw sales rebuilt every category's sorted set in 0.76 seconds in one process. The real archive is 1 billion sales a month, about 5,000 times larger than my demo; I would scale the backfill by partitioning the replay by product and merging, which works because a product's total is a sum. (This is arithmetic, not a measurement.)

### 6.10 Rank queries and products in more than one category

A product in two categories simply gets an update in each category's sorted set (my events carry a list of categories, and test 2 covers it). If categories can change, or a product is added to a category later, you must rebuild that product's contribution from the raw data. The primer says items do not change categories, which avoids this. I would ask the interviewer before assuming it.

If you need an "all products" ranking, either keep one more sorted set (`rank:all:7d`) updated for every sale, or compute it on a schedule. It is one more write per sale. Do not add it for free; it is a hot key.

## 7. Failure modes and trade-offs

| Problem | Effect | Handling |
|---|---|---|
| Aggregator crashes | In-memory buckets lost | Checkpoint the buckets with the stream offset; replay from the offset (dedupe protects against double counting) |
| Duplicate events | Sales counted twice | Event ids per hour bucket (tested) or idempotent writes |
| Late events | Wrong hour | Event-time buckets; a lateness limit; later ones are dropped and counted, or handled by backfill |
| Clock moves forward in the middle of a batch | Old hours expire before pending changes are applied | Flush pending changes before expiring (the bug in 6.3) |
| Redis node lost | Rankings gone or stale | Replica + persistence; serve cached top-100 with `asOf`; rebuild from raw data |
| Hot category | One key overloaded | Micro-batch, shard the key and merge, cache top-N at the edge |
| Wrong ranking logic released | Bad lists for hours | Version the key, backfill into a new key, compare, then switch |
| Window drift (add and expire do not match) | Scores slowly wrong | Periodic full recompute for a sample of categories and compare (my test 6) |
| Returns and fraud | Rank inflated | Negative events; filter suspicious sales before they enter the stream |
| Product deleted | Dead item in the list | Filter at read time against the catalogue; remove from the sets on a delete event |

**Trade-offs to say aloud**

- **Batch vs stream**: batch is simple and exact, and the requirement allows it. Stream gives freshness and lower cost per update, at the price of state and care.
- **Freshness vs write cost**: coalescing helps a lot on skewed bursts (500x in my flash-sale test) and very little on spread-out data (2.3%).
- **Full sorted set vs top-K only**: full is exact and supports any rank lookup; top-K saves memory but cannot recover when the top items expire.
- **Units vs revenue vs a mix**: the score is the product's business decision. Units are simple to add and subtract; a weighted score is also possible if it is a sum over events.
- **Exact vs approximate**: here exact, because the data is small enough. If the item count grew to billions, [Lesson 5](/design-cases/lesson-5)'s sketches would come back.

## 8. How to say it in an interview (60 seconds)

"Sales are written about 400 times a second and read about 100 times more, so I separate the paths. Sales events go to a stream partitioned by product, and raw events are archived for backfill. A stateful aggregator keeps hourly buckets per category and product, dedupes by event id, and applies micro-batches to a Redis sorted set per category and window, where the member is the product and the score is units sold. When an hour leaves the 7-day window I subtract its bucket. Reads are one `ZREVRANGE` for the top N or `ZREVRANK` for one product, behind an API and CDN cache of a few seconds, so the cost of a read does not depend on the number of sales. The simplest version is the primer's hourly batch job, and I keep it as the checker: in my test the incremental result matched a full recompute for all 50 categories. Coalescing writes helped 500 times in a flash-sale test and 2% on spread-out data. A hot category I handle with micro-batches, a cached top-100, and key sharding with an exact merge. Backfill replays raw sales into a new versioned key, then switches over."

## Interview questions

### Q1. Design sales rank by category. Where do you start? (Must know)

I clarify the window (last 7 days), freshness (hourly is fine), scale (10M products, 1,000 categories, ~400 sales/s, ~40,000 reads/s), and whether a product can be in several categories. Then I split write path and read path. The write path counts sales per (category, product) over the window; the read path serves a precomputed top-N. I propose the hourly batch first, then the stream upgrade.

### Q2. Why a Redis sorted set for the read path? (Must know)

It keeps products ordered by score. The top N is one `ZREVRANGE`, a product's rank is one `ZREVRANK`, and a score change is `ZINCRBY` in `O(log n)`. With a SQL table I would sort at read time or maintain an index. A sorted set per (category, window) is the lookup structure for exactly this question. My demo implements the same behaviour in memory.

### Q3. Walk me through the batch version from the primer. (Must know)

Raw sales log lines go to an object store. Every hour a MapReduce job maps each line to `(category, product) -> quantity`, reduces by sum, then sorts, and writes a `sales_rank` table. The Rank API reads that table. It is simple and exact. Its cost is that every run reads the whole window, and the list is as old as the last run.

### Q4. How do you do a sliding 7-day window incrementally? (Must know)

I keep hourly buckets. A sale adds to its hour's bucket and to the sorted set. When the clock moves forward, the hour that leaves the window is subtracted from the sorted set and deleted. So each sale is touched twice. I test it against a full recompute; in my run all 50 categories matched.

### Q5. What happens if the same sale event arrives twice? (Trap)

Without protection, it is counted twice and nobody sees it. Stream delivery is usually at least once. I keep the event ids seen per hour bucket and drop repeats, and delete the id set when the hour expires. For huge scale, an idempotent write keyed by event id in a store with expiry works too.

### Q6. A sale arrives 10 hours late. What do you do? (Senior signal)

Bucket by event time. The late sale goes into its original hour's bucket and into the sorted set, if that hour is still inside the window (my test 5). When that hour expires it is subtracted, which is correct. If it is older than the window, I drop it and count the drop in a metric. For rules that need very late data, I use the backfill path.

### Q7. How fresh does the ranking need to be? (Senior signal)

I ask. The primer says hourly. Per-sale updates cost a lot and nobody can see the difference. I would use micro-batches of a few seconds to minutes for big categories and add a cache of 5 to 60 seconds on reads. In my test, batching cut sorted-set writes by 50 to 500 times in a flash sale, and by only 2.3% on spread-out data, so I would measure real traffic before choosing.

### Q8. One category gets 40% of the traffic. What breaks and how do you fix it? (Senior signal)

Three things can break. One key takes many writes: coalesce in micro-batches, or shard the key by product hash and merge the shard top lists, which is exact because a product lives in one shard. One key takes many reads: cache the top-100 in the API process and the CDN, and use replicas. One product dominates: coalescing again. The sorted set's size is not the issue; the update rate is.

### Q9. How do you handle a product in several categories? (Must know)

The event carries the list of categories, and the aggregator updates the sorted set and bucket of each one. A sale is then counted once per category, which is correct for per-category ranking. For a global ranking I would not just sum the category counts, since that counts the sale twice; I would keep a separate "all" set or compute it separately.

### Q10. How do you rebuild after a bug in the aggregator? (Must know)

Raw sales are in cheap storage, so I replay the window into a new sorted set key with a version in its name. When it has caught up I compare it against the live key on sample categories, then switch the API to the new key, and delete the old one later. I do not write over the live key. In my test, a full rebuild of 200,000 sales took 0.76 s locally and gave the same top-10.

### Q11. How do you know the incremental ranking is right? (Senior signal)

I keep the slow, obvious version as a checker: a recompute from raw events. A job compares both on a sample of categories and alerts on a mismatch. In development I run both on random data. That test found a real bug in my first version: pending changes were written after old hours were expired, so expired sales stayed in the sets.

### Q12. Why not keep only the top 100 per category in the sorted set? (Trap)

It saves memory, but a product below the cut has no score, so when a leader expires, you cannot tell who comes next. The window changes only by subtraction, and a missing member cannot be subtracted properly. Options: keep the full set (exact, easy), or keep a larger bounded set and rebuild it from buckets on a schedule. I kept the full set and did not test the bounded one.

### Q13. What if Redis goes down? (Senior signal)

Reads should degrade, not fail. API servers keep the last top-100 per category with its `asOf` time and serve it. Redis has a replica and persistence, and if both fail I rebuild from the checkpointed buckets and the raw archive. The write path continues into the stream; the aggregator catches up when Redis is back.

### Q14. How would you change this for revenue instead of units? (Trap)

The score becomes the sum of price times quantity. The structure stays the same, as long as the score is a sum over events so that add and subtract work. Use integer cents, not floats, so subtraction is exact. A blended score (units, revenue, recency) is fine if it is linear in the events; a score that is not a sum needs a recompute from buckets.

## Key takeaways

- Split the **write path** (stream, dedupe, hourly buckets, windowed aggregation) from the **read path** (a precomputed sorted set per category and window, served behind a cache).
- Start with the primer's hourly batch. Add the stream version for freshness and cost, and keep the batch as backfill and as the correctness check.
- Sliding window = add new events, subtract the expired hour. Order matters: apply pending changes before expiring. I hit this bug and a test against a recompute caught it.
- Measured: the incremental result matched a full recompute for all 50 categories; a full rebuild of 200,000 sales took 0.76 s locally.
- Coalescing writes: 100,000 writes became 200 (flash sale, batches of 10,000) but only 2.3% fewer on spread-out data. Measure on real traffic.
- Dedupe by event id and bucket by event time so duplicates and late events do not break the counts.
- A hot category is a write-rate problem more than a size problem: micro-batch, shard the key and merge exactly, cache the top-N.
- Keep raw sales so you can rebuild into a new versioned key and switch over.
