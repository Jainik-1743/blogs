> **In one line:** running one system in **more than one data centre** protects you from losing a whole site, and puts users closer to the servers. It costs you the thing a single site gives for free: **one truth**. The design is about choosing **active-passive or active-active**, steering users with **DNS**, deciding **sync or async replication** (which sets how much data you can lose, the **RPO**), handling **conflicts** and **split brain**, and planning **failover and failback** before the bad day.

[Lesson 1](/design-cases/lesson-1) built a key-value store with replicas inside one cluster; this lesson stretches replication over a long, slow, sometimes broken link. ## Words used in this lesson

- **Data centre (DC)** is a building (or a cloud **region**, which is a group of them) with servers, power and network. An **availability zone** is one failure-isolated part of a region.
- **Active-passive** means one DC serves all traffic and the other waits as a standby. **Active-active** means both serve traffic at the same time.
- **Failover** is switching traffic from a failed site to a healthy one. **Failback** is moving back after the first site is repaired.
- **RPO (recovery point objective)** is how much data you can lose, measured in time ("up to 5 seconds of writes"). **RTO (recovery time objective)** is how long you can be down.
- **Replication** is copying data to another machine. **Synchronous** replication waits for the copy before saying "done". **Asynchronous** replication says "done" first and copies later.
- **Replication lag** is the delay between a write on the primary and the same write on the replica.
- **DNS (domain name system)** turns names into IP addresses. **TTL (time to live)** is how long a resolver may cache an answer. **GSLB (global server load balancing)** is a DNS service that answers differently depending on health and location.
- **Split brain** is when two sites each think they are the primary and both accept writes.
- **Quorum** is a majority vote. With 3 voters, 2 is a quorum.
- **Fencing token** is a number that grows with each new primary, so a storage system can reject writes from an old primary.
- **Conflict** is two different updates to the same data on two sites that did not know about each other.
- **LWW (last write wins)** is a rule: keep the value with the latest timestamp.
- **Data residency** is a legal or contract rule that some data must stay in a given country or region.

## 1. Requirements

**Functional**

- The service keeps working for users when one whole data centre is lost (power, network, fire, a bad deployment).
- Users are sent to a nearby, healthy site.
- Writes are not lost, or the loss is **bounded and known** (the RPO).
- After the failed site comes back, it rejoins without corrupting data.
- Some data (for example EU users' personal data) stays in its region.

**Non-functional**

- **RTO**: back in service in minutes, not hours (assume a target of 5 minutes).
- **RPO**: depends on the data. Payments: zero. A "like" counter: a few seconds is fine. **Decide it per data type**, not once.
- **Latency**: reads and writes should feel local to the user, as far as the laws of physics allow.
- **Consistency**: say which operations need a single truth (money, unique names) and which can be eventually consistent ([System Design Lesson 28](/system-design/lesson-28)).
- **Operability**: failover must be a rehearsed, mostly automatic procedure, not an invention at 3 a.m.

**Out of scope here**: building the database replication protocol itself, and multi-cloud portability.

## 2. Back-of-envelope numbers

Everything here is an **assumption** or simple physics. I ran `maths.ts`.

**Distance sets the floor for latency.** Light in fibre travels at about two thirds of its speed in vacuum, so roughly 200,000 km/s (memory). I used great-circle distances (rounded, assumed):

```text
route                                min RTT (straight fibre)
same metro (50 km)                      0.5 ms   (real routes are longer; real RTT is higher)
New York - London (~5,570 km)          55.7 ms
New York - Singapore (~15,300 km)     153.1 ms
Mumbai - Frankfurt (~6,600 km)         66.0 ms
```

You cannot configure this away. Real cables do not run straight, and routers add delay, so real round trips are higher. Use these as the best case.

**What a synchronous remote write costs.** Assume a local commit takes 2 ms and the write waits for one remote acknowledgement:

```text
remote RTT   1 ms -> commit ~3 ms -> one client thread does at most 333 serial writes/s
remote RTT  20 ms -> commit ~22 ms -> one client thread does at most 45 serial writes/s
remote RTT  80 ms -> commit ~82 ms -> one client thread does at most 12 serial writes/s
remote RTT 160 ms -> commit ~162 ms -> one client thread does at most 6 serial writes/s
```

Many threads in parallel get you more total throughput, but **every user-visible write still waits 80 ms** or more. This is the whole reason people use async replication across long distances.

**Availability of two sites.** If each DC is up 99.9% of the time and failures are **independent**:

```text
one site 99.90% (525.6 min/yr down) -> two sites 99.9999% (0.5 min/yr down)
```

Treat this as an upper bound. Failures are not independent. A bad software release goes to both sites. A shared DNS provider or a shared configuration service fails for both. Most real multi-DC outages are caused by software and configuration, not by fire. Two sites remove the "building" risk and add the "coordination" risk.

**DNS failover time** (worst case, if resolvers obey the TTL):

```text
check every 10s, 3 fails to declare down, TTL 300s -> detect 30s + TTL 300s = up to 330s
check every 10s, 3 fails to declare down, TTL 60s  -> detect 30s + TTL 60s  = up to 90s
check every 5s,  2 fails to declare down, TTL 30s  -> detect 10s + TTL 30s  = up to 40s
```

A 5-minute RTO is achievable with DNS only if the TTL is short. Some resolvers and clients cache longer than the TTL (memory), so keep the first number as a floor.

**Data at risk during lag**: `writes per second x lag`.

```text
  1000 writes/s x 0.04 s lag = 40 writes at risk
  1000 writes/s x 4 s lag = 4,000 writes at risk
 50000 writes/s x 4 s lag = 200,000 writes at risk
```

## 3. API

Users see no change. The new API is for **operators** and for **services** that need to know where they are.

```http
# Data plane: same URLs. Only the DNS name steers.
GET https://api.example.com/v1/orders/42
→ 200 OK   X-Served-By: eu-west-1     # many systems expose the serving site in a header, for debugging

# Control plane (operators)
GET  /v1/sites                     → [{ "site":"eu-west-1","role":"primary","health":"ok","replLagMs":38 }, ...]
POST /v1/failover   { "to":"us-east-1", "mode":"planned|emergency", "fenceToken": 18 }
POST /v1/failback   { "site":"eu-west-1", "after":"resync-complete" }
PUT  /v1/traffic    { "weights": {"eu-west-1": 100, "us-east-1": 0} }    # drain, or shift gradually
```

Notes:

- `mode: planned` first stops writes on the old primary, waits for lag to be 0, and then promotes. Nothing is lost. `emergency` promotes without waiting and accepts the RPO.
- `fenceToken` increases on every promotion, so old primaries can be refused (section 6.7).
- Every write API that crosses sites should be **idempotent** (safe to repeat), because after a failover the client does not know whether its last request arrived. See [System Design Lesson 34](/system-design/lesson-34).

## 4. Data model

Decide for each kind of data **where the truth lives**:

```text
User profile      home_region = "EU"   -> written only in EU, replicated read-only elsewhere (or not at all if residency says so)
Orders            owner site per order (home region of the buyer)
Counters / likes  CRDT counter, each site adds to its own slot; the total is the sum
Session / cache   per site; can be lost; rebuilt on login
Config / feature  one primary, replicated everywhere (rare writes)
```

Metadata each replicated row carries:

```text
row_id, value, version / vector, last_modified_ts, origin_site, tombstone (for deletes)
```

And the control state, kept in a small store with a **majority vote** across three places (two DCs plus a witness, section 6.7):

```text
cluster_state: { primary: "eu-west-1", epoch: 18, members: [...], updated_at }
```

`epoch` is the fencing token: a number that increases each time the primary changes.

## 5. High-level architecture

```text
                          Users worldwide
                                |
                    GSLB / GeoDNS (health checks, TTL 30-60 s)
                    /                            \
        "eu users -> EU"                    "us users -> US"
                   v                                 v
     +-------- DC-EU (primary for EU data) ----+   +-------- DC-US (primary for US data) -------+
     |  L7 load balancer                       |   |  L7 load balancer                         |
     |  stateless app servers (N)              |   |  stateless app servers (N)                |
     |  cache (per site)                       |   |  cache (per site)                         |
     |  DB: EU shard leader + local replicas   |   |  DB: US shard leader + local replicas     |
     |  queue / log                            |   |  queue / log                              |
     +----------------+------------------------+   +----------------------+--------------------+
                      |  async replication of changes (both directions)  |
                      +<------------------------------------------------>+
                                     ^                    ^
                          cross-site link (80 ms RTT)     |
                                                    Witness / tie-break (third site):
                                                    holds the majority vote for "who is primary"
```

Reading the picture:

- Each site is **self-contained**: load balancer, app servers, cache, database, queue. A request is served entirely inside one site (no cross-site call on the hot path).
- Each piece of data has **one home**. Writes go to the home, then replicate to the other site asynchronously. This is "active-active at the service level, but single-writer per record".
- A third place (a witness) breaks ties, so that a network cut between the two DCs does not give two primaries.
- If DC-EU dies, GSLB sends EU users to DC-US, and DC-US promotes its replica of the EU data (section 6.6).

## 6. Deep dives

### 6.1 Active-passive vs active-active

| | Active-passive (warm standby) | Active-active, single writer per record | Active-active, multi-writer |
|---|---|---|---|
| Who serves | primary only | both, each for its own data | both, for anything |
| Standby cost | full hardware idle | little idle (both used) | little idle |
| Failover | promote and redirect | redirect; promote the other copy | redirect only |
| Conflicts | none | none | **yes, the hard part** |
| Latency for far users | bad (all go to primary) | good for local data | good |
| Typical use | most systems, billing, payments | social, SaaS with tenants per region | shopping carts, counters, collaborative data |
| Main risk | standby is untested, it "worked on paper" | cross-region requests when a user travels | silent data loss from merges |

My advice, which most real designs agree with: **start with active-passive**. It is much easier to reason about, because there is one truth. Move to "active-active with a home site per record" when you need low latency for far users or must use the standby's capacity. Go to true multi-writer only for data that merges safely, such as counters, sets and carts, and only on purpose.

> [!warn] "Active-active" is often a hope, not a design. If each site is sized at 100% and carries 60% of the traffic, then when one dies the other gets 120% and falls over. Each site must be able to take the whole load (N+1 at the site level), or you must have a load-shedding plan ([System Design Lesson 40](/system-design/lesson-40) on redundancy).

### 6.2 Steering traffic: DNS, GSLB and anycast

How does a user reach the right site?

- **GeoDNS / GSLB**: the DNS server gives different answers by location (nearest site) and by health (never an unhealthy one). It runs health checks against each site. The cost is the **TTL**: after a site dies, resolvers may keep handing out its address until the cached answer expires. See the arithmetic in section 2: with 3 failed checks of 10 s and a 60 s TTL, the worst case is 90 s.
- **Anycast**: the same IP is announced from both sites and the internet's routing sends users to the closest. If a site stops announcing, traffic moves in the time routes take to change (often seconds to a minute, memory). No DNS cache problem, but you need network-level control. See [Lesson 4](/design-cases/lesson-4).
- **Client-side retry**: mobile and web clients keep a list of endpoints and try the next one on failure. This beats DNS for failover time, and works only for clients you control.
- **Weighted shift**: use weights (95/5, then 50/50) to test the second site with real traffic **before** you need it.

Practical points: use a low TTL (30 to 60 s) only on the names that must fail over, and run DNS on a provider that is separate from your sites. Make health checks test something real (can the app read and write its database?), not just "port 443 answers", otherwise a site with a dead database stays "healthy".

### 6.3 Synchronous vs asynchronous replication, with numbers

This is the central trade-off. I wrote `replication.ts` to measure it in a simple model:

- The primary takes 1,000 writes per second (random arrivals) for 120 s.
- Each write is shipped over one link with a one-way delay of half the RTT (80 ms RTT assumed). The link can apply 3,000 writes per second normally.
- **Async**: the client gets its acknowledgement 1 ms after the write. **Sync**: the client gets the acknowledgement only after the secondary applied the write, plus the way back.
- I crash the primary at 2,000 random moments. A write is **lost** if it was acknowledged to the client but not yet applied on the secondary.
- Scenarios 2 and 3 add a congested link: during part of the run it can only apply 700 writes per second, so a backlog builds.

```text
scenario                                              ack p50 lag p50 lag max  lost mean  lost p99  lost max  window max
async, 80 ms RTT, link has 3x headroom                   1 ms   40 ms    42 ms       39.4        56        65       41 ms
async, 80 ms RTT, 10 s congestion at 700 writes/s        1 ms   40 ms  4070 ms      304.0      3591      3939     4057 ms
async, 80 ms RTT, 30 s congestion at 700 writes/s        1 ms   41 ms 12719 ms     2884.8     12361     12732    12678 ms
sync,  80 ms RTT, link has 3x headroom                  80 ms   40 ms    42 ms        0.0         0         0        0 ms
```

How to read it:

- **Healthy async**: the client sees 1 ms. The replica is about 40 ms behind. If the primary dies at a random moment, about **39 acknowledged writes are lost** on average (up to 65). That matches the simple formula: 1,000 writes/s x 0.04 s = 40. The loss window ("window max") is at most 41 ms of data.
- **Short congestion (10 s)**: lag reaches 4 seconds. A crash in the worst moment loses up to about **3,900 acknowledged writes**, about 4 seconds of data. The mean is 304 because the crash is usually at a calm moment, but the worst case matters for your RPO.
- **Long congestion (30 s)**: lag reaches 12.7 s and a crash loses up to **12,700 writes**. The backlog keeps growing while the link is slower than the write rate.
- **Sync**: zero loss, but **every write waits 80 ms** (RTT).

So the RPO of an async system is **not a constant**. It is the lag at the moment of the crash, and lag is highest exactly when the network is in trouble, which is also when a failover is likely. Measure replication lag as a first-class metric and alert on it. Your real RPO is the **worst** lag you allow before you stop accepting writes or page someone.

**Middle roads (memory, not tested here):**

- **Semi-synchronous**: wait for the copy to reach one nearby replica (another availability zone, 1 to 2 ms away), and ship to the far DC asynchronously. You survive the loss of one machine or zone with no loss, and lose a small window only if the whole region goes.
- **Quorum writes** (3 sites, wait for 2): lose nothing if one site fails, pay the latency of the second-nearest site. Used by consensus-based databases (Raft or Paxos style).
- **Synchronous only for the writes that need it**: payments sync, "last seen" async.

> [!note] The model has one link, one secondary and no retries. Real systems batch, compress, and have several replicas and several links. The point is the **shape**: async loses about `rate x lag`, sync costs about one RTT per write.

### 6.4 RPO and RTO, set per data type

| Data | RPO target | RTO target | Replication |
|---|---|---|---|
| Payments, ledger | 0 | minutes | sync or quorum across 2+ sites |
| Orders | seconds | minutes | async with lag alert, replay from the queue |
| User profile edits | seconds to minutes | minutes | async |
| Like counts, view counts | minutes (or rebuild from logs) | minutes | async, CRDT counters |
| Caches, sessions | none (rebuild) | minutes | none |
| Search index | rebuild from source | hours is OK | none |

This table is what an interviewer wants to hear: "I would not use one rule for everything." A zero RPO costs latency and availability. Spend it only where the business needs it.

### 6.5 Conflicts when both sites can write

If the same record is written at both sites while they cannot talk (or before replication arrives), you have a conflict. The options, from simplest to most work:

1. **Avoid them**: one home site per record (section 4). Most systems should stop here.
2. **Last write wins (LWW)**: keep the update with the later timestamp. Simple, and it **silently drops** the other update. It also trusts clocks that are never perfect.
3. **Version vectors**: each site keeps a counter per site for each record. You can then tell "A is newer than B" from "A and B are concurrent" and **detect** the conflict (memory). Detection is cheap; what you do next is the hard part: show both to the user, or merge in code.
4. **CRDTs (conflict-free replicated data types)**: data structures whose merge always works, such as counters, sets, and registers (memory). Good for likes, carts, presence. Not for "bank balance must not go below zero", because no merge rule knows about that constraint.
5. **Application merge**: a function that knows the business (for example, a document merge). This is the area of [Lesson 3 (collaborative editing)](/design-cases/lesson-3).

I measured the cost of LWW in the same script. Both sites accept writes for 30 s during a partition (100 writes per second each, 200 keys), with site B's clock 50 ms fast:

```text
== split brain: both data centres accept writes for 30 s, 100 writes/s each side, 200 keys ==
writes accepted: 6000; keys changed on both sides: 200 of 200
last-write-wins: A's value kept for 101 keys, B's for 99 keys; the other side's value is silently dropped for all 200
a version-vector check would instead flag these 200 keys as conflicts for the app to merge
```

With a small key space, **every** key was changed on both sides, and LWW threw away one side's last update for every key. It also picked winners by the 50 ms clock difference, not by anything real. For a profile "bio" field that is acceptable. For an order status it is a bug. (The script keeps only the last write per key per side, so the real number of dropped updates is larger than 200.)

### 6.6 Failover and failback

**Failover steps (emergency)**

1. **Detect**: health checks and a human or automated decision. Beware false alarms: a flapping link can trigger a failover that causes more damage than the problem.
2. **Fence the old primary**: make sure it cannot accept writes any more (section 6.7). This comes **before** promotion.
3. **Promote** the replica in the other DC: it becomes the primary. Increase the epoch.
4. **Check the data**: you accept the RPO. Record what was lost: the last replicated position of the old primary versus the new primary's position.
5. **Steer traffic**: update GSLB, drain the old site.
6. **Warm up**: the new primary's caches are cold, which means a load spike on its database. Ramp traffic in steps.

**Planned failover** (a drill, or a migration) is easier: stop writes, wait for lag 0, promote, switch. RPO is zero. **Practise it regularly.** A standby that has never taken traffic is a belief, not a fact.

**Failback** is harder than failover, and people forget it:

1. The old primary comes back with a **tail of writes that never reached the new primary**. In my 10 s congestion scenario this tail was up to about 3,900 writes. These were acknowledged to users. You must decide: discard them (and tell users or support), or extract and re-apply them where they do not conflict. Never just let the old primary rejoin as primary.
2. Make the old primary a **replica of the new one**: wipe or roll back its extra tail, then resync from the new primary.
3. Wait for lag to reach about zero.
4. **Optionally** switch back with a planned failover, at a quiet time. Often you simply stay where you are, and the old site becomes the standby. There is no rule that the first site must be primary.

### 6.7 Split brain, quorum and fencing

**Split brain**: the link between the DCs breaks. Each site cannot tell "the other site died" from "the link is down". If both promote themselves, both accept writes, and the data diverges (section 6.5 shows the size of the damage).

Defences:

- **A third voter** (witness), in a third location. A site may be primary only if it can reach a **majority** of the three voters (memory: this is the idea behind Raft and Paxos style systems). With a cut link, the side that can still see the witness has 2 of 3 and stays primary. The other side has 1 of 3 and **stops accepting writes**. This is the CAP trade-off in action ([System Design Lesson 27](/system-design/lesson-27)): in a partition, the minority chooses consistency over availability.
- **Fencing tokens**: each promotion gets a higher epoch number. The storage or the downstream service rejects writes carrying an older epoch. This protects against the **zombie** primary: a machine that was paused (a long garbage collection, a frozen virtual machine) and wakes up still believing it is primary.
- **Lease with a timeout**: the primary must renew its lease from the voters every few seconds. If it cannot renew, it stops. The new primary waits for longer than one lease before taking over. This depends on clocks running at about the same speed (not on them showing the same time), and it is a classic place for bugs.
- **STONITH ("shoot the other node in the head")**: power off or isolate the old primary through an out-of-band path before promoting. Blunt, but sure.

With only two sites and no witness you must choose: **automatic failover with split-brain risk**, or **manual failover with a human as the tie-break**. Many teams choose manual for the data layer and automatic for the stateless layer.

### 6.8 Latency in an active-active design

Cross-site calls are slow (section 2). Rules that follow:

- **Keep a request inside one site.** Do not make the hot path call another site. If a service must, use a timeout much shorter than the usual and a fallback.
- **Read local, write home.** Reads come from the local replica (maybe a little stale), writes go to the record's home site. If the user is far from the home site, the write is slower, so choose a home near where the user usually is.
- **Read-your-own-writes.** After a write the user must see it. A common trick: for a short time after a write, route this user's reads to the home site, or send a "min version" token with the next read, and make the replica wait until it has caught up to that version.
- **Travelling users**: a user from the EU who logs in from the US is routed to DC-US, whose copy of their data is read-only and a bit stale. Say what happens: redirect writes to the EU home, or serve slower.
- **Queues are a friend**: use a local queue and process slowly in the background, rather than a cross-site synchronous call.

### 6.9 Data residency

Some rules (company policy or national law) say that certain data must be stored and processed in a region. This changes the design:

- **Tag data with a residency class** at creation (`home_region`), and **replicate only inside the allowed set of regions**. Backups, logs, search indexes and analytics copies count too. This is where most violations happen.
- The "other site" for failover of EU data must itself be in the allowed area. With two EU regions that works. With one EU and one US region it does not, for personal data.
- **Routing**: a user's profile lives in their home region. Requests from elsewhere are proxied there or served with non-personal data only.
- **Keys**: if the rules allow only encrypted copies elsewhere, keep the encryption keys in the home region.
- **Deletion** must reach every copy in the region, including replicas and backups.

I am not a lawyer, and I did not check any specific law here. The design lesson is: residency is a **data placement constraint** that you have to put into the design at the start. Adding it later means moving data.

## 7. Failure modes and trade-offs

| Problem | Effect | Handling |
|---|---|---|
| Whole DC lost | Users of that site fail until traffic moves | Health checks, GSLB, other site sized for 100% of the load |
| Replication lag spikes | RPO grows (my model: up to 4 s of writes at 10 s congestion) | Alert on lag; slow or reject writes above a limit; semi-sync for critical data |
| Link between DCs cut | Split-brain risk | Witness/quorum, fencing, minority side stops writes |
| Zombie primary wakes up | Old primary writes on top of the new | Fencing tokens, leases, STONITH |
| Promotion of a stale replica | Acknowledged writes are lost | Record the gap; support/replay process; choose the most advanced replica |
| Failover storm | Cold caches overload the new primary | Warm caches, ramp traffic, load shedding |
| DNS clients ignore TTL | Some users stay on the dead site | Client retries, anycast, short TTL, accept a tail |
| Shared dependency fails (DNS, auth, config) | Both sites fail together | Independent providers, config rollout per site, kill switches |
| Bad release | Goes to both sites | Release one site first, bake, then the other |
| Failback done carelessly | Old tail corrupts data | Resync old primary as a replica; discard or reconcile its tail |
| Never-tested standby | Failover fails when needed | Scheduled game days, planned failovers, traffic weights |
| Residency breach through backups or logs | Legal exposure | Tag data, restrict replication targets, audit copies |
| Clock skew between sites | LWW picks wrong winners | Prefer version vectors or home-site writes; avoid LWW for important data |

**Trade-offs to say aloud**

- **Active-passive vs active-active**: simplicity and one truth against capacity use and local latency.
- **Sync vs async**: zero loss and an RTT per write, against fast writes and an RPO equal to the lag.
- **Automatic vs manual failover**: fast recovery with split-brain and flapping risk, against a human delay.
- **Consistency vs availability in a partition**: the minority stops (consistent) or both continue (available, conflicting).
- **Short DNS TTL vs resolver load and cache effects**: faster failover against more DNS queries and some users ignoring it anyway.
- **Cost**: a second site, a witness, network links and extra people-time for drills. Do the maths against the cost of an outage.

## 8. How to say it in an interview (60 seconds)

"I start with RPO and RTO per data type, because that decides everything. For most data I would use active-passive with a warm standby, or active-active where each record has one home site, so there are no write conflicts. Users reach the nearest healthy site through GeoDNS or anycast with health checks that test the database, and a low TTL, so DNS failover takes about detection time plus TTL, say 90 seconds in the worst case. Replication across regions is asynchronous, because a synchronous write pays the round trip, 80 ms or more. My simulation showed async loses about write rate times lag: about 40 writes at 40 ms lag, but up to 4,000 when a 10-second congestion pushed lag to 4 seconds, so I alert on lag and use sync or quorum only for money. To avoid split brain I put a witness in a third place and use fencing epochs, so the minority side stops writing and a zombie primary is rejected. On failover I fence first, then promote, then steer traffic and warm up. On failback I resync the old primary as a replica and deal with its unreplicated tail. And for residency I tag data with a home region and restrict where copies, backups and logs go."

Change `ARRIVAL`, the link `capacity`, the `congestion` window or `rttMs` in `replication.ts` and watch the "lost" columns.

> [!warn] The simulation is a teaching model, not a database. A real replication stream has batching, several replicas, retries, and lag that depends on disk and CPU on the replica, not only on the link. Measure lag in your own system (most databases expose it) and take your RPO from those numbers.

## Try it

**Exercise 1.** Your primary takes 20,000 writes/s. Replication lag is normally 50 ms and sometimes reaches 3 s. How many acknowledged writes can a crash lose in the normal case and the bad case?
**Answer:** 20,000 x 0.05 = 1,000 writes normally. 20,000 x 3 = 60,000 in the bad case. The RPO you should quote is the bad case, or you must limit the lag.

**Exercise 2.** Two sites with a 70 ms RTT. A request does 4 database writes in order, each synchronous across sites. What is the minimum extra latency per request?
**Answer:** 4 x 70 ms = 280 ms more than the local commit time. Fixes: batch the writes into one transaction (1 round trip), or replicate asynchronously.

**Exercise 3.** The link between your two data centres breaks, and no witness exists. Both sites still have users. What are your options?
**Answer:** (a) Pre-decide a preferred primary site. The other site becomes read-only when it cannot see the preferred one. This is safe, but if the preferred site really died, the other stays read-only until a human promotes it. (b) Let both write and accept conflicts, then merge later (section 6.5 shows the cost). (c) Stop writes on both until a human decides. A witness in a third place makes the choice automatic and safe.

## Interview questions

### Q1. Design a system that survives the loss of a whole data centre. Where do you start? (Must know)

I ask for the RPO and RTO per kind of data, and the traffic and latency needs of users. Then I choose the pattern: active-passive if one truth is fine, or active-active with a home site per record if far users need low latency. I add traffic steering with health checks, replication (async by default, sync or quorum for money), a witness for tie-breaks, and a rehearsed failover and failback. I finish with the failure table.

### Q2. Active-passive or active-active? (Must know)

Active-passive is simpler and has no write conflicts, but the standby capacity sits idle and far users have high latency. Active-active uses both sites and gives local latency, but if both can write the same record, I have to solve conflicts. So I use active-active where each record has one home site, and true multi-writer only for data that merges, like counters. I also make sure each site can take the whole load, otherwise "active-active" fails on the first outage.

### Q3. Synchronous or asynchronous replication across regions? (Must know)

Sync gives RPO zero but every write waits for the round trip. At 80 ms RTT that is 80 ms per write, which my simulation confirmed. Async acknowledges at once, but a crash loses the writes still in flight. In my model that was about 39 writes at a healthy 40 ms lag, and up to about 3,900 when a 10-second congestion pushed lag to 4 seconds. I choose per data type: sync or quorum for payments, async with a lag alert for most things. A middle road is semi-sync to a nearby replica, then async to the far one.

**Follow-up:** *Why is lag worst when you most need it?* Because network trouble, which causes lag, is also a common reason for failover.

### Q4. What is split brain and how do you prevent it? (Must know)

Both sites believe they are the primary and both accept writes, so data diverges. It happens when the link breaks and each side cannot tell a dead peer from a cut link. I prevent it with a witness in a third place so only the side with a majority may be primary, fencing tokens (a growing epoch that storage checks, so a zombie primary is rejected), and leases that expire. With only two sites and no witness, I would use manual failover for the data layer.

### Q5. How does failover work, step by step? (Must know)

Detect, then fence the old primary, then promote the replica and bump the epoch, record what was lost, steer traffic with GSLB, and ramp up because caches are cold. Fencing comes before promotion, otherwise the old primary may still be writing. Planned failover is cleaner: stop writes, wait for lag zero, then promote, so RPO is zero.

### Q6. Why is failback harder than failover? (Senior signal)

The old primary comes back with writes that were acknowledged but never reached the new primary. If I let it rejoin as primary, I lose the newer data or create a mix of both. So I rejoin it as a replica: roll back or save its extra tail, resync from the new primary, wait for lag zero, and only then optionally switch back in a planned failover at a quiet time. Often I simply leave the roles swapped.

### Q7. How long does DNS failover take? (Trap)

Not zero, and not just the TTL. It is detection time (check interval times the number of failed checks) plus the TTL of cached answers, and some resolvers and clients cache longer than that (memory). With a check every 10 s, 3 failures and a 60 s TTL, I computed up to 90 s worst case. To go faster I use client-side retries to a second endpoint or anycast. I also keep the TTL short only on names that must fail over.

### Q8. How do you handle write conflicts in active-active? (Senior signal)

First avoid them: one home site per record. If I cannot, I choose by data type. LWW is simple but silently drops an update and trusts clocks; in my test every one of 200 contested keys lost one side's data. Version vectors let me detect that two updates were concurrent. CRDTs merge safely for counters and sets. For business objects I write an application-level merge, or route the conflicting writes to a single owner.

### Q9. Is two data centres twice as available as one? (Trap)

On paper, if failures are independent: 99.9% each gives about 99.9999%. In practice, failures are correlated: a bad release, a shared DNS provider, a shared config store, or a human mistake hit both sites. Also failover itself is software that can fail. So the real gain is less, and the main benefit is protection against site-level events. I would release one site at a time and keep the control plane independent.

### Q10. What is the RPO of an async replicated system? (Senior signal)

It is not a fixed number. It is the replication lag at the time of the failure, about `write rate x lag` in lost writes. It is small when the link is healthy and large when it is congested. So I define the RPO as a limit on lag: if lag goes over, for example, 5 seconds, I alert, and for critical data I stop accepting writes or switch to sync. I measure the real distribution of lag.

### Q11. How do you give users read-your-own-writes with async replicas? (Senior signal)

After a write, the client or the session carries a version or position token. The next read either goes to the home site, or goes to a local replica that waits until it has applied at least that version. Without this, a user saves a change, reloads, hits a replica that is 40 ms behind, and sees the old value, which looks like data loss.

### Q12. How would you handle data residency in this design? (Senior signal)

Tag every record with a home region at creation and restrict the replication targets to regions allowed for that class. That includes backups, logs, search indexes and analytics, which are where most breaches happen. Failover for EU data must go to another EU site. Requests from other regions are proxied to the home region or served non-personal data. Deletion has to reach every copy in the allowed set. I would raise it at the start, because moving data later is painful.

### Q13. When would you refuse to go active-active? (Trap)

When the system needs one strict global order of operations, such as a matching engine or a ledger with a hard constraint. A strict order needs a single sequencer, and multiple writers across 80 ms break it. For these I use one active site with a hot standby and a short, well-tested failover, plus sync replication of the log to the standby. [Lesson 8](/design-cases/lesson-8) does this.

### Q14. How do you know your failover will work? (Must know)

I practise it. Planned failovers on a schedule, game days where I kill a site, traffic weights that send a small share of real users to the standby, and a runbook that people have actually used. A standby that never took traffic is an assumption: certificates, config, capacity and cache warm-up are the usual surprises. I also measure RTO and the data gap in each drill and keep the numbers.

## Key takeaways

- Decide RPO and RTO per data type first. Payments and a like counter do not need the same plan.
- Prefer one truth: active-passive, or active-active with one home site per record. True multi-writer is for data that merges.
- Distance sets the floor: New York to London is about 56 ms round trip in straight fibre. A synchronous cross-site write pays that on every write.
- Async replication loses about `write rate x lag`. In my model: about 39 writes at 40 ms lag, up to about 3,900 after a 10-second congestion, about 12,700 after 30 s. Alert on lag.
- DNS failover is detection time plus TTL (90 s in the example), and some clients ignore the TTL.
- Split brain is solved by a majority vote with a third voter, plus fencing epochs and leases. A minority side must stop writing.
- LWW silently drops updates (200 of 200 contested keys in my test). Use home sites, version vectors, CRDTs or an application merge.
- Failback is harder than failover: resync the old primary as a replica and handle its unreplicated tail.
- Practise failover. Each site should carry 100% of the load. Residency is a placement rule decided at the start.
