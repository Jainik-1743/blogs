> **In one line:** debugging containers is a short loop: **look at the state, read the logs, read the events, compare with what you expected, change one thing**. With Docker the tools are `docker ps -a`, `logs`, `inspect` and `exec`. With Kubernetes they are `get`, `describe`, `logs`, `exec` and `debug`, and almost every classic failure (`CrashLoopBackOff`, `ImagePullBackOff`, `Pending`, `OOMKilled`) tells you its cause in the **events** or the **exit code** if you know where to look.

Everyone's first Kubernetes day ends the same way: you apply a file, run `kubectl get pods`, and see a status you do not understand. The good news is that the number of statuses is small, and each has a short list of causes. The skill is to avoid guessing, and instead to read the one place that holds the answer.

## Words used in this lesson

- **Exit code** is the number a process returns when it ends. `0` means success. Anything else means some kind of failure.
- **Signal** is a message the kernel sends to a process, such as `SIGTERM` (please stop) or `SIGKILL` (stop now, no choice).
- **PID 1** is the first process in a container. Linux treats it specially: it ignores signals it has no handler for.
- **Event** is a short record Kubernetes writes when something happens to an object ("Scheduled", "FailedScheduling", "Pulled").
- **Status** (in `kubectl get pods`) is a display word that kubectl builds from the pod. It is not an official state.
- **Phase** is the official one-word state of a pod: `Pending`, `Running`, `Succeeded`, `Failed` or `Unknown`.
- **CrashLoopBackOff** means a container keeps crashing and Kubernetes waits longer and longer between restarts.
- **ImagePullBackOff** means the node cannot download the image and keeps retrying with a growing delay.
- **OOMKilled** means the kernel stopped the container for using more memory than its limit. The exit code is 137.
- **Ephemeral container** is a temporary extra container that you add to a running pod just to debug it.
- **Port-forward** is a tunnel from a port on your laptop to a port on a pod.
- **Endpoint** is one address behind a Service. An empty list means the Service has nowhere to send traffic.
- **Node** is a machine in the cluster. `NotReady` means its kubelet has stopped reporting that it is healthy.

## A method that works

Before any command, here is the loop I follow every time. It is the same for Docker and Kubernetes.

1. **State.** What is the thing doing right now? Running, exited, restarting, pending? How many restarts?
2. **Logs.** What did the program itself say before it died or while it misbehaves?
3. **Events or exit code.** What did the platform say about it? (Kubernetes events, Docker exit code and `OOMKilled` flag.)
4. **Compare.** What is different from the version that worked? A new image, a new setting, a new limit?
5. **Change one thing**, and check again.

Most people jump to step 5. They edit the YAML and re-apply, hoping. Steps 1 to 3 cost seconds and nearly always name the cause.

## Part 1: Docker, with real runs

### A container that exits at once

Here is a small Node.js program that needs a setting and exits if it is missing. This is the same mistake as forgetting a ConfigMap key in lesson 6.

```js
// crash.js
const need = process.env.DATABASE_URL;
console.log("starting notes-api");
if (!need) {
  console.error("FATAL: DATABASE_URL is not set");
  process.exit(1);
}
console.log("connected to", need);
```

Run it in the background and look:

```bash
docker run -d --name l8-crash -v $PWD/crash.js:/app/crash.js:ro \
  mirror.gcr.io/library/node:22-alpine node /app/crash.js
docker ps -a --filter name=l8-crash --format 'table {{.Names}}\t{{.Status}}'
docker logs l8-crash
docker inspect l8-crash --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}} status={{.State.Status}}'
```

```text
NAMES      STATUS
l8-crash   Exited (1) 1 second ago
starting notes-api
FATAL: DATABASE_URL is not set
exit=1 oom=false status=exited
```

Three lessons are in this small output.

- `docker ps` shows only running containers. **`docker ps -a`** (all) shows the exited ones. A beginner who runs plain `docker ps` sees nothing and thinks the container "disappeared".
- `docker logs` shows what the program wrote to stdout and stderr, even after it died. The reason is right there.
- `docker inspect` gives you the exact exit code and the `OOMKilled` flag. Exit code `1` is the generic "the program failed".

The fix is to pass the setting. Running again with `-e DATABASE_URL=postgres://db/notes` prints `connected to postgres://db/notes` and exits normally.

### Exit codes, and what they usually mean

I collected these from real runs in my lab. Codes 125, 126 and 127 are returned by the `docker` command itself.

| Exit code | Meaning | How I saw it |
|---|---|---|
| `0` | Success | `sh -c 'exit 0'` |
| `1` or other small number | The program chose to fail | `crash.js` returned 1 |
| `125` | The `docker` command itself failed (daemon error) | A port clash returned 125 |
| `126` | The command was found but cannot be run | `docker run busybox /etc/passwd` returned 126 |
| `127` | The command was not found | `docker run busybox nope` returned 127 |
| `137` | Killed by `SIGKILL` (128 + 9). Either `docker kill`, the OOM killer, or a stop that timed out | `docker kill` and the OOM test below |
| `143` | Ended by `SIGTERM` (128 + 15) | A stop on a server without a handler, with `--init` |
| `255` | A runtime error before the program started | `exec /busybox: no such file or directory` |

The rule of thumb: an exit code above 128 means "killed by a signal", and the signal number is the code minus 128. That gives you `137 = 9 (KILL)` and `143 = 15 (TERM)`. Kubernetes shows the same numbers.

### The restart loop

A container with a restart policy shows what a crash loop looks like. I ran the same crashing program with `--restart on-failure`:

```bash
docker run -d --name l8-loop --restart on-failure \
  -v $PWD/crash.js:/app/crash.js:ro mirror.gcr.io/library/node:22-alpine node /app/crash.js
sleep 6
docker ps -a --filter name=l8-loop --format '{{.Names}} | {{.Status}}'
docker inspect l8-loop --format 'restarts={{.RestartCount}} status={{.State.Status}} exit={{.State.ExitCode}}'
docker logs l8-loop | sort | uniq -c
```

```text
l8-loop | Restarting (1) 1 second ago
restarts=6 status=restarting exit=1
      6 FATAL: DATABASE_URL is not set
      6 starting notes-api
```

In six seconds the container started six times. The `RestartCount` is the number to watch, and the logs show the same error each time. This is what Kubernetes' `CrashLoopBackOff` is: the same loop, but with a growing wait between tries so it does not burn the node. Docker's own restart policy also backs off (its delay starts small and doubles), which is why a long-running loop looks slower than my six-second sample.

### OOMKilled, for real

Here is a program that holds on to more and more memory:

```js
// hog.js
const chunks = [];
console.log("allocating memory");
setInterval(() => { chunks.push(Buffer.alloc(10 * 1024 * 1024, 1)); console.log("held", chunks.length * 10, "MiB"); }, 100);
```

I ran it with a 64 MiB limit and no swap:

```bash
docker run -d --name l8-oom --memory 64m --memory-swap 64m \
  -v $PWD/hog.js:/app/hog.js:ro mirror.gcr.io/library/node:22-alpine node /app/hog.js
sleep 4
docker ps -a --filter name=l8-oom --format '{{.Names}} | {{.Status}}'
docker inspect l8-oom --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
docker logs l8-oom | tail -3
```

```text
l8-oom | Exited (137) 3 seconds ago
exit=137 oom=true
held 30 MiB
held 40 MiB
held 50 MiB
```

This is the whole story of an OOM kill. The program printed `held 50 MiB`, tried to grow past the limit, and the kernel killed it. **There is no error message in the logs.** The program did not get a chance to say anything, because it was killed by `SIGKILL`. The only clues are the exit code `137` and the flag `oom=true`. This is why "no error in the logs, but the pod keeps restarting" should make you think of memory first.

### Looking inside a running container

For a container that is running, these are the tools. I ran each against a small Node HTTP server (`server.js`, which answers `hello from notes-api` and has a `/healthz` path):

```bash
docker run -d --name l8-web -p 18080:3000 -v $PWD/server.js:/app/server.js:ro \
  mirror.gcr.io/library/node:22-alpine node /app/server.js
docker logs l8-web
docker ps --filter name=l8-web --format '{{.Names}} | {{.Status}} | {{.Ports}}'
docker port l8-web
curl -s localhost:18080/healthz
```

```text
listening on 3000
l8-web | Up 1 second | 0.0.0.0:18080->3000/tcp
3000/tcp -> 0.0.0.0:18080
ok
```

Now `exec`, `top`, `stats`, and `diff`:

```bash
docker exec l8-web sh -c 'id; ls /app; wget -qO- localhost:3000/healthz'
docker top l8-web
docker stats --no-stream --format 'name={{.Name}} cpu={{.CPUPerc}} mem={{.MemUsage}} pids={{.PIDs}}' l8-web
docker exec l8-web sh -c 'echo x > /tmp/scratch.txt'
docker diff l8-web
```

```text
uid=0(root) gid=0(root) groups=0(root),0(root),1(bin),2(daemon),...
server.js
ok
UID   PID     PPID    C   STIME   TTY   TIME       CMD
root  24258   24232   5   03:13   ?     00:00:00   node /app/server.js
name=l8-web cpu=0.03% mem=9.352MiB / 15.72GiB pids=7
A /app
A /app/server.js
C /tmp
A /tmp/scratch.txt
```

What each one tells you:

- **`exec`** runs a command inside the container. First, look at `id`: it says `uid=0(root)`. The container runs as root, which lesson 2 told you to avoid.
- **`top`** shows the processes of this container as the host sees them. Only one: `node /app/server.js`.
- **`stats`** shows live CPU and memory. Memory `9.3MiB` and `mem=... / 15.72GiB`: with no limit, the "limit" shown is the whole machine.
- **`diff`** lists files that changed in the container's writable layer compared to the image (`A` added, `C` changed, `D` deleted). It is great for "where is my app writing files?".

### Debugging the network with a sidecar

When the app image has no tools, you can start a second container that **shares the first container's network**. Then `localhost` means the same thing in both:

```bash
docker run --rm --network container:l8-web mirror.gcr.io/library/busybox:1.36 wget -qO- localhost:3000/
```

```text
hello from notes-api
```

This is the same idea as a Kubernetes sidecar and an ephemeral debug container: put your tools in a separate container, and share the namespace of the broken one.

### Signals and `docker stop`: a trap with a real number

`docker stop` sends SIGTERM and, after 10 seconds, SIGKILL. A well-behaved server stops quickly. I tested two servers. One has a SIGTERM handler:

```js
process.on("SIGTERM", () => { console.log("got SIGTERM, bye"); srv.close(() => process.exit(0)); });
```

```text
$ time docker stop l8-web
real    0m0.299s
$ docker logs l8-web | tail -2
listening on 3000
got SIGTERM, bye
exit=0
```

The other server (`server-nosig.js`) has no handler. Because it runs as PID 1 in the container, and Linux does not apply the default "terminate" action for signals to PID 1 unless the program installs a handler, the SIGTERM is simply ignored:

```text
$ time docker stop l8-nosig
real    0m10.216s
exit=137
```

It took the whole 10 seconds and ended with `137` (killed). Now the same server with `--init`, which puts a tiny init program (tini) in front as PID 1 to forward signals and clean up zombie processes:

```text
$ time docker stop l8-init
real    0m0.208s
exit=143
```

Quick and clean (`143` is SIGTERM). In Kubernetes the same trap makes every pod take the full `terminationGracePeriodSeconds` (30 s) to stop, which makes rollouts slow. It also happens when a Dockerfile uses the **shell form** `CMD node server.js`, because then `/bin/sh` is PID 1 and may not pass the signal on. Use the exec form `CMD ["node", "server.js"]` (see [lesson 1](/docker-kubernetes/lesson-1)).

### Start-up failures with the exact error text

All of these are real Docker errors from my runs. Learn to recognise them.

**Command not found:**

```text
docker: Error response from daemon: failed to create task for container: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: exec: "nope": executable file not found in $PATH
```

The long prefix is Docker's plumbing. The useful part is at the end: `exec: "nope": executable file not found in $PATH`. Typo in `CMD`, or the binary is not in the image.

**File not found (the app, not the runtime):**

```text
Error: Cannot find module '/app/missing.js'
  code: 'MODULE_NOT_FOUND',
```

Here Node started fine and then could not find the file. The error comes from your program. Check `WORKDIR`, `COPY` paths and `.dockerignore`.

**Image tag does not exist:**

```text
Error response from daemon: failed to resolve reference "mirror.gcr.io/library/node:22-doesnotexist": mirror.gcr.io/library/node:22-doesnotexist: not found
```

**Port already in use:**

```text
docker: Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint l8-b (ffd0774015bc...): Bind for 0.0.0.0:18081 failed: port is already allocated
```

Note what `docker ps -a` then showed: `l8-b | Created`. The container was created but never started. The cause: another container already published host port 18081. Fix by choosing another host port (`-p 18082:3000`).

**Binary built for the wrong environment.** I made a tiny image `FROM scratch` that holds only a copy of busybox. My first try copied a *dynamically linked* busybox, and the container died with:

```text
exec /busybox: no such file or directory
```

with exit code `255`. The file **exists**. What is missing is the *loader* (the dynamic linker) that the binary needs, which a `scratch` image does not have. This confusing message ("no such file" for a file that is there) is a classic for people who build in one base image and run in another. The fix was a **static** busybox (the `1.36-musl` variant).

### An image with no shell

That static `scratch` image is a good test for a very common problem: a minimal or "distroless" image has no `sh`, so `docker exec -it ... sh` fails.

```text
$ docker exec l8-nosh sh
OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH
```

You are not stuck. Attach a tools container that shares the namespaces of the broken one:

```bash
docker run --rm --network container:l8-nosh mirror.gcr.io/library/busybox:1.36 wget -qO- localhost:8080
docker run --rm --pid container:l8-nosh mirror.gcr.io/library/busybox:1.36 ps
```

```text
static page
PID   USER     TIME  COMMAND
    1 1000      0:00 /busybox httpd -f -p 8080 -h /www
   13 root      0:00 ps
```

The first command reached the app through its network. The second sees its **processes** (the web server is PID 1, running as user 1000). This is how I would debug a distroless image on a laptop. In Kubernetes there is a ready-made version of this: the **ephemeral container**, below. (When I tried to read the other container's files through `/proc/1/root`, I got `Permission denied`, because the server ran as user 1000 and my tools container ran as root without the right capabilities. Namespaces are a boundary, and sharing a PID namespace does not give you free access to everything.)

## Part 2: Kubernetes

### The first four commands

When a pod looks wrong, I run these in order.

```bash
kubectl get pods -o wide        # state, restarts, which node, which IP
kubectl describe pod NAME       # everything about it, with EVENTS at the bottom
kubectl logs NAME               # what the app printed
kubectl get events --sort-by=.lastTimestamp   # recent events in the namespace
```

`kubectl describe` is the most useful of the four. Its last section, **Events**, is a short diary of what the scheduler and the kubelet did and what went wrong. Here is a real one, for a pod that cannot be scheduled. I made a pod that asks for 100 CPUs:

```text
$ kubectl -n lab8 describe pod too-big
Name:         too-big
Namespace:    lab8
Node:         <none>
Status:       Pending
Containers:
  app:
    Image:      notes-api:1.0
    Requests:
      cpu:        100
      memory:     1Gi
Conditions:
  Type           Status
  PodScheduled   False
QoS Class:       Burstable
Events:
  Type     Reason            Age    From               Message
  ----     ------            ----   ----               -------
  Warning  FailedScheduling  8m37s  default-scheduler  0/1 nodes are available: 1 Insufficient cpu. no new claims to deallocate, preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling.
```

(I removed some lines for space.) See how much it tells you. `Node: <none>` and `PodScheduled False` say the scheduler has not placed it. The event says why: `Insufficient cpu`.

### `kubectl logs`: the flags you need

```bash
kubectl logs NAME                      # the one container (if the pod has one)
kubectl logs NAME -c CONTAINER         # pick a container in a multi-container pod
kubectl logs NAME --previous           # the logs of the LAST crashed instance
kubectl logs -f NAME                   # follow, like tail -f
kubectl logs NAME --since=10m          # only recent lines
kubectl logs -l app=notes-api --tail=20  # by label, last 20 lines of each
```

The one to remember is **`--previous`**. When a container crashes and restarts, plain `kubectl logs` shows the *new* instance, which may have just started and printed nothing yet. The reason for the crash is in the *previous* instance. The Kubernetes docs list `--previous` for exactly this.

> [!note] **Status:** these commands are standard and documented. I could not run `logs` against a real container (no kubelet), so there is no pasted output. **Reviewed, not run on a cluster here.**

### `kubectl exec`, `port-forward` and `debug`

```bash
kubectl exec -it NAME -- sh            # a shell in the container
kubectl exec NAME -- cat /etc/notes/app.json   # one command
kubectl port-forward pod/NAME 8080:3000   # laptop:8080 -> pod:3000
kubectl port-forward svc/NAME 8080:80     # same, through a Service
```

When the pod is not running, these fail early with a clear message. This one is real:

```text
$ kubectl -n lab8 port-forward pod/web-89f547c8c-8bs4b 8080:3000
error: unable to forward port because pod is not running. Current status=Pending
```

**Ephemeral containers** are the answer to the "no shell in the image" problem from the Docker half. `kubectl debug` adds a temporary container (with tools such as busybox) into a **running** pod, and `--target` makes it share the process namespace of your app container. I ran it against a pod in my lab. The API server accepted it, and the pod now had this in its spec (real output, shown as JSON):

```json
[
  {
    "command": ["sleep", "3600"],
    "image": "mirror.gcr.io/library/busybox:1.36",
    "imagePullPolicy": "IfNotPresent",
    "name": "dbg",
    "resources": {},
    "securityContext": { "capabilities": { "add": ["SYS_PTRACE"] } },
    "targetContainerName": "notes-api",
    "terminationMessagePath": "/dev/termination-log",
    "terminationMessagePolicy": "File"
  }
]
```

Notice `targetContainerName` (which container's namespaces to share) and that the `general` profile added the `SYS_PTRACE` capability so tools like `strace` can attach. In real use you add `-it` and get a shell: `kubectl debug -it NAME --image=busybox:1.36 --target=CONTAINER`. Mistyping `--target` is caught by the server, as I found out. My first try used the wrong container name, and the answer was `spec.ephemeralContainers[0].targetContainerName: Not found: "web"`. (The container name came from the image name, `notes-api`, since I had made the Deployment with `kubectl create deployment`.) Two limits: an ephemeral container cannot be removed once added (delete the pod to get rid of it), and it only works on a pod that has been scheduled.

Two more `kubectl debug` forms, from the docs:

- **`--copy-to=NAME2`** makes a **copy** of the pod with a change (a different image, or a different command). It is for pods that crash at start, where you cannot `exec` because the container never stays up. For example: copy the pod, change the command to `sleep 3600`, and `exec` into the copy to look around. I ran the copy form against my lab and a `web-debug` pod appeared next to the original.
- **`kubectl debug node/NAME -it --image=ubuntu`** starts a pod on that node with the node's filesystem mounted at `/host`. It is for node-level problems.

### The status words, and where the answer is

Here is the table I use. The "meaning" column is from the Kubernetes docs (Pod lifecycle, Images, resource management). I could not produce these states in my lab, because they need a kubelet, so I do **not** show terminal output for them. **From the docs, not run on a cluster here.**

| Status you see | What it means | Where the answer is |
|---|---|---|
| `Pending` (no node) | The scheduler cannot place the pod | `describe` events: `FailedScheduling` |
| `Pending` / `ContainerCreating` (has node) | The node is preparing: pulling an image, mounting a volume | `describe` events from the kubelet |
| `ErrImagePull`, `ImagePullBackOff` | The node cannot download the image; it retries with a growing delay up to 5 minutes | `describe` events: reason and registry message |
| `CrashLoopBackOff` | The container starts, exits, restarts; the wait doubles (10 s, 20 s, 40 s, up to 300 s) | `logs --previous`, exit code in `describe` |
| `OOMKilled` (in `Last State`) | The container passed its memory limit. Exit code 137 | `describe`: `Reason: OOMKilled` |
| `Error`, `Completed` | The container exited (non zero or zero) and will not restart if `restartPolicy` says so | `logs`, exit code |
| `Running` but `0/1` ready | The readiness probe fails | `describe` events: `Readiness probe failed` |
| `Terminating` for a long time | A delete was requested but cannot finish (a finalizer, or a node that is gone) | `describe`, finalizers |
| `Evicted` | The node removed the pod, for example under memory or disk pressure | `describe` message |

Notice the pattern: **the answer is almost always in `describe` events, `logs --previous`, or the exit code.**

### Pending: three real causes, three real messages

Pending is the one status I can fully show, because the scheduler is real. I made three pods that could never be placed, each for a different reason. These are real events from my lab.

**1. Not enough CPU or memory (the pod asked for 100 CPUs):**

```text
Warning  FailedScheduling  default-scheduler  0/1 nodes are available: 1 Insufficient cpu. no new claims to deallocate, preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling.
```

**2. The node selector matches no node (the pod wants a node labelled `disktype: ssd`):**

```text
Warning  FailedScheduling  default-scheduler  0/1 nodes are available: 1 node(s) didn't match Pod's node affinity/selector. no new claims to deallocate, preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling.
```

**3. The volume claim does not exist (the pod mounts a claim named `no-such-claim`):**

```text
Warning  FailedScheduling  default-scheduler  0/1 nodes are available: persistentvolumeclaim "no-such-claim" not found. not found
```

The format is always the same: `0/N nodes are available:` followed by the **count of nodes and the reason for each group**. Read the reasons. They are the whole answer. Other reasons you will see: `node(s) had untolerated taint` (the node refuses pods without a matching toleration; I saw `{node.kubernetes.io/unreachable: }` in my lab when the fake node's heartbeat stopped),.

Other Pending causes from the earlier lessons: a PVC that is itself `Pending` (lesson 6; real event `no persistent volumes available for this claim and no storage class is set`), and a ResourceQuota that stops the pod from being created at all (lesson 7; the pod does not even appear, the error is on the ReplicaSet).

One honest note: the pods `crashy`, `typo-tag` and `memory-hog` (their manifests are in the next sections) were **scheduled** (event `Successfully assigned lab8/crashy to fake-node-1`) but stayed `Pending`, because nothing could start them. In a real cluster they would move on to the states in the next sections.

### CrashLoopBackOff

**What it is.** The container starts, exits, and the kubelet restarts it with a delay that doubles (10 s, 20 s, 40 s, and so on, capped at 5 minutes). It resets after the container has run for 10 minutes without a problem. `CrashLoopBackOff` is the display word for "waiting to restart".

**Common causes** (listed in the docs): the app has a bug or exits on bad config (our missing `DATABASE_URL` is exactly this, and the Docker restart loop above is the same thing), the container has too little memory or CPU, or a liveness or startup probe keeps failing.

**What to run:**

```bash
kubectl logs NAME --previous      # why did the last run die?
kubectl describe pod NAME         # Last State: exit code, reason; events
```

This is a pod I wrote to show it (it prints an error and exits 1):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: crashy
spec:
  restartPolicy: Always
  containers:
    - name: app
      image: mirror.gcr.io/library/busybox:1.36
      command: ["sh", "-c", "echo 'FATAL: DATABASE_URL is not set' >&2; exit 1"]
```

> [!note] **Status:** this manifest passed `kubeconform -strict` and was accepted by the real API server, and the scheduler assigned it to my fake node. It never ran there. **Reviewed, not run on a cluster here.** The same program, run as a Docker container, produced the real restart loop above (`restarts=6`).

Reading `describe` for it, per the docs: in the container section you would look at `State: Waiting, Reason: CrashLoopBackOff`, and `Last State: Terminated` with an `Exit Code` and a `Reason`. Exit code 1 and an error in `--previous` logs means "my code failed". Exit code 137 means "killed", so look at OOM and probes. Exit code 127 or 126 means "bad command".

> [!warn] **`kubectl logs` shows the new container, not the one that crashed.** In a crash loop, the new container may be seconds old and silent. Always add `--previous` for the crash reason.

### ImagePullBackOff

**What it is.** The node tried to download the image and failed, and it will retry with growing delays (up to 5 minutes). `ErrImagePull` is the first failure, `ImagePullBackOff` is the waiting.

**Common causes** (from the Images docs and the debug guide): the image name or tag has a typo, the tag does not exist (we saw the Docker error `not found` above for `node:22-doesnotexist`), the image is in a private registry and the pod has no `imagePullSecrets` (the Secret from lesson 6), or the registry is rate limiting or unreachable from the node.

**What to run:** `kubectl describe pod NAME`, and read the Events for the `Failed` and `Pulling` reasons and the registry's message. Then **test the pull yourself from a machine with the same access**: `docker pull IMAGE`. The Kubernetes debug guide suggests exactly this. If you get `not found`, it is the name or tag. If you get `unauthorized`, it is credentials.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: typo-tag
spec:
  containers:
    - name: app
      image: mirror.gcr.io/library/node:22-doesnotexist
```

> [!note] **Status:** valid manifest, accepted by the API server. **Reviewed, not run on a cluster here.** The real registry answer for that image is the Docker message shown earlier (`failed to resolve reference ... not found`). Kubernetes wraps the same registry error into its event text.

> [!warn] **`:latest` and no tag are not the same as "newest on this node".** If you omit the tag, Kubernetes treats it as `latest` and defaults `imagePullPolicy` to `Always`, so every pod start contacts the registry. For repeatable deployments use a specific tag (or better, a digest).

### OOMKilled

**What it is.** The container used more memory than its limit, and the kernel killed it. In `kubectl describe pod`, under the container, the docs show `Last State: Terminated` with `Reason: OOMKilled` and `Exit Code: 137`, and a `Restart Count` that grows. Like the Docker run above, there is **no message in the logs**.

**What to run:** `kubectl describe pod NAME` and look at `Last State`. Then check memory use over time (`kubectl top pod`, which needs metrics-server; in my lab it printed `error: Metrics API not available`, the classic sign that it is missing).

**Fix:** find the leak or the large allocation. If the app is healthy and just needs more, raise the memory limit and the request together. Do not only raise the limit: the scheduler packs by *requests*, so a pod with a low request and a high limit can push a node into memory pressure.

The pod I wrote for this test (a Node program that keeps allocating, limit 64Mi):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: memory-hog
spec:
  containers:
    - name: app
      image: mirror.gcr.io/library/node:22-alpine
      command: ["node", "-e", "const a=[];setInterval(()=>a.push(Buffer.alloc(1e7,1)),100)"]
      resources:
        requests:
          memory: 32Mi
        limits:
          memory: 64Mi
```

> [!note] **Status:** accepted by the real API server, scheduled to the fake node, never started. **Reviewed, not run on a cluster here.** The same limit enforced by a real container runtime is the Docker run above (`exit=137 oom=true`).

### Readiness failures and empty Services

A pod that is `Running` but `0/1` ready has a failing readiness probe. `describe` shows probe failure events. A Service in front of it then has **no endpoints**. This is the real Service check from lesson 5, and I ran it. I exposed a Deployment whose only pod was not ready:

```text
$ kubectl -n lab8 get endpointslices -l kubernetes.io/service-name=web
NAME        ADDRESSTYPE   PORTS     ENDPOINTS   AGE
web-lrgpc   IPv4          <unset>   <unset>     0s

$ kubectl -n lab8 describe svc web | grep -E 'Selector|Endpoints'
Selector:                 app=web
Endpoints:
```

`ENDPOINTS <unset>` and an empty `Endpoints:` line mean no ready pod matches. There are two causes, and you must tell them apart: **(a)** the Service selector does not match the pod labels (a typo), or **(b)** the labels match but the pods are not ready. Check with `kubectl get pods -l app=web` (using the Service's selector). If pods show up there but not ready, go to readiness. If nothing shows up, the selector is wrong.

### Service debugging in order

When "I cannot reach my app", walk the path in order, nearest to farthest:

1. Is the pod `Running` and `Ready`? (`kubectl get pods`)
2. Does the app answer inside the pod? (`kubectl exec` and `wget`/`curl localhost:PORT`, or `kubectl port-forward pod/NAME`)
3. Does the Service have endpoints? (`kubectl get endpointslices -l kubernetes.io/service-name=NAME`)
4. Does the Service `targetPort` match the port the app listens on?
5. Does DNS work from another pod? (`kubectl exec OTHERPOD -- nslookup NAME`)
6. Is a NetworkPolicy blocking it? (lesson 5)
7. Is the Ingress and its controller healthy? (`kubectl describe ingress NAME`)

Each step removes one layer. Going nearest to farthest means that when a step fails, you know the layer.

### Everything is applied but "nothing happens": check the object, not your file

The Kubernetes debug guide has a point I like: if a pod runs but does not do what you meant, the YAML may have been accepted with part of it ignored, for example a misspelled key. Two checks. First, use strict validation: in my tests the typo `envfrom` was accepted by non-strict `kubeconform` and caught by `kubeconform -strict` and by the real API server (`strict decoding error: unknown field ...`), as lesson 6 showed. Second, compare what you sent with what the server stored: `kubectl get pod NAME -o yaml` and look for fields you wrote that are missing. And `kubectl explain pod.spec.containers.resources` (needs a cluster connection) prints the documentation of any field.

### Cluster-level problems

If many pods on one node have trouble, look at the node.

```bash
kubectl get nodes
kubectl describe node NAME
```

A healthy node is `Ready`. A node whose kubelet stopped reporting becomes `NotReady`, and, according to the docs, its pods are evicted after about five minutes. `describe node` lists **Conditions** (`Ready`, `MemoryPressure`, `DiskPressure`, `PIDPressure`), **Taints**, and **Allocated resources**. Here is a real piece from my lab node, which is useful for judging "is this node full?":

```text
Allocated resources:
  (Total limits may be over 100 percent, i.e., overcommitted.)
  Resource           Requests     Limits
  --------           --------     ------
  cpu                1 (50%)      0 (0%)
  memory             512Mi (12%)  1Gi (25%)
```

Remember from lesson 7: this is requests, not usage. Also notice the note that limits may be over 100%: limits can add up to more than the machine has (overcommit), while requests cannot.

For control-plane problems (the API server is slow, a controller does nothing), the docs point to the logs of the control-plane components and `kubectl cluster-info dump`. On a managed cloud cluster you cannot see those; the provider's tools do. For a self-managed node, the kubelet logs (usually via `journalctl -u kubelet`) say why a node is not healthy. A short list of node-level causes: the kubelet is down, the disk is full (`DiskPressure`), the container runtime is stuck, the network plugin is not working, or the machine is gone.

## Putting it together: a flow you can follow

| You see | First command | Likely cause | Fix direction |
|---|---|---|---|
| `Pending`, no node | `describe pod` (events) | Insufficient resources, selector, taint, unbound PVC | Lower requests, add nodes, fix selector, fix claim |
| `ImagePullBackOff` | `describe pod`, then `docker pull` | Name, tag, credentials, registry limits | Fix image, add `imagePullSecrets` |
| `CrashLoopBackOff` | `logs --previous` | App error, bad config, missing env | Fix config or code |
| Restarts, no error in logs | `describe` (Last State) | `OOMKilled` (137), or a failing liveness probe | Raise memory, fix leak, loosen probe |
| `Running`, `0/1` | `describe` (probe events) | Readiness failing | Fix endpoint, timing, dependency |
| Service has no endpoints | `get endpointslices`, `get pods -l` | Selector typo, or pods not ready | Fix labels or readiness |
| Slow rollout, 30 s per pod | Check the app's signal handling | SIGTERM ignored, PID 1 problem | Handle SIGTERM, exec form, `--init` |
| Many pods bad on one node | `describe node` | Pressure, kubelet, network | Drain and repair node |

## Commands to know

| Goal | Docker | Kubernetes |
|---|---|---|
| List including stopped | `docker ps -a` | `kubectl get pods -o wide` |
| Why did it stop? | `docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}'` | `kubectl describe pod` (Last State) |
| What did the app say? | `docker logs NAME` | `kubectl logs NAME --previous` |
| Shell inside | `docker exec -it NAME sh` | `kubectl exec -it NAME -- sh` |
| No shell in image | `docker run --network container:NAME TOOLS` | `kubectl debug -it NAME --image=busybox --target=C` |
| Live CPU and memory | `docker stats` | `kubectl top pod` |
| Changed files | `docker diff NAME` | `kubectl exec NAME -- ls` |
| Platform events | `docker events` | `kubectl get events --sort-by=.lastTimestamp` |
| Reach the app | `docker port NAME` | `kubectl port-forward` |

## Try it

You can do the Docker steps on any machine with Docker.

1. Run `docker run -d --name t1 mirror.gcr.io/library/busybox:1.36 sh -c 'echo boom >&2; exit 3'` (or use `busybox` from Docker Hub). `docker ps` shows nothing. How do you find the container, the message and the exit code?
2. Run a container with `--memory 32m` that allocates memory in a loop (adapt `hog.js`). What exit code and flag do you expect? Is there an error in the logs?
3. A Node server in your image ignores SIGTERM. Give two different fixes (one in the Dockerfile or run command, one in the code).
4. A Kubernetes pod is `Pending`. `describe` shows `0/3 nodes are available: 3 node(s) had untolerated taint`. What does it mean, and what are two ways to fix it?
5. A pod is in `CrashLoopBackOff`. `kubectl logs POD` prints nothing. What do you run next?
6. A Service has an empty endpoints list. Which two commands tell you if it is a selector problem or a readiness problem?
7. Your image has no shell. Name two ways to inspect a running container from Kubernetes or Docker.

### Answers

1. `docker ps -a` lists it as `Exited (3)`. `docker logs t1` prints `boom`. `docker inspect t1 --format '{{.State.ExitCode}}'` prints `3`.
2. Exit code `137` and `OOMKilled` true in `docker inspect`. There is no error in the logs because the process was killed by SIGKILL and had no chance to print.
3. In the run command or Dockerfile: use the exec form for the command and run with `--init` (or add `tini`) so signals are forwarded. In the code: add `process.on("SIGTERM", ...)` that closes the server and exits.
4. All three nodes have a taint that the pod does not tolerate. Fix by adding a matching `tolerations` entry to the pod, or by removing or changing the taint on the nodes, or by adding nodes without the taint.
5. `kubectl logs POD --previous` (logs of the crashed instance) and `kubectl describe pod POD` (exit code, reason, events).
6. `kubectl get pods -l <the Service's selector>`: if no pods show up, the selector or labels are wrong; if pods show up but are not `READY`, it is readiness (check `describe pod` events). Also `kubectl get endpointslices -l kubernetes.io/service-name=NAME`.
7. Kubernetes: `kubectl debug` with an ephemeral container (`--target`), or `--copy-to` a copy with a different image. Docker: run a tools container with `--network container:NAME` and `--pid container:NAME`.

## Interview questions

### Q1. A pod is in CrashLoopBackOff. How do you debug it? (Must know)

I explain what the state means first: the container keeps exiting, and Kubernetes waits longer between restarts (10, 20, 40 seconds, up to five minutes). Then I run `kubectl logs POD --previous` to see the crashed instance, because plain `logs` shows the new one. Then `kubectl describe pod` to see the last state, the exit code and the events. Exit code 1 and an error means app or config problem. 137 means killed, so I check OOM and probes. 126 or 127 means a bad command. If it crashes too fast to `exec`, I use `kubectl debug --copy-to` with a sleep command to get a shell in a copy.

### Q2. What does exit code 137 mean? (Must know)

It is 128 plus 9, so the process was killed by SIGKILL. In Kubernetes there are two common reasons. One is OOMKilled: the container passed its memory limit, and `describe` shows `Reason: OOMKilled`. The other is that the pod did not stop within `terminationGracePeriodSeconds` after SIGTERM, so it was force-killed. I have reproduced both with Docker: a 64 MiB limit gave `exit=137 oom=true`, and a server with no signal handler gave 137 after a 10 second stop.

### Q3. A container restarts but there is no error in the logs. Why? (Trap)

An OOM kill gives no message, because SIGKILL cannot be caught. The program never gets to print anything. I check `kubectl describe pod` for `Last State: Terminated, Reason: OOMKilled, Exit Code: 137`. It could also be a failing liveness probe, where the kubelet kills the container (events show `Liveness probe failed`). The trap is to keep reading the app logs when the answer is in the platform events and the exit code.

### Q4. ImagePullBackOff: what are the causes and how do you find the real one? (Must know)

Causes: wrong image name or tag, a tag that was never pushed, no credentials for a private registry, or a registry that is rate limiting or unreachable from the node. I run `kubectl describe pod` and read the events for the registry's message, and I try `docker pull` of the same image from a machine with similar access. `not found` points to name or tag, `unauthorized` points to credentials. For a private registry I check the `imagePullSecrets`: it must exist in the same namespace as the pod.

### Q5. A pod is Pending. What are the possible reasons? (Must know)

Pending means either not scheduled, or scheduled but not started. For not scheduled, `describe` events from the default scheduler give the reason: insufficient CPU or memory (based on requests), a node selector or affinity that matches nothing, untolerated taints, or a PVC that does not exist or is not bound. I have seen the exact messages for the first three. For scheduled but waiting, it may be pulling an image or waiting for a volume to attach. Also if a ResourceQuota blocks creation, the pod does not exist at all and the error is on the ReplicaSet events.

### Q6. `kubectl logs` shows nothing for a pod that is clearly failing. What else do you try? (Trap)

First `--previous`, since the current instance may be new. Then `-c` in case it is a multi-container pod and I am looking at the wrong container, and init containers (`-c INIT_NAME`). Then `describe` for events, because the failure may be before the app starts (image pull, volume mount, missing ConfigMap or Secret). And if the process exits without any output, the exit code tells the story.

### Q7. How do you debug a container whose image has no shell? (Senior signal)

I use an ephemeral container: `kubectl debug -it POD --image=busybox --target=CONTAINER`. It adds a temporary container with tools that shares the process namespace of the target, so I can see its processes and its network. It cannot be removed afterwards, so it is for debugging only. For a pod that crashes at start I use `--copy-to` to make a copy with a different command or image. On a laptop with Docker I do the same with a tools container sharing `--network container:NAME` and `--pid container:NAME`, which I have tested with a `FROM scratch` image that had no `sh`.

### Q8. Why does `docker stop` sometimes take exactly 10 seconds, and what is the Kubernetes version of this? (Senior signal)

The process is PID 1 in its container and has no SIGTERM handler. Linux does not apply the default action for signals sent to PID 1, so the signal is ignored. Docker waits 10 seconds and then sends SIGKILL. I measured 10.2 seconds and exit code 137, against 0.2 seconds with `--init` and 0.3 seconds with a handler. In Kubernetes it shows as every pod taking the full `terminationGracePeriodSeconds` of 30 seconds to stop, so rollouts and scale-downs are slow. The fixes are a SIGTERM handler, the exec form of `CMD`, and an init like tini. A shell-form `CMD` is a common cause, because the shell is PID 1 and may not forward the signal.

### Q9. A Service returns connection refused or times out. Walk me through it. (Must know)

I go from the pod outward. Is the pod ready? Does the app answer on its port inside the pod (`exec` or `port-forward`)? Does the Service have endpoints (`get endpointslices`)? If endpoints are empty, is it a selector typo or are the pods not ready? Does the Service `targetPort` match the real listening port? Does DNS resolve from another pod? Is a NetworkPolicy blocking it? Is the Ingress healthy? Each step removes one layer, so I always know which layer is failing.

### Q10. A node is `NotReady`. What do you do? (Senior signal)

I run `kubectl describe node` and read the conditions and events: is it the kubelet not reporting, memory or disk pressure, or a network problem? Pods on a NotReady node are evicted after about five minutes by default. If it is a cloud VM, I look at the instance health and the kubelet logs on the machine, for example with `journalctl -u kubelet`. In the meantime I check that my apps have more than one replica spread across nodes and a PodDisruptionBudget, so one node does not take the service down. If the node is unrecoverable I drain and replace it.

### Q11. What is the difference between pod status and pod phase? (Trap)

Phase is the official field in the API: `Pending`, `Running`, `Succeeded`, `Failed` or `Unknown`. The STATUS column in `kubectl get pods` is a display word that kubectl builds from phase, container states and other fields, so you see `CrashLoopBackOff`, `ImagePullBackOff`, `Terminating`, `Init:0/1` and so on. They are not phases. The Pod lifecycle docs warn about confusing the two. A pod in `CrashLoopBackOff` has the phase `Running`, which surprises people.

### Q12. My manifest applies fine but the app ignores one setting. How could that be? (Trap)

Most likely the field was misspelled or nested wrongly, and was ignored. Older kubectl and non-strict schema checks accept unknown fields. I use `kubeconform -strict` in CI and the server's strict field validation, and I compare `kubectl get pod -o yaml` with my file to see missing fields. I have seen `envfrom` (wrong case) pass non-strict validation and fail strict.

## Key takeaways

- Use the loop: **state, logs, events or exit code, compare, change one thing.**
- Docker: `ps -a`, `logs`, `inspect` (exit code, `OOMKilled`), `exec`, `diff`, `stats`. Exit codes above 128 mean "killed by signal": `137` is KILL, `143` is TERM.
- An OOM kill leaves **no log message**. Look for exit `137` and `OOMKilled`.
- A process that ignores SIGTERM as PID 1 makes `docker stop` wait 10 s, and a pod wait 30 s. Handle the signal, use the exec form, use `--init`.
- Kubernetes: `describe` events are the answer to Pending and image problems, and `logs --previous` is the answer to CrashLoopBackOff.
- `Pending` events have a fixed shape: `0/N nodes are available:` plus reasons (Insufficient cpu, selector, taint, missing claim).
- `ImagePullBackOff`: check name, tag, credentials, then `docker pull` it yourself.
- Empty Service endpoints mean a selector typo or unready pods. Check which.
- `kubectl debug` gives you an ephemeral container for pods with no shell, `--copy-to` for pods that crash at start.
- Status is a display word. Phase is the real state.
