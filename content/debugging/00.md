> **In one line:** never fix what you have not measured. Every performance or bug scenario in an interview is answered by the same four moves: **measure** the symptom, **isolate** which layer owns it, **hypothesize** one cause, **verify** by changing one thing and measuring again.

Senior interviewers rarely want the "right" answer to "the page is slow." They want to hear **how you would find the answer** without guessing. This lesson is the framework that every later lesson in this series reuses, plus the tool map that tells you which panel answers which question.

## The four moves

```text
1. MEASURE     Turn "it feels slow" into a number, a place and a baseline.
2. ISOLATE     Find which layer owns the time: network, server, database, main thread, rendering.
3. HYPOTHESIZE Form ONE specific, testable explanation for that layer.
4. VERIFY      Change one thing, measure again against the baseline. Keep it only if the number moved.
```

If an answer skips straight to "add `useMemo`" or "add Redis", it has skipped moves 1 and 2. That is the most common way to sound junior.

## Move 1: Measure (pin down the symptom)

Before touching code, ask questions that turn a complaint into a **precise problem statement**:

| Question | Why it matters |
|---|---|
| **What exactly is slow?** Load, a click, scrolling, a specific API, one page? | "Slow" is not a metric. Load speed and interaction speed have different causes |
| **How slow, compared to what?** 3 s vs a 1 s goal? vs last week? | Gives you a baseline and a finish line |
| **For whom?** All users, mobile, one region, one browser, logged-in only, large accounts? | A problem for 1% of users on mobile is not the same as a problem for everyone |
| **Since when?** | Correlate with a deploy, a data-volume jump, a traffic spike, a dependency update |
| **Is it constant or intermittent?** | Constant means code or config; intermittent means contention, cache misses, cold starts, noisy neighbours |
| **What changed?** | Releases, feature flags, new third-party scripts, data growth, infrastructure changes |
| **Where is the evidence?** Field data (RUM), logs, traces, user reports | Your laptop is the least representative device |

### Use percentiles, not averages

If 1% of requests take 10 seconds, the *average* looks fine and thousands of users suffer. Always look at **p50, p95 and p99** for latency and the **75th percentile** for Core Web Vitals ([Browser Contract, Lesson 09](/browser/lesson-9)).

### Field data vs lab data

- **Field data (RUM, analytics, CrUX)** says *whether and for whom* there is a problem.
- **Lab data (DevTools, Lighthouse, a load test)** lets you *reproduce and debug* it. Throttle the CPU (4x or 6x slowdown) and the network, because your development machine hides problems that a mid-range phone exposes.

## Move 2: Isolate (which layer owns the time?)

A user action passes through layers. Your job is to find the layer that holds most of the time **before** optimising anything.

```text
User clicks ─▶ [Main thread: handler, render] ─▶ [Network] ─▶ [Edge/CDN] ─▶ [App server]
                                                                              │
                              ◀──────────── response ◀── [DB / cache / 3rd-party APIs]
```

The first fork is the most important one:

> **Is the time spent *waiting for the network/server*, or *working on the main thread* in the browser?**

Open the **Network** tab, click the slow request, and read the **Timing** breakdown:

| Phase | Meaning | If it is large… |
|---|---|---|
| **Queueing / Stalled** | Waiting for a connection slot or a higher-priority request | Too many parallel requests; HTTP/1.1 limits; blocked by scripts |
| **DNS Lookup / Initial Connection / SSL** | Connection setup | Distance, no keep-alive, no CDN, many origins ([Browser Contract, Lesson 00](/browser/lesson-0)) |
| **Waiting for server response (TTFB)** | The server and everything behind it is working | **Backend problem**: slow code, database, external calls, cold start ([Lesson 02](/debugging/lesson-2)) |
| **Content Download** | Receiving bytes | Payload too big, missing compression, slow link |

Then read the **Performance** panel for what happens *after* the response arrives: scripting, rendering and painting on the main thread.

### The decision tree

```text
Is the page slow...
├─ ...before anything appears?           → Network + server: TTFB, redirects, render-blocking CSS/JS, bundle size
│                                           (Lessons 02 and 06)
├─ ...after the response arrives,        → Main thread: parsing, re-rendering, long tasks, hydration
│   but the API was fast?                   (Lessons 01, 03, 07)
├─ ...only on interaction (click/type)?  → Handlers, re-renders, long tasks (INP)         (Lessons 01, 03, 08)
├─ ...worse the longer the tab is open?  → Memory leak                                      (Lesson 04)
├─ ...making the same request twice?     → Effects, double submits, races                   (Lesson 05)
└─ ...jumping around as it loads?        → Layout shift (CLS)                               (Lesson 08)
```

## The tool map

| Question | Tool | What to look at |
|---|---|---|
| Which request is slow? Where does its time go? | **DevTools Network** tab | Waterfall, Timing breakdown, size (transferred vs resource) |
| What is the main thread doing? | **DevTools Performance** panel | Long tasks (red corners), Scripting vs Rendering vs Painting, flame chart |
| Why did this component re-render? | **React DevTools Profiler** | Commit flame chart, "why did this render", highlight updates |
| What is in my bundle? | `@next/bundle-analyzer`, `source-map-explorer`, Lighthouse "unused JavaScript" | Largest modules, duplicates |
| Is memory growing? | **DevTools Memory** tab, Performance monitor | Heap snapshots, detached DOM nodes, listener count |
| How do real users experience it? | RUM with the `web-vitals` library, **CrUX**, Search Console | p75 LCP, INP, CLS by device and route |
| What does the whole page look like cold? | **Lighthouse**, **WebPageTest** | Filmstrip, waterfall, LCP element, blocking resources |
| Which part of the request is slow server-side? | **APM / tracing** (OpenTelemetry, Datadog, X-Ray), `Server-Timing` header | Span breakdown: handler, DB, external calls |
| Why is this query slow? | **`EXPLAIN (ANALYZE, BUFFERS)`**, `pg_stat_statements` | Seq scans, sorts, row estimates vs actual ([Backend, Lesson 07](/backend/lesson-7)) |
| What happened to this one request? | **Structured logs** by request ID | The full story, errors, durations ([Backend, Lesson 05](/backend/lesson-5)) |
| Is the event loop blocked on the server? | Event-loop-lag metric, CPU profile | p99 lag, flame graph ([Backend, Lesson 10](/backend/lesson-10)) |

## Move 3: Hypothesize (one cause at a time)

State the hypothesis so that it can be **proved wrong**:

- Weak: "Maybe the database is slow."
- Strong: "The `/orders` endpoint issues one query per order line (N+1), so latency grows with the number of lines. If true, a customer with 200 lines should show ~200 queries in the trace, and `include` should drop it to 2."

A good hypothesis predicts **what you will see** if it is true. It also tells you the cheapest experiment.

### Techniques for narrowing down

- **Bisect.** If it used to be fast, find the commit with `git bisect`, or toggle feature flags and bundles to halve the search space.
- **Remove, don't add.** Disable third-party scripts, extensions (use an incognito window), or a suspect component and see if the symptom disappears.
- **Compare a fast case to a slow case.** Same endpoint, small account vs large account: what differs?
- **Look at the shape of the cost.** Linear in list size (N+1, rendering every row), step changes at deploys (a regression), growth over time (leak), periodic spikes (cron jobs, GC, cache expiry).
- **Reproduce at scale.** A bug that needs 10,000 rows will not show in your seed data. Generate realistic volumes.

## Move 4: Verify (change one thing, compare to the baseline)

1. **Record the baseline** first (same device, same throttling, several runs; take the median).
2. **Change one variable** only.
3. **Re-measure** and compare. A real fix moves the number meaningfully, not by noise.
4. **Check for regressions elsewhere** (a cache can fix latency and break freshness).
5. **Keep a guard**: a performance budget in CI, an alert, a regression test, a dashboard panel, so it cannot silently return.

```ts
// A minimal, repeatable in-browser measurement
performance.mark("filter:start");
applyFilter(rows, query);
performance.mark("filter:end");
performance.measure("filter", "filter:start", "filter:end");
console.table(performance.getEntriesByName("filter"));
```

## Talking it through in an interview

A structure that works for any scenario question:

1. **Clarify** ("Is it slow on load or on interaction? For everyone? Since a deploy?").
2. **State the plan** ("I'd first split time between network, server and main thread.").
3. **Name the tool for each step** ("Network tab timing, then the Performance panel").
4. **Give 2 or 3 ranked hypotheses** with how you would confirm each.
5. **Propose fixes with trade-offs** (what each costs and risks).
6. **Close with prevention** (budgets, monitoring, tests).

Say your reasoning out loud; the interviewer is evaluating the *process*, not whether you guess the exact bug.

## Anti-patterns

| Anti-pattern | Why it fails |
|---|---|
| **Optimising before measuring** | You improve something that was never the bottleneck |
| **Memoising everything** (`useMemo`, `memo`, `useCallback`) | Adds overhead and complexity; fixes nothing if re-renders are not the problem |
| **Adding a cache to hide a slow query** | Masks the cause; adds invalidation bugs; the first uncached request is still slow |
| **Testing only on a fast laptop and fast network** | Misses the slow-device and slow-network users who suffer most |
| **Changing several things at once** | You cannot tell which change helped (or hurt) |
| **Trusting averages** | The tail users are invisible |
| **"Works on my machine"** | Production data volume, concurrency and caches differ |
| **Fixing symptoms in the UI for a backend problem** (or the reverse) | The real cost stays |

## A worked mini-example

**Report:** "The orders page takes 4 seconds."

1. **Measure:** in the Network tab, `GET /orders` has **Waiting (TTFB) = 3.4 s**, content download 40 ms. The Performance panel shows the main thread is idle for most of that.
2. **Isolate:** the time is *server-side*, not in the browser.
3. **Hypothesize:** the trace shows 120 near-identical `SELECT … FROM order_items WHERE order_id = $1` queries: an N+1. Prediction: a customer with 5 orders should be fast, one with 200 slow.
4. **Verify:** switch to one query with `include`/`IN`; TTFB drops from 3.4 s to 180 ms; confirm with the 200-order customer. Add a test asserting "at most 3 queries" and a p95 latency alert.

Two minutes, four moves, no guessing. That is the whole series in miniature.

## Common mistakes

1. Starting with a solution instead of a measurement.
2. Looking only at the layer you know best (frontend engineers blaming React; backend engineers blaming the network).
3. Using averages and a single run.
4. Debugging in production-unlike conditions (no throttling, tiny data).
5. Changing multiple variables, then crediting the wrong one.
6. Never adding a guard, so the same regression returns months later.

## Interview questions

### Q1. How do you approach "the app is slow"?

I clarify the symptom (what, for whom, since when, how slow), measure it, then split the time between network, server and main-thread work using the Network and Performance panels. I form one testable hypothesis for the layer that owns the time, change one thing, re-measure against the baseline, and finally add monitoring or a budget so it does not regress.

### Q2. Lab vs field data?

Field data comes from real users (RUM, CrUX) and tells me whether there is a problem and for which devices, regions and routes, at percentiles like p75. Lab data comes from controlled runs (Lighthouse, DevTools with throttling) and lets me reproduce, profile and verify fixes. I use field data to prioritise and lab data to debug.

### Q3. What do you measure before changing any code?

A baseline for the specific symptom: the metric (LCP, INP, TTFB, endpoint p95), under defined conditions (device, CPU and network throttling, data volume), repeated several times. Then a breakdown by layer so I know where the time goes. Without a baseline I cannot prove that a change helped.

### Q4. Why look at percentiles instead of averages?

Averages hide the slow tail. A few extremely slow requests barely change the mean but affect real users. Percentiles (p95, p99) show what the slowest part of the user base experiences and are the basis for SLOs and Core Web Vitals (75th percentile).

### Q5. How do you tell a frontend problem from a backend problem?

In the Network tab, check the request's Timing: a large "Waiting for server response" (TTFB) points to the backend; a fast response followed by a busy main thread in the Performance panel points to the frontend (parsing, rendering, long tasks). Server-Timing headers and traces confirm the backend breakdown.

### Q6. What is the risk of fixing a slow endpoint by adding a cache first?

It hides the root cause, adds invalidation complexity and stale-data risks, and cold or missed requests are still slow. I diagnose why the query or code is slow first (indexes, N+1, payload), fix that, and add caching only where the access pattern justifies it.

### Q7. How do you make sure a performance fix stays fixed?

Add a regression guard: a performance budget in CI (bundle size, Lighthouse thresholds), a test asserting query counts, dashboards and alerts on p95 latency or web vitals, and RUM to watch real users after release.

## Key takeaways

- **Measure, isolate, hypothesize, verify**, in that order, one change at a time.
- First fork: is the time **before the response** (network/server) or **after** (main thread)? The Network timing tab answers it in seconds.
- Use **percentiles**, **field data to prioritise** and **lab data (throttled) to debug**.
- State hypotheses that predict what you will see; use bisecting and comparisons.
- Add a **guard** (budget, test, alert) so the fix lasts.
