> **In one line:** answer a security scenario in four parts: **Impact** (what can an attacker do?), **Reproduce and confirm**, **Fix at the root cause** (not only the symptom), and **Prevent the whole class of bug** (tests, safe defaults, scanning). If the problem is live, contain it first.

This lesson has fourteen realistic scenarios. They build on [Browser Contract Lessons 02, 03, 04 and 07](/browser/lesson-7) and [Backend Lesson 06](/backend/lesson-6).

## The scenarios

### 1. "A user's profile bio executes JavaScript for anyone who views it."

**Impact:** this is stored XSS (cross-site scripting). The attacker's code is saved in your data and runs in other people's browsers. The attacker can steal sessions or act as other users.

**Reproduce:** put `<img src=x onerror=…>` in the bio.

**Fix at the root:**
- Show text as text (escape it). If you must allow HTML, clean it at render time with an **allow-list sanitiser** (a tool that keeps only safe tags).
- Check URLs (only `https:`).
- Add a **CSP** (a browser rule about which scripts may run), so injected inline script cannot run.
- Check **every place** that shows the same data: the profile page, admin tools, emails and exports.

**Prevent:** add lint rules for `dangerouslySetInnerHTML` and `innerHTML`. Write security tests with XSS payloads. Start the CSP in report-only mode, then enforce it. Use HttpOnly cookies to limit the damage. ([Browser Contract, Lesson 07](/browser/lesson-7))

### 2. "Changing `/orders/123` to `/orders/124` shows someone else's order."

**Impact:** this is broken object-level authorization, also called IDOR. The server does not check who owns the object. Many people's data can be exposed.

**Fix:** limit **every query to the owner or tenant** (`where: { id, userId }`). Return `404` for objects that belong to others. Keep the access rules in one place. Check all endpoints that accept an ID, including **nested resources, exports and file downloads**.

**Prevent:** write cross-user tests for every endpoint. Use a deny-by-default policy layer. UUIDs help a little, but they are not the fix. ([Backend, Lesson 06](/backend/lesson-6))

### 3. "Password reset can be abused to take over accounts."

**Common flaws and fixes:**
- **Tokens that can be guessed or reused** → use long random tokens that work **only once**, store them hashed in the database, and give them a short life.
- **Token in the URL leaks through `Referer` or logs** → set `Referrer-Policy`, do not log URLs that contain tokens, and cancel the token once it is used.
- **Host header injection** (the reset link is built from the request's `Host`) → build links from a base URL that you set in config.
- **Account enumeration** (the reply says "no such email", so attackers learn which emails exist) → give the same reply for all emails.
- **No rate limit** → limit by account and by IP.
- **Sessions stay valid after a reset** → end the other sessions.
- **Email change without asking for the password again.**

**Prevent:** design the flow with a threat model (a list of how it could be attacked). Add security tests. Ask for MFA (a second proof of identity) for sensitive actions.

### 4. "A session token was stolen. What limits the damage, and what do you do now?"

**Contain:** **revoke** the affected sessions or tokens. If the signing key leaked, rotate it too. Force the account to log in again. Block the source if it is abusing the system.

**Investigate:** how was it stolen? It could be XSS, malware, leaked logs, a proxy or a shared device. Check the audit logs for what the attacker did.

**Reduce future damage:**
- **short-lived access tokens**
- refresh-token **rotation with reuse detection** (each refresh token works once, and a second use is a warning sign)
- tying sessions to extra signals, such as the device, or asking again for risky actions (step-up auth)
- HttpOnly, Secure and SameSite cookies
- notices for logins from a new device

([Browser Contract, Lessons 02 and 03](/browser/lesson-3))

### 5. "A pentest says our CORS configuration reflects any origin with credentials."

**Impact:** a pentest is a test where security experts try to break your system. CORS controls which websites may call your API from the browser. If you accept every origin with credentials, any website can make logged-in requests as the user and **read the answers**.

**Fix:** use an **allow-list** of exact origins. Never copy the `Origin` header back without checking. Never use `*` with credentials. Add `Vary: Origin`. Keep CORS *before* auth so preflight requests work. Remember that CORS is not the security of the API. The API must still check permission for every request.

**Prevent:** use a separate config for each environment. Add a test that an untrusted origin gets no CORS headers. ([Browser Contract, Lesson 04](/browser/lesson-4))

### 6. "After login, `?next=https://evil.com` redirects users to an attacker's site."

**Impact:** this is an **open redirect**. It allows phishing from your trusted domain, and it can leak OAuth codes.

**Fix:** accept only **relative paths** or hosts from an allow-list. Parse the value with `new URL(value, base)` and compare the origin. Reject anything that starts with `//` or contains a scheme (such as `https:`).

**Prevent:** use one shared redirect helper. Write tests with tricky inputs (`//evil.com`, `/\evil.com`, `https:evil.com`).

### 7. "A security scan reports SQL injection in the search endpoint."

**Impact:** in SQL injection, the attacker's input becomes part of your SQL command. They can steal data, change it, or do worse.

**Fix:** use **parameterised queries** everywhere (an ORM or placeholders), so input is always treated as data. For names that cannot be parameters (sort columns, table names), use an allow-list. Never build SQL by joining strings, also not in `$queryRawUnsafe`. Give database users **least privilege** (only the rights they need).

**Prevent:** add lint rules against raw SQL strings. Review raw queries in code review. Use a WAF (a web application firewall) as a second layer. Write tests with attack payloads. ([Backend, Lesson 03](/backend/lesson-3))

### 8. "The 'link preview' feature can be used to read our cloud metadata service."

**Impact:** this is **SSRF** (server-side request forgery). The server fetches URLs that the attacker chooses. So the attacker can reach internal services and cloud credentials, for example the instance metadata endpoint.

**Fix:**
- Allow only `http` and `https`.
- **Look up the hostname and block private, loopback and link-local addresses** (internal ranges). Check again after redirects, because DNS can change.
- Limit redirects, response size and time.
- Run the fetcher in an **isolated network** with no access to internal services.
- Require IMDSv2 (the safer metadata version) on cloud instances.

**Prevent:** use one separate, locked-down fetch service. Use allow-lists where you can.

### 9. "A critical vulnerability is announced in a library we use. What do you do?"

**Respond:**
1. Find out the **exposure**. Is the weak version in production, and can an attacker reach it? Use the lockfile and an SBOM (a list of all software parts).
2. **Patch or reduce the risk** (upgrade, config flag, WAF virtual patch), in order of priority.
3. Deploy and check.
4. Look in the logs for **signs of attack**.
5. Tell the people who need to know.

**Prevent:** scan dependencies automatically and open update PRs. Keep a short path to patch. Use few dependencies. Keep a list of what runs where.

### 10. "Credential stuffing: thousands of failed logins from many IPs."

Credential stuffing means attackers try passwords leaked from other sites.

**Detect:** watch the rate of failed logins per account and per IP. Look for many accounts with the same password.

**Respond:** **rate-limit** by account and by IP. Add growing delays. Show a **CAPTCHA or proof-of-work** after failures. Ask for MFA or step-up for risky logins. Block known bad networks. Tell affected users. Force a password reset for hacked accounts. Check passwords against **breach lists**.

**Prevent:** use MFA and passkeys. Use bot management at the edge. Give generic error messages. Set alerts for unusual logins. ([Practical Design Problems, Lesson 02](/design-problems/lesson-2))

### 11. "An API key was committed to a public Git repository."

**Treat the key as stolen right away**, even if you remove the commit. History, forks and scrapers keep a copy.

**Do this:** **rotate or revoke** the key first. Check usage logs for abuse. Remove it from history only as a second step. Move to secrets management (environment variables from a secrets manager, short-lived credentials).

**Prevent:** use **secret scanning** (pre-commit and in CI, with push protection). Put env files in `.gitignore`. Use keys with least privilege. Use separate keys for each environment.

### 12. "Users can upload files, and one of them runs script when viewed."

**Impact:** an uploaded HTML or SVG file, served from your own origin, can cause stored XSS or spread malware.

**Fix:** serve uploads from a **separate domain that has no cookies**. Also:
- send `X-Content-Type-Options: nosniff`
- send the correct `Content-Type`
- use `Content-Disposition: attachment` for risky types
- **re-encode images**
- check the magic bytes (the first bytes that show the real file type)
- scan for malware
- block file types that can run code

**Prevent:** upload straight to storage, using keys that the server creates. ([Practical Design Problems, Lesson 04](/design-problems/lesson-4))

### 13. "A state-changing endpoint can be triggered from another site."

**Impact:** this is CSRF (cross-site request forgery). Another site makes the victim's browser send a request, and the browser adds the victim's cookies. The action is done as the victim.

**Fix:** use `SameSite=Lax` or `Strict` cookies. Use **CSRF tokens**, or check Origin or Fetch-Metadata headers, on unsafe methods. Never change state on `GET`. Require custom headers for JSON APIs.

**Prevent:** turn on the framework's CSRF protection by default. Write tests that a cross-origin form post is rejected. ([Browser Contract, Lesson 03](/browser/lesson-3))

### 14. "A third-party script we load from a CDN was compromised."

**Impact:** the attacker can run any code in every visitor's browser. They can steal credentials or skim payment data.

**Contain:** **remove or block** the script now (with a feature flag or a deploy). **Purge** the caches. Check what data it could reach. Tell the right people if the rules require it.

**Prevent:** **host critical scripts yourself**. Use **SRI** with pinned versions. Use a strict **CSP**, including `connect-src` to limit where data can be sent. Use as little third-party code as you can. Watch for changes in scripts. ([Browser Contract, Lesson 07](/browser/lesson-7))

## A baseline you should be able to recite

An interviewer may ask: "What security practices would you insist on from day one?" A good answer: **HTTPS everywhere with HSTS, login with hashed passwords and MFA, permission checks on every object, input validation and parameterised queries, output encoding with a CSP, secure cookie flags, rate limiting, dependency and secret scanning, least privilege, logging and alerts that do not contain secrets, backups, and an incident-response plan.**

## Interview questions

### Q1. Scenario: changing an ID in the URL shows another user's data. What do you do?

First I contain the problem by fixing the worst endpoints quickly. Then I fix the root cause. I limit every query to the owner or tenant, return 404 for other people's objects, and keep the access rules in one place. I check all endpoints that accept an ID, including nested resources and downloads. I add cross-user regression tests and look in the logs for earlier abuse.

### Q2. Scenario: an API key is found in a public repository. What are the steps?

I rotate and revoke the key at once, because history and forks keep a copy. I check the usage logs for abuse. I replace the key with managed secrets and give keys least privilege. I add secret scanning with push protection in CI. Removing the commit alone is not enough.

### Q3. Scenario: a feature fetches user-supplied URLs. What are the risks and defences?

The risk is SSRF. Attackers can reach internal services and cloud metadata. I allow only http and https. I look up the hostname and block private and link-local ranges, also after every redirect. I limit size, time and redirects. I run the fetcher in a restricted network and turn on the metadata-service protections.

### Q4. Scenario: you suspect credential stuffing. How do you confirm and respond?

I look for many failed logins across many accounts and IPs. I rate-limit by account and IP, add delays and a CAPTCHA, and ask for MFA or step-up. I block abusive networks, force resets for hacked accounts, and check passwords against breach lists. I keep error messages generic.

### Q5. Scenario: the CORS config reflects any origin with credentials. What is the risk and fix?

Any site could make logged-in requests and read the answers. I replace the copying of the origin with an exact allow-list. I add `Vary: Origin`. I never combine `*` with credentials. The API must still check permission, whatever CORS says.

### Q6. Scenario: a library has a critical CVE. What is your process?

A CVE is a public ID for a known security flaw. First I find out if the weak code is in production and if it can be reached (lockfile, SBOM). I patch or reduce the risk in order of priority. I deploy and check. I look for signs of attack in the logs and tell the right people. Then I improve the automation, so patching is faster next time.

## Key takeaways

- Answer in this order: **Impact, Reproduce, Fix the root cause, Prevent the class**. **Contain first** when the problem is live.
- The same root causes appear again and again: **missing permission checks, output that is not escaped, SQL built from strings, trusting input, leaked secrets, CORS and redirects that are too open, and third-party code**.
- **Defence in depth** (CSP, cookie flags, rate limits, least privilege, scanning) means several layers protect you. Then one mistake does not become a disaster.
