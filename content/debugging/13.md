> **In one line:** a security scenario is answered in four beats: **Impact** (what can an attacker do?), **Reproduce and confirm**, **Fix at the root cause** (not just the symptom), and **Prevent the class of bug** (tests, defaults, scanning). Contain first if it is live.

Fourteen realistic scenarios. They build on [Browser Contract Lessons 02, 03, 04 and 07](/browser/lesson-7) and [Backend Lesson 06](/backend/lesson-6).

## The scenarios

### 1. "A user's profile bio executes JavaScript for anyone who views it."

**Impact:** stored XSS: an attacker steals sessions or acts as other users.

**Reproduce:** put `<img src=x onerror=…>` in the bio.

**Fix at the root:** render text as text (escape), or sanitise with an **allow-list sanitiser** at render time if HTML is required; validate URLs (`https:` only); add a **CSP** so injected inline script cannot run; check **every sink** of the same data (profile page, admin tool, emails, exports).

**Prevent:** lint for `dangerouslySetInnerHTML`/`innerHTML`, security tests with XSS payloads, CSP in report-only then enforce, HttpOnly cookies to limit the damage. ([Browser Contract, Lesson 07](/browser/lesson-7))

### 2. "Changing `/orders/123` to `/orders/124` shows someone else's order."

**Impact:** broken object-level authorization (IDOR): mass data exposure.

**Fix:** scope **every query by owner or tenant** (`where: { id, userId }`), return `404` for others' objects, centralise policies; audit all endpoints that accept an ID, including **nested resources, exports and file downloads**.

**Prevent:** cross-user tests for every endpoint, a default-deny policy layer, UUIDs (as a minor hardening, not the fix). ([Backend, Lesson 06](/backend/lesson-6))

### 3. "Password reset can be abused to take over accounts."

**Common flaws and fixes:**
- **Guessable or reusable tokens** → long random, **single-use**, hashed in the database, short expiry.
- **Token in the URL leaked via `Referer` or logs** → `Referrer-Policy`, do not log URLs with tokens, invalidate on use.
- **Host header injection** (reset link built from the request's `Host`) → build links from a configured base URL.
- **Account enumeration** ("no such email") → identical responses for all emails.
- **No rate limit** → limit per account and IP.
- **Not invalidating sessions** after reset → revoke other sessions.
- **Email change without re-authentication.**

**Prevent:** a threat-modelled flow, security tests, MFA for sensitive actions.

### 4. "A session token was stolen. What limits the damage, and what do you do now?"

**Contain:** **revoke** the affected sessions or tokens (and rotate signing keys if the key leaked), force re-login for the account, block the source if abusive.

**Investigate:** how was it stolen (XSS, malware, leaked logs, a proxy, a shared device)? Check audit logs for the attacker's actions.

**Reduce future impact:** **short-lived access tokens**, refresh-token **rotation with reuse detection**, binding sessions to extra signals (device, step-up auth for risky actions), HttpOnly/Secure/SameSite cookies, notifications for new-device logins. ([Browser Contract, Lessons 02 and 03](/browser/lesson-3))

### 5. "A pentest says our CORS configuration reflects any origin with credentials."

**Impact:** any website can make authenticated requests as the user and **read the responses**.

**Fix:** use an **allow-list** of exact origins, never reflect the `Origin` header blindly, never `*` with credentials, add `Vary: Origin`, keep CORS *before* auth for preflights, and remember CORS is not the API's security: the API still authorises every request.

**Prevent:** per-environment config, a test that an untrusted origin gets no CORS headers. ([Browser Contract, Lesson 04](/browser/lesson-4))

### 6. "After login, `?next=https://evil.com` redirects users to an attacker's site."

**Impact:** an **open redirect** enables phishing from your trusted domain and can leak OAuth codes.

**Fix:** accept only **relative paths** or an allow-list of hosts; parse with `new URL(value, base)` and compare the origin; reject anything starting with `//` or containing a scheme.

**Prevent:** a shared redirect helper, tests with tricky inputs (`//evil.com`, `/\evil.com`, `https:evil.com`).

### 7. "A security scan reports SQL injection in the search endpoint."

**Impact:** data theft, modification or worse.

**Fix:** **parameterised queries** everywhere (ORM or placeholders); allow-list identifiers that cannot be parameters (sort columns, table names); no string-built SQL, including in `$queryRawUnsafe`; apply **least-privilege** database users.

**Prevent:** lint rules against raw string SQL, code review of raw queries, WAF as a secondary layer, tests with payloads. ([Backend, Lesson 03](/backend/lesson-3))

### 8. "The 'link preview' feature can be used to read our cloud metadata service."

**Impact:** **SSRF**: the server fetches attacker-chosen URLs, reaching internal services and cloud credentials (for example the instance metadata endpoint).

**Fix:** allow only `http`/`https`; **resolve the hostname and block private, loopback and link-local ranges** (and re-check after redirects, since DNS can change); limit redirects, response size and time; run the fetcher in an **isolated network** without access to internal services; require IMDSv2 on cloud instances.

**Prevent:** a dedicated, locked-down fetch service; allow-lists where possible.

### 9. "A critical vulnerability is announced in a library we use. What do you do?"

**Respond:** identify **exposure** (is the vulnerable version in production and reachable?) using the lockfile and a software bill of materials; **patch or mitigate** (upgrade, config flag, WAF virtual patch) in priority order; deploy and verify; check logs for **signs of exploitation**; communicate.

**Prevent:** automated dependency scanning and update PRs, a short path to patch, minimal dependencies, an inventory of what runs where.

### 10. "Credential stuffing: thousands of failed logins from many IPs."

**Detect:** failed-login rate per account and per IP, many accounts with one password.

**Respond:** **rate-limit** per account and per IP, add progressive delays, **CAPTCHA or proof-of-work** after failures, require MFA or step-up for risky logins, block known bad networks, notify affected users, force resets for compromised accounts, check passwords against **breach lists**.

**Prevent:** MFA and passkeys, bot management at the edge, generic error messages, alerts on login anomalies. ([Practical Design Problems, Lesson 02](/design-problems/lesson-2))

### 11. "An API key was committed to a public Git repository."

**Treat the key as compromised immediately**, even if the commit was removed (history, forks and scrapers keep it).

**Do:** **rotate/revoke** the key first; review usage logs for abuse; remove it from history only as a secondary step; replace with secrets management (environment variables from a secrets manager, short-lived credentials).

**Prevent:** **secret scanning** (pre-commit and CI, push protection), `.gitignore` for env files, least-privilege scoped keys, separate keys per environment.

### 12. "Users can upload files, and one of them runs script when viewed."

**Impact:** stored XSS or malware distribution via an uploaded HTML or SVG file served from your origin.

**Fix:** serve user uploads from a **separate cookie-less domain**, with `X-Content-Type-Options: nosniff`, correct `Content-Type`, `Content-Disposition: attachment` for risky types, **re-encode images**, validate magic bytes, scan for malware, block active content types.

**Prevent:** direct-to-storage uploads with server-generated keys. ([Practical Design Problems, Lesson 04](/design-problems/lesson-4))

### 13. "A state-changing endpoint can be triggered from another site."

**Impact:** CSRF: actions performed with the victim's cookies.

**Fix:** `SameSite=Lax/Strict` cookies, **CSRF tokens** or Origin/Fetch-Metadata checks on unsafe methods, never change state on `GET`, require custom headers for JSON APIs.

**Prevent:** framework-level CSRF protection enabled by default, tests that a cross-origin form post is rejected. ([Browser Contract, Lesson 03](/browser/lesson-3))

### 14. "A third-party script we load from a CDN was compromised."

**Impact:** arbitrary code in every visitor's browser: credential theft, skimming.

**Contain:** **remove or block** the script now (feature flag or deploy), **purge** caches, check what data it could access, notify as required.

**Prevent:** **self-host** critical scripts, **SRI** with pinned versions, a strict **CSP** (including `connect-src` to limit exfiltration), minimal third-party code, monitoring of script changes. ([Browser Contract, Lesson 07](/browser/lesson-7))

## A baseline you should be able to recite

If asked "what security practices would you insist on from day one?": **HTTPS everywhere with HSTS, authentication with hashed passwords and MFA, authorization checks on every object, input validation and parameterised queries, output encoding with a CSP, secure cookie flags, rate limiting, dependency and secret scanning, least privilege, logging and alerting without secrets, backups, and an incident-response plan.**

## Interview questions

### Q1. Scenario: changing an ID in the URL shows another user's data. What do you do?

Contain by fixing the worst endpoints quickly, then fix at the root: scope every query by owner or tenant, return 404 for others' objects, centralise policies and audit all ID-accepting endpoints including nested resources and downloads. Add cross-user regression tests and check logs for prior exploitation.

### Q2. Scenario: an API key is found in a public repository. What are the steps?

Rotate and revoke it immediately because history and forks keep it, review usage logs for abuse, replace it with managed secrets, scope keys to least privilege, and add secret scanning with push protection in CI. Removing the commit alone is not remediation.

### Q3. Scenario: a feature fetches user-supplied URLs. What are the risks and defences?

SSRF: attackers can reach internal services and cloud metadata. Allow only http(s), resolve and block private and link-local ranges after every redirect, limit size, time and redirects, isolate the fetcher in a restricted network, and enforce metadata-service protections.

### Q4. Scenario: you suspect credential stuffing. How do you confirm and respond?

Look for high failed-login rates across many accounts and IPs. Rate-limit per account and IP, add delays and CAPTCHA, require MFA or step-up, block abusive networks, force resets for compromised accounts and check passwords against breach lists; keep error messages generic.

### Q5. Scenario: the CORS config reflects any origin with credentials. What is the risk and fix?

Any site could make authenticated requests and read responses. Replace reflection with an exact allow-list, add `Vary: Origin`, never combine `*` with credentials, and keep authorization enforced in the API regardless of CORS.

### Q6. Scenario: a library has a critical CVE. What is your process?

Determine whether the vulnerable code is in production and reachable (lockfile, SBOM), patch or mitigate by priority, deploy and verify, check for exploitation in logs, communicate, and improve automation so patching is fast next time.

## Key takeaways

- Answer in **Impact, Reproduce, Fix the root cause, Prevent the class**; **contain first** when it is live.
- The recurring root causes: **missing authorization checks, unescaped output, string-built queries, trusting input, leaked secrets, over-permissive CORS and redirects, third-party code**.
- **Defence in depth** (CSP, cookie flags, rate limits, least privilege, scanning) turns a single mistake into a non-event.
