> **In one line:** every scenario answer has the same three-beat shape: **Diagnose** (what evidence would you gather first?), **Fix** (the smallest change that removes the cause) and **Prevent** (the guard that stops it coming back). Practise saying them out loud.

This is the revision lesson. Fifteen realistic scenarios, drawn from the whole series, each answered as an interviewer would want to hear it. Try to answer before opening each one.

## How to use this lesson

1. Read the symptom. Say your first three diagnostic steps **aloud**.
2. Open the answer and compare. Notice the **evidence** each step collects.
3. Re-read the *Prevent* line: seniors always close with it.

## The scenarios

### 1. "It works locally but fails in production with a CORS error."

**Diagnose:** open the failing request in the Network tab. Check the **`OPTIONS` preflight** (status and response headers) and the **real request**. Compare the page's origin with the server's allow-list: scheme, host, port, `www`. Check whether the error response came from the app or from a proxy/gateway (a `502` or `403` without CORS headers shows up as "a CORS error"). Look at `credentials`, `Access-Control-Allow-Credentials`, and whether `Allow-Origin` is `*` with cookies.

**Fix:** add the exact production origin to the allow-list, register CORS middleware **before** auth so preflights get `2xx`, return `Vary: Origin` when echoing origins, and fix the real `5xx` if that is hiding behind the CORS message. Better: make the API same-origin through a proxy or BFF.

**Prevent:** an allow-list per environment in config, an integration test for the preflight, and a staging environment with the production domain shape. ([Browser Contract, Lesson 04](/browser/lesson-4))

### 2. "Users get logged out at random."

**Diagnose:** is it random per user or time-based? Check cookie attributes (`Max-Age`, `Domain`, `SameSite`, `Secure`) and whether the cookie is **actually being set** on the response. Check session store behaviour (Redis eviction, TTL shorter than expected, multiple app instances without a shared store), token expiry versus refresh (access token expires and refresh fails or races: two tabs refresh at once and rotation invalidates one), clock skew, a deploy that changed the signing key or `SESSION_SECRET`, a load balancer sending requests to instances with different secrets, or browser privacy features (Safari ITP) shortening script-set cookies.

**Fix:** use a shared session store with the right TTL and a consistent secret across instances; serialise refresh calls (a single in-flight refresh promise); keep a short grace window for rotated refresh tokens to survive races; set cookies from the server with correct attributes.

**Prevent:** log session creation, refresh and invalidation with a request ID; alert on sudden spikes in 401s; test multi-tab refresh. ([Browser Contract, Lessons 02 and 03](/browser/lesson-2))

### 3. "The API returns 429 during normal use."

**Diagnose:** which key is being limited (IP, user, API key)? Check whether the **frontend** is generating the traffic: duplicate effect fetches, no request dedupe, polling in every tab, retry loops with no backoff, Strict Mode in dev. Or many users share one NAT IP and a per-IP limit.

**Fix:** dedupe through a shared cache (React Query/SWR), poll less or use SSE, pause when hidden, back off using `Retry-After`, limit per user or API key rather than per IP, raise limits for known-good shared IPs.

**Prevent:** emit `RateLimit-*` headers, dashboard requests per user per endpoint, a client-side request budget in tests. ([Lesson 05](/debugging/lesson-5), [Practical Design Problems, Lesson 02](/design-problems/lesson-2))

### 4. "Server memory grows over several days."

**Diagnose:** plot heap versus RSS; take **heap snapshots** (a baseline and one hours later) and diff; look at the retainers of the growing objects. Common culprits: unbounded in-memory caches and maps, listeners added per request (`MaxListenersExceededWarning`), global arrays collecting data, unclosed streams or connections, timers never cleared, closures holding large request objects.

**Fix:** bound caches (LRU with size/TTL), remove listeners and clear timers on completion, close streams, avoid per-request accumulation. As a stopgap, restart instances on a schedule or memory threshold while you find the retainer.

**Prevent:** memory and heap metrics with alerts, a soak test in staging, code review for module-level collections. ([Lesson 04](/debugging/lesson-4), [Backend, Lesson 10](/backend/lesson-10))

### 5. "After a deploy, some users get a blank page or ChunkLoadError."

**Diagnose:** the HTML (or a stale Service Worker) references **old chunk names** that the new deploy deleted, or a CDN cached old HTML. Check `Cache-Control` on HTML, whether old assets still exist, CDN cache status headers, and the Service Worker version.

**Fix:** serve HTML with `no-cache`, hash asset names, **keep the previous build's assets available** for a while, purge the CDN for changed paths, catch chunk-load failures and reload once, and update the Service Worker deliberately.

**Prevent:** immutable hashed assets plus short-lived HTML, a deploy process that retains N previous builds, a Sentry alert on ChunkLoadError. ([Browser Contract, Lesson 05](/browser/lesson-5))

### 6. "Cookies are missing after a deploy or behind the load balancer."

**Diagnose:** inspect the `Set-Cookie` header and the Application tab. Common causes: the app thinks the request is HTTP (TLS terminated at the proxy), so a `Secure` cookie is never set (fix `trust proxy` and `X-Forwarded-Proto`); `Domain` or `Path` mismatch; `SameSite` blocking a cross-site flow; a changed cookie name or `__Host-` prefix rules not met; cookie too large (over about 4 KB) and dropped; a CDN stripping or caching `Set-Cookie`.

**Fix:** configure the proxy trust setting, align attributes, keep cookies small, make sure CDN rules do not cache or strip authenticated responses.

**Prevent:** an end-to-end test that logs in on a production-like stack with TLS termination. ([Browser Contract, Lesson 01](/browser/lesson-1))

### 7. "A GraphQL query is slow."

**Diagnose:** use tracing to see resolver timings and the number of database queries; look for **N+1** (the same query repeated per parent), missing indexes (`EXPLAIN`), over-fetching deep or large lists with no pagination, and expensive fields requested in every query.

**Fix:** batch with DataLoader (per request), add indexes, enforce pagination and a depth/complexity limit, move heavy fields to separate queries or caching, consider persisted queries for caching.

**Prevent:** query-count assertions in tests, resolver tracing in production, cost limits on the API. ([Backend, Lessons 08 and 09](/backend/lesson-8))

### 8. "Maximum update depth exceeded" / an infinite render loop.

**Diagnose:** find the component in the stack; look for `setState` called **during render**, or in an effect whose dependencies change every time (an object or array created in render used as a dependency, or an effect that sets state that appears in its own dependencies).

**Fix:** move the update into an event handler, derive the value during render instead of copying into state, stabilise dependencies (`useMemo`, move constants outside the component), and add proper conditions.

**Prevent:** the `react-hooks/exhaustive-deps` lint rule, code review for "state derived from props," and tests. ([Frontend Depth, Lesson 01](/frontend-depth/lesson-1))

### 9. "Hydration failed because the server HTML didn't match the client" (Next.js).

**Diagnose:** the first client render produced different output than the server. Typical causes: using `Date.now()`, `Math.random()`, `window`, `localStorage` or `navigator` during render; locale/timezone formatting that differs between server and browser; invalid HTML nesting (`<div>` inside `<p>`); browser extensions injecting nodes; conditional rendering based on client-only state.

**Fix:** render the same thing on both, then update **after mount** in an effect for client-only values (or use `suppressHydrationWarning` for harmless text such as timestamps); fix invalid nesting; format dates with a fixed locale/timezone or on the client only.

**Prevent:** lint for impure render code, test hydration in CI, avoid client-only branches in the initial render. ([Frontend Depth, Lesson 02](/frontend-depth/lesson-2))

### 10. "Intermittent 502 or 504 errors from the load balancer, but the app logs look fine."

**Diagnose:** check timeouts at every hop. A classic cause: the load balancer's **idle timeout** (for example 60 s on an AWS ALB) is longer than the Node server's **keep-alive timeout** (default 5 s). The server closes an idle connection just as the load balancer reuses it, producing sporadic `502`s. Also check request timeouts for slow endpoints (`504`), health checks failing during deploys, and instances being killed without graceful shutdown.

**Fix:** set `server.keepAliveTimeout` (and `headersTimeout`) **higher** than the load balancer's idle timeout; implement graceful shutdown and proper health checks; align timeouts across proxy, load balancer and app; move long work to async jobs.

**Prevent:** document and test the timeout chain, alert on `5xx` by source (load balancer vs app), and run a deploy test with traffic. ([Backend, Lesson 04](/backend/lesson-4))

### 11. "After scaling out, the database says 'too many connections'."

**Diagnose:** connections = instances × pool size (plus serverless concurrency). Check pool configuration and whether each request or hot reload creates a new client; inspect `pg_stat_activity` for idle connections.

**Fix:** a pooler (PgBouncer, RDS Proxy), a smaller per-instance pool, a single client per process, shorter transactions, and fix slow queries holding connections.

**Prevent:** capacity math in the runbook, an alert on connection usage, load tests at target scale. ([Backend, Lesson 08](/backend/lesson-8))

### 12. "A customer was charged twice."

**Diagnose:** find both requests by idempotency key, request ID or order ID. Were they two distinct client submissions (double-click, two tabs), a client **retry after a timeout**, or a server/queue **redelivery**? Check whether the payment provider received two identical charge requests.

**Fix:** refund the duplicate; add idempotency end to end (client key per attempt, server unique-constrained key store, pass the key to the payment provider), and a natural unique constraint (one payment per order).

**Prevent:** idempotent handlers for queue consumers, reconciliation reports, alerts on duplicate charges. ([Lesson 05](/debugging/lesson-5), [Backend, Lesson 02](/backend/lesson-2))

### 13. "The page works for me, but some users see a blank screen."

**Diagnose:** get **field evidence**: error monitoring (Sentry), RUM, browser/OS/version distribution of affected users, and the failing console error. Typical causes: a JS error with no **error boundary** (React unmounts the whole tree), an unsupported browser feature (no transpile or polyfill), a failing third-party script, **ad blockers** or extensions blocking an endpoint or script, CSP blocking something, a failed chunk load, bad data from the API that crashes rendering (null where you assumed an object), or a regional CDN failure.

**Fix:** reproduce with the affected browser or data; add error boundaries with fallback UIs; guard against missing data; fix the incompatibility; make non-critical third parties fail soft.

**Prevent:** error boundaries at route level, source-map-enabled error reporting, a browser support matrix and cross-browser E2E tests on critical flows. ([Frontend Depth](/frontend-depth))

### 14. "The product page's LCP is slow on mobile."

**Diagnose:** field LCP by device; identify the LCP element and its four sub-parts; test on a throttled mobile profile. Typical causes: hero image too large with no `srcset`, discovered late (CSS background or JS-injected), lazy-loaded, render-blocking CSS and a big JS bundle on slow CPUs, high TTFB from an uncached SSR page.

**Fix:** responsive modern images with `priority`/`fetchpriority="high"` and no lazy-loading on the hero, preload where needed, trim blocking CSS/JS, server-render, cache HTML at the edge.

**Prevent:** a performance budget and Lighthouse CI on mobile settings, RUM alerts on p75 LCP. ([Lesson 06](/debugging/lesson-6), [Browser Contract, Lesson 09](/browser/lesson-9))

### 15. "Search is slow on a table with a million rows."

**Diagnose:** run `EXPLAIN (ANALYZE, BUFFERS)` on the query: likely `WHERE name LIKE '%term%'` forcing a **sequential scan** (a leading wildcard cannot use a B-tree), or `lower(column)` with no expression index, or sorting an unindexed column with a big `OFFSET`.

**Fix:** use the right tool: a **trigram (GIN) index** for substring search, PostgreSQL **full-text search** for word search, or a dedicated search engine (OpenSearch/Elasticsearch/Typesense) when relevance and scale demand it; add an expression index for case-insensitive equality; switch to **keyset pagination**; debounce and abort on the client.

**Prevent:** test with production-sized data, `pg_stat_statements` monitoring for slow queries, query-plan checks in code review. ([Backend, Lesson 07](/backend/lesson-7))

## Interview questions (practise out loud)

### Q1. "It works locally but fails in production with a CORS error." Walk me through it.

Check the preflight and the real request in the Network tab, compare the page origin to the server allow-list (scheme, host, port), look for credentials and wildcard conflicts, and confirm whether the response came from the app or a gateway returning an error without CORS headers. Fix by allow-listing the exact origin, putting CORS before auth and fixing underlying `5xx`s, and prevent it with per-environment config and a preflight integration test.

### Q2. "Users get logged out at random." What do you check?

Cookie attributes and whether the cookie is really set, session store TTL and sharing across instances, consistent secrets after deploys, refresh-token rotation races between tabs or expiry handling, clock skew, and browser privacy restrictions. I add logging around session creation, refresh and invalidation and alert on 401 spikes.

### Q3. "The API returns 429 during normal use." Whose fault is it?

Possibly the client's: duplicate fetches, polling in every tab, retries without backoff, Strict Mode in dev; possibly the limiter's key, such as many users behind one IP. Dedupe and back off on the client, rate-limit by user or API key, and publish `RateLimit` headers so clients can adapt.

### Q4. "Server memory grows over several days." What next?

Diff heap snapshots over time to find the growing objects and their retainers, check for unbounded caches, per-request listeners, global collections and unclosed resources, bound or clean them, restart as a stopgap, and add heap metrics, alerts and a soak test.

### Q5. What are the three beats of a good scenario answer?

Diagnose with named evidence and tools, fix the root cause with the smallest effective change and its trade-offs, and prevent recurrence with a test, budget, alert or process change.

## Key takeaways

- Always answer in **Diagnose → Fix → Prevent**; name the **tool and evidence** at each step.
- Many production mysteries live **between** layers: proxies and TLS, timeouts that do not align, caches with stale HTML, sessions across instances, pools versus instance counts.
- Differentiate **client-caused** load (duplicates, polling, retries) from server limits.
- Close every answer with a **guard**: a test, a budget, an alert, a runbook.
