> **In one line:** if the UI is quick but the request takes seconds, the time is spent **waiting on the server**. Break the request into stages (network, edge, app code, database, external calls, serialisation), find the dominant one, fix the root cause, then use caching and UX tricks for the rest.

The mirror of [Lesson 01](/debugging/lesson-1). Here the browser's main thread is idle; the Network tab shows a huge **Waiting for server response (TTFB)**. As a full-stack engineer you are expected to trace it all the way down.

## Step 1: confirm it is the server, and split the time

In the Network tab, read the request's **Timing**:

- **DNS / Connect / SSL** large: connection setup, distance, no CDN or keep-alive ([Browser Contract, Lesson 00](/browser/lesson-0)).
- **Waiting (TTFB)** large: the server and what is behind it.
- **Content Download** large: payload too big or no compression.

Then **split the server's share**. Ways to get a breakdown:

- A **`Server-Timing` header** that your API adds, which DevTools displays in the Timing tab:

```ts
app.use((req, res, next) => {
  const t0 = process.hrtime.bigint();
  const marks: string[] = [];
  res.locals.time = async <T>(name: string, fn: () => Promise<T>) => {
    const s = process.hrtime.bigint();
    try { return await fn(); }
    finally { marks.push(`${name};dur=${Number(process.hrtime.bigint() - s) / 1e6}`); }
  };
  const writeHead = res.writeHead.bind(res);
  res.writeHead = (...args: any[]) => {
    marks.push(`total;dur=${Number(process.hrtime.bigint() - t0) / 1e6}`);
    res.setHeader("Server-Timing", marks.join(", "));
    return writeHead(...args);
  };
  next();
});
// usage: const orders = await res.locals.time("db", () => repo.listOrders(user.id));
```

- **Distributed tracing / APM** (OpenTelemetry, Datadog, X-Ray, New Relic): a span waterfall shows handler time, each SQL query and each outgoing HTTP call.
- **Structured logs with durations** per request ([Backend, Lesson 05](/backend/lesson-5)).

A 3-second request usually decomposes like this; the biggest bar tells you where to dig:

```text
total 3,050 ms
├─ edge/network + TLS          60 ms
├─ auth + validation           15 ms
├─ DB: 118 queries          2,300 ms   ← N+1
├─ external pricing API       550 ms   ← serial call
├─ JSON serialisation          90 ms
└─ response (1.8 MB)           35 ms
```

## Step 2: the usual suspects

### 1. N+1 queries

One query per row ([Backend, Lesson 08](/backend/lesson-8)). Evidence: tens or hundreds of near-identical queries in the trace; latency grows with list size. Fix: eager load (`include`/`select`, join strategy), a single `IN` query, DataLoader.

### 2. Missing or unusable indexes

A filter or sort on a column with no index forces a sequential scan that gets slower as the table grows. A foreign key without an index (PostgreSQL does not create these automatically) makes joins and cascades slow. Evidence: `EXPLAIN (ANALYZE, BUFFERS)` shows *Seq Scan* with large *Rows Removed by Filter*, or an external-disk *Sort* ([Backend, Lesson 07](/backend/lesson-7)). Fix: add the right (often composite) index, and make sure queries can use it (no function on the column).

### 3. Unbounded queries and no pagination

`SELECT * FROM events` returning 400,000 rows for a "recent activity" widget. Fix: always `LIMIT`, paginate with a cursor, select only needed columns, and enforce a maximum page size.

### 4. Slow external calls, made one after another

```ts
// ❌ Serial: 3 x 400 ms = 1.2 s
const user = await getUser(id);
const prices = await pricingApi.get(sku);
const stock = await inventoryApi.get(sku);

// ✅ Independent calls in parallel: ~400 ms (the slowest)
const [user, prices, stock] = await Promise.all([getUser(id), pricingApi.get(sku), inventoryApi.get(sku)]);
```

More fixes:

- **Set timeouts** and **fail soft** (return the page without the optional widget) instead of waiting forever.
- **Cache** stable third-party data.
- **Move non-critical calls off the request path:** push to a queue, process in a background worker, return `202` ([Practical Design Problems, Lesson 05](/design-problems/lesson-5)).
- Use a **circuit breaker** so a failing dependency does not make every request wait for its timeout.

### 5. No caching of expensive, repeated work

The same aggregate recomputed for every request. See the caching section below.

### 6. Cold starts and cold caches

Serverless functions (and scaled-to-zero containers) pay a start-up cost on the first request after idle. Evidence: the slow requests are the *first* after a quiet period and the trace shows initialisation time. Fixes: keep instances warm or use provisioned concurrency, reduce bundle size and start-up work, lazy-load heavy modules, reuse connections across invocations, and move latency-critical paths to always-on services.

### 7. Wrong region or far-away dependencies

The app server is in Virginia, the database in Mumbai, and the user in Ahmedabad. Every query crosses an ocean; an N+1 multiplies the round trip. Fix: co-locate app and database, use read replicas or edge caching near users, and reduce chattiness.

### 8. Connection pool exhaustion and lock contention

All database connections are in use, so requests **queue** waiting for one (the wait appears as app time, not query time). Causes: long transactions, slow queries, too many instances for the database's connection limit ([Backend, Lesson 08](/backend/lesson-8)). Evidence: pool wait metrics, "too many connections", queries that are fast alone but slow under load. Fixes: shorten transactions, add a pooler, tune pool sizes, find and fix the slow queries holding connections. Also check for row or table **locks** (`pg_locks`, `pg_stat_activity`).

### 9. Event-loop blocking in the Node process

CPU-heavy synchronous work (large JSON, report generation, sync crypto) delays all requests ([Backend, Lesson 10](/backend/lesson-10)). Evidence: high event-loop lag; latency spikes for unrelated endpoints. Fix: offload to workers or queues, stream, optimise.

### 10. Heavy payloads and serialisation

A 2 MB response takes time to build, serialise, compress and download. Fix: return only needed fields, paginate, compress with gzip or Brotli, use efficient formats where appropriate, and avoid returning whole ORM objects with every relation.

### 11. Chatty APIs

The page calls 20 endpoints to render. Each is "fast", but the combined latency and connection overhead is not. Fix: a purpose-built aggregate endpoint or BFF, GraphQL, or server-side data loading.

## Scenario: an endpoint got slow after a feature added a relation. What do you suspect?

My ranked hypotheses, each with a fast check:

1. **N+1**: the new relation is loaded per row. *Check:* count queries in the trace; compare a small and a large account.
2. **Missing index** on the new foreign key or the new filter. *Check:* `EXPLAIN (ANALYZE, BUFFERS)` on the new query; look for Seq Scan.
3. **Join explosion / over-fetching:** an `include` of a to-many relation multiplies rows (orders × items × tags); with the join strategy the parent data repeats per child. *Check:* row counts and response size; switch to a separate query or paginate the child relation.
4. **Unbounded to-many include:** loading all children of every parent. *Check:* response size growth; add `take`/pagination.
5. **Serial external call** added by the feature. *Check:* trace spans.

Fix the confirmed cause, add a regression test ("at most N queries for this endpoint") and compare p95 before and after.

## Caching: where, what and how to invalidate

Caching is the last tool, not the first: it hides slowness rather than removing it, and invalidation is hard. When the work is genuinely expensive and repeated, cache in layers:

| Layer | Example | Good for | Watch out for |
|---|---|---|---|
| **Browser / HTTP cache** | `Cache-Control`, ETag ([Browser Contract, Lesson 05](/browser/lesson-5)) | Static and public data | Personalised data must be `private`/`no-store` |
| **CDN / edge** | `s-maxage`, `stale-while-revalidate` | Public, read-heavy responses | Never cache user-specific responses |
| **Shared cache (Redis/Memcached)** | Cache-aside for query results, sessions, rate limits | Expensive aggregates, hot reads across instances | Invalidation, stampedes, serialisation cost |
| **In-process memory** | An LRU map | Tiny, very hot, rarely-changing data | Per-instance copies, memory growth, inconsistency |
| **Database** | Materialised views, summary tables, query cache | Heavy reports | Refresh strategy |

**Cache-aside pattern:**

```ts
async function getProductPage(id: string) {
  const key = `product:v2:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const data = await buildProductPage(id);                 // the expensive work
  await redis.set(key, JSON.stringify(data), "EX", 300);   // TTL as a safety net
  return data;
}
// On update: await redis.del(`product:v2:${id}`)  ← explicit invalidation when the source changes
```

How to invalidate (pick deliberately):

- **TTL only:** simplest; accept bounded staleness.
- **Explicit invalidation** on write (delete or update the key), ideally from the code path that changes the data, or via events.
- **Versioned keys** (`v2`, or a version number stored per entity) to invalidate groups at once.
- **Stale-while-revalidate:** serve the stale value while refreshing in the background.

**Cache stampede:** when a hot key expires, thousands of requests miss at once and hammer the database. Mitigate with request coalescing ("single flight": one request recomputes, the others wait), a short lock, **jittered TTLs**, and serving stale while refreshing.

**Do not cache:** highly personalised responses (unless the key includes the user), data that must be strongly consistent (balances, stock at checkout), or error responses for long.

## Meanwhile, improve the UX (the frontend half)

If the backend cannot be fixed this week, make the wait feel shorter and stay correct:

- **Skeletons and incremental rendering:** show the layout instantly, fill in data as it arrives. Use **Suspense and streaming** so slow sections do not block fast ones.
- **Optimistic UI:** update the screen immediately on a mutation and roll back on error.
- **Stale-while-revalidate on the client** (React Query/SWR): show the last known data instantly and refresh quietly.
- **Prefetch** likely next requests (hover, route prefetch) and **cache** responses client-side.
- **Paginate or load progressively** (above-the-fold first).
- **Show progress for long operations:** return `202`, then poll or push status; never freeze the page on a spinner for 30 seconds.
- **Timeouts, retries with backoff and clear error states** so users are not left hanging.
- **Reduce requests** (batch, dedupe) so the slow endpoint is called less often.

## Common mistakes

1. **Adding Redis before finding why the query is slow.**
2. **Fixing average latency** while p99 is still terrible.
3. **Optimising the handler** when the time is in the database, or vice versa.
4. **Serial awaits** for independent calls.
5. **No timeouts** on outbound calls.
6. **Testing with tiny seed data**, so N+1 and missing indexes never appear.
7. **Caching personalised data in shared caches.**
8. **Ignoring cold starts and pool waits** because they do not show up as query time.

## Interview questions

### Q1. How do you find which part of a 3 s request is slow?

First confirm in the Network tab that TTFB dominates, then break the server's share down with a Server-Timing header, distributed tracing or structured logs with durations. The span waterfall shows handler time, each query and each outbound call. I pick the largest bar, inspect it (EXPLAIN for queries, counts for N+1, timings for external calls) and fix that before anything else.

### Q2. Scenario: an endpoint got slow after a feature added a relation. What do you suspect?

An N+1 on the new relation, a missing index on the new foreign key or filter, a join explosion or unbounded to-many include inflating rows and payload, or a new serial external call. I check query counts in the trace, `EXPLAIN ANALYZE`, response size and span timings, then fix, add a query-count test and compare p95.

### Q3. Where would you add caching, and how do you invalidate it?

After fixing the root cause, I cache expensive, repeated, mostly-read data in layers: HTTP/CDN for public responses, Redis cache-aside for aggregates, in-process only for tiny hot data. I combine a TTL as a safety net with explicit invalidation on writes (or versioned keys), and protect against stampedes with request coalescing, jitter and stale-while-revalidate. I avoid caching personalised or strongly consistent data in shared caches.

### Q4. What can the frontend do while the backend is being fixed?

Skeletons and streaming so the page is useful immediately, client-side stale-while-revalidate and caching, optimistic updates for mutations, prefetching, pagination and progressive loading, a `202` plus status-polling pattern for long operations, and clear timeouts, retries and error states. These improve perceived performance without hiding the real problem.

### Q5. Why can a request be slow even when every database query is fast?

The time may be in connection-pool waits, event-loop blocking, serial external calls, serialisation of a huge payload, a cold start, or far-apart regions, none of which appear as slow queries. A trace shows where the wall-clock time actually goes.

### Q6. How do you prevent a cache stampede?

Coalesce concurrent misses so only one request recomputes while others wait or get stale data, use short locks, add random jitter to TTLs so keys do not expire together, refresh popular keys proactively, and serve stale content while revalidating.

### Q7. How do you handle a slow third-party API you depend on?

Set strict timeouts, call it in parallel with other work, cache stable results, move non-critical calls to background jobs, add retries with backoff only for idempotent requests, wrap it in a circuit breaker with a fallback, and monitor its latency and error rate separately.

## Key takeaways

- **Break TTFB into stages** (edge, app, DB, external calls, serialisation) using Server-Timing, traces and logs; fix the biggest bar.
- The usual causes: **N+1, missing indexes, unbounded queries, serial external calls, pool exhaustion, cold starts, event-loop blocking, huge payloads, wrong region.**
- **Fix the cause first, then cache** deliberately with a clear invalidation strategy and stampede protection.
- Meanwhile, **skeletons, streaming, optimistic UI, SWR, prefetch and async jobs** keep users unblocked.
- Add a **query-count test and a p95 alert** so it does not return.
