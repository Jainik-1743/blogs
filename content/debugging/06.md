> **In one line:** a slow first load is usually **too many bytes of JavaScript, discovered too late, blocking the thing the user came to see**. Measure the bundle, send less, split what remains, load the LCP resource first, and move work to the server.

First load is where **LCP** is decided ([Browser Contract, Lesson 09](/browser/lesson-9)) and where SEO, bounce rates and conversions are won or lost. This lesson is the playbook for diagnosing and shrinking it.

## Step 1: measure what you are shipping

### See the bundle

- **Next.js:** the `next build` output lists each route's JS size ("First Load JS"). Use **`@next/bundle-analyzer`** for a treemap:

```ts
// next.config.ts
import analyzer from "@next/bundle-analyzer";
const withAnalyzer = analyzer({ enabled: process.env.ANALYZE === "true" });
export default withAnalyzer({ /* your config */ });
// ANALYZE=true pnpm build
```

- **Vite/Webpack apps:** `rollup-plugin-visualizer`, `webpack-bundle-analyzer`, or **`source-map-explorer`** on the production source maps.
- **Lighthouse** reports **"Reduce unused JavaScript"** and **"Reduce JavaScript execution time"** with the largest offenders.
- **DevTools Coverage** panel shows the percentage of each file actually executed on load.

### Sizes: know which number you are quoting

| Size | Meaning |
|---|---|
| **Raw / parsed** | What the browser must parse and execute (the real CPU cost) |
| **Gzip / Brotli (transferred)** | What crosses the network (the bandwidth cost) |

A "2 MB bundle" that is 600 KB over the wire still costs 2 MB of parse, compile and execute time, which on a mid-range phone is often **more painful than the download**. State which one you mean.

### Check the waterfall

Use the Network tab (throttled to "Slow 4G" and CPU 4x) and a tool like WebPageTest to see: when the **HTML**, **CSS**, **JS**, **LCP image** and **fonts** are requested, what **blocks rendering**, and how many requests are chained (a script that loads a script that loads a font).

## Step 2: the levers

### Lever 1: send less JavaScript

| Technique | What to do |
|---|---|
| **Remove dead code and dependencies** | Delete unused packages and components; check for duplicate versions of the same library |
| **Replace heavy libraries** | `moment` (large, with locale data) → `date-fns`, `dayjs` or the built-in `Intl`; whole `lodash` → per-function imports or native methods; big UI kits → tree-shakeable ones |
| **Tree-shaking friendly imports** | `import { debounce } from "lodash-es"`, not `import _ from "lodash"`. Watch **barrel files** (`index.ts` re-exporting everything), which can pull in whole packages; Next's `optimizePackageImports` handles common libraries |
| **Avoid unneeded polyfills** | Target modern browsers via `browserslist`; ship legacy bundles only if analytics justify it |
| **Prefer server work** | Format dates, render markdown, syntax-highlight and compute data **on the server** so the code and libraries never reach the client |
| **Avoid shipping data as JS** | Large JSON inlined in bundles; fetch it lazily or paginate |

### Lever 2: code splitting

Split the bundle so each page loads only what it needs, and rarely used heavy features load on demand.

- **Route-level splitting** is automatic in Next.js (each page is its own chunk).
- **Component-level splitting** for heavy, non-critical or conditional UI: charts, rich-text editors, maps, PDF viewers, modals, admin panels.

```tsx
import dynamic from "next/dynamic";

const Chart = dynamic(() => import("./Chart"), {
  ssr: false,                      // only if it needs `window`/canvas and isn't needed for first paint
  loading: () => <div style={{ height: 320 }} aria-busy="true" />,   // reserve space to avoid layout shift
});
```

```tsx
// Plain React: lazy + Suspense
const Editor = React.lazy(() => import("./Editor"));
<Suspense fallback={<EditorSkeleton />}>{showEditor && <Editor />}</Suspense>
```

Load on **interaction** (open the modal → import the editor) or when **visible** (IntersectionObserver) rather than on page load.

### Lever 3: Server Components and streaming

In the Next.js App Router, **Server Components** render on the server and send **no component JavaScript** to the client. Make components server-side by default and add `"use client"` only to interactive leaves ([Frontend Depth, Lesson 02](/frontend-depth/lesson-2)). Combined with **streaming** (`<Suspense>` boundaries), the shell and above-the-fold content reach the browser immediately while slower data streams in, and less JS means less hydration ([Lesson 01](/debugging/lesson-1)).

### Lever 4: images (the usual LCP element)

- **Right format:** AVIF or WebP instead of PNG/JPEG where supported.
- **Right size:** responsive `srcset`/`sizes`, never a 4000 px image shown at 400 px.
- **Right priority:** the LCP image must be **in the HTML**, **not lazy-loaded**, and fetched with **`fetchpriority="high"`** (in Next.js: `<Image priority />`). Everything below the fold gets `loading="lazy"`.
- **Reserve space:** `width`/`height` or `aspect-ratio`, to prevent layout shift.
- **Serve from a CDN** with long cache lifetimes and correct compression.

```tsx
import Image from "next/image";
<Image src="/hero.jpg" alt="…" width={1200} height={630} priority sizes="100vw" />
```

### Lever 5: fonts

Web fonts can delay text (invisible text) or shift layout when they swap.

- **Self-host** and subset (only the glyphs and weights you use); `next/font` does this and removes the extra network hop to a font CDN.
- **`font-display: swap`** (or `optional`) so text shows immediately with a fallback.
- **Size-adjusted fallbacks** (`size-adjust`, `ascent-override`) to minimise shift when the real font loads (`next/font` handles this).
- **Preload** the one or two critical font files; limit weights and styles.

### Lever 6: CSS and render-blocking resources

CSS blocks rendering, and synchronous scripts block parsing ([Browser Contract, Lesson 00](/browser/lesson-0)).

- Keep CSS small: remove unused CSS (Tailwind's purging, CSS modules), inline **critical CSS** where the framework supports it.
- Use `defer`/`async` or `type="module"` for scripts; avoid synchronous third-party tags in `<head>`.
- Load **third-party scripts** (analytics, chat, A/B tools) with `next/script` strategies such as `afterInteractive` or `lazyOnload`, and question whether each one is needed.

### Lever 7: network and delivery

- **Compression:** Brotli (or gzip) for text assets at the CDN or server.
- **Caching:** hashed assets with a year-long `immutable` policy ([Browser Contract, Lesson 05](/browser/lesson-5)).
- **CDN** to reduce RTT; **HTTP/2 or HTTP/3** for multiplexing.
- **Fewer origins:** each new origin adds DNS, TCP and TLS; `preconnect` only to the few that are truly critical.
- **Avoid redirect chains** (`http` → `https` → `www` → `/en`).

## Preload vs prefetch vs preconnect

| Hint | Meaning | Priority | Use for |
|---|---|---|---|
| **`preload`** | "I need this **for the current page**, fetch it now" | High | The LCP image, a critical font, a key script discovered late |
| **`prefetch`** | "I **might** need this for a **future navigation**" | Lowest, during idle time | The JS/data of the likely next page (Next's `<Link>` prefetches automatically) |
| **`preconnect`** | Open DNS + TCP + TLS to an origin early | Medium | A critical third-party origin (API, font host) |
| **`dns-prefetch`** | Resolve DNS only | Low | Less critical third-party origins |

Overusing `preload` hurts: it competes with other critical resources. Preload **one or two** things you have verified are discovered late.

## Putting it together

```text
Typical LCP timeline (bad)                          Optimised
─────────────────────────────                       ─────────────────────────────
HTML ........ 900 ms (no CDN, no streaming)         HTML (CDN, streamed) ...... 150 ms
CSS ......... blocks until 1,100 ms                 Critical CSS inline ........ 0 ms extra
JS bundle 2 MB executes until 2,400 ms              ~150 KB initial JS, rest lazy
LCP image discovered by JS at 2,500 ms              <img priority> in HTML, fetched at 200 ms
LCP ≈ 3.8 s                                         LCP ≈ 1.4 s
```

## Scenario: the JS bundle is 2 MB. Plan how to halve it.

1. **Establish a baseline:** note parsed and compressed sizes per route, First Load JS, Lighthouse unused-JS, and field LCP/INP.
2. **Analyse:** run the bundle analyzer; list the **top 10 contributors**. Look for the usual suspects: a date or charting library, an icon pack imported whole, moment locales, duplicate React/lodash versions, an unused UI kit, a polyfill bundle.
3. **Quick wins first:**
   - Remove unused dependencies and dead code.
   - Fix imports (per-icon, per-function, `lodash-es`); enable `optimizePackageImports` where relevant.
   - De-duplicate versions (`pnpm dedupe`, resolutions).
   - Target modern browsers to drop polyfills.
4. **Split what's left:** dynamic-import heavy, below-the-fold or interaction-only features (editor, charts, admin, PDF export); verify each now loads on demand.
5. **Move work to the server:** convert non-interactive components to Server Components; do formatting/highlighting/markdown on the server.
6. **Replace heavy libraries** with lighter or native alternatives where it pays off.
7. **Check delivery:** Brotli, caching headers, CDN.
8. **Lock it in:** set a **performance budget** in CI (`size-limit`, Lighthouse CI, or Next's checks) that fails the build when a route's JS exceeds a threshold.
9. **Measure again:** parsed and compressed sizes, route First Load JS, LCP, INP and Total Blocking Time. Confirm the improvement in field data after release.

## Diagnosing a poor LCP: a short procedure

1. Identify the **LCP element** (Lighthouse or Performance panel "LCP" marker; DevTools "Performance Insights").
2. Break LCP into **TTFB, resource load delay, resource load duration, element render delay**.
3. Fix the dominant part:
   - **High TTFB:** CDN, caching, streaming, faster data ([Lesson 02](/debugging/lesson-2)).
   - **High load delay:** make the LCP resource discoverable in HTML; preload; remove JS-injected or CSS-background heroes; don't lazy-load it.
   - **High load duration:** smaller, modern, correctly sized image; CDN.
   - **High render delay:** render-blocking CSS/JS, client-side rendering waiting on JS, main-thread congestion.

## Common mistakes

1. **Quoting only the gzipped size** and ignoring parse and execute cost.
2. **Lazy-loading the hero image.**
3. **Importing entire libraries** for one function; barrel-file imports.
4. **Client-rendering content** that could be server-rendered.
5. **Preloading everything.**
6. **Loading third-party scripts synchronously** or on page load.
7. **No performance budget**, so the bundle grows back.
8. **Optimising on a fast machine** with a warm cache.

## Interview questions

### Q1. How do you diagnose a poor LCP?

Find the LCP element, then split LCP into TTFB, resource load delay, load duration and element render delay and fix the largest part: faster server and caching for TTFB, discoverable and prioritised LCP resource (in HTML, preload, `fetchpriority`, not lazy) for load delay, smaller and modern images for load duration, and removing render-blocking CSS/JS or client-side rendering delays for render delay. Verify with field data.

### Q2. Scenario: the JS bundle is 2 MB. Plan how to halve it.

Baseline sizes and metrics, run a bundle analyzer, remove unused and duplicate dependencies, fix imports and polyfills, code-split heavy or rarely-used features with dynamic imports, push non-interactive work to Server Components, replace heavy libraries, ensure Brotli and caching, add a size budget in CI, and re-measure parsed size, route JS and LCP/INP.

### Q3. Preload vs prefetch?

`preload` fetches a resource needed for the current page at high priority (the LCP image, a critical font). `prefetch` fetches a resource that may be needed for a future navigation at the lowest priority during idle time. Preload too much and you delay important resources; prefetch speeds up likely next pages.

### Q4. What is the LCP element, and how do you speed it up?

The largest visible content element in the viewport during load, usually a hero image or heading. Make it discoverable early in the HTML (not a CSS background or JS-injected), prioritise it (`fetchpriority="high"`, preload, `priority` in Next Image), serve it small, modern and from a CDN, and avoid render-blocking resources that delay painting it.

### Q5. Why does bundle size matter beyond download time?

JavaScript must be parsed, compiled and executed on the main thread, which is slow on mid-range phones. That delays rendering, hydration and interactivity (INP). Compressed size affects network time, but the uncompressed size drives CPU cost.

### Q6. How do Server Components help first-load performance?

They run on the server and send no component JavaScript, so less code is downloaded, parsed and hydrated. Combined with streaming Suspense boundaries, users see content sooner and the main thread is freer for interaction.

### Q7. How do you stop a bundle from growing back?

Set a performance budget enforced in CI (size-limit, Lighthouse CI, framework checks), review dependency additions, track bundle size per route in pull requests and monitor field LCP/INP after release.

### Q8. How do you handle third-party scripts?

Question whether each is necessary, load them asynchronously with a late strategy (`lazyOnload`, after interaction), self-host or isolate heavy ones (Partytown/web workers where appropriate), measure their long-task and INP impact, and remove those that cost more than they deliver.

## Key takeaways

- Measure **parsed and compressed** bundle size, route by route; use an analyzer and Lighthouse; read the waterfall.
- **Send less** (dead code, lighter libs, tree-shaking, no needless polyfills), **split the rest** (dynamic imports on interaction or visibility), and **move work to Server Components**.
- Make the **LCP resource early and high priority**; optimise images and fonts; keep CSS and scripts from blocking.
- Use `preload` sparingly, `prefetch` for next pages, `preconnect` for critical origins.
- Enforce a **budget** and watch field data.
