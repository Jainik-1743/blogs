> **In one line:** a slow first load usually means **too much JavaScript, found too late, blocking what the user came to see**. Measure the bundle (all the JavaScript files your page sends), send less, split what is left, load the main image or text first, and move work to the server.

The first load decides your **LCP** (Largest Contentful Paint: the time until the biggest thing on screen appears). See [Browser Contract, Lesson 09](/browser/lesson-9). It also affects SEO, bounce rate (people leaving at once) and sales. This lesson shows you how to find the problem and make the first load smaller.

## Step 1: measure what you are shipping

### See the bundle

A **bundle** is the JavaScript file (or files) your build makes for the browser. First, look inside it.

- **Next.js:** the `next build` output lists each route's JS size ("First Load JS"). For a picture of what takes space (a treemap), newer versions have a built-in analyzer (`npx next experimental-analyze`). You can also use **`@next/bundle-analyzer`**:

```ts
// next.config.ts
import analyzer from "@next/bundle-analyzer";
const withAnalyzer = analyzer({ enabled: process.env.ANALYZE === "true" });
export default withAnalyzer({ /* your config */ });
// ANALYZE=true pnpm build
```

- **Vite/Webpack apps:** use `rollup-plugin-visualizer`, `webpack-bundle-analyzer`, or **`source-map-explorer`** on the production source maps.
- **Lighthouse** shows **"Reduce unused JavaScript"** and **"Reduce JavaScript execution time"**, with the biggest problems first.
- The **DevTools Coverage** panel shows how much of each file really ran on load.

### Sizes: know which number you are quoting

| Size | Meaning |
|---|---|
| **Raw / parsed** | What the browser must read and run. This is the real CPU cost. |
| **Gzip / Brotli (transferred)** | What travels over the network. This is the bandwidth cost. (Gzip and Brotli are ways to compress files.) |

Say a bundle is "2 MB" but only 600 KB goes over the network. The browser still has to read, compile and run all 2 MB. On a mid-range phone this is often **worse than the download**. Always say which number you mean.

### Check the waterfall

The **waterfall** is a chart of every request, in time order. Use the Network tab (set to "Slow 4G" and CPU 4x slower) and a tool like WebPageTest. Look for these things:

- When the **HTML**, **CSS**, **JS**, **LCP image** and **fonts** are requested.
- What **blocks rendering** (stops the page from drawing).
- How many requests are chained (a script loads a script that loads a font).

## Step 2: the levers

A lever is one thing you can change to make the first load faster.

### Lever 1: send less JavaScript

| Technique | What to do |
|---|---|
| **Remove dead code and dependencies** | Delete packages and components you do not use. Check for two versions of the same library. |
| **Replace heavy libraries** | Swap `moment` (large, with language data) for `date-fns`, `dayjs` or the built-in `Intl`. Instead of all of `lodash`, import single functions or use native methods. Swap big UI kits for ones that tree-shake (see next row). |
| **Tree-shaking friendly imports** | Tree-shaking means the build removes code you never use. Write `import { debounce } from "lodash-es"`, not `import _ from "lodash"`. Watch out for **barrel files** (an `index.ts` that re-exports everything). They can pull in a whole package. Next's `optimizePackageImports` fixes this for common libraries. |
| **Avoid unneeded polyfills** | A polyfill is extra code that adds a feature to old browsers. Target modern browsers with `browserslist`. Send legacy bundles only if your analytics show you need them. |
| **Prefer server work** | Format dates, render markdown, highlight code and compute data **on the server**. Then the code and libraries never reach the browser. |
| **Avoid shipping data as JS** | Do not put large JSON inside the bundle. Fetch it later, or split it into pages. |

### Lever 2: code splitting

Code splitting means cutting the bundle into smaller pieces. Each page then loads only what it needs. Heavy features that few people use load only when needed.

- **Route-level splitting** is automatic in Next.js. Each page is its own chunk (piece).
- **Component-level splitting** is for heavy or optional parts of the UI: charts, rich-text editors, maps, PDF viewers, modals, admin panels.

```tsx
import dynamic from "next/dynamic";

const Chart = dynamic(() => import("./Chart"), {
  ssr: false,                      // only if it needs `window`/canvas and isn't needed for first paint
  loading: () => <div style={{ height: 320 }} aria-busy="true" />,   // reserve space to avoid layout shift
});
```

> [!warn] In the App Router, you can use `ssr: false` only inside a **Client Component** (a file with `"use client"`). Using it in a Server Component is an error. Put the `dynamic()` call in a small client wrapper.

```tsx
// Plain React: lazy + Suspense
const Editor = React.lazy(() => import("./Editor"));
<Suspense fallback={<EditorSkeleton />}>{showEditor && <Editor />}</Suspense>
```

Load code when the user **acts** (they open the modal, so you import the editor). Or load it when the part becomes **visible** (use IntersectionObserver). Do not load it when the page first opens.

### Lever 3: Server Components and streaming

In the Next.js App Router, **Server Components** run on the server. They send **no component JavaScript** to the browser. So make components server-side by default. Add `"use client"` only to small interactive parts ([Frontend Depth, Lesson 02](/frontend-depth/lesson-2)).

**Streaming** means the server sends the page in pieces. You use `<Suspense>` boundaries for this. The page shell and the top of the page arrive first. Slower data follows later. Less JS also means less hydration (the browser work that makes server HTML interactive). See [Lesson 01](/debugging/lesson-1).

### Lever 4: images (the usual LCP element)

- **Right format:** use AVIF or WebP instead of PNG or JPEG where the browser supports them.
- **Right size:** use responsive `srcset` and `sizes`. Never show a 4000 px image at 400 px.
- **Right priority:** the LCP image must be **in the HTML**. It must **not be lazy-loaded**. Fetch it with **`fetchpriority="high"`**. In Next.js, write `<Image fetchPriority="high" loading="eager" />`. The older `priority` prop was deprecated in Next.js 16 in favour of `preload`, so check the docs for your version. Everything below the fold (the part you must scroll to see) gets `loading="lazy"`.
- **Reserve space:** set `width` and `height`, or `aspect-ratio`. This stops layout shift (content jumping).
- **Serve from a CDN** (servers close to users) with long cache times and correct compression.

```tsx
import Image from "next/image";
<Image src="/hero.jpg" alt="…" width={1200} height={630} fetchPriority="high" loading="eager" sizes="100vw" />
```

### Lever 5: fonts

Web fonts can hide your text for a while (invisible text). They can also move the layout when the real font replaces the first one.

- **Self-host** the fonts and subset them (keep only the letters and weights you use). `next/font` does this. It also removes the extra network trip to a font CDN.
- Use **`font-display: swap`** (or `optional`). Then text shows at once in a fallback font.
- Use **size-adjusted fallbacks** (`size-adjust`, `ascent-override`). They make the fallback font about the same size as the real one, so less shift happens. `next/font` does this for you.
- **Preload** the one or two most important font files. Keep the number of weights and styles low.

### Lever 6: CSS and render-blocking resources

A **render-blocking** resource stops the browser from drawing the page until it has loaded. CSS blocks rendering. Synchronous scripts block parsing (reading the HTML). See [Browser Contract, Lesson 00](/browser/lesson-0).

- Keep CSS small. Remove unused CSS (Tailwind's purging, CSS modules). Put **critical CSS** (the CSS needed for the first screen) inline, if your framework supports it.
- Use `defer`, `async` or `type="module"` for scripts. Avoid synchronous third-party tags in `<head>`.
- Load **third-party scripts** (analytics, chat, A/B tools) with `next/script` strategies such as `afterInteractive` or `lazyOnload`. Also ask if you need each one at all.

### Lever 7: network and delivery

- **Compression:** use Brotli (or gzip) for text files at the CDN or server.
- **Caching:** give hashed files (files with a content hash in the name) a year-long `immutable` policy. See [Browser Contract, Lesson 05](/browser/lesson-5).
- **CDN** to cut RTT (round-trip time: the time for a request to go and come back). Use **HTTP/2 or HTTP/3** so many requests can share one connection.
- **Fewer origins:** each new origin (website address) adds DNS, TCP and TLS setup work. Use `preconnect` only for the few that are truly critical.
- **Avoid redirect chains** such as `http` to `https` to `www` to `/en`.

## Preload vs prefetch vs preconnect

These are hints you give the browser about what to load early.

| Hint | Meaning | Priority | Use for |
|---|---|---|---|
| **`preload`** | "I need this **for the current page**. Fetch it now." | High | The LCP image, a critical font, a key script found late |
| **`prefetch`** | "I **might** need this for a **future page**." | Lowest, runs when the browser is idle | The JS and data of the likely next page (Next's `<Link>` prefetches by itself) |
| **`preconnect`** | Open DNS + TCP + TLS to an origin early | Medium | A critical third-party origin (API, font host) |
| **`dns-prefetch`** | Look up the DNS only | Low | Less important third-party origins |

Too much `preload` hurts. The files compete with other important files. Preload **one or two** things that you have checked are found late.

## Putting it together

```text
Typical LCP timeline (bad)                          Optimised
─────────────────────────────                       ─────────────────────────────
HTML ........ 900 ms (no CDN, no streaming)         HTML (CDN, streamed) ...... 150 ms
CSS ......... blocks until 1,100 ms                 Critical CSS inline ........ 0 ms extra
JS bundle 2 MB executes until 2,400 ms              ~150 KB initial JS, rest lazy
LCP image discovered by JS at 2,500 ms              <img fetchpriority=high> in HTML, fetched at 200 ms
LCP ≈ 3.8 s                                         LCP ≈ 1.4 s
```

## Scenario: the JS bundle is 2 MB. Plan how to halve it.

1. **Set a baseline.** Write down the parsed and compressed sizes per route, First Load JS, the Lighthouse unused-JS number, and the real-user LCP and INP (INP measures how fast the page reacts to clicks and taps).
2. **Analyse.** Run the bundle analyzer. List the **top 10 contributors**. Look for the usual causes:
   - a date or charting library
   - a whole icon pack
   - moment locales
   - two versions of React or lodash
   - an unused UI kit
   - a polyfill bundle
3. **Do the quick wins first:**
   - Remove unused dependencies and dead code.
   - Fix imports (one icon, one function, `lodash-es`). Turn on `optimizePackageImports` where it helps.
   - Remove duplicate versions (`pnpm dedupe`, resolutions).
   - Target modern browsers to drop polyfills.
4. **Split what is left.** Use dynamic imports for heavy features: below-the-fold parts and features used only after a click (editor, charts, admin, PDF export). Check that each one now loads only when needed.
5. **Move work to the server.** Turn parts that are not interactive into Server Components. Do formatting, highlighting and markdown on the server.
6. **Replace heavy libraries** with lighter or native options where it is worth it.
7. **Check delivery:** Brotli, cache headers, CDN.
8. **Lock it in.** Set a **performance budget** in CI (your automatic checks). Tools: `size-limit`, Lighthouse CI, or Next's checks. The build fails when a route's JS goes over a limit.
9. **Measure again:** parsed and compressed sizes, route First Load JS, LCP, INP and Total Blocking Time (how long the main thread was stuck). After release, confirm the gain in real-user data.

## Diagnosing a poor LCP: a short procedure

1. Find the **LCP element**. Use Lighthouse, or the "LCP" marker in the Performance panel, or DevTools "Performance Insights".
2. Break LCP into four parts: **TTFB** (time until the first byte arrives), **resource load delay**, **resource load duration** and **element render delay**.
3. Fix the biggest part:
   - **High TTFB:** use a CDN, caching, streaming and faster data ([Lesson 02](/debugging/lesson-2)).
   - **High load delay:** make the LCP resource easy to find in the HTML. Preload it. Remove heroes added by JS or set as CSS backgrounds. Do not lazy-load it.
   - **High load duration:** use a smaller, modern, correctly sized image. Use a CDN.
   - **High render delay:** look for render-blocking CSS or JS, client-side rendering that waits for JS, and a busy main thread.

## Common mistakes

1. **Quoting only the gzipped size** and ignoring the cost to parse and run the code.
2. **Lazy-loading the hero image.**
3. **Importing a whole library** for one function, or importing through barrel files.
4. **Rendering content in the browser** when the server could render it.
5. **Preloading everything.**
6. **Loading third-party scripts** synchronously or at page load.
7. **No performance budget**, so the bundle grows back.
8. **Tuning on a fast machine** with a warm cache (files already stored).

## Interview questions

### Q1. How do you diagnose a poor LCP?

First I find the LCP element. Then I split LCP into four parts: TTFB, resource load delay, load duration and element render delay. I fix the biggest part.

- For slow TTFB, I use a faster server and caching.
- For load delay, I make the LCP resource easy to find and give it priority. It goes in the HTML, with preload and `fetchpriority`, and it is not lazy.
- For load duration, I use smaller, modern images.
- For render delay, I remove render-blocking CSS and JS, or client-side rendering delays.

At the end I check with real-user data.

### Q2. Scenario: the JS bundle is 2 MB. Plan how to halve it.

I write down the baseline sizes and metrics. Then I run a bundle analyzer. I remove unused and duplicate dependencies, and fix imports and polyfills. I split heavy or rarely used features with dynamic imports. I move work that is not interactive to Server Components. I replace heavy libraries. I make sure Brotli and caching are on, and I add a size budget in CI. At the end I measure parsed size, route JS and LCP/INP again.

### Q3. Preload vs prefetch?

`preload` fetches a resource that the current page needs, at high priority. Examples are the LCP image and a critical font. `prefetch` fetches a resource that a future page may need, at the lowest priority, when the browser is idle. If you preload too much, you slow down the important files. Prefetch makes the likely next pages faster.

### Q4. What is the LCP element, and how do you speed it up?

It is the largest visible element in the viewport (the part of the page you can see) while the page loads. It is usually a hero image or a heading. To speed it up:

- Make it easy to find early in the HTML. It should not be a CSS background or added by JS.
- Give it priority with `fetchpriority="high"` and preload. In Next Image, use `fetchPriority` or `preload`.
- Serve it small and in a modern format, from a CDN.
- Remove render-blocking files that delay drawing it.

### Q5. Why does bundle size matter beyond download time?

The main thread must parse, compile and run JavaScript. This is slow on mid-range phones. It delays rendering, hydration and interactivity (INP). The compressed size affects network time. But the uncompressed size decides the CPU cost.

### Q6. How do Server Components help first-load performance?

They run on the server and send no component JavaScript. So the browser downloads, parses and hydrates less code. With streaming Suspense boundaries, users see content sooner. The main thread is also freer to respond to clicks.

### Q7. How do you stop a bundle from growing back?

I set a performance budget and enforce it in CI (size-limit, Lighthouse CI, framework checks). I review new dependencies. I track bundle size per route in pull requests. After each release I watch real-user LCP and INP.

### Q8. How do you handle third-party scripts?

First I ask if each one is really needed. I load them asynchronously with a late strategy (`lazyOnload`, or after the user acts). For heavy ones, I self-host them or isolate them (Partytown or web workers, where it makes sense). I measure their effect on long tasks and INP. I remove the ones that cost more than they give.

## Key takeaways

- Measure the **parsed and compressed** bundle size, route by route. Use an analyzer and Lighthouse. Read the waterfall.
- **Send less** (dead code, lighter libraries, tree-shaking, no needless polyfills). **Split the rest** (dynamic imports when the user acts or the part is visible). **Move work to Server Components.**
- Make the **LCP resource load early and with high priority**. Optimise images and fonts. Keep CSS and scripts from blocking.
- Use `preload` sparingly, `prefetch` for next pages, and `preconnect` for critical origins.
- Enforce a **budget** and watch real-user data.
