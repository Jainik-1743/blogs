> **In one line:** **layout shift** is content moving *after* the user has started reading or aiming at it; **jank** is the page failing to respond or animate smoothly. Shift is fixed by **reserving space**; jank is fixed by **keeping the main thread free** and acknowledging input immediately.

Both are about trust. A button that jumps as you tap it sends you to the wrong page; an input that lags a character behind makes the app feel broken. They map to two Core Web Vitals, **CLS** and **INP** ([Browser Contract, Lesson 09](/browser/lesson-9)).

## Part 1: layout shift (CLS)

### What counts

A layout shift occurs when a **visible element changes its start position between frames** without a user-initiated cause. Each shift is scored by:

```text
shift score = impact fraction × distance fraction
```

(how much of the viewport the moving content affected, multiplied by how far it moved relative to the viewport). CLS reports the worst burst of shifts ("session window") during the page's life. Good is **0.1 or less** at the 75th percentile. Shifts within about half a second of a user input (opening a menu, clicking "show more") are excluded because the user expects them.

### Common causes and fixes

| Cause | What happens | Fix |
|---|---|---|
| **Images, video and iframes without dimensions** | The browser does not know the height until the file arrives, then pushes content down | Set `width` and `height` attributes (the browser derives an aspect ratio) or CSS `aspect-ratio`; `next/image` requires dimensions or `fill` with a sized parent |
| **Late-loading ads, embeds and widgets** | An empty slot becomes 250 px tall | Reserve the slot size with `min-height` (use the most common ad size); collapse only below the fold or after the user has scrolled past |
| **Banners and notices inserted above content** | Cookie banner, promo bar or "related" strip pushes everything down | Reserve space in advance, insert **below** the visible content, or overlay with `position: fixed`/`sticky` and `transform` instead of pushing the layout |
| **Web font swap** | Fallback text reflows when the real font loads with different metrics | `font-display: swap` plus a **metrics-matched fallback** (`size-adjust`, `ascent-override`; `next/font` generates these), or `font-display: optional`; preload the key font |
| **Content injected by client-side rendering** | The skeleton and the final content have different heights | Make skeletons **match the final size**; render above-the-fold on the server; fixed-height containers for lists with predictable rows |
| **Animations using layout properties** | Animating `top`, `height`, `margin` triggers layout each frame | Animate `transform` and `opacity` |
| **Lazy-loaded images without reserved space** | The page jumps as images enter | Same as images: dimensions or `aspect-ratio` |
| **Dynamic content after hydration** | A client component swaps text (locale, a logged-in name) and changes line wrapping | Render the same on server and client; reserve width; avoid layout-changing personalisation after first paint |
| **Responsive images with unknown ratio** | Container resizes on load | Use `aspect-ratio` on the container |

```css
/* Reserve space before anything loads */
.hero img    { width: 100%; height: auto; aspect-ratio: 16 / 9; }
.ad-slot     { min-height: 250px; }
.avatar      { width: 40px; height: 40px; }
.skeleton-row{ height: 56px; }               /* equals the real row height */

/* Stop the browser re-anchoring scroll position when content above changes (sometimes you want the opposite) */
.chat-log { overflow-anchor: auto; }
```

```tsx
// Reserve the space while a client component loads
const Map = dynamic(() => import("./Map"), { ssr: false, loading: () => <div style={{ height: 400 }} /> });
```

### Debugging CLS

1. **Chrome DevTools → Performance panel**: record a load; the **Experience → Layout Shifts** track marks each shift; click one to see which nodes moved and the score.
2. **Rendering tab → "Layout Shift Regions"**: flashes blue where shifts occur, live.
3. **Lighthouse** lists "Avoid large layout shifts" with the culprit elements and "Image elements do not have explicit width and height".
4. **In code**, with a `PerformanceObserver`:

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries() as any[]) {
    if (entry.hadRecentInput) continue;               // user-initiated shifts don't count
    console.log("shift", entry.value.toFixed(4), entry.sources?.map((s: any) => s.node));
  }
}).observe({ type: "layout-shift", buffered: true });
```

5. **Field data:** the `web-vitals` library's attribution build reports the **largest shift source** per page view so you can see which element shifts for real users.

### Scenario: the page jumps when a banner loads. Fix it.

- **Diagnose** with Layout Shift Regions or the Performance track: the banner `<div>` is injected at the top by a script after first paint and pushes the page down.
- **Fix options:** (1) render the banner on the server so it is in the initial HTML; (2) reserve its height with a fixed-size container (CSS `min-height`) before the script runs; (3) make it an overlay (`position: fixed` at the bottom) so nothing moves; (4) animate it with `transform` rather than layout properties.
- **Prevent:** a Lighthouse CI check on CLS, RUM alerts for CLS regressions, and a code-review rule: "anything that appears after load must have reserved space."

## Part 2: janky interactions (INP and frame drops)

### What it feels like

- Typing into an input: characters appear late or in bursts.
- Clicking a button: nothing happens for a beat, then everything happens at once.
- Scrolling stutters; animations skip frames.

INP breaks an interaction into **input delay** (the main thread was busy), **processing time** (your handlers) and **presentation delay** (rendering the result). All three come from the same place: the main thread being occupied ([Browser Contract, Lesson 08](/browser/lesson-8)).

### Causes and fixes

| Cause | Fix |
|---|---|
| **A heavy event handler** doing too much synchronously (validation, filtering 10k items, analytics, logging) | Do the minimum to update the UI, then **defer the rest** with `startTransition`, `setTimeout(0)`/`scheduler.yield()`, `requestIdleCallback`, or a Web Worker |
| **Large re-render triggered by the input** (each keystroke re-renders the page) | Colocate state, memoise, `useDeferredValue` ([Lesson 03](/debugging/lesson-3)) |
| **Controlled inputs in giant forms** | Use uncontrolled inputs or a form library that isolates field re-renders (React Hook Form); validate on blur or debounced |
| **Long tasks from third-party scripts** | Lazy-load, delay until after interaction, remove, or isolate in a worker |
| **Layout thrashing in handlers or scroll listeners** | Batch reads then writes; `requestAnimationFrame`; observers instead of polling geometry |
| **Scroll/touch listeners that aren't passive** | `{ passive: true }`; avoid synchronous work in them |
| **Huge DOM** making every style and layout pass expensive | Virtualise ([Lesson 07](/debugging/lesson-7)); `content-visibility` |
| **Animations on layout properties** | Use `transform` and `opacity`; `will-change` sparingly |
| **Expensive CSS** (deep selectors, large `box-shadow`/`filter` on many elements) | Simplify, reduce painted area, use the compositor |
| **Synchronous `localStorage`, big JSON parsing or `structuredClone` in handlers** | Move off the main thread or do lazily |

**Yield to let the browser paint first** (the "acknowledge, then work" pattern):

```ts
button.addEventListener("click", async () => {
  button.classList.add("loading");                       // 1. immediate visual feedback
  await (globalThis.scheduler?.yield?.() ?? new Promise((r) => setTimeout(r, 0))); // 2. let the browser paint
  const result = expensiveWork();                         // 3. then the heavy part
  render(result);
});
```

In React, `startTransition` gives the same shape: update the urgent state now, the expensive state in the background.

### Debugging janky interactions

1. **Performance panel**: record the interaction with **CPU throttling**; the **Interactions** track shows each interaction's duration and splits input delay, processing and presentation. Click a long one and inspect the flame chart for the dominant function.
2. Look for **long tasks** (red-cornered) around the interaction and **forced reflow** warnings.
3. Chrome's **Long Animation Frames (LoAF)** API and DevTools Insights attribute long frames to scripts and callbacks, helping to blame a specific handler or third-party script.
4. **React Profiler** for re-render cost during the interaction.
5. **Field INP** via the `web-vitals` attribution build identifies the slowest interaction target and the phase responsible.

```ts
import { onINP } from "web-vitals/attribution";

onINP(({ value, attribution }) => {
  navigator.sendBeacon("/vitals", JSON.stringify({
    inp: value,
    target: attribution.interactionTarget,     // which element
    type: attribution.interactionType,         // click, keyboard…
    inputDelay: attribution.inputDelay,
    processing: attribution.processingDuration,
    presentation: attribution.presentationDelay,
  }));
});
```

## A short checklist

**Before launch**

- Every image, video, iframe and ad has reserved dimensions.
- Fonts use `font-display` with a matched fallback (or `next/font`).
- Skeletons match final heights; anything dynamic has reserved space.
- Animations use `transform`/`opacity`.
- Event handlers are light; heavy work is deferred or off-thread.
- Scroll and touch listeners are passive; no layout reads in loops.
- Large lists are virtualised or paginated.
- Third-party scripts are lazy-loaded and measured.

**In production**

- RUM tracks CLS and INP with attribution (element, phase), segmented by route and device.
- Alerts fire on regression; Lighthouse CI guards the main pages.
- New UI patterns are reviewed for "what moves when this loads?" and "what runs when this is clicked?"

## Common mistakes

1. **Images without dimensions** (still the number one CLS cause).
2. **Inserting content above existing content** after load.
3. **Skeletons with different dimensions** than the final content.
4. **Font swaps** with no size-matched fallback.
5. **Animating layout properties.**
6. **Doing all the work inside the click handler** before the UI updates.
7. **Controlled inputs re-rendering a huge form** on each keystroke.
8. **Not testing on throttled CPUs and real devices.**

## Interview questions

### Q1. What causes CLS?

Content that changes position after it has rendered: images, video or iframes without reserved dimensions; late-loading ads and embeds; banners or content injected above existing content; web fonts swapping with different metrics; skeletons that do not match final sizes; and animations that change layout properties. Fix by reserving space, matching fallbacks, and animating `transform`.

### Q2. Scenario: the page jumps when a banner loads. Fix it.

Find the shift with the Layout Shift Regions overlay or the Performance panel, then render the banner in the initial HTML, reserve its height before it loads, or make it an overlay so it does not push content. Animate with `transform`, and add CLS monitoring and a CI check to prevent regressions.

### Q3. How do you reserve space for dynamic content?

Use `width`/`height` or `aspect-ratio` for media, fixed or minimum heights for slots and skeletons that match the real content, and `contain-intrinsic-size` for deferred sections. For unknown-height content, reserve the typical size, or load it in an overlay or below the fold.

### Q4. Why does input lag happen and how do you fix it?

The main thread is busy when the event arrives (input delay), the handler does too much (processing time), or rendering after it is expensive (presentation delay). Do the minimum work in the handler, defer the rest with transitions, yielding or workers, reduce re-render scope, virtualise big lists, and move or remove heavy third-party scripts.

### Q5. How do you debug a slow interaction?

Record it in the Performance panel with CPU throttling, inspect the Interactions track to see which phase dominates, open the flame chart for the long task, check for forced reflows and React re-render cost, and use the `web-vitals` attribution build to find the worst interaction in the field.

### Q6. How do you prevent font-related layout shift?

Use `font-display: swap` or `optional`, provide a fallback font adjusted to match the web font's metrics (`size-adjust`, `ascent-override`), preload the critical font and self-host with subsetting. `next/font` automates most of this.

### Q7. Which interactions are excluded from CLS and why?

Layout shifts within about 500 ms after a user input (click, tap, key press) are excluded because the user expects the interface to change in response. Unexpected movement with no recent input is what harms the experience.

## Key takeaways

- **CLS = reserve space.** Dimensions for media, fixed slots for late content, matched skeletons and fonts, insert below or overlay, animate `transform`.
- **Jank/INP = free the main thread.** Light handlers, defer the rest, narrow re-renders, passive listeners, batched layout reads, virtualised lists, lazy third parties.
- Use **Layout Shift Regions** and the **Interactions track**; collect **attribution data** in production.
- Guard with **Lighthouse CI and RUM alerts**, and review every new late-loading or interactive UI for these two questions.
