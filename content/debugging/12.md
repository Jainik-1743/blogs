> **In one line:** sixteen frontend and React "what would you do?" scenarios, from stale data and flaky tests to **micro-frontends**, **design systems** and **incremental migrations**, each answered as **Diagnose, Fix, Prevent**.

The earlier lessons covered the performance fundamentals ([Lessons 01 to 08](/debugging/lesson-1)). This bank adds the broader scenarios that show up in senior frontend loops: product bugs, architecture and delivery.

## The scenarios

### 1. "After saving a form the list still shows old data."

**Diagnose:** the mutation succeeded but the **client cache was not invalidated**; or a CDN or HTTP cache is serving a stale `GET`; or the component copied server data into local state and never refreshed it.

**Fix:** invalidate or update the relevant query key after the mutation (`queryClient.invalidateQueries`), or update the cache optimistically; for server-rendered pages revalidate the path or tag; use `Cache-Control: no-cache` where freshness matters.

**Prevent:** do not copy server data into state; centralise query keys; add a test "create then see it in the list". ([Frontend Depth, Lesson 03](/frontend-depth/lesson-3))

### 2. "Users lose what they typed when they hit Back or refresh."

**Diagnose:** form state lives only in component memory.

**Fix:** persist drafts (debounced) to `sessionStorage` or the server, restore on mount, warn on unsaved changes (`beforeunload` sparingly), and keep filters and wizard steps **in the URL**. Mind the Back/Forward cache: avoid `unload` handlers that disable it.

**Prevent:** a convention for draft persistence in the form library; test the back-button flow. ([Browser Contract, Lessons 00 and 01](/browser/lesson-1))

### 3. "The app is fine on my laptop but unusable on older Android phones."

**Diagnose:** reproduce with **CPU throttling (4x to 6x)** and a slow network profile; look at **field data** for that device segment. Typical causes: a large bundle (parse and execute cost), heavy hydration, long tasks, big images, too many DOM nodes.

**Fix:** reduce JavaScript (code split, Server Components, lighter libraries), defer non-critical work, virtualise lists, serve responsive images, simplify animations.

**Prevent:** performance budgets on mobile settings in CI, RUM segmented by device class, a test device in the team. ([Lesson 06](/debugging/lesson-6))

### 4. "A real-time dashboard receives 5,000 updates per second and the tab freezes."

**Diagnose:** every message triggers a state update and re-render; the main thread is saturated and memory grows with history.

**Fix:** **batch** incoming messages and flush at most once per frame or every 100 to 250 ms (`requestAnimationFrame` or a timer), keep only the **latest value per key** (not every event), update **only the changed rows** (stable keys, memoised rows, selectors), cap history length, and drop to **sampling or server-side aggregation** for high-frequency series. Consider rendering charts on canvas or a worker.

**Prevent:** backpressure design with the backend (aggregate there), a performance test with a message generator. ([Lesson 07](/debugging/lesson-7))

### 5. "Our React single-page app is not getting indexed, and shares look empty."

**Diagnose:** content is **client-rendered**, so crawlers and link-preview bots see an empty shell; metadata is set only in JavaScript.

**Fix:** render public pages on the **server** (SSR or static generation), set per-page **titles, descriptions, canonical and Open Graph tags** in the server HTML, provide a sitemap, make navigation real links (`<a href>`), keep important content out of lazy client-only fetches.

**Prevent:** check "View source" and a crawler tool in review; Lighthouse SEO checks in CI. ([Frontend Depth, Lesson 02](/frontend-depth/lesson-2))

### 6. "The API token expires while users are working, and they get kicked to the login page."

**Diagnose:** no refresh handling, or several concurrent requests all try to refresh at once (and rotation invalidates one of them).

**Fix:** a single **refresh-and-retry** layer: on `401`, refresh the token **once** (a shared in-flight promise so concurrent requests wait for it), then retry the original requests; if refresh fails, log out cleanly and preserve the user's place. Refresh proactively shortly before expiry.

**Prevent:** a test with expiring tokens and parallel calls; a BFF so the browser never handles tokens. ([Browser Contract, Lessons 02 and 03](/browser/lesson-3))

### 7. "An optimistic update shows success, then the server rejects it."

**Diagnose:** the UI assumed success without handling failure.

**Fix:** keep the previous state, **roll back** on error, show a clear message (and offer retry), and reconcile with the server's response afterwards (`onSettled` refetch). Use idempotency keys so retries are safe.

**Prevent:** test the failure path, not only the happy path. ([Lesson 05](/debugging/lesson-5))

### 8. "Typing in a big form (80 fields) is laggy."

**Diagnose:** each keystroke updates parent state, re-rendering the whole form; validation runs on every field each time.

**Fix:** use a form library with **uncontrolled inputs** (React Hook Form), validate on blur or debounce, split the form into memoised sections, isolate expensive widgets, and use `useDeferredValue` for derived previews.

**Prevent:** profile large forms in review; set a render budget. ([Lesson 08](/debugging/lesson-8))

### 9. "A bug appears only in Safari (or only on iOS)."

**Diagnose:** reproduce on the real browser or an accurate emulator; check the console and network; common causes: a missing API or CSS feature, date parsing differences (`new Date("2026-05-01 10:00")` is not valid everywhere), `100vh` and the dynamic toolbar, input zoom for small font sizes, storage and cookie restrictions (ITP), flexbox/grid gaps in older versions.

**Fix:** use **standards-compliant formats** (ISO 8601), feature detection or polyfills, `dvh` units, 16 px inputs, `@supports` fallbacks.

**Prevent:** a **browser support matrix** (from analytics), cross-browser E2E on critical flows (Playwright runs WebKit), autoprefixer and `browserslist`, linting for unsupported APIs.

### 10. "State is out of sync between two open tabs."

**Diagnose:** each tab holds its own in-memory state.

**Fix:** server state: refetch on focus and use cache invalidation; client state: sync with `BroadcastChannel` or the `storage` event; for auth, broadcast logout. Decide which data truly needs cross-tab consistency.

**Prevent:** treat the server as the source of truth; test with two tabs. ([Browser Contract, Lesson 01](/browser/lesson-1))

### 11. "Our end-to-end tests fail randomly in CI."

**Diagnose:** classify the flakes: **timing** (waiting on fixed sleeps), **shared state or data** between tests, **order dependence**, **network or third-party** dependence, **animation** or viewport differences, **CI resource limits**. Use traces, videos and the failure frequency per test.

**Fix:** web-first assertions and auto-waiting locators instead of sleeps, isolated data per test, mock third parties, disable animations, retry once with trace capture **while** fixing root causes, quarantine truly broken tests with a ticket.

**Prevent:** a flake-rate dashboard, a policy that red CI is a bug, a smaller E2E suite with more lower-level tests. ([Frontend Depth, Lesson 05](/frontend-depth/lesson-5))

### 12. "A third-party script (chat, analytics, ads) breaks the page for some users."

**Diagnose:** console errors from the vendor domain; **ad blockers** or **CSP** blocking it; a long task attributed to that origin; an unhandled error escaping.

**Fix:** load it `async`/late and **fail soft** (the page must work without it), wrap integration code in try/catch, isolate it, consider a self-hosted or lighter alternative, remove it if its cost exceeds its value.

**Prevent:** a third-party inventory with owners, performance and error budgets, SRI where applicable, a CSP report-only monitor. ([Browser Contract, Lesson 07](/browser/lesson-7))

### 13. "Design asks for a micro-frontend architecture so five teams can deploy independently. What do you consider?"

**Think in trade-offs.** Micro-frontends split a UI into independently built and deployed pieces. They fit **large organisations with truly independent domains**; they add cost.

- **Composition:** build-time (npm packages), **runtime** (Module Federation, import maps, web components), or **server-side/edge composition** (fragments), or simply **separate routes/apps** behind one domain (the simplest form).
- **Shared concerns:** design system, auth/session, routing, analytics, error handling, i18n; one shared **contract** for events and navigation.
- **Performance:** duplicate framework copies, waterfalls loading remotes, layout shift; share dependencies deliberately and set budgets.
- **Consistency and UX:** a shared design system and tokens, a11y standards, one navigation shell.
- **Versioning and deploys:** independent releases need **backward-compatible contracts** and a rollback story; integration tests across boundaries.
- **Ownership:** clear domain boundaries (by business capability, not by technical layer).

**My answer:** start with a **modular monolith** (clear boundaries, one deployable) and split only when team coordination, not code size, is the bottleneck; if splitting, prefer **route-level separation** over component-level runtime sharing.

### 14. "We need to roll out a design system across three products. How?"

**Plan:** (1) audit existing UI and decide the scope; (2) define **design tokens** (colour, spacing, typography) as the shared source; (3) build **accessible primitives** first (button, input, dialog) with documentation and examples (Storybook); (4) publish as a **versioned package** with a changelog and codemods for breaking changes; (5) migrate **incrementally** (new screens first, then highest-traffic ones) so products stay shippable; (6) governance: contribution model, ownership, review for accessibility; (7) measure adoption and visual regressions (screenshot tests).

**Pitfalls:** big-bang rewrites, no versioning policy, inaccessible components, and a team that becomes a bottleneck rather than an enabler.

### 15. "Migrate a large JavaScript codebase to TypeScript (or CRA to Next.js) without stopping feature work."

**Approach:** **incremental, strangler-style.** Add the tooling first (`allowJs`, strict off for old code), convert **leaf modules and shared utilities** first, enforce strictness on **new** files (and "ratchet" per directory), add types at **boundaries** (API schemas) for the biggest win, track progress with a metric (percentage typed, `any` count), and keep CI green throughout. For a framework migration, run **both side by side** behind routing (migrate route by route), keep shared components working in both, and have a rollback.

**Avoid:** a long-lived migration branch, rewriting for its own sake, and stopping delivery for months.

### 16. "Accessibility audit found 200 issues. Where do you start?"

**Prioritise by impact and effort:** (1) **blockers** on critical journeys (keyboard traps, unlabeled form controls, missing focus management in modals); (2) **systemic fixes in shared components** (one fix clears many instances); (3) automated, mechanical issues (contrast, alt text); (4) the long tail. Add **lint and axe checks in CI** so the count only goes down, test with keyboard and a screen reader, and include accessibility in the **definition of done**. ([Frontend Depth, Lesson 06](/frontend-depth/lesson-6))

## Interview questions

### Q1. Scenario: a dashboard receives thousands of updates per second and freezes. What do you do?

Batch and throttle updates (flush once per frame or every 100 to 250 ms), keep only the latest value per key, update only changed rows with stable keys and memoised components or selectors, cap history, move heavy work to a worker or the server, and ask the backend to aggregate. Verify with the Performance panel.

### Q2. Scenario: five teams want to deploy their parts of the UI independently. How do you design the frontend?

Weigh the cost first: begin with a modular monolith and route-level separation, and consider runtime micro-frontends (Module Federation, web components) only when team coordination is the bottleneck. Define domain boundaries, a shared design system, shared auth and navigation contracts, dependency sharing with performance budgets, independent versioned deploys with backward-compatible contracts and cross-boundary tests.

### Q3. Scenario: the token expires mid-session and users are logged out. Fix it.

Centralise refresh in the HTTP layer: on 401, perform one shared refresh, queue other requests behind it, retry them with the new token, and only log out if refresh fails, preserving the user's place. Refresh slightly before expiry, and consider a backend-for-frontend so tokens never live in the browser.

### Q4. Scenario: how do you migrate a large JavaScript app to TypeScript while shipping features?

Incrementally: configure `allowJs`, type shared utilities and API boundaries first, require strict types for new files, ratchet directory by directory, track `any` counts, keep CI green and avoid a long-lived branch. Measure progress and treat it as ongoing work alongside features.

### Q5. Scenario: E2E tests are flaky in CI. What is your approach?

Classify failures by cause (timing, shared data, order, third parties, animation, resources), use traces to find root causes, replace sleeps with auto-waiting assertions, isolate data and mock external services, quarantine with a ticket rather than ignoring, and keep E2E small by testing logic at lower levels.

### Q6. Scenario: a design system must serve three products. What is your rollout plan?

Define tokens and accessible primitives first, document them, ship a versioned package with a changelog and codemods, migrate new and high-traffic screens incrementally, add visual regression and accessibility tests, and set governance so the team enables rather than blocks.

## Key takeaways

- Frontend scenarios are about **caches, async ordering, state ownership, device reality, and delivery**, not only React APIs.
- **Incremental migration beats rewrite**; **boundaries and contracts** make micro-frontends and design systems work.
- Always connect an answer to **measurement, a guard and a rollout plan**.
