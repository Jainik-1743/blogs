> **In one line:** sixteen "what would you do?" questions about frontend and React. They go from old data and flaky tests to **micro-frontends**, **design systems** and **step-by-step migrations**. Each is answered as **Diagnose, Fix, Prevent**.

The earlier lessons covered the basics of performance ([Lessons 01 to 08](/debugging/lesson-1)). This lesson adds wider scenarios that come up in senior frontend interviews: product bugs, architecture and delivery.

## The scenarios

### 1. "After saving a form the list still shows old data."

**Diagnose:** the save worked, but the **client cache was not refreshed**. Or a CDN or HTTP cache is giving an old `GET` response. Or the component copied server data into local state and never updated it.

**Fix:** after the save, mark the right query as old (`queryClient.invalidateQueries`), or update the cache straight away (an optimistic update). For server-rendered pages, revalidate the path or tag. Use `Cache-Control: no-cache` where fresh data matters.

**Prevent:** do not copy server data into state. Keep all query keys in one place. Add a test: "create an item, then see it in the list". ([Frontend Depth, Lesson 03](/frontend-depth/lesson-3))

### 2. "Users lose what they typed when they hit Back or refresh."

**Diagnose:** the form state lives only in the component's memory. Memory is cleared when the page reloads.

**Fix:** save drafts to `sessionStorage` or to the server. Wait a short time between saves (debounce). Restore the draft when the component loads. Warn about unsaved changes, but use `beforeunload` only a little. Keep filters and wizard steps **in the URL**. Also think about the Back/Forward cache (a browser feature that keeps whole pages for fast Back). Do not use `unload` handlers, because they turn it off.

**Prevent:** make one rule for saving drafts in your form library. Test the back-button flow. ([Browser Contract, Lessons 00 and 01](/browser/lesson-1))

### 3. "The app is fine on my laptop but unusable on older Android phones."

**Diagnose:** repeat the problem with **CPU throttling (4x to 6x slower)** and a slow network profile. Look at **field data** (real measurements from real users) for that kind of device. Common causes:
- a large bundle (the phone must read and run all that code)
- heavy hydration (the page must be made interactive in the browser)
- long tasks that block the screen
- big images
- too many DOM nodes

**Fix:** send less JavaScript. Split code into parts, use Server Components, and choose lighter libraries. Delay work that is not urgent. Use virtual lists (draw only the visible rows). Serve images in the right size. Make animations simpler.

**Prevent:** set performance budgets for mobile settings in CI. Use RUM (real user monitoring) split by device class. Keep a test device in the team. ([Lesson 06](/debugging/lesson-6))

### 4. "A real-time dashboard receives 5,000 updates per second and the tab freezes."

**Diagnose:** each message causes a state update and a re-render. The main thread (the one thread that runs your page code) is full, and memory grows with the history.

**Fix:**
- **Batch** the messages. Update the screen at most once per frame, or every 100 to 250 ms (use `requestAnimationFrame` or a timer).
- Keep only the **latest value for each key**, not every event.
- Update **only the rows that changed**. Use stable keys, memoised rows (rows that do not redraw if their data is the same) and selectors.
- Limit how much history you keep.
- For very fast data, use **sampling or summing on the server**.
- Think about drawing charts on a canvas or in a worker.

**Prevent:** agree with the backend on how to handle too much data (backpressure), and let the backend sum the data. Write a performance test with a message generator. ([Lesson 07](/debugging/lesson-7))

### 5. "Our React single-page app is not getting indexed, and shares look empty."

**Diagnose:** the content is **drawn in the browser** (client-rendered). Search crawlers and link-preview bots see only an empty shell. The page metadata is set only in JavaScript.

**Fix:** draw public pages on the **server** (SSR or static generation). Put the **title, description, canonical and Open Graph tags** for each page in the server HTML. Add a sitemap. Make navigation real links (`<a href>`). Do not hide important content behind lazy fetches that run only in the browser.

**Prevent:** in review, check "View source" and use a crawler tool. Run Lighthouse SEO checks in CI. ([Frontend Depth, Lesson 02](/frontend-depth/lesson-2))

### 6. "The API token expires while users are working, and they get kicked to the login page."

**Diagnose:** the app has no refresh handling. Or many requests try to refresh the token at once, and token rotation makes one of them fail.

**Fix:** build one **refresh-and-retry** layer. When a request gets `401`, refresh the token **only once**. Use one shared promise (a "work in progress" value), so other requests wait for it. Then retry the original requests. If the refresh fails, log the user out cleanly and remember where they were. Also refresh a little before the token expires.

**Prevent:** write a test with expiring tokens and parallel calls. Use a BFF (backend for frontend, a small server for your UI), so the browser never handles tokens. ([Browser Contract, Lessons 02 and 03](/browser/lesson-3))

### 7. "An optimistic update shows success, then the server rejects it."

**Diagnose:** an optimistic update shows the result before the server answers. Here the UI assumed success and had no plan for failure.

**Fix:** keep the previous state. **Roll back** if there is an error. Show a clear message and offer a retry. After that, match the screen to the server's answer (refetch in `onSettled`). Use idempotency keys (a unique key per action), so a retry is safe.

**Prevent:** test the failure path, not only the happy path. ([Lesson 05](/debugging/lesson-5))

### 8. "Typing in a big form (80 fields) is laggy."

**Diagnose:** each key press updates the parent state, so the whole form re-renders. Validation also runs on every field each time.

**Fix:** use a form library with **uncontrolled inputs** (the browser keeps the value, not React), such as React Hook Form. Validate on blur (when the user leaves the field) or after a short delay. Split the form into memoised sections. Keep expensive widgets apart. Use `useDeferredValue` for previews that come from the typed values.

**Prevent:** profile big forms in review. Set a render budget. ([Lesson 08](/debugging/lesson-8))

### 9. "A bug appears only in Safari (or only on iOS)."

**Diagnose:** repeat the bug in the real browser or in an accurate emulator. Check the console and the network tab. Common causes:
- a missing API or CSS feature
- different date parsing (`new Date("2026-05-01 10:00")` is not valid everywhere)
- `100vh` and the toolbar that changes size
- input zoom when the font size is small
- limits on storage and cookies (ITP)
- flexbox or grid `gap` problems in older versions

**Fix:** use **standard formats** such as ISO 8601. Use feature detection or polyfills (code that adds a missing feature). Use `dvh` units, 16 px inputs and `@supports` fallbacks.

**Prevent:** keep a **browser support matrix** (based on your analytics). Run cross-browser E2E tests on key flows (Playwright can run WebKit). Use autoprefixer and `browserslist`. Add linting for APIs that are not supported.

### 10. "State is out of sync between two open tabs."

**Diagnose:** each tab keeps its own state in memory.

**Fix:** for server state, refetch when the tab gets focus and use cache invalidation. For client state, sync with `BroadcastChannel` or the `storage` event. For login, send a logout message to all tabs. Decide which data really needs to match across tabs.

**Prevent:** treat the server as the source of truth. Test with two tabs. ([Browser Contract, Lesson 01](/browser/lesson-1))

### 11. "Our end-to-end tests fail randomly in CI."

**Diagnose:** a flaky test passes sometimes and fails sometimes. Sort the flakes by cause:
- **timing** (waiting with fixed sleeps)
- **shared state or data** between tests
- **order dependence**
- **network or third-party** services
- **animation** or screen-size differences
- **CI resource limits**

Use traces, videos and how often each test fails.

**Fix:** use web-first assertions and auto-waiting locators instead of sleeps. Give each test its own data. Mock third parties. Turn off animations. Retry once and save a trace **while** you fix the root causes. Move tests that are truly broken to a quarantine, with a ticket.

**Prevent:** show the flake rate on a dashboard. Make a rule that a red CI is a bug. Keep the E2E suite small and add more lower-level tests. ([Frontend Depth, Lesson 05](/frontend-depth/lesson-5))

### 12. "A third-party script (chat, analytics, ads) breaks the page for some users."

**Diagnose:** look for console errors from the vendor domain. Check if an **ad blocker** or a **CSP** (a browser rule about which scripts may load) blocks it. Look for a long task from that origin. Look for an unhandled error that escapes.

**Fix:** load it with `async`, or late. Make it **fail soft**: the page must work without it. Wrap the integration code in try/catch and keep it isolated. Think about a self-hosted or lighter option. Remove it if it costs more than it gives.

**Prevent:** keep a list of third-party scripts with an owner for each. Set performance and error budgets. Use SRI (a hash that checks the file was not changed) where it fits. Run a CSP in report-only mode to watch. ([Browser Contract, Lesson 07](/browser/lesson-7))

### 13. "Design asks for a micro-frontend architecture so five teams can deploy independently. What do you consider?"

**Think about trade-offs.** A micro-frontend splits a UI into parts that are built and deployed on their own. It fits **large organisations with truly independent areas of work**. It also adds cost.

- **Composition (how the parts join):** at build time (npm packages), at **runtime** (Module Federation, import maps, web components), by **server or edge composition** (page fragments), or just **separate routes or apps** under one domain. The last one is the simplest.
- **Shared concerns:** design system, login and session, routing, analytics, error handling, translations. Agree one shared **contract** for events and navigation.
- **Performance:** many copies of the framework, slow chains of loading remote parts, and layout shift. Share dependencies on purpose and set budgets.
- **Consistency and UX:** a shared design system and tokens, accessibility standards, and one navigation shell.
- **Versions and deploys:** independent releases need **contracts that stay backward-compatible** and a rollback plan. Run integration tests across the boundaries.
- **Ownership:** clear boundaries by business area, not by technical layer.

**My answer:** start with a **modular monolith** (clear boundaries, one deployable app). Split only when team coordination, not code size, is the problem. If you split, prefer **separation by route** over sharing components at runtime.

### 14. "We need to roll out a design system across three products. How?"

**Plan:**
1. Review the current UI and decide the scope.
2. Define **design tokens** (named values for colour, spacing and type) as the shared source.
3. Build **accessible basic parts** first (button, input, dialog). Add documentation and examples (Storybook).
4. Publish it as a **versioned package** with a changelog and codemods (scripts that update code for you) for breaking changes.
5. Migrate **step by step**: new screens first, then the busiest ones. Products stay shippable.
6. Set rules (governance): how to contribute, who owns what, and accessibility review.
7. Measure adoption and visual regressions with screenshot tests.

**Pitfalls:** a big-bang rewrite, no versioning policy, parts that are not accessible, and a team that blocks others instead of helping them.

### 15. "Migrate a large JavaScript codebase to TypeScript (or CRA to Next.js) without stopping feature work."

**Approach:** go **step by step, in the strangler style** (replace the old system piece by piece). Set up the tools first (`allowJs`, and strict mode off for old code). Convert **leaf modules and shared utilities** first. Require strict rules for **new** files, and tighten them directory by directory (a "ratchet"). Add types at **boundaries** such as API schemas, because that gives the most value. Track progress with a number, such as the percentage typed or the count of `any`. Keep CI green all the time. For a framework migration, run **both side by side** behind routing and move route by route. Keep shared components working in both. Have a rollback plan.

**Avoid:** a migration branch that lives for a long time, a rewrite for its own sake, and stopping delivery for months.

### 16. "Accessibility audit found 200 issues. Where do you start?"

**Sort by impact and effort:**
1. **Blockers** on important user journeys, such as keyboard traps, form controls with no labels, and missing focus handling in modals.
2. **System-wide fixes in shared components.** One fix clears many problems.
3. Simple, automatic fixes such as contrast and alt text.
4. The long tail of small issues.

Add **lint and axe checks in CI**, so the count only goes down. Test with a keyboard and a screen reader. Make accessibility part of the **definition of done**. ([Frontend Depth, Lesson 06](/frontend-depth/lesson-6))

## Interview questions

### Q1. Scenario: a dashboard receives thousands of updates per second and freezes. What do you do?

I batch and throttle the updates. I update the screen once per frame or every 100 to 250 ms. I keep only the latest value for each key. I update only the rows that changed, with stable keys and memoised components or selectors. I limit the history. I move heavy work to a worker or the server, and I ask the backend to sum the data. I check the result in the Performance panel.

### Q2. Scenario: five teams want to deploy their parts of the UI independently. How do you design the frontend?

I look at the cost first. I would begin with a modular monolith and separation by route. I would use runtime micro-frontends (Module Federation, web components) only when team coordination is the real problem. I would define clear boundaries, a shared design system, and shared contracts for login and navigation. I would share dependencies with performance budgets. Each team gets its own versioned deploys with backward-compatible contracts, and I would test across the boundaries.

### Q3. Scenario: the token expires mid-session and users are logged out. Fix it.

I put the refresh in one place, the HTTP layer. When a request gets 401, I do one shared refresh. Other requests wait behind it and then retry with the new token. I log the user out only if the refresh fails, and I remember where they were. I also refresh a little before expiry. I would think about a backend-for-frontend, so tokens never live in the browser.

### Q4. Scenario: how do you migrate a large JavaScript app to TypeScript while shipping features?

I go step by step. I turn on `allowJs`. I type shared utilities and API boundaries first. I require strict types for new files and tighten directory by directory. I track the `any` count and keep CI green. I avoid a branch that lives for a long time. I measure progress and treat the work as ongoing, next to features.

### Q5. Scenario: E2E tests are flaky in CI. What is your approach?

I sort the failures by cause: timing, shared data, order, third parties, animation and resources. I use traces to find root causes. I replace sleeps with assertions that wait automatically. I give each test its own data and mock outside services. I quarantine broken tests with a ticket instead of ignoring them. I keep the E2E suite small and test logic at lower levels.

### Q6. Scenario: a design system must serve three products. What is your rollout plan?

I define tokens and accessible basic parts first, and I write documentation. I ship a versioned package with a changelog and codemods. I migrate new screens and busy screens step by step. I add visual regression tests and accessibility tests. I set rules for ownership, so the team helps others and does not block them.

## Key takeaways

- Frontend scenarios are about **caches, the order of async work, who owns state, real devices, and delivery**. They are not only about React APIs.
- **Step-by-step migration beats a rewrite.** **Clear boundaries and contracts** make micro-frontends and design systems work.
- Always link your answer to **a measurement, a guard and a rollout plan**.
