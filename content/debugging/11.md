> **In one line:** sixteen server-side "what would you do?" questions, each answered in the same three beats: **Diagnose** (the evidence you gather first), **Fix** (the smallest change that removes the cause) and **Prevent** (the guard that stops it returning).

Use this as a practice set. Cover the answer, say yours aloud, then compare. Where a scenario has a full lesson behind it, the link is in brackets.

## The scenarios

### 1. "An endpoint returns 500, but only for some users."

**Diagnose:** find a failing request by **request ID** in the logs and read the exception and stack. Ask what those users share: a **tenant, a plan, a region, a data shape** (a null where code assumes a value, a very long string, an unusual character, a huge list), or an **old record created before a migration**. Reproduce with that user's data in staging.

**Fix:** handle the missing or odd value, add validation at the boundary, and backfill or repair the bad data.

**Prevent:** a regression test with the offending shape, stricter database constraints (`NOT NULL`, `CHECK`), error tracking grouped by exception so a new type is noticed immediately. ([Backend, Lessons 03 and 04](/backend/lesson-3))

### 2. "A coupon was redeemed twice (or stock went negative) under load."

**Diagnose:** a **check-then-write race**: two requests read "unused", both write. Reproduce by firing parallel requests at the endpoint.

**Fix:** make it one atomic step: `UPDATE coupons SET used_at = now() WHERE id = $1 AND used_at IS NULL` and check the affected row count, or add a **unique constraint** on `(coupon_id, user_id)`, or lock the row (`SELECT … FOR UPDATE`).

**Prevent:** a concurrency test (N parallel calls, assert exactly one wins), constraints as the last line of defence. ([Backend, Lesson 07](/backend/lesson-7))

### 3. "After a traffic increase we get 'timeout acquiring a connection' errors, but the database CPU is low."

**Diagnose:** the **connection pool is exhausted**, not the database. Requests queue waiting for a free connection. Check pool metrics, **long-running transactions** (an API call inside a transaction), slow queries holding connections, and whether `instances × pool size` exceeds the database limit.

**Fix:** shorten transactions (no network calls inside), fix the slow queries, size pools deliberately, add a pooler (PgBouncer, RDS Proxy), add timeouts.

**Prevent:** alert on pool wait time and in-use connections, load tests, and a connection budget in the capacity plan. ([Backend, Lesson 08](/backend/lesson-8))

### 4. "The Node process is killed with an out-of-memory error every few hours."

**Diagnose:** is memory growing (leak) or spiking (a huge response held in memory)? Check the heap trend, take **heap snapshots** a while apart and diff them; look for unbounded caches, listeners added per request, big JSON built in memory, or `readFile` on large files. Check the container memory limit versus Node's heap limit.

**Fix:** bound the cache, stream large payloads, remove per-request listeners, raise the limit only as a stopgap.

**Prevent:** memory and event-loop metrics with alerts, a soak test, code review of module-level collections. ([Lesson 04](/debugging/lesson-4), [Backend, Lesson 10](/backend/lesson-10))

### 5. "A webhook from the payment provider was processed twice, and sometimes events arrive out of order."

**Diagnose:** providers deliver **at least once** and do not guarantee order. Check whether you dedupe by **event ID** and whether handlers assume order ("refund" arriving before "charge").

**Fix:** store processed event IDs under a unique constraint and ignore repeats; make handlers **idempotent**; use the event's timestamp or a **state machine** that rejects illegal transitions; when unsure, **fetch the current state from the provider's API** instead of trusting the payload. Verify the **signature**, respond `2xx` quickly and process asynchronously.

**Prevent:** replay tests with duplicated and shuffled events, a reconciliation job against the provider. ([Practical Design Problems, Lesson 07](/design-problems/lesson-7))

### 6. "The list endpoint gets slower the further users scroll."

**Diagnose:** offset pagination: `OFFSET 100000` reads and discards 100,000 rows. Confirm with `EXPLAIN ANALYZE` and per-page latency.

**Fix:** switch to **keyset (cursor) pagination** with a composite index and a unique tiebreaker; cap `limit` and the maximum offset for old clients.

**Prevent:** test with production-sized data, document the cursor contract. ([Practical Design Problems, Lesson 03](/design-problems/lesson-3))

### 7. "Our scheduled job ran twice, so customers received two emails."

**Diagnose:** two instances (or a restart during the run) each ran the cron, and the job is not idempotent.

**Fix:** use a **distributed lock** or a leader (Redis `SET NX PX`, a database advisory lock, or a managed scheduler that triggers one run), and make the job **idempotent** (a sent-flag or unique `(user, campaign)` row).

**Prevent:** run schedulers outside the web tier, log job start and finish with run IDs, alert on duplicates or missed runs.

### 8. "The monthly report endpoint times out and slows everything else."

**Diagnose:** CPU-heavy or long-running work on the request path blocks workers or the event loop; the gateway timeout fires first. ([Backend, Lesson 10](/backend/lesson-10))

**Fix:** make it **asynchronous**: return `202` with a job ID, process in a worker, store the result (object storage), let the client poll or be notified. Push aggregation into SQL, stream the output, cache identical reports.

**Prevent:** a rule that nothing slower than about a second runs inline, separate worker pools, per-user job limits.

### 9. "A mobile app release broke because we renamed an API field."

**Diagnose:** a **breaking change** shipped without a version, and mobile users cannot all update at once.

**Fix:** restore the old field alongside the new one (**additive change**), then migrate clients gradually; add the `Deprecation`/`Sunset` headers.

**Prevent:** an OpenAPI **breaking-change check in CI**, contract tests, a versioning policy (additive by default, `/v2` for breaking), and usage metrics per client version. ([Backend, Lessons 02 and 11](/backend/lesson-2))

### 10. "After a user updates their profile, the page still shows the old data for a minute."

**Diagnose:** a **cache** serving stale data (CDN, Redis, browser), or a **read replica lagging** behind the primary. Check `Cache-Control`, cache keys and the replica lag metric.

**Fix:** invalidate or update the cache on write, `private`/no-store for personalised data, or **read from the primary for a short window after a write** ("read your own writes").

**Prevent:** a clear invalidation strategy per cache layer, replica-lag monitoring, tests that write then read. ([Lesson 02](/debugging/lesson-2))

### 11. "A database migration locked the table and the site froze."

**Diagnose:** a long `ALTER TABLE` or `CREATE INDEX` took a lock that blocked reads and writes on a large table.

**Fix:** cancel the migration if safe; redo it the **online** way: `CREATE INDEX CONCURRENTLY`, add columns as nullable then backfill in batches, add constraints as `NOT VALID` and validate separately, set a **lock timeout** so migrations fail fast instead of queueing everything behind them.

**Prevent:** rehearse migrations on a production-sized copy, review them for locking, use **expand and contract** so each step is backward compatible. ([Scenario 4 of Lesson 14](/debugging/lesson-14))

### 12. "Some requests return 401 right after a deploy, then work again."

**Diagnose:** mixed instances during a rolling deploy using **different signing keys or secrets**, a **JWKS cache** that has not picked up a rotated key, **clock skew** failing `exp` or `nbf` checks, or session store keys changed.

**Fix:** keep **old and new keys valid during rotation** (publish both in the JWKS), refresh the key set on unknown `kid`, allow small clock skew, make secrets consistent across instances.

**Prevent:** a documented key-rotation procedure, tests that verify tokens signed with the previous key, NTP on all hosts. ([Browser Contract, Lesson 02](/browser/lesson-2))

### 13. "Rate limits do not work: each instance allows the full limit."

**Diagnose:** counters are **in memory per instance**, so with 10 instances users get 10 times the limit.

**Fix:** move counting to a shared store (Redis) with an **atomic** operation (Lua or `INCR` with expiry), or use gateway-level limiting.

**Prevent:** load-test limits against the deployed topology, not one instance. ([Practical Design Problems, Lesson 02](/design-problems/lesson-2))

### 14. "Users in different time zones see different 'today' in reports, and daily totals do not match."

**Diagnose:** mixing **server time, UTC and local time**, or truncating dates in the wrong zone; daylight saving transitions create 23- and 25-hour days.

**Fix:** store timestamps in **UTC** (`timestamptz`), convert at the edge using the user's or the business's zone (`AT TIME ZONE`), define reports by explicit zone and half-open ranges (`>= start AND < end`).

**Prevent:** tests around DST and month boundaries, an ISO 8601 UTC convention in the API, no `toLocaleString` on the server for data. ([Backend, Lesson 02](/backend/lesson-2))

### 15. "A health check fails during deploys and instances are killed in a loop."

**Diagnose:** the **liveness probe** checks something slow or external (the database), so a brief dependency blip restarts healthy instances; or the app needs longer to start than the probe allows (**readiness** not configured).

**Fix:** separate **liveness** ("the process is alive", cheap) from **readiness** ("ready for traffic", checks dependencies), set a sensible start-up grace period, handle `SIGTERM` with a **graceful shutdown**.

**Prevent:** deploy with a canary, test the probes, alert on restart counts. ([Backend, Lesson 04](/backend/lesson-4))

### 16. "We cannot trace a failing request across three services."

**Diagnose:** no shared **correlation ID**; logs are unstructured; each service logs differently.

**Fix:** generate or accept `X-Request-ID`/`traceparent` at the edge, propagate it on every outbound call, include it in every log line (AsyncLocalStorage) and in error responses; adopt OpenTelemetry for traces.

**Prevent:** a shared logging library, a test asserting the header is forwarded, dashboards by trace ID. ([Backend, Lesson 05](/backend/lesson-5))

## Practice drill

Pick five scenarios at random. For each, give a 60-second answer containing: **one piece of evidence you would look at, one root-cause hypothesis, one fix, one guard**. That is the shape interviewers listen for.

## Interview questions

### Q1. Scenario: after a traffic increase you see "timeout acquiring a connection" but the database CPU is low. What is happening?

The connection pool is exhausted, so requests wait in the application for a connection. Causes are long transactions (often an external call inside one), slow queries holding connections, or too many instances for the database's limit. I would inspect pool metrics and `pg_stat_activity`, shorten transactions, fix slow queries, size pools and add a pooler, and alert on pool wait time.

### Q2. Scenario: a webhook is processed twice and events arrive out of order. How do you make the handler robust?

Treat delivery as at-least-once and unordered: verify the signature, store processed event IDs under a unique constraint, make handlers idempotent, use a state machine so illegal transitions are ignored, fetch the authoritative state from the provider when ordering matters, acknowledge fast and process asynchronously.

### Q3. Scenario: a migration locked a hot table. How do you do it safely next time?

Use online techniques: `CREATE INDEX CONCURRENTLY`, add nullable columns and backfill in batches, add constraints as not-validated and validate later, set a lock timeout, run migrations in expand-and-contract steps, and rehearse on production-sized data.

### Q4. Scenario: the job scheduler runs a task twice. What do you change?

Ensure only one instance runs it (a distributed lock, an advisory lock or a managed scheduler) and make the job idempotent so a duplicate run is harmless; log run IDs and alert on duplicates or misses.

### Q5. Scenario: after updating their profile a user still sees old data. Where do you look?

At every cache layer (browser, CDN, Redis) and at replica lag: check cache headers and keys, whether writes invalidate or update the cache, and whether the read hit a lagging replica. Fix with explicit invalidation, no-store for personalised data or reading from the primary briefly after a write.

## Key takeaways

- Most backend scenarios reduce to a few root causes: **races, N+1/indexing, pools and timeouts, retries and idempotency, caching, migrations, key rotation and config drift**.
- Always answer **Diagnose with named evidence, Fix minimally, Prevent with a guard**.
- **Idempotency, constraints, timeouts and observability** appear in nearly every "Prevent" line. Build them in early.
