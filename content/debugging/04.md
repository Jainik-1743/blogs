> **In one line:** a memory leak is memory your app **no longer needs but still references**, so the garbage collector cannot free it. In a single-page app the tab never reloads, so small leaks per navigation pile up until the page crawls or crashes.

On a server a leak shows up as a growing process. In a browser it shows up as a tab that becomes sluggish after an hour of use, a laptop fan that never stops, or "Aw, Snap!" on a phone. SPAs are especially exposed, because **route changes do not reload the page**; anything you forget to clean up lives on.

## How garbage collection decides what to free

JavaScript frees an object when it is **unreachable** from the **roots** (global object, the current call stack, active timers and listeners, DOM). If something reachable still *points to* an object, even one you consider dead, it stays.

```text
roots ─▶ window ─▶ someCache (Map) ─▶ bigObject      ← reachable, so never freed
                └▶ setInterval callback ─▶ closure ─▶ detached <div> tree  ← also kept alive
```

A **leak** is therefore always a **retention path**: some long-lived thing holds a reference to something that should have died. Debugging a leak is finding that path.

## The common sources in SPAs

### 1. Event listeners that are never removed

```tsx
// ❌ A new listener per mount; the old ones (and everything they close over) stay forever
useEffect(() => {
  window.addEventListener("resize", () => setWidth(window.innerWidth));
}, []);

// ✅ Remove it on cleanup, with the same function reference
useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener("resize", onResize);
  return () => window.removeEventListener("resize", onResize);
}, []);
```

The same applies to `document`, `window`, `matchMedia`, `BroadcastChannel`, `MutationObserver`, `ResizeObserver`, `IntersectionObserver` (call `disconnect()`), and any custom event emitter.

### 2. Timers and intervals

```tsx
useEffect(() => {
  const id = setInterval(refreshPrices, 5000);
  return () => clearInterval(id);       // without this, the interval (and its closure) lives on after unmount
}, []);
```

An interval that keeps calling `setState` on an unmounted component also keeps the component and its closures alive.

### 3. Subscriptions and connections

WebSockets, SSE (`EventSource`), RxJS subscriptions, store subscriptions, Firebase/GraphQL subscriptions, `postMessage` listeners. Always return an unsubscribe/close in the effect cleanup.

### 4. Detached DOM nodes

A DOM node removed from the page but still referenced from JavaScript (a variable, a cache, a closure, an array of "rows") keeps the **whole subtree** in memory.

```js
let cachedRow;                       // module-level reference
function remember(el) { cachedRow = el; }
// el is later removed from the document, but cachedRow still points to it → "Detached HTMLDivElement"
```

### 5. Closures capturing large objects

A callback created in a scope that holds a big array or response keeps it alive as long as the callback lives, even if the callback uses only one small field.

```js
function attach(el, bigResponse) {
  const id = bigResponse.id;
  el.addEventListener("click", () => track(bigResponse.id)); // captures the entire bigResponse
}
// Better: capture only what you need
// el.addEventListener("click", () => track(id));
```

### 6. Caches and collections that only grow

```ts
const cache = new Map<string, Data>();       // module-level, never cleared
export async function getUser(id: string) {
  if (!cache.has(id)) cache.set(id, await fetchUser(id));
  return cache.get(id)!;                     // grows with every distinct id for the life of the tab
}
```

Fixes: **bound the cache** (an LRU with a maximum size or TTL), use **`WeakMap`/`WeakRef`** when keys are objects that should be collectable, or use a data-fetching library with built-in garbage collection of unused queries (React Query's `gcTime`).

### 7. Third-party widgets that need explicit teardown

Charts, maps, rich-text editors, video players, virtualisation libraries. If they offer `destroy()`/`dispose()`/`remove()`, call it in the cleanup.

```tsx
useEffect(() => {
  const chart = new Chart(canvasRef.current!, config);
  return () => chart.destroy();               // otherwise each mount leaves a chart (and its listeners) behind
}, []);
```

### 8. In-flight requests and unresolved promises

A long-pending request whose callback references component state keeps that component alive. Abort requests on unmount (`AbortController`), which also fixes stale updates ([Lesson 05](/debugging/lesson-5)).

### 9. Growing app state

Redux/Zustand state that accumulates (an ever-growing log, normalised entities that are never removed), undo history without a cap, and `console.log` of large objects (DevTools keeps references to logged objects while it is open, which can make a leak look worse in development).

### 10. Global variables and accidental globals

Assigning to an undeclared variable, or attaching data to `window`.

### Why effect cleanup matters (and what Strict Mode teaches)

In development, React **Strict Mode** mounts, unmounts and remounts components to confirm that your effect cleanup properly reverses the setup. A missing cleanup is exposed immediately: you will see duplicate listeners, doubled intervals or repeated subscriptions. Treat that as a free leak detector rather than an annoyance.

## How to diagnose a leak in Chrome DevTools

### Step 1: notice the symptom with the Performance monitor

Open **DevTools → More tools → Performance monitor**. Watch **JS heap size**, **DOM nodes** and **JS event listeners** while using the app. Healthy memory looks like a **sawtooth**: it climbs, then drops after garbage collection, returning to a similar baseline. A leak looks like a **staircase or upward trend**: each cycle ends higher than the last, and the node and listener counts keep rising.

### Step 2: compare heap snapshots

The **Memory** tab → *Heap snapshot*:

1. Load the page, **trigger garbage collection** (the trash-can icon), and take **Snapshot 1** (baseline).
2. **Perform the suspicious action several times** (navigate to the route and back 10 times, open and close a modal).
3. Trigger GC again and take **Snapshot 2**.
4. Select Snapshot 2 and choose **"Objects allocated between Snapshot 1 and Snapshot 2"** (or compare). Sort by **Retained Size** or count.
5. Look for objects whose count grows **linearly with the number of repetitions** (10 actions → 10 extra component instances, 10 listeners).
6. Type **"Detached"** in the class filter to find **detached DOM trees**.
7. Select a suspicious object and read the **Retainers** panel at the bottom: it shows the **reference chain** from a GC root to the object. That chain is the leak: for example `window → Map → closure → HTMLDivElement`.

### Step 3: allocation tracking

- **Allocation instrumentation on timeline** records allocations over time and highlights those that survive: good for pinpointing the *function* that creates the leaked objects.
- **Allocation sampling** has low overhead and shows which functions allocate the most memory.

### Step 4: confirm the fix

After the fix, repeat the same action 10 times and check that the snapshot diff no longer grows, and that the sawtooth returns to baseline.

## Scenario: the tab's memory grows by 50 MB on every route change. What next?

1. **Reproduce deliberately:** navigate A → B → A repeatedly while watching the Performance monitor; confirm the staircase.
2. **Narrow it:** does it grow on every route or one specific route? Disable features (a chart, a websocket) to bisect.
3. **Heap snapshot diff** around 5 to 10 navigations; sort by retained size; filter "Detached"; identify the class (a page component, a big array, a canvas).
4. **Read the retainer chain** to see what is holding it: a module-level cache, a listener on `window`, a timer, a store subscription.
5. **Fix** the specific retainer (cleanup, bound the cache, destroy the chart, unsubscribe).
6. **Re-run the same test** and compare snapshots; add a guard (a Playwright test that navigates repeatedly and asserts heap growth stays under a threshold, or monitoring of `performance.memory`/`measureUserAgentSpecificMemory` in field data).

A 50 MB step per route is typically a **large retained structure** (an API response, a decoded image set, a chart's canvas buffers), not tiny listeners. The retainer chain tells you which.

## Memory problems on the server

The same ideas apply in Node: a growing RSS or heap over days usually means unbounded caches, listeners added per request (`MaxListenersExceededWarning`), global arrays/maps, unclosed streams or connections, or closures retaining large request objects. Use heap snapshots (`--inspect`, `node --heapsnapshot-signal`), `process.memoryUsage()` metrics and restarts as a stopgap while you find the retainer ([Backend, Lesson 10](/backend/lesson-10)).

## Prevention habits

- **Every `addEventListener`, `setInterval`, `subscribe` and `new Observer` gets a matching cleanup**, in the same `useEffect`.
- **Bound every cache** (size and/or TTL); prefer libraries that manage cache lifetime.
- Use **`AbortController`** for requests and event-listener removal (`{ signal }` option).
- Prefer **`WeakMap`/`WeakSet`** for metadata keyed by objects.
- **Destroy third-party instances** on unmount.
- Avoid stashing DOM nodes in module-level variables.
- Add a **long-running memory test** to CI for key flows, and track **field memory/crash rates** for heavy apps.

```ts
// A single signal removes many listeners at once
const ctrl = new AbortController();
window.addEventListener("resize", onResize, { signal: ctrl.signal });
window.addEventListener("scroll", onScroll, { signal: ctrl.signal, passive: true });
// cleanup:
ctrl.abort(); // removes both
```

## Common mistakes

1. **Adding listeners in effects with no cleanup.**
2. **Intervals and timeouts never cleared.**
3. **Unbounded module-level caches and arrays.**
4. **Leaving chart/map/editor instances alive after unmount.**
5. **Holding references to removed DOM nodes.**
6. **Diagnosing in a single snapshot** instead of comparing before/after an action.
7. **Mistaking normal GC sawtooth for a leak**, or ignoring a slow staircase.
8. **Forgetting that open DevTools and `console.log` of big objects retain memory.**

## Interview questions

### Q1. Name common sources of memory leaks in React apps.

Event listeners and observers not removed, timers and intervals not cleared, subscriptions (WebSocket, store, RxJS) not unsubscribed, third-party instances (charts, maps) not destroyed, unbounded module-level caches or growing state, closures retaining large objects, detached DOM nodes referenced from JavaScript, and in-flight requests that keep unmounted components alive. Effect cleanup functions are the main defence.

### Q2. How do you use heap snapshots to confirm a leak?

Force GC and take a baseline snapshot, repeat the suspected action many times, force GC and take a second snapshot, then compare or filter "objects allocated between snapshots". Objects whose count grows with the number of repetitions, or "Detached" DOM nodes, are suspects; the Retainers panel shows the reference chain from a GC root that keeps them alive, which is the thing to fix.

### Q3. Scenario: the tab's memory grows by 50 MB on every route change. What next?

Reproduce with repeated navigation while watching the Performance monitor, bisect which route or feature is responsible, diff heap snapshots, sort by retained size and inspect the retainer chain to find what holds the large structure (a cache, listener, timer or subscription). Fix that reference, repeat the test to confirm no growth, and add a regression check.

### Q4. Why does effect cleanup matter?

Effects set up external resources (listeners, timers, subscriptions) that React does not manage. Without cleanup they persist after unmount or re-run, duplicating work and retaining the component and its closures. Strict Mode's double mount in development deliberately exposes missing cleanups.

### Q5. How does a closure cause a leak?

A function keeps its entire enclosing scope reachable. If a long-lived function (an event handler, a timer callback, a cached promise) closes over a large object, that object cannot be freed even if the function only uses a small part of it. Capture only the values you need, and release long-lived callbacks when done.

### Q6. What is a detached DOM node?

An element removed from the document that is still referenced from JavaScript, so it and its subtree remain in memory. Heap snapshots list them under "Detached" classes. Find the retainer (a variable, cache, closure or array) and drop the reference.

### Q7. How do you tell a leak from normal garbage-collection behaviour?

Normal memory forms a sawtooth: it grows then drops back to a stable baseline after GC. A leak shows a rising baseline (staircase) over repeated actions, with DOM node or listener counts that keep increasing. Forcing GC and comparing snapshots after repeating an action confirms it.

### Q8. When would you use WeakMap or WeakRef?

When you need to associate metadata with objects without preventing their collection, such as caching computed data per DOM node or per object. Entries disappear automatically when the key object is no longer referenced elsewhere. Use sparingly: behaviour depends on GC timing, so it is not a place for logic that must be deterministic.

## Key takeaways

- A leak is a **retention path** from a long-lived root to something that should be dead.
- SPAs leak through **listeners, timers, subscriptions, caches, detached DOM, closures and un-destroyed widgets**.
- Spot it with the **Performance monitor** (staircase heap, rising listeners/nodes); confirm with **snapshot diffs** and read the **Retainers**.
- Always write **cleanup**; bound caches; use **AbortController**; destroy third-party instances.
- Add a **repeat-navigation memory test** so leaks do not return.
