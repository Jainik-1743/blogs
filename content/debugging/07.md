> **In one line:** the browser is slow at **having** 10,000 rows of DOM, not at **sorting** 10,000 rows of data. The fix is to render only what the user can see (**virtualization**), fetch only what they need (**server-side pagination and filtering**), and keep heavy computation off the main thread.

"Our table freezes with large data" is a classic. A strong answer starts by saying where the time *really* goes, then offers options with trade-offs.

## Where the time goes

Take a table with 10,000 rows × 8 columns:

- That is ~80,000 cells plus wrappers: **hundreds of thousands of DOM nodes**.
- **React** must create and diff 10,000 row components on mount and again on every update that re-renders them.
- The browser must run **style, layout and paint** across all of those nodes.
- **Memory** grows with the node count.

Sorting 10,000 items in JavaScript takes only a few milliseconds. What freezes the page after you click a sort header is **re-rendering 10,000 rows** and the layout work that follows, which can take seconds on a mid-range phone.

> [!note] Confirm in the Performance panel before choosing a fix: if Scripting for the *sort* is small but Rendering/Layout/Paint after it is huge, the problem is DOM size. If the sort or filter comparator itself is slow, optimise that ([below](#heavy-computation-off-the-main-thread)).

## The options

| Option | Idea | Pros | Cons |
|---|---|---|---|
| **Server-side pagination** | Fetch and render one page (say 50 rows) at a time | Smallest payload and DOM; works with any size of dataset; simple | Page controls instead of continuous scrolling; extra requests |
| **Infinite scroll** (load more) | Append the next page as the user nears the end | Natural feeling | The DOM **keeps growing** (still slows down eventually); hard to reach the footer; losing position on back navigation |
| **Virtualization / windowing** | Render only the visible rows (plus a small overscan); recycle them as the user scrolls | Smooth scrolling over very large lists; constant DOM size | Complexity; accessibility and find-in-page trade-offs; dynamic heights are harder |
| **`content-visibility: auto`** | CSS tells the browser to skip layout and paint for off-screen sections | One line of CSS; DOM stays | Nodes still exist (memory, React work); needs size hints |
| **Chunked rendering** | Render the list in batches over time (`requestIdleCallback`, `startTransition`) | Keeps the page responsive while content appears | Content appears progressively; total work unchanged |
| **Server-side sort and filter** | Let the database sort and filter; send only results | Scales to millions of rows | Network round trips; needs indexes ([Backend, Lesson 07](/backend/lesson-7)) |
| **Web Worker** | Move heavy sorting, filtering or parsing off the main thread | Main thread stays free | Data must be transferred or shared; some complexity |

**Rule of thumb:** up to a few hundred rows, render them all. Thousands: virtualise or paginate. Tens of thousands and beyond (or data that is expensive to ship): do it **on the server**, with pagination, filters and sorting, and virtualise the page of results if needed.

## How virtualization works

A virtualised list has a scrollable container with a **fixed total height** (so the scrollbar looks right), and renders only the items whose positions fall in the visible window:

```text
total height = itemCount × rowHeight           (a "spacer" gives the scrollbar its size)
first visible index = floor(scrollTop / rowHeight)
last visible index  = first + ceil(viewportHeight / rowHeight)
render items [first - overscan … last + overscan], each positioned absolutely at index × rowHeight
```

On scroll, indexes change; React re-renders a small fixed number of rows (30 or so), reusing the DOM nodes. The DOM size stays constant whether there are 1,000 or 1,000,000 items.

Use a library rather than writing it yourself: **TanStack Virtual**, **react-window**, **react-virtuoso** (handles variable heights and sticky headers).

```tsx
import { useVirtualizer } from "@tanstack/react-virtual";

function VirtualList({ rows }: { rows: Row[] }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const virtualizer = useVirtualizer({
    count: rows.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 44,         // estimated row height in px
    overscan: 8,                    // extra rows rendered above/below for smooth scrolling
  });

  return (
    <div ref={parentRef} style={{ height: 600, overflow: "auto" }}>
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map((v) => (
          <div
            key={rows[v.index].id}
            style={{ position: "absolute", top: 0, left: 0, width: "100%", height: v.size, transform: `translateY(${v.start}px)` }}
          >
            <RowView row={rows[v.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
```

Things to get right:

- **Stable keys** (`row.id`), not indexes.
- **`memo` the row component** with stable props, since rows re-render as you scroll ([Lesson 03](/debugging/lesson-3)).
- **Fixed heights** are simplest and fastest; dynamic heights require measurement (`measureElement`) and cost more.
- **Avoid layout reads per row** in render.
- **Positioning with `transform`** keeps scrolling off the layout path.

### The accessibility cost of virtualization

Virtualization changes what exists in the DOM, which has consequences you should name in an interview:

- **Screen readers** only see the rendered rows. Provide **`aria-rowcount`** (total) and **`aria-rowindex`** on each row, use proper `role="grid"`/`role="table"` semantics, and make sure focus and keyboard navigation can move beyond the rendered window (arrow keys, Page Down, Home/End).
- **Browser find-in-page (Ctrl+F)** will not find off-screen rows. Offer an in-app search.
- **Focus management:** if the focused row scrolls out of the window and unmounts, focus is lost. Keep the focused row rendered or restore focus.
- **Printing and "select all"** only affect rendered rows.
- **Anchor links and scroll restoration** need explicit support.

For read-only reports where everything must be searchable and printable, **pagination** may be the more accessible choice; combine it with virtualisation only if a single page is still large.

## `content-visibility` for long pages

```css
.section {
  content-visibility: auto;                 /* skip rendering work while off-screen */
  contain-intrinsic-size: auto 600px;       /* reserve estimated space so the scrollbar doesn't jump */
}
```

Good for long articles, feeds and card lists. It reduces layout and paint cost but the nodes still exist (React still renders them), so it is not a substitute for virtualising very large lists.

## Chunked rendering

When you must produce a large list quickly but cannot virtualise (a print view, an export preview), render in slices so the page stays responsive:

```tsx
function ChunkedList({ items }: { items: Item[] }) {
  const [count, setCount] = useState(100);

  useEffect(() => {
    if (count >= items.length) return;
    const id = requestIdleCallback(() => setCount((c) => Math.min(c + 200, items.length)), { timeout: 200 });
    return () => cancelIdleCallback(id);
  }, [count, items.length]);

  return <>{items.slice(0, count).map((it) => <ItemRow key={it.id} item={it} />)}</>;
}
```

The first paint is fast; the rest appears over the next frames. Total work is unchanged, but input stays responsive. Wrapping updates in `startTransition` achieves a similar priority effect.

## Heavy computation off the main thread

If the **sort/filter itself** is slow (tens of thousands of rows with expensive comparators), then:

1. **Make it cheaper first.**
   - Precompute sort keys once (a lowercase name, a timestamp number) instead of recomputing in the comparator.
   - Use `Intl.Collator` for locale-aware string sorting instead of `localeCompare` in a hot loop.
   - Build a `Map` or index for lookups instead of `find()` inside loops.
   - **Debounce** filtering as the user types.
2. **Move it to a Web Worker** so the main thread keeps rendering:

```ts
// table.worker.ts
const collator = new Intl.Collator("en");
let rows: Row[] = [];

self.onmessage = (e: MessageEvent<{ type: "load"; rows: Row[] } | { type: "query"; sort?: string; filter?: string; offset: number; limit: number }>) => {
  if (e.data.type === "load") { rows = e.data.rows; return; }
  const { sort, filter, offset, limit } = e.data;
  let out = filter ? rows.filter((r) => r.searchText.includes(filter)) : rows;
  if (sort) out = [...out].sort((a, b) => collator.compare(String(a[sort as keyof Row]), String(b[sort as keyof Row])));
  (self as unknown as Worker).postMessage({ total: out.length, page: out.slice(offset, offset + limit) });
};
```

   The main thread sends the query and receives only the **visible page**, never the 50,000-row result. (Libraries like **Comlink** make worker calls feel like async functions.) Transferring large data to a worker has a cost too; load it once and send small queries.
3. **Move it to the server** when the dataset is large or shared: let PostgreSQL sort and filter with indexes, return a page, and use **cursor pagination** ([Practical Design Problems, Lesson 03](/design-problems/lesson-3)).

## Scenario: a dashboard with 50k rows freezes when sorted. Fix it.

1. **Measure:** Performance panel after clicking the header: is the cost in the sort (Scripting) or in rendering/layout? Usually rendering 50,000 rows.
2. **Reduce the DOM:** virtualise the table (or paginate) so only ~40 rows render.
3. **Make the update cheap:** memoise row components with stable props and keys, so a sort reuses nodes instead of rebuilding.
4. **Optimise the sort:** precomputed keys, `Intl.Collator`, avoid sorting on every render (`useMemo` on `[rows, sortKey]`).
5. **Offload if still slow:** run sort/filter in a Web Worker, or on the server for large datasets.
6. **Keep input responsive:** `useDeferredValue`/`startTransition` for filter inputs; debounce.
7. **Re-measure:** interaction latency (INP), memory and DOM node count; add a test with realistic data volume.

## Pagination vs infinite scroll vs virtualization: choosing

| Need | Choose |
|---|---|
| Huge dataset, searchable, shareable pages, accessibility is critical | **Server-side pagination** (with filters/sorting on the server) |
| A feed users skim (social, notifications) | **Infinite scroll** with a cap, or windowing for long sessions |
| A large table or log viewer where users scroll continuously | **Virtualization** (often over server-paginated chunks) |
| A long, mostly static page | **`content-visibility`** |

## Common mistakes

1. **Blaming the sort** when the cost is rendering the rows.
2. **Infinite scroll without windowing**, so the DOM grows without limit.
3. **Virtualising but re-rendering every row on each scroll** (no `memo`, unstable keys).
4. **Ignoring accessibility** (no `aria-rowcount`, broken keyboard navigation) and find-in-page.
5. **Loading all rows to the client** to sort them there when the database could.
6. **Variable row heights without measurement**, causing jumpy scrollbars.
7. **Optimising on a developer laptop** with 5,000 rows instead of production volume on a mid-range device.

## Interview questions

### Q1. How does list virtualization work?

It keeps a scroll container with a spacer sized to the full list height and renders only the rows currently in (or near) the viewport, computed from the scroll offset and row height, positioning them absolutely. As the user scrolls, it updates which indexes are rendered, reusing a fixed small number of DOM nodes. DOM size and render cost stay constant regardless of list length.

### Q2. Scenario: a dashboard with 50k rows freezes when sorted. Fix it.

Profile to confirm the cost is rendering rows. Virtualise or paginate so few rows render, memoise rows with stable keys, optimise or precompute the sort, offload to a Web Worker or the server if the computation is heavy, and use deferred values for typing. Re-measure INP, DOM size and memory.

### Q3. Pagination vs infinite scroll vs virtualization?

Pagination gives bounded DOM, shareable URLs and good accessibility, and pairs with server-side filtering. Infinite scroll feels continuous but the DOM grows unless windowed. Virtualization keeps a constant DOM for continuous scrolling of very large lists but needs care for accessibility and find-in-page. For large searchable data I favour server-side pagination, adding virtualisation for long single pages.

### Q4. What does virtualization cost in accessibility?

Screen readers and find-in-page only see rendered rows, so you must supply total counts and positions with `aria-rowcount`/`aria-rowindex`, ensure keyboard navigation and focus survive rows unmounting, provide in-app search, and consider that printing and select-all only affect rendered rows. In some cases pagination is the more accessible choice.

### Q5. Why is the DOM size the real problem, not the data size?

Each row creates many nodes that the browser must style, lay out, paint and keep in memory, and React must reconcile them. Sorting or filtering an array of 50,000 objects is cheap by comparison; re-rendering 50,000 rows is not. Reducing the number of nodes gives the largest gain.

### Q6. When would you use a Web Worker for table data?

When sorting, filtering, parsing or aggregating large data is itself CPU-heavy, so doing it on the main thread would block input and rendering. The worker holds the dataset, answers queries and returns only the visible page. For very large or shared data the server is usually better.

### Q7. What does `content-visibility: auto` do and when is it enough?

It lets the browser skip layout and paint of off-screen subtrees until they approach the viewport (with `contain-intrinsic-size` to reserve space). It is a cheap win for long pages and card lists, but nodes and React rendering still exist, so for very large lists virtualisation is still needed.

## Key takeaways

- Rendering **DOM nodes** is the bottleneck, not sorting data. Confirm with the Performance panel.
- **Reduce rows first** (server-side pagination and filters), then **virtualise**, then **memoise rows** with stable keys.
- Make computation cheaper (**precomputed keys, `Intl.Collator`, indexes**) before moving it to a **Web Worker** or the **server**.
- Virtualisation has **accessibility and find-in-page costs**: add ARIA row semantics and keyboard support, or prefer pagination.
- Use `useDeferredValue`/debounce so typing stays responsive; test with production-sized data on throttled hardware.
