> **In one line:** when you fire async work from user events and effects, **order is not guaranteed** and **repeats are easy**. The fixes are layered: cancel what is outdated on the client, ignore stale results, disable repeat actions in the UI, and make the server safe against duplicates with idempotency.

These bugs are subtle because each piece looks correct on its own. They show up as flickering results, double charges, duplicate rows and "429 Too Many Requests" from your own app.

## Problem 1: the effect fetches twice in development

```tsx
useEffect(() => {
  fetch(`/api/items/${id}`).then(r => r.json()).then(setItem);
}, [id]);
// In dev, the Network tab shows two requests for the same URL
```

**Why:** React **Strict Mode** (on by default in the Next.js dev server and in many templates) mounts, unmounts and remounts each component once in development, to check that effects clean up correctly. This **does not happen in production builds**.

What to do:

- **Do not "fix" it by removing Strict Mode.** It is revealing a real property: your effect is not idempotent or has no cleanup.
- Make the effect **safe to run twice**: abort or ignore the first run's result (below).
- Better, **stop fetching in effects** for ordinary data. Use a data-fetching library (React Query, SWR, RTK Query) that **deduplicates** requests with the same key and caches results, or fetch on the server (Server Components, loaders). The React docs recommend this over hand-written effect fetching.

## Problem 2: out-of-order responses (a race condition)

**Scenario:** the user types "r", "re", "rea", "reac", "react". Five requests fly. Request 3 is slow and arrives **last**, so the screen shows results for "rea" while the box says "react".

```text
type "re"    ──▶ req A (slow, 900 ms)  ─────────────────────────▶ arrives last → overwrites!
type "rea"   ──▶ req B (200 ms)      ──▶ arrives
type "react" ──▶ req C (150 ms)     ─▶ arrives first (correct), then A overwrites it with stale data
```

The network does not preserve request order. You must make the **latest request win**.

### Fix A: cancel the previous request with `AbortController`

```tsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setResults)
    .catch((err) => {
      if (err.name !== "AbortError") setError(err);   // aborting is expected, not an error
    });

  return () => controller.abort();                    // runs before the next effect, and on unmount
}, [query]);
```

Abort **cancels the in-flight request** (saving bandwidth and server work; the server may still process it, so it is not a guarantee of non-execution) and guarantees the stale response never resolves into your state.

### Fix B: the "ignore" flag (when you cannot abort)

```tsx
useEffect(() => {
  let ignore = false;
  fetchResults(query).then((data) => {
    if (!ignore) setResults(data);        // only the latest effect run may update state
  });
  return () => { ignore = true; };
}, [query]);
```

This is the pattern from the React docs. It doesn't cancel the network call but prevents the stale result from being used.

### Fix C: let a library own it

React Query or SWR keys results by query (`["search", query]`): a different key is a different cache entry, so an old response can never overwrite the current one, and they abort, dedupe and retry for you.

```tsx
const { data, isFetching } = useQuery({
  queryKey: ["search", query],
  queryFn: ({ signal }) => fetch(`/api/search?q=${query}`, { signal }).then((r) => r.json()),
  enabled: query.length > 1,
  placeholderData: keepPreviousData,       // show the last results while the new ones load
});
```

### Debounce vs abort: they solve different problems

| | Debounce | Abort / ignore stale |
|---|---|---|
| **Reduces** | The **number** of requests (wait until the user pauses) | Wrong results from **overlapping** requests |
| **Does not stop** | A slow earlier request overwriting a later one | Sending many requests while typing |
| **Typical use** | Search-as-you-type input | Every fetch that can be superseded |

Use **both** for typeahead: debounce (200 to 300 ms) to cut traffic, and abort/ignore so stale responses never win ([Practical Design Problems, Lesson 06](/design-problems/lesson-6)).

## Problem 3: double-click and double-submit

A user clicks "Pay" twice (or the network is slow, so they click again). Two requests, two orders, two charges.

Defence in depth: **client and server both**.

### Client: prevent repeats

```tsx
function PayButton({ onPay }: { onPay: () => Promise<void> }) {
  const [pending, setPending] = useState(false);

  async function handleClick() {
    if (pending) return;               // guard against rapid double events (state may not update before a 2nd click)
    setPending(true);
    try { await onPay(); } finally { setPending(false); }
  }
  return <button disabled={pending} onClick={handleClick}>{pending ? "Processing…" : "Pay"}</button>;
}
```

- **Disable the button** and show progress while pending. For forms, use the form's pending state (`useFormStatus`, `useActionState`, or your form library's `isSubmitting`).
- Use a **ref guard** (`useRef`) if two clicks can occur before React re-renders.
- **Navigate away or lock the UI** after success so the action cannot be repeated.

### Server: make duplicates harmless with idempotency

The client cannot be trusted (retries, flaky networks, two tabs, API clients). Generate an **idempotency key** when the form is created (not on every click), send it with the request, and let the server enforce "at most once" ([Backend, Lesson 02](/backend/lesson-2)):

```tsx
// Generated once per form instance/attempt, reused on retries of the SAME submission
const idempotencyKey = useRef(crypto.randomUUID());

await fetch("/api/orders", {
  method: "POST",
  headers: { "Idempotency-Key": idempotencyKey.current, "Content-Type": "application/json" },
  body: JSON.stringify(order),
});
```

Server side, store the key with the result under a **unique constraint** and return the stored response for repeats. As a final guard, use a **natural unique constraint** where one exists (`UNIQUE (user_id, cart_id)` for "one order per cart"). A button disabled in the UI is a convenience; the database constraint is the guarantee.

## Problem 4: your own frontend triggers rate limits (429)

Duplicate requests also cause **429 Too Many Requests**:

- Effects without correct dependencies firing on every render.
- Multiple components each fetching the same resource (no dedupe).
- Polling that is too frequent, or polling in **every open tab**.
- Retry loops without exponential backoff and jitter.
- StrictMode doubling in development.
- Several users behind one corporate IP and a per-IP limit.

Fixes: dedupe through a shared cache, increase poll intervals or use SSE/WebSockets, pause polling when the tab is hidden (`document.visibilityState`), back off on `429` using `Retry-After`, and coordinate tabs with `BroadcastChannel` or a leader election if needed ([Lesson 09](/debugging/lesson-9)).

## Problem 5: stale closures and stale state in handlers

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);   // ❌ closes over count = 0 forever
    return () => clearInterval(id);
  }, []);
  // ✅ setCount((c) => c + 1)  — the functional update does not depend on a captured value
}
```

Async callbacks capture the values of the render in which they were created. Use functional updates, refs for "latest value" access, or correct effect dependencies ([Frontend Depth, Lesson 01](/frontend-depth/lesson-1)).

## Problem 6: request deduplication and caching

When many components ask for the same thing:

- **React Query / SWR:** identical keys share one in-flight request and one cache entry.
- **Next.js (App Router):** identical `fetch` calls (same URL and options) within a single server render pass are **memoised/deduplicated**, so several Server Components can call `getUser()` without issuing several network requests. (Caching beyond a render depends on your `fetch` cache settings and framework version; check the docs for your version.)
- **Your own tiny dedupe:** store the in-flight promise by key.

```ts
const inflight = new Map<string, Promise<unknown>>();
export function dedupe<T>(key: string, fn: () => Promise<T>): Promise<T> {
  if (!inflight.has(key)) inflight.set(key, fn().finally(() => inflight.delete(key)));
  return inflight.get(key) as Promise<T>;
}
```

## Scenario walkthroughs

### "Fast typing shows results for an older query"

1. **Diagnose:** Network tab shows overlapping requests; a slow earlier one resolves last and overwrites state.
2. **Fix:** abort the previous request (or ignore stale results) on every change; key results by query.
3. **Improve:** debounce input; keep previous results visible while loading.
4. **Prevent:** use React Query/SWR; add a test with a mocked slow response for the first call.

### "How do you prevent a duplicate order submission, from the button to the database?"

1. **UI:** disable the button, show pending state, guard with a ref.
2. **Request:** send a stable `Idempotency-Key` created per checkout attempt.
3. **Server:** unique-constrained idempotency record; return the stored response for repeats; reject the same key with a different body.
4. **Database:** a natural uniqueness constraint (one order per cart).
5. **Payments:** pass the key through to the payment provider as well, so it dedupes charges.
6. **Observe:** log the key and count duplicate hits.

## Common mistakes

1. **Removing Strict Mode** to hide double effects.
2. **No abort/ignore logic**, so stale responses overwrite fresh data.
3. **Debouncing only**, believing it solves races.
4. **Relying only on a disabled button** for duplicate prevention.
5. **Generating a new idempotency key on each retry** (defeating the purpose).
6. **Polling in every tab** and never pausing when hidden.
7. **Using `fetch` in effects for everything**, instead of a deduping data layer or the server.
8. **Treating `AbortError` as a failure** and showing an error UI.

## Interview questions

### Q1. Why does my effect fetch twice in development?

React Strict Mode intentionally mounts, unmounts and remounts components in development to surface effects that are not clean or idempotent. It does not occur in production. The right response is to make the effect safe (abort or ignore stale results) or move fetching to a library or server that dedupes, not to disable Strict Mode.

### Q2. Scenario: fast typing shows results for an older query. Fix it.

Responses can arrive out of order, so an older slow response overwrites a newer one. Abort the previous request with `AbortController` (or use an ignore flag) in the effect cleanup, key results by the query (React Query/SWR), debounce to cut traffic, and show previous results while loading. Add a test with a delayed first response.

### Q3. How do you prevent a duplicate order submission, from the button to the database?

Disable the button and show pending state (with a ref guard), send an idempotency key generated once per attempt, have the server store the key with the response under a unique constraint and replay it for repeats, back it with a natural unique constraint in the database, and pass the key to the payment provider. The database and server layers are the real guarantee.

### Q4. Debounce vs abort?

Debounce reduces how many requests are made by waiting for a pause in input, but does not prevent an older response from arriving after a newer one. Abort (or ignoring stale results) ensures only the latest request's result is used and cancels wasted work. Use both for search-as-you-type.

### Q5. How can your own frontend cause 429 errors?

Effects that fire too often, multiple components fetching the same data without deduplication, aggressive polling (especially across many tabs), retry loops without backoff, Strict Mode doubling in dev, and many users sharing one IP. Fix with dedupe, longer intervals or push channels, backoff with `Retry-After`, and pausing polling when hidden.

### Q6. Does AbortController stop the server from doing the work?

Not necessarily. It cancels the client's wait and closes the connection; the server may already have processed (or continue processing) the request unless it detects the closed connection. So it prevents stale state and saves some resources, but is not a guarantee that a side effect did not happen; use idempotency for writes.

### Q7. Why is a disabled button not enough to prevent duplicates?

State updates are asynchronous, so two quick clicks can both fire before the button disables; users can also double-submit via Enter, multiple tabs, retries or direct API calls. Duplicate protection must be enforced on the server with idempotency keys and database constraints.

### Q8. How does Next.js reduce duplicate server-side fetches?

Within one server render pass, identical `fetch` calls (same URL and options) are deduplicated automatically, so multiple Server Components can request the same data without multiple network calls. For caching across requests you configure fetch caching or use your own cache layer, depending on the framework version.

## Key takeaways

- **Responses are not ordered.** Make the latest request win: abort previous requests, ignore stale results, key data by query.
- **Strict Mode's double effect is a feature**: write idempotent, cleaned-up effects, or use a dedupe-capable data layer or server fetching.
- **Debounce reduces traffic; abort prevents stale overwrites.** Use both.
- Prevent duplicate submissions at every layer: **UI pending state → idempotency key → server dedupe → database constraint.**
- Dedupe shared requests, back off on 429, and pause background polling.
