> **In one line:** when you start async work (work that finishes later) from user events and effects, **the order of results is not guaranteed** and **repeats are easy**. The fixes come in layers. On the client, cancel what is outdated and ignore stale results. In the UI, disable repeat actions. On the server, make duplicates safe with idempotency (doing the same request twice has the same result as doing it once).

These bugs are hard to spot, because each piece of code looks correct on its own. They show up as flickering results, double charges, duplicate rows, and "429 Too Many Requests" errors from your own app.

## Problem 1: the effect fetches twice in development

```tsx
useEffect(() => {
  fetch(`/api/items/${id}`).then(r => r.json()).then(setItem);
}, [id]);
// In dev, the Network tab shows two requests for the same URL
```

**Why:** React **Strict Mode** is on by default in the Next.js dev server and in many templates. It mounts each component, unmounts it, and mounts it again, once, in development. This checks that your effects clean up correctly. This **does not happen in production builds**.

What to do:

- **Do not "fix" it by removing Strict Mode.** It shows you a real problem: your effect is not idempotent, or it has no cleanup.
- Make the effect **safe to run twice**. Abort the first run, or ignore its result (see below).
- Even better, **stop fetching in effects** for ordinary data. Use a data-fetching library (React Query, SWR, RTK Query). These libraries **deduplicate** requests with the same key (they send only one) and cache the results. Or fetch on the server (Server Components, loaders). The React docs recommend this instead of fetching by hand in effects.

## Problem 2: out-of-order responses (a race condition)

A race condition is a bug where the result depends on which of two things finishes first.

**Scenario:** the user types "r", "re", "rea", "reac", "react". Five requests fly. Request 3 is slow and arrives **last**. So the screen shows results for "rea" while the box says "react".

```text
type "re"    ──▶ req A (slow, 900 ms)  ─────────────────────────▶ arrives last → overwrites!
type "rea"   ──▶ req B (200 ms)      ──▶ arrives
type "react" ──▶ req C (150 ms)     ─▶ arrives first (correct), then A overwrites it with stale data
```

The network does not keep requests in order. You must make sure the **latest request wins**.

### Fix A: cancel the previous request with `AbortController`

`AbortController` lets you cancel a request that is still running.

```tsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setResults)
    .catch((err) => {
      if (err.name !== "AbortError") setError(err);   // aborting is expected, not an error
    });

  return () => controller.abort();                    // runs before the next effect, and on unmount
}, [query]);
```

Abort **cancels the request that is in flight**. This saves bandwidth and server work. The server may still process the request, so abort does not guarantee that the work did not run. Abort also makes sure that the stale response never reaches your state.

### Fix B: the "ignore" flag (when you cannot abort)

```tsx
useEffect(() => {
  let ignore = false;
  fetchResults(query).then((data) => {
    if (!ignore) setResults(data);        // only the latest effect run may update state
  });
  return () => { ignore = true; };
}, [query]);
```

This is the pattern from the React docs. It does not cancel the network call. It only stops the stale result from being used.

### Fix C: let a library own it

React Query and SWR store results by query key (`["search", query]`). A different key is a different cache entry. So an old response can never overwrite the current one. They also abort, dedupe and retry for you.

```tsx
const { data, isFetching } = useQuery({
  queryKey: ["search", query],
  queryFn: ({ signal }) => fetch(`/api/search?q=${query}`, { signal }).then((r) => r.json()),
  enabled: query.length > 1,
  placeholderData: keepPreviousData,       // show the last results while the new ones load
});
```

### Debounce vs abort: they solve different problems

| | Debounce | Abort / ignore stale |
|---|---|---|
| **Reduces** | The **number** of requests (it waits until the user pauses) | Wrong results from **overlapping** requests |
| **Does not stop** | A slow earlier request overwriting a later one | Sending many requests while typing |
| **Typical use** | Search-as-you-type input | Every fetch that a newer one can replace |

For typeahead (suggestions while you type), use **both**. Debounce (200 to 300 ms) to cut traffic. Abort or ignore so that stale responses never win. See [Practical Design Problems, Lesson 06](/design-problems/lesson-6).

## Problem 3: double-click and double-submit

A user clicks "Pay" twice. Or the network is slow, so they click again. This gives two requests, two orders and two charges.

The defence has layers: use **both the client and the server**.

### Client: prevent repeats

```tsx
function PayButton({ onPay }: { onPay: () => Promise<void> }) {
  const [pending, setPending] = useState(false);

  async function handleClick() {
    if (pending) return;               // guard against rapid double events (state may not update before a 2nd click)
    setPending(true);
    try { await onPay(); } finally { setPending(false); }
  }
  return <button disabled={pending} onClick={handleClick}>{pending ? "Processing…" : "Pay"}</button>;
}
```

- **Disable the button** and show progress while the request is pending. For forms, use the form's pending state (`useFormStatus`, `useActionState`, or `isSubmitting` from your form library).
- Use a **ref guard** (`useRef`) if two clicks can happen before React re-renders.
- **Navigate away or lock the UI** after success, so the action cannot be repeated.

### Server: make duplicates harmless with idempotency

You cannot trust the client. There are retries, bad networks, two tabs and API clients. So make an **idempotency key**. This is a unique ID for one attempt. Create it when the form is created (not on every click), and send it with the request. The server then makes sure the action happens "at most once". See [Backend, Lesson 02](/backend/lesson-2):

```tsx
// Generated once per form instance/attempt, reused on retries of the SAME submission
const idempotencyKey = useRef(crypto.randomUUID());

await fetch("/api/orders", {
  method: "POST",
  headers: { "Idempotency-Key": idempotencyKey.current, "Content-Type": "application/json" },
  body: JSON.stringify(order),
});
```

On the server, store the key together with the result, under a **unique constraint** (a database rule that allows each value only once). If the same request comes again, return the stored response.

As a last guard, use a **natural unique constraint** where one exists. For example, `UNIQUE (user_id, cart_id)` means "one order per cart". A disabled button in the UI is only a convenience. The database constraint is the real guarantee.

## Problem 4: your own frontend triggers rate limits (429)

Duplicate requests can also cause **429 Too Many Requests**. These are the common causes:

- Effects without the right dependencies, which fire on every render.
- Many components that each fetch the same resource (no dedupe).
- Polling (asking the server again and again) that is too frequent, or polling in **every open tab**.
- Retry loops without exponential backoff and jitter. Backoff means waiting longer after each failure. Jitter means adding a small random delay.
- The Strict Mode double run in development.
- Several users behind one company IP address, with a limit for each IP.

Fixes:

- Dedupe through a shared cache.
- Poll less often, or use SSE/WebSockets.
- Pause polling when the tab is hidden (`document.visibilityState`).
- Back off on `429` and use the `Retry-After` header.
- If needed, coordinate the tabs with `BroadcastChannel` or a leader election (the tabs choose one leader to do the work). See [Lesson 09](/debugging/lesson-9).

## Problem 5: stale closures and stale state in handlers

A closure is a function that remembers the variables from the place where it was created. A closure is "stale" when it remembers an old value.

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);   // ❌ closes over count = 0 forever
    return () => clearInterval(id);
  }, []);
  // ✅ setCount((c) => c + 1)  — the functional update does not depend on a captured value
}
```

Async callbacks remember the values from the render in which they were created. To avoid old values, you can:

- Use functional updates.
- Use refs to read the "latest value".
- Set the effect dependencies correctly.

See [Frontend Depth, Lesson 01](/frontend-depth/lesson-1).

## Problem 6: request deduplication and caching

Many components may ask for the same thing. Here is how to handle it:

- **React Query / SWR:** requests with the same key share one request in flight and one cache entry.
- **Next.js (App Router):** identical `fetch` calls (same URL and options) in one server render pass are **memoised** (remembered) and deduplicated. So several Server Components can call `getUser()` without making several network requests. Caching beyond one render depends on your `fetch` cache settings and framework version. Check the docs for your version.
- **Your own small dedupe:** store the promise that is in flight, by key.

```ts
const inflight = new Map<string, Promise<unknown>>();
export function dedupe<T>(key: string, fn: () => Promise<T>): Promise<T> {
  if (!inflight.has(key)) inflight.set(key, fn().finally(() => inflight.delete(key)));
  return inflight.get(key) as Promise<T>;
}
```

## Scenario walkthroughs

### "Fast typing shows results for an older query"

1. **Diagnose:** the Network tab shows overlapping requests. A slow earlier one finishes last and overwrites the state.
2. **Fix:** on every change, abort the previous request (or ignore stale results). Key the results by query.
3. **Improve:** debounce the input. Keep the previous results visible while loading.
4. **Prevent:** use React Query/SWR. Add a test with a mocked slow response for the first call.

### "How do you prevent a duplicate order submission, from the button to the database?"

1. **UI:** disable the button, show a pending state, and guard with a ref.
2. **Request:** send a stable `Idempotency-Key` that you create for each checkout attempt.
3. **Server:** keep an idempotency record with a unique constraint. Return the stored response for repeats. Reject the same key if the body is different.
4. **Database:** add a natural uniqueness constraint (one order per cart).
5. **Payments:** pass the key on to the payment provider too, so it also removes duplicate charges.
6. **Observe:** log the key and count the duplicate hits.

## Common mistakes

1. **Removing Strict Mode** to hide double effects.
2. **No abort/ignore logic**, so stale responses overwrite fresh data.
3. **Debouncing only**, and believing it solves races.
4. **Relying only on a disabled button** to prevent duplicates.
5. **Making a new idempotency key on each retry.** This defeats the purpose.
6. **Polling in every tab** and never pausing when the tab is hidden.
7. **Using `fetch` in effects for everything**, instead of a data layer that dedupes, or the server.
8. **Treating `AbortError` as a failure** and showing an error screen.

## Interview questions

### Q1. Why does my effect fetch twice in development?

React Strict Mode mounts, unmounts and remounts components in development, on purpose. It does this to show effects that do not clean up or that are not idempotent. It does not happen in production. The right answer is to make the effect safe (abort, or ignore stale results). Or move the fetching to a library or to the server, which dedupes. Do not turn Strict Mode off.

### Q2. Scenario: fast typing shows results for an older query. Fix it.

Responses can arrive out of order. So an older, slow response overwrites a newer one. In the effect cleanup, I abort the previous request with `AbortController` (or use an ignore flag). I key the results by query (React Query/SWR). I debounce to cut traffic, and I show the previous results while loading. I also add a test with a delayed first response.

### Q3. How do you prevent a duplicate order submission, from the button to the database?

I disable the button and show a pending state, with a ref guard. I send an idempotency key that is created once for each attempt. The server stores the key with the response under a unique constraint, and sends the same response again for repeats. I back this up with a natural unique constraint in the database, and I pass the key to the payment provider. The server and database layers are the real guarantee.

### Q4. Debounce vs abort?

Debounce reduces how many requests you send, because it waits for a pause in the input. But it does not stop an older response from arriving after a newer one. Abort (or ignoring stale results) makes sure only the result of the latest request is used. It also cancels work that is no longer needed. For search-as-you-type, use both.

### Q5. How can your own frontend cause 429 errors?

These things can cause it:

- Effects that fire too often.
- Many components fetching the same data without dedupe.
- Aggressive polling, especially across many tabs.
- Retry loops without backoff.
- The Strict Mode double run in dev.
- Many users that share one IP.

To fix it, dedupe requests, poll less often or use push channels, back off with `Retry-After`, and pause polling when the tab is hidden.

### Q6. Does AbortController stop the server from doing the work?

Not always. It cancels the client's wait and closes the connection. The server may already have processed the request, or may keep processing it, unless it notices the closed connection. So abort prevents stale state and saves some resources. But it does not guarantee that a side effect (a change such as saving data) did not happen. For writes, use idempotency.

### Q7. Why is a disabled button not enough to prevent duplicates?

State updates are asynchronous, so two quick clicks can both fire before the button is disabled. Users can also submit twice with the Enter key, with several tabs, with retries, or with direct API calls. So the server must prevent duplicates, with idempotency keys and database constraints.

### Q8. How does Next.js reduce duplicate server-side fetches?

In one server render pass, identical `fetch` calls (same URL and options) are deduplicated automatically. So several Server Components can ask for the same data without several network calls. To cache across requests, you configure fetch caching or use your own cache layer. This depends on the framework version.

## Key takeaways

- **Responses do not arrive in order.** Make the latest request win: abort previous requests, ignore stale results, and key data by query.
- **The double effect in Strict Mode is a feature.** Write effects that are idempotent and clean up. Or use a data layer that dedupes, or fetch on the server.
- **Debounce reduces traffic. Abort prevents stale overwrites.** Use both.
- Prevent duplicate submissions at every layer: **UI pending state → idempotency key → server dedupe → database constraint.**
- Dedupe shared requests, back off on 429, and pause background polling.
