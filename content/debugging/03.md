> **In one line:** a component re-renders when **its own state changes, its parent renders, or a context it reads changes**. Re-rendering is normally cheap, so only fix it when the Profiler shows it costs real time. Prefer **structural fixes** (move state down, split components) over scattering `memo`, `useMemo` and `useCallback`.

React re-renders are not "bugs"; they are how React works. The skill is knowing *when they matter*, *which ones are wasted*, and *the cheapest correct fix*.

## What causes a component to re-render?

1. **Its own state changes** (`useState`, `useReducer`).
2. **Its parent re-renders** (by default, all children re-render, even if their props did not change).
3. **A context it consumes changes value.**
4. **A store subscription it uses changes** (Redux, Zustand, etc.), for the selected slice.
5. A **hook it uses** triggers an update (a data-fetching library, a media-query hook).

Not a cause: the **props "looking the same."** Without `memo`, React re-renders the child anyway. With `memo`, React compares props shallowly, so a new object, array or function **identity** on every render defeats it.

> [!note] **Render is not the same as DOM update.** A re-render calls your component function and diffs the result (reconciliation). React only touches the DOM for what actually changed. A "wasted" render costs CPU for the function call and the diff, not necessarily a repaint. It matters when components are expensive, numerous, or render often.

In development, **Strict Mode** intentionally renders components (and runs effects) twice to expose impure code. Do not mistake that for a production problem.

## Measure first: React DevTools Profiler

1. Open **React DevTools → Profiler**, click **Record**, perform the slow interaction, stop.
2. In the **flame chart**, grey components did not render in that commit; coloured ones did (colour and width show render time).
3. Turn on **"Record why each component rendered"** in the settings to see the reason (props changed, state changed, parent rendered, hooks changed).
4. Use **"Highlight updates when components render"** in the general settings for a quick visual of what flashes on each interaction.
5. Look for: components that render **on every keystroke** with large cost, **many commits per interaction**, and components rendering **with unchanged props**.

Decide by numbers: if a whole commit takes 3 ms, leave it alone. If typing triggers a 120 ms commit, fix it.

## Fixes, from cheapest to most invasive

### 1. Colocate state (move it down)

The most effective fix and it adds no hooks. Keep state in the smallest component that needs it.

```tsx
// ❌ query lives in the page, so every keystroke re-renders the whole page
function Dashboard() {
  const [query, setQuery] = useState("");
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <Results query={query} />
      <HeavyCharts />   {/* re-renders on every keystroke for no reason */}
      <ActivityFeed />
    </>
  );
}

// ✅ the state (and the re-renders) live in a small component
function Dashboard() {
  return (
    <>
      <SearchBox />      {/* owns query; Results lives inside it or receives it by context/URL */}
      <HeavyCharts />    {/* no longer affected */}
      <ActivityFeed />
    </>
  );
}
```

### 2. Lift content up / pass children

If a stateful wrapper re-renders but its children come from a parent that did not re-render, React reuses those element objects and skips them:

```tsx
function Layout({ children }: { children: React.ReactNode }) {
  const [open, setOpen] = useState(false);    // changing this re-renders Layout...
  return <div className={open ? "open" : ""}>{children}</div>;  // ...but `children` is the same element object
}
// <Layout><ExpensiveTree /></Layout> — ExpensiveTree is created by the parent, so it is skipped
```

### 3. Split components along update boundaries

Separate the **fast-changing** part (an input, a timer, a hover state) from the **slow, expensive** part so each re-renders independently.

### 4. `memo` with stable props

`memo` skips re-rendering when props are shallowly equal. It only pays off when the component is **expensive**, renders **often**, and its props are **stable**.

```tsx
const Row = memo(function Row({ item, onSelect }: { item: Item; onSelect: (id: string) => void }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

function List({ items }: { items: Item[] }) {
  const [selected, setSelected] = useState<string | null>(null);

  // Stable identity: without useCallback, a new function each render breaks memo(Row)
  const onSelect = useCallback((id: string) => setSelected(id), []);

  return <ul>{items.map((it) => <Row key={it.id} item={it} onSelect={onSelect} />)}</ul>;
}
```

**When `memo` doesn't help:**

- A prop is a **new object, array or function on every render** (`style={{...}}`, `options={[…]}`, `onClick={() => …}`) and you did not stabilise it.
- The component is **cheap**: comparing props costs about as much as rendering.
- It receives **`children`** (JSX elements are new objects each render) unless the parent is stable.
- The re-render is caused by **context or its own state**, which `memo` does not block.

### 5. `useMemo` and `useCallback`, used deliberately

- **`useMemo`** caches a computed value; use it for **genuinely expensive** derivations, or to keep an **object/array identity stable** for a memoised child or an effect dependency.
- **`useCallback`** caches a function identity; useful when passing callbacks to `memo`-ed children or as hook dependencies.
- Both have a cost (memory, dependency comparison, code noise). Applying them everywhere makes code harder to read and rarely helps.

### 6. Fix context re-renders

Every consumer re-renders when the context **value** changes identity. A single "app state" context that changes often re-renders the whole tree under it.

```tsx
// ❌ One big, frequently-changing value; new object every render
<AppContext.Provider value={{ user, theme, cart, setCart }}>...</AppContext.Provider>

// ✅ Split by update frequency, and memoise the value
const value = useMemo(() => ({ cart, setCart }), [cart]);
<UserContext.Provider value={user}>
  <CartContext.Provider value={value}>...</CartContext.Provider>
</UserContext.Provider>
```

Better still: for **frequently changing state** (cart, form, live data), use an **external store with selectors** (Zustand, Redux Toolkit, Jotai, `useSyncExternalStore`), so a component subscribes only to the slice it uses and re-renders only when that slice changes:

```tsx
const itemCount = useCartStore((s) => s.items.length);   // re-renders only when the length changes
```

Context is excellent for **rarely changing** values (theme, locale, auth user); it is a poor fit for **high-frequency** updates ([Frontend Depth, Lesson 03](/frontend-depth/lesson-3)).

### 7. Reduce what each render does

- Don't compute heavy derived data in render without memoisation; precompute it.
- Avoid creating large objects or running `sort`/`filter` over huge arrays on each render.
- **Virtualise** long lists so only visible rows render ([Lesson 07](/debugging/lesson-7)).
- Use **stable, unique `key`s**: unstable keys (`Math.random()`, array index on reorderable lists) cause remounts and lost state.

### 8. Defer non-urgent updates

`useDeferredValue` and `startTransition` keep input responsive while expensive children catch up ([Lesson 01](/debugging/lesson-1)). For rapid events, **debounce** the state that triggers heavy work.

### 9. The React Compiler

React has an opt-in **compiler** that automatically memoises components and values at build time, so much of the manual `memo`/`useMemo`/`useCallback` work becomes unnecessary where it is enabled. It does not remove the need for **good structure** (colocated state, small components, split contexts) and it cannot fix expensive work that genuinely needs to happen. Check the version and setup your project uses, and avoid adding manual memoisation "just in case."

## Scenario: typing in a search box re-renders the whole page. Fix it.

1. **Profile it:** Profiler shows the page, a chart, a table and a sidebar re-rendering on each keystroke; the table renders 500 rows (45 ms per commit).
2. **Move state down:** put `query` state inside `SearchBox`, and have the results subscribe through a small store, URL search param or a callback that updates only the results component.
3. **Defer the expensive part:** `useDeferredValue(query)` for the results list (or debounce at 200 ms for server requests).
4. **Memoise the table rows** (`memo` + stable `key`s and callbacks) and **virtualise** the list.
5. **Memoise the filter computation** (`useMemo` on `[rows, deferredQuery]`) and precompute lowercase search text.
6. **Re-profile:** the commit on typing now touches only the input and the visible results.

## Debugging "why did this render?" in code

```tsx
// Quick, temporary helper
function useWhyDidYouRender(name: string, props: Record<string, unknown>) {
  const prev = useRef(props);
  useEffect(() => {
    const changed = Object.entries(props).filter(([k, v]) => prev.current[k] !== v).map(([k]) => k);
    if (changed.length) console.log(`[${name}] re-rendered because:`, changed);
    prev.current = props;
  });
}
```

Remove it afterwards; the React Profiler's "why did this render" is usually enough.

## Common mistakes

1. **Optimising without profiling.**
2. **`memo` on components that receive new object/array/function props every render.**
3. **`useMemo`/`useCallback` on everything** (noise, no gain).
4. **One giant context** updated frequently, re-rendering the whole tree.
5. **State too high in the tree** (fix by colocation).
6. **Index keys on dynamic lists**, causing state to jump between rows ([Frontend Depth, Lesson 00](/frontend-depth/lesson-0)).
7. **Panicking about Strict Mode's double render** in development.
8. **Storing derived data in state** (copying props into state) and syncing it with effects, causing extra renders. Compute it during render instead.

## Interview questions

### Q1. What causes a component to re-render?

Its own state changing, its parent re-rendering (children re-render by default even with identical props), a consumed context value changing, a subscribed store slice changing, or a hook inside it triggering an update. Props "looking equal" is irrelevant unless the component is wrapped in `memo` and the props are referentially stable.

### Q2. When does `memo` not help?

When props are new on every render (inline objects, arrays, functions, JSX children), when the component is cheap, or when the re-render comes from context or internal state, which `memo` doesn't block. You also need stable references via `useMemo`/`useCallback` or restructuring for it to pay off.

### Q3. Scenario: typing in a search box re-renders the whole page. Fix it.

Profile first, then colocate the input state in a small component so only it re-renders on keystrokes, defer or debounce the expensive results update (`useDeferredValue` or debounce), memoise heavy children with stable props, memoise or precompute the filtering, and virtualise large lists. Re-profile to verify the commit is small.

### Q4. Context vs an external store for frequently changing state?

Context re-renders every consumer whenever the value changes, which is fine for rarely changing values like theme or locale but wasteful for high-frequency state. An external store with selectors (Zustand, Redux Toolkit, `useSyncExternalStore`) lets each component subscribe to just the slice it needs and re-render only when that slice changes.

### Q5. What is the "children as props" (lift content up) pattern and why does it avoid renders?

If a stateful wrapper receives `children` created by a parent that does not re-render, those element objects keep the same identity, so React skips re-rendering them when the wrapper's state changes. It isolates the expensive subtree from the wrapper's updates without `memo`.

### Q6. How do you decide whether a re-render is a problem?

I measure with the React Profiler: render duration, how often it happens per interaction and whether it affects interaction latency (INP). Frequent, expensive commits during input or animation are worth fixing; short renders of small components are not.

### Q7. Where does the React Compiler fit?

It memoises automatically at build time where enabled, reducing the need for manual `memo`, `useMemo` and `useCallback`. Component structure still matters, and expensive work must still be reduced or deferred; the compiler does not make a heavy computation or a giant list cheap.

## Key takeaways

- Re-renders come from **state, parent, context, store**; they are cheap until components are large, many or frequent.
- **Profile first** (React DevTools Profiler, "why did this render", highlight updates).
- Prefer **structure**: colocate state, pass children, split components; then **`memo` with stable props**, split contexts or use **selectors**.
- Use **`useMemo`/`useCallback` deliberately**, **virtualise** long lists, **defer** non-urgent updates.
- Don't copy props into state; derive during render. Keep keys stable.
