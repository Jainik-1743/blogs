> **In one line:** if the API answers quickly but the screen is slow, the time is being spent **on the main thread**: parsing a huge response, building too many DOM nodes, re-rendering too often, or running long tasks. Find which one in the Performance panel, then reduce the work or move it off the critical path.

This is the single most common senior-level frontend scenario, and it ties directly to the **INP** metric ([Browser Contract, Lesson 09](/browser/lesson-9)).

## Confirm the diagnosis

1. **Network tab:** the request's *Waiting (TTFB)* is small (for example 80 ms) and *Content Download* is reasonable. The server is not the problem.
2. **Performance panel** (with 4x CPU throttling): record the interaction. Look for:
   - **Long tasks** (more than 50 ms, red corners) on the Main thread.
   - A large **Scripting** (yellow) slice after the response arrives.
   - **Recalculate Style / Layout** (purple) and **Paint / Commit** (green) slices.
3. **Break the delay down** (for interactions, the INP model): *input delay* (main thread busy before the handler), *processing time* (handlers and the work they trigger), *presentation delay* (render and paint after handlers).

Now the usual suspects, roughly in order of how often they are the cause.

## Suspect 1: rendering far too many DOM nodes

A 5 MB JSON feeding a table of 20,000 rows creates hundreds of thousands of DOM nodes. Creating, styling, laying out and painting them dominates the time, **far more than parsing the JSON**.

Evidence: a huge Scripting + Layout + Paint cost after the response; the Elements panel shows an enormous DOM; `document.querySelectorAll("*").length` is in the tens of thousands.

Fixes (in order of effectiveness):

- **Don't send or render what the user cannot see:** server-side **pagination** or cursor paging, filters applied on the server ([Practical Design Problems, Lesson 03](/design-problems/lesson-3)).
- **Virtualize** long lists so only visible rows exist in the DOM ([Lesson 07](/debugging/lesson-7)).
- **`content-visibility: auto`** for long, mostly off-screen sections.
- Simplify each row's markup (fewer wrappers, fewer nested components).

## Suspect 2: parsing and processing a huge payload

Parsing is synchronous and CPU-bound. `JSON.parse` of 5 MB is usually tens of milliseconds on a desktop but **several times slower on a mid-range phone**, and the work that follows (mapping, sorting, normalising 50,000 objects) often costs more than the parse itself.

Fixes:

- **Send less:** return only the fields the screen needs (`select` on the server, sparse fieldsets, GraphQL fields), drop unused data, compress (Brotli), paginate.
- **Do heavy transformations on the server** or in a precomputed endpoint.
- **Move CPU-heavy parsing and processing to a Web Worker**, then send only the result to the main thread.
- **Stream** NDJSON and render progressively instead of waiting for one giant blob.
- Avoid repeated deep copies (`structuredClone`, `JSON.parse(JSON.stringify(x))`) of large state on every update.

```ts
// worker.ts — processing happens off the main thread
self.onmessage = (e: MessageEvent<{ rows: Row[]; query: string }>) => {
  const { rows, query } = e.data;
  const result = rows.filter((r) => r.name.toLowerCase().includes(query)).sort(byDateDesc);
  (self as unknown as Worker).postMessage(result.slice(0, 200)); // send back only what will be shown
};
```

## Suspect 3: re-render storms

A single state change re-renders a huge component tree, repeatedly. Typing in a search box re-renders the entire dashboard on every keystroke; a context value changes and every consumer updates.

Evidence: the React Profiler shows many components rendering on each commit; "Highlight updates when components render" flashes everywhere; the same interaction triggers several commits.

Fixes are the subject of [Lesson 03](/debugging/lesson-3): **colocate state**, split components, memoise the expensive children **with stable props**, split contexts or use selectors, and virtualise.

## Suspect 4: expensive work during render

```tsx
function Table({ rows, query, sortKey }: Props) {
  // ❌ Runs on EVERY render, even if rows/query/sortKey did not change (e.g. a parent re-render)
  const visible = rows.filter((r) => match(r, query)).sort(compare(sortKey));
  return <>{visible.map((r) => <Row key={r.id} row={r} />)}</>;
}
```

Fixes:

- `useMemo` for derived data **when the computation is genuinely expensive and its inputs are stable** (measure first).
- Move derived work out of render: compute once when data arrives, or on the server.
- Use a better algorithm: precompute a lowercase search field once instead of lowercasing every row on every keystroke; use a `Map` for lookups instead of `find` inside loops (accidental O(n²)).
- Debounce or defer the expensive part ([below](#starttransition-and-usedeferredvalue)).

## Suspect 5: layout thrashing and forced reflows

Reading layout (`offsetHeight`, `getBoundingClientRect()`) after writing styles, inside loops or effects, forces synchronous layout repeatedly ([Browser Contract, Lesson 08](/browser/lesson-8)). In the Performance panel you will see repeated Layout blocks with a "Forced reflow" warning.

Fix: **batch reads then writes**, measure once, use `ResizeObserver`/`IntersectionObserver`, avoid measuring per row.

## Suspect 6: hydration cost

On a Next.js page, the HTML arrives fast and looks ready, but the buttons do nothing for a second or two because React is **hydrating**: re-running components on the client and attaching handlers, which scales with the amount of client-side JS and component tree size.

Evidence: a long task right after the JS bundle loads; "Hydrate" or large `commitRoot` work; users clicking early see no response (poor INP and "rage clicks").

Fixes:

- **Ship less client JavaScript:** make components **Server Components** by default and mark only interactive leaves with `"use client"` ([Frontend Depth, Lesson 02](/frontend-depth/lesson-2)).
- **Code-split** heavy, non-critical widgets (dynamic import) and load them after interaction or when visible.
- **Selective hydration** with `<Suspense>` boundaries so parts hydrate independently and the page prioritises what the user interacts with.
- Avoid rendering huge lists on the client at hydration.

## Suspect 7: client-side waterfalls

The API is fast, but the page makes **sequential** calls: render → fetch user → render → fetch their projects → render → fetch project details. Each step waits for the last render. Ten 80 ms calls become a second of waiting, plus extra renders.

Fixes:

- **Fetch in parallel** (`Promise.all`) when requests do not depend on each other.
- **Hoist fetching** to the route/server (Server Components, loaders) so data is requested before the component tree renders.
- **Prefetch** likely next requests (link hover, route prefetch).
- Combine chatty endpoints (a purpose-built endpoint, or a GraphQL query that returns the related data in one call) ([Backend, Lesson 09](/backend/lesson-9)).

## Suspect 8: third-party scripts and other main-thread hogs

Analytics, tag managers, chat widgets, A/B testing and ad scripts run on the same main thread. Evidence: long tasks attributed to a third-party domain; the Performance panel's "Bottom-up" view grouped by origin.

Fixes: load with `async`/`defer` or Next's `next/script` strategies (`afterInteractive`, `lazyOnload`; the experimental `worker` strategy does not yet work with the App Router), remove what you do not need, and measure each tag's INP cost. Also check **image decoding** (huge images), heavy CSS selectors and **animations** that trigger layout.

## `startTransition` and `useDeferredValue`

These React APIs do not make work cheaper; they make it **interruptible and lower priority** so input stays responsive.

```tsx
function Search({ rows }: { rows: Row[] }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);          // lags behind during heavy renders

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />  {/* urgent: updates immediately */}
      <ResultList rows={rows} query={deferredQuery} />                    {/* non-urgent: re-renders when React has time */}
    </>
  );
}

const ResultList = memo(function ResultList({ rows, query }: { rows: Row[]; query: string }) {
  const visible = useMemo(() => rows.filter((r) => r.searchText.includes(query)), [rows, query]);
  return <ul>{visible.slice(0, 200).map((r) => <li key={r.id}>{r.name}</li>)}</ul>;
});
```

- **`useDeferredValue(value)`** gives you a copy that "catches up" later. While the heavy `ResultList` renders with the old value, the input stays snappy. The deferred render can be **interrupted** by new typing.
- **`startTransition(() => setState(...))`** marks a state update as non-urgent so React can render it in the background without blocking urgent updates such as typing or clicking.
- **Requirement:** the slow child should be wrapped in `memo` (so it does not re-render for the urgent update) and its render should be **interruptible**. These do not help if the cost is a single huge synchronous computation outside React rendering, or if the DOM work in the commit phase is the bottleneck (commit is not interruptible).
- They improve **INP** by reducing blocked input, but total CPU work is the same; combine with virtualisation and memoisation to reduce the work itself.

## Scenario: a 5 MB JSON feeds a table. Where is the time going?

A quick ranked analysis you can say out loud:

| Stage | Typical cost | How to check |
|---|---|---|
| Download | Depends on size (compressed?) | Network tab "Content Download", transferred vs resource size |
| `JSON.parse` | Tens of ms desktop, 5x or more on mid-range phones | Performance panel "Parse"/scripting just after the response |
| Building state / mapping 50k objects | 10s to 100s of ms | User timing marks around the code |
| **React render of 50k rows** | **Often the largest: hundreds of ms to seconds** | Profiler render duration, Scripting after parse |
| **DOM creation, style, layout, paint** | **Also large with ~100k+ nodes** | Performance panel purple/green slices; DOM node count |
| Subsequent interactions (sort/filter) re-render all rows again | Repeats the render cost on each action | Profiler on a sort click |

Plan: first **send less** (paginate or filter on the server, trim fields), then **virtualise** the list, then **memoise rows** and move heavy sorting/filtering off the main thread or to the server, and finally use `useDeferredValue` so typing stays responsive. Verify each step with a new recording and compare INP and total blocking time.

## A checklist you can recite

1. Confirm in the Network tab that TTFB is small; record the Performance panel under CPU throttling.
2. Identify the dominant slice: Scripting, Layout/Style, Paint, or long tasks.
3. Count DOM nodes and rows rendered; reduce with pagination or virtualisation.
4. Check payload size and what is parsed; trim, compress, offload to a worker.
5. Open the React Profiler: what re-renders, why, how often?
6. Look for work in render (filter/sort/map) and forced reflows.
7. Check hydration and client JS size; move to Server Components, split code.
8. Look for sequential client fetches and third-party scripts.
9. Use transitions or deferred values for non-urgent updates.
10. Re-measure; add a budget or RUM alert.

## Common mistakes

1. **Blaming the API** because the page feels slow, without reading the Timing breakdown.
2. **Fixing JSON parsing** when the real cost is rendering the rows.
3. **Wrapping everything in `useMemo`/`memo`** without profiling.
4. **Expecting `startTransition` to reduce work**; it only reschedules it.
5. **Profiling on a fast laptop** with no CPU throttling.
6. **Fetching waterfalls** inside nested components.
7. **Ignoring hydration cost** on server-rendered pages.

## Interview questions

### Q1. What's your first step in DevTools?

Open the Network tab and check the slow request's Timing to confirm the server is fast (small TTFB), then record the Performance panel with CPU throttling while reproducing the slowness. I look for long tasks and whether Scripting, Layout or Paint dominates, and for the React Profiler to see what rendered.

### Q2. How do long tasks affect INP?

A long task blocks the main thread, so a click that arrives during it must wait (input delay), and a handler that triggers a long render delays the next paint (processing and presentation). INP is based on the full interaction latency, so frequent long tasks directly worsen it. Break tasks up, defer non-urgent work and reduce rendering cost.

### Q3. Scenario: a 5 MB JSON response feeds a table. Where is the time going?

Mostly not in the download or `JSON.parse`; it is in building state for tens of thousands of items and above all rendering and laying out huge numbers of DOM nodes, repeated on every sort or filter. I would verify with the Performance panel and Profiler, then reduce the data (server pagination, fewer fields), virtualise the list, memoise rows, move heavy processing to a worker or the server, and defer non-urgent updates.

### Q4. How would `startTransition` or `useDeferredValue` help?

They mark an update as non-urgent so React renders it in the background and can interrupt it when urgent input arrives, keeping typing and clicking responsive and improving INP. They do not reduce total work, and they need the slow subtree to be memoised and the cost to be in React rendering, not in an uninterruptible synchronous computation.

### Q5. The page looks loaded but buttons don't respond for two seconds. What's happening?

Probably hydration: the server HTML is visible, but the client bundle must download, run and re-render components to attach handlers. Reduce client JavaScript with Server Components, code-split non-critical widgets, use Suspense boundaries for selective hydration and trim third-party scripts.

### Q6. How do you find out whether a slowdown is caused by rendering or by data processing?

Use User Timing marks (`performance.mark/measure`) around the processing step, compare it with React Profiler render durations and the Performance panel's Scripting versus Layout/Paint slices. If processing is small and rendering/commit dominate, the fix is fewer DOM nodes and re-renders; if processing dominates, optimise or offload it.

### Q7. What is a client-side waterfall and how do you avoid it?

Sequential dependent requests where each fetch starts only after the previous one's data has rendered, so latencies add up. Avoid it by fetching in parallel, hoisting data loading to the server or route level, prefetching, and combining endpoints.

## Key takeaways

- **API fast, UI slow = main-thread work.** Find it in the Performance panel and React Profiler under CPU throttling.
- Biggest culprits: **too many DOM nodes, re-render storms, expensive render-time work, big payload processing, hydration, waterfalls, third-party scripts.**
- Reduce the work first (**send less, render less, virtualise, memoise with stable props**); then reschedule it (**transitions, deferred values, workers**).
- Verify with INP and total blocking time, and keep a budget.
