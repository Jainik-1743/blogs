> **In one line:** between the user and your code there are usually several machines that do not run your business logic but decide whether your site is fast, safe and up: **reverse proxies, load balancers, CDNs and firewalls**. Learn what each one sees (a raw TCP stream, or a full HTTP request), what it adds (headers, retries, caching), and what it hides (the real client IP), and most "it works on my laptop but not in production" problems become easy to explain.

When you run `node server.js` on your laptop and open `localhost:3000`, there is one hop. In production there might be five: a CDN, a cloud load balancer, a reverse proxy such as nginx, and finally your app, all inside a firewall. Each one can change the request, time it out, cache it, or refuse it. Many bugs live in those gaps: the user's IP address that is always `10.0.3.7`, a WebSocket that dies after one minute, a `502 Bad Gateway` that your logs never show, an old page that will not go away.

This is lesson 6 of a nine-lesson series. It builds on [TLS and certificates](/networking/lesson-5) (because proxies usually hold your certificate), on [HTTP](/networking/lesson-4) and on [TCP](/networking/lesson-2). The next lesson, [WebSockets and server-sent events](/networking/lesson-7), will go through these same proxies and show what they do to long-lived connections. For the security side of servers see [Security Lesson 7 (APIs and servers)](/security/lesson-7).

## Words used in this lesson

- **A proxy** is a server that sits between two parties and passes messages along.
- **A forward proxy** works for the *client*. Clients inside a company send their requests to it to reach the internet.
- **A reverse proxy** works for the *server*. Clients think they talk to your site, but they talk to the proxy, which forwards to your app.
- **A load balancer** spreads requests over several backend servers.
- **A backend** (or **upstream**) is a server that sits behind the proxy.
- **Layer 4 (L4)** means working with TCP connections only: addresses and ports. **Layer 7 (L7)** means reading HTTP: paths, headers, cookies.
- **A health check** is a small request sent to a backend on a timer to see if it is fine.
- **A sticky session** (also called session affinity) means the same client goes to the same backend each time.
- **TLS termination** means the proxy decrypts HTTPS so the backends see plain HTTP.
- **A CDN (content delivery network)** is a set of cache servers around the world. Users get content from a server near them.
- **An edge** server is one of those servers close to the user.
- **A cache hit** means the answer came from the cache. A **miss** means the cache had to ask the origin (your server).
- **The origin** is your real server behind the CDN.
- **A firewall** allows or blocks network traffic by rules. A **security group** is the cloud version, attached to a server.
- **Gateway errors**: **502 Bad Gateway** (the proxy got a bad or no answer from the backend), **503 Service Unavailable** (no backend can take the request), **504 Gateway Timeout** (the backend took too long).

## Why put something in front of your app?

A proxy in front of your Node app can do many jobs, so that the app does not have to:

- **Terminate TLS**: hold the certificate and do the encryption work.
- **Spread load** across several copies of the app, and avoid sending traffic to sick ones.
- **Serve static files** and compress responses without waking up your JavaScript.
- **Cache** answers that do not change.
- **Hide the internal network**: the outside world sees one address, not your database or your worker machines.
- **Limit damage**: rate limits, request size limits, timeouts, blocking known bad requests.
- **Allow zero-downtime deploys**: start new servers, move traffic over, remove the old ones.

The price: another hop (a little latency), another thing that can fail, and another place where behaviour can differ from your laptop. Let us look at each piece, starting with the simplest.

## Forward proxy: the client's helper

A forward proxy is configured on the **client side**. In a company, all laptops may send their web traffic through one proxy that logs, filters, or caches. Your app uses it when you set `HTTPS_PROXY` or `HTTP_PROXY` (in my sandbox this was set and it caught me out in the last lesson).

How does a proxy handle HTTPS if it cannot read it? For plain HTTP, the client sends the whole request to the proxy with a full URL. For HTTPS, the client sends one plain request first: `CONNECT host:443`. That says "please open a TCP tunnel to this host and port". After the proxy replies `200 Connection Established`, the client starts the TLS handshake **through the tunnel**, directly with the real server. The proxy just copies bytes.

I wrote a tiny forward proxy in Node (about 20 lines: an HTTP server for plain requests, and a `connect` event handler that opens a TCP socket and pipes both ways). Then I made one plain HTTP request and one HTTPS request through it, with a secret in the query string of each:

```text
$ curl -s -x http://127.0.0.1:3128 http://127.0.0.1:3001/secret?token=abc
{"backend":"b1","count":1,...}

$ curl -s -x http://127.0.0.1:3128 --cacert pki/ca.crt https://app.lab.test:8441/private?token=abc
hello from good over TLSv1.3

-- what the proxy logged:
[proxy] plain  GET http://127.0.0.1:3001/secret?token=abc
[proxy] CONNECT app.lab.test:8441
```

Read the two log lines. For plain HTTP, the proxy saw the **full URL including the token**. For HTTPS, the proxy saw only **the host and port**. The path, query and body were inside the encrypted tunnel. That is why TLS protects you from your own network operator, and also why some companies install their own CA on laptops and run a proxy that *does* decrypt (it presents a certificate for each site signed by the company CA). If your code behaves differently inside such a network, the certificate issuer will be the company, not the real one.

> [!warn] If an HTTPS call fails only at work or only inside a container, check the proxy environment variables (`env | grep -i proxy`) and `NO_PROXY`. A wrong proxy setting gives errors like connection reset or a certificate from an unexpected issuer, which look like TLS bugs but are not.

## Reverse proxy: the server's front door

A reverse proxy is the opposite. The **client does not know about it**. DNS points your domain at the proxy, the proxy accepts the connection and forwards the request to the app. Here is the smallest useful nginx setup. It listens on port 8080 and passes everything to a Node app on 3001:

```nginx
events { worker_connections 256; }
http {
  server {
    listen 127.0.0.1:8080;
    location / {
      proxy_pass http://127.0.0.1:3001;
      proxy_set_header Host $host;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
    }
  }
}
```

The three `proxy_set_header` lines matter. Without them your app sees the proxy, not the user.

### What the backend sees, and what it does not

My test backend prints the headers and the network peer for every request. Through the proxy:

```text
{"backend":"b1","count":1,"xff":"127.0.0.1","peer":"127.0.0.1","host":"localhost"}
```

`peer` is `127.0.0.1`, the proxy's own address, because **the TCP connection is from the proxy to the app**. The real client address is only in the `X-Forwarded-For` header (here `127.0.0.1` is the client too, because I ran curl on the same machine). In production, `peer` is the proxy's private IP, and if you log or rate-limit by `req.socket.remoteAddress`, every user looks the same. This is the number one beginner bug with proxies: all users blocked at once by a rate limit, because they all share the proxy's address.

Another thing I noticed. In one test config I forgot the `Host` line, and nginx sent the backend this:

```text
"host":"one"
```

`one` is the *name of my upstream block*. By default nginx sets `Host` to the upstream name (from my background knowledge of nginx, and I saw it happen). If your app builds URLs from the `Host` header, or has several sites keyed by host name, it will break. Set `proxy_set_header Host $host;` unless you have a reason not to.

### X-Forwarded-For can be forged

`X-Forwarded-For` is just a header. A client can send it too. nginx has two common ways to set it:

- `$proxy_add_x_forwarded_for`: **append** the connecting address to whatever the client sent.
- `$remote_addr`: **overwrite** with the connecting address only.

I sent a request that already claimed `X-Forwarded-For: 1.2.3.4` to a location of each kind:

```text
append:     "xff":"1.2.3.4, 127.0.0.1"
overwrite:  "xff":"127.0.0.1"
```

With "append", the app receives a list, and the first entry is **whatever the attacker typed**. If your code does `req.headers['x-forwarded-for'].split(',')[0]` to find "the client IP", an attacker can pick their own IP and escape rate limits or fake an audit log. The right way: know how many trusted proxies are in front of you, and take the entry that many places from the **right** (the proxies add to the end). In Express this is the `trust proxy` setting (set to the number of proxies, never to plain `true` unless the edge strips client-supplied values). The edge-most proxy should either overwrite or strip the header. I did not run Express here; check its docs for the exact option for your version.

```explainer
networking-6-forwarded-for
```

Also pass `X-Forwarded-Proto`. When TLS ends at the proxy, your app only sees HTTP. Code that says "if the request is not HTTPS, redirect to HTTPS" will loop forever unless it reads `X-Forwarded-Proto` from the trusted proxy.

## Layer 4 versus layer 7

Load balancers come in two flavours, and the difference is what they read.

- **L4 (transport layer).** The balancer sees TCP connections only. It picks a backend when the connection opens and then copies bytes both ways. It cannot see the URL, headers or cookies. It is very fast and works for any protocol: databases, MQTT, game servers, TLS passed through without decrypting. Also, one TCP connection stays on one backend for its whole life.
- **L7 (application layer).** The balancer reads HTTP. It can route `/api` to one pool and `/images` to another, add headers, retry a failed request on another backend, cache, rewrite and read cookies. It costs more CPU. And it balances **per request**, not per connection.

I put the same two backends behind HAProxy twice, once in `mode http` (port 8090) and once in `mode tcp` (port 8091), and sent requests to both:

```text
--- L7 (mode http) on 8090: backend sees the forwarded header
{"backend":"b2","count":4,"xff":"127.0.0.1","peer":"127.0.0.1","host":"localhost:8090"}

--- L4 (mode tcp) on 8091: backend sees only a TCP connection, no XFF header
{"backend":"b1","count":8,"xff":null,"peer":"127.0.0.1","host":"localhost:8091"}
{"backend":"b2","count":5,"xff":null,"peer":"127.0.0.1","host":"localhost:8091"}
```

In L7 mode HAProxy added `X-Forwarded-For` (I turned on `option forwardfor`). In L4 mode, `xff` is `null`: the proxy never looked inside, so it could not add a header. For L4 balancing, the original client address is lost unless you use the **PROXY protocol** (a small line the balancer writes at the start of the TCP stream) or the balancer preserves the source address at the network level (some cloud balancers do). I did not test the PROXY protocol here.

A common cloud layout is an L4 balancer in front (cheap, fast, handles huge numbers of connections) pointing at a fleet of L7 proxies (smart routing), pointing at your apps.

| | L4 | L7 |
|---|---|---|
| Sees | IPs, ports, bytes | Full HTTP request |
| Can route by path or header | No | Yes |
| Can add `X-Forwarded-For` | No (needs PROXY protocol) | Yes |
| Balances | Per connection | Per request |
| Can retry on another backend | Only if the connect fails | Yes, if the request is safe to retry |
| Works for non-HTTP traffic | Yes | No |
| Cost | Low | Higher |

## Balancing algorithms

How does the balancer pick a backend?

- **Round robin**: take turns. 1, 2, 3, 1, 2, 3. Simple, fair if requests cost about the same.
- **Weighted round robin**: some backends get more turns. Useful when servers have different sizes.
- **Least connections**: pick the backend with the fewest active requests. Better when some requests are slow.
- **Hash-based** (such as nginx `ip_hash`, or hashing a cookie or URL): the same input always picks the same backend. This gives stickiness and is used for caches.

Real runs against nginx (three backends, ten requests):

```text
round robin, 6 requests:   b1 b2 b3 b1 b2 b3

weights 3:1:1, 10 requests (counts):
      6 b1
      2 b2
      2 b3

ip_hash, 6 requests from the same client (counts):
      6 b3
```

Round robin did what it says. The 3:1:1 weights split the ten requests as 6, 2, 2. And `ip_hash` sent all six requests from my one address to the same backend, `b3`. The problem with `ip_hash`: everyone behind the same NAT (an office, a mobile carrier) has the same IP address and lands on one server. So it balances badly.

### Sticky sessions: usually a bandage

Why would you want a user to return to the same backend? Because the backend keeps something in memory for that user: a login session, a shopping cart, a WebSocket connection. If the user lands on another server, that memory is not there.

Sticky sessions solve this by routing on a cookie or IP, but they have costs: uneven load, and when that server dies or restarts for a deploy, the users' state dies with it. The better design is **stateless backends**: keep sessions in a shared store (Redis or a database), and let any server handle any request. Use stickiness only when you must, for example WebSocket servers that hold connection state (next lesson).

## Health checks: how a balancer knows who is alive

A balancer that keeps sending traffic to a dead server is worse than none. There are two ways to know.

**Passive checks** watch real traffic. If a request to a backend fails (connection refused, timeout), the balancer marks that backend as failed for a while and tries another. Open-source nginx works this way (`max_fails` and `fail_timeout`). I killed backend b2 and sent six requests:

```text
200 b1
200 b3
200 b3
200 b1
200 b3
200 b1
```

No errors reached the client. nginx tried b2 on one request, saw the connection refused, and **retried the same request on the next backend** within the same call. Then it skipped b2 for the next ten seconds. That is the upside of an L7 proxy. The downside is that a real user request paid for finding out.

**Active checks** are made by the balancer itself on a timer, even with no user traffic. HAProxy does this with `option httpchk GET /health` and `check inter 500ms fall 2 rise 2` (check every half second, two failures to mark it down, two successes to bring it back). My backend's `/health` returned 503 when I switched it, while the process was still running and still accepting connections:

```text
--- status all up
b1 UP   b2 UP   b3 UP
--- make b2 unhealthy (the process is alive but /health returns 503)
b1 UP   b2 DOWN   b3 UP
--- 9 requests: b1 got 4, b3 got 5, b2 got 0
--- b2 healthy again
b1 UP   b2 UP   b3 UP
--- kill the b1 process completely
b1 DOWN   b2 UP   b3 UP
```

(The uneven 4 and 5 is because the round-robin counter was in the middle of its turn.) Two things to see. First, the health check noticed a backend that was **running but sick**, which a plain TCP connect check cannot. Second, the check protected users: b2 received no traffic while it was down, with no failed requests.

> [!warn] **Design `/health` carefully.** A shallow check (`return 200`) misses a broken database connection. A deep check (calls the database and three other services) can take every backend out of rotation at the same moment when one shared dependency has a hiccup, and turn a small slowdown into a full outage. A good middle: the load balancer's health check tests "can this process serve requests", and your monitoring tests the dependencies and alerts you.

### Retries can hurt

Retries hide failures, but they multiply load and can repeat actions. I set a 1-second read timeout in nginx and called an endpoint that takes 1.5 seconds, with several backends:

```text
slow endpoint, 3 backends (one already dead): 502 after 2.0 s    (nginx waited 1 s, retried on the next backend, waited 1 s again, then gave up)
slow endpoint, 1 backend:   504 after 1.0 s
```

On a timeout nginx, by default, tries the next server (the `proxy_next_upstream` setting; I saw it retry here, which matches how I understand the default to work, but check the docs). Think about what happens if the endpoint was "charge the customer" and the first backend actually did the work slowly: the retry charges again. By default nginx does not retry non-idempotent requests like POST after they were sent (from my background knowledge, not tested here), and you should keep it that way. The real fix is to make your own endpoints **idempotent**, with an idempotency key, so that a retry is safe.

### Reading gateway errors

The status codes tell you where to look:

| Status | Meaning from the proxy's view | I reproduced it by |
|---|---|---|
| **502 Bad Gateway** | I tried the backend and got an invalid reply or could not connect. | Pointing `proxy_pass` at a closed port: `502`. |
| **503 Service Unavailable** | No backend is available, or I am shedding load. | Killing all backends in the upstream group: nginx logged `no live upstreams` and returned `502` in my config (the code differs by product and settings). |
| **504 Gateway Timeout** | The backend took longer than my timeout. | One backend that sleeps 1.5 s and a 1 s read timeout: `504 Gateway Time-out`. |

The proxy's error log says more than the status. For example (real lines):

```text
connect() failed (111: Connection refused) while connecting to upstream, ... upstream: "http://127.0.0.1:3002/slow"
upstream timed out (110: Connection timed out) while reading response header from upstream, ...
no live upstreams while connecting to upstream, ... upstream: "http://rr/x"
```

Notice that your **app's own logs show nothing** for a 502 or a timeout of the "connection refused" kind, because the request never arrived. Always read the proxy's logs first. Also, set timeouts on purpose: the proxy's read timeout should be a little above your slowest legitimate response, and your app should have its own timeout for each outgoing call that is lower than the proxy's.

## Caching and CDNs

A cache stores a copy of a response so the next request does not need the origin. A **CDN** is a big shared cache with many locations. When a user in Mumbai asks for `logo.png`, a nearby edge server answers; only the first request, or an expired one, travels to your origin. Benefits: lower latency (shorter distance), less origin load, protection from traffic spikes, and edge TLS (the handshake from [last lesson](/networking/lesson-5) is made with a nearby server, so its round trips are short).

I could not run a real CDN in this sandbox, but nginx's `proxy_cache` follows the same rules, so here is the same behaviour with real output. My backend sends `Cache-Control: public, max-age=5`. I made three requests, waited six seconds and made a fourth, printing nginx's cache status header each time:

```text
X-Cache-Status: MISS
X-Cache-Status: HIT
X-Cache-Status: HIT
(after 6 seconds)
X-Cache-Status: EXPIRED
```

The first request was a **miss** and went to the backend. The next two were **hits**: the backend counter did not move. After five seconds the copy was stale, so the cache asked the origin again (**expired**) and refreshed its copy. That is the whole idea of web caching in four lines.

What you control, as a developer, is the **response headers**:

- `Cache-Control: public, max-age=3600` means "any cache may keep this for an hour". `private` means "only the user's own browser", never a shared cache. `no-store` means "do not keep it". `no-cache` means "you may keep it but check with me before using it" (a name people get wrong).
- `Vary: Accept-Encoding` means "the response depends on this request header, so the cache key must include it". Without correct `Vary`, a cache can serve a compressed page to a client that cannot read it, or one user's language to another.
- `ETag` / `Last-Modified` let a cache ask "has it changed?" and get a tiny `304 Not Modified` back.
- **Cache key**: by default, usually method plus URL (plus the `Vary` headers). Putting a user id in a query string makes every user a separate cache entry and the hit ratio falls to zero.

> [!warn] **The classic CDN leak: caching a private page.** If an endpoint that returns the *logged-in user's* data is cacheable, the CDN may serve user A's page to user B. This has happened to large companies. Rules: personalised responses must send `Cache-Control: private` or `no-store`; never let the CDN cache anything that depends on a cookie or `Authorization` header unless you are certain of the key; and test with two users.

When you deploy new files, how do you get rid of old cached ones? Two ways: **purge** (an API call to tell the CDN to forget a URL) or **versioned names** (`app.3f9a2c.js`, so a new file has a new URL and the old one can be cached for a year). Versioned names are simpler and more reliable, and are what most frontend build tools produce. For the dynamic API, many teams still use short `max-age`s and `stale-while-revalidate` ideas, but I did not test those here.

CDNs also provide DDoS absorption, a web application firewall (WAF), bot filters, image resizing and edge functions. I list them from general knowledge. I did not read a CDN vendor's docs in this session, so check your provider's documentation for what is available and for the exact header names (they differ by vendor).

## Firewalls and security groups

A firewall decides which packets may pass, by rules on source and destination address, port and protocol, and direction. Cloud **security groups** are firewalls attached to a server or network interface. They are normally **stateful**: if a connection out was allowed, the answer back is allowed automatically. And they are **default deny**: nothing is allowed unless a rule says so.

Good rules for a typical web app:

- Only the load balancer is open to the internet, on ports 80 and 443.
- App servers accept traffic only from the load balancer (a rule that names the balancer's security group, not "anywhere").
- The database accepts traffic only from the app servers on its own port, and never from the internet.
- SSH is limited to a known address or replaced by a managed access tool.
- Restrict *outbound* traffic too where you can. A compromised server that cannot call out is harder to use.

### What a firewall looks like from the client

This part matters for debugging, so I tested it with `iptables` on my machine. A firewall can refuse in two ways:

- **REJECT**: send back an immediate "no" (a TCP reset). The client fails fast.
- **DROP**: say nothing. The client waits for its own timeout.

```text
open port:                       200 in 0.011 s
iptables ... -j REJECT --reject-with tcp-reset
   curl: exit 7  (connection refused)  in 0.0002 s
iptables ... -j DROP
   curl: exit 28 (timed out)           after 4.0 s  (I set -m 4)
nothing listening at all:        curl exit 7 (connection refused), instantly
```

So `connection refused` and a long silent `timed out` mean different things. A refusal says "the machine is up, but nothing is listening on that port (or a firewall actively rejected you)". A timeout says "my packets disappeared": most often a firewall or security group that drops, a wrong IP, or a network route problem. Most cloud security groups use the DROP style, so a forgotten rule shows up as a **hang**, not as an error. I captured both cases with `tcpdump` (full details in lesson 8): refused shows a single reset from the server, and dropped shows the client's SYN being sent again and again about one second apart with no answer at all.

> [!warn] When you run `iptables` or change firewall rules on a machine you are connected to over SSH, a wrong rule can lock you out. I ran my experiments on the loopback interface only and removed the rules right after. Never practise on a remote server you cannot reach physically.

A firewall at the network edge is not a replacement for authentication in the app. A **WAF** (web application firewall) works at layer 7 and tries to block known attack patterns, but it can be bypassed and gives false positives. Treat it as one layer, like in [Security Lesson 0](/security/lesson-0).

2. Alternating: backend 1, 2, 1, 2, 1, 2 (round robin is the default).

## Interview questions

### Q1. What is the difference between a forward proxy and a reverse proxy? (Must know)

A forward proxy acts for the client: the client is configured to send its traffic through it to reach the internet, and the servers see the proxy. A reverse proxy acts for the server: clients think they are talking to the site, but they reach the proxy, which forwards to the backends. In a forward proxy, HTTPS passes as a CONNECT tunnel, so the proxy sees only host and port. I built a tiny one and its log showed the full URL for plain HTTP but only `CONNECT host:port` for HTTPS.

### Q2. What is the difference between an L4 and an L7 load balancer? (Must know)

L4 works on TCP connections. It chooses a backend when a connection opens and copies bytes, so it is fast, protocol-agnostic and cannot see URLs or headers. L7 reads HTTP, so it can route by path or header, add `X-Forwarded-For`, retry a request on another backend, cache and balance per request. In my test the same backends behind HAProxy in tcp mode saw no `X-Forwarded-For`, and in http mode they did. L7 costs more CPU.

### Q3. All of our users seem to come from one IP in the logs, and the rate limiter is blocking everyone. What happened? (Trap)

The app is behind a proxy, so the TCP peer address is the proxy's. The real client address is in `X-Forwarded-For`, and the app needs to read it, but only from trusted proxies. I would configure the framework's trust-proxy setting with the exact number of proxies in front, and take the address that many entries from the right, because the left side can be written by the client. The edge should overwrite or strip any client-supplied header.

### Q4. How would you get the real client IP in a Node app behind two proxies, safely? (Senior signal)

The header is a comma-separated list where each proxy appends the address it saw. With two trusted proxies, the correct client address is the third entry from the right, or equivalently, the last one before my trusted hops. Anything further left was supplied by the client and is untrusted. In my test with the append mode, a client that sent `X-Forwarded-For: 1.2.3.4` produced `1.2.3.4, 127.0.0.1`, so using the first entry would have accepted a forged value. I also make sure the outermost proxy overwrites the header.

### Q5. Explain active versus passive health checks. (Must know)

Passive checks learn from real traffic: when a request to a backend fails, the balancer marks it down for a while and retries elsewhere. Open-source nginx works this way. Active checks are probes the balancer sends on a timer, so it knows about a bad backend before users hit it, and it can bring it back when the probes succeed. In HAProxy I turned `/health` to return 503 while the process was still alive. It marked the server DOWN within about a second and sent no traffic to it. A plain TCP check would have missed that.

### Q6. What should a health check endpoint check? (Senior signal)

The load balancer check should answer "can this instance serve requests right now", for example that the process is up and not overloaded. It should not call every dependency, because a shared database blip would fail every instance at the same time, the balancer would remove them all, and a small problem becomes a full outage. I put dependency checks in a separate endpoint used by monitoring and readiness probes where appropriate, and alert on those.

### Q7. What is the difference between 502, 503 and 504? (Must know)

502 means the proxy got an invalid response from the backend or could not connect to it. 503 means no backend is available or the service is intentionally shedding load. 504 means the backend did not answer within the proxy's timeout. In my lab, a closed backend port gave 502 and a slow backend with a one second timeout gave 504. The first place to debug is the proxy's error log, because for a refused connection the app logs show nothing.

### Q8. Are sticky sessions a good idea? (Senior signal)

Usually they are a workaround. They hide the real problem, which is state stored in a server's memory. They cause uneven load, and the state is lost when that server restarts. I prefer stateless services with sessions in Redis or a database. Sticky routing is justified for things that are tied to a connection, like WebSockets, or a local cache that is expensive to warm. If I must use it, cookie-based stickiness is better than IP hash, because many users share one IP behind NAT. In my test `ip_hash` sent all requests from my one address to one backend.

### Q9. Why can retrying a request at the proxy be dangerous? (Trap)

If the first attempt reached the backend and did the work but was slow, the retry runs it a second time. That can double a payment or an email. In my test a slow endpoint was retried on a second backend after nginx's timeout. Safe retries need the request to be idempotent: either a GET, or a POST with an idempotency key that the server checks. I also keep retries limited, since retries multiply the load on a system that is already struggling.

### Q10. What does a CDN cache, and how do you control it? (Must know)

It caches responses at edge locations near users, keyed by method, URL and the headers named in `Vary`. I control it with response headers: `Cache-Control` with `max-age` or `s-maxage` for how long, `public` or `private` for who may store it, `no-store` for never, and `ETag` for cheap revalidation. For static assets I use fingerprinted file names with a long max-age, so a deploy changes the URL and I never need to purge. In my nginx experiment, with `max-age=5`, the sequence was MISS, HIT, HIT, then EXPIRED after six seconds.

### Q11. What could go wrong if a CDN caches an authenticated page? (Trap)

One user's private data could be served to another user, because the cache key is the URL and the cached copy has nothing to do with who asked. Personalised responses must be `private` or `no-store`, and the CDN must not cache anything keyed on a cookie unless I put the identity into the cache key or `Vary` on purpose. I test it by requesting the same URL as two different users and by checking the cache status header.

### Q12. A request hangs for 30 seconds and then fails. Another fails instantly with "connection refused". What is the likely difference? (Senior signal)

The instant failure means the packet reached a machine that answered with a reset: the host is up, but nothing listens on that port, or something actively rejected it. The long hang means the packets got no answer: a firewall or security group that drops, a wrong IP, or a routing problem. I reproduced both with iptables: REJECT failed in under a millisecond with curl exit code 7, DROP hung until the timeout with exit code 28. In `tcpdump` the dropped case shows the SYN being retried again and again.

### Q13. What is TLS termination and where would you do it? (Must know)

It means the proxy holds the certificate and decrypts the traffic, so the backends receive plain HTTP. I usually do it at the edge (CDN or load balancer) because it centralises certificate renewal and takes the CPU work off the app servers. If the internal network is not trusted, or compliance requires it, I re-encrypt to the backends. The app must then read `X-Forwarded-Proto` from the trusted proxy to know the user used HTTPS, or an "enforce HTTPS" redirect will loop.

### Q14. Why did our WebSocket or long download get cut after exactly 60 seconds? (Senior signal)

A proxy or balancer in the path has an idle or read timeout, often 60 seconds, and it closes connections that look inactive. In my next-lesson test, an nginx location with a 2 second read timeout closed an idle WebSocket after 2 seconds with close code 1006. The fix is to send heartbeats more often than the timeout, and to raise the timeout on the routes that need long connections.

## Key takeaways

- A forward proxy works for clients, a reverse proxy works for servers. HTTPS goes through a forward proxy as a CONNECT tunnel, so the proxy sees only host and port.
- Behind a proxy, the TCP peer is the proxy. The real client IP is in `X-Forwarded-For`, which clients can forge: take the entry that your trusted proxies added, from the right.
- Set `Host` and `X-Forwarded-Proto` on purpose, or the app will see the wrong host name or loop on HTTPS redirects.
- L4 balancers move bytes and are fast. L7 balancers read HTTP and can route, retry and cache.
- Round robin, weights, least connections and hashing are the main algorithms. IP hash is poor behind NAT. Prefer stateless backends over sticky sessions.
- Passive health checks learn from failures. Active checks probe on a timer. Keep the health endpoint shallow.
- 502 is a bad or missing reply, 503 is no capacity, 504 is a timeout. Read the proxy's error log first.
- Retries can repeat actions. Make endpoints idempotent.
- A CDN is a shared cache driven by your response headers. Never let personalised responses be cached by a shared cache.
- Firewalls that REJECT fail fast; firewalls that DROP cause hangs. A hang usually means "blocked", a refusal means "nothing is listening".
