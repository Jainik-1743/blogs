> **In one line:** an LLM bill and an LLM delay both grow with **the number of tokens you send and receive**, so the cheap wins are to send less, answer less, reuse work (caches), use a small model first, and put hard limits on time, retries and spend.

You already know how to call a model ([LLMs, agents and RAG](/fullstack-qa/lesson-10), [Vercel AI SDK](/fullstack-qa/lesson-11)). This lesson is about what happens when real traffic arrives: the bill, the wait, and the failures. I do the arithmetic for one request, explain time to first token and streaming, then cover prompt design, prompt caching, response caching, model routing, batching, timeouts and budgets. At the end I run a small simulation that shows how much a cache and a router can save.

## Words used in this lesson

- **Token:** a small piece of text the model reads or writes. It can be a word, part of a word, or punctuation.
- **Input tokens / output tokens:** tokens you send (the prompt) and tokens the model writes back.
- **Context window:** the maximum number of tokens the model can handle in one call (input plus output). It differs by model and provider.
- **Time to first token (TTFT):** how long until the first piece of the answer arrives.
- **Total time:** how long until the whole answer is finished.
- **Streaming:** the server sends the answer in small pieces as they are made, not all at the end.
- **Prompt (prefix) cache:** the provider reuses its work for the start of a prompt that it has seen before, and usually charges less for it.
- **Response cache:** your own store of finished answers, keyed by the question.
- **Semantic cache:** a response cache that matches questions by meaning (similar), not by exact text.
- **Router:** code that picks which model handles a request.
- **Escalation:** sending a request to a stronger, more expensive model after the cheap one fails or is unsure.
- **Backoff:** waiting longer after each failed try (for example 200 ms, 400 ms, 800 ms). **Jitter** adds a small random amount so many clients do not retry at the same moment.
- **Budget:** a hard limit, per user or per day, on spend or tokens.

## What a token is, and why cost follows it

A model does not read letters or words. A tokenizer program first cuts the text into tokens, and the model works on those. Short common words are often one token. Long or rare words, code, and non-English text are often several tokens. The only safe way to know is to count with the provider's own tokenizer, or to read the counts the API returns with each response.

Providers usually bill **input tokens and output tokens at different rates**, and output tokens usually cost more per token. Some also offer a lower rate for input that was served from a prompt cache. So the shape of the formula is:

```text
cost = (fresh input tokens x input rate)
     + (cached input tokens x cached rate)
     + (output tokens x output rate)
```

The numbers in the formula change by provider and by date. I use **example numbers, not real prices**, in "credits per 1,000 tokens":

| Tier (made up) | Input | Cached input | Output | Time to first token | Time per output token |
|---|---|---|---|---|---|
| small | 1 | 0.1 | 4 | 200 ms | 10 ms |
| large | 10 | 1 | 40 | 600 ms | 30 ms |

Two facts follow from any such table, whatever the real numbers are:

1. **Long prompts cost money on every call.** A 300-token system prompt sent with each request is paid again for each request.
2. **Output is the expensive and slow part.** Each output token costs more and is made one after another. Asking for "a short answer, max 3 sentences" saves both money and time.

For request 2: 6 x 10 / 1000 = 0.06, plus 309 x 1 / 1000 = 0.309, plus 1.12, total 1.489. Note that **output was 26% of the tokens but 26% to 75% of the cost** in these example numbers. And note that in my fake model, the cache changed the **price** but not the **time**. Real providers say that a prefix cache can also reduce time; I did not model that. Check the provider's documentation.

## Time to first token versus total time

Users feel two different delays.

- **Time to first token (TTFT)** is mostly the wait before the model starts. It grows with input length, because the model reads the whole prompt first, and with how busy the provider is.
- **Total time** is TTFT plus (output tokens x time per token). A 500-token answer takes much longer to finish than a 20-token one.

In the fake large tier: 600 ms + 28 tokens x 30 ms = 1,440 ms. If the answer were 500 tokens, it would be 600 + 15,000 = 15,600 ms.

### Streaming

With streaming, you show text as it arrives. The user waits only for TTFT before seeing something, even if the total time is long. This is the biggest *felt* speed-up for chat. It does not reduce cost or total time. It has costs of its own:

- You cannot validate a full JSON answer until it ends. For structured output, either stream only the human text, or buffer.
- You cannot easily run an output check (moderation, schema) on text the user has already seen. Decide what you do if a check fails halfway.
- If the user closes the page, make sure you cancel the model call. Otherwise you pay for output nobody reads.

The Vercel AI SDK has helpers for streaming; see [Lesson 11](/fullstack-qa/lesson-11) rather than repeating them here.

## Prompt design for cost

Before any cache, make the prompt smaller. These are the usual levers:

| Lever | What to do | Watch out for |
|---|---|---|
| Shorter system prompt | Remove repeated rules and long examples; keep what a test shows is needed | Removing a rule that was preventing a failure. Run your evaluation set ([Lesson 2](/ai-engineering/lesson-2)) before and after |
| Retrieval, not stuffing | Fetch the 3 to 5 relevant passages (see [Lesson 35](/fullstack-qa/lesson-35)) instead of pasting the whole manual | Bad retrieval gives wrong answers cheaply |
| Trim history | Keep the last N turns plus a short summary of older ones | Losing a fact the user said early |
| Limit output | Ask for a format and a maximum length; set a maximum output token setting | Cut-off answers; check how your provider reports a cut-off |
| Structured, compact output | Ask for a small JSON, not an essay | Needs validation ([Lesson 4](/ai-engineering/lesson-4)) |

A common mistake is to put the whole knowledge base into every prompt "to be safe". It is slow, costly, can hit the context limit, and often makes answers worse because the relevant part is buried. Retrieval costs a little engineering and saves tokens on every request.

## Prompt (prefix) caching

When many requests start with the same long text (system prompt, tool descriptions, a big shared document), the provider can reuse the work it did on that start. This is **prompt caching** or **prefix caching**. The details (how long entries live, the minimum size, whether you must mark the prefix, the discount) differ by provider. **Check the provider's current documentation.** The shape is the same everywhere I know of, so here is the concept:

- The cache matches the **start** of the prompt, token by token. It is a prefix match. One changed token early on breaks the match for everything after it.
- So build prompts as **stable part first, changing part last**.

```text
GOOD (prefix is the same for every user)
  [system rules][tool descriptions][shared policy text] | [user question]

BAD (a timestamp at the top changes every call, so nothing is reused)
  [Today is 2026-10-11 14:03:22][system rules][tool descriptions] | [user question]
```

What makes a prefix cacheable:

1. **It is byte-for-byte the same** across requests. Watch for timestamps, request ids, user names, random ordering of tools, or a map printed in a different key order.
2. **It is long enough** to be worth it (providers set their own minimum).
3. **It comes first.** Per-user and per-request text goes at the end.
4. **Requests come close enough in time** that the entry has not expired.

Prompt caching saves money (and sometimes time) on the input side only. The model still writes a fresh answer every time. For the second kind of caching, see the next section.

## Response caching

A response cache stores finished answers in your own store (for example Redis, see [Lesson 18](/fullstack-qa/lesson-18)). A hit costs no model call: no tokens, near-zero delay.

### Exact keys

The key is a hash of everything that can change the answer: the **normalized** question, the model id string, the prompt version, and any settings. Normalizing (lowercase, trim spaces, remove filler) raises the hit rate. This is safe because the text you match on is the text you answered.

### Semantic keys

A semantic cache turns the question into an **embedding** (a list of numbers that captures meaning, see [Lesson 35](/fullstack-qa/lesson-35)) and returns a stored answer if a past question is *close enough* (a similarity threshold). "How do I reset my password" and "I forgot my password, how to change it" can share one answer.

This is where risk starts. I did not build a semantic cache in the demo (an embedding needs a real embedding model; a fake would prove nothing about quality). The risks are conceptual:

| Risk | Example | Defence |
|---|---|---|
| **Stale answer** | The refund policy changed, the cache still returns the old text | Short time to live (TTL); include the prompt version and a content version in the key; clear on change |
| **Wrong-user answer** | "What is my balance?" is cached for Ana and returned to Ben | Put the user or tenant id in the key, or never cache answers built from personal data |
| **Near but not same** | "Can I cancel after 30 days?" matches "Can I cancel within 30 days?" and gets the wrong answer | High threshold, test with real pairs, or limit semantic caching to low-risk FAQ |
| **Cache poisoning** | An attacker gets a bad answer stored that others then receive | Only cache answers that passed your output checks; scope the cache per tenant |
| **Leaking private text** | The cache stores prompts that held personal data | Redact before storing ([Lesson 4](/ai-engineering/lesson-4)); set short TTLs |

The demo at the end shows the wrong-user bug with a simple key.

## Model routing

Not every request needs the strongest model. A **router** sends easy requests to a cheap, fast model and uses the strong model only when needed.

Three simple styles:

1. **Rules first:** short question with no risky words goes small; anything with money, legal or medical terms goes large.
2. **Cascade (cheap first, escalate):** ask the small model. If it says it is unsure, or its answer fails a check, ask the large model. You pay for both on escalated requests, so this only wins when most requests stay on the small model.
3. **A classifier:** a small model or a cheap function labels the request, then you choose. Another call is added, so count its cost.

The danger is quality, not money. A router that sends hard questions to the cheap model saves cost and hurts users. So: run your evaluation set per route ([Lesson 2](/ai-engineering/lesson-2)), log which route each request took ([Lesson 4](/ai-engineering/lesson-4)), and watch the escalation rate. If the escalation rate climbs, the cheap model is no longer enough, or the traffic changed.

## Batching

Two different meanings, so be clear which one you mean:

- **Batch many independent jobs into one non-urgent run**, for example labelling 50,000 old tickets overnight. Some providers offer a separate batch interface with a lower price and a longer wait. **Check the provider's documentation** for whether and how. Use it for work no user is waiting for.
- **Put several small items in one prompt** ("classify these 20 titles") to share the instruction text. It saves repeated input tokens. The risks: one bad item can confuse the others, the output is longer, and one failure fails the whole batch. Validate every item.

For live chat, neither helps much. The live-chat savings come from caching, routing and short prompts.

## Timeouts, retries and budgets

Model calls are slow and sometimes fail. Three controls keep that from becoming an outage or a surprise bill.

**Timeouts.** Set one for each attempt **and** one total deadline for the request. The attempt timeout must be shorter than the total deadline, or the deadline cannot work (my demo shows this mistake on purpose).

**Retries with backoff.** Retry only errors that may go away: overloaded, timeout, rate-limited. Do **not** retry a bad request, because the same input fails again. Wait longer after each failure and add jitter. Cap the number of attempts. Each retry costs tokens if the first try did any work, and many clients retrying together make an overload worse.

**Budgets.** Limit what one user, one tenant and the whole app can spend per day. Check *before* the call with an estimate (input tokens are known; output is capped by your setting), and record the *real* cost after. This ties to "unbounded consumption" in [Lesson 0](/ai-engineering/lesson-0), LLM10. Also cap the number of agent steps and the output size per call.

## Build it: a cache and a router, with numbers

The file below has the fake model, a whitespace tokenizer (stand-in), the example price table, and five ways to serve the same 200 requests. The traffic is only 8 distinct questions in different casing, repeated, so it is **very repetitive on purpose**. The small tier says `UNSURE` for questions with words such as refund, legal, contract, dispute. That rule is my fake stand-in for "the cheap model cannot handle this". It is not how real models behave.

`cost.ts` (run with `node cost.ts`; Node 22 strips the types itself):

```ts
// Stand-in tokenizer: one token per whitespace-separated word.
// Real tokenizers split text differently (often into sub-word pieces).
const countTokens = (text: string): number =>
  text.trim() === "" ? 0 : text.trim().split(/\s+/).length;

// EXAMPLE NUMBERS, NOT REAL PRICES. Units: "credits" per 1,000 tokens.
type Tier = { name: string; inPer1k: number; outPer1k: number; cachedInPer1k: number;
              msToFirstToken: number; msPerOutToken: number };
const SMALL: Tier = { name: "small", inPer1k: 1, outPer1k: 4, cachedInPer1k: 0.1, msToFirstToken: 200, msPerOutToken: 10 };
const LARGE: Tier = { name: "large", inPer1k: 10, outPer1k: 40, cachedInPer1k: 1, msToFirstToken: 600, msPerOutToken: 30 };

type Usage = { inTok: number; cachedTok: number; outTok: number; cost: number; ms: number; ttft: number };

// Fake model. Deterministic. "Answer quality" is a rule: the small tier only
// handles questions that contain no word from HARD_WORDS; otherwise it says UNSURE.
const HARD_WORDS = ["refund", "legal", "contract", "dispute"];
class FakeModel {
  private prefixSeen = new Set<string>(); // prefixes the "provider" has cached
  calls = 0;
  tier: Tier;
  constructor(tier: Tier) { this.tier = tier; }
  call(prefix: string, question: string): { text: string; unsure: boolean; usage: Usage } {
    this.calls++;
    const prefixTok = countTokens(prefix);
    const qTok = countTokens(question);
    const cached = this.prefixSeen.has(prefix) ? prefixTok : 0;
    this.prefixSeen.add(prefix);
    const hard = HARD_WORDS.some((w) => question.toLowerCase().includes(w));
    const unsure = this.tier.name === "small" && hard;
    const text = unsure ? "UNSURE" : `Answer (${this.tier.name}) to: ${question.trim().split(/\s+/).slice(0, 4).join(" ")} ... ` + "word ".repeat(20).trim();
    const inTok = prefixTok + qTok;
    const outTok = countTokens(text);
    const cost = ((inTok - cached) * this.tier.inPer1k + cached * this.tier.cachedInPer1k + outTok * this.tier.outPer1k) / 1000;
    const ttft = this.tier.msToFirstToken;
    return { text, unsure, usage: { inTok, cachedTok: cached, outTok, cost, ttft, ms: ttft + outTok * this.tier.msPerOutToken } };
  }
}

// ---- Part 1: arithmetic for one request ----
const SYSTEM = ("You are a support assistant. Be short and polite. " + "Policy line. ".repeat(150)).trim();
const q0 = "How do I reset my password";
{
  const m = new FakeModel(LARGE);
  const a = m.call(SYSTEM, q0).usage;
  const b = m.call(SYSTEM, q0).usage;
  console.log("tokens: system", countTokens(SYSTEM), "question", countTokens(q0));
  console.log("request 1 (cold prefix):", a);
  console.log("request 2 (warm prefix):", b);
}

// ---- Part 2: traffic and strategies ----
const base = ["How do I reset my password", "Where is my invoice", "How do I change my email", "Can I get a refund for last month",
  "I want to dispute a charge", "What are your opening hours", "How do I delete my account", "Explain the contract terms"];
const traffic: string[] = [];
for (let i = 0; i < 200; i++) {
  const q = base[(i * 7 + (i >> 2)) % base.length]; // deterministic, repeated mix
  traffic.push(i % 5 === 0 ? q.toLowerCase() + " please" : i % 3 === 0 ? q.toUpperCase() : q);
}

type Report = { name: string; cost: number; avgMs: number; modelCalls: number };
const report = (name: string, cost: number, ms: number, calls: number): Report =>
  ({ name, cost: +cost.toFixed(2), avgMs: Math.round(ms / traffic.length), modelCalls: calls });

// A: always the large model, no cache
function runA(): Report {
  const m = new FakeModel(LARGE); let c = 0, t = 0;
  for (const q of traffic) { const r = m.call(SYSTEM, q); c += r.usage.cost; t += r.usage.ms; }
  return report("A large, prefix cache only", c, t, m.calls);
}
// B: exact-match response cache (key = exact string)
function runB(): Report {
  const m = new FakeModel(LARGE); const cache = new Map<string, string>(); let c = 0, t = 0;
  for (const q of traffic) {
    if (cache.has(q)) { t += 1; continue; }
    const r = m.call(SYSTEM, q); cache.set(q, r.text); c += r.usage.cost; t += r.usage.ms;
  }
  return report("B + exact response cache", c, t, m.calls);
}
// C: normalized key (lowercase, strip 'please', collapse spaces). Still exact, just cleaner.
const norm = (q: string) => q.toLowerCase().replace(/\bplease\b/g, "").replace(/\s+/g, " ").trim();
function runC(): Report {
  const m = new FakeModel(LARGE); const cache = new Map<string, string>(); let c = 0, t = 0;
  for (const q of traffic) {
    const k = norm(q);
    if (cache.has(k)) { t += 1; continue; }
    const r = m.call(SYSTEM, q); cache.set(k, r.text); c += r.usage.cost; t += r.usage.ms;
  }
  return report("C + normalized key", c, t, m.calls);
}
// D: C plus a router: small first, escalate to large when small says UNSURE
function runD(): Report {
  const small = new FakeModel(SMALL), large = new FakeModel(LARGE);
  const cache = new Map<string, string>(); let c = 0, t = 0;
  for (const q of traffic) {
    const k = norm(q);
    if (cache.has(k)) { t += 1; continue; }
    let r = small.call(SYSTEM, q); c += r.usage.cost; t += r.usage.ms;
    if (r.unsure) { r = large.call(SYSTEM, q); c += r.usage.cost; t += r.usage.ms; }
    cache.set(k, r.text);
  }
  return report("D + router (small first)", c, t, small.calls + large.calls);
}
// E: router with NO cache, to show the router alone
function runE(): Report {
  const small = new FakeModel(SMALL), large = new FakeModel(LARGE); let c = 0, t = 0, esc = 0;
  for (const q of traffic) {
    let r = small.call(SYSTEM, q); c += r.usage.cost; t += r.usage.ms;
    if (r.unsure) { esc++; r = large.call(SYSTEM, q); c += r.usage.cost; t += r.usage.ms; }
  }
  console.log("router only: escalations", esc, "of", traffic.length);
  return report("E router only, no response cache", c, t, small.calls + large.calls);
}
console.table([runA(), runB(), runC(), runE(), runD()]);

// ---- Part 3: wrong-user risk with a cache key that forgets the user ----
const cacheBad = new Map<string, string>();
const answerFor = (user: string, q: string) => `Your balance is ${user === "ana" ? 120 : 9} (for ${user}) -- ${q}`;
function badLookup(user: string, q: string) { const k = norm(q); if (!cacheBad.has(k)) cacheBad.set(k, answerFor(user, q)); return cacheBad.get(k)!; }
console.log("bad key, ana :", badLookup("ana", "What is my balance"));
console.log("bad key, ben :", badLookup("ben", "what is my balance"));
const cacheOk = new Map<string, string>();
function okLookup(user: string, q: string) { const k = user + "|" + norm(q); if (!cacheOk.has(k)) cacheOk.set(k, answerFor(user, q)); return cacheOk.get(k)!; }
console.log("good key, ben:", okLookup("ben", "what is my balance"));
```

### Retries, backoff, deadline and budget

`retry.ts` uses a simulated clock (no real waiting) and a fake model that follows a script:

```ts
// Simulated clock: no real waiting, so the run is instant and repeatable.
let now = 0;
const sleep = (ms: number) => { now += ms; };

class ProviderError extends Error {
  retryable: boolean;
  constructor(msg: string, retryable: boolean) { super(msg); this.retryable = retryable; }
}

// Fake model: fails with a scripted pattern, then answers. Each call takes 300 ms.
function makeFake(script: Array<"ok" | "overloaded" | "badrequest" | "slow">) {
  let i = 0;
  return () => {
    const step = script[Math.min(i++, script.length - 1)];
    if (step === "slow") { sleep(5000); throw new ProviderError("timeout after 5000 ms", true); }
    sleep(300);
    if (step === "overloaded") throw new ProviderError("overloaded", true);
    if (step === "badrequest") throw new ProviderError("bad request", false);
    return "answer";
  };
}

// Deterministic "jitter" (a real one uses Math.random()).
const jitter = (n: number) => (n * 37) % 50;

function callWithRetry(fn: () => string, o: { maxAttempts: number; baseMs: number; deadlineMs: number }) {
  const start = now;
  for (let attempt = 1; ; attempt++) {
    try { return { ok: true, value: fn(), attempt, spent: now - start }; }
    catch (e) {
      const err = e as ProviderError;
      const wait = o.baseMs * 2 ** (attempt - 1) + jitter(attempt);
      const outOfTime = now - start + wait > o.deadlineMs;
      console.log(`  attempt ${attempt} failed: ${err.message}; retryable=${err.retryable}; next wait ${wait} ms; elapsed ${now - start} ms`);
      if (!err.retryable || attempt >= o.maxAttempts || outOfTime) return { ok: false, value: err.message, attempt, spent: now - start };
      sleep(wait);
    }
  }
}

const opts = { maxAttempts: 4, baseMs: 200, deadlineMs: 3000 };
console.log("case 1: two overloads then success");
console.log(callWithRetry(makeFake(["overloaded", "overloaded", "ok"]), opts));
console.log("case 2: bad request is not retried");
console.log(callWithRetry(makeFake(["badrequest", "ok"]), opts));
console.log("case 3: slow calls hit the overall deadline");
console.log(callWithRetry(makeFake(["slow", "slow", "ok"]), opts));

// Per-user daily budget (credits). Check BEFORE the call with an estimate, record AFTER with the real cost.
const spent = new Map<string, number>();
function withBudget(user: string, estimate: number, limit: number, run: () => number) {
  const used = spent.get(user) ?? 0;
  if (used + estimate > limit) return `refused: ${user} used ${used.toFixed(1)} of ${limit}`;
  const real = run();
  spent.set(user, used + real);
  return `ok: ${user} now at ${(used + real).toFixed(1)} of ${limit}`;
}
for (let i = 0; i < 4; i++) console.log(withBudget("ana", 3, 10, () => 3.4));
```

```text
case 1: two overloads then success
  attempt 1 failed: overloaded; retryable=true; next wait 237 ms; elapsed 300 ms
  attempt 2 failed: overloaded; retryable=true; next wait 424 ms; elapsed 837 ms
{ ok: true, value: 'answer', attempt: 3, spent: 1561 }
case 2: bad request is not retried
  attempt 1 failed: bad request; retryable=false; next wait 237 ms; elapsed 300 ms
{ ok: false, value: 'bad request', attempt: 1, spent: 300 }
case 3: slow calls hit the overall deadline
  attempt 1 failed: timeout after 5000 ms; retryable=true; next wait 237 ms; elapsed 5000 ms
{ ok: false, value: 'timeout after 5000 ms', attempt: 1, spent: 5000 }
ok: ana now at 3.4 of 10
ok: ana now at 6.8 of 10
ok: ana now at 10.2 of 10
refused: ana used 10.2 of 10
```

Three lessons from the output:

- Case 1: two overloads, then success on attempt 3, after 1,561 simulated ms. The waits were 237 and 424 ms (base x 2^n plus a fixed stand-in for jitter).
- Case 2: a bad request is not retried. Retrying would only waste money.
- Case 3 is a **bug I left in on purpose**. The first attempt took 5,000 ms, which is longer than the whole 3,000 ms deadline, because I never gave the attempt its own timeout. The retry loop stopped, but only after the damage. Fix: give each attempt a timeout smaller than the remaining deadline.
- The budget check let `ana` reach 10.2 of 10, because the estimate (3) was lower than the real cost (3.4). Budgets based on estimates can overshoot a little. Use a conservative estimate, or a hard stop mid-stream.

## Try it

1. A prompt has 2,000 input tokens and the answer has 300. Using the example "large" rates in this lesson (10 in, 40 out per 1,000), what is the cost?
2. Your prompt starts with `Current time: <ISO timestamp>`. Why does your prompt cache never hit, and what is the fix?
3. You add a semantic cache for "What is my order status?". What can go wrong, and what do you add to the key?
4. Your router sends 80% of requests to the small tier and 20% escalate. Each small call costs 1 unit, each large call costs 10. Cost per 100 requests versus all-large?

**Answers.**

1. Input: 2,000 x 10 / 1000 = 20. Output: 300 x 40 / 1000 = 12. Total 32 credits. Output is 15% of tokens and 37.5% of the cost.
2. The timestamp changes every call, so no two prompts share a prefix. Move it to the end (or drop it, or round it to the day if the answer does not need seconds).
3. It can return Ana's order status to Ben. Include the user or tenant id in the key, or do not cache personal answers at all. Also add a short TTL, since order status changes.
4. In a cascade every request first goes to the small model: 100 x 1 = 100. The 20 that escalate also cost 20 x 10 = 200. Total 300, versus 1,000 for all-large. If the small model had to be called for all and 60% escalated, it would be 100 + 600 = 700, still less, but the margin shrinks as escalation grows.

## Interview questions

### Q1. Why does an LLM feature cost more as prompts grow? (Must know)

Because providers bill by tokens, input and output, usually at different rates. A long system prompt is paid again on every request. Output tokens usually cost more and are produced one at a time, so they also drive the wait. So I look at tokens per request first: shorten the prompt, retrieve only the relevant passages, cap output length. I take real prices from the provider's current documentation, not from memory.

### Q2. What is the difference between time to first token and total time? (Must know)

TTFT is the wait before output starts. It grows with input size and provider load. Total time adds the time to write every output token, so it grows with answer length. Streaming improves the *felt* delay because users see text after TTFT, but it does not lower cost or total time.

### Q3. What makes a prompt prefix cacheable? (Must know)

The start of the prompt must be identical, token for token, across requests, and long enough for the provider's minimum. Stable content (rules, tool descriptions, shared documents) goes first, and anything that changes (timestamp, user name, question) goes last. One early change breaks the match for everything after it. Exact rules, lifetimes and discounts depend on the provider, so I check its documentation.

### Q4. How is a response cache different from a prompt cache? (Must know)

A prompt cache is the provider's: it saves work on the input and still generates a new answer. A response cache is mine: it stores finished answers and skips the model call completely, so cost and delay are near zero on a hit. The response cache brings correctness risks (stale, wrong-user) that a prompt cache does not.

### Q5. How would you design the key for an LLM response cache? (Senior signal)

Hash the normalized input plus everything that changes the output: model id string, prompt version, settings, and a content or data version. Add the user or tenant id unless the answer is truly public. Add a TTL. Only store answers that passed output validation. I would also log hit rate so I can see if it is worth keeping.

**Follow-up: "Would you use a semantic cache?"** Only for low-risk, public, FAQ-style questions, with a high similarity threshold tested on real pairs, because near-duplicate questions can need different answers.

### Q6. What can go wrong with a semantic cache? (Senior signal)

A stale answer after a policy change. A wrong-user answer if personal data is in the cached text. A near-match that is not the same question (30 days versus within 30 days). Poisoning, where a bad answer is stored and served to others. I reduce these with scoped keys, short TTLs, high thresholds, and storing only validated answers.

### Q7. How would you do model routing, and how do you know it is safe? (Senior signal)

Start with rules or a cheap-first cascade: the small model answers, and the request escalates if the model is unsure or a check fails. I evaluate each route on a fixed test set before launch, log the route per request, and watch the escalation rate and the user feedback by route. If the escalation rate rises, the small route is failing more often, and the cascade also pays for both calls on those requests.

### Q8. Which errors do you retry, and how? (Must know)

Only errors that may be temporary: timeouts, overload, rate limits. Not bad requests or validation failures of my own input. I use exponential backoff with jitter, a maximum number of attempts, a per-attempt timeout and a total deadline. I also remember that retries can cost tokens and, when many clients retry together, make an overload worse.

### Q9. How do you stop one user from running up the bill? (Must know)

Per-user and per-tenant daily budgets in tokens or credits, checked before the call with an estimate and updated after with the real number. Caps on input size, output size and agent steps. A rate limit per user. An alert on app-wide spend, and a kill switch ([Lesson 4](/ai-engineering/lesson-4)) for emergencies.

### Q10. Streaming makes your feature feel faster. What does it make harder? (Senior signal)

Checks that need the full answer. I cannot validate a whole JSON object or run output moderation before the user sees the start. So for structured output I buffer, and for chat I decide in advance what happens when a late check fails (replace the message, show a notice). I also cancel the model call when the user leaves, so I do not pay for unread text.

### Q11. Your costs doubled this week and traffic did not. How do you investigate? (Trap)

The trap is blaming the provider. I look at my own logs: average input and output tokens per request, by prompt version and route. Typical causes are a longer prompt after a release, a lower cache hit rate (a changed prefix, a new timestamp), a router escalating more, a retry storm, or one user or bot. I need per-request token counts and cost logged to answer this ([Lesson 4](/ai-engineering/lesson-4)).

### Q12. Is batching good for a chat feature? (Trap)

Mostly no. Batch interfaces and multi-item prompts help with offline, non-urgent jobs. In live chat the user waits, so I rely on short prompts, prefix caching, response caching and routing instead.

## Key takeaways

- Cost and delay follow tokens. Input and output are billed differently, and output is usually the slower, pricier part.
- Count tokens with the provider's tokenizer, and take prices from the provider's current documentation. My whitespace tokenizer and prices in this lesson are stand-ins.
- Shorten prompts and retrieve instead of stuffing before you add any cache.
- Put stable text first and changing text last so a prefix can be cached.
- Response caches need careful keys (user, prompt version, content version), TTLs, and validated answers only.
- Route cheap first, escalate when unsure, and measure quality per route.
- Set a per-attempt timeout, a total deadline, capped retries with backoff and jitter, and per-user budgets.
- Measure your own hit rate and escalation rate. The demo's savings came from repetitive made-up traffic.
