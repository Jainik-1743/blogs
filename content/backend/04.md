> **In one line:** separate **operational errors** (the world misbehaved: bad input, a timeout, a missing row) from **programmer errors** (a bug). Handle the first kind gracefully and consistently; for the second, log it loudly and let the process restart. And never lie to the client about which one happened.

Error handling is where backend code reveals its maturity. A frontend developer is used to `try/catch` around a `fetch`. A backend must decide, for every failure, *what the client sees, what the logs record, and whether the process is still trustworthy*.

## Two kinds of errors

| | Operational error | Programmer error |
|---|---|---|
| **What it is** | A run-time problem in a correct program | A bug in the code |
| **Examples** | Invalid input, record not found, DB connection refused, upstream timeout, disk full, rate limit exceeded | `undefined is not a function`, reading a property of `null`, wrong argument type, an off-by-one, forgetting to `await` |
| **Expected?** | Yes: it will happen eventually | No: it should never happen |
| **Recoverable?** | Often: retry, fall back, report to the user | Not safely: the process may be in an unknown state |
| **Right response** | Handle, map to an HTTP status, log at `warn`/`info` | Log at `error`/`fatal` with the stack, return a generic `500`, **restart the process** |

Why the distinction matters: if you "handle" a programmer error by catching it and carrying on, you keep running with possibly corrupted state (half-updated objects, leaked locks). The Node.js guidance is to treat these as reasons to **crash and restart** under a process manager.

## Typed errors

Use classes so the rest of the system can tell errors apart without parsing messages:

```ts
export class AppError extends Error {
  readonly isOperational = true;
  constructor(
    message: string,
    readonly status: number,
    readonly code: string,
    options?: { cause?: unknown; details?: unknown },
  ) {
    super(message, { cause: options?.cause });
    this.name = new.target.name;
    this.details = options?.details;
    Error.captureStackTrace?.(this, new.target);
  }
  details?: unknown;
}

export class ValidationError extends AppError { constructor(msg: string, details?: unknown) { super(msg, 422, "VALIDATION_FAILED", { details }); } }
export class UnauthorizedError extends AppError { constructor(msg = "Authentication required") { super(msg, 401, "UNAUTHORIZED"); } }
export class ForbiddenError extends AppError { constructor(msg = "Not allowed") { super(msg, 403, "FORBIDDEN"); } }
export class NotFoundError extends AppError { constructor(what = "Resource") { super(`${what} not found`, 404, "NOT_FOUND"); } }
export class ConflictError extends AppError { constructor(msg: string, code = "CONFLICT") { super(msg, 409, code); } }
export class TooManyRequestsError extends AppError { constructor(readonly retryAfterSeconds: number) { super("Too many requests", 429, "RATE_LIMITED"); } }
```

Notes:

- The **`cause`** option (supported by modern Node) keeps the original error attached when you wrap it, so logs show the full chain: "Could not create order" caused by "unique constraint failed".
- Domain code throws `NotFoundError`, **not** `res.status(404)`. Only the HTTP layer knows about status codes ([Lesson 01](/backend/lesson-1)).

## One central error handler

Do not scatter `res.status(...).json(...)` in every controller. Throw, and translate in **one** place:

```ts
import type { ErrorRequestHandler } from "express";
import { AppError } from "../shared/errors";
import { logger } from "../lib/logger";

export const errorHandler: ErrorRequestHandler = (err, req, res, _next) => {
  // If headers already went out (streaming), delegate to Express' default handler
  if (res.headersSent) return _next(err);

  const requestId = req.id; // set by a request-id middleware

  if (err instanceof AppError) {
    logger.warn({ err, requestId, code: err.code }, "operational error");
    if (err instanceof TooManyRequestsError) res.set("Retry-After", String(err.retryAfterSeconds));
    return res.status(err.status).type("application/problem+json").json({
      type: `https://api.example.com/errors/${err.code.toLowerCase()}`,
      title: err.message,
      status: err.status,
      code: err.code,
      requestId,
      ...(err.details ? { errors: err.details } : {}),
    });
  }

  // Anything else is unexpected: log everything, tell the client nothing
  logger.error({ err, requestId, path: req.path }, "unhandled error");
  res.status(500).type("application/problem+json").json({
    type: "https://api.example.com/errors/internal",
    title: "Something went wrong",
    status: 500,
    code: "INTERNAL",
    requestId, // lets the user quote it to support
  });
};
```

It is registered **last** (`app.use(errorHandler)` after all routes). An error-handling middleware has **four** parameters; Express identifies it by that arity.

**Never** send `err.stack`, SQL text, file paths or the internal message of an unexpected error to the client. That is an information leak (and a free reconnaissance gift to an attacker).

## Async errors: Express 5 vs Express 4

This is a frequent interview question.

- **Express 5:** route handlers and middleware that return a **promise** automatically forward a rejection (or a thrown error in an `async` function) to `next(err)`. You can write handlers naturally:

```ts
// Express 5: works as written. The thrown NotFoundError reaches errorHandler.
app.get("/orders/:id", async (req, res) => {
  const order = await orders.get(req.params.id);   // throws NotFoundError
  res.json(order);
});
```

- **Express 4:** a rejected promise inside an `async` handler is **not** caught by Express. It becomes an **unhandled rejection**, the request hangs, and on current Node versions an unhandled rejection **terminates the process**. You must wrap handlers:

```ts
// Express 4 only
const asyncHandler = (fn: RequestHandler): RequestHandler => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);
app.get("/orders/:id", asyncHandler(async (req, res) => { /* ... */ }));
```

(or use the `express-async-errors` patch). Synchronous throws inside a handler were already caught in both versions; the difference is promises. If you are on 4, plan the upgrade.

## Process-level safety nets

Some errors escape every `try/catch`: a rejected promise nobody awaited, an exception inside an event callback.

```ts
process.on("unhandledRejection", (reason) => {
  logger.fatal({ err: reason }, "unhandledRejection");
  shutdown(1);
});
process.on("uncaughtException", (err) => {
  logger.fatal({ err }, "uncaughtException");
  shutdown(1);
});

function shutdown(code: number) {
  // Stop accepting new connections, finish in-flight requests, close DB; then exit
  server.close(() => prisma.$disconnect().finally(() => process.exit(code)));
  setTimeout(() => process.exit(code), 10_000).unref(); // hard deadline
}
process.on("SIGTERM", () => shutdown(0)); // sent by Kubernetes/ECS/systemd on deploy
```

**Should you catch `uncaughtException` and keep running?** No. After an uncaught exception the process is in an undefined state. Log it, **exit**, and let a supervisor (PM2, systemd, Kubernetes, ECS) start a fresh instance. This only works well if you run **more than one instance** behind a load balancer and handle in-flight requests with a graceful shutdown.

## Mapping infrastructure errors

Translate low-level failures to your domain at the boundary (usually the repository):

```ts
import { Prisma } from "@prisma/client";

export async function createUser(data: { email: string; name: string }) {
  try {
    return await prisma.user.create({ data });
  } catch (e) {
    if (e instanceof Prisma.PrismaClientKnownRequestError) {
      if (e.code === "P2002") throw new ConflictError("Email already registered", "EMAIL_TAKEN", ); // unique constraint
      if (e.code === "P2025") throw new NotFoundError("User");                                          // record not found
    }
    throw e; // unknown: let it bubble as an unexpected error
  }
}
```

- Unique violation → `409`. Foreign-key violation → usually `422`/`409`. Not found → `404`.
- A **timeout or connection error** from a dependency is operational but not the client's fault: `502`/`503`/`504`, ideally with `Retry-After`, and retried internally if the operation is idempotent.
- Wrap and add context, **keeping the cause**: `throw new AppError("Could not charge card", 502, "PAYMENT_UNAVAILABLE", { cause: e })`.

## Retries, timeouts and not hanging forever

- **Always set timeouts** on outbound calls (HTTP, database, queue). A missing timeout turns a slow dependency into exhausted connections everywhere.
- **Retry only transient failures** (network blips, `429`, `503`) and only **idempotent** operations, with **exponential backoff and jitter** ([Practical Design Problems, Lesson 07](/design-problems/lesson-7)).
- Use a **circuit breaker** around flaky dependencies so you fail fast instead of piling up requests.
- `Promise.all` fails fast on the first rejection and leaves the others running; use `Promise.allSettled` when partial success is acceptable.

```ts
const results = await Promise.allSettled([sendEmail(), updateCrm(), notifySlack()]);
for (const r of results) if (r.status === "rejected") logger.warn({ err: r.reason }, "non-critical side effect failed");
```

## Common mistakes

1. **Swallowing errors** (`catch (e) {}`) or logging and continuing as if nothing happened.
2. **Leaking internals** (stack traces, SQL, file paths) to clients.
3. **Returning `200`** on failure, or `500` for client mistakes.
4. **Inconsistent error shapes** across endpoints.
5. **Using `throw "string"`** or throwing non-`Error` values, which lose the stack trace.
6. **`catch` and rethrow without the cause**, destroying the root problem.
7. **Handling a programmer error and continuing**, instead of crashing cleanly.
8. **No timeouts** on outbound calls; **no graceful shutdown**.
9. **Logging the same error at every layer**, producing noise. Log once, where you handle it.

## Interview questions

### Q1. Operational vs programmer error?

Operational errors are expected run-time conditions in a correct program (bad input, missing record, timeouts, connection failures); handle them, map them to proper status codes and often retry. Programmer errors are bugs (null dereference, wrong types); you cannot safely recover, so log with full detail and restart the process. The distinction determines whether you handle or crash.

### Q2. How does Express 5 handle a rejected async handler?

Express 5 detects that the handler returned a promise and, if it rejects or an async function throws, automatically calls `next(err)`, sending the error to your error-handling middleware. In Express 4 the rejection is unhandled: the request hangs and, on current Node, can crash the process, so you need an async wrapper.

### Q3. Should you catch `uncaughtException` and keep running?

No. The process may be in an inconsistent state. Log it, start a graceful shutdown (stop accepting connections, finish in-flight requests, close resources) and exit, relying on a process manager or orchestrator to start a clean instance, with multiple instances so users are not impacted.

### Q4. Scenario: errors leak stack traces to clients. Fix it.

Introduce a central error-handling middleware that distinguishes known `AppError`s (translated to a status, stable code and safe message) from unexpected errors (generic `500` with a request ID). Log the full error with stack server-side. Set `NODE_ENV=production`, remove any `res.send(err)`-style code and add a test that asserts no stack appears in responses.

### Q5. How do you design error classes?

A base `AppError` carrying `status`, `code`, safe `message`, optional `details` and the original `cause`, with subclasses (`NotFoundError`, `ConflictError`, `ValidationError`). Domain and repository code throw them; one central handler maps them to the HTTP response. Clients switch on `code`, never on message text.

### Q6. Why log the error once?

Logging at every layer on the way up creates duplicate entries that hide the real count and cause. Log at the point where the error is handled (typically the central handler) with full context and the correlation ID, and let intermediate layers add context via `cause` instead.

### Q7. When do you retry a failed operation?

Only when the failure is transient (timeouts, connection resets, `429`, `503`) and the operation is idempotent or protected by an idempotency key. Use bounded attempts with exponential backoff and jitter, respect `Retry-After`, set timeouts and consider a circuit breaker so retries do not amplify an outage.

### Q8. What does a graceful shutdown involve?

On `SIGTERM`: stop accepting new connections (and fail the readiness check), let in-flight requests finish within a deadline, close the database and queue connections, flush logs, then exit. A hard timeout forces exit if something hangs. This prevents dropped requests during deploys and restarts.

## Key takeaways

- **Operational errors: handle and report. Programmer errors: log and restart.**
- Use **typed errors** with `status`, stable `code` and `cause`; throw domain errors, translate to HTTP in **one** central handler.
- **Express 5 forwards async rejections automatically**; Express 4 needs a wrapper.
- Never leak internals; return a **request ID** instead.
- Set **timeouts**, retry only idempotent transient failures with backoff and jitter, and shut down gracefully.
