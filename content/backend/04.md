> **In one line:** keep two kinds of errors apart. **Operational errors** happen because the world misbehaves (bad input, a timeout, a missing row). **Programmer errors** are bugs. Handle the first kind calmly and in the same way every time. For the second kind, log it loudly and let the process restart. And never lie to the client about which one happened.

Error handling shows how mature backend code is. A frontend developer is used to `try/catch` around a `fetch`. A backend must decide, for every failure, *what the client sees, what the logs record, and whether the process can still be trusted*.

## Two kinds of errors

| | Operational error | Programmer error |
|---|---|---|
| **What it is** | A problem at run time in a correct program | A bug in the code |
| **Examples** | Invalid input, record not found, database connection refused, timeout from another service, disk full, rate limit exceeded | `undefined is not a function`, reading a property of `null`, wrong argument type, an off-by-one mistake, forgetting to `await` |
| **Expected?** | Yes: it will happen sooner or later | No: it should never happen |
| **Recoverable?** | Often: retry, use a fallback, tell the user | Not safely: the process may be in an unknown state |
| **Right response** | Handle it, map it to an HTTP status, log at `warn`/`info` | Log at `error`/`fatal` with the stack, return a generic `500`, **restart the process** |

Why does this matter? Say you catch a programmer error and carry on. Your program keeps running with data that may be broken (half-updated objects, locks that are never released). Node.js guidance says to treat these as a reason to **crash and restart** under a process manager (a tool that restarts your app when it stops).

## Typed errors

Use classes, so the rest of the system can tell errors apart without reading the message text:

```ts
export class AppError extends Error {
  readonly isOperational = true;
  constructor(
    message: string,
    readonly status: number,
    readonly code: string,
    options?: { cause?: unknown; details?: unknown },
  ) {
    super(message, { cause: options?.cause });
    this.name = new.target.name;
    this.details = options?.details;
    Error.captureStackTrace?.(this, new.target);
  }
  details?: unknown;
}

export class ValidationError extends AppError { constructor(msg: string, details?: unknown) { super(msg, 422, "VALIDATION_FAILED", { details }); } }
export class UnauthorizedError extends AppError { constructor(msg = "Authentication required") { super(msg, 401, "UNAUTHORIZED"); } }
export class ForbiddenError extends AppError { constructor(msg = "Not allowed") { super(msg, 403, "FORBIDDEN"); } }
export class NotFoundError extends AppError { constructor(what = "Resource") { super(`${what} not found`, 404, "NOT_FOUND"); } }
export class ConflictError extends AppError { constructor(msg: string, code = "CONFLICT") { super(msg, 409, code); } }
export class TooManyRequestsError extends AppError { constructor(readonly retryAfterSeconds: number) { super("Too many requests", 429, "RATE_LIMITED"); } }
```

Notes:

- The **`cause`** option (supported by modern Node) keeps the original error attached when you wrap it. The logs then show the whole chain. For example: "Could not create order", caused by "unique constraint failed".
- Domain code throws `NotFoundError`. It does **not** call `res.status(404)`. Only the HTTP layer knows about status codes ([Lesson 01](/backend/lesson-1)).

## One central error handler

Do not scatter `res.status(...).json(...)` in every controller. Throw the error, and turn it into a response in **one** place:

```ts
import type { ErrorRequestHandler } from "express";
import { AppError } from "../shared/errors";
import { logger } from "../lib/logger";

export const errorHandler: ErrorRequestHandler = (err, req, res, _next) => {
  // If headers already went out (streaming), delegate to Express' default handler
  if (res.headersSent) return _next(err);

  const requestId = req.id; // set by a request-id middleware

  if (err instanceof AppError) {
    logger.warn({ err, requestId, code: err.code }, "operational error");
    if (err instanceof TooManyRequestsError) res.set("Retry-After", String(err.retryAfterSeconds));
    return res.status(err.status).type("application/problem+json").json({
      type: `https://api.example.com/errors/${err.code.toLowerCase()}`,
      title: err.message,
      status: err.status,
      code: err.code,
      requestId,
      ...(err.details ? { errors: err.details } : {}),
    });
  }

  // Anything else is unexpected: log everything, tell the client nothing
  logger.error({ err, requestId, path: req.path }, "unhandled error");
  res.status(500).type("application/problem+json").json({
    type: "https://api.example.com/errors/internal",
    title: "Something went wrong",
    status: 500,
    code: "INTERNAL",
    requestId, // lets the user quote it to support
  });
};
```

Register it **last** (`app.use(errorHandler)` after all routes). An error-handling middleware has **four** parameters. Express knows it is an error handler because of that number (this is called its "arity").

**Never** send `err.stack`, SQL text, file paths or the internal message of an unexpected error to the client. That leaks information, and it gives an attacker free clues.

## Async errors: Express 5 vs Express 4

Interviewers often ask about this.

- **Express 5:** if a route handler or middleware returns a **promise**, Express sends a rejection to `next(err)` for you. This also works when an `async` function throws. You can write handlers in a natural way:

```ts
// Express 5: works as written. The thrown NotFoundError reaches errorHandler.
app.get("/orders/:id", async (req, res) => {
  const order = await orders.get(req.params.id);   // throws NotFoundError
  res.json(order);
});
```

- **Express 4:** Express does **not** catch a rejected promise inside an `async` handler. It becomes an **unhandled rejection** (a failed promise that nothing handles). The request hangs. On current Node versions, an unhandled rejection also **stops the process**. So you must wrap handlers:

```ts
// Express 4 only
const asyncHandler = (fn: RequestHandler): RequestHandler => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);
app.get("/orders/:id", asyncHandler(async (req, res) => { /* ... */ }));
```

You can also use the `express-async-errors` patch. Both versions already caught normal (synchronous) throws inside a handler. Only promises are different. If you are on Express 4, plan to upgrade.

## Process-level safety nets

Some errors escape every `try/catch`. Examples are a rejected promise that nobody awaited, and an exception inside an event callback.

```ts
process.on("unhandledRejection", (reason) => {
  logger.fatal({ err: reason }, "unhandledRejection");
  shutdown(1);
});
process.on("uncaughtException", (err) => {
  logger.fatal({ err }, "uncaughtException");
  shutdown(1);
});

function shutdown(code: number) {
  // Stop accepting new connections, finish in-flight requests, close DB; then exit
  server.close(() => prisma.$disconnect().finally(() => process.exit(code)));
  setTimeout(() => process.exit(code), 10_000).unref(); // hard deadline
}
process.on("SIGTERM", () => shutdown(0)); // sent by Kubernetes/ECS/systemd on deploy
```

**Should you catch `uncaughtException` and keep running?** No. After an uncaught exception, the process is in an undefined state. Log it and **exit**. Let a supervisor (PM2, systemd, Kubernetes, ECS) start a fresh instance. This works well only if you run **more than one instance** behind a load balancer (a server that shares traffic between instances). You also need a graceful shutdown (finish the current requests before exiting).

## Mapping infrastructure errors

Turn low-level failures into your own domain errors at the boundary. This is usually the repository:

```ts
import { Prisma } from "@prisma/client";

export async function createUser(data: { email: string; name: string }) {
  try {
    return await prisma.user.create({ data });
  } catch (e) {
    if (e instanceof Prisma.PrismaClientKnownRequestError) {
      if (e.code === "P2002") throw new ConflictError("Email already registered", "EMAIL_TAKEN", ); // unique constraint
      if (e.code === "P2025") throw new NotFoundError("User");                                          // record not found
    }
    throw e; // unknown: let it bubble as an unexpected error
  }
}
```

- A unique violation → `409`. A foreign-key violation → usually `422`/`409`. Not found → `404`.
- A **timeout or connection error** from a dependency is operational, but it is not the client's fault. Use `502`/`503`/`504`, ideally with `Retry-After`. If the operation is idempotent (safe to repeat), also retry it inside your server.
- Wrap the error and add context, but **keep the cause**: `throw new AppError("Could not charge card", 502, "PAYMENT_UNAVAILABLE", { cause: e })`.

## Retries, timeouts and not hanging forever

- **Always set timeouts** on calls that go out (HTTP, database, queue). With no timeout, one slow dependency can use up all your connections everywhere.
- **Retry only short-lived failures** (network blips, `429`, `503`). Retry only **idempotent** operations. Use **exponential backoff and jitter** (wait longer after each try, with a small random change, so clients do not all retry together) ([Practical Design Problems, Lesson 07](/design-problems/lesson-7)).
- Use a **circuit breaker** around unreliable dependencies. It stops calls for a while after repeated failures, so you fail fast and requests do not pile up.
- `Promise.all` fails on the first rejection and leaves the other promises running. Use `Promise.allSettled` when partial success is acceptable.

```ts
const results = await Promise.allSettled([sendEmail(), updateCrm(), notifySlack()]);
for (const r of results) if (r.status === "rejected") logger.warn({ err: r.reason }, "non-critical side effect failed");
```

## Common mistakes

1. **Swallowing errors** (`catch (e) {}`), or logging them and then carrying on as if nothing happened.
2. **Leaking internals** (stack traces, SQL, file paths) to clients.
3. **Returning `200`** on failure, or `500` for mistakes made by the client.
4. **Different error shapes** in different endpoints.
5. **Using `throw "string"`** or throwing values that are not `Error` objects. They lose the stack trace.
6. **Catching and rethrowing without the cause.** This hides the root problem.
7. **Handling a programmer error and carrying on**, instead of crashing cleanly.
8. **No timeouts** on outgoing calls, and **no graceful shutdown**.
9. **Logging the same error at every layer.** This makes noise. Log once, where you handle it.

## Interview questions

### Q1. Operational vs programmer error?

Operational errors are expected problems at run time in a correct program: bad input, a missing record, timeouts, connection failures. I handle them, map them to the right status codes, and often retry. Programmer errors are bugs, like a null dereference or a wrong type. I cannot recover from them safely. So I log them with full detail and restart the process. This difference decides whether I handle the error or crash.

### Q2. How does Express 5 handle a rejected async handler?

Express 5 sees that the handler returned a promise. If the promise rejects, or an async function throws, Express calls `next(err)` automatically. The error then goes to your error-handling middleware. In Express 4, the rejection is unhandled. The request hangs, and on current Node it can crash the process. So Express 4 needs an async wrapper.

### Q3. Should you catch `uncaughtException` and keep running?

No. The process may be in a broken state. I log the error and start a graceful shutdown: stop accepting connections, let the current requests finish, and close resources. Then I exit. A process manager or orchestrator starts a clean instance. I run several instances, so users do not notice.

### Q4. Scenario: errors leak stack traces to clients. Fix it.

I add one central error-handling middleware. It treats known `AppError`s differently from unexpected errors. Known errors become a status, a stable code and a safe message. Unexpected errors become a generic `500` with a request ID. I log the full error with its stack on the server. I set `NODE_ENV=production` and remove any code like `res.send(err)`. Then I add a test that checks no stack trace appears in responses.

### Q5. How do you design error classes?

I make a base `AppError` that carries `status`, `code`, a safe `message`, optional `details` and the original `cause`. Subclasses extend it (`NotFoundError`, `ConflictError`, `ValidationError`). Domain and repository code throw them. One central handler turns them into the HTTP response. Clients switch on `code`, never on the message text.

### Q6. Why log the error once?

If you log at every layer on the way up, you get duplicate entries. These hide the real count and the real cause. I log where the error is handled, which is usually the central handler. I include full context and the correlation ID. The layers in between add context through `cause` instead.

### Q7. When do you retry a failed operation?

Only when the failure is temporary (timeouts, connection resets, `429`, `503`) and the operation is idempotent or protected by an idempotency key. I use a limited number of attempts with exponential backoff and jitter. I respect `Retry-After` and set timeouts. I also consider a circuit breaker, so retries do not make an outage worse.

### Q8. What does a graceful shutdown involve?

When `SIGTERM` arrives, I stop accepting new connections and make the readiness check fail. I let the current requests finish within a time limit. I close the database and queue connections and flush the logs. Then I exit. A hard timeout forces the exit if something hangs. This avoids dropped requests during deploys and restarts.

## Key takeaways

- **Operational errors: handle and report. Programmer errors: log and restart.**
- Use **typed errors** with `status`, a stable `code` and `cause`. Throw domain errors, and turn them into HTTP in **one** central handler.
- **Express 5 forwards async rejections automatically.** Express 4 needs a wrapper.
- Never leak internals. Return a **request ID** instead.
- Set **timeouts**. Retry only idempotent, short-lived failures, with backoff and jitter. Shut down gracefully.
