> **In one line:** an **index** makes reads fast and writes slower; a **transaction** makes a group of changes all-or-nothing; an **isolation level** decides what concurrent transactions can see of each other. Most "mysterious" API bugs and slowdowns are one of these three.

You do not need to be a DBA, but a full-stack engineer who owns an API must be able to read a query plan and reason about concurrent requests. The examples use PostgreSQL, the usual pairing with Prisma, but the ideas carry over.

## How an index works

Without an index, `SELECT * FROM orders WHERE user_id = 42` makes the database read **every row** (a **sequential scan**): cost grows linearly with table size. A **B-tree index** keeps the column values sorted in a tree, so the database can jump to the matching rows in **logarithmic** time, like an index at the back of a book.

```sql
CREATE INDEX idx_orders_user_id ON orders (user_id);
```

What a B-tree index helps with: equality (`=`), ranges (`<`, `>`, `BETWEEN`), `ORDER BY` on the indexed columns, `LIKE 'abc%'` (prefix), `MIN`/`MAX`, and joins on the indexed column.

### Costs

- Every `INSERT`, `UPDATE` (of indexed columns) and `DELETE` must also maintain each index, so **more indexes = slower writes** and more storage.
- Indexes consume memory when cached.
- An unused index is pure cost. Add indexes for **real query patterns**, not for every column.

> [!warn] PostgreSQL does **not** automatically index foreign-key columns (it does index primary keys and unique constraints). A foreign key like `order_items.order_id` without an index makes joins and cascading deletes slow. Add one yourself.

### Composite indexes and column order

A multi-column index sorts by the first column, then the second within it, and so on. It can serve queries that use a **leftmost prefix** of its columns.

```sql
CREATE INDEX idx_orders_user_status_created ON orders (user_id, status, created_at DESC);
```

| Query | Uses the index? |
|---|---|
| `WHERE user_id = 7` | Yes (leftmost) |
| `WHERE user_id = 7 AND status = 'paid'` | Yes |
| `WHERE user_id = 7 AND status = 'paid' ORDER BY created_at DESC` | Yes, and **avoids a sort** |
| `WHERE status = 'paid'` | **Poorly**: the first column is missing |
| `WHERE created_at > '2026-01-01'` | Poorly |

**Order columns by how you query:** equality columns first, then the range/sort column. A good rule is "equality, sort, range" (ESR).

### Other useful index types and features

- **Unique indexes** enforce uniqueness (and the database does it atomically).
- **Partial indexes** (`WHERE deleted_at IS NULL`, `WHERE status = 'pending'`) index only the rows you query: smaller and faster.
- **Expression indexes** (`CREATE INDEX ON users (lower(email))`) for queries on computed values.
- **Covering indexes** (`INCLUDE (total)`) let the database answer from the index alone (an **index-only scan**), skipping the table.
- **GIN indexes** for `jsonb`, arrays and full-text search; **GiST/BRIN** for ranges, geometry and huge append-only tables.

### When an index does NOT help

1. **Tiny tables**: scanning a few hundred rows is faster than using an index; the planner knows.
2. **Low selectivity**: an index on `is_active` where 95% of rows are `true` returns most of the table anyway.
3. **A function or cast on the column**: `WHERE lower(email) = 'a@b.com'` cannot use a plain index on `email` (create an expression index), nor `WHERE created_at::date = ...` (use a range instead).
4. **Leading wildcards**: `LIKE '%abc'` cannot use a B-tree (use a trigram/GIN index or full-text search).
5. **Implicit type conversions** between mismatched column and parameter types.
6. **The wrong column order** in a composite index.
7. **Stale statistics**: the planner chooses badly. `ANALYZE` (autovacuum usually handles it).
8. **Fetching a large fraction of the table**: a sequential scan is correct.
9. `OR` across different columns can prevent index use (consider `UNION` or a bitmap scan).
10. **`OFFSET` with huge values**: the index finds the start but the database still skips all earlier rows ([Practical Design Problems, Lesson 03](/design-problems/lesson-3)).

## Reading `EXPLAIN ANALYZE`

`EXPLAIN` shows the **plan**; `EXPLAIN ANALYZE` actually **runs the query** and adds real timings and row counts. Add `BUFFERS` to see I/O.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42 AND status = 'paid' ORDER BY created_at DESC LIMIT 20;
```

```text
Limit  (cost=0.43..45.2 rows=20 width=96) (actual time=0.05..0.31 rows=20 loops=1)
  ->  Index Scan using idx_orders_user_status_created on orders
        (cost=0.43..210.8 rows=94 width=96) (actual time=0.05..0.29 rows=20 loops=1)
        Index Cond: ((user_id = 42) AND (status = 'paid'::text))
        Buffers: shared hit=24
Planning Time: 0.2 ms
Execution Time: 0.4 ms
```

What to look for:

| Plan node | Meaning |
|---|---|
| **Seq Scan** | Reads the whole table. Fine for small tables, a red flag on large ones with selective filters |
| **Index Scan** | Walks the index, then fetches rows from the table |
| **Index Only Scan** | Answers from the index alone (needs a covering index and a recently vacuumed table) |
| **Bitmap Index/Heap Scan** | Combines several index conditions, good for medium selectivity |
| **Sort** (esp. "external merge, Disk") | Sorting not served by an index; may spill to disk |
| **Nested Loop / Hash Join / Merge Join** | Join strategies; a nested loop with huge `loops` is the N+1 shape inside the database |

Key numbers:

- **`cost`** is the planner's estimate in arbitrary units; **`actual time`** is real milliseconds (first row..all rows).
- **`rows` (estimated) vs actual rows**: a big mismatch means bad statistics and likely a bad plan.
- **`loops`** multiplies the per-loop cost: `actual time` is per loop.
- **`Rows Removed by Filter`** large means you read many rows to keep few: an index candidate.
- **`Buffers: shared read`** (from disk) vs **`hit`** (from cache).

Workflow: find the slow query (from logs, `pg_stat_statements`), run `EXPLAIN (ANALYZE, BUFFERS)` on realistic data, spot the scan or sort, add or adjust an index, re-run, and compare. Test on production-sized data; a plan on 100 rows tells you little.

## Transactions and ACID

A **transaction** groups statements so they succeed or fail **together**.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;      -- or ROLLBACK; to undo everything
```

| Letter | Guarantee |
|---|---|
| **A**tomicity | All statements apply, or none do |
| **C**onsistency | The database moves from one valid state to another (constraints hold) |
| **I**solation | Concurrent transactions do not see each other's partial work, to a degree set by the isolation level |
| **D**urability | Once committed, it survives a crash (written to the write-ahead log) |

In Prisma:

```ts
await prisma.$transaction(async (tx) => {
  const from = await tx.account.update({ where: { id: 1 }, data: { balance: { decrement: 500 } } });
  if (from.balance < 0) throw new Error("Insufficient funds"); // throwing rolls back everything
  await tx.account.update({ where: { id: 2 }, data: { balance: { increment: 500 } } });
});
```

Keep transactions **short**: they hold locks and a connection from the pool. Never call slow external APIs (payment providers, email) inside a transaction.

## Isolation levels and what can go wrong

When transactions run concurrently, several anomalies are possible:

| Anomaly | What happens |
|---|---|
| **Dirty read** | You read data another transaction has not committed |
| **Non-repeatable read** | You read a row twice and it changed in between (someone committed an update) |
| **Phantom read** | You run a query twice and new rows appear |
| **Lost update** | Two transactions read a value, both modify it, the second overwrites the first |
| **Write skew** | Two transactions each read overlapping data, make decisions based on it and write different rows, together violating a rule (two on-call doctors both go off-call) |

PostgreSQL's levels:

| Level | Behaviour in PostgreSQL |
|---|---|
| **Read Committed** (default) | Each *statement* sees data committed before it started. No dirty reads; non-repeatable reads, phantoms and lost updates are possible |
| **Repeatable Read** | The whole transaction sees one **snapshot**. Prevents non-repeatable and phantom reads; you may get a **serialization failure** to retry; write skew is still possible |
| **Serializable** | Behaves as if transactions ran one after another (using serializable snapshot isolation). Prevents write skew too; the application **must retry** on serialization failures |

(PostgreSQL treats Read Uncommitted the same as Read Committed, so dirty reads never happen.) Higher isolation costs throughput and requires retry logic.

```ts
await prisma.$transaction(async (tx) => { /* ... */ }, { isolationLevel: "Serializable" });
```

## Scenario: two users buy the last item at the same moment

```text
Tx A: SELECT stock → 1          Tx B: SELECT stock → 1
Tx A: stock = 1 - 1 → writes 0  Tx B: stock = 1 - 1 → writes 0
Both orders succeed. Stock is 0 but two items were sold. ← overselling
```

The "read, check, then write" pattern is a **race**. Ways to prevent it, from simplest:

1. **Atomic conditional update**, letting the database do the check:

```sql
UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1;
-- check the affected row count: 1 = reserved, 0 = out of stock
```

```ts
const { count } = await prisma.product.updateMany({ where: { id, stock: { gte: 1 } }, data: { stock: { decrement: 1 } } });
if (count === 0) throw new ConflictError("Out of stock", "OUT_OF_STOCK");
```

2. **Pessimistic locking:** `SELECT ... FOR UPDATE` locks the row until the transaction ends, so the second buyer waits and then sees the updated stock.
3. **Optimistic locking:** a `version` column; `UPDATE ... WHERE id = $1 AND version = $2` and retry (or fail) when no row matched.
4. **A database constraint** (`CHECK (stock >= 0)`) as a final guard.
5. **Serializable isolation** with retries, when the logic is too complex for a single statement.
6. **Reservation tables** (hold stock for a checkout window with an expiry) for real e-commerce flows.

Also use **unique constraints** for "only one" rules (one active subscription per user, one vote per user per poll), instead of check-then-insert.

### Deadlocks

Two transactions each hold a lock the other needs; the database detects it and aborts one. Reduce them by locking rows in a **consistent order**, keeping transactions short, and **retrying** the aborted transaction.

## Connections matter too

Each database connection is expensive (a process in PostgreSQL), and the server supports a limited number. APIs use a **connection pool**; if requests hold connections too long (long transactions, slow queries), the pool is exhausted and *everything* waits. This is why serverless deployments need a pooler ([Lesson 08](/backend/lesson-8)).

## Common mistakes

1. **Indexing every column**, or **none** besides the primary key.
2. **Forgetting indexes on foreign keys** in PostgreSQL.
3. **Functions on indexed columns** in `WHERE` (`lower(email)`, `date(created_at)`).
4. **Read-check-write races** instead of atomic updates, locks or constraints.
5. **Long transactions** that include network calls.
6. **Trusting `EXPLAIN` on tiny dev data.**
7. **`SELECT *`** and fetching more than needed (also blocks index-only scans).
8. **Assuming the default isolation level protects against everything.**

## Interview questions

### Q1. When does an index not help?

On tiny tables, low-selectivity columns, queries that apply functions or casts to the indexed column, leading-wildcard `LIKE`, mismatched types, missing leftmost columns of a composite index, queries returning a large fraction of the table, or when statistics are stale. Also, indexes cost write performance, so unused ones should be removed.

### Q2. What does `EXPLAIN ANALYZE` show?

The execution plan the database chose, plus the actual run: node types (Seq Scan, Index Scan, joins, sorts), estimated vs actual row counts, per-node timing, loops, rows removed by filters and buffer hits. I compare estimates to actuals to spot bad statistics and look for sequential scans, expensive sorts and nested loops with many iterations.

### Q3. Scenario: two users buy the last item at the same moment. Prevent overselling.

Make the check and the decrement a single atomic step: `UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1` and treat zero affected rows as out of stock. Alternatives are `SELECT … FOR UPDATE`, optimistic locking with a version column, a `CHECK (stock >= 0)` constraint as a backstop, or serializable transactions with retries. Avoid read-then-write in application code.

### Q4. Read Committed vs Repeatable Read?

In Read Committed (the PostgreSQL default) each statement sees data committed before that statement began, so the same query run twice in one transaction can return different results. In Repeatable Read the whole transaction uses one snapshot, so reads are stable, but it can fail with serialization errors that you must retry, and write skew is still possible; Serializable closes that gap.

### Q5. Why index foreign keys in PostgreSQL?

PostgreSQL does not create an index on the referencing column automatically. Without one, joins from parent to child and cascading deletes or updates need sequential scans of the child table, which gets slower as it grows.

### Q6. How does column order in a composite index matter?

The index is sorted by the first column, then the second within it, so it serves queries using a leftmost prefix. Put equality-filtered columns first, then the column used for sorting or range filtering. An index on `(user_id, created_at)` helps `WHERE user_id = ? ORDER BY created_at`, but not a query that only filters on `created_at`.

### Q7. What is a lost update and how do you prevent it?

Two transactions read the same value, both compute a new one and the second write overwrites the first. Prevent it with atomic updates (`SET x = x + 1`), row locks (`FOR UPDATE`), optimistic version checks, or stricter isolation with retries.

### Q8. Why keep transactions short?

They hold locks and a pooled connection until they finish. Long transactions block other writers, increase deadlock risk, bloat the database with old row versions and can exhaust the connection pool. Do slow work such as external API calls outside the transaction.

### Q9. Scenario: a report query takes 30 seconds, but only at month end. What do you check?

Data volume and plan changes: at month end the date range covers many more rows, so the planner may switch to a sequential scan or the sort spills to disk. Run `EXPLAIN (ANALYZE, BUFFERS)` on the month-end parameters, check indexes for the filter and sort columns, row estimates versus actuals, and lock or I/O contention from batch jobs. Fix with the right composite index, pre-aggregated summary tables or running the report on a replica.

## Key takeaways

- Indexes trade **write cost for read speed**; design them from real queries, mind **column order**, and index foreign keys yourself in PostgreSQL.
- Read **`EXPLAIN (ANALYZE, BUFFERS)`**: scan type, estimated vs actual rows, loops, sorts.
- **ACID** transactions make multi-step changes atomic; keep them **short**.
- Know the **isolation levels** and anomalies; prefer **atomic updates, locks, constraints** over read-check-write.
- Races are solved in the database, not in application `if` statements.
