> **In one line:** logs tell you **what happened**. Metrics tell you **how often and how fast**. Traces tell you **where the time went**. In production you use all three together, joined by a **request ID**.

On the frontend, you can reproduce a bug in DevTools. On the backend, you often *cannot*. It happened to someone else, at 2 a.m., once. "Observability" means being able to find out what happened inside your system, even when you were not there. Plan it before you need it.

## Words used in this lesson

- **A log** is a record, written by your program, of something that happened. **Logging** is the act of writing these records. Example: "order 42 created".
- **Observability** is how well you can understand what happens inside a running system by looking at the data it produces (logs, metrics and traces).
- **A metric** is a number measured over time, such as requests per second. Metrics are cheap to store and good for graphs and alerts.
- **A trace** is the record of one request as it travels through the parts of a system. It is made of **spans**. A span is one timed step, such as one database call.
- **A request ID (or correlation ID)** is a unique value given to one request and put on every log line for it. It lets you join all the lines of that request.
- **A log level** is a label that says how serious a line is: `trace`, `debug`, `info`, `warn`, `error`, `fatal` (from least to most serious).
- **Structured logging** means writing each log line as data (usually one JSON object) with named fields, not as free text.
- **JSON** is a text format for data, made of `{"key": value}` pairs.
- **stdout / stderr** are the two standard output streams of a program. By default, stdout is for normal output and stderr is for errors. Platforms read them to collect logs.
- **Redaction** means replacing secret values in a log with a placeholder such as `[REDACTED]` before the line is written.
- **pino** is a fast Node.js logging library that writes JSON lines.
- **Latency** is the time between sending a request and getting the answer.
- **A percentile** (p50, p95, p99) is the value below which that share of measurements fall. If p95 latency is 300 ms, then 95 out of 100 requests took 300 ms or less. p50 is the median.
- **The event loop** is the part of Node.js that takes the next piece of waiting work and runs it. **Event-loop lag** is how late it is in starting that work. High lag means your code is blocking it.
- **Cardinality** is the number of different values a label or field can take. A `status` label has low cardinality (a few values). A `userId` label has high cardinality (millions of values).
- **An SLO** (service level objective) is a target for service quality, for example "99.9% of requests succeed". An **error budget** is the amount of failure the SLO still allows.
- **A runbook** is a written guide that says what to do when a given alert fires.
- **Sampling** means keeping only a share of the events (for example 1 in 10) to save cost.
- **Retention** is how long stored data is kept before it is deleted.
- **A tenant** is one customer (or organisation) in a system that serves many customers.
- **A commit SHA** is the unique ID of one version of your code in Git. Putting it in logs tells you which release wrote the line.

Difference in one line: a **log** says what happened once, a **metric** counts it over time, and a **trace** shows where one request spent its time.

## Why `console.log` is not enough

| Problem with `console.log` | What you need instead |
|---|---|
| Plain text; hard to search or count | **Structured (JSON) logs** with fields |
| No levels; you cannot turn noise down or errors up | **Log levels** |
| No request context; lines from different requests mix together | **Correlation / request IDs** on every line |
| Cannot hide secrets | **Redaction** (hiding secret values) in the logger |
| No transport, rotation or sampling | A real logger that writes to **stdout**, collected by the platform |
| Slow in busy code paths | A fast logger (such as **pino**) built for production |

## Structured logs

A structured log is not a sentence. It is data with named fields, so a tool can search it. In pino, a level is also stored as a number (`trace` 10, `debug` 20, `info` 30, `warn` 40, `error` 50, `fatal` 60). That is why the example below shows `"level":30`, and why you can filter with `level>=50`.

```ts
import pino from "pino";

export const logger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  redact: {
    paths: ["req.headers.authorization", "req.headers.cookie", "*.password", "*.token", "*.refreshToken", "*.cardNumber"],
    censor: "[REDACTED]",
  },
  base: { service: "orders-api", env: process.env.NODE_ENV },
  timestamp: pino.stdTimeFunctions.isoTime,
});

logger.info({ orderId: "ord_42", userId: "u_9", durationMs: 87, itemCount: 3 }, "order created");
```

The output is one JSON object per line:

```json
{"level":30,"time":"2026-05-01T09:30:00.123Z","service":"orders-api","env":"production","orderId":"ord_42","userId":"u_9","durationMs":87,"itemCount":3,"msg":"order created"}
```

Now you can ask a question like this: "show all `level>=50` for `service=orders-api` where `durationMs > 1000` in the last hour". You can ask it in CloudWatch Logs Insights, Loki, Datadog or Elasticsearch. You do not need to search through text.

### Log levels

| Level | Use for |
|---|---|
| `fatal` | The process cannot continue (it is about to exit) |
| `error` | An operation failed and needs attention (unexpected exceptions, failed payments) |
| `warn` | Something unexpected happened but was handled (operational errors, retries, use of deprecated features) |
| `info` | Normal, important events (server started, order created, job finished) |
| `debug` | Detail for developers; off in production by default |
| `trace` | Very fine detail; rarely on |

**Make the level changeable at run time.** Use an environment variable, and ideally allow a change without a new deploy. Then you can turn on `debug` for one instance during an incident.

### What a good log line contains

- **What happened:** a stable message such as `"order created"`. Do not write a sentence with values inside it.
- **Who or what it was about:** `userId`, `orderId`, `tenantId` as **fields**.
- **Correlation:** `requestId` and, if you use tracing, `traceId`.
- **Result and cost:** `status`, `durationMs`, retry count.
- **Where:** service, version or commit SHA, environment, hostname.
- For errors: the **error object** (message, stack, `cause`, error `code`).

Keep the message **the same every time** and put the changing values **in fields**. Fixed messages are easy to group and count. Messages with values inside are not.

### What you must never log

Never log secrets or sensitive personal data. This includes passwords, tokens, API keys, session IDs, full card numbers, CVV, government IDs, health data, and full request bodies of sensitive endpoints. OWASP's logging guidance and privacy laws (GDPR, India's DPDP Act) both apply here. Use **redaction** by field path. Log **IDs** instead of the data. Cut large payloads short. Also be careful with whole `req.headers` (they hold cookies and auth) and with whole error responses from third parties.

## Correlation IDs: tracing one request across everything

Give each incoming request an ID. Add it to **every log line** made while handling that request. Send it back to the client. **Pass it on** to the calls you make to other services.

```ts
import { randomUUID } from "node:crypto";
import { AsyncLocalStorage } from "node:async_hooks";

const als = new AsyncLocalStorage<{ requestId: string; userId?: string }>();

export const requestContext = (req, res, next) => {
  const requestId = req.header("x-request-id") ?? randomUUID(); // honour an upstream ID
  res.setHeader("x-request-id", requestId);
  als.run({ requestId }, next);
};

// A child logger that automatically includes the context — no passing IDs around by hand
export const log = () => logger.child(als.getStore() ?? {});
```

`AsyncLocalStorage` is a Node.js class that keeps a value attached to the current chain of asynchronous calls. Here it keeps the data of the current request, like a note that follows the request around. A **child logger** (`logger.child(...)`) is a logger that adds fixed fields to every line it writes. Deeper code (a service, a repository, a helper) can call `log().info(...)`, and the `requestId` is added for you. This works even across `await` calls.

For systems with many services, use the **W3C `traceparent` header**. It is an HTTP header, defined by a W3C standard, that carries the trace ID from one service to the next. **OpenTelemetry** is an open-source toolkit (libraries and a data format) for creating traces, metrics and logs. It instruments Node, Express, Prisma and `fetch`. It sends traces and metrics to a backend (Jaeger, Tempo, Datadog, AWS X-Ray and others).

### The access log

An access log is a record with one line for each request that the server handled. One structured line for each request is the cheapest and most useful signal:

```ts
app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  res.on("finish", () => {
    log().info({
      method: req.method, path: req.route?.path ?? req.path, // route pattern, not the raw URL (low cardinality)
      status: res.statusCode,
      durationMs: Number(process.hrtime.bigint() - start) / 1e6,
      bytes: res.getHeader("content-length"),
      userId: req.user?.id,
    }, "request completed");
  });
  next();
});
```

Use the **route pattern** (`/orders/:id`) and not the raw path (`/orders/8412`). If you use the raw path, your metrics and queries split into millions of different URLs. (Having too many different values is called high cardinality.)

## The three pillars

| Pillar | Answers | Examples |
|---|---|---|
| **Logs** | What happened, in detail? | An error with a stack trace, an audit event (a record of who did what, kept for security checks) |
| **Metrics** | How much, how often, how fast? Trends and alerts | Request rate, error rate, latency percentiles, queue depth, DB pool usage |
| **Traces** | Where did the time go across services? | One request: API 12 ms, DB 340 ms, payment provider 900 ms |

### Metrics worth having (RED and USE)

- **RED** for every service or endpoint: **R**ate (requests per second), **E**rrors (the share that fail, such as 5xx), **D**uration (latency, shown as **p50/p95/p99**, not averages).
- **USE** (a method for resources) for resources (CPU, memory, DB connections, disk): **U**tilisation (how busy), **S**aturation (how much work is waiting), **E**rrors.
- Node-specific: **event-loop lag** (measured with `perf_hooks.monitorEventLoopDelay`), heap used (the memory your objects take), **GC pauses** (GC means garbage collection: the engine frees memory that is no longer used, and may pause your code for a moment), and open handles (open sockets, files and timers that keep the process alive).
- **Business metrics:** orders per minute, signups, payment failures. They often show a problem before the technical metrics do.

Averages hide pain. Say 1% of requests take 10 seconds. The average still looks fine, but thousands of users suffer. Always look at **percentiles**. A p99 of 2 seconds means 99 out of 100 requests were faster than 2 seconds.

### Alerting

An **alert** is an automatic message sent to people when a metric crosses a limit. Alert on **symptoms that users feel** (error rate, latency, failed checkouts). Do not alert on every possible cause (such as CPU at 70%). Wake a person only for urgent problems they can act on. Everything else becomes a ticket or a dashboard. Add a **runbook link** (a guide that says what to do) to each alert. (The System Design series explains SLOs and error budgets in depth.) **Alert fatigue** is what happens when there are so many alerts that people stop reacting to them.

## Where do logs go?

- Write **JSON to stdout/stderr**. Do not manage log files or rotation (starting a new file when the old one gets big, and deleting old ones) inside the app. This follows the twelve-factor approach, a well-known set of rules for cloud apps, which says to treat logs as a stream of events that the platform collects.
- The platform collects the logs. Examples are **CloudWatch Logs** on AWS (the DevOps series covers this), Docker log drivers, or a collector program (Fluent Bit or the OpenTelemetry Collector) that reads the logs and sends them to a store such as Elasticsearch, Loki or Datadog.
- Choose **retention** (how long you keep logs) on purpose. Logs cost money. They may also hold personal data that you must not keep forever.
- Think about **sampling** (keeping only some) for logs that are high in volume and low in value, like successful health checks (calls that only ask "are you alive?"). Keep all errors.

## Scenario: an intermittent 500 you cannot reproduce

Here is what you need *already in place*:

1. A **request ID** in the error response that the user can quote ("Reference: 7f3a…").
2. **Logs found by that ID** that show the whole path of the request. This includes the unhandled error with its stack and `cause`.
3. The **shape of the inputs** (not secrets): which endpoint, which user or tenant, key parameters, payload size.
4. **Timings of dependencies** (database, cache, third parties) from traces or log fields. Was it a timeout?
5. **Metrics from around that time.** Was there a deploy, a traffic spike, full DB connections, event-loop lag or memory pressure?
6. **Version tags** (commit SHA) on logs, so you know which release made the error.

Then the investigation goes like this. Find the request ID and read the story. Form a guess. Check the metrics for a link. Then add a targeted log or a regression test. Without these things, you are only guessing.

## Common mistakes

1. **`console.log` in production** with strings joined together.
2. **Logging secrets or full request bodies.**
3. **No request ID**, so lines from the same request cannot be linked.
4. **Logging at every layer** (duplicate errors), or logging so much that the useful lines are lost.
5. **Metric labels with too many values** (user IDs, raw URLs). A label is a name=value tag on a metric. Each different value creates a new series to store, so the metrics store grows too big.
6. **Averages instead of percentiles.**
7. **Alerting on causes instead of symptoms.** This causes alert fatigue (people stop trusting alerts).
8. **Treating logging as an afterthought**, with no structured fields and no retention policy.

## Interview questions

### Q1. What goes into a good log line?

A fixed, clear message plus structured fields. The fields are: a request or trace ID, the things involved (user, order, tenant), the result (status, error code), timing and retries, and the service, version and environment. For errors, I include the error object with stack and cause. I never include secrets or personal data that I do not need.

### Q2. How do you trace one user request across services?

I create a request ID at the edge, or accept one that comes in. I put it in an async context, so every log line includes it. I return it in the response. I pass it on in every outgoing call, ideally with the W3C `traceparent` header and OpenTelemetry. Then I can join the logs and traces from all services by that ID.

### Q3. Scenario: an intermittent 500 in production that you can't reproduce. What do you need?

I need a request ID that the user can see, and structured logs with stack traces and the error cause. I need the endpoint and the shape of the key inputs, timings of dependencies (from traces), and metrics from the time of the incident (deploys, saturation, event-loop lag). I also need release version tags. With these, I can rebuild the failing request instead of guessing.

### Q4. Why not use `console.log` in production?

It has no structure, no levels and no redaction. It gives no context for each request, and it does not work well with log collection tools. A production logger like pino writes fast, structured, redacted JSON. It has levels and child contexts that tools can search and alert on.

### Q5. What is the difference between logs, metrics and traces?

Logs are single detailed events, used to look into specific cases. Metrics are numbers added up over time, used for dashboards and alerts. Traces follow one request across components and show the time for each step. Metrics tell you *that* something is wrong. Traces show *where*. Logs explain *why*.

### Q6. Why prefer percentiles to averages for latency?

Averages hide the slow tail. A few very slow requests barely change the average, but they ruin the experience for those users. p95 and p99 show what the slowest part of your traffic sees. SLOs (service level objectives, the quality targets) are usually defined on these numbers.

### Q7. What should you never log?

Passwords, tokens, API keys, session identifiers, full payment card data and other sensitive personal data. I redact by field path, log identifiers instead of whole payloads, and limit how long logs are kept.

### Q8. What are the RED metrics?

Rate, Errors and Duration for each service or endpoint. That means how many requests come in, what share of them fail, and how long they take (as percentiles). They give a quick view of health from the user's side. I pair them with USE metrics (utilisation, saturation, errors) for resources.

### Q9. Scenario: your log bill tripled after a release. How do you investigate and cut it?

I find the noisy sources by grouping log volume by service, level and message. Usual causes are debug logging left on, a log line inside a hot loop, full request bodies in logs, or one error repeating thousands of times. I fix the sources and sample the high-volume, low-value logs. I set levels for each environment, add retention policies, and alert on unusual log volume. I keep errors and audit events in full.

## Key takeaways

- Use a **structured, levelled logger that hides secrets** (pino) and writes JSON to stdout.
- Every request gets a **request ID**. `AsyncLocalStorage` carries it, you return it to the client, and you pass it on to other services.
- Collect **RED metrics** with **percentiles**. Add event-loop lag and business metrics.
- Never log secrets or personal data. Keep messages fixed and put variables in fields.
- Alert on **symptoms**, add runbooks, and design observability **before** the incident.
