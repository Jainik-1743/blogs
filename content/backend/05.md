> **In one line:** logs tell you **what happened**, metrics tell you **how often and how fast**, traces tell you **where the time went**. In production you debug with all three, stitched together by a **request ID**.

On the frontend you reproduce a bug in DevTools. On the backend you usually *cannot* reproduce it: it happened to someone else, at 2 a.m., once. Observability is how you investigate without access to the moment. Design it before you need it.

## Why `console.log` is not enough

| Problem with `console.log` | What you need instead |
|---|---|
| Plain text; hard to search or aggregate | **Structured (JSON) logs** with fields |
| No levels; you cannot turn noise down or errors up | **Log levels** |
| No request context; lines from concurrent requests interleave | **Correlation / request IDs** on every line |
| Cannot redact secrets | **Redaction** in the logger |
| No transport, rotation or sampling | A real logger writing to **stdout**, collected by the platform |
| Slow in hot paths | A fast logger (such as **pino**) designed for production |

## Structured logs

```ts
import pino from "pino";

export const logger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  redact: {
    paths: ["req.headers.authorization", "req.headers.cookie", "*.password", "*.token", "*.refreshToken", "*.cardNumber"],
    censor: "[REDACTED]",
  },
  base: { service: "orders-api", env: process.env.NODE_ENV },
  timestamp: pino.stdTimeFunctions.isoTime,
});

logger.info({ orderId: "ord_42", userId: "u_9", durationMs: 87, itemCount: 3 }, "order created");
```

Output (one JSON object per line):

```json
{"level":30,"time":"2026-05-01T09:30:00.123Z","service":"orders-api","env":"production","orderId":"ord_42","userId":"u_9","durationMs":87,"itemCount":3,"msg":"order created"}
```

The benefit: you can now ask "show all `level>=50` for `service=orders-api` where `durationMs > 1000` in the last hour" in CloudWatch Logs Insights, Loki, Datadog or Elasticsearch, instead of grepping text.

### Log levels

| Level | Use for |
|---|---|
| `fatal` | The process cannot continue (about to exit) |
| `error` | An operation failed and needs attention (unexpected exceptions, failed payments) |
| `warn` | Something unexpected but handled (operational errors, retries, deprecated usage) |
| `info` | Normal significant events (server started, order created, job finished) |
| `debug` | Detail for developers; off in production by default |
| `trace` | Very fine detail; rarely on |

**Make the level configurable at runtime** (an environment variable, ideally changeable without redeploying) so you can turn on `debug` for one instance during an incident.

### What a good log line contains

- **What happened** (a stable message such as `"order created"`, not a sentence with embedded values).
- **Who / what it was about:** `userId`, `orderId`, `tenantId` as **fields**.
- **Correlation:** `requestId` and, when you have tracing, `traceId`.
- **Outcome and cost:** `status`, `durationMs`, retry count.
- **Where:** service, version/commit SHA, environment, hostname.
- For errors: the **error object** (message, stack, `cause`, error `code`).

Keep the message **constant** and the variables **in fields**: constant messages group and count well; messages with values baked in do not.

### What you must never log

Secrets and sensitive personal data: passwords, tokens, API keys, session IDs, full card numbers, CVV, government IDs, health data, full request bodies of sensitive endpoints. OWASP's logging guidance and privacy law (GDPR, India's DPDP Act) both apply. Use **redaction** by field path, log **IDs** rather than the data, and truncate large payloads. Also beware of logging whole `req.headers` (cookies, auth) and whole error responses from third parties.

## Correlation IDs: tracing one request across everything

Assign each incoming request an ID, attach it to **every log line** produced while handling it, return it to the client, and **forward it** to downstream calls.

```ts
import { randomUUID } from "node:crypto";
import { AsyncLocalStorage } from "node:async_hooks";

const als = new AsyncLocalStorage<{ requestId: string; userId?: string }>();

export const requestContext = (req, res, next) => {
  const requestId = req.header("x-request-id") ?? randomUUID(); // honour an upstream ID
  res.setHeader("x-request-id", requestId);
  als.run({ requestId }, next);
};

// A child logger that automatically includes the context — no passing IDs around by hand
export const log = () => logger.child(als.getStore() ?? {});
```

With `AsyncLocalStorage`, any code deeper in the call chain (service, repository, helper) can call `log().info(...)` and the `requestId` is attached automatically, even across `await` boundaries.

For multi-service systems, use the **W3C `traceparent` header** (standard distributed-tracing propagation) so all services share one trace ID. **OpenTelemetry** is the standard toolkit that instruments Node, Express, Prisma and `fetch`, and exports traces and metrics to a backend (Jaeger, Tempo, Datadog, AWS X-Ray, and others).

### The access log

One structured line per request is the cheapest, highest-value signal:

```ts
app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  res.on("finish", () => {
    log().info({
      method: req.method, path: req.route?.path ?? req.path, // route pattern, not the raw URL (low cardinality)
      status: res.statusCode,
      durationMs: Number(process.hrtime.bigint() - start) / 1e6,
      bytes: res.getHeader("content-length"),
      userId: req.user?.id,
    }, "request completed");
  });
  next();
});
```

Use the **route pattern** (`/orders/:id`), not the raw path, so metrics and queries are not split into millions of unique URLs.

## The three pillars

| Pillar | Answers | Examples |
|---|---|---|
| **Logs** | What happened, in detail? | An error with stack trace, an audit event |
| **Metrics** | How much, how often, how fast? Trends and alerts | Request rate, error rate, latency percentiles, queue depth, DB pool usage |
| **Traces** | Where did the time go across services? | One request: API 12 ms, DB 340 ms, payment provider 900 ms |

### Metrics worth having (RED and USE)

- **RED** for every service/endpoint: **R**ate (requests per second), **E**rrors (failed fraction, 5xx), **D**uration (latency as **p50/p95/p99**, not averages).
- **USE** for resources (CPU, memory, DB connections, disk): **U**tilisation, **S**aturation, **E**rrors.
- Node-specific: **event-loop lag** (`perf_hooks.monitorEventLoopDelay`), heap used, GC pauses, open handles.
- **Business metrics:** orders per minute, signups, payment failures. They often detect problems before technical metrics do.

Averages hide pain. If 1% of requests take 10 s, the mean looks fine while thousands of users suffer: always look at **percentiles**.

### Alerting

Alert on **symptoms users feel** (error rate, latency, failed checkouts), not on every cause (CPU 70%). Page a human only for actionable, urgent issues; everything else is a ticket or dashboard. Attach a **runbook link** to each alert. (The System Design series covers SLOs and error budgets in depth.)

## Where do logs go?

- Write to **stdout/stderr** as JSON; do not manage log files or rotation inside the app (the twelve-factor approach).
- The platform collects them: **CloudWatch Logs** on AWS (the DevOps series covers this), Docker log drivers, Fluent Bit or the OpenTelemetry Collector shipping to Elasticsearch, Loki or Datadog.
- Set **retention** deliberately: logs cost money and may contain personal data you must not keep forever.
- Consider **sampling** high-volume, low-value logs (successful health checks) while keeping all errors.

## Scenario: an intermittent 500 you cannot reproduce

What you need *already in place*:

1. A **request ID** in the error response the user can quote ("Reference: 7f3a…").
2. **Logs by that ID** showing the whole request path, including the unhandled error with stack and `cause`.
3. The **inputs' shape** (not secrets): which endpoint, which user or tenant, key parameters, payload size.
4. **Dependency timings** (DB, cache, third parties) from traces or log fields: was it a timeout?
5. **Metrics around that time:** was there a deploy, a traffic spike, DB connection saturation, event-loop lag, memory pressure?
6. **Version tags** (commit SHA) on logs so you know which release produced it.

Then the investigation is: find the request ID, read the story, form a hypothesis, check metrics for correlation, and add a targeted log or a regression test. Without those ingredients you are guessing.

## Common mistakes

1. **`console.log` in production** with string concatenation.
2. **Logging secrets or full request bodies.**
3. **No request ID**, so concurrent lines cannot be linked.
4. **Logging at every layer** (duplicate errors) or logging so much that signal drowns.
5. **High-cardinality metric labels** (user IDs, raw URLs) that explode the metrics store.
6. **Averages instead of percentiles.**
7. **Alerting on causes instead of symptoms**, producing alert fatigue.
8. **Treating logging as an afterthought**, with no structured fields and no retention policy.

## Interview questions

### Q1. What goes into a good log line?

A constant, descriptive message plus structured fields: request or trace ID, the entities involved (user, order, tenant), the outcome (status, error code), timing and retries, and the service, version and environment. For errors, include the error object with stack and cause. Never include secrets or unnecessary personal data.

### Q2. How do you trace one user request across services?

Generate or accept a request ID at the edge, put it in an async context so every log line includes it, return it in the response, and propagate it (ideally via the W3C `traceparent` header and OpenTelemetry) on every outbound call. Then logs and traces from all services can be joined by that ID.

### Q3. Scenario: an intermittent 500 in production that you can't reproduce. What do you need?

A request ID surfaced to the user, structured logs with stack traces and the error cause, the endpoint and key input shape, dependency timings (traces), metrics around the incident time (deploys, saturation, event-loop lag) and release version tags. With those I can reconstruct the failing request instead of guessing.

### Q4. Why not use `console.log` in production?

It is unstructured, has no levels or redaction, offers no context per request, and does not integrate with log aggregation. A production logger like pino emits fast, structured, redacted JSON with levels and child contexts that tools can query and alert on.

### Q5. What is the difference between logs, metrics and traces?

Logs are discrete detailed events for investigating specifics; metrics are aggregated numbers over time for dashboards and alerts; traces follow one request across components showing timing per step. Metrics tell you *that* something is wrong, traces show *where*, logs explain *why*.

### Q6. Why prefer percentiles to averages for latency?

Averages hide the slow tail. A few very slow requests barely move the mean but ruin the experience for those users. p95/p99 show what the slowest portion experiences and are what SLOs are usually defined on.

### Q7. What should you never log?

Passwords, tokens, API keys, session identifiers, full payment card data and other sensitive personal data. Redact by field path, log identifiers rather than payloads, and limit retention.

### Q8. What are the RED metrics?

Rate, Errors and Duration for each service or endpoint: how many requests, what fraction fail, and how long they take (as percentiles). They give a quick, user-centred health view; pair them with USE metrics (utilisation, saturation, errors) for resources.

## Key takeaways

- Use a **structured, levelled, redacting logger** (pino) writing JSON to stdout.
- Every request gets a **request ID** carried by `AsyncLocalStorage`, returned to the client and propagated downstream.
- Collect **RED metrics** with **percentiles**, and add event-loop lag and business metrics.
- Never log secrets or personal data; keep messages constant and variables in fields.
- Alert on **symptoms**, include runbooks, and design observability **before** the incident.
