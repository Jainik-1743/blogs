> **In one line:** Node runs your JavaScript on **one thread**. If something slow or CPU-heavy runs on that thread, **every** request must wait until it finishes. Keep the event loop free, stream big data, and move heavy work somewhere else.

Browser developers already know the main-thread rule from rendering ([Browser Contract, Lesson 08](/browser/lesson-8)). On the server, the same rule has a different result. In the browser you get a choppy animation. On the server, **one slow request makes other users time out**.

## The event loop, server edition

The event loop is the part of Node that picks the next piece of work to run. Think of one waiter in a restaurant. The waiter takes an order, gives it to the kitchen, and goes to the next table while the food cooks. The waiter is fast because he never stands and waits.

Node can handle thousands of connections with one JavaScript thread because **I/O does not block it**. When you write `await db.query()`, Node gives the job to the operating system (or a worker pool) and moves on to other requests. The loop runs in phases: timers, pending callbacks, poll for I/O, `setImmediate`, and close callbacks. It runs one callback at a time until that callback is finished.

```text
Request A: parse → await DB ──(waiting, loop is free)──▶ continue → respond
Request B:        parse → await cache ─(waiting)─▶ continue → respond
```

This model is great for I/O-bound work. That means APIs that mostly wait for databases and networks. It is **bad for CPU-bound work**, where the CPU does the heavy lifting.

### Node's hidden thread pool

Not everything runs on the loop. libuv (the library under Node that does I/O) keeps a small **thread pool**. The default size is **4**, and you can change it with `UV_THREADPOOL_SIZE`. The pool is used for:

- **file system operations**
- **`dns.lookup`**
- **some `crypto` functions** (such as `pbkdf2`, `scrypt`, `randomBytes`)
- **`zlib` compression**

Network I/O uses the operating system's non-blocking sockets instead. So if many password hashes or compression jobs arrive at once, they **wait in a queue for four threads**. This can slow down file or DNS operations that have nothing to do with them.

## What blocks the event loop

| Cause | Example | Why it hurts |
|---|---|---|
| **Synchronous APIs** | `fs.readFileSync`, `execSync`, `crypto.pbkdf2Sync`, `bcrypt.hashSync` in a request path | The loop waits and does nothing else |
| **Big JSON** | `JSON.parse`/`JSON.stringify` of a 50 MB body or response | It is synchronous and CPU-bound. It gets slower as the data grows |
| **CPU-heavy loops** | Making a report, resizing images, sorting millions of rows, rendering Markdown or PDF inside the process | Pure calculation on the main thread |
| **Catastrophic regex (ReDoS)** | `/(a+)+$/` against `"aaaaaaaaaaaaaaaaaaaa!"` | The regex engine tries too many ways to match (exponential backtracking). A small input can freeze the process |
| **Huge synchronous array work** | `.map().filter().reduce()` over millions of items | Long tasks that cannot be interrupted |
| **Deep recursion or copying large objects** | `structuredClone` of giant structures | Blocks until it is done |
| **Unbounded `Promise.all`** | Starting 50,000 operations at the same time | Floods the pool, the memory and the loop with callbacks |

```js
// ❌ One request to /report blocks every other request for seconds
app.get("/report", (req, res) => {
  const rows = loadAllRowsSync();          // sync I/O
  const result = heavyAggregate(rows);     // pure CPU
  res.json(result);
});
```

### Seeing it: event-loop lag

Event-loop lag means how late the loop runs things. To measure it, check how late timers fire. If the loop is blocked for 400 ms, a 10 ms timer fires about 400 ms late.

```ts
import { monitorEventLoopDelay } from "node:perf_hooks";

const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();

setInterval(() => {
  logger.info({ p50: h.percentile(50) / 1e6, p99: h.percentile(99) / 1e6, max: h.max / 1e6 }, "event loop delay (ms)");
  h.reset();
}, 10_000).unref();
```

Send this number out as a **metric** and set an alert for a high p99 lag ([Lesson 05](/backend/lesson-5)). (p99 means 99% of the measurements are faster than this value.) A healthy service shows a few milliseconds. For deeper checks, use `--cpu-prof`, or `node --inspect` with Chrome DevTools. You can also use tools like **Clinic.js** (flame graphs, which are charts that show where the time goes) and **0x**.

## Scenario: p99 latency spikes whenever one report endpoint is hit

**Symptoms:** Most endpoints take 20 ms. Every few minutes, everything jumps to several seconds. This happens at the same time as calls to `/reports/monthly`.

**Diagnosis:** The report handler does heavy CPU work (or turns a giant object into JSON) on the main thread. While it runs, the event loop cannot serve any other request. You can confirm this with event-loop-lag metrics and a CPU profile.

**Fixes, from best to last choice:**

1. **Move the work into the database.** Use aggregates, `GROUP BY` and window functions instead of pulling rows into JavaScript.
2. **Make it asynchronous.** Accept the request, put a job in a queue and return `202`. A **separate worker process** makes the report and saves it (for example in S3, with a status endpoint). Users check the status or get a message when it is ready ([Practical Design Problems, Lesson 05](/design-problems/lesson-5)).
3. **Move CPU work to `worker_threads`.** A library like `piscina` manages a pool of them. The main loop stays free.
4. **Stream** large results instead of building the whole result in memory.
5. **Split the work into chunks.** Process 1,000 rows, then give control back with `setImmediate`. This is a short-term fix.
6. **Isolate it.** Serve heavy endpoints from a separate deployment, so they cannot starve the main API.
7. **Cache** the result if many users get the same report.

## Streams: handle big data without loading it

Reading a 2 GB file into memory with `fs.readFile` uses 2 GB of memory. It may also go over Node's buffer limits. So one request can use up all the memory. **Streams** process data in small pieces (chunks):

```ts
import { createReadStream } from "node:fs";
import { pipeline } from "node:stream/promises";
import { createGzip } from "node:zlib";

app.get("/exports/:id", async (req, res) => {
  res.setHeader("Content-Type", "text/csv");
  res.setHeader("Content-Encoding", "gzip");
  await pipeline(createReadStream(pathFor(req.params.id)), createGzip(), res); // constant memory, handles backpressure
});
```

Key ideas:

- **Backpressure** means "slow down, I am not ready". If the consumer (for example a slow client) cannot keep up, the stream **pauses the producer**. It does not store everything in memory. Use **`stream.pipeline`** (or `pipeline` from `node:stream/promises`). It also handles errors and cleans up when something fails. A plain `.pipe()` does not do this.
- Stream **database cursors**, **S3 objects**, **CSV or JSON-lines** exports, and **uploads** (send the request straight into storage). Even better: let clients upload and download **directly to object storage with presigned URLs** (temporary links). Then your API never touches the bytes ([Practical Design Problems, Lesson 04](/design-problems/lesson-4)).
- For JSON, prefer **NDJSON** (one object per line) for large exports. The reader can then parse it piece by piece.

## Concurrency: cluster, worker threads, child processes, containers

| Option | What it is | Use for |
|---|---|---|
| **`cluster`** (or PM2 cluster mode) | Several Node **processes** that share one port, one for each CPU core | Using all cores for an I/O-bound API on one machine |
| **`worker_threads`** | Threads inside one process, each with its own event loop (they can share memory with `SharedArrayBuffer`) | **CPU-bound** tasks (hashing, parsing, image processing) without blocking the main loop |
| **`child_process`** | Starts a separate program (a CLI tool, ffmpeg, Python) | Running other programs, with strong separation |
| **Horizontal scaling** (containers, many instances behind a load balancer) | More copies of the whole app | The usual cloud answer: add instances and keep each process simple |

In container setups, most teams run **one Node process in each container** and change the number of containers. `cluster` matters mostly on a plain VM (virtual machine).

## Other practical Node performance habits

- **Never use sync APIs on request paths.** They are fine at startup.
- **Use a fast JSON serialiser** or schema-based serialisation (Fastify's `fast-json-stringify`) for busy endpoints. Avoid huge responses. Paginate, and compress (`gzip` or Brotli, which is often better done at the proxy or CDN).
- **Reuse connections.** Use HTTP keep-alive agents for outgoing calls, and a shared database pool.
- **Limit concurrency** when you send many requests at once (`p-limit`). Do not fire thousands at once.
- **Set timeouts** everywhere and **limit request body sizes**.
- **Watch memory.** Heap usage that keeps growing means a leak. Common causes are event listeners, caches with no limit, and closures (functions that keep old variables alive). Take heap snapshots. Set `--max-old-space-size` to fit the container.
- **Cache** expensive work that repeats. Use an in-process LRU cache (it drops the least recently used items) for small hot data, and Redis for shared data.
- **Use a current Node version** and keep dependencies up to date. Engine improvements are free speedups.
- **Test with realistic load** (`autocannon`, k6) and look at p95 and p99, not only throughput.

## Common mistakes

1. **CPU-heavy work inside request handlers.**
2. **`*Sync` calls** in busy code paths.
3. **Loading whole files or result sets into memory** instead of streaming.
4. **Unbounded `Promise.all`** over big lists.
5. **Using `.pipe()` without error handling.** Streams and file descriptors leak.
6. **Not measuring event-loop lag.** Blocking stays invisible until an incident.
7. **Regexes on untrusted input** without checking for catastrophic backtracking.
8. **Believing "async/await" means "runs in parallel".** It only avoids blocking *while waiting*, not while calculating.

## Interview questions

### Q1. What blocks the Node event loop?

Anything that runs for a long time without stopping on the main thread. Examples are sync I/O (`readFileSync`), CPU-heavy loops, large `JSON.parse` or `stringify`, catastrophic regexes, big sorts or aggregations in memory, and synchronous crypto. While it runs, no other request is processed. Waiting for I/O with `await` does not block the loop.

### Q2. Scenario: p99 latency spikes whenever one report endpoint is hit. Why?

That endpoint is probably doing CPU-bound or synchronous work on the main thread. This starves every other request. I would confirm it with event-loop-lag metrics and a CPU profile. Then I would move the aggregation into the database, or send it to a queue and a worker (returning `202`). Other options are `worker_threads`, streaming the output, or putting the endpoint in its own service.

### Q3. Streams vs buffering a 2 GB file?

Buffering loads all 2 GB into memory. This can use up the memory, and the client waits a long time for the first byte. Streaming reads and writes small chunks, so memory stays the same and backpressure is handled. The client starts receiving data right away. I use `stream.pipeline` so errors are handled correctly. For large transfers, I can hand the job to object storage with presigned URLs.

### Q4. Cluster vs worker_threads?

`cluster` starts several processes so that many CPU cores can handle requests at the same time. Each process has its own memory and event loop. `worker_threads` runs extra threads inside one process. They are good for moving CPU-bound tasks away, while the main thread keeps serving requests. In containers, I usually add more container instances instead of using `cluster`.

### Q5. What is libuv's thread pool and why does it matter?

It is a default pool of four threads. It handles file system operations, `dns.lookup`, some crypto (pbkdf2, scrypt) and zlib. If I use these a lot, the pool can become full and delay other unrelated operations. I can raise `UV_THREADPOOL_SIZE`, or move the heavy work to workers or other services.

### Q6. How do you detect event-loop blocking in production?

I record the event-loop delay with `perf_hooks.monitorEventLoopDelay`. I send p50, p99 and max as metrics and set alerts. I compare them with the latency spikes. Then I use CPU profiles or flame graphs (Clinic.js, `--cpu-prof`) to find the cause.

### Q7. What is backpressure?

It is a way for a slow consumer to tell the producer to pause. This way data is not stored without limit. Node streams do this. `pipeline` connects everything and makes sure cleanup happens. Without backpressure, a fast source and a slow client can use up all the memory.

### Q8. Does async/await make code parallel?

No. It lets the single thread do other work while it *waits* for I/O. But JavaScript callbacks still run one at a time. CPU-bound work inside an `async` function still blocks the loop. For parallel CPU work, I need worker threads, processes or separate services.

### Q9. Scenario: a 4-core server runs one Node process at 100% on one core while the others idle. What do you do?

Node runs JavaScript on one thread, so one process uses one core. For I/O-bound traffic, I run several processes (cluster, PM2, or several containers behind a load balancer). For CPU-heavy tasks, I use worker threads or a job queue. I also check the hot path with a CPU profile. Removing synchronous work or reducing JSON size may help more than adding cores.

## Key takeaways

- **One JS thread:** keep request handlers short and async. Keep CPU-heavy and synchronous work out of them.
- Measure **event-loop lag** and set an alert. Use flame graphs to find the cause.
- **Stream** large data with `pipeline` and backpressure, or skip the server with presigned URLs.
- Move heavy calculation to **the database, a queue plus a worker, or `worker_threads`**. Scale out with more instances.
- The libuv thread pool (default 4) serves fs, DNS lookup, some crypto and zlib.
