> **In one line:** Node runs your JavaScript on **one thread**. Anything CPU-heavy or synchronous on that thread freezes **every** request until it finishes. Keep the event loop free, stream big data, and move heavy computation elsewhere.

Browser developers already know the main-thread rule from rendering ([Browser Contract, Lesson 08](/browser/lesson-8)). On the server the same rule has a different consequence: instead of a janky animation, **one slow request makes unrelated users time out**.

## The event loop, server edition

Node handles thousands of concurrent connections with a single JavaScript thread because **I/O does not block it**: when you `await db.query()`, Node hands the work to the OS (or a worker pool) and moves on to other requests. The loop runs phases (timers, pending callbacks, poll for I/O, `setImmediate`, close callbacks), executing one callback at a time to completion.

```text
Request A: parse → await DB ──(waiting, loop is free)──▶ continue → respond
Request B:        parse → await cache ─(waiting)─▶ continue → respond
```

This model is excellent for I/O-bound work (APIs that mostly wait on databases and networks) and **poor for CPU-bound work**.

### Node's hidden thread pool

Not everything is on the loop: libuv keeps a small **thread pool** (default size **4**, configurable with `UV_THREADPOOL_SIZE`) used for **file system operations, `dns.lookup`, some `crypto` functions (such as `pbkdf2`, `scrypt`, `randomBytes`) and `zlib` compression**. Network I/O uses the OS's non-blocking sockets. So a burst of password hashes or compression jobs can **queue behind four threads** and slow unrelated file or DNS operations.

## What blocks the event loop

| Cause | Example | Why it hurts |
|---|---|---|
| **Synchronous APIs** | `fs.readFileSync`, `execSync`, `crypto.pbkdf2Sync`, `bcrypt.hashSync` in a request path | The loop waits, doing nothing else |
| **Big JSON** | `JSON.parse`/`JSON.stringify` of a 50 MB body or response | Synchronous and CPU-bound; scales with size |
| **CPU-heavy loops** | Generating a report, image resizing, sorting millions of rows, Markdown/PDF rendering in-process | Pure computation on the main thread |
| **Catastrophic regex (ReDoS)** | `/(a+)+$/` against `"aaaaaaaaaaaaaaaaaaaa!"` | Exponential backtracking can freeze the process on a small input |
| **Huge synchronous array work** | `.map().filter().reduce()` over millions of items | Long uninterrupted tasks |
| **Deep recursion / large object cloning** | `structuredClone` of giant structures | Blocks until done |
| **Unbounded `Promise.all`** | Starting 50,000 concurrent operations | Floods the pool, memory and the loop with callbacks |

```js
// ❌ One request to /report blocks every other request for seconds
app.get("/report", (req, res) => {
  const rows = loadAllRowsSync();          // sync I/O
  const result = heavyAggregate(rows);     // pure CPU
  res.json(result);
});
```

### Seeing it: event-loop lag

Measure how late timers fire. If the loop is blocked for 400 ms, a 10 ms timer fires ~400 ms late.

```ts
import { monitorEventLoopDelay } from "node:perf_hooks";

const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();

setInterval(() => {
  logger.info({ p50: h.percentile(50) / 1e6, p99: h.percentile(99) / 1e6, max: h.max / 1e6 }, "event loop delay (ms)");
  h.reset();
}, 10_000).unref();
```

Export it as a **metric** and alert on high p99 lag ([Lesson 05](/backend/lesson-5)). Healthy services show single-digit milliseconds. For deeper analysis use `--cpu-prof`, `node --inspect` with Chrome DevTools, or tools like **Clinic.js** (flame graphs) and **0x**.

## Scenario: p99 latency spikes whenever one report endpoint is hit

**Symptoms:** most endpoints are 20 ms; every few minutes everything jumps to seconds, correlated with `/reports/monthly`.

**Diagnosis:** the report handler does CPU-heavy aggregation (or giant JSON serialisation) on the main thread; while it runs, the event loop cannot serve any other request. Confirm with event-loop-lag metrics and a CPU profile.

**Fixes, in order of preference:**

1. **Push the work into the database** (aggregates, `GROUP BY`, window functions) instead of pulling rows into JavaScript.
2. **Make it asynchronous:** accept the request, enqueue a job, return `202`, and let a **separate worker process** compute the report and store it (S3 plus a status endpoint). Users poll or get notified ([Practical Design Problems, Lesson 05](/design-problems/lesson-5)).
3. **Offload CPU work to `worker_threads`** (a thread pool library such as `piscina`) so the main loop stays free.
4. **Stream** large results instead of materialising them.
5. **Chunk the work** (process 1,000 rows, then yield with `setImmediate`) as a stopgap.
6. **Isolate it:** serve heavy endpoints from a separate deployment so they cannot starve the main API.
7. **Cache** the result if the report is the same for many users.

## Streams: handle big data without loading it

Reading a 2 GB file into memory (`fs.readFile`) allocates 2 GB (and may exceed Node's buffer limits), so one request can exhaust memory. **Streams** process data in small chunks:

```ts
import { createReadStream } from "node:fs";
import { pipeline } from "node:stream/promises";
import { createGzip } from "node:zlib";

app.get("/exports/:id", async (req, res) => {
  res.setHeader("Content-Type", "text/csv");
  res.setHeader("Content-Encoding", "gzip");
  await pipeline(createReadStream(pathFor(req.params.id)), createGzip(), res); // constant memory, handles backpressure
});
```

Key ideas:

- **Backpressure:** if the consumer (a slow client) cannot keep up, the stream **pauses the producer** instead of buffering everything. Use **`stream.pipeline`** (or `pipeline` from `node:stream/promises`), which also handles errors and cleans up on failure, unlike a bare `.pipe()`.
- Stream **database cursors** and **S3 objects**, **CSV/JSON lines** exports, and **uploads** (pipe the request into storage). Better still: let clients upload and download **directly to object storage with presigned URLs** so your API never touches the bytes ([Practical Design Problems, Lesson 04](/design-problems/lesson-4)).
- For JSON, prefer **NDJSON** (one object per line) for large exports so consumers can parse incrementally.

## Concurrency: cluster, worker threads, child processes, containers

| Option | What it is | Use for |
|---|---|---|
| **`cluster`** (or PM2 cluster mode) | Several Node **processes** sharing a port, one per CPU core | Using all cores for an I/O-bound API on one machine |
| **`worker_threads`** | Threads inside one process, with their own event loops (can share memory via `SharedArrayBuffer`) | **CPU-bound** tasks (hashing, parsing, image processing) without blocking the main loop |
| **`child_process`** | Spawn a separate program (a CLI tool, ffmpeg, Python) | Running other executables, strong isolation |
| **Horizontal scaling** (containers, many instances behind a load balancer) | More copies of the whole app | The standard cloud answer: scale instances, keep each process simple |

In containerised deployments, most teams run **one Node process per container** and scale the number of containers; `cluster` mostly matters on a plain VM.

## Other practical Node performance habits

- **Never use sync APIs on request paths** (they are fine at startup).
- **Use a fast JSON serialiser** or schema-based serialisation (Fastify's `fast-json-stringify`) for hot endpoints; avoid huge responses; paginate and compress (`gzip` or Brotli, often better at the proxy or CDN).
- **Reuse connections:** HTTP keep-alive agents for outbound calls, a shared database pool.
- **Cap concurrency** when fanning out (`p-limit`) instead of firing thousands of requests at once.
- **Set timeouts** everywhere and **limit request body sizes**.
- **Watch memory:** growing heap usage means a leak (event listeners, unbounded caches, closures). Take heap snapshots; configure `--max-old-space-size` to fit the container.
- **Cache** expensive, repeated work (in-process LRU for tiny hot data, Redis for shared).
- **Use the right Node version** and keep dependencies current: engine improvements are free speedups.
- **Benchmark with realistic load** (`autocannon`, k6) and check p95/p99, not just throughput.

## Common mistakes

1. **CPU-heavy work inside request handlers.**
2. **`*Sync` calls** in hot paths.
3. **Loading whole files or result sets into memory** instead of streaming.
4. **Unbounded `Promise.all`** over big lists.
5. **Using `.pipe()` without error handling**, leaking streams and file descriptors.
6. **Not measuring event-loop lag**, so blocking is invisible until an incident.
7. **Regexes on untrusted input** without checking for catastrophic backtracking.
8. **Believing "async/await" means "runs in parallel"**: it only avoids blocking *while waiting*, not while computing.

## Interview questions

### Q1. What blocks the Node event loop?

Anything that runs synchronously for a long time on the main thread: sync I/O (`readFileSync`), CPU-heavy loops, large `JSON.parse`/`stringify`, catastrophic regexes, big in-memory sorts or aggregations, and synchronous crypto. While it runs no other request is processed. Awaiting I/O does not block the loop.

### Q2. Scenario: p99 latency spikes whenever one report endpoint is hit. Why?

That endpoint is likely doing CPU-bound or synchronous work on the main thread, starving every other request. I would confirm with event-loop-lag metrics and a CPU profile, then move aggregation into the database, offload to a queue and worker (returning `202`), use `worker_threads`, stream the output, or isolate the endpoint in its own service.

### Q3. Streams vs buffering a 2 GB file?

Buffering loads all 2 GB into memory, risking exhaustion and long delays before the first byte. Streaming reads and writes in small chunks with constant memory and backpressure, so the client starts receiving immediately. Use `stream.pipeline` for correct error handling, or hand large transfers to object storage with presigned URLs.

### Q4. Cluster vs worker_threads?

`cluster` forks multiple processes to use several CPU cores for handling requests in parallel, each with its own memory and event loop. `worker_threads` run extra threads inside one process, ideal for offloading CPU-bound tasks while the main thread keeps serving requests. In containers, you usually scale by adding container instances rather than using `cluster`.

### Q5. What is libuv's thread pool and why does it matter?

A default pool of four threads that handles file system operations, `dns.lookup`, some crypto (pbkdf2, scrypt) and zlib. Heavy use of these can saturate the pool and delay unrelated operations, so you may raise `UV_THREADPOOL_SIZE` or move heavy work to workers or other services.

### Q6. How do you detect event-loop blocking in production?

Record event-loop delay with `perf_hooks.monitorEventLoopDelay` and export p50/p99/max as metrics with alerts; correlate with latency spikes and use CPU profiles or flame graphs (Clinic.js, `--cpu-prof`) to find the culprit.

### Q7. What is backpressure?

A mechanism where a slow consumer signals the producer to pause, so data is not buffered without limit. Node streams implement it; `pipeline` wires it up and ensures cleanup. Without it a fast source and slow client can exhaust memory.

### Q8. Does async/await make code parallel?

No. It lets the single thread do other work while *waiting* for I/O, but JavaScript callbacks still run one at a time. CPU-bound work in an `async` function still blocks the loop. For parallel CPU work you need worker threads, processes or separate services.

### Q9. Scenario: a 4-core server runs one Node process at 100% on one core while the others idle. What do you do?

Node runs JavaScript on one thread, so a single process uses one core. Run several processes (cluster, PM2 or several containers behind a load balancer) for I/O-bound traffic, and use worker threads or a job queue for CPU-heavy tasks. Also check what the hot path is with a CPU profile: removing synchronous work or JSON bloat may help more than adding cores.

## Key takeaways

- **One JS thread:** keep request handlers short, async and free of CPU-heavy or synchronous work.
- Measure **event-loop lag** and alert on it; profile with flame graphs.
- **Stream** large data with `pipeline` and backpressure, or bypass the server with presigned URLs.
- Offload heavy computation to the **database, a queue plus worker, or `worker_threads`**; scale out with more instances.
- The libuv thread pool (default 4) serves fs, DNS lookup, some crypto and zlib.
