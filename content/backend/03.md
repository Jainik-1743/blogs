> **In one line:** treat every byte from outside your process as hostile until a schema says otherwise. Validate **at the edge**, convert it into a trusted typed object ("parse, don't validate"), and let the database constraints be the last line of defence.

You already validate forms in the frontend. Backend validation is a different job: the browser's checks are a *convenience for honest users*, while the server's checks are the *security boundary*. Anyone can call your API with `curl` and send anything.

## Why validate on the server (and everywhere)

| Where | Purpose | Trustworthy? |
|---|---|---|
| **Client (browser)** | Fast feedback, better UX | **No.** Trivially bypassed |
| **Server (API edge)** | Reject malformed or malicious input before it reaches logic | **Yes.** The authoritative check |
| **Business layer** | Rules that need data ("coupon still valid?") | Yes |
| **Database** | Constraints: `NOT NULL`, `UNIQUE`, `CHECK`, foreign keys | Yes, the final safety net |

So the answer to "where should validation happen: client, server or database?" is **all three, for different reasons**, with the server edge as the primary guard.

## Parse, don't validate

Instead of checking a value and then continuing to pass around the *unchecked* type, **parse** the raw input into a new, **typed and trusted** value. After parsing, the rest of the code needs no more defensive checks.

```ts
import { z } from "zod";

export const createOrderSchema = z.object({
  items: z
    .array(z.object({ sku: z.string().min(1).max(64), qty: z.number().int().min(1).max(100) }))
    .min(1)
    .max(50),
  couponCode: z.string().trim().toUpperCase().max(32).optional(),
  note: z.string().trim().max(500).optional(),
}).strict(); // reject unknown fields

export type CreateOrderInput = z.infer<typeof createOrderSchema>; // the TypeScript type comes from the schema
```

`z.infer` means the **schema is the single source of truth** for both runtime checks and compile-time types. (Zod is one popular choice; Valibot, ArkType, Joi, Yup and TypeBox follow the same idea.)

> [!note] **Zod 3 vs Zod 4.** The examples use the long-standing chained style (`.strict()`, `z.string().uuid()`), which still works. Zod 4 promotes these to top-level helpers (`z.strictObject({ … })`, `z.uuid()`, `z.email()`) and deprecates the chained forms, and its `z.uuid()` is stricter than the old check. Match the version in your project.

### A reusable validation middleware

```ts
import type { RequestHandler } from "express";
import type { ZodTypeAny } from "zod";
import { ValidationError } from "../shared/errors";

export const validate =
  (schemas: { body?: ZodTypeAny; query?: ZodTypeAny; params?: ZodTypeAny }): RequestHandler =>
  (req, _res, next) => {
    const issues: { where: string; path: string; message: string; code: string }[] = [];
    for (const key of ["params", "query", "body"] as const) {
      const schema = schemas[key];
      if (!schema) continue;
      const result = schema.safeParse(req[key]);
      if (result.success) {
        if (key === "body") req.body = result.data;       // replace with the parsed, typed value
        else (req as any)[`valid${key[0].toUpperCase()}${key.slice(1)}`] = result.data;
      } else {
        for (const i of result.error.issues) issues.push({ where: key, path: i.path.join("."), message: i.message, code: i.code });
      }
    }
    if (issues.length) return next(new ValidationError("Validation failed", issues));
    next();
  };
```

> [!note] In Express 5, `req.query` is a read-only getter, so you cannot assign the parsed result back onto it. Store parsed values on another property (as above) or in `res.locals`. In Express 4 many examples reassign `req.query`; that pattern no longer works.

## Query parameters and path params are strings

Everything in a URL arrives as a **string**. Coerce deliberately:

```ts
export const listOrdersQuery = z.object({
  status: z.enum(["pending", "paid", "shipped", "cancelled"]).optional(),
  limit: z.coerce.number().int().min(1).max(100).default(20),
  cursor: z.string().max(200).optional(),
  sort: z.enum(["createdAt", "-createdAt", "total", "-total"]).default("-createdAt"),
});
export const idParams = z.object({ id: z.string().uuid() });
```

An allow-list `enum` for `sort` and `status` is also an **injection defence**: only known values reach the query builder.

## Mass assignment (over-posting)

**Scenario:** the frontend sends an extra `isAdmin: true` field. If your code does:

```ts
// ❌ DANGEROUS: whatever the client sent goes straight into the database
await prisma.user.update({ where: { id }, data: req.body });
```

then a malicious client can set fields you never intended: `isAdmin`, `role`, `balance`, `emailVerified`, `ownerId`.

Defences:

1. **Whitelist fields via the schema.** Build the update object from the **parsed** schema (which contains only allowed keys), never from raw `req.body`. `.strict()` also **rejects** unknown keys outright.
2. **Separate schemas per use case:** `updateProfileSchema` (name, avatar) is not the same as an admin's `updateUserRoleSchema`.
3. **Never let the client dictate ownership or server-controlled values.** Set `userId` from the authenticated session, set timestamps and status on the server.
4. **Keep the DTO distinct from the database model.** A DTO (data transfer object) is the shape of the **API contract**; the database entity has more (internal flags, hashes, audit fields). Map between them explicitly and return only intended fields (never `passwordHash`).

```ts
const updateProfileSchema = z.object({ displayName: z.string().min(1).max(60), bio: z.string().max(280).optional() }).strict();

const data = updateProfileSchema.parse(req.body);                 // only these two keys can pass
await prisma.user.update({ where: { id: req.user!.id }, data });  // id comes from the session, not the body
```

## Validation errors vs business-rule errors

Keep them distinct, because the client reacts differently:

| Kind | Example | Status | Client action |
|---|---|---|---|
| **Malformed or invalid input** | `qty: -3`, invalid email, missing field | `400` or `422` with field errors | Highlight the field |
| **Business-rule violation** | "Insufficient stock", "Coupon expired", "Order already shipped" | `409` or `422` with a domain `code` | Show a message and offer an alternative |
| **Not found / not allowed** | Unknown order, someone else's order | `404` / `403` | Navigate away or show access error |

Pick `400` vs `422` for validation once and stay consistent ([HTTP semantics](/browser/lesson-6)). Return paths so the frontend can map errors to inputs:

```json
{ "status": 422, "title": "Validation failed",
  "errors": [{ "path": "items.0.qty", "code": "too_small", "message": "Number must be greater than or equal to 1" }] }
```

## Share types and schemas with the frontend

Contract drift (backend changes a field, the frontend breaks in production) is a classic bug. Options, from simplest to strongest:

1. **Shared package in a monorepo** (`packages/schemas`) exporting Zod schemas and inferred types, imported by both the Next.js app and the API. One definition, impossible to drift.
2. **OpenAPI as the source of truth**, with generated TypeScript types and clients (`openapi-typescript`) or a typed layer such as tRPC for TypeScript-only stacks.
3. **Generate the OpenAPI spec from the schemas** (for example `zod-to-openapi`), so documentation never lags.

Client-side use of the same schema gives instant form feedback; the server still validates independently.

## Other input hygiene

- **Limit body size** (`express.json({ limit: "100kb" })`) and the number of array items. Unbounded input is a denial-of-service vector.
- **Check `Content-Type`.** Reject unexpected types with `415`.
- **Validate and normalise early:** trim strings, lowercase emails, convert dates to `Date` once.
- **Sanitise only where it makes sense.** *Validation* decides whether data is acceptable; *escaping/encoding* happens at **output** (HTML, SQL parameters). Do not try to strip "bad characters" as a security strategy.
- **Parameterise queries.** Use the ORM or `$1` placeholders; never build SQL with string concatenation. (Prisma's tagged `$queryRaw` template is parameterised; `$queryRawUnsafe` with interpolation is not.)
- **Validate files**: size, declared and detected type, extension; store outside the web root or in object storage ([Practical Design Problems, Lesson 04](/design-problems/lesson-4)).
- **Validate configuration at startup** (`env.ts` with a schema) so missing secrets crash the process immediately rather than at 3 a.m.:

```ts
export const env = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]),
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_PUBLIC_KEY: z.string().min(1),
}).parse(process.env);
```

- **Let the database enforce invariants** too: `UNIQUE (email)`, `CHECK (qty > 0)`, `NOT NULL`, foreign keys. Application checks race (two requests can both pass a "does the email exist?" check); a unique constraint cannot. Catch the constraint error and map it to `409`.

## Common mistakes

1. **Trusting the frontend's validation.**
2. **Spreading `req.body` into database writes** (mass assignment).
3. **Validating but then using the original untyped input**, instead of the parsed result.
4. **No size limits** on bodies, arrays and strings.
5. **Forgetting that query and path params are strings** (`"0"` is truthy, `"false"` is not a boolean).
6. **Mixing validation errors and business errors**, returning the same status for both.
7. **Check-then-insert races** with no unique constraint behind them.
8. **Hand-rolled regexes for emails and URLs** instead of tested libraries and `new URL()`.

## Interview questions

### Q1. Where should validation happen: client, server or database?

All three. The client validates for user experience; the server is the authoritative security boundary and validates every request; the database enforces invariants (unique, not null, check, foreign keys) because application checks can race. The server edge is where untrusted data first becomes trusted typed data.

### Q2. Scenario: the frontend sends an extra `isAdmin` field. What stops mass assignment?

I never pass raw `req.body` to the database. A schema defines exactly which fields each endpoint accepts (`.strict()` rejects extras), I build the write from the *parsed* output, and server-controlled values (`userId`, role, timestamps) come from the session or code, never from the client. Separate schemas per use case ensure ordinary users cannot even express an admin-only change.

### Q3. How do you share types between Next.js and the API?

Put the schemas in a shared package in a monorepo and infer TypeScript types from them (`z.infer`), so both sides use one definition. Alternatively, treat an OpenAPI document as the contract and generate types and clients from it. Either way, contract drift becomes a compile-time error, and the server still validates independently.

### Q4. What does "parse, don't validate" mean?

Instead of checking a value and continuing with the same untyped data, convert raw input into a new typed value that is guaranteed valid by construction. Downstream code receives the parsed type, so it cannot accidentally use unvalidated data, and it needs no repeated defensive checks.

### Q5. How do you differentiate validation errors from business-rule errors?

Validation errors mean the request is malformed or violates declared constraints (400 or 422 with field paths). Business-rule errors mean the request is well-formed but conflicts with the current domain state (409 or 422 with a domain code such as `INSUFFICIENT_STOCK`). Distinct codes let the client highlight fields in one case and show a contextual message in the other.

### Q6. Why do you still need database constraints if the app validates?

Because application-level checks are subject to races (two concurrent requests can both pass a "does this email exist?" check) and bugs in other code paths (scripts, other services). A unique constraint or check constraint is atomic and cannot be bypassed; the app catches the violation and maps it to a `409`.

### Q7. What are the risks of unbounded input?

Huge JSON bodies, deeply nested objects, very long strings and enormous arrays consume memory and CPU, enabling denial of service. Set request-size limits, array and string length caps, pagination maximums and timeouts.

### Q8. How do you stop SQL injection in a Node API?

Use parameterised queries through the ORM or driver placeholders, never string-concatenated SQL. Allow-list identifiers that cannot be parameterised (sort columns, table names). Use least-privilege database accounts, and treat raw-query escape hatches (`$queryRawUnsafe`) as code-review red flags.

### Q9. Scenario: the frontend sends dates as strings in four different formats and some are silently wrong. What do you do?

Define one wire format (ISO 8601, UTC) in the API contract and the schema, reject everything else with a clear 422, and convert once at the boundary. Never rely on `new Date(string)` guessing formats. Share the schema with the frontend so the format cannot drift, and add tests around time zones and daylight-saving edges.

## Key takeaways

- **Validate at the edge**, on the server, always. Client checks are UX, not security.
- **Parse into typed objects** with a schema; let `z.infer` give you the types.
- Defend against **mass assignment** with strict, per-endpoint schemas and server-set fields.
- Separate **validation errors** from **business-rule errors**; return field paths.
- Share schemas (monorepo or OpenAPI) so the frontend and backend cannot drift.
- Cap sizes, parameterise queries, validate config at startup and back everything with **database constraints**.
