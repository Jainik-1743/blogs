> **In one line:** a good folder structure makes the *dependency direction* obvious: HTTP at the edge, business logic in the middle, data access at the bottom, and nothing reaching upward. Layers keep concerns apart; feature folders keep related code together. Most mature projects use **both**.

"How do you structure an Express/Node API?" is a question about **boundaries**. The folder names are secondary. The answer interviewers want is *what goes where, and why the request object never leaves the controller*.

## The four layers

```text
HTTP request
   │
   ▼
Routes        ← URL + method → which controller function; attaches middleware
   │
   ▼
Controllers   ← translate HTTP ⇄ application: parse input, call a service, shape the response
   │
   ▼
Services      ← business rules and use cases; orchestration; transactions
   │
   ▼
Repositories  ← data access: the only place that knows about the ORM or SQL
   │
   ▼
Database / external APIs
```

| Layer | Responsible for | Must **not** |
|---|---|---|
| **Routes** | Mapping `METHOD /path` to a handler, applying middleware (auth, validation, rate limits) | Contain logic |
| **Controllers** | Reading `req` (params, query, body, user), calling **one** service function, choosing the status code and response shape | Know about the database; contain business rules |
| **Services** | Business rules, use cases, calling multiple repositories and external services, transaction boundaries, authorization decisions that need data | Import `express`; see `req`/`res`; know HTTP status codes |
| **Repositories** | Queries and persistence (Prisma/SQL), mapping rows to domain objects | Contain business decisions |

The **dependency rule**: arrows point **down** only. A service never imports a controller. A repository never imports a service. This is what makes each layer testable and replaceable.

### Why the request object must never reach a service

```ts
// ❌ The service now depends on Express
async function createOrder(req: Request) {
  const userId = req.user.id;           // hidden coupling to the auth middleware
  const items = req.body.items;
  ...
}

// ✅ The service takes plain, typed data
async function createOrder(input: { userId: string; items: OrderItemInput[] }): Promise<Order> { ... }
```

Why it matters:

- **Reuse:** the same `createOrder` can be called from a queue worker, a cron job, a CLI script or a GraphQL resolver. None of them has a `req`.
- **Testing:** calling `createOrder({ userId, items })` needs no HTTP mock.
- **Clarity:** the function signature **states** its inputs. With `req` they are a mystery bag.

## Layer folders vs feature (component) folders

### By layer (technical grouping)

```text
src/
  routes/       orders.routes.ts, users.routes.ts, ...
  controllers/  orders.controller.ts, users.controller.ts, ...
  services/     orders.service.ts, users.service.ts, ...
  repositories/ orders.repo.ts, users.repo.ts, ...
```

Fine at first. Problem: one feature (orders) is **scattered across four folders**, and every change touches all of them. Folders grow to dozens of unrelated files.

### By feature / business component (recommended as the app grows)

```text
src/
  modules/
    orders/
      orders.routes.ts
      orders.controller.ts
      orders.service.ts
      orders.repository.ts
      orders.schema.ts      ← validation schemas (Zod)
      orders.types.ts
      orders.test.ts
    users/
      ...
    payments/
      ...
  shared/
    errors.ts               ← AppError and subclasses
    http.ts                 ← helpers used by controllers
    logger.ts
  middleware/
    auth.ts
    validate.ts
    error-handler.ts
    request-id.ts
  config/
    env.ts                  ← parsed, validated environment (one place)
  lib/
    prisma.ts               ← the single PrismaClient
  app.ts                    ← builds the Express app (no listen)
  server.ts                 ← starts listening, handles shutdown
```

You **keep the layers inside each feature** while grouping by business area. This is what community guidance recommends for Node: structure by **business components** first, layers within. Benefits:

- A feature's code lives together: easy to find, change and (later) extract into its own service.
- Teams can own modules.
- Modules expose a **small public surface** (for example only `orders.service.ts` is imported elsewhere); internals stay private.

**Rule for modules:** one module may call another module's **service**, never its repository or tables directly. Otherwise you re-create a tangle.

## `app.ts` vs `server.ts`

Separate **building** the app from **starting** it:

```ts
// app.ts — importable by tests; no network
import express from "express";
import { ordersRouter } from "./modules/orders/orders.routes";
import { errorHandler } from "./middleware/error-handler";

export function buildApp() {
  const app = express();
  app.use(express.json({ limit: "100kb" }));
  app.use("/v1/orders", ordersRouter);
  app.use(errorHandler); // last
  return app;
}

// server.ts — the only file that listens
import { buildApp } from "./app";
import { env } from "./config/env";

const server = buildApp().listen(env.PORT, () => console.log(`listening on ${env.PORT}`));
process.on("SIGTERM", () => server.close(() => process.exit(0))); // graceful shutdown
```

Tests import `buildApp()` and call it with Supertest without opening a port.

## A vertical slice, end to end

```ts
// orders.routes.ts
import { Router } from "express";
import { requireAuth } from "../../middleware/auth";
import { validate } from "../../middleware/validate";
import { createOrderSchema } from "./orders.schema";
import * as controller from "./orders.controller";

export const ordersRouter = Router();
ordersRouter.post("/", requireAuth, validate({ body: createOrderSchema }), controller.create);
ordersRouter.get("/:id", requireAuth, controller.getOne);

// orders.controller.ts — HTTP in, HTTP out; nothing else
import type { Request, Response } from "express";
import * as service from "./orders.service";

export async function create(req: Request, res: Response) {
  const order = await service.createOrder({ userId: req.user!.id, items: req.body.items });
  res.status(201).location(`/v1/orders/${order.id}`).json(order);
}

export async function getOne(req: Request, res: Response) {
  const order = await service.getOrderForUser({ orderId: req.params.id, userId: req.user!.id });
  res.json(order);
}

// orders.service.ts — business rules; no Express
import { NotFoundError } from "../../shared/errors";
import * as repo from "./orders.repository";

export async function createOrder(input: { userId: string; items: { sku: string; qty: number }[] }) {
  if (input.items.length === 0) throw new ValidationError("Order needs at least one item");
  const priced = await repo.priceItems(input.items);
  return repo.insertOrder({ userId: input.userId, lines: priced, total: sum(priced) });
}

export async function getOrderForUser({ orderId, userId }: { orderId: string; userId: string }) {
  const order = await repo.findByIdForUser(orderId, userId); // ownership is part of the query
  if (!order) throw new NotFoundError("Order");              // 404 also for "not yours": no information leak
  return order;
}

// orders.repository.ts — the only file that knows Prisma
import { prisma } from "../../lib/prisma";

export const findByIdForUser = (id: string, userId: string) =>
  prisma.order.findFirst({ where: { id, userId }, include: { lines: true } });
```

With Express 5, a rejected promise from `create` is forwarded to the error middleware automatically ([Lesson 04](/backend/lesson-4)). With Express 4 you need a small `asyncHandler` wrapper.

## Where do these things live?

| Concern | Where | Why |
|---|---|---|
| **Input validation** (shape, types, required) | Middleware or the top of the controller, using schemas | Reject bad data at the edge, before any logic ([Lesson 03](/backend/lesson-3)) |
| **Business validation** ("stock available", "coupon not expired") | Service | It needs data and is a domain rule |
| **Authentication** ("who are you?") | Middleware | Same for every protected route |
| **Authorization** ("may you do this?") | Service or a policy function, backed by repository queries that include ownership | It depends on the data; do not rely on route-level checks alone ([Lesson 06](/backend/lesson-6)) |
| **Transactions** | Service (the unit of work), executed through the repository | One use case = one atomic operation |
| **Rate limiting, CORS, request ID, logging** | Middleware | Cross-cutting, order matters |
| **Environment config** | One `config/env.ts` validated at startup | Fail fast if a variable is missing |
| **Error translation** (domain error to HTTP) | One error-handling middleware | Consistent responses ([Lesson 04](/backend/lesson-4)) |
| **Third-party calls** (Stripe, email) | A small client/adapter module injected into services | Easy to fake in tests |

## Scenario: you need a CLI and a queue worker that reuse the same logic

If your service functions take plain arguments and return plain results, the worker simply imports `orders.service` and calls `createOrder(...)`. If logic lives in controllers, or services read `req`, you must duplicate it or fake HTTP objects. **That scenario is the test of whether your structure is real.**

## Do you need the repository layer?

Honest answer: it depends.

- **For:** hides the ORM, gives one place for queries, easy to fake in unit tests, keeps services free of database types.
- **Against:** with Prisma, the client is already a typed data layer. A repository that merely forwards calls adds files without value ("ceremony").
- **Pragmatic rule:** introduce repositories when queries are non-trivial or reused, when you need to fake persistence in unit tests, or when you want ownership and tenancy rules enforced in one place. For simple CRUD modules, calling Prisma from a service may be fine. State your reasoning in the interview; both answers are defensible, an unexamined one is not.

## Growing the structure

- **Start simple:** a flat `src/` with a handful of files is fine for a small service. Do not build a cathedral on day one.
- **Split by module** once features appear.
- **Extract to a package or service** only when a module has a stable interface and independent scaling or ownership needs (a "modular monolith" first, microservices later if ever).
- Keep an **`index.ts`** per module exporting only what other modules may use.

## Common mistakes

1. **Passing `req`/`res` into services**, tying business logic to HTTP.
2. **Fat controllers** that query the database and contain rules.
3. **Anemic everything:** every layer only forwards to the next with no purpose.
4. **Cross-module database access** (module A querying module B's tables).
5. **`utils/` and `helpers/` junk drawers** that become dependencies of everything.
6. **Reading `process.env` all over the code** instead of one validated config module.
7. **Mixing `app` creation and `listen`**, which makes testing awkward.
8. **Circular imports** between modules.

## Interview questions

### Q1. Why separate controllers from services?

Controllers translate HTTP (parse input, choose status codes). Services hold business rules and are independent of the transport. Separating them lets the same logic be reused from jobs, CLIs or other entry points, makes it testable without HTTP, and means a change in the API contract does not touch business rules.

### Q2. Where does validation live? Where does authorization live?

Input validation (shape, types) happens at the edge in middleware or the controller using a schema, so bad data never reaches the service. Business validation lives in the service because it needs data. Authentication is middleware; authorization lives in the service or a policy function and is enforced in the data query itself (for example `where: { id, userId }`), not only in a route guard.

### Q3. Scenario: you need a CLI and a queue worker that reuse the same logic. Does your structure allow it?

Yes if the logic lives in services with plain-argument functions and no `req`/`res`. The CLI and worker import and call the same service. If the logic is in controllers, I would first extract it into services, then reuse it, rather than copying it.

### Q4. Feature folders vs layer folders?

Layers are fine for small apps, but they scatter one feature across many folders. Feature (business-component) folders keep related code together and scale better, and I keep the layered split *inside* each module. Modules call each other only through public service functions.

### Q5. Why separate `app.ts` and `server.ts`?

`app.ts` builds and exports the Express app without opening a port, so tests can import it and use Supertest. `server.ts` is the only file that listens and handles process signals, which keeps startup concerns apart from application logic.

### Q6. Do you always need a repository layer?

No. Use it when queries are complex or shared, when you want to fake persistence in unit tests, or to centralise rules like tenancy and ownership. For simple CRUD with Prisma, a service calling the client directly can be simpler. I decide per module and avoid pass-through layers.

### Q7. Where should database transactions be started?

In the service, because a transaction represents one business use case spanning several operations. The service opens it (often via a helper from the repository or ORM) and passes the transaction handle to repository functions so they all participate.

### Q8. How do you stop modules from becoming tangled?

Define a public surface per module (only the service is importable by others), forbid cross-module repository/table access, enforce boundaries with lint or dependency-cruiser rules, and avoid circular imports. When coupling is unavoidable, communicate through events or explicit interfaces.

## Key takeaways

- **Routes → controllers → services → repositories**, dependencies pointing down only.
- Controllers speak **HTTP**; services speak **business**; repositories speak **data**. **`req` never enters a service.**
- Group **by feature**, keep layers inside each feature, and expose a small public surface per module.
- Separate `buildApp()` from `listen()`; centralise config, errors and middleware.
- Add layers when they earn their keep: structure is a means to testability and change, not an end.
