> **In one line:** REST gives you **simple, cacheable, resource-shaped** endpoints; GraphQL gives clients **exactly the data they ask for** from one endpoint, at the price of caching, security and N+1 complexity; Hasura gives you GraphQL **over Postgres almost for free**, at the price of moving logic into configuration. Choose by the problem, not the trend.

You have used GraphQL and Hasura from the client side. Interviewers want to hear the **trade-offs from the server side**: where each style hurts and how you mitigate it.

## The core difference

| | REST | GraphQL |
|---|---|---|
| **Shape** | Many endpoints, each returns a fixed shape | One endpoint; the **client describes** the response shape |
| **Over/under-fetching** | Common: too many fields, or several round trips for related data | Largely solved: ask for exactly what you need in one request |
| **Versioning** | URL or header versions | Evolve the schema; deprecate fields |
| **Caching** | **Easy**: HTTP caching, CDNs, ETags work out of the box | **Harder**: usually `POST` to one URL; needs client-side normalised caches or persisted queries |
| **Typing** | Optional (OpenAPI) | **Built in**: schema is the contract, great tooling |
| **Errors** | HTTP status codes | Usually `200` with an `errors` array and partial `data` |
| **File uploads** | Natural (`multipart`) | Awkward (needs a spec extension or presigned URLs) |
| **Learning curve** | Low | Higher (schema design, resolvers, dataloaders) |
| **Real-time** | Polling, SSE, WebSockets separately | **Subscriptions** (over WebSockets) in the spec |

## Over- and under-fetching

- **Over-fetching:** `GET /users/1` returns 30 fields when the screen needs a name and an avatar.
- **Under-fetching:** to render a profile page you call `/users/1`, then `/users/1/posts`, then `/posts/9/comments`: a **waterfall** of requests, each adding latency.

GraphQL lets the screen ask for what it needs:

```graphql
query ProfilePage($id: ID!) {
  user(id: $id) {
    name
    avatarUrl
    posts(first: 5) { id title commentCount }
  }
}
```

REST has answers too: sparse fieldsets (`?fields=`), expansion (`?expand=posts`), purpose-built **composite endpoints** (`/profile-page/1`) or a **backend-for-frontend** layer ([Browser Contract, Lesson 03](/browser/lesson-3)) shaped for each client. When an app has many different clients with different needs, GraphQL's flexibility pays off; when screens map neatly to endpoints, REST plus a BFF is simpler.

## Caching: the biggest practical difference

### REST

`GET /products/5` is a URL; any browser, proxy or CDN can cache it with `Cache-Control` and revalidate with `ETag` ([Browser Contract, Lesson 05](/browser/lesson-5)). Public, read-heavy APIs benefit enormously.

### GraphQL

All queries usually go to `POST /graphql`, and `POST` responses are not cached by default. Options:

1. **Client-side normalised caches** (Apollo Client, urql, Relay) store entities by `__typename + id`, so one query's result updates every screen that shows that entity.
2. **Persisted queries / automatic persisted queries (APQ):** the client sends a hash of a known query instead of the whole text, and it can use `GET /graphql?id=…`, which **CDNs can cache**.
3. **Response caching** per field or per query on the server (`@cacheControl` hints), keyed by the query and variables, only for public, non-personalised data.
4. **Cache at the data layer:** DataLoader (per request) and Redis for expensive lookups.

> [!warn] GraphQL makes **HTTP-level** caching hard, not impossible. If your API is a public, cache-heavy, read-mostly service (a product catalogue behind a CDN), that is a point for REST.

## Schema evolution

REST usually versions (`/v1`, `/v2`). GraphQL's convention is to **never remove fields abruptly**: add new fields freely, mark old ones `@deprecated(reason: "...")`, watch usage metrics from the schema registry, and remove when no client asks for them. Because clients request only the fields they use, additive changes are non-breaking. Changing a field's type, nullability or arguments **is** breaking.

## The server-side risks of GraphQL

Clients choose the query, so a client can ask for something **very expensive**.

### 1. Deeply nested and expensive queries

```graphql
{ user(id: 1) { friends { friends { friends { friends { name } } } } } }
```

Each level multiplies the work. Defences:

- **Depth limiting:** reject queries deeper than N.
- **Complexity / cost analysis:** assign a cost to each field (and multiply by list sizes), and reject queries over a budget per request and per client.
- **Pagination required** on every list; cap `first`/`limit`.
- **Timeouts** on resolvers and the whole request.
- **Persisted-query allow-list** for public clients: only pre-approved query documents may run. This is the strongest defence for first-party apps.
- **Rate limit by query cost**, not just by request count.

### 2. Batching and alias abuse

A single request can contain thousands of aliases or batched operations that bypass per-request rate limits (for example 1,000 `login` mutations aliased in one query). Limit aliases, batch sizes and per-field rate limits, and protect sensitive mutations separately.

### 3. Introspection and field suggestions

Introspection exposes the full schema. Many teams disable it (and field-suggestion hints) in production for private APIs, though it is not a substitute for authorization.

### 4. Authorization

Authorization must be enforced **per field and per object in resolvers or a policy layer** ([Lesson 06](/backend/lesson-6)); a query can reach the same object through many paths, so guarding only the top-level resolver leaks data (a classic GraphQL BOLA).

### 5. N+1 in resolvers

The `User.posts` resolver runs once per user. Use **DataLoader per request** ([Lesson 08](/backend/lesson-8)).

### 6. Errors

A GraphQL response can be `200` with partial `data` and an `errors` array. Make sure monitoring counts errors by inspecting the body, not only HTTP status; map domain errors to stable `extensions.code` values.

## Where Hasura fits

**Hasura** connects to PostgreSQL (and other sources) and **auto-generates** a GraphQL API: queries, mutations, filters, pagination, relationships and subscriptions, with no resolvers to write. It compiles a nested GraphQL query into **one SQL query**, so N+1 is not a concern.

| Strengths | Trade-offs |
|---|---|
| Instant, typed API over your schema; huge velocity | Business logic moves into **metadata and configuration** (permissions, actions, event triggers), which needs its own discipline: version control, migrations, review |
| **Row-level permissions** declared per role (`{ user_id: { _eq: "X-Hasura-User-Id" } }`) | Permission rules become part of your security model; mistakes are easy to miss without tests |
| Subscriptions and live queries built in | Complex rules and workflows need **Actions**, **event triggers** or remote schemas, i.e. you still write backend code |
| Fast to prototype and build admin tools | Coupling to Hasura's model and conventions; data schema shapes the API directly |

Hasura is a strong fit for CRUD-heavy products with a Postgres-centred model; it is less natural when most of your value is custom domain logic or when you want the API shape decoupled from table design.

## When GraphQL is the wrong choice

- A **simple CRUD API** with a handful of clients: REST is less machinery.
- A **public API with heavy CDN caching** and many third-party consumers.
- **File-heavy** or streaming workloads.
- A **small team** without the capacity to run schema governance, cost limits and dataloaders.
- **Strict, simple contracts between services:** gRPC or REST are usually better for service-to-service.
- When you cannot invest in **GraphQL security** (cost analysis, persisted queries, field-level auth).

## When GraphQL shines

- **Many clients (web, iOS, Android, partners) needing different shapes** of the same data.
- **Deeply related data** where REST would need waterfalls.
- **Fast-moving frontends** that change what data they need without waiting for backend endpoints.
- Teams that value a **strongly typed schema and generated types** end to end.
- Aggregating **several backends** behind one graph (federation or schema stitching).

## Scenario: mobile and web need the same data in different shapes. What do you pick?

Options and how I would decide:

1. **GraphQL**: each client queries what it needs; one backend, strong types. Worth it if there are several clients or frequent UI changes, and you will invest in cost limits and dataloaders.
2. **REST with a BFF per client**: a thin server for mobile and another for web, each calling the same domain services and returning a tailored shape. Simpler operations and caching, more code per client.
3. **REST with sparse fields/expansion**: enough when differences are small.

For one web app and one mobile app on a small team, option 3 or 2 is often enough; as client count and variety grow, GraphQL's benefits outweigh its cost.

## Common mistakes

1. **Choosing GraphQL by default**, then fighting caching and N+1 without the tooling.
2. **No depth, complexity or pagination limits** on a public GraphQL endpoint.
3. **Authorization only on the root field**, not on nested objects.
4. **Global DataLoaders**, or resolvers that bypass them.
5. **Monitoring only HTTP status**, missing `200` responses full of errors.
6. **Using Hasura permissions casually**, without tests for every role.
7. **Treating REST as "outdated"** when HTTP caching and simplicity are what the problem needs.
8. **Breaking schema changes** (type or nullability changes) without a deprecation path.

## Interview questions

### Q1. When is GraphQL the wrong choice?

For simple CRUD APIs with few clients, cache-heavy public APIs that depend on CDN/HTTP caching, file-heavy or streaming workloads, service-to-service contracts, and teams that cannot afford the operational work of cost limiting, persisted queries and schema governance. In those cases REST (or gRPC internally) is simpler and cheaper.

### Q2. How do you cache GraphQL responses?

Use normalised client caches (Apollo, urql, Relay) for the UI, persisted queries so requests become cacheable `GET`s for CDNs, server-side response caching with cache-control hints for public data, and a data-layer cache (Redis, per-request DataLoader). Personalised data is cached per user or not at all.

### Q3. How do you block a malicious, deeply nested query?

Limit query depth, run cost/complexity analysis with a per-request budget, require and cap pagination, set resolver and request timeouts, limit aliases and batch sizes, and use persisted-query allow-lists for first-party clients. Combine with authentication and cost-based rate limiting.

### Q4. Scenario: mobile and web need the same data in different shapes. What do you pick?

With several clients and shifting needs I would choose GraphQL so each client requests its own shape, accepting the cost of dataloaders, cost limits and schema governance. For one or two clients on a small team, a REST API with sparse fieldsets or a BFF per client is usually cheaper and easier to cache. The decision rests on client variety, team capacity and caching needs.

### Q5. What problem does Hasura solve, and what are its trade-offs?

It auto-generates a typed GraphQL API over Postgres with role-based row-level permissions, relationships and subscriptions, compiling nested queries to single SQL statements. That removes boilerplate and N+1. The trade-offs: logic and permissions live in metadata that must be versioned and tested, custom workflows need actions or event triggers, and the API is coupled to the database model.

### Q6. How do you evolve a GraphQL schema without breaking clients?

Add fields and types freely, deprecate rather than remove fields, track field usage, and remove only when unused. Avoid changing types, nullability or argument requirements of existing fields. For breaking changes use a migration path with new fields, or schema versioning via the registry and CI checks.

### Q7. Why does GraphQL often return 200 for errors, and how do you monitor it?

A single request can partially succeed, so the protocol carries `data` and `errors` together under a `200`. Monitor by parsing responses (or using server-side instrumentation) to count errors by `extensions.code`, operation name and field, and alert on error rates rather than HTTP status alone.

### Q8. Where does authorization belong in GraphQL?

At the object and field level in the resolver/policy layer (or through database row-level security), because the same entity is reachable through many query paths. Guarding only top-level queries lets nested fields leak data.

### Q9. Scenario: your public GraphQL API is hit by very deep, expensive queries. How do you protect it?

Add depth and complexity limits with a per-request cost budget, require and cap pagination, set resolver and request timeouts, limit aliases and batching, use persisted queries or an allow-list for first-party clients, rate-limit by cost, and use DataLoader to avoid N+1. Log query cost to find abusers and enforce authorization on nested fields.

## Key takeaways

- **REST = simple, cacheable, resource-oriented; GraphQL = flexible, typed, client-shaped at the cost of caching and security work.**
- GraphQL needs **depth/cost limits, pagination caps, persisted queries, field-level authorization and per-request dataloaders**.
- **Hasura** gives instant GraphQL over Postgres with declarative permissions; the price is logic living in metadata.
- Match the style to **client variety, caching needs and team capacity**, not fashion.
