> **In one line:** **authentication** proves *who you are*; **authorization** decides *what you may do*. Most real breaches come from the second: a logged-in user touching data that is not theirs. Check ownership on **every** resource, in the **query**, on the **server**.

The browser-side lessons covered where credentials live ([Browser Contract, Lessons 02-03](/browser/lesson-2)). Here is the backend half: storing passwords, issuing and verifying sessions or tokens, and modelling permissions so they cannot be bypassed.

## Authentication

### Storing passwords

The rules:

1. **Never store passwords** (or anything reversible). Store a **slow, salted, one-way hash**.
2. **Use a password hashing function**, not a general hash. Fast hashes (SHA-256, MD5) can be brute-forced at billions of guesses per second on a GPU.
3. Recommended algorithms (per OWASP's Password Storage guidance, roughly in order of preference): **Argon2id**, then **scrypt**, then **bcrypt** (cost factor of at least 10, with its 72-byte input limit in mind), or PBKDF2 where compliance requires it.
4. A **unique random salt per password** is built into these libraries and stored inside the resulting hash string. A **pepper** (a secret key kept outside the database, for example in a secrets manager) is an optional extra layer.
5. **Use parameters that cost real time** (tens to hundreds of milliseconds), and raise them as hardware improves; store parameters in the hash so you can **rehash on login** when they change.
6. **Compare in constant time** (the libraries do this).

```ts
import argon2 from "argon2";

export const hashPassword = (plain: string) =>
  argon2.hash(plain, { type: argon2.argon2id, memoryCost: 19456, timeCost: 2, parallelism: 1 }); // OWASP's minimum-profile style settings

export async function verifyPassword(hash: string, plain: string) {
  return argon2.verify(hash, plain); // constant-time compare inside
}
```

Because hashing is deliberately expensive (CPU and memory), do it with **asynchronous** APIs so you do not block the event loop ([Lesson 10](/backend/lesson-10)) and **rate-limit login attempts**.

### Login endpoint hygiene

- **Generic failure message:** "Invalid email or password" for both unknown email and wrong password, so you do not reveal which accounts exist (**user enumeration**). Equalise timing too: hash a dummy password when the user is not found.
- **Rate limit and lock out gradually** (per account and per IP) to slow credential stuffing; add **CAPTCHA or MFA** challenges after repeated failures.
- **Support MFA** (TOTP apps, WebAuthn/passkeys). Passkeys remove passwords as the weak link.
- **Regenerate the session ID on login** to prevent **session fixation** (an attacker planting a known session ID before the victim logs in).
- **Password reset:** a long random single-use token, **stored hashed**, short expiry (for example 15–60 minutes), invalidated after use, sent only to the registered email, with a generic response ("If that account exists, we sent an email").
- **Check passwords against known-breach lists** and prefer length over complexity rules; do not impose arbitrary composition rules or force periodic changes.

### Sessions or tokens

Covered in depth in [Browser Contract Lesson 02](/browser/lesson-2). Server-side essentials:

- **Session IDs** must be generated by a cryptographically secure random generator with plenty of entropy. OWASP asks for at least **64 bits**; in practice use 128+ bits (`crypto.randomBytes(32)`).
- Store sessions in **Redis or the database** with an expiry, **idle timeout and absolute timeout**.
- Cookie flags: `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite`.
- **For JWTs:** verify the signature with a **pinned algorithm**, and check `exp`, `iss` and `aud`. Never use `decode` as if it were `verify`. Keep access tokens short-lived and rotate refresh tokens.
- **Logout** destroys the session or revokes the refresh token server-side.

```ts
// Express middleware: authentication only, "who is this?"
export const requireAuth: RequestHandler = async (req, _res, next) => {
  const sid = req.cookies["__Host-sid"];
  const session = sid ? await sessions.get(sid) : null;          // Redis lookup
  if (!session) throw new UnauthorizedError();                    // 401 → "log in"
  req.user = { id: session.userId, role: session.role };
  next();
};
```

## Authorization

Authentication says "this is user 42." Authorization asks "may user 42 do **this action** on **that resource**?" It must be evaluated **on the server, for every request**, using the current data.

### Broken access control

OWASP ranks **Broken Access Control** at the top of its Top 10 list of web application risks, and its API Security list puts **Broken Object Level Authorization (BOLA)** first: the API accepts an object ID and does not verify that the caller may access *that* object. This is also called **IDOR** (insecure direct object reference).

**The classic scenario:** a user changes `/orders/123` to `/orders/124` and sees someone else's order. What failed? **The server authenticated the user but never authorized access to that specific object.** UUIDs make guessing harder but do **not** fix this: authorization checks do.

### Enforce ownership in the query

Put the check **in the data access**, so it is impossible to forget:

```ts
// ❌ Fetches by ID alone. Any logged-in user can read any order.
const order = await prisma.order.findUnique({ where: { id } });

// ✅ Scope by owner: someone else's order simply "doesn't exist" for this user
const order = await prisma.order.findFirst({ where: { id, userId: req.user.id } });
if (!order) throw new NotFoundError("Order"); // 404, not 403, so existence isn't revealed
```

The same applies to **updates and deletes**:

```ts
const { count } = await prisma.post.deleteMany({ where: { id, authorId: user.id } });
if (count === 0) throw new NotFoundError("Post");
```

For multi-tenant systems, **always include `tenantId`** in every query (or enforce it with a Prisma extension or **PostgreSQL row-level security**), so a missing filter cannot leak data across customers.

Also check **function-level** and **property-level** authorization:

- **Function level:** admin-only endpoints must check the role, not rely on being "hidden" ([Lesson 03](/backend/lesson-3), mass assignment).
- **Property level:** a user may update their `displayName` but not their `role`; filter response fields so users cannot see others' private attributes.

### Authorization models

| Model | Idea | Good for | Watch out for |
|---|---|---|---|
| **RBAC** (role-based) | Users have roles; roles have permissions (`admin`, `editor`, `viewer`) | Most apps; simple and auditable | "Role explosion"; cannot express "only their own" without extra checks |
| **ABAC** (attribute-based) | Decisions use attributes of user, resource, action and context (`dept == resource.dept && time in office hours`) | Fine-grained, contextual rules | Harder to reason about and test |
| **ReBAC** (relationship-based) | Access flows from relationships (owner, member of team, shared with) | Sharing models like Drive or GitHub | Needs a graph or a dedicated engine |
| **Ownership checks** | "Is `resource.ownerId === user.id`?" | Almost every endpoint | Easily forgotten without a pattern |

Most backends use **RBAC plus ownership checks**, centralised in **policy functions**:

```ts
// A single place that answers "may this user do this?"
export const can = {
  readOrder:   (u: User, o: Order) => u.role === "admin" || o.userId === u.id,
  cancelOrder: (u: User, o: Order) => (u.role === "admin" || o.userId === u.id) && o.status === "pending",
  refundOrder: (u: User)           => u.role === "admin" || u.role === "support",
};

export async function cancelOrder(user: User, orderId: string) {
  const order = await orders.getById(orderId);
  if (!order || !can.readOrder(user, order)) throw new NotFoundError("Order"); // don't reveal existence
  if (!can.cancelOrder(user, order)) throw new ForbiddenError("Order cannot be cancelled");
  ...
}
```

Policies in one module are testable and auditable. **Default deny:** if no rule says yes, the answer is no.

### Don't trust the client for authorization data

Roles, user IDs, tenant IDs and prices must come from the **session or database**, not from request bodies, headers or hidden form fields. A JWT's claims are trusted only after verification, and stale claims (a demoted admin) are a risk with long-lived tokens.

### `401` vs `403` vs `404`

- `401`: not authenticated.
- `403`: authenticated but not permitted (when the user is allowed to know the resource exists).
- `404`: when revealing that a resource exists would itself leak information (someone else's order).

## Defence in depth

- **Rate limit** authentication and sensitive endpoints ([Practical Design Problems, Lesson 02](/design-problems/lesson-2)).
- **Audit-log** security events: logins, failures, permission changes, data exports (with user IDs, never secrets).
- **Least privilege everywhere:** database users, cloud roles, API keys.
- **Secrets management:** keys in a secrets manager, rotated; never in the repo.
- **Test authorization explicitly:** for each endpoint, write tests that a different user, an unauthenticated user and a lower-privileged role are denied.

```ts
it("does not let user B read user A's order", async () => {
  const order = await createOrderFor(userA);
  const res = await request(app).get(`/v1/orders/${order.id}`).set(authFor(userB));
  expect(res.status).toBe(404);
});
```

## Common mistakes

1. **Checking authentication but not ownership** (the IDOR/BOLA bug).
2. **Authorization only in the UI** or only in a route guard, not in the data layer.
3. **Fast hashes** (SHA-256) or unsalted hashes for passwords; **logging passwords** by accident.
4. **Different error messages** for "no such user" and "wrong password."
5. **Trusting IDs, roles or tenant IDs from the request body.**
6. **Missing session regeneration on login; guessable session IDs.**
7. **Stale roles in long-lived tokens.**
8. **No default-deny**: new endpoints open until someone remembers to protect them.

## Interview questions

### Q1. How do you store passwords?

With a slow, salted, memory-hard password hashing algorithm, preferably Argon2id (or scrypt, or bcrypt with a suitable cost). The library generates a unique salt and embeds the parameters in the output; I verify with the library's constant-time compare, use async APIs, rate-limit logins and rehash on login when parameters are upgraded. Never SHA-256 or reversible encryption.

### Q2. Where do you enforce "users can only edit their own posts"?

On the server, in the data access path: the update or delete query includes the owner (`where: { id, authorId: user.id }`), and a service-level policy function expresses the rule. It is not enough to hide the button in the UI or to rely on a route-level role check, because the object-level decision depends on the specific record.

### Q3. Scenario: changing `/orders/123` to `/orders/124` shows another user's order. What failed?

Broken object-level authorization (IDOR). The endpoint authenticated the caller but did not check that this order belongs to them. Fix it by scoping the query to the current user (or tenant) and returning `404` when no match, add policy functions, add regression tests for cross-user access, and review other endpoints for the same pattern. Using UUIDs alone is not a fix.

### Q4. What are the entropy requirements for session IDs?

They must come from a cryptographically secure random generator and be unguessable; OWASP's guidance is at least 64 bits of entropy, and in practice 128 bits or more (for example 32 random bytes) so brute-forcing is infeasible even with very many active sessions.

### Q5. RBAC vs ABAC?

RBAC grants permissions through roles, which is simple and easy to audit but struggles with "own resources only" and contextual rules. ABAC evaluates attributes of the user, resource, action and context, giving fine-grained rules at the price of complexity. Most apps use RBAC plus explicit ownership checks, and move to ABAC or relationship-based models when requirements demand it.

### Q6. Why return 404 instead of 403 for someone else's resource?

A `403` confirms that the resource exists, which lets attackers enumerate valid IDs and learn about other tenants' data. Returning `404` for objects the user may not even know about avoids that leak. Use `403` when the user legitimately knows the resource exists but lacks permission for the action.

### Q7. What is session fixation and how do you prevent it?

An attacker sets or learns a victim's session ID before login; if the application keeps the same ID after authentication, the attacker now has an authenticated session. Prevent it by issuing a fresh session ID on login (and privilege change), invalidating the old one, and using strict cookie settings.

### Q8. How do you avoid user enumeration at login and reset?

Return the same generic message and status for unknown email and wrong password, make response timing similar (for example verify against a dummy hash), and for password reset always respond "If that account exists, we've sent instructions." Also rate-limit these endpoints.

## Key takeaways

- **Authentication ≠ authorization.** Most severe bugs are missing object-level checks.
- Hash passwords with **Argon2id/scrypt/bcrypt**, never fast hashes; rate-limit and use generic login errors.
- **Scope every query by owner or tenant**; centralise rules in **policy functions**; **default deny**.
- Take roles and IDs from the **session**, not the request; session IDs need high entropy and regeneration on login.
- **Test authorization**: other user, no user, lower role.
