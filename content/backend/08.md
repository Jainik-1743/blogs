> **In one line:** Prisma makes it easy to write code that is correct and accidentally slow. The classic trap is the **N+1 query**: one query for a list, then one more per row. Know how to spot it, three ways to fix it, and how to keep your connection pool from running dry.

You know the Prisma/GraphQL/Hasura stack from the frontend side of the wire. This lesson is the production-backend view: what SQL your code *really* produces, and the settings that decide whether the API survives load.

## The N+1 problem

**N+1** means: 1 query to fetch a list of N items, then N additional queries to fetch something for each item. 101 queries for 100 users.

```ts
// ❌ 1 query for users + N queries for their posts
const users = await prisma.user.findMany({ take: 100 });
for (const user of users) {
  user.posts = await prisma.post.findMany({ where: { authorId: user.id } }); // runs 100 times
}
```

Each query is individually fast (2 ms), which is why N+1 hides in development with 5 rows and explodes in production with 5,000. The cost is **latency multiplied by N** plus **connection pool pressure**.

### Where it hides

- **Loops** with `await` inside (as above).
- **`map` with `Promise.all`:** still N queries, just in parallel (and now they stampede your pool).
- **GraphQL resolvers:** the `posts` field resolver on `User` runs once per user in the list ([Lesson 09](/backend/lesson-9)).
- **ORM lazy loading** in other ORMs (Prisma does not lazy-load, which is good, but your own helper functions can recreate it).
- **Serialisation or "to DTO" mappers** that call the database per item.

### How to detect it

- **Log queries in development**:

```ts
const prisma = new PrismaClient({ log: [{ emit: "event", level: "query" }] });
prisma.$on("query", (e) => console.log(`${e.duration}ms ${e.query}`));
```

- **Count queries per request** in tests (assert "at most 3 queries for this endpoint").
- **Tracing / APM** shows a "waterfall" of repeated identical queries.
- In PostgreSQL, **`pg_stat_statements`** shows statements with huge call counts.
- Look for one endpoint whose latency scales with the **page size**.

## Fix 1: eager loading with `include` / `select`

Tell Prisma which relations to load, and it fetches them together:

```ts
const users = await prisma.user.findMany({
  take: 100,
  include: { posts: { take: 5, orderBy: { createdAt: "desc" } } },
});
```

By default Prisma runs **one query for users and one `WHERE authorId IN (…)` query for all their posts** and joins the result in memory: **2 queries**, not 101. That default is called the **`query`** load strategy.

### Join strategy

Recent Prisma versions can instead ask the database to do the join in a **single SQL query** (using lateral joins and JSON aggregation in PostgreSQL):

```ts
const users = await prisma.user.findMany({
  relationLoadStrategy: "join",       // one query, joined in the database
  include: { posts: true },
});
```

Depending on your Prisma version you may need to enable the `relationJoins` preview feature in the schema (`previewFeatures = ["relationJoins"]`); the feature has been moving from Preview towards general availability, so check the documentation for the version you run.

| Strategy | Queries | Good when | Trade-off |
|---|---|---|---|
| `query` (default) | One per relation level | Large relations, wide rows; lets the app do the merge | More round trips |
| `join` | One total | Many small related rows; latency-sensitive paths | Big, complex SQL; duplicated parent data in a single result; test on your data |

Neither is always better: measure with `EXPLAIN ANALYZE` and real data.

### `select` to trim the payload

```ts
const users = await prisma.user.findMany({
  select: { id: true, name: true, posts: { select: { id: true, title: true } } },
});
```

Fetch only the columns you return. Narrow selects cut data transfer, memory and enable index-only scans. **`include` returns every scalar field of the relation**, so `select` is often the better habit for API endpoints.

## Fix 2: batch it yourself with `in`

When the relationship is not modelled in the schema or you need control:

```ts
const users = await prisma.user.findMany({ take: 100 });
const posts = await prisma.post.findMany({ where: { authorId: { in: users.map((u) => u.id) } } });

const byAuthor = Map.groupBy(posts, (p) => p.authorId);
const result = users.map((u) => ({ ...u, posts: byAuthor.get(u.id) ?? [] }));
```

Two queries, regardless of N. (`Map.groupBy` needs Node 21 or newer, and `lib: ["ES2024"]` in your `tsconfig` for the types; a small `reduce` works otherwise.)

## Fix 3: DataLoader (and Prisma's `findUnique` batching)

DataLoader collects all the keys requested **in the same tick of the event loop** and runs **one** batched query:

```ts
import DataLoader from "dataloader";

export const postsByAuthorLoader = () =>
  new DataLoader<string, Post[]>(async (authorIds) => {
    const posts = await prisma.post.findMany({ where: { authorId: { in: [...authorIds] } } });
    const grouped = Map.groupBy(posts, (p) => p.authorId);
    return authorIds.map((id) => grouped.get(id) ?? []);   // MUST return results in the same order as the keys
  });

// GraphQL: create loaders per request (never share across users) and put them in context
const resolvers = { User: { posts: (user, _args, ctx) => ctx.loaders.postsByAuthor.load(user.id) } };
```

Prisma also ships its own **dataloader for `findUnique`**: multiple `findUnique` calls for the same model in the same tick are automatically batched into one `WHERE id IN (…)` query. That is why a resolver that does `prisma.user.findUnique({ where: { id } })` for each post does not fall over, **as long as the calls are `findUnique`** (not `findFirst` or `findMany`) and happen in the same tick.

> [!note] **Create DataLoaders per request.** Their cache is keyed by ID; a global loader would serve one user's data to another and never refresh.

**Hasura** (and similar GraphQL-to-SQL engines) avoids N+1 by design: it compiles the whole GraphQL query into a single SQL statement, joining nested relations in the database. That is a major reason people adopt it.

## Other Prisma performance habits

- **Paginate** every list (`take`, cursor-based where possible: [Practical Design Problems, Lesson 03](/design-problems/lesson-3)).
- **Index the columns you filter and sort on**, including foreign keys ([Lesson 07](/backend/lesson-7)). Prisma's `@@index` documents them in the schema.
- **Use `_count`** instead of loading rows just to count them: `include: { _count: { select: { posts: true } } }`.
- **Use `createMany` / `updateMany` / `deleteMany`** instead of loops of single writes. Use `$transaction([...])` for batches that must succeed together.
- **Avoid fetching large JSON/text columns** unless needed (use `select`).
- **Drop to raw SQL** (`$queryRaw` with the tagged-template form for parameterisation) for reports, aggregates and window functions that the client cannot express efficiently.
- **Interactive transactions** (`$transaction(async tx => …)`) hold a connection: keep them short and avoid external calls inside them. They also have a default timeout.
- **Cache** read-heavy, rarely-changing data (Redis, in-process) and invalidate deliberately ([Scenario Debugging, Lesson 02](/debugging/lesson-2)).

## Connection pools

Each Prisma Client instance maintains a **pool** of database connections, and **where the pool lives depends on your Prisma version**:

| | Prisma 6 and earlier | Prisma 7 and later |
|---|---|---|
| **Who owns the pool** | Prisma's built-in query engine | The Node.js **driver adapter** you pass in (for PostgreSQL, the `pg` pool) |
| **Default size** | About `num_physical_cpus × 2 + 1` | `max` of **10** (the driver's default) |
| **How to set it** | Connection string: `?connection_limit=10&pool_timeout=10` | Pool options on the adapter: `max`, `idleTimeoutMillis`, `connectionTimeoutMillis` |

Prisma 7 (released November 2025) made driver adapters the default, so the connection-string limits you may remember from older tutorials no longer apply there. Read the pool section of the documentation for the version you use.

### Reuse one `PrismaClient`

Creating a new `PrismaClient` per request or per module reload opens a **new pool each time** and quickly exhausts the database's connection limit.

```ts
// lib/prisma.ts — one instance per process
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };

export const prisma = globalForPrisma.prisma ?? new PrismaClient();
if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma; // survives hot reload in dev
```

With Prisma 7 the client is created with a driver adapter, which is also where you size the pool (and the import comes from the client you generate in your project, so check your generator's `output` setting):

```ts
import { PrismaPg } from "@prisma/adapter-pg";
import { PrismaClient } from "../generated/prisma/client";   // path depends on your generator output

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL, max: 5 });   // pool size lives here
export const prisma = new PrismaClient({ adapter });
```

The `globalThis` trick matters in Next.js development, where hot reloading re-evaluates modules and would otherwise create a new client on every change.

### The serverless connection problem

**Scenario:** your API runs on serverless functions (Vercel, AWS Lambda). Each function instance has its own pool, and under load hundreds of instances open connections at once. A typical PostgreSQL server allows only on the order of 100 connections: you hit "too many connections," requests fail, and the database CPU is wasted on connection handling.

Fixes:

1. **Use an external connection pooler** between the app and the database: **PgBouncer** (transaction mode), the cloud provider's pooler (**RDS Proxy**, Supabase's pooler, Neon's pooler) or **Prisma Accelerate**. Instances connect to the pooler (many cheap connections), which multiplexes them onto few real database connections.
2. **Set a small pool per instance** (often 1 to 5 for serverless: `connection_limit` in Prisma 6 and earlier, the adapter's `max` in Prisma 7) so many instances do not each open a big pool.
3. When using PgBouncer in transaction mode, follow your Prisma version's guidance (Prisma 6 uses the `pgbouncer=true` connection-string flag; with a Prisma 7 driver adapter, configure the driver for transaction pooling), and use a **direct** (non-pooled) URL for **migrations**.
4. Reuse the client across invocations (module-level singleton) so warm functions do not reconnect.
5. Prefer a long-running server (a container) for connection-heavy workloads, if the architecture allows.

(PgBouncer's transaction mode means session-level features such as advisory locks and prepared statements across statements need care.)

## Migrations in production

- Use `prisma migrate deploy` in CI/CD (not `migrate dev`).
- Make migrations **backward-compatible** so old and new code can run against the same schema during a rolling deploy: the **expand and contract** pattern (add a new nullable column, deploy code that writes both, backfill, switch reads, then drop the old column later).
- Big table changes (adding an index) should use `CREATE INDEX CONCURRENTLY` in a hand-edited migration to avoid blocking writes.

## Common mistakes

1. **`await` inside loops** (and `Promise.all(users.map(...query))`) over large lists.
2. **`include` everywhere**, pulling whole relations and wide rows when `select` would do.
3. **Using `findFirst`/`findMany` in resolvers** and losing automatic batching.
4. **Global DataLoaders** that leak data across users.
5. **A new `PrismaClient` per request** or per hot reload.
6. **Serverless without a pooler**, then "too many connections."
7. **Unpaginated list endpoints.**
8. **Not logging or counting queries**, so N+1 goes unnoticed until production.
9. **Interactive transactions that call external services.**

## Interview questions

### Q1. What is the N+1 problem?

One query fetches a list of N rows, then the code issues one additional query per row to load related data, so N+1 queries total. It scales latency and database load with list size. Fix it with eager loading (`include`/`select` or a join strategy), a single `IN` query, or batching via DataLoader.

### Q2. How does Prisma batch `findUnique` calls?

Prisma's built-in dataloader groups `findUnique` calls on the same model that occur in the same tick of the event loop and sends them as one query with an `IN` condition, then distributes the results back to each caller. It only applies to `findUnique`, so replacing it with `findFirst` or `findMany` loses the batching.

### Q3. `include` vs separate queries: what are the trade-offs?

`include` expresses relations declaratively and by default issues one extra query per relation level, avoiding N+1. With the join strategy it can become a single SQL query, trading fewer round trips for a larger, more complex statement and duplicated parent data. Separate hand-written queries give the most control (select only needed columns, tune indexes, use raw SQL) at the price of more code. Measure with real data.

### Q4. Scenario: serverless functions exhaust database connections. Fix it.

Each function instance opens its own pool, so total connections scale with concurrency. Put a pooler (PgBouncer, RDS Proxy or the provider's pooler, or Prisma Accelerate) between the functions and the database, set a small pool size per instance (`connection_limit` in Prisma 6, the adapter's `max` in Prisma 7), reuse a singleton client, use the pooled URL for the app and a direct URL for migrations, and consider a long-running service if connection counts remain a problem.

### Q5. How do you find N+1 queries in an existing API?

Enable query logging or APM tracing and look for repeated identical queries within one request, check whether latency grows with page size, query `pg_stat_statements` for high-call-count statements, and add tests that assert a maximum query count per endpoint.

### Q6. Why create DataLoader instances per request?

DataLoader caches results by key. A shared instance would reuse cached data across requests and users, leaking data and serving stale results. A per-request instance batches within that request and is discarded afterwards.

### Q7. Why must you reuse a single PrismaClient?

Each client has its own connection pool. Creating many clients (per request or on every hot reload) multiplies open connections and exhausts the database's limit. Share one instance per process, and in development store it on `globalThis` so hot reloads reuse it.

### Q8. When would you drop to raw SQL in a Prisma app?

For complex reporting, aggregates, window functions, CTEs, bulk operations or performance-critical queries where the generated queries are inefficient. Use the tagged-template `$queryRaw` for safe parameterisation, and type the results explicitly.

## Key takeaways

- **N+1** = one query per row. Fix with `include`/`select` (or the join strategy), an `IN` query, or **DataLoader**.
- Prisma batches **`findUnique`** calls in the same tick automatically; GraphQL engines like Hasura compile nested queries into one SQL statement.
- Prefer **`select`** for API responses, **paginate** everything, **index** filter/sort columns and foreign keys.
- One **`PrismaClient`** per process; use a **pooler** (and a small per-instance pool) for serverless.
- Make migrations **backward-compatible**, and watch your query count.
