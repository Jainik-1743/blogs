> **In one line:** test **behaviour** at the right level: many fast **unit** tests for pure business logic, a solid layer of **integration** tests through HTTP against a **real database**, and a few **contract** tests that stop the frontend and backend drifting apart. Mock the edges, not your own code.

On the frontend you know "test what the user sees." The backend equivalent is "test what the **API promises**": status codes, bodies, side effects in the database and the rules that govern them. This lesson gives you a strategy you can defend and examples you can copy.

## What to test, and at what level

| Level | What it exercises | Speed | Where it earns its keep |
|---|---|---|---|
| **Unit** | One function or class in isolation: pricing, eligibility, state machines, parsers, policy functions | Milliseconds | **Pure business logic** with many edge cases |
| **Integration** | Several real parts together: HTTP route → validation → service → real database | Tens to hundreds of ms | The **most valuable layer** for APIs: catches wiring, SQL, constraint and serialisation bugs |
| **Contract** | The agreement between two services/clients (shape of requests and responses) | Fast | Preventing "backend changed a field, frontend broke" |
| **End-to-end** | The deployed system through a browser or full client | Seconds | A handful of critical journeys only (login, checkout) |

The common shape: **many unit tests for logic, a thick slice of integration tests for endpoints, a few end-to-end tests**. Some teams favour a "trophy" (heavier on integration) over a strict pyramid; for CRUD-ish backends that is usually right, because most bugs live in the *seams*, not in isolated functions.

Why you cannot rely only on unit tests with mocked databases: the test passes while the real SQL fails on a missing column, a constraint or a transaction behaviour. The mock agrees with your assumptions, which is exactly the thing that might be wrong.

## Unit tests: pure logic

Because [clean code](/backend/lesson-0) pushes rules into pure functions, they test trivially:

```ts
import { describe, it, expect } from "vitest";
import { calculateDiscount } from "./pricing";

describe("calculateDiscount", () => {
  it.each([
    [{ subtotal: 10_000, itemCount: 1 }, { tier: "gold" }, 1_000],   // gold = 10%
    [{ subtotal: 10_000, itemCount: 10 }, { tier: "free" }, 500],    // bulk = 5%
    [{ subtotal: 10_000, itemCount: 2 }, { tier: "free" }, 0],
    [{ subtotal: 0, itemCount: 0 }, { tier: "gold" }, 0],            // edge case
  ])("order %j, customer %j → %i", (order, customer, expected) => {
    expect(calculateDiscount(order, customer)).toBe(expected);
  });
});
```

Good unit tests: no network, no database, no clock (inject it), no randomness, and assertions on **outputs**, not on which internal helper was called.

## Integration tests: through HTTP, against a real database

Use **Supertest** (or `fetch` against `buildApp()`; [Lesson 01](/backend/lesson-1)) with a real PostgreSQL, typically in Docker.

```ts
import request from "supertest";
import { beforeAll, afterAll, beforeEach, describe, it, expect } from "vitest";
import { buildApp } from "../src/app";
import { prisma } from "../src/lib/prisma";
import { createUser, authFor } from "./helpers";

const app = buildApp();

beforeEach(async () => {
  // Reset state so tests are independent
  await prisma.$executeRaw`TRUNCATE TABLE "OrderItem", "Order", "User" RESTART IDENTITY CASCADE`;
});
afterAll(() => prisma.$disconnect());

describe("POST /v1/orders", () => {
  it("creates an order and returns 201 with Location", async () => {
    const user = await createUser();
    const res = await request(app)
      .post("/v1/orders")
      .set(authFor(user))
      .send({ items: [{ sku: "SKU-1", qty: 2 }] });

    expect(res.status).toBe(201);
    expect(res.headers.location).toMatch(/\/v1\/orders\/.+/);
    expect(res.body).toMatchObject({ status: "pending", userId: user.id });

    const saved = await prisma.order.findUnique({ where: { id: res.body.id }, include: { items: true } });
    expect(saved?.items).toHaveLength(1);                         // verify the side effect, not just the response
  });

  it("rejects an empty cart with 422 and field errors", async () => {
    const res = await request(app).post("/v1/orders").set(authFor(await createUser())).send({ items: [] });
    expect(res.status).toBe(422);
    expect(res.body.errors[0].path).toContain("items");
  });

  it("returns 401 without credentials", async () => {
    expect((await request(app).post("/v1/orders").send({})).status).toBe(401);
  });

  it("does not let user B read user A's order", async () => {
    const [a, b] = [await createUser(), await createUser()];
    const order = await createOrderFor(a);
    const res = await request(app).get(`/v1/orders/${order.id}`).set(authFor(b));
    expect(res.status).toBe(404);
  });
});
```

### Make the database part easy

- **Run a real PostgreSQL in Docker**: `docker compose` in CI and locally, or **Testcontainers** to start a throwaway container from the test code.
- **Apply real migrations** (`prisma migrate deploy`) to the test database so the schema is production-shaped.
- **Isolate tests:** truncate tables between tests (simple, slightly slower), or wrap each test in a transaction that rolls back (fast, but trickier with code that itself uses transactions), or give each test file its own schema/database to run files in parallel.
- **Use factories/builders** (`createUser()`, `createOrderFor(user)`) so setup is short and intention-revealing.
- **Keep tests deterministic:** control time (`vi.useFakeTimers()` or an injected clock), randomness and ID generation.

### Test the unhappy paths

For each endpoint, cover: **validation failures, unauthenticated, unauthorized (other user, lower role), not found, conflicts (duplicates, stale versions), idempotent retries, and dependency failures** (payment provider down). Error handling is behaviour; it deserves tests ([Lesson 04](/backend/lesson-4)).

## What to mock (and what not)

> [!ok] **Mock the boundaries you do not own and cannot run cheaply**; **do not mock the things you are trying to verify.**

| Mock / fake | Don't mock |
|---|---|
| Third-party HTTP APIs (payments, email, SMS), using a local fake server such as **MSW/nock** or a fake implementing your gateway interface | Your own services and repositories when testing an endpoint |
| The clock, randomness, UUID generation | The database, in integration tests |
| Slow or non-deterministic resources (a large cloud service) | The framework (Express) |
| Queues in unit tests (a fake publisher that records messages) | The validation layer |

Over-mocking produces tests that verify the mocks. A sign you are doing it: you edit tests every time you refactor, even though behaviour has not changed.

**Fakes vs mocks vs spies:** a **fake** is a working lightweight implementation (an in-memory repository); a **mock** asserts on calls; a **spy** wraps a real function to observe it. Prefer fakes and assertions on **outcomes** over assertions on *how* something was called.

```ts
// A fake payment gateway implementing the same interface (injected, see Lesson 00)
class FakeGateway implements PaymentGateway {
  charges: { orderId: string; amount: number }[] = [];
  shouldFail = false;
  async charge(orderId: string, amount: number) {
    if (this.shouldFail) throw new PaymentUnavailableError();
    this.charges.push({ orderId, amount });
    return { id: "ch_fake" };
  }
}
```

## Contract tests

**Scenario:** the backend renames `total` to `totalAmount`. Unit and integration tests on the backend still pass (they were updated). The frontend still reads `total` and breaks in production. **Which test was missing?** A **contract** test: an automated check that the *shape both sides rely on* has not changed.

Approaches:

1. **Shared schema package** in a monorepo ([Lesson 03](/backend/lesson-3)): the frontend and backend import the same Zod schemas and types, so a rename is a compile error on both sides. The API test also asserts that responses **parse against the schema** (`orderResponseSchema.parse(res.body)`).
2. **OpenAPI as the contract:** generate types and clients from it; in CI, run a **breaking-change detector** (`oasdiff`, `openapi-diff`) on pull requests, and validate real responses against the spec in tests.
3. **Consumer-driven contracts (Pact):** the *consumer* (frontend) records the requests it makes and the responses it needs; the *provider* (API) verifies it can satisfy them in its own CI. Good when many independent consumers exist.
4. **Snapshot of the API schema** (GraphQL schema checks in a registry) with CI that fails on breaking changes.

Also protect **database migrations**: test that the migration applies to a copy of production-like data, and use **backward-compatible (expand/contract)** changes so old and new code can coexist during a rolling deployment ([Lesson 08](/backend/lesson-8)).

## Other kinds of testing worth knowing

- **Load/performance tests** (k6, autocannon) in CI or staging for critical endpoints, with thresholds on p95/p99.
- **Security tests:** authorization matrix tests, dependency audits, and a periodic automated scan; add a regression test for every security bug.
- **Concurrency tests:** fire parallel requests at "buy the last item" or "apply coupon once" endpoints and assert the invariant holds ([Lesson 07](/backend/lesson-7)).
- **Property-based tests** (fast-check) for parsers, serialisers and money math.
- **Mutation testing** (Stryker) to see whether tests would catch changed logic, a better signal than coverage percentage.

## Practices that keep a test suite healthy

- **Fast feedback:** unit tests in seconds, integration in a minute or two, run on every PR in CI; parallelise.
- **One reason to fail:** each test checks one behaviour and has a name that states it ("returns 404 when the order belongs to another user").
- **Arrange, Act, Assert** structure; no logic (loops, conditionals) in tests.
- **No shared mutable state** between tests; no dependence on test order.
- **Flaky tests are bugs:** quarantine and fix them; do not ignore red CI.
- **Coverage is a smoke detector, not a goal.** 80% with strong assertions beats 100% of lines that merely execute code.
- **Tests are code:** refactor them, keep helpers tidy.

## Common mistakes

1. **Mocking the database** in tests that are supposed to prove the endpoint works.
2. **Testing implementation details** (which function was called) rather than outcomes.
3. **Only testing the happy path.**
4. **Shared, order-dependent test data**, causing flaky failures.
5. **Slow suites** that developers stop running.
6. **No contract protection** between frontend and backend.
7. **Chasing a coverage number** with assertion-free tests.
8. **Real third-party calls in tests** (flaky, costly, unsafe).

## Interview questions

### Q1. What do you mock, and what don't you?

I mock or fake things I do not own or cannot run cheaply and deterministically: third-party HTTP APIs, email/SMS, the clock and randomness. I do not mock my own services, the database or the validation layer when testing an endpoint, because those are exactly what the test should verify. I prefer fakes and outcome assertions over call-count assertions.

### Q2. Scenario: tests pass, but production breaks on a schema change. Which test was missing?

A contract test (or a breaking-change check): the frontend relied on a response shape or field name that the backend changed. Shared schemas or generated types from OpenAPI, plus a breaking-change detector in CI and response validation in API tests, would have failed the build. A related gap is migration testing against realistic data and using backward-compatible expand/contract migrations.

### Q3. How do you test error paths?

Each endpoint gets tests for validation failure, unauthenticated, unauthorized (other user and lower role), not found, conflict or duplicate, idempotent retry, and simulated dependency failure (a fake gateway that throws). I assert the status code, the error body shape (including the stable `code`) and that no side effects leaked into the database.

### Q4. Unit vs integration tests: where do you put most of your effort in a backend?

Unit tests for dense business logic with many edge cases, but the bulk of the value is in integration tests that run the real HTTP stack against a real database, since most defects are in wiring, SQL, constraints and serialisation rather than in isolated functions.

### Q5. How do you keep integration tests isolated and fast?

Use a real PostgreSQL in Docker or Testcontainers with migrations applied, reset state per test with truncation or a rolled-back transaction (or per-file schemas for parallelism), build data with factories, control time and randomness, and run files in parallel in CI.

### Q6. What is a consumer-driven contract test?

The consumer of an API records the interactions it depends on (requests and expected response shapes). The provider verifies in its own pipeline that it can satisfy those contracts. It catches breaking changes before they are deployed and shows exactly which consumer would break.

### Q7. How do you test concurrency-sensitive code like "last item in stock"?

Write a test that fires many parallel requests against the endpoint with only one item available, then assert exactly one succeeds and stock never goes negative. This verifies that the atomic update, lock or constraint really prevents overselling under contention.

### Q8. Is high code coverage a good goal?

It is a useful smoke detector for untested areas, not a quality target. Coverage measures executed lines, not verified behaviour. I focus on meaningful assertions, risk-based coverage of critical paths and error cases, and sometimes mutation testing to check whether tests would catch real changes.

## Key takeaways

- **Unit** test pure logic; **integration** test endpoints through HTTP with a **real database**; **contract** test the frontend/backend agreement; keep **E2E** to critical flows.
- **Mock the edges, not your own code**; prefer fakes and outcome assertions.
- Cover **unhappy paths** (validation, auth, other users, conflicts, dependency failures) and **concurrency** invariants.
- Keep tests **isolated, deterministic and fast**, and treat flakiness as a bug.
- Protect against **schema drift** with shared schemas or OpenAPI breaking-change checks, and use **backward-compatible migrations**.
