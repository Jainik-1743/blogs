> **In one line:** clean backend code is code where **business rules are easy to find, easy to test and hard to break**: small functions with honest names, logic separated from I/O, and dependencies passed in rather than reached for.

You have shipped many production frontends; the backend questions in a senior loop probe whether you can *design for change*. "Clean code" is not about style. It is a handful of habits that make a codebase cheap to modify under pressure. This lesson gives you the habits, the vocabulary (SOLID, DRY) and an honest view of when abstraction hurts.

## What "clean" means in a backend

A backend codebase is clean when a new teammate can answer, quickly:

1. **Where does this rule live?** (one obvious place)
2. **What does this function touch?** (database, network, clock, filesystem)
3. **How do I test it?** (without starting the world)
4. **What happens when it fails?** (an explicit, typed outcome)

Everything below serves those four questions.

## Naming

Names are the cheapest documentation. Rules that pay off:

- **Name by intent, not by implementation.** `getActiveSubscriptionsExpiringIn(days)` beats `getData2()`.
- **Functions are verbs, data are nouns, booleans are questions.** `calculateInvoiceTotal`, `invoice`, `isOverdue`, `hasPaidPlan`.
- **Be specific about units and meaning.** `timeoutMs`, `amountInPaise`, `expiresAtUtc`. A bare `timeout = 30` has cost people outages.
- **Avoid noise words** (`data`, `info`, `manager`, `helper`, `util`). A `UserManager` usually hides several responsibilities.
- **One concept, one word.** Do not mix `fetch`, `get`, `retrieve` and `load` for the same idea.
- **Length should match scope.** `i` in a three-line loop is fine; a module-level name should be descriptive.

```ts
// ❌ Reader must decode everything
function proc(d: any, f: boolean) {
  if (d.s === 2 && !f) return d.a * 0.18 + d.a;
  return d.a;
}

// ✅ Intent is visible; units are explicit; no flag argument
const GST_RATE = 0.18;
function totalWithTax(order: Order): number {
  return order.status === "taxable" ? order.subtotal * (1 + GST_RATE) : order.subtotal;
}
```

## Small functions that do one thing

A function should be understandable **without scrolling** and operate at **one level of abstraction**. A function that validates, queries, applies business rules, sends email and formats the response is four functions in a coat.

Practical heuristics:

- If you need a comment to explain a *block*, extract that block into a function named after the comment.
- **Early returns and guard clauses** beat deep nesting.
- **Avoid boolean "flag" parameters** (`createUser(data, true)`): they mean the function does two things. Split it, or pass a named option.
- Prefer **few parameters**. More than three often signals a missing object (`{ userId, from, to }`).
- A function that returns a value should not also cause a side effect (a "command-query" mindset).

```ts
// ❌ Nested and mixed concerns
async function checkout(req: Request, res: Response) {
  if (req.body.items) {
    if (req.body.items.length > 0) {
      const user = await db.user.findUnique({ where: { id: req.userId } });
      if (user) {
        if (user.balance >= total(req.body.items)) {
          /* ... 80 more lines ... */
        } else res.status(402).send("no money");
      } else res.status(404).send("no user");
    } else res.status(400).send("empty");
  } else res.status(400).send("no items");
}

// ✅ Guard clauses; each step has a name
async function checkout(input: CheckoutInput, ctx: Ctx): Promise<Order> {
  if (input.items.length === 0) throw new ValidationError("Cart is empty");
  const user = await ctx.users.getById(input.userId);          // throws NotFoundError
  const total = priceItems(input.items);                       // pure
  assertCanAfford(user, total);                                // pure, throws PaymentRequiredError
  return ctx.orders.create({ userId: user.id, items: input.items, total });
}
```

## Separate pure logic from I/O

The single most valuable structural habit:

- **Pure functions** take inputs and return outputs. They have no database, no clock, no randomness, no network. They are trivially testable and reusable.
- **I/O at the edges.** Controllers, repositories, API clients and queue consumers handle the outside world and **call** pure logic.

```ts
// Pure: the business rule. No imports from Prisma or Express.
export function calculateDiscount(order: { subtotal: number; itemCount: number }, customer: { tier: "free" | "gold" }): number {
  if (customer.tier === "gold") return Math.round(order.subtotal * 0.1);
  if (order.itemCount >= 10) return Math.round(order.subtotal * 0.05);
  return 0;
}

// Impure: gathers inputs, calls the rule, persists the result.
export async function applyDiscount(orderId: string) {
  const order = await orders.getById(orderId);
  const customer = await customers.getById(order.customerId);
  const discount = calculateDiscount(order, customer);
  await orders.setDiscount(orderId, discount);
}
```

The rule `calculateDiscount` can now be tested with a table of inputs in milliseconds, with no mocks.

### Avoid hidden I/O

`new Date()`, `Math.random()`, `process.env.X`, a global database client imported at the top of a service: all are hidden dependencies. They make tests slow or flaky and behaviour surprising. **Pass them in**:

```ts
// ❌ Hidden clock — how do you test "expires in 24 hours"?
function isExpired(token: Token) { return token.expiresAt < new Date(); }

// ✅ Explicit
function isExpired(token: Token, now: Date) { return token.expiresAt < now; }
```

## Dependency injection without a framework

"Dependency injection" just means **a function receives what it needs instead of creating or importing it**. You do not need a container or decorators.

```ts
// A factory returns a service wired with its dependencies.
export function createOrderService(deps: { orders: OrderRepo; payments: PaymentGateway; clock: () => Date }) {
  return {
    async place(input: PlaceOrderInput) {
      const order = await deps.orders.create({ ...input, createdAt: deps.clock() });
      await deps.payments.charge(order.id, order.total);
      return order;
    },
  };
}

// In production: real repos. In tests: tiny fakes.
const service = createOrderService({ orders: prismaOrderRepo, payments: stripeGateway, clock: () => new Date() });
```

## SOLID, translated for backends

You will be asked about SOLID. Answer with an example from a backend, not a definition.

| Principle | Meaning | Backend example |
|---|---|---|
| **S**ingle Responsibility | A module has **one reason to change** | The controller changes when the HTTP contract changes; the service when the business rule changes; the repository when the schema changes |
| **O**pen/Closed | Open to extension, closed to modification | Add a new payment provider by adding a class that implements `PaymentGateway`, not by editing a giant `switch` |
| **L**iskov Substitution | A subtype must be usable wherever its parent is | Any `PaymentGateway` implementation must honour the same contract (same errors, same idempotency), or swapping it breaks callers |
| **I**nterface Segregation | Small, focused interfaces | A reporting job depends on a `ReadOnlyOrderRepo`, not on the full repo with write methods |
| **D**ependency Inversion | Depend on **abstractions**, not concretions | The service depends on an `EmailSender` interface; SES, SendGrid or a test fake plug in |

In TypeScript, interfaces and plain function types are enough.

```ts
interface PaymentGateway { charge(orderId: string, amountMinor: number): Promise<{ id: string }>; }

class StripeGateway implements PaymentGateway { /* ... */ }
class FakeGateway implements PaymentGateway { charges: string[] = []; async charge(id: string) { this.charges.push(id); return { id: "fake" }; } }
```

## DRY, and when it is harmful

**DRY** (Don't Repeat Yourself) is about **knowledge**, not text. Two functions that look alike but represent different business rules are **not** duplicates; merging them couples things that will diverge.

- **The rule of three:** tolerate duplication twice; abstract on the third occurrence, when you can see what truly varies.
- **"Duplication is far cheaper than the wrong abstraction."** A shared function with seven boolean flags to cover every caller's quirks is worse than three simple copies.
- **Do** deduplicate genuine single sources of truth: a pricing rule, a permission check, a validation schema.
- **Do not** share code between services just to avoid copying; the coupling usually costs more.

### When *not* to abstract

- You have **one** implementation and no realistic second one. A `UserRepositoryInterface` with a single Prisma class and a factory may be ceremony. (Counter-argument: it makes testing easy. Weigh the value.)
- The abstraction is guessing future needs ("what if we switch databases?"). You almost never do, and when you do, the abstraction you guessed is rarely the right one.
- The abstraction hides important differences (for example, treating a queue and an HTTP call as the same "client" when their failure modes differ).

A good test: **would deleting this layer make the code simpler without losing a real benefit?** If yes, delete it.

## Errors are part of the design

Make failure explicit and typed instead of returning `null` or throwing strings:

```ts
export class AppError extends Error {
  constructor(message: string, public status: number, public code: string, options?: { cause?: unknown }) {
    super(message, options);
  }
}
export class NotFoundError extends AppError { constructor(what: string) { super(`${what} not found`, 404, "NOT_FOUND"); } }
export class ConflictError extends AppError { constructor(msg: string) { super(msg, 409, "CONFLICT"); } }
```

Details are in [Lesson 04](/backend/lesson-4). The point here: domain code throws **domain errors**; only the outermost layer translates them to HTTP.

## Make the standards automatic

Standards that depend on code review comments erode. Enforce them with tools:

- **TypeScript `strict`** (and `noUncheckedIndexedAccess`) so whole classes of bugs never compile.
- **ESLint** with rules for unused variables, floating promises (`@typescript-eslint/no-floating-promises`), no `any`, import boundaries (for example, forbid `services/` importing `express`).
- **Prettier** so formatting is never discussed.
- **CI** runs lint, typecheck and tests on every PR; branch protection requires green.
- **Pre-commit hooks** (lint-staged) for fast feedback.
- **Architecture tests** (such as `dependency-cruiser`) that fail if a layer imports one it should not.

## Scenario: you inherit a 600-line controller

Do **not** rewrite it. Refactor safely in small steps:

1. **Pin behaviour with tests first.** Write characterization tests (HTTP-level, against a test database) that capture current behaviour, including its quirks.
2. **Extract input validation** into a schema ([Lesson 03](/backend/lesson-3)).
3. **Extract pure business rules** into functions with unit tests (pricing, eligibility, state transitions).
4. **Extract data access** into repository functions.
5. **Leave the controller thin:** parse input, call one service function, map the result or error to HTTP.
6. After each step run the tests and commit. Small commits can be reviewed and reverted.
7. Fix bugs you discover **in separate commits** so refactors stay behaviour-preserving.

## Common mistakes

1. **Business logic in controllers or route handlers**, impossible to reuse from a job or CLI.
2. **God services** (`UserService` with 40 methods).
3. **Hidden dependencies** (global singletons, `process.env` read in the middle of a function).
4. **Premature abstraction**, layers with a single implementation and no reason to exist.
5. **Premature DRY**, merging code that looks the same today but changes for different reasons.
6. **Boolean-flag parameters** and functions that return different shapes.
7. **Comments that restate the code**, and no comments explaining *why*.
8. **Swallowed errors** (`catch {}`) and generic `Error("failed")`.

## Interview questions

### Q1. What makes code "maintainable" to you?

That a change touches few places and a reader can predict the effect. In practice: clear names, small single-purpose functions, business rules separated from I/O so they are testable without infrastructure, explicit dependencies, typed errors, and automated checks (types, lint, tests) that protect behaviour. I measure it by how long a new teammate takes to make a safe change.

### Q2. Scenario: you inherit a 600-line controller. How do you refactor it safely?

Characterization tests first, then peel layers off in small commits: validation schema, pure business rules, repository functions, finally a thin controller. Behaviour stays identical at each step; bugs found along the way go in separate commits. I avoid a big-bang rewrite because it hides regressions and blocks other work.

### Q3. When is DRY harmful?

When it merges code that is only *textually* similar but represents different rules that change for different reasons. The shared helper then grows flags and branches for every caller. I wait for the third occurrence (the rule of three) and abstract only the knowledge that is truly shared, such as one pricing rule or one permission check.

### Q4. How do you enforce standards across a team?

By tooling, not reminders: strict TypeScript, ESLint (including import-boundary and floating-promise rules), Prettier, CI gates on every PR, and pre-commit hooks. For architecture, dependency-boundary checks that fail the build if a layer imports the wrong thing. Review comments then focus on design, not formatting.

### Q5. Explain the Single Responsibility Principle with a backend example.

A module should have one reason to change. A controller changes when the HTTP contract changes, a service when the business rule changes, a repository when the data model changes. If one function validates input, applies pricing rules, writes to the database and formats the response, any of those four changes forces you to edit and retest the same code.

### Q6. What is dependency injection and do you need a framework for it?

It means passing a function what it needs (a repository, a clock, a payment gateway) rather than having it import or create them. You can do it with plain factory functions or constructor arguments. A framework or container helps in very large codebases but is not required, and plain injection gives the main benefit, which is easy testing with fakes.

### Q7. Why separate pure logic from I/O?

Pure functions are deterministic and need no setup, so they can be tested in milliseconds with a table of inputs and reused anywhere. I/O code is harder to test and more likely to fail, so keeping it thin and at the edges limits how much of your logic depends on infrastructure.

### Q8. How do you decide whether an abstraction is worth it?

I ask whether it removes real duplication of knowledge, whether there is more than one implementation or a genuine testing need, and whether deleting it would make the code simpler. If it only exists for hypothetical future flexibility, I leave it out and add it when the need is real.

## Key takeaways

- Clean code is code that makes **where, what, how to test and what fails** obvious.
- **Name by intent**, keep functions small and single-purpose, prefer guard clauses to nesting.
- **Pure logic in the middle, I/O at the edges**; inject dependencies (clock, repositories, gateways) instead of importing them.
- **SOLID** is a set of change-isolation tactics: explain each with a backend example.
- **DRY is about knowledge**, not text. Abstract on the third repetition, and delete layers that earn nothing.
- Automate standards (strict types, lint, CI, architecture checks) and refactor legacy code behind tests, in small steps.
