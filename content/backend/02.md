> **In one line:** a good REST API is **predictable**. Use nouns for resources, HTTP methods for actions, and status codes for results. Use one error format. Make changes that never break existing clients. Predictable APIs let frontend developers guess correctly.

You use APIs every day as a frontend engineer. This helps you, because you already know what annoys a client. This lesson turns those annoyances into design rules. It also covers senior-level topics: versioning, idempotency keys, partial updates, filtering and concurrency control.

## Resources, not verbs

REST models **things (resources)**, like orders or users. The HTTP methods (GET, POST, DELETE) are the verbs.

| ❌ RPC-style | ✅ Resource-style |
|---|---|
| `POST /createOrder` | `POST /orders` |
| `GET /getOrderById?id=7` | `GET /orders/7` |
| `POST /deleteOrder` | `DELETE /orders/7` |
| `POST /updateOrderStatus` | `PATCH /orders/7` with `{ "status": "shipped" }` |

(RPC means "remote procedure call": the URL names a function to run.)

Conventions:

- **Use plural nouns** for collections: `/orders`, `/users`. One item is `/orders/{id}`.
- **Nest only when one thing truly belongs to another**, and keep it shallow. `/orders/7/items` is fine. `/users/3/orders/7/items/2/refunds` is a warning sign. When the path gets deeper than about two levels, use `/refunds?orderId=7` or a top-level resource.
- **For actions that are not CRUD:** model them as sub-resources or state changes (`POST /orders/7/cancellation`, `POST /payments/{id}/refunds`). Do not put verbs in the path. A practical `POST /orders/7/cancel` is common and acceptable if you use it the same way everywhere.
- **Use lowercase, hyphenated paths** (`/order-items`). **Use camelCase JSON fields** (to match what the frontend uses).
- **Use IDs that are safe to show.** UUIDs/ULIDs do not reveal how many records you have, and they are hard to guess one by one. But you must still check authorization.

## Methods and status codes together

When the mapping is always the same, nobody has to guess ([HTTP semantics](/browser/lesson-6)):

| Operation | Request | Success | Common errors |
|---|---|---|---|
| List | `GET /orders?status=paid&limit=20` | `200` with items | `400` bad query, `401`, `403` |
| Read one | `GET /orders/7` | `200` | `404`, `403` |
| Create | `POST /orders` | `201` + `Location: /orders/7` | `400`/`422` validation, `409` duplicate |
| Replace | `PUT /orders/7` | `200` or `204` | `404`, `409`, `412` |
| Partial update | `PATCH /orders/7` | `200` (with body) or `204` | `404`, `409`, `422` |
| Delete | `DELETE /orders/7` | `204` | `404` (or `204` again: idempotent) |
| Async work | `POST /reports` | `202` + `Location: /reports/jobs/9` | |

> [!warn] **Never return `200 OK` with an error in the body.** Clients, API gateways, retry logic, monitoring and caches all read the status code. A `200` that says `{"success": false}` breaks all of them.

## A single error format

Every error from every endpoint should have the same shape. The industry standard is **Problem Details for HTTP APIs** (`application/problem+json`):

```json
{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/v1/orders",
  "requestId": "01HZX3V7N8Q2",
  "errors": [
    { "path": "items[0].qty", "code": "too_small", "message": "Must be at least 1" }
  ]
}
```

This helps the frontend in three ways:

- It can switch on a stable `code` or `type` that a program can read. It does not need to read the message text.
- It can show field-level errors next to the inputs.
- It can show the `requestId` to support staff.

Never put stack traces or SQL in `detail`.

## Collections: filtering, sorting, pagination

```text
GET /orders?status=paid&createdAfter=2026-01-01&sort=-createdAt&limit=20&cursor=eyJpZCI6MTAwfQ
```

- **Filter** with query parameters named after fields. Check them and allow only known names. Do not pass them straight into queries.
- **Sort** with a `sort` parameter (a `-` prefix means descending). Allow only indexed fields that you chose.
- **Always paginate** (return lists in pages). A list with no limit will cause an outage one day. Choose offset or cursor pagination on purpose ([Practical Design Problems, Lesson 03](/design-problems/lesson-3)). Set a **maximum limit** (for example 100). Return pagination info.
- **Sparse fields** (`fields=id,status`) and **expansion** (`expand=customer`) let clients get less or more data. Add them only if you need them.

```json
{
  "data": [ { "id": "ord_1", "status": "paid" } ],
  "page": { "limit": 20, "nextCursor": "eyJpZCI6MTIwfQ", "hasMore": true }
}
```

Should you wrap the list in an envelope (`{ data, page }`) or return a bare array? That is a matter of taste. Wrapping is easier to grow, because you can add extra data later without breaking clients. So many teams choose it.

## Data conventions that save pain

- **Timestamps:** use ISO 8601 in UTC (`2026-05-01T09:30:00Z`). Do not send local time or epoch milliseconds unless you document it.
- **Money:** use whole numbers in the **smallest unit** (`amountMinor: 4999` for ₹49.99) plus a `currency` code. Never use floats (decimal numbers can have rounding errors).
- **Null vs missing:** decide what each one means and write it down. For PATCH, for example: "`null` = clear the field; missing = leave it unchanged".
- **Booleans:** name them in a positive way (`isActive`, not `isNotDisabled`).
- **Enums:** use stable strings (`"shipped"`), not numbers.
- **IDs:** use strings in JSON. JavaScript loses precision on very large integers.

## Versioning

You do not control your clients, and they will not update when you do. Follow these rules:

1. **Prefer changes that only add things and do not break old clients.** Adding an optional field, a new endpoint, or a new enum value (if clients ignore unknown values) needs no new version.
2. **Breaking changes** need a new version. A change is breaking if it removes or renames a field, changes a type, changes a meaning, makes an optional field required, or makes validation stricter.
3. **Strategies:**

| Strategy | Example | Pros | Cons |
|---|---|---|---|
| **URL path** | `/v1/orders` | Obvious, easy to route, cache and test | The whole API is versioned at once; the URL "changes" |
| **Header / media type** | `Accept: application/vnd.example.v2+json` | Clean URLs, versions per resource | Hidden, harder to try in a browser, easy to forget |
| **Query parameter** | `/orders?version=2` | Simple | Messes up cache keys; easy to leave out |

For most teams, **URL versioning** (`/v1`) is the practical default.

4. **Retire old versions with care:** announce it, add `Deprecation` and `Sunset` response headers, measure who still calls the old version, and then remove it.
5. **Be tolerant on both sides.** Servers should ignore unknown request fields carefully (or reject them on purpose, for security). Clients should ignore unknown response fields, so added fields are safe.

## Idempotency keys (safe retries)

"Idempotent" means that doing the same request many times has the same result as doing it once. Think of a lift button: pressing it five times still calls the lift only once.

Networks fail. Say `POST /payments` times out. The client cannot know whether it worked. If it retries blindly, it might charge the customer twice. The fix:

```http
POST /v1/payments
Idempotency-Key: 3d1c0b6e-6a9e-4c4e-9f0a-1a2b3c4d5e6f
```

What the server does:

1. Look up the key (limited to this user).
2. **Key not seen before:** process the request. Store `(key → request fingerprint, response)`. Return the response.
3. **Key seen, same request:** return the **stored response**. Do not do the work again.
4. **Key seen, different request body:** return `409`/`422`. The key was reused for something else.
5. **Two duplicates at the same time:** use a unique constraint or a lock on the key, so only one runs. The other one waits or gets `409`.
6. Delete keys after some time (for example 24 hours).

```ts
// Simplified: a unique constraint is the guard
await prisma.$transaction(async (tx) => {
  const existing = await tx.idempotencyKey.findUnique({ where: { userId_key: { userId, key } } });
  if (existing) return existing.response;        // replay
  const result = await createPayment(tx, input);  // do the work
  await tx.idempotencyKey.create({ data: { userId, key, response: result } });
  return result;
});
```

`PUT` and `DELETE` are idempotent by nature. `POST` is the one that needs a key.

## Partial updates: PUT vs PATCH

- **`PUT`** replaces the whole resource. Missing fields are treated as cleared. This is dangerous when a client sends a partial body by mistake.
- **`PATCH`** changes only the fields you send. The simple, common convention is **JSON Merge Patch**: send only the fields to change, and `null` means "clear this field".
- Check patch bodies with the same schema, made `.partial()`. Also reject **unknown fields**, so a typo does not succeed silently.

## Concurrency control with ETags

Two users edit the same record. With no protection, the second save silently overwrites the first. This is called a "lost update". The fix is **optimistic concurrency**: you assume conflicts are rare, and you detect them when they happen.

```http
GET /articles/5            → 200, ETag: "v7"
PUT /articles/5            If-Match: "v7"
                           → 200  (and a new ETag "v8")
# if someone else saved "v8" first:
                           → 412 Precondition Failed
```

An ETag is a label for the current version of a resource. The client sends it back in `If-Match`. If the label is old, the server refuses with `412`. The client then reloads the data, merges the changes, and tries again. You can also use a `version` column and return `409`.

## Other operational conventions

- **Rate limit headers** on responses (`RateLimit-Limit`, `RateLimit-Remaining`, and `Retry-After` on `429`), so clients know when to slow down ([Practical Design Problems, Lesson 02](/design-problems/lesson-2)).
- **Request IDs** in a response header and in error bodies, to help debugging ([Lesson 05](/backend/lesson-5)).
- **CORS** set up on purpose ([Browser Contract, Lesson 04](/browser/lesson-4)).
- **Compression** (gzip or Brotli) and **caching headers** where they help. An `ETag` on `GET` responses allows cheap `304` checks (the server says "nothing changed").
- **Documentation as code:** keep an OpenAPI description in the repo. Ideally it generates types for the frontend. Then a mismatch between frontend and backend becomes a compile error ([Lesson 03](/backend/lesson-3)).
- **Bulk operations:** prefer clear endpoints (`POST /orders/batch`) with a clear rule for partial failure (per-item results, like `207`). This is better than overloading single-item endpoints.

## What about HATEOAS, GraphQL and RPC?

"Pure" REST includes hypermedia links (links in responses that tell the client what it can do next; this is called HATEOAS). Most real APIs are "REST-ish": resources plus HTTP rules. That is fine. GraphQL may fit when clients need very different shapes of the same data, or when you want one typed endpoint ([Lesson 09](/backend/lesson-9)). For internal service-to-service calls with strict contracts, gRPC is common. Choose on purpose, and be ready to say why.

## Common mistakes

1. **Verbs and RPC names in paths** (`/getUsers`), mixed with REST in other places.
2. **`200` with an error body**, or different error shapes in different endpoints.
3. **No pagination** on list endpoints.
4. **Breaking changes with no new version**, or no process to retire old versions.
5. **Floats for money, local-time strings for dates, numeric IDs as JSON numbers.**
6. **A `POST` that is not idempotent and gets retried blindly**, which causes duplicates.
7. **Exposing the database structure** (internal IDs, responses shaped like tables) instead of designing for what the client needs.
8. **Filtering or sorting on fields that are not indexed or not checked.** This invites slow queries and injection.

## Interview questions

### Q1. Design endpoints for orders and order items.

`GET/POST /v1/orders`, `GET/PATCH /v1/orders/{id}`, `POST /v1/orders/{id}/cancellation` for the cancel action, `GET /v1/orders/{id}/items` (items belong to an order), and filters like `GET /v1/orders?status=paid&limit=20&cursor=…`. Creates return `201` with `Location`. Errors use one problem-details format. Money is in minor units. Timestamps are ISO 8601 UTC. Lists are paginated with a maximum limit.

### Q2. How do you version without breaking clients?

I make changes additive whenever I can. New optional fields and endpoints need no version. For breaking changes, I add a new version, usually in the URL (`/v2`), and run both versions side by side. I announce the end of the old one with `Deprecation` and `Sunset` headers. I watch how much the old version is still used, and I remove it only when the traffic is gone. Clients should ignore unknown fields, so additions are safe.

### Q3. How do you make a payment POST safe to retry?

I require an `Idempotency-Key` header. The server saves the key, a fingerprint of the request and the response in a record with a unique constraint. If the same key comes again, the server returns the saved response and does not charge again. The same key with different content is rejected. Two duplicates at the same time are handled one after the other by the constraint. Keys expire after some time.

### Q4. Is returning 200 with an error body ever OK?

No. Status codes drive client logic, retries, monitoring, alerts, caches and gateways. I use the correct 4xx/5xx code and put the details in one consistent problem-details body. The exception is a protocol that does this on purpose, like GraphQL with partial results. Then it is a documented rule, not an accident.

### Q5. PUT vs PATCH?

`PUT` replaces the whole resource and is idempotent. Fields you leave out are cleared. `PATCH` changes only the fields you send, often with JSON Merge Patch rules. I use `PATCH` for partial edits. I check the body with a partial schema, reject unknown fields, and document how `null` is treated.

### Q6. How do you prevent two users overwriting each other's edits?

I use optimistic concurrency. I return an `ETag` or version with the resource. I require `If-Match` (or the version) on updates. If it is old, I reply `412` or `409`. The client reloads, merges and retries. For cases with many conflicts, I could use pessimistic locking (lock the record first) or operational transforms (used in live co-editing). But optimistic locking is enough for most CRUD apps.

### Q7. What should a good error response contain?

It needs the correct status code and a stable code or type that a program can read. It needs a human title and detail. For validation errors, it needs field-level errors with paths. It also needs a request or trace ID. It must never show stack traces, SQL or internal host names. Every endpoint should use the same structure.

### Q8. How would you design filtering and sorting safely?

I allow only listed fields and operators. I check types and ranges. I map them to indexed columns. I set a maximum page size and always paginate. I never put parameters straight into SQL. I use parameterised queries (the values are sent separately from the SQL text) or the ORM. I document the defaults and the tiebreaker that keeps the order stable.

### Q9. Scenario: your public API needs a breaking change to a field that thousands of clients use. How do you ship it?

I avoid a hard break. I add the new field next to the old one (an additive change). I announce the deprecation with `Deprecation` and `Sunset` headers and in the docs. I measure which clients still use the old field, and I give them a long time to move. If the change truly cannot be additive, I add `/v2`, run both versions side by side, move clients slowly, and remove v1 only when its traffic is gone. An OpenAPI breaking-change check in CI stops accidental breaks.

### Q10. Scenario: a client times out on `POST /payments`, retries, and the customer is charged twice. What do you change?

I require an `Idempotency-Key` for each payment attempt. The server stores the key with a request fingerprint under a unique constraint. It returns the saved response for repeats and rejects the same key with a different body. It also passes the key to the payment provider. This way, a crash between the provider call and our save cannot cause a double charge. The client must reuse the same key when it retries. It must treat a timeout as "unknown", not as "failed".

## Key takeaways

- **Nouns for resources, HTTP methods for actions, status codes for results.** Never use `200` for errors.
- Use one **problem-details error format**, stable error codes and request IDs.
- **Always paginate**, cap page sizes, and allow only known filters and sorts.
- **Prefer changes that only add things.** Version breaking changes (URL `/v1` by default) and warn clients before you retire old versions.
- **Idempotency keys** make `POST` safe to retry. **ETags and `If-Match`** prevent lost updates.
- Use ISO 8601 UTC timestamps, whole numbers in minor units for money, and string IDs.
