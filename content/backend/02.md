> **In one line:** a good REST API is **predictable**: nouns for resources, HTTP methods for actions, status codes for outcomes, one error format, and changes that never break existing clients. Predictability is a feature; it is what lets frontend developers guess correctly.

You consume APIs every day as a frontend engineer, which is an advantage: you already know what frustrates a client. This lesson turns those frustrations into design rules, and covers the senior-level topics: versioning, idempotency keys, partial updates, filtering and concurrency control.

## Resources, not verbs

REST models **things (resources)**, and uses HTTP methods as the verbs.

| ❌ RPC-style | ✅ Resource-style |
|---|---|
| `POST /createOrder` | `POST /orders` |
| `GET /getOrderById?id=7` | `GET /orders/7` |
| `POST /deleteOrder` | `DELETE /orders/7` |
| `POST /updateOrderStatus` | `PATCH /orders/7` with `{ "status": "shipped" }` |

Conventions:

- **Plural nouns** for collections: `/orders`, `/users`. Items are `/orders/{id}`.
- **Nest only for true ownership**, and keep it shallow: `/orders/7/items` is fine; `/users/3/orders/7/items/2/refunds` is a smell. Prefer `/refunds?orderId=7` or a top-level resource when depth passes about two.
- **Actions that are not CRUD:** model them as sub-resources or state changes (`POST /orders/7/cancellation`, `POST /payments/{id}/refunds`) rather than verbs in the path. A pragmatic `POST /orders/7/cancel` is common and acceptable if used consistently.
- **Lowercase, hyphenated paths** (`/order-items`), **camelCase JSON fields** (match what the frontend uses).
- Use **identifiers that are safe to expose**: UUIDs/ULIDs avoid leaking counts and enumeration, but authorization must still be enforced.

## Methods and status codes together

A consistent mapping removes guesswork ([HTTP semantics](/browser/lesson-6)):

| Operation | Request | Success | Common errors |
|---|---|---|---|
| List | `GET /orders?status=paid&limit=20` | `200` with items | `400` bad query, `401`, `403` |
| Read one | `GET /orders/7` | `200` | `404`, `403` |
| Create | `POST /orders` | `201` + `Location: /orders/7` | `400`/`422` validation, `409` duplicate |
| Replace | `PUT /orders/7` | `200` or `204` | `404`, `409`, `412` |
| Partial update | `PATCH /orders/7` | `200` (with body) or `204` | `404`, `409`, `422` |
| Delete | `DELETE /orders/7` | `204` | `404` (or `204` again: idempotent) |
| Async work | `POST /reports` | `202` + `Location: /reports/jobs/9` | |

> [!warn] **Never return `200 OK` with an error in the body.** Clients, API gateways, retries logic, monitoring and caches all use the status code. A `200` that says `{"success": false}` breaks every one of them.

## A single error format

Every error, from every endpoint, should have the same shape. The industry standard is **Problem Details for HTTP APIs** (`application/problem+json`):

```json
{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/v1/orders",
  "requestId": "01HZX3V7N8Q2",
  "errors": [
    { "path": "items[0].qty", "code": "too_small", "message": "Must be at least 1" }
  ]
}
```

Why it helps the frontend: it can switch on a stable machine-readable `code`/`type` (not on message text), show field-level errors next to inputs, and show the `requestId` to support. Never leak stack traces or SQL in `detail`.

## Collections: filtering, sorting, pagination

```text
GET /orders?status=paid&createdAfter=2026-01-01&sort=-createdAt&limit=20&cursor=eyJpZCI6MTAwfQ
```

- **Filter** with query parameters named after fields. Validate and whitelist them; do not pass them straight into queries.
- **Sort** with a `sort` parameter (`-` prefix for descending) limited to indexed, allowed fields.
- **Paginate always.** An unbounded list is a future outage. Choose offset or cursor deliberately ([Practical Design Problems, Lesson 03](/design-problems/lesson-3)), set a **maximum limit** (for example 100), and return pagination info.
- **Sparse fields** (`fields=id,status`) and **expansion** (`expand=customer`) let clients trim or enrich responses, if you need them.

```json
{
  "data": [ { "id": "ord_1", "status": "paid" } ],
  "page": { "limit": 20, "nextCursor": "eyJpZCI6MTIwfQ", "hasMore": true }
}
```

Whether to wrap in an envelope (`{ data, page }`) or return a bare array is a taste decision. Wrapping is more evolvable (you can add metadata later without breaking clients), so many teams choose it.

## Data conventions that save pain

- **Timestamps:** ISO 8601 in UTC (`2026-05-01T09:30:00Z`). Do not send local time or epoch milliseconds unless documented.
- **Money:** integers in the **smallest unit** (`amountMinor: 4999` for ₹49.99) plus a `currency` code. Never floats.
- **Nulls vs missing:** decide what each means and document it ("`null` = explicitly cleared; missing = unchanged" for PATCH).
- **Booleans** named positively (`isActive`, not `isNotDisabled`).
- **Enums** as stable strings (`"shipped"`), not numbers.
- **IDs** as strings in JSON (large integers lose precision in JavaScript).

## Versioning

Clients you do not control will not update when you do. Rules:

1. **Prefer additive, backward-compatible changes.** Adding an optional field, a new endpoint or a new enum value (if clients ignore unknown values) needs no version.
2. **Breaking changes** need a new version: removing or renaming a field, changing a type, changing meaning, making an optional field required, tightening validation.
3. **Strategies:**

| Strategy | Example | Pros | Cons |
|---|---|---|---|
| **URL path** | `/v1/orders` | Obvious, easy to route, cache and test | Whole API versioned at once; URL "changes" |
| **Header / media type** | `Accept: application/vnd.example.v2+json` | Clean URLs, per-resource versions | Hidden, harder to try in a browser, easy to forget |
| **Query parameter** | `/orders?version=2` | Simple | Pollutes caching keys; easy to omit |

For most teams, **URL versioning** (`/v1`) is the pragmatic default.

4. **Deprecate gracefully:** announce, add `Deprecation` and `Sunset` response headers, measure who still calls the old version, then remove.
5. **Be tolerant as a server and as a client:** servers ignore unknown request fields cautiously (or reject them deliberately for security), and clients ignore unknown response fields so additive changes are safe.

## Idempotency keys (safe retries)

Networks fail. If `POST /payments` times out, the client cannot know whether it succeeded. A blind retry could charge twice. The fix:

```http
POST /v1/payments
Idempotency-Key: 3d1c0b6e-6a9e-4c4e-9f0a-1a2b3c4d5e6f
```

Server logic:

1. Look up the key (scoped to the user).
2. **Not seen:** process the request, store `(key → request fingerprint, response)`, return the response.
3. **Seen with the same request:** return the **stored response** without redoing the work.
4. **Seen with a different request body:** return `409`/`422` (the key was reused for something else).
5. Concurrent duplicates: use a unique constraint or lock on the key so only one executes; the other waits or gets `409`.
6. Expire keys after a window (for example 24 hours).

```ts
// Simplified: a unique constraint is the guard
await prisma.$transaction(async (tx) => {
  const existing = await tx.idempotencyKey.findUnique({ where: { userId_key: { userId, key } } });
  if (existing) return existing.response;        // replay
  const result = await createPayment(tx, input);  // do the work
  await tx.idempotencyKey.create({ data: { userId, key, response: result } });
  return result;
});
```

`PUT` and `DELETE` are idempotent by nature; `POST` is the one that needs a key.

## Partial updates: PUT vs PATCH

- **`PUT`** replaces the whole resource. Missing fields are treated as cleared, which is dangerous when clients send partial bodies by mistake.
- **`PATCH`** changes only the provided fields. The simple, common convention is **JSON Merge Patch**: send only the fields to change; `null` means "clear this field".
- Validate patch bodies with the same schema made `.partial()`, and reject **unknown fields** so typos do not silently succeed.

## Concurrency control with ETags

Two users edit the same record. Without protection, the second save silently overwrites the first ("lost update"). **Optimistic concurrency:**

```http
GET /articles/5            → 200, ETag: "v7"
PUT /articles/5            If-Match: "v7"
                           → 200  (and a new ETag "v8")
# if someone else saved "v8" first:
                           → 412 Precondition Failed
```

The client re-fetches, merges and retries. You can also use a `version` column and return `409`.

## Other operational conventions

- **Rate limit headers** on responses (`RateLimit-Limit`, `RateLimit-Remaining`, `Retry-After` on `429`) so clients can back off ([Practical Design Problems, Lesson 02](/design-problems/lesson-2)).
- **Request IDs** returned in a header and error bodies for debugging ([Lesson 05](/backend/lesson-5)).
- **CORS** configured deliberately ([Browser Contract, Lesson 04](/browser/lesson-4)).
- **Compression** (gzip or Brotli) and **caching headers** where appropriate: `ETag` on `GET`s enables cheap `304` revalidation.
- **Documentation as code:** an OpenAPI description kept in the repo, ideally generating types for the frontend so contract drift becomes a compile error ([Lesson 03](/backend/lesson-3)).
- **Bulk operations:** prefer explicit endpoints (`POST /orders/batch`) with a clear partial-failure contract (`207`-style per-item results) over overloading single-item endpoints.

## What about HATEOAS, GraphQL and RPC?

"Pure" REST includes hypermedia links; most real APIs are "REST-ish" (resources plus HTTP semantics) and that is fine. When clients need very different shapes of the same data, or you want a typed single endpoint, GraphQL may fit ([Lesson 09](/backend/lesson-9)). For internal service-to-service calls with strict contracts, gRPC is common. Pick deliberately, and say why.

## Common mistakes

1. **Verbs and RPC names in paths** (`/getUsers`), mixed with REST elsewhere.
2. **`200` with an error body**, or inconsistent error shapes between endpoints.
3. **No pagination** on list endpoints.
4. **Breaking changes without a version**, or no deprecation process.
5. **Floats for money, local-time strings for dates, numeric IDs as JSON numbers.**
6. **Non-idempotent `POST` retried blindly**, causing duplicates.
7. **Exposing database structure** (internal IDs, table-shaped responses) rather than designing for the client's use.
8. **Filtering/sorting on unindexed or unvalidated fields**, inviting slow queries and injection.

## Interview questions

### Q1. Design endpoints for orders and order items.

`GET/POST /v1/orders`, `GET/PATCH /v1/orders/{id}`, `POST /v1/orders/{id}/cancellation` for the cancel action, `GET /v1/orders/{id}/items` (items belong to an order), and filters like `GET /v1/orders?status=paid&limit=20&cursor=…`. Creates return `201` with `Location`, errors use one problem-details format, money is in minor units, timestamps are ISO 8601 UTC, and lists are paginated with a maximum limit.

### Q2. How do you version without breaking clients?

Make changes additive whenever possible (new optional fields and endpoints need no version). For breaking changes, introduce a new version, usually in the URL (`/v2`), run both side by side, announce deprecation with `Deprecation`/`Sunset` headers, track usage of the old version, and remove it only when traffic is gone. Clients should ignore unknown fields so additions are safe.

### Q3. How do you make a payment POST safe to retry?

Require an `Idempotency-Key` header. The server stores the key with a fingerprint of the request and the resulting response in a unique-constrained record. A repeat with the same key returns the stored response without charging again; the same key with different content is rejected; concurrent duplicates are serialised by the constraint. Keys expire after a window.

### Q4. Is returning 200 with an error body ever OK?

No. Status codes drive client logic, retries, monitoring, alerting, caches and gateways. Use the correct 4xx/5xx and put details in a consistent problem-details body. The exception is protocols that deliberately do it (GraphQL's partial results), and then it is a documented convention rather than an accident.

### Q5. PUT vs PATCH?

`PUT` replaces the resource entirely and is idempotent; omitted fields are cleared. `PATCH` changes only the supplied fields, commonly with JSON Merge Patch semantics. I use `PATCH` for partial edits, validate with a partial schema, reject unknown fields and document how `null` is treated.

### Q6. How do you prevent two users overwriting each other's edits?

Optimistic concurrency: return an `ETag` or version with the resource, require `If-Match` (or the version) on updates, and respond `412` or `409` when it is stale. The client reloads, merges and retries. For high-contention cases consider pessimistic locking or operational transforms, but optimistic locking covers most CRUD apps.

### Q7. What should a good error response contain?

The correct status code, a stable machine-readable code or type, a human title and detail, field-level errors with paths for validation failures, and a request or trace ID. It must never expose stack traces, SQL or internal hostnames. The same structure should be used everywhere.

### Q8. How would you design filtering and sorting safely?

Whitelist the allowed fields and operators, validate types and ranges, map them to indexed columns, set a maximum page size and always paginate. Never interpolate parameters into SQL; use parameterised queries or the ORM. Document defaults and the deterministic tiebreaker used for stable ordering.

### Q9. Scenario: your public API needs a breaking change to a field that thousands of clients use. How do you ship it?

I avoid a hard break. Add the new field alongside the old one (an additive change), announce the deprecation with `Deprecation` and `Sunset` headers and docs, measure which clients still use the old field, and give them a long window. If the change truly cannot be additive, introduce `/v2`, run both versions side by side, migrate clients gradually and remove v1 only when its traffic is gone. An OpenAPI breaking-change check in CI prevents accidental breaks.

### Q10. Scenario: a client times out on `POST /payments`, retries, and the customer is charged twice. What do you change?

Require an `Idempotency-Key` per payment attempt. The server stores the key with a request fingerprint under a unique constraint, returns the stored response for repeats, rejects the same key with a different body, and passes the key to the payment provider so a crash between the provider call and our save cannot double-charge. The client must reuse the same key on retries and treat a timeout as unknown rather than failed.

## Key takeaways

- **Nouns for resources, HTTP methods for actions, status codes for outcomes**; never `200` for errors.
- One **problem-details error format**, stable error codes, request IDs.
- **Always paginate**, cap page sizes, whitelist filters and sorts.
- **Prefer additive changes**; version breaking ones (URL `/v1` by default) and deprecate with notice.
- **Idempotency keys** make `POST` retry-safe; **ETags/`If-Match`** prevent lost updates.
- Use ISO 8601 UTC timestamps, integer minor units for money, string IDs.
