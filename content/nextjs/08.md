> **In one line:** Config is where most "works on my machine" bugs hide. In Next.js, a plain environment variable stays on the server, but a variable that starts with `NEXT_PUBLIC_` is copied into the browser JavaScript **when you build**, and cannot change after that. Static pages read their variables at build time too. To ship the app, you run `next build`, then either `next start`, the `standalone` output, or a Docker image. I did all three, and the numbers and outputs are below.

This lesson goes through them in the order you meet them, and proves each claim.

## Words used in this lesson

- **Environment variable** is a named value that lives outside your code, such as `DATABASE_URL`. Programs read it at start or at run time.
- **`.env` file** is a text file with `NAME=value` lines. Next.js reads it into `process.env`.
- **Build time** is when you run `next build`. **Run time** is when the server runs and answers requests.
- **Inline** means to replace a variable with its value inside the code at build time, like find and replace.
- **`NEXT_PUBLIC_`** is a name prefix. Variables that start with it are inlined into the JavaScript sent to the browser.
- **Secret** is a value that must stay private: a database password, an API key, a session signing key.
- **`next.config.ts`** is the settings file at the root of a Next.js project.
- **Standalone output** is a build mode (`output: 'standalone'`) that makes a small folder with only the files needed to run the server.
- **Output file tracing** means Next.js follows your `import`s to find which files each page needs, so it can copy only those.
- **Docker image** is a packaged app plus its runtime. A **container** is a running copy of an image.
- **Multi-stage build** is a Dockerfile that uses several `FROM` steps, so the final image does not carry build tools.
- **Instrumentation** is code that sets up logging and monitoring when the server starts. The file is `instrumentation.ts`.
- **Health check** is a small endpoint that says "I am alive", used by a platform to decide if a container is working.
- **Version skew** means a browser running old code talks to a server running new code, after a deployment.

## Environment variables: the load order

Next.js reads `.env` files for you. You do not need the `dotenv` package. The docs say the lookup goes in this order and stops at the first match:

1. `process.env` (the variables that are really set in the shell or the platform)
2. `.env.$(NODE_ENV).local`
3. `.env.local` (not read when `NODE_ENV` is `test`)
4. `.env.$(NODE_ENV)`
5. `.env`

`NODE_ENV` is `development` for `next dev` and `production` for `next build` and `next start`. Let me prove the order. I made three files, and put the same name, `SHARED`, in each:

```text
.env              GREETING=from-.env             SHARED=env
.env.production   SHARED=env.production          NEXT_PUBLIC_API_URL=https://api.prod.example.com
.env.local        SECRET_TOKEN=sk_live_super_secret_123
                  NEXT_PUBLIC_BUILD_LABEL=label-from-env-local
                  SHARED=env.local
```

(The `sk_live_...` value is made up for this lab.) `next build` told me which files it loaded, in order:

```text
- Environments: .env.local, .env.production, .env
```

And a static page that prints `GREETING` and `SHARED` showed:

```text
GREETING=from-.env SHARED=env.local (read while building)
```

`GREETING` exists only in `.env`, so it came from there. `SHARED` is in all three files, and `.env.local` won. Good: `.env.local` is meant for your own machine and for secrets. The create-next-app template adds `.env*.local` to `.gitignore`. This blog's `.gitignore` has the same line. The docs say you almost never want to commit these files.

> [!warn] **Commit `.env` with safe defaults if you like, never commit `.env.local` or a real secret.** A secret that was ever in git history must be treated as leaked, even if you delete it later. See [Secrets, Encryption and Data Protection](/security/lesson-5).

## Server variables and `NEXT_PUBLIC_` variables

Here is the rule from the docs: **by default, an environment variable exists only on the server.** If you want the browser to see it, you must start its name with `NEXT_PUBLIC_`. Next.js then **inlines** the value into the JavaScript during `next build`.

Let me show both halves in a real browser. I made a Client Component that prints three variables:

```tsx
'use client'
// app/leak/client.tsx (shortened)
setTxt(JSON.stringify({
  NEXT_PUBLIC_API_URL: process.env.NEXT_PUBLIC_API_URL,
  NEXT_PUBLIC_BUILD_LABEL: process.env.NEXT_PUBLIC_BUILD_LABEL,
  SECRET_TOKEN: process.env.SECRET_TOKEN,
}))
```

Then I opened the page with Playwright and read what the browser printed:

```text
{"NEXT_PUBLIC_API_URL":"https://api.prod.example.com","NEXT_PUBLIC_BUILD_LABEL":"label-from-env-local"}
```

Two keys, no `SECRET_TOKEN`. (`JSON.stringify` leaves out `undefined`, so the secret was `undefined` in the browser.) So a plain variable did **not** leak. I also searched the build output for the secret:

```text
secret in .next/static: 0 files
```

Zero files in the folder that is sent to browsers. Good.

Two warnings here.

**First: the failure is silent.** If you forget the prefix on a value the browser needs, you do not get an error. You get `undefined`, and a bug that shows up only in the browser. In the other direction, putting `NEXT_PUBLIC_` on a secret is a leak. The name is the only guard. Review any `NEXT_PUBLIC_` name as if it were printed on the page, because it is.

**Second: a good guard exists for server code.** Put `import 'server-only'` at the top of a file that uses secrets. If a Client Component imports it, even by accident, the build fails. I tested it, and the real output was:

```text
Error: 'server-only' cannot be imported from a Client Component module
> 1 | import 'server-only'
It should only be used from a Server Component.
Import traces:
  Client Component Browser:
    ./a8/lib/secret.ts [Client Component Browser]
    ./a8/app/leak2/page.tsx [Client Component Browser]
```

(You also saw this in [lesson 5](/nextjs/lesson-5).) The docs also mention a `taint` option for marking a value as not allowed to reach the client. I did not test it.

## "Build time" is the trap

Now the part that surprises people. I started the production server with **different** values from the ones I built with:

```text
GREETING=changed-at-start SHARED=changed-at-start \
NEXT_PUBLIC_API_URL=https://runtime-override.example.com next start -p 3109
```

And then I asked for three things.

```text
static:  GREETING=from-.env SHARED=env.local (read while building)
runtime: GREETING=changed-at-start SHARED=changed-at-start (read per request)
```

- The **static page** still showed the old values. It was built during `next build`, with the variables of that moment, and the file does not change.
- The **runtime page** showed the new values. It is dynamic (it calls `await connection()`), so it reads `process.env` on each request. A real environment variable beats the `.env` files, as the load order says.

And the browser variable:

```text
files in .next/static with the build-time URL (api.prod.example.com):   1
files in .next/static with the runtime URL (runtime-override):           0
```

The `NEXT_PUBLIC_API_URL` I gave at **start** time was ignored. The browser code still had the value from the **build**. This is exactly what the docs say: after the build, the app no longer responds to changes in `NEXT_PUBLIC_` variables. If you build one Docker image and promote it from "staging" to "production", the browser code will still point to the staging URL.

So there are two kinds of values, and you must keep them straight:

| Kind | Example | When the value is fixed | How to change it |
|---|---|---|---|
| Server variable, read in a **dynamic** route or route handler | `DATABASE_URL` | Each request (when `process.env` is read) | Restart the container with a new value |
| Server variable, read in a **static** page or at module load | A site name in a prerendered page | At build time | Rebuild |
| `NEXT_PUBLIC_` variable | `NEXT_PUBLIC_API_URL` | At build time, inside the JavaScript | Rebuild |

The docs give two ways out for "I need one image for many environments": (1) read the value on the server during dynamic rendering, after calling `connection()` (or any request API), and pass it to the browser as a prop, or (2) serve a small API that returns the config. The doc comment says it plainly: the variable is read at run time "meaning this env variable is evaluated at runtime".

> [!warn] **A dynamic lookup is not inlined.** The docs say that `process.env[varName]` and `const env = process.env; env.NEXT_PUBLIC_X` are **not** replaced at build time, because Next.js can only find the plain form `process.env.NEXT_PUBLIC_X`. In the browser those would be `undefined`. I did not test this one. I am quoting the docs.

> [!note] **How this blog does it.** Its `lib/site.ts` builds the site URL from, in order: `NEXT_PUBLIC_SITE_URL`, then Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, then `VERCEL_URL`, then `http://localhost:3000`. It also decides whether the deployment may be indexed, with `process.env.VERCEL_ENV`. This is a good pattern: one file reads the environment, with a sensible fallback, and the rest of the code imports a constant.

## `next.config.ts`: what lives there

`next.config.ts` (or `.js`, `.mjs`) is in the project root. It exports an object. Most settings you will use fall into a few groups:

- **Headers, redirects, rewrites.** (`headers()`, `redirects()`, `rewrites()`. Lesson 4 covers redirects and rewrites.)
- **Images.** `images.remotePatterns`, `formats`, `qualities`. (Lesson 7.)
- **Output.** `output: 'standalone'` or `'export'`.
- **Caching model.** `cacheComponents: true`. (Lessons 2 and 6.)
- **Server Actions.** `serverActions.allowedOrigins`. (Lesson 5.)
- **Small switches.** `poweredByHeader`, `reactStrictMode`, `typedRoutes`, `experimental.*`.

The config file runs only when the build or the server starts, so it can read `process.env`. I saw `✓ Running next.config.ts took 51ms` in the output each time.

Headers are the most useful production setting. Mine:

```ts
const nextConfig: NextConfig = {
  output: 'standalone',
  poweredByHeader: false,
  async headers() {
    return [{ source: '/:path*', headers: [
      { key: 'X-Content-Type-Options', value: 'nosniff' },
      { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
    ] }]
  },
}
```

What `curl -i` saw:

```text
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
```

and there was **no** `X-Powered-By: Next.js` header, because `poweredByHeader: false`. That header tells everyone which framework you run, which helps attackers a little and helps you not at all.

This blog's `next.config.ts` is a nice real example of production headers. It sets a Content-Security-Policy (CSP), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Strict-Transport-Security`, `Permissions-Policy` and `Cross-Origin-Opener-Policy`. It turns the CSP **off in development**, because the dev tools need more than a strict policy allows. And a comment explains a trade-off: a per-request CSP nonce would force every page to be dynamic, so this fully static site allows inline scripts and limits the external origins instead. For the theory behind each header, see [XSS, CSRF, Clickjacking and Security Headers](/security/lesson-2) and [Frontend Security Checklist](/browser/lesson-7).

## Three ways to run it

### 1. `next start`

The simplest. You copy the project, run `npm ci`, `npm run build`, `npm run start`. It needs the whole `node_modules` folder (mine is 402 MB here). The docs say this server supports **all** Next.js features. It reads the `PORT` variable (or `-p`). The docs recommend putting a reverse proxy such as nginx in front, to handle slow clients, payload limits and rate limits.

### 2. Standalone output

With `output: 'standalone'`, `next build` makes a folder `.next/standalone` with only the files the server needs. It uses output file tracing: it follows your imports and copies just those files and the used parts of `node_modules`. Compare the sizes:

```text
67M   .next/standalone
592K  .next/static
402M  node_modules (the full dev install)
```

A 67 MB folder instead of 402 MB. It contains a tiny `server.js`. You start it with `node server.js`, not `next start`. I saw a message about this:

```text
⚠ "next start" does not work with "output: standalone" configuration. Use "node .next/standalone/server.js" instead.
```

(In my test, `next start` still answered requests, but I would follow the warning.) Two more things from the docs that I checked:

- The standalone folder does **not** copy `public/` or `.next/static`, because a CDN should serve them. If you serve them from the same server, you copy them yourself. I copied them and ran:

```bash
cp -r public .next/standalone/a8/
cp -r .next/static .next/standalone/a8/.next/
cd .next/standalone/a8 && PORT=3110 HOSTNAME=127.0.0.1 GREETING=standalone-run node server.js
```

```text
▲ Next.js 16.3.5
- Local:         http://127.0.0.1:3110
✓ Ready in 0ms
[instrumentation] register() runs once at server start, pid 3956
```

```text
$ curl localhost:3110/api/health
{"ok":true,"node":"v22.22.0","uptimeSeconds":2}
$ curl localhost:3110/runtime      ->  GREETING=standalone-run SHARED=env.production (read per request)
static asset: 200
```

`PORT` and `HOSTNAME` control where it listens. `GREETING=standalone-run` was read at run time, as expected.

- Look at the path: `.next/standalone/a8/server.js`, not `.next/standalone/server.js`. My lab app lives in a subfolder of a folder with its `node_modules`, so Next.js used the parent as the tracing root and kept the folder name. In a monorepo the docs say to set `outputFileTracingRoot`, and the tracing root decides where `server.js` ends up. If you cannot find `server.js`, look here first.

And an important detail about env files: in the standalone folder, I found `.env` and `.env.production`, but **not** `.env.local`. The server printed `SHARED=env.production`, not `env.local`. So the secrets in `.env.local` were not there. I did not dig into why. The lesson is to **never depend on `.env` files in an image or a server**. Set real environment variables in the platform.

### 3. A Docker image

The docs say Docker supports all features and show the standalone pattern. Here is the Dockerfile I used. It has three stages: install, build, and a small runtime image:

```dockerfile
# syntax=docker/dockerfile:1
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:22-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
# NEXT_PUBLIC_* values are frozen into the browser JS here, at build time.
ARG NEXT_PUBLIC_API_URL=https://api.example.com
ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL
RUN npm run build

FROM node:22-alpine AS run
WORKDIR /app
ENV NODE_ENV=production
ENV PORT=3000
ENV HOSTNAME=0.0.0.0
RUN addgroup -S app && adduser -S app -G app
COPY --from=build --chown=app:app /app/.next/standalone ./
COPY --from=build --chown=app:app /app/.next/static ./.next/static
COPY --from=build --chown=app:app /app/public ./public
USER app
EXPOSE 3000
CMD ["node", "server.js"]
```

The key points:

- **Three stages.** The final image has no build tools, no source and no dev dependencies. Only the standalone output.
- **`ARG` for `NEXT_PUBLIC_`.** These must be known at **build** time. A `docker run -e NEXT_PUBLIC_X=...` is too late. I will prove it below.
- **`HOSTNAME=0.0.0.0`.** Inside a container, the server must listen on all interfaces, or you cannot reach it from outside.
- **A non-root user.** `USER app`, so a bug in the app does not run as root.
- **A `.dockerignore`** with `node_modules`, `.next`, `.env.local` and `.git`, so you do not send your secrets and your local build into the build context.

I built it:

```text
docker build ... -t nb-lab:1 .
...
#16 [run 4/6] COPY --from=build --chown=app:app /app/.next/standalone ./
#17 [run 5/6] COPY --from=build --chown=app:app /app/.next/static ./.next/static
#18 [run 6/6] COPY --from=build --chown=app:app /app/public ./public
#19 naming to docker.io/library/nb-lab:1 done      (about 48 seconds on a cold cache)
```

```text
IMAGE      DISK USAGE   CONTENT SIZE
nb-lab:1   332MB        84.9MB
node:22-alpine  238MB   61.1MB          (the base image alone)
```

The app adds about 94 MB on disk to the 238 MB base image. Now I ran it, and passed runtime variables, **including a different `NEXT_PUBLIC_API_URL`**:

```bash
docker run -d --name nb-run --network host \
  -e PORT=3111 -e GREETING=from-docker-run \
  -e NEXT_PUBLIC_API_URL=https://changed-at-run.example.com nb-lab:1
```

```text
▲ Next.js 16.3.5
- Local:         http://localhost:3111
- Network:       http://0.0.0.0:3111
✓ Ready in 0ms
[instrumentation] register() runs once at server start, pid 1
```

```text
$ curl localhost:3111/api/health
{"ok":true,"node":"v22.23.3","uptimeSeconds":3}
$ curl localhost:3111/runtime   ->  GREETING=from-docker-run SHARED=env.production (read per request)

files in /app/.next/static with the build ARG url (api.example.com): 1
files in /app/.next/static with the runtime -e url (changed-at-run): 0
```

Everything matches what I proved earlier:

- The container ran as user `app`, not root.
- `GREETING`, a server variable, was read at run time from `-e`.
- The browser variable was **not** changed by `-e`. It stayed at the value from the build.
- The server started as process `pid 1`, so signals (like a stop request) reach it directly.

> [!warn] **If you need one image for staging and production, do not put environment-specific URLs in `NEXT_PUBLIC_` variables.** Either build one image per environment (pass different `--build-arg` values), or have the server read the value at run time and hand it to the browser.

**What I did not test:** Kubernetes, health probes against this image, or running several copies of the container at once. The docs warn about three things there: the default cache is kept **per instance** (in memory and on disk), so a revalidation on one pod does not reach the others unless you configure a shared cache handler; all instances must share the same Server Actions encryption key (`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`), or users get "Failed to find Server Action" errors after a request lands on another instance; and a rolling deploy needs a `deploymentId` for version-skew protection, so old browsers do not request files that new servers no longer have.

## Deploying to a platform

The docs list four options: a **Node.js server** (all features), a **Docker container** (all features), a **static export** (limited), and **adapters** for platforms. Vercel and Bun have verified adapters, according to the page I read. They also list templates for many hosts (Railway, Fly.io, Google Cloud Run, Render, DigitalOcean and others).

On a platform like Vercel, you connect the Git repository, the platform runs `next build` for you, and it serves static files from a CDN and runs dynamic routes as functions. You set environment variables in the platform's dashboard, per environment (production, preview). The platform also sets its own variables. This blog reads `VERCEL_ENV` and `VERCEL_PROJECT_PRODUCTION_URL` from them. I did not deploy anything, so I cannot show you output.

A **static export** (`output: 'export'`) builds plain HTML, CSS and JS files that any web server can host, such as S3. The docs say it does not support features that need a server. That includes `proxy.ts` and server rendering per request. I did not run one. If your site is a pure blog, it is worth asking if you need more than that.

A last point from the docs' rendering guide: the finer-grained rendering model of Next.js (streaming, partial prerendering, on-demand revalidation) moves some complexity into the **hosting platform**. A single Node.js process supports every feature. Streaming needs the proxies and CDNs in front of it not to buffer the response. Nginx and similar proxies buffer by default, and the docs say to send the header `X-Accel-Buffering: no` to turn that off. If your streamed page seems to arrive all at once in production but not locally, look for a buffering proxy.

## Logging and monitoring

When a production server breaks, you have two questions: what happened, and how often? Next.js gives you one hook for the first: `instrumentation.ts` in the project root. It can export two functions:

- `register()` runs **once**, when a new server instance starts, before it takes requests. Use it to start your monitoring SDK. The docs show `registerOTel('next-app')` from `@vercel/otel` for OpenTelemetry.
- `onRequestError(error, request, context)` runs when the server captures an error. Use it to send errors to your error tracker.

Mine just prints to the console. I also made a route that throws, to trigger it:

```ts
// instrumentation.ts
export function register() {
  if (process.env.NEXT_RUNTIME === 'nodejs') console.log('[instrumentation] register() runs once at server start, pid', process.pid)
}
export const onRequestError: Instrumentation.onRequestError = async (err, request, context) => {
  const message = err instanceof Error ? err.message : String(err)
  console.log('[instrumentation] onRequestError', JSON.stringify({ message, path: request.path, method: request.method, routeType: context.routeType, routePath: context.routePath }))
}
```

```text
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3109/api/boom
500
```

and the server log:

```text
[instrumentation] register() runs once at server start, pid 3723
⨯ Error: boom from route handler
    at <unknown> (.next/server/chunks/[root-of-the-server]__0q20b9r._.js:1:1073)
[instrumentation] onRequestError {"message":"boom from route handler","path":"/api/boom","method":"GET","routeType":"route","routePath":"/api/boom"}
```

The hook got the message, the path, the method and, from `context`, that it was a `route` (not a page render or an action). In a real app, you would send that to an error tracker. The docs warn that the error object may not be the original: React can change it during Server Component rendering, and you can use its `digest` to match it to the log line. They also say to `await` any async work inside the hook.

Other habits that need almost no code:

- **A health endpoint.** I made `app/api/health/route.ts` with `export const dynamic = 'force-dynamic'`. It returned `{"ok":true,"node":"v22.22.0","uptimeSeconds":7}`. A platform can call it to see if the process is alive. Keep it cheap: do not make it call your database unless you also want "ready" checks.
- **Log to stdout.** In a container, `console.log` goes to the platform's log system. Do not write log files inside the container.
- **Web vitals from real users.** Use the `useReportWebVitals` hook (lesson 7).
- **Do not log secrets.** A request header or an environment object can contain them. See [Logging and Observability](/backend/lesson-5).

## A short production checklist

This is my own list, based on what I proved above and on the docs' checklist. Tick each one before you go live.

1. `next build` passes in CI, and I read the route table. Each route is what I expect.
2. I ran `next start` (or the standalone server, or the image) and clicked through. Not just `next dev`.
3. No secret has a `NEXT_PUBLIC_` name. Files that use secrets import `server-only`.
4. `.env*.local` is in `.gitignore`. No `.env` file is needed inside the image. Real variables are set on the platform.
5. Every `NEXT_PUBLIC_` value is correct **at build time** for that environment.
6. Metadata has `metadataBase`, and previews are not indexable.
7. Security headers are set (`headers()` or a CDN), and `poweredByHeader` is off.
8. Images have sizes and `remotePatterns`. Fonts come from `next/font`.
9. `app/error.tsx`, `app/not-found.tsx` and `app/global-error.tsx` exist (the docs recommend a global error page and a global 404).
10. Errors reach my tracker through `onRequestError`, or an SDK in `register()`.
11. Multiple instances: shared cache handler, same encryption key, a `deploymentId`.
12. A buffering proxy does not break streaming.
13. The container runs as a non-root user, listens on `0.0.0.0`, and I know how it is stopped.

## Common mistakes

- Using `NEXT_PUBLIC_` on a secret.
- Forgetting the prefix on a value the browser needs, and getting `undefined`.
- Expecting `docker run -e NEXT_PUBLIC_X=...` to change browser code.
- Reading `process.env` in a static page and expecting it to follow the environment at run time.
- Committing `.env.local`, or copying it into an image.
- Using `process.env[name]` with a variable name for a public variable.
- `HOSTNAME` not set to `0.0.0.0` in a container, so the app is not reachable.
- Forgetting to copy `public/` and `.next/static` next to a standalone `server.js` and no CDN serving them.
- A single `Dockerfile` stage that keeps all of `node_modules` and the source in the final image.
- Running several instances with the default per-instance cache and expecting `revalidateTag` to reach all of them.
- Putting Node-only code in `instrumentation.ts` without the `NEXT_RUNTIME` check.
- Testing production behavior only in dev.

## Try it

1. Make `.env`, `.env.production` and `.env.local`, each with `SHARED=` and a different value. Run `next build` and look at the line that starts with `Environments:`. Which value does a static page show?
2. Make a static page and a page that calls `await connection()` that both print `process.env.GREETING`. Build, then start with `GREETING=new npm run start`. Which page changes?
3. Make a Client Component that prints `process.env.NEXT_PUBLIC_X` and `process.env.SECRET_X`. What does the browser show for each?
4. Build with `NEXT_PUBLIC_X=one`, then start with `NEXT_PUBLIC_X=two`. What does the browser show? How can you check the JS files?
5. Make a file with `import 'server-only'` and import it from a Client Component. What happens at build time?
6. Add `output: 'standalone'` and build. How big is `.next/standalone`? Run it with `node .../server.js` and `PORT=4000`.
7. Add an `instrumentation.ts` with `register` and `onRequestError`. Make a route that throws. What do you see in the log?
8. (Optional) Write the three-stage Dockerfile. Build it and run it with `-e` for one server variable and one `NEXT_PUBLIC_` variable. Which one changes?

### Answers

1. The line lists the files in order. A variable that is in several files shows the value from the most specific one: `.env.local` before `.env.production` before `.env`.
2. Only the `connection()` page. The static page was built before the start, with the old value.
3. `NEXT_PUBLIC_X` shows its value. `SECRET_X` is `undefined`.
4. It shows `one`. Search the files in `.next/static` with `grep`. You find `one`, and you do not find `two`.
5. The build fails with "'server-only' cannot be imported from a Client Component module" and an import trace.
6. Usually tens of MB, much smaller than a full `node_modules`. It listens on port 4000.
7. The `register` line once at start, and an `onRequestError` line for each error, with the message, path and route type.
8. The server variable changes. The `NEXT_PUBLIC_` one does not, because it was frozen into the JavaScript at build time.

## Interview questions

### Q1. How do environment variables work in Next.js? (Must know)

Next.js loads `.env` files into `process.env`. The lookup order is the real environment, then `.env.$(NODE_ENV).local`, then `.env.local`, then `.env.$(NODE_ENV)`, then `.env`, and it stops at the first match. By default, variables are only available on the server. Variables that start with `NEXT_PUBLIC_` are inlined into the browser JavaScript at build time. I proved the order with a variable in three files: `.env.local` won.

### Q2. What does `NEXT_PUBLIC_` really do, and what is the catch? (Senior signal)

At build time, Next.js replaces `process.env.NEXT_PUBLIC_X` with the literal value in the JavaScript it sends to the browser. The catch is that it is frozen. I built with one URL and started with another, and the browser files still had the build-time URL. So one Docker image cannot serve several environments if the browser needs different values. I either build per environment, or read the value on the server at run time and pass it down, or serve it from a small API.

### Q3. Can a normal server variable leak to the browser? (Trap)

Not by itself. In a Client Component, `process.env.SECRET` is `undefined`, and I found zero copies of my test secret in the `.next/static` folder. The leaks come from: a `NEXT_PUBLIC_` name on a secret, passing a secret as a prop from a Server Component to a Client Component, or logging it. I add `import 'server-only'` to files that use secrets, which makes the build fail if a Client Component imports them. I tested that.

### Q4. A page shows an old value of an environment variable after I changed it on the server. Why? (Trap)

If the page is static, it was built at build time, so `process.env` was read once, then. Changing the variable later changes nothing until the next build. I started a server with a new `GREETING`: the dynamic page used it and the static page did not. To read it at run time, the route must be dynamic (for example, call `connection()` or use a request API). Or I rebuild after changing it.

### Q5. What is `output: 'standalone'`, and when would you use it? (Senior signal)

It makes `.next/standalone`, a small folder with only the files the server needs, found by tracing your imports, plus a `server.js` to start it with `node`. My lab went from a 402 MB `node_modules` to 67 MB. I use it for Docker images. It does not copy `public/` or `.next/static`, so I copy them or serve them from a CDN. In a monorepo I set `outputFileTracingRoot`, which also decides where `server.js` ends up.

### Q6. How would you containerize a Next.js app? (Must know)

A multi-stage Dockerfile: one stage installs dependencies, one runs `next build` with `output: 'standalone'`, and a last small stage copies the standalone folder, `.next/static` and `public`, runs as a non-root user, sets `HOSTNAME=0.0.0.0` and `PORT`, and starts `node server.js`. Build-time values such as `NEXT_PUBLIC_` go in as `ARG`s. I built one: the image was 332 MB on disk with a 238 MB base. A `.dockerignore` keeps `.env.local` and `node_modules` out of the build context.

### Q7. I changed `NEXT_PUBLIC_API_URL` with `docker run -e`, and the browser still calls the old URL. Why? (Trap)

Because the value was inlined into the JavaScript during `next build`, which ran when the image was built. `docker run -e` changes only the process environment at run time. I tested it: the build-time URL was in one JavaScript file and the run-time URL was in none. The fix is a rebuild with a different `--build-arg`, or reading the value on the server at run time.

### Q8. What do you put in `next.config.ts` for production? (Senior signal)

Security headers through `headers()`, `poweredByHeader: false`, `images.remotePatterns` and format settings, redirects, `output: 'standalone'` for containers, and any caching flags. I verified the headers with `curl -i`, and that `X-Powered-By` disappeared. This blog turns off its strict CSP in development, because dev tools need more than the policy allows.

### Q9. How do you monitor errors and start monitoring in a Next.js server? (Senior signal)

With `instrumentation.ts` in the project root. `register()` runs once when a server instance starts, and I use it to start a monitoring SDK such as OpenTelemetry. `onRequestError` runs when the server captures an error and gives me the error, the request path and method, and a context with the route type (`render`, `route`, `action` or `proxy`). I confirmed it with a route that throws. I guard Node-only code with `process.env.NEXT_RUNTIME === 'nodejs'`, because the file is also compiled for the edge runtime and the build warned me when I did not.

### Q10. What changes when you run several instances of a Next.js app? (Senior signal)

Three things, from the docs. The default cache is per instance, so `revalidateTag` on one does not reach the others unless I configure a shared cache handler. All instances need the same `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`, or an action encrypted by one instance fails on another with "Failed to find Server Action". And rolling deploys need a `deploymentId` to protect against version skew. I did not run multiple instances myself, so this part is from the documentation.

### Q11. Why does a streamed page arrive all at once in production? (Trap)

Something between the server and the browser buffers the response. Nginx and similar reverse proxies buffer by default. The docs say to set the header `X-Accel-Buffering: no` (for example from `next.config.ts` headers) so the proxy passes chunks through. A CDN can do the same. I measured chunks arriving over time when I connected directly to the Node server, so I know the server was not the problem.

### Q12. What is a good health check for a Next.js container? (Senior signal)

A tiny route handler that returns `200` and a small JSON, marked dynamic so it runs on every request. It tells the platform the process is alive and can answer. I keep it cheap and separate from a deeper "ready" check that touches the database, because a database blip should not make the platform kill every container. I tested a version that returned `{"ok":true,"uptimeSeconds":...}`.

## Key takeaways

- Load order: real environment, then `.env.$(NODE_ENV).local`, `.env.local`, `.env.$(NODE_ENV)`, `.env`. I proved it with one variable in three files.
- Server variables stay on the server. `NEXT_PUBLIC_` variables are copied into the browser JavaScript at **build** time and never change after that. I tried to override one at start time and failed.
- Static pages read the environment when you build. Dynamic routes read it on each request.
- Use `import 'server-only'` for files with secrets. A wrong import fails the build with a trace.
- `next.config.ts` holds headers, images, output mode and flags. Turn off `poweredByHeader`. Set security headers.
- `output: 'standalone'` cut my deployable folder from 402 MB to 67 MB. Start it with `node server.js`, and copy `public` and `.next/static` yourself.
- A Docker image: three stages, non-root user, `HOSTNAME=0.0.0.0`, `ARG` for build-time values. Mine was 332 MB and behaved as proved.
- `instrumentation.ts` gives you `register` and `onRequestError`. Guard Node-only code with `NEXT_RUNTIME`.
- With many instances, plan for a shared cache, one encryption key and a deployment ID. I did not test those.
- I did not deploy to a host. Test your own platform, and always run a production build first.
