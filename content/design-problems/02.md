> **In one line:** a rate limiter decides, per caller, whether a request may proceed **right now**. The algorithm is the easy part; the interview is about **where it runs, how counts are shared across servers atomically, what you return to clients, and what happens when the limiter itself fails**.

You met rate limits as a client in [Debugging, Lesson 09](/debugging/lesson-9) (the unexpected `429`). Now design the thing that returns it.

## 1. Requirements

**Functional**

- Limit requests per **key**: user ID, API key, IP address, or a combination (and per route, for example login attempts stricter than reads).
- Support **multiple rules** (100 requests per minute **and** 5,000 per day; burst allowed).
- Reject excess requests with **HTTP 429** and tell the client when to retry.
- Configurable per plan or endpoint, changeable without redeploying.

**Non-functional**

- **Very low latency**: it runs on every request (target under 1 to 2 ms added).
- **Accurate across many servers**: 10 instances must not each allow the full limit.
- **Highly available**: the limiter must not become the outage.
- Memory-efficient for millions of keys.

Also distinguish related ideas:

| Concept | What it protects against | Example |
|---|---|---|
| **Rate limiting** | One caller sending too fast | 100 requests per minute per API key |
| **Quota** | Total usage over a long period (billing) | 1 million calls per month |
| **Load shedding** | The system itself being overloaded, regardless of caller | Drop low-priority traffic when CPU is above 90% |
| **Concurrency limit** | Too many in-flight requests | 10 simultaneous uploads per user |

## 2. Where does it live?

| Location | Pros | Cons |
|---|---|---|
| **Client-side** | Courtesy only | Cannot be trusted: attackers ignore it |
| **API gateway / edge / CDN / WAF** (AWS API Gateway throttling, Cloudflare, nginx `limit_req`) | Stops abuse **before** it reaches your servers; no code | Less flexible rules (business logic, per-user plans); vendor-specific |
| **Middleware in your app** | Full flexibility (per user, per plan, per route) | Each request already consumed app resources; needs shared state across instances |
| **Dedicated limiter service** (called by gateways/apps) | One implementation for many services; central rules | An extra network hop and a critical dependency |

Common practice is **layers**: coarse IP limits at the edge (protect against floods), plus precise per-user and per-endpoint limits in the application or gateway using a shared store like Redis.

## 3. The algorithms

### Fixed window counter

Count requests per key in the current fixed time window (for example each calendar minute); reject when the count exceeds the limit.

```text
key = userId + ":" + floor(now / 60s)
count = INCR key ; set expiry 60s on first increment
if count > 100 → reject
```

- **Pro:** trivial, very cheap (one counter per key per window).
- **Con: boundary burst.** A client can send 100 requests at 0:59 and another 100 at 1:00: **200 requests in two seconds**, double the intended rate.

### Sliding window log

Store a timestamp for each request; on each request drop timestamps older than the window and count what remains.

- **Pro:** exact.
- **Con:** memory heavy (one entry per request per key); more work per request. Fine for small limits.

### Sliding window counter (the practical compromise)

Keep counters for the **current** and **previous** fixed windows and weight the previous one by how much of it still overlaps the sliding window:

```text
estimated = prevCount × (1 − elapsedFractionOfCurrentWindow) + currentCount
reject if estimated ≥ limit
```

- **Pro:** two numbers per key, smooths the boundary burst, very accurate in practice (an approximation that assumes requests in the previous window were evenly spread).
- **Con:** still an approximation.

### Token bucket (the most common)

A bucket holds up to **capacity** tokens and refills at a **steady rate**. Each request consumes a token; with none left, the request is rejected.

```text
capacity = 100 tokens, refill = 100 tokens / minute  (≈ 1.67 per second)
Idle for a while → bucket fills up → a client can burst up to 100 at once, then is limited to the refill rate.
```

- **Pro:** allows **bursts** (good for real clients) while enforcing the **average rate**; only two values per key (tokens and last refill time); used by Stripe and AWS API Gateway.
- **Con:** two parameters to tune; burst size must be chosen deliberately.

### Leaky bucket

Requests enter a queue (the bucket) that drains at a **constant rate**; if the queue is full, new requests are dropped.

- **Pro:** produces a **smooth, constant outflow**, protecting a fragile downstream (nginx `limit_req` behaves like this).
- **Con:** a burst fills the queue and adds latency to queued requests; old requests can starve newer ones if the queue is long.

### Comparison

| Algorithm | Memory per key | Burst handling | Accuracy | Best for |
|---|---|---|---|---|
| Fixed window | 1 counter | Allows 2x at boundary | Low | Simple, coarse limits |
| Sliding window log | Many timestamps | Exact | Exact | Low limits needing precision |
| Sliding window counter | 2 counters | Smooth | High (approx.) | General per-minute limits |
| **Token bucket** | 2 values | **Controlled bursts** | High | APIs with burst tolerance |
| Leaky bucket | Queue | None (smoothed) | High | Protecting a constant-rate downstream |

## 4. A token bucket you can run

First the logic in plain JavaScript (single process), so you can reason about it and test it:

```js
function makeTokenBucket({ capacity, refillPerSec }) {
  const buckets = new Map(); // key -> { tokens, last }

  return function allow(key, now = Date.now(), cost = 1) {
    const b = buckets.get(key) ?? { tokens: capacity, last: now };
    const elapsed = (now - b.last) / 1000;
    b.tokens = Math.min(capacity, b.tokens + elapsed * refillPerSec); // refill lazily on access
    b.last = now;
    const allowed = b.tokens >= cost;
    if (allowed) b.tokens -= cost;
    buckets.set(key, b);
    return { allowed, remaining: Math.floor(b.tokens), retryAfterSec: allowed ? 0 : Math.ceil((cost - b.tokens) / refillPerSec) };
  };
}

const allow = makeTokenBucket({ capacity: 5, refillPerSec: 1 });
let t = 0;
const results = [];
for (let i = 0; i < 7; i++) results.push(allow("u1", t).allowed);   // 7 requests at the same instant
console.log(results.join(","));                                      // true,true,true,true,true,false,false
console.log(allow("u1", t + 2000).allowed);                          // true  (2 tokens refilled after 2 s)
console.log(allow("u1", t + 2000).remaining);                        // 0     (this call used the second refilled token)
```

Notice **lazy refill**: no timer per key; tokens are computed from elapsed time when a request arrives. That is what makes millions of keys cheap.

## 5. Making it correct across many servers

Ten API instances need one shared view, so counters live in a **central, fast store: Redis**. The danger is a **race**: two instances read the same count, both allow, both write, and the limit is exceeded. The check and update must be **atomic**.

### Fixed window with Redis (simple, atomic enough)

```ts
const key = `rl:${userId}:${Math.floor(Date.now() / 60_000)}`;
const count = await redis.incr(key);              // atomic
if (count === 1) await redis.expire(key, 60);     // ⚠ a crash between INCR and EXPIRE leaves a key that never expires
if (count > 100) return reject();
```

The `INCR` + `EXPIRE` pair is not atomic. Prefer a single atomic operation: `SET key 0 EX 60 NX` then `INCR`, or a Lua script.

### Token bucket with a Lua script (atomic)

Redis runs a Lua script **atomically**: nothing else executes in between, so read-modify-write is race-free.

```lua
-- KEYS[1] = bucket key; ARGV = capacity, refillPerSec, nowMs, cost
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local cost     = tonumber(ARGV[4])

local data   = redis.call("HMGET", KEYS[1], "tokens", "ts")
local tokens = tonumber(data[1])
local ts     = tonumber(data[2])
if tokens == nil then tokens = capacity; ts = now end

local elapsed = math.max(0, now - ts) / 1000
tokens = math.min(capacity, tokens + elapsed * rate)

local allowed = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1 end

redis.call("HSET", KEYS[1], "tokens", tokens, "ts", now)
redis.call("PEXPIRE", KEYS[1], math.ceil(capacity / rate * 1000) * 2)   -- idle buckets disappear
return { allowed, math.floor(tokens) }
```

```ts
// Express middleware (ioredis)
const sha = await redis.script("LOAD", luaSource);

export const rateLimit = (capacity: number, perSec: number) => async (req, res, next) => {
  const key = `rl:${req.user?.id ?? req.ip}:${req.route?.path ?? "global"}`;
  try {
    const [allowed, remaining] = (await redis.evalsha(sha, 1, key, capacity, perSec, Date.now(), 1)) as [number, number];
    res.set({ "RateLimit-Limit": String(capacity), "RateLimit-Remaining": String(remaining) });
    if (!allowed) {
      res.set("Retry-After", String(Math.ceil(1 / perSec)));
      return res.status(429).json({ type: "https://api.example.com/errors/rate-limited", title: "Too many requests", status: 429 });
    }
    next();
  } catch {
    next(); // fail open: see "When the limiter itself fails"
  }
};
```

(Use the **time from Redis** (`redis.call("TIME")`) instead of each server's clock if clock skew between app servers is a concern.)

### Other multi-server options

- **Local limiters per instance** with a divided limit (limit ÷ instances): no network call, but inaccurate when load is uneven or instances scale.
- **Approximate / eventually consistent sync:** each instance counts locally and periodically syncs to Redis; very low latency, small overshoot allowed. Good at huge scale where exactness is not required.
- **Sticky routing by key** (hash user ID to an instance) so one instance owns each key's counter; fragile when instances change.
- **Redis Cluster:** keys are sharded by hash slot, and the Lua script must touch keys in one slot (use hash tags like `{user42}` if multiple keys are involved). Add replicas for availability; accept that failover can lose a few recent counts.

## 6. Keys, rules and configuration

- **Choose the key** to match the threat: **API key or user ID** for authenticated traffic (fair and precise); **IP** for anonymous traffic and credential stuffing, with care (below); **IP + route** for login and OTP endpoints; **global** keys to protect a fragile dependency (an SMS provider).
- **Rules as data:** store them in config or a database (`plan-free: 100/min, burst 100`; `login-per-ip: 10/min`), cache locally, hot-reload. Multiple rules per request are checked together; reject if any fails.
- **Cost-based limits:** an expensive endpoint consumes more tokens (`cost = 10`).
- **Tiered limits:** free vs paid plans; internal services exempt or with higher limits.

## 7. What the client sees

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 18
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 18
Content-Type: application/problem+json

{ "type": "https://api.example.com/errors/rate-limited", "title": "Too many requests", "status": 429 }
```

- **Status `429`** (not `403`), with **`Retry-After`** (seconds or an HTTP date), defined in the HTTP specification.
- **`RateLimit-*` headers** let clients adapt before they hit the wall. Today most APIs use the older `X-RateLimit-Limit/Remaining/Reset` convention; an IETF **draft** standardises `RateLimit-Policy` and `RateLimit` fields, but it is still a draft, so say "emerging" in an interview.
- Include a machine-readable error body and a request ID.

**Client behaviour:** honour `Retry-After`; use **exponential backoff with jitter** for retries; do not retry non-idempotent requests blindly; surface a friendly message ("Try again in 18 seconds"); spread background work; dedupe duplicate requests ([Debugging, Lesson 05](/debugging/lesson-5)).

## 8. When the limiter itself fails

If Redis is down or slow, what should happen?

| Choice | Behaviour | Use when |
|---|---|---|
| **Fail open** | Allow the request (no limit while the limiter is down) | Most APIs: availability matters more than strict limits, and you have other protections |
| **Fail closed** | Reject the request | **Security-sensitive** endpoints: login, OTP, password reset, where unlimited attempts enable brute force |

Make this **per rule**, set a **tight timeout** on the limiter call (a few ms), alert loudly, and consider a **local in-memory fallback limiter** with conservative limits so you degrade rather than drop protection completely.

## 9. Scenario: legitimate users sharing one IP get blocked

Hundreds of employees behind a company NAT, or a mobile carrier's CGNAT, share a single public IP. A per-IP limit throttles them as if they were one abuser.

Fixes:

1. **Do not use IP as the only key for authenticated traffic.** Limit per **user ID or API key**; keep IP limits only as a generous outer layer.
2. **Authenticate first**, then apply user-level rules, and give logged-in users higher IP-level allowances.
3. **Higher limits or allow-listing** for known corporate ranges and partners.
4. **Combine signals** (IP + device or cookie fingerprint + account) for anonymous abuse detection, and use **challenges** (CAPTCHA, proof-of-work) rather than hard blocks for suspicious traffic.
5. **Get the client IP right:** behind proxies and load balancers, read it from `X-Forwarded-For` **only from trusted proxies**; otherwise attackers spoof the header and evade or frame others.
6. Monitor the 429 rate per key type so you notice collateral damage.

## 10. Scaling and observability

- **Throughput:** 100,000 requests per second means 100,000 limiter checks per second. A Redis node handles on the order of 100,000+ simple operations per second; use a **cluster** and keep the check to **one round trip** (one Lua call), or reduce load with local pre-filters.
- **Latency budget:** same availability zone, pipelined connections, short timeouts.
- **Memory:** two fields per key with TTLs, so only active keys occupy memory; 10 million active keys × ~100 bytes ≈ 1 GB.
- **Hot keys:** a single abusive key concentrates traffic on one shard; edge-level blocks stop it earlier.
- **Metrics:** allowed vs rejected by rule, limiter latency and errors, top limited keys; alert on spikes. Return the limiter decision in logs with the request ID.
- **Testing:** unit-test algorithms with a controllable clock; load-test the Redis path; chaos-test limiter failure behaviour.

## Common mistakes

1. **Client-side-only limiting.**
2. **Fixed windows without acknowledging boundary bursts.**
3. **Non-atomic read-modify-write** across servers (a race that overshoots the limit).
4. **`INCR` without a reliable `EXPIRE`**, leaking keys.
5. **Limiting only by IP**, punishing shared networks.
6. **Trusting `X-Forwarded-For` from the open internet.**
7. **No decision about fail-open vs fail-closed.**
8. **No `Retry-After`**, so clients retry immediately and make things worse.
9. **Using `403` instead of `429`.**

## Interview questions

### Q1. Token bucket vs sliding window: what are the trade-offs?

A token bucket stores two values per key, permits controlled bursts up to its capacity while enforcing an average refill rate, and is cheap and intuitive for APIs. A sliding window enforces "no more than N in any window" more strictly (exactly with a log, approximately with the two-counter version) and avoids boundary bursts, but does not model burst allowance as naturally. I pick token bucket when bursts are acceptable, and a sliding window when the limit must hold over any interval.

### Q2. How do you rate-limit across 10 server instances?

Keep counters in a shared low-latency store such as Redis and perform the check-and-update atomically (a Lua script or atomic commands) so concurrent instances cannot overshoot. For extreme scale, accept approximate limits with local counters synced periodically. Use Redis time or tolerate small clock skew.

### Q3. Which headers do you return to clients?

`429 Too Many Requests` with `Retry-After`, and rate-limit information headers (`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, or the common `X-RateLimit-*` equivalents). The IETF RateLimit header fields are still a draft, so they are emerging rather than finalised.

### Q4. Scenario: legitimate users who share one IP address behind a NAT get blocked. Fix it.

Stop using IP as the primary key for authenticated users and limit per user or API key instead, keep a generous IP-level outer limit, allow-list known corporate ranges, combine signals and use challenges for anonymous traffic, and parse the real client IP only from trusted proxy headers. Monitor collateral blocking.

### Q5. How should the frontend respond to a 429?

Respect `Retry-After`, back off exponentially with jitter, stop automatic retries of non-idempotent requests, show a clear message with when to try again, pause polling, dedupe repeated calls and avoid synchronized retries across tabs or users.

### Q6. Fail open or fail closed when Redis is down?

It depends on the endpoint: most APIs fail open so a limiter outage does not become a total outage, perhaps with a conservative local fallback, while security-critical endpoints like login or OTP fail closed to prevent unlimited brute-force attempts. The choice is configured per rule and monitored.

### Q7. What is the boundary problem in fixed-window counters?

A client can use the full limit at the end of one window and again at the start of the next, sending up to twice the limit within a short interval around the boundary. Sliding windows or token buckets avoid this.

### Q8. Where would you place the limiter in the architecture?

In layers: coarse IP/flood protection at the edge or API gateway before traffic reaches the app, and precise per-user or per-endpoint limits in a gateway or middleware using Redis for shared state. For many services, a central limiter service or sidecar keeps rules consistent.

## Key takeaways

- A limiter is **key + rule + algorithm + shared state + response**.
- **Token bucket** (bursts + average rate) is the common default; **sliding window counter** avoids boundary bursts; fixed window is simple but bursty; leaky bucket smooths output.
- Make the check **atomic in Redis** (Lua), refill **lazily**, and expire idle keys.
- Return **429 with `Retry-After`** and rate-limit headers; clients should back off with jitter.
- Decide **fail open vs fail closed** per endpoint; do not rely on IP alone and do not trust spoofable headers.
