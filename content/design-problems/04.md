> **In one line:** don't stream gigabytes through your API server. Let the client upload **directly to object storage** with a short-lived **presigned URL**, then process the file **asynchronously** after it lands. Your API handles *metadata and permissions*; the storage service handles *bytes*.

File upload looks like a form field; at scale it is a pipeline with security, reliability and cost concerns. The AWS S3 side is covered in the DevOps series; here is the design.

## 1. Requirements

**Functional**

- Users upload files (images, documents, videos) from a web app.
- Show **progress**, allow **cancel**, and **resume** after a failure for large files.
- Files become available (downloadable, thumbnails, previews) after processing.

**Non-functional**

- Handle **large files** (hundreds of MB to several GB) and **many concurrent uploads** without exhausting API servers.
- **Security:** validate type and size, block malware, prevent files from attacking other users.
- **Reliability:** flaky mobile networks, retries, no half-uploaded junk forever.
- **Cost:** minimise bandwidth and compute on your own servers.

## 2. Option A: upload through your API (multipart/form-data)

```text
Browser ──(entire file)──▶ API server ──(entire file)──▶ Object storage
```

```ts
// Express + multer: simple, and fine for small files
app.post("/upload", upload.single("file"), async (req, res) => { /* save req.file to S3 */ });
```

**Pros:** simple; you can inspect the bytes in flight; one endpoint.

**Cons (why it breaks at scale):**

- Every byte is **received and re-sent by your server**: bandwidth, CPU and memory cost doubled and tied to your instances.
- A few large uploads can **tie up connections and workers** for minutes, starving normal traffic ([Backend, Lesson 10](/backend/lesson-10)).
- **Timeouts and limits** at every hop: load balancer idle or request timeouts, reverse proxy `client_max_body_size`, API Gateway payload limits (about 10 MB), serverless function limits (about 6 MB for synchronous Lambda invocations), Node memory if you buffer.
- A failure at 95% means starting over.

Acceptable for small files (avatars, a few MB) when you want the simplest thing; do not use it for large files.

## 3. Option B: presigned URL, direct-to-storage (the standard answer)

```text
1. Browser ─ "I want to upload report.pdf, 48 MB, application/pdf" ──▶ API
2. API: authenticate, authorise, validate declared name/type/size, create a DB row (status "pending"),
        generate a presigned URL for a unique key ──▶ Browser
3. Browser ──────────────── PUT bytes directly ───────────────▶ Object storage (S3)
4. Storage ── "ObjectCreated" event ──▶ queue/Lambda/worker: verify, scan, process ──▶ DB row "ready"
5. Browser polls (or is notified): file is ready
```

A **presigned URL** is a URL that contains a time-limited signature made with your credentials, letting its holder perform one specific operation (for example `PUT` of one object key) without having AWS credentials.

```ts
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";
import { randomUUID } from "node:crypto";

const s3 = new S3Client({ region: "ap-south-1" });
const ALLOWED = new Map([["image/jpeg", "jpg"], ["image/png", "png"], ["application/pdf", "pdf"]]);
const MAX_BYTES = 100 * 1024 * 1024;

app.post("/v1/uploads", requireAuth, async (req, res) => {
  const { filename, contentType, size } = uploadRequestSchema.parse(req.body);       // validate (Backend, Lesson 03)
  if (!ALLOWED.has(contentType)) throw new ValidationError("File type not allowed");
  if (size > MAX_BYTES) throw new ValidationError("File too large");

  const key = `uploads/${req.user.id}/${randomUUID()}.${ALLOWED.get(contentType)}`;   // never trust the client's filename as the key
  const file = await prisma.file.create({
    data: { id: randomUUID(), userId: req.user.id, key, originalName: filename, contentType, size, status: "PENDING" },
  });

  const url = await getSignedUrl(
    s3,
    new PutObjectCommand({ Bucket: process.env.BUCKET!, Key: key, ContentType: contentType, ContentLength: size }),
    { expiresIn: 300 },                                                               // valid for 5 minutes
  );
  res.status(201).json({ fileId: file.id, uploadUrl: url, method: "PUT", headers: { "Content-Type": contentType } });
});
```

Key points:

- The signature is bound to the **key, method and (when included) content type and length**, so the client cannot upload a different type or write elsewhere.
- **Short expiry** (minutes), and a unique, **server-generated key**, never the user's file name (path traversal, collisions, leaking names).
- For stricter limits, use a **presigned POST** with a **policy** such as `content-length-range` (min and max size), `Content-Type` prefix and key prefix, which S3 enforces during the upload.
- The bucket is **private**; the browser needs **CORS** configured on the bucket for the app's origin (`PUT`, the headers you send) ([Browser Contract, Lesson 04](/browser/lesson-4)).
- **Integrity:** supply a checksum (for example `x-amz-checksum-sha256`) so storage rejects corrupted uploads.

### Client with progress and cancel

`fetch` still has no upload-progress event in all browsers, so `XMLHttpRequest` is the dependable way to show progress:

```ts
function uploadWithProgress(url: string, file: File, onProgress: (pct: number) => void, signal?: AbortSignal) {
  return new Promise<void>((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    xhr.open("PUT", url);
    xhr.setRequestHeader("Content-Type", file.type);
    xhr.upload.onprogress = (e) => e.lengthComputable && onProgress(Math.round((e.loaded / e.total) * 100));
    xhr.onload = () => (xhr.status >= 200 && xhr.status < 300 ? resolve() : reject(new Error(`Upload failed: ${xhr.status}`)));
    xhr.onerror = () => reject(new Error("Network error"));
    signal?.addEventListener("abort", () => { xhr.abort(); reject(new DOMException("Aborted", "AbortError")); });
    xhr.send(file);                                   // streams the File without loading it all into memory
  });
}
```

After the PUT succeeds, call `POST /v1/uploads/{id}/complete` (or rely on the storage event) so the server can verify and mark the file.

## 4. Large files: multipart and resumable uploads

A single `PUT` of 2 GB over a mobile network will fail eventually. Split the file into **parts** (chunks).

**S3 multipart upload:**

1. **Initiate** (`CreateMultipartUpload`) → an `UploadId`.
2. **Upload parts** (`UploadPart`), each between **5 MB and 5 GB** (except the last), numbered 1 to **10,000**, so objects up to **5 TB**. Each part can be **uploaded in parallel**, and **retried individually** if it fails.
3. **Complete** (`CompleteMultipartUpload`) with the list of part numbers and ETags; S3 assembles the object.
4. **Abort** if abandoned. Also add a **lifecycle rule** to abort incomplete multipart uploads after some days; incomplete parts are billed storage and otherwise linger invisibly.

With presigned URLs, the API signs **each part** (the client asks "give me URLs for parts 1 to N") and later calls complete:

```text
client ─▶ API: start upload (size 2 GB)  → uploadId, partSize 16 MB, N = 128 parts
client ─▶ API: presign parts 1..N        → N URLs
client ─▶ S3: PUT part k (parallel, 3–5 at a time), retry on failure, collect ETag
client ─▶ API: complete (uploadId, [{part, etag}…]) → API calls CompleteMultipartUpload
```

**Resuming** after a refresh or crash: persist `uploadId` and finished part numbers (locally, and/or ask S3 `ListParts`), and upload only the missing parts. Slicing is cheap in the browser: `file.slice(start, end)`.

```ts
async function uploadParts(file: File, partSize: number, urls: string[], concurrency = 4) {
  const etags: { PartNumber: number; ETag: string }[] = [];
  let next = 0;
  async function worker() {
    while (next < urls.length) {
      const i = next++;
      const chunk = file.slice(i * partSize, (i + 1) * partSize);
      for (let attempt = 1; ; attempt++) {
        try {
          const res = await fetch(urls[i], { method: "PUT", body: chunk });
          if (!res.ok) throw new Error(String(res.status));
          etags.push({ PartNumber: i + 1, ETag: res.headers.get("ETag")! });
          break;
        } catch (e) {
          if (attempt === 4) throw e;
          await new Promise((r) => setTimeout(r, 2 ** attempt * 500 + Math.random() * 250)); // backoff + jitter
        }
      }
    }
  }
  await Promise.all(Array.from({ length: concurrency }, worker));
  return etags.sort((a, b) => a.PartNumber - b.PartNumber);
}
```

(The bucket's CORS configuration must **expose the `ETag` header** to the browser.) An open standard for resumable uploads is the **tus protocol**; libraries such as **Uppy** implement S3 multipart and tus with progress, retries and a UI.

## 5. After the bytes land: asynchronous processing

Never make the user wait for heavy work inside a request. Use storage events:

```text
S3 ObjectCreated ──▶ SQS queue ──▶ worker(s):
    1. Fetch metadata; verify size and detected content type (magic bytes), not just the extension
    2. Scan for malware (ClamAV or a managed scanning service)
    3. Generate derivatives: thumbnails, transcodes, text extraction
    4. Move/copy to the final location; set status READY (or REJECTED with a reason)
    5. Notify the client (webhook, SSE, push) or let it poll GET /v1/files/{id}
```

States: `PENDING` (URL issued) → `UPLOADED` (object present) → `SCANNING` → `READY` | `REJECTED`. A **cleanup job** deletes `PENDING` rows and objects that never completed. Make workers **idempotent**, since queues deliver at least once ([Lesson 07](/design-problems/lesson-7)). Use a **dead-letter queue** for poison files.

## 6. Validating files safely

Client-side checks are a UX nicety; **the server side is the authority**.

| Check | How |
|---|---|
| **Size** | Enforce in the presigned policy (`content-length-range`) and re-check after upload |
| **Type** | Allow-list **MIME types and extensions** and verify the **magic bytes** (file signature) of the actual content; the declared `Content-Type` and extension are attacker-controlled |
| **Name** | Never use the client's name for the storage key or filesystem path (path traversal like `../../etc/passwd`, Unicode tricks, collisions); keep it only as display metadata, sanitised |
| **Content** | Malware scan; for images, **re-encode** them (this strips embedded payloads and EXIF metadata including GPS location); limit image dimensions (decompression bombs) |
| **Archives and documents** | Limit expansion size and nesting (zip bombs); consider disabling macros or converting to PDF |
| **Quotas** | Per-user storage and rate limits ([Lesson 02](/design-problems/lesson-2)) |

### Serving user uploads safely

User-supplied files are an XSS vector: an uploaded **SVG or HTML file** served from your main domain can run script with your origin's privileges.

- Serve uploads from a **separate domain** (for example `usercontent.example.net`) or a CDN origin with no cookies and no shared origin, so script in a file cannot touch your session ([Browser Contract, Lesson 07](/browser/lesson-7)).
- Send **`X-Content-Type-Options: nosniff`**, a correct `Content-Type`, and for downloads **`Content-Disposition: attachment`**.
- Prefer **private buckets with short-lived signed GET URLs** (or CloudFront signed URLs/cookies) for access-controlled files; public CDN URLs only for genuinely public assets.
- Apply a **Content-Security-Policy** (`sandbox`) to risky types.

## 7. Scenario: uploads time out behind the load balancer

**Diagnosis.** The upload goes *through* the API. A slow client uploading 500 MB takes minutes; the **load balancer's idle timeout** (60 seconds by default on many setups) or the request timeout at nginx, API Gateway or the function platform cuts the connection, or the app server runs out of memory or connections.

**Fixes (best first):**

1. **Move to presigned direct-to-storage uploads** so the bytes never touch the load balancer or your app.
2. Use **multipart/chunked** uploads so each request is small and retryable.
3. As a stopgap: raise timeouts and body-size limits at each hop (proxy, LB, app), stream the request to storage instead of buffering, and keep connections alive.
4. Move long processing to async workers.

## 8. Scale and cost

- **Bandwidth and compute** for ingestion shift to the storage provider, which scales horizontally by itself.
- **Transfer acceleration/edge endpoints** (S3 Transfer Acceleration or regional upload endpoints) speed up distant users.
- **Lifecycle policies:** transition cold files to cheaper tiers, delete temp/`PENDING` objects and abort stale multipart uploads.
- **Deduplication:** compute a content hash (client-side SHA-256 or from the storage checksum) to avoid storing identical files twice, if appropriate (privacy implications).
- **Observability:** upload success rate, abandoned upload rate, processing latency, rejection reasons, storage growth.

## Common mistakes

1. **Streaming all uploads through the API server.**
2. **Trusting the client's `Content-Type`, extension or file name.**
3. **Long-lived or over-broad presigned URLs** (minutes, one key, one method is the goal).
4. **Public buckets** and serving user files from the main application origin.
5. **No cleanup** of pending uploads and incomplete multipart uploads.
6. **No malware scan or image re-encode** on user content.
7. **No integrity check or retry** for chunks; no resume path.
8. **Doing heavy processing synchronously** in the request that confirms the upload.

## Interview questions

### Q1. Why use presigned URLs?

They let the client upload directly to object storage, so large files do not consume your API servers' bandwidth, memory or connections, avoid load-balancer and gateway limits, and scale automatically. The URL is time-limited and scoped to one key and operation, so the client needs no credentials while the API still controls who can upload what.

### Q2. How do you resume a failed 2 GB upload?

Use multipart (or a resumable protocol like tus): split the file into parts, upload them in parallel with per-part retries and backoff, record completed part numbers and ETags (and the upload ID) locally or retrieve them with `ListParts`, and on resume upload only the missing parts before completing the upload. Add a lifecycle rule to abort stale multipart uploads.

### Q3. How do you validate file type safely?

Treat the declared MIME type, extension and name as untrusted. Enforce an allow-list, inspect the file's magic bytes (and parse it, for example re-encode images), scan for malware, limit size and dimensions, and serve files with correct headers from a separate origin. Do it asynchronously after upload, marking files `REJECTED` if checks fail.

### Q4. Scenario: uploads time out behind the load balancer. Fix it.

The bytes are going through a hop with an idle or request timeout. Switch to direct-to-storage presigned (multipart for large files) uploads so the load balancer is out of the data path; as a stopgap raise timeouts and stream rather than buffer. Process the file asynchronously after the upload completes.

### Q5. What can go wrong if user-uploaded files are served from your main domain?

An uploaded SVG or HTML file executes script in your origin, enabling XSS and session theft. Serve uploads from a separate cookie-less domain with `nosniff`, correct content types and `Content-Disposition: attachment` where appropriate, and keep private files behind signed URLs.

### Q6. Presigned PUT vs presigned POST?

A presigned PUT is simple and signs one specific object request (key, content type, optionally length). A presigned POST uses a policy document with conditions such as a size range, content-type prefix and key prefix that the storage service enforces, so it is better when you need server-enforced size limits or form-based uploads.

### Q7. How do you track upload state?

Create a database record when issuing the URL (`PENDING`), update it on the storage event or completion call (`UPLOADED`), then through scanning and processing to `READY` or `REJECTED`. A scheduled cleanup removes abandoned `PENDING` records and objects, and the client polls or receives a notification.

### Q8. Why generate the storage key on the server?

User-controlled names can cause path traversal, collisions, overwriting other users' files, leaking personal information and unsafe characters. A server-generated key (user prefix plus UUID) is unique and predictable only to you, and the original name is stored as sanitised metadata for display.

## Key takeaways

- **Control plane vs data plane:** your API issues permissions (presigned URL) and tracks state; **object storage handles the bytes.**
- **Multipart + parallel parts + per-part retry** gives large-file reliability and resume; abort stale uploads with lifecycle rules.
- **Validate on the server**: allow-list types, check magic bytes, enforce size, scan, re-encode images, generate your own keys.
- **Process asynchronously** from storage events with idempotent workers, and expose a clear state machine.
- **Serve safely**: separate domain, `nosniff`, `attachment`, signed URLs for private files.
- Behind-the-load-balancer timeouts are a symptom of proxying bytes: **take your servers out of the data path**.
