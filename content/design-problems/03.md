> **In one line:** **offset pagination** (`LIMIT 20 OFFSET 4000`) is simple but gets slower the deeper you go and skips or repeats rows when data changes. **Cursor (keyset) pagination** remembers *where you were* (the last row's sort key) and asks for "the next rows after that", staying fast and stable. Use offset for small, jumpable tables; cursor for feeds and large data.

Pagination appears in every list endpoint, so a precise answer ("here is the SQL, here is the index, here is why rows duplicate") is a strong signal.

## Offset pagination

```http
GET /orders?page=3&limit=20
```

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 40;
```

**Pros**

- Trivial to implement and understand.
- Supports **jumping to any page** and showing "page 3 of 57" (with a `COUNT(*)`).
- Works with any sort order without extra design.

**Cons**

1. **It gets slower with depth.** `OFFSET 100000` makes the database find and **read and discard 100,000 rows** before returning 20. Even with an index it must walk 100,000 index entries. Latency grows linearly with the page number.
2. **Inconsistent results when data changes.** Between page requests, rows are inserted or deleted, so everything shifts: the user sees **duplicates** (a new row pushes the previous last row onto the next page) or **skips rows** (a deleted row pulls an unseen row onto the previous page).
3. `COUNT(*)` for the total is itself expensive on big tables.

## Why feeds repeat or skip items

**Scenario:** items repeat or get skipped while paging through a live feed.

```text
Newest first, 3 per page. Items are numbered by recency.

Page 1 (offset 0): [E, D, C]            User is now looking at E, D, C
                                         — someone posts a new item F —
Order is now: F, E, D, C, B, A
Page 2 (offset 3): [C, B, A]            C appears AGAIN (duplicate); nothing was skipped here,
                                         but the user saw C twice because everything shifted by one.

If an item is DELETED between pages instead, one unseen item slides into the earlier page and is skipped.
```

The root cause: offset is a **position**, and positions change when the data changes. A **cursor** points at a **specific row**, which does not move.

## Cursor (keyset) pagination

Instead of "skip N rows", say "give me rows **after this one**", using the sort key.

```http
GET /orders?limit=20
→ { "data": [...20 items...], "page": { "nextCursor": "eyJjIjoiMjAyNi0wNS0wMVQwOTozMDowMFoiLCJpIjoxNDJ9" } }

GET /orders?limit=20&cursor=eyJjIjoi...
```

```sql
-- first page
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 21;

-- next page: rows strictly "after" the last seen (created_at, id) in this ordering
SELECT * FROM orders
WHERE (created_at, id) < ($1, $2)          -- $1, $2 = the cursor values from the last row
ORDER BY created_at DESC, id DESC
LIMIT 21;
```

Key properties:

- **Fast at any depth**: with an index on `(created_at DESC, id DESC)` the database seeks **directly** to the cursor position and reads 21 rows. Cost does not grow with how far the user has paged.
- **Stable**: new or deleted rows elsewhere do not shift your position, so no duplicates or skips relative to the rows you have already seen.
- **Trade-offs:** you **cannot jump to page N**, there is no cheap total count, and it needs a **deterministic sort** with a unique tiebreaker.

### A stable sort needs a unique tiebreaker

If you sort by `created_at` alone and two rows share the same timestamp, the database may return them in any order, and the cursor cannot tell which was last seen. **Always add a unique column** (usually the primary key) as the final sort key:

```sql
ORDER BY created_at DESC, id DESC
```

Without it, rows at the boundary can be skipped or repeated even with keyset pagination.

### The row-value comparison

`(created_at, id) < ($1, $2)` is a **row-value comparison**: it means "created_at is less than $1, **or** created_at equals $1 and id is less than $2". It is supported by PostgreSQL, MySQL and SQLite and can use a composite index. If your database lacks it, write the expanded form:

```sql
WHERE created_at < $1 OR (created_at = $1 AND id < $2)
```

(The expanded `OR` form may be harder for some planners to use efficiently; test with `EXPLAIN`.)

### Fetch `limit + 1` to know if there is a next page

Ask for 21 rows when the page size is 20. If you get 21, there **is** another page: return 20 and set `nextCursor` from the 20th. This avoids an extra `COUNT` query.

## Cursor encoding

Make the cursor **opaque**: clients must treat it as a black box so you can change its contents later.

```ts
type Cursor = { c: string; i: number };            // created_at (ISO) and id

export const encodeCursor = (c: Cursor) => Buffer.from(JSON.stringify(c)).toString("base64url");

export function decodeCursor(raw: string): Cursor {
  try {
    const v = JSON.parse(Buffer.from(raw, "base64url").toString("utf8"));
    if (typeof v.c !== "string" || !Number.isInteger(v.i) || Number.isNaN(Date.parse(v.c))) throw new Error();
    return v;
  } catch {
    throw new ValidationError("Invalid cursor");   // 400/422 — never trust a client-supplied cursor
  }
}
```

- **Validate** it strictly: a malicious cursor must not become a SQL injection or error (parameterise the query).
- Optionally **sign** it (HMAC) so clients cannot forge arbitrary positions, if that matters (for example, to prevent probing hidden ranges).
- Include the **sort and filter fingerprint** in the cursor (or reject cursors used with different filters), because a cursor from one sort order is meaningless in another.

## Doing it with Prisma

```ts
// Simple case: ordering by a unique, sequential column
const rows = await prisma.order.findMany({
  take: limit + 1,
  ...(cursor && { cursor: { id: cursor }, skip: 1 }),      // skip the cursor row itself
  orderBy: { id: "desc" },
});

// Non-unique sort key: use the composite condition explicitly
const rows = await prisma.order.findMany({
  where: cursor && {
    OR: [
      { createdAt: { lt: cursor.createdAt } },
      { createdAt: cursor.createdAt, id: { lt: cursor.id } },
    ],
  },
  orderBy: [{ createdAt: "desc" }, { id: "desc" }],
  take: limit + 1,
});

const hasMore = rows.length > limit;
const page = hasMore ? rows.slice(0, limit) : rows;
const nextCursor = hasMore ? encodeCursor({ c: page.at(-1)!.createdAt.toISOString(), i: page.at(-1)!.id }) : null;
```

Prisma's `cursor` option uses a unique field and the query's `orderBy`; for sorting by a non-unique column, the explicit composite `where` above is the reliable pattern. Make sure the matching **composite index** exists:

```sql
CREATE INDEX orders_created_id_desc ON orders (created_at DESC, id DESC);
```

## Paging backwards and "previous"

Support `before` the same way by reversing the comparison and the sort, then reversing the result:

```sql
SELECT * FROM (
  SELECT * FROM orders WHERE (created_at, id) > ($1, $2) ORDER BY created_at ASC, id ASC LIMIT 21
) t ORDER BY created_at DESC, id DESC;
```

Return `prevCursor` (from the first row) and `nextCursor` (from the last).

## Filters and different sort orders

Every distinct `ORDER BY` needs an index that matches it: `(status, created_at DESC, id DESC)` for "orders of a given status, newest first". Letting users sort by arbitrary columns means indexes for each, or a limit on the allowed sorts. When filters change, the cursor is no longer valid: **start from the first page.**

For sorting by a computed or nullable column, define explicit rules (`NULLS LAST`) and include them in the comparison; nullable sort keys are a common source of keyset bugs.

## Relay-style connections (GraphQL)

GraphQL standardised cursor pagination as **connections**:

```graphql
query {
  orders(first: 20, after: "eyJjIjoi...") {
    edges { cursor node { id total status } }
    pageInfo { hasNextPage hasPreviousPage startCursor endCursor }
    totalCount           # optional and expensive; often omitted or approximated
  }
}
```

- `first`/`after` page forwards; `last`/`before` page backwards.
- Each **edge** has its own cursor; `pageInfo.endCursor` is what you pass as `after` next.
- This models exactly the keyset approach and fits client libraries (Apollo, Relay) that merge pages into a cache ([Backend, Lesson 09](/backend/lesson-9)).

## Total counts and page numbers

If the UI needs "page 3 of 57" or a total:

- `COUNT(*)` on large tables is slow (it scans an index). Options: **approximate counts** (PostgreSQL's `reltuples` or `EXPLAIN` estimates), **cached counts** updated periodically, a **counter table**, or showing "10,000+" capped at a limit (`SELECT count(*) FROM (SELECT 1 FROM t WHERE … LIMIT 10001)`).
- Or avoid totals: infinite scroll and "Load more" need only `hasMore`.

## Choosing

| Situation | Choose |
|---|---|
| Small tables (hundreds to a few thousand rows), admin screens needing page jumps and totals | **Offset** |
| Feeds, timelines, activity logs, big tables, APIs for third parties | **Cursor/keyset** |
| Infinite scroll or "Load more" | **Cursor** |
| Need deep random access ("go to page 500") on a huge dataset | Re-think the UX (search, filters, date jump) or accept offset with a cap (for example, max page 100) |
| Search results ranked by relevance (Elasticsearch/OpenSearch) | `search_after` (the same keyset idea over the sort values) |

Many APIs offer **both**, or document a **maximum offset** to protect the database.

## Failure modes and protections

- **Cap `limit`** (for example max 100) and set a **default**.
- **Cap offset depth** if you support it.
- **Validate cursors**; handle a cursor pointing at a row that has since been deleted (keyset still works: the comparison uses values, not the existence of the row).
- **Consistent snapshots** (rarely needed): for exports, use a snapshot timestamp or run a long read in a repeatable-read transaction, or page by a stable ID range.
- **Index regressions:** check the plan with `EXPLAIN` ([Backend, Lesson 07](/backend/lesson-7)); a missing index turns keyset into a full sort.
- **Documentation:** describe the cursor as opaque, the ordering, and what happens when filters change.

## A small experiment (runs anywhere with SQLite)

You can see the difference without a server. This Python script builds 50,000 rows, pages with a keyset while inserting new rows, and verifies no duplicates or skips:

```python
import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE t (id INTEGER PRIMARY KEY, created INTEGER)")
db.executemany("INSERT INTO t (created) VALUES (?)", [(i // 3,) for i in range(1, 50001)])  # many ties on `created`
db.execute("CREATE INDEX t_idx ON t (created DESC, id DESC)")

seen, cursor = [], None
while True:
    if cursor is None:
        rows = db.execute("SELECT id, created FROM t ORDER BY created DESC, id DESC LIMIT 1001").fetchall()
    else:
        rows = db.execute("SELECT id, created FROM t WHERE (created, id) < (?, ?) ORDER BY created DESC, id DESC LIMIT 1001", cursor).fetchall()
    page = rows[:1000]
    seen += [r[0] for r in page]
    if len(rows) <= 1000: break
    cursor = (page[-1][1], page[-1][0])
    db.execute("INSERT INTO t (created) VALUES (999999)")     # new rows appear at the TOP while we page

assert len(seen) == len(set(seen)) == 50000, (len(seen), len(set(seen)))
print("no duplicates, no skips:", len(seen))
```

Even with new rows arriving at the top mid-pagination, the keyset walk visits each original row exactly once. An offset version of the same loop would repeat rows after each insert.

## Common mistakes

1. **Offset pagination on large, changing tables.**
2. **Cursor without a unique tiebreaker**, so ties cause skips or duplicates.
3. **Missing composite index**, so keyset still sorts the whole table.
4. **Trusting client cursors** without validation, or exposing raw IDs in a guessable cursor with no validation.
5. **Unbounded `limit`.**
6. **Computing `COUNT(*)` on every request.**
7. **Reusing a cursor after the sort or filter changed.**
8. **Inconsistent nullable sort columns.**

## Interview questions

### Q1. Offset vs cursor: when do you use each?

Offset when the dataset is small and users need to jump to arbitrary pages or see totals (admin tables). Cursor (keyset) for feeds, large or fast-changing data and public APIs, because it stays fast at any depth and is stable under inserts and deletes, at the cost of no random page access and no cheap total.

### Q2. Scenario: items repeat or get skipped while paging through a live feed. Why?

Offset is a position, and positions shift when rows are inserted or deleted between requests, so items move across page boundaries and appear twice or get missed. A cursor anchors to a specific row's sort key, which does not move, so the next page continues exactly after the last item seen.

### Q3. How do you paginate by a column that isn't unique?

Add a unique tiebreaker (usually the primary key) to the sort, and make the cursor carry both values: `ORDER BY created_at DESC, id DESC` with the condition `(created_at, id) < (cursorCreated, cursorId)`. Back it with a composite index in the same order.

### Q4. How does Relay-style pagination model this?

A connection returns `edges` (each with a `node` and a `cursor`) and `pageInfo` (`hasNextPage`, `endCursor`, etc.). Clients pass `first` and `after` (or `last` and `before`) with an opaque cursor. It is keyset pagination with a standard shape that client caches can merge.

### Q5. Why is a large OFFSET slow?

The database cannot jump to row N; it has to produce and discard the first N rows in the sort order (walking index entries or sorting), so cost grows with the offset. Keyset seeks straight to the position with an index.

### Q6. How do you provide a total count without a slow COUNT?

Avoid it where possible (infinite scroll needs only "has more"), or use a capped count, an approximate count from planner statistics, a periodically refreshed cached count, or a maintained counter table, and be explicit that it is approximate.

### Q7. Why should cursors be opaque?

So the server can change the underlying keys, ordering or encoding without breaking clients, and so clients do not construct or depend on its internals. Validate (and optionally sign) cursors, and reject ones that do not match the current sort and filters.

### Q8. How do you page backwards with a keyset?

Reverse the comparison operator and the sort direction, fetch limit plus one, then reverse the results to restore the display order, and return both `prevCursor` (first row) and `nextCursor` (last row).

## Key takeaways

- **Offset = position**: simple, jumpable, but **O(offset)** and unstable under change.
- **Keyset = anchor**: fast at any depth and stable; needs a **unique tiebreaker**, a **composite index** and an **opaque, validated cursor**.
- Fetch **`limit + 1`** to compute `hasMore`; cap `limit`; avoid expensive totals.
- GraphQL **connections** are keyset pagination with a standard shape; search engines use `search_after`.
- Choose by data size, change rate and UX needs; test the query plan.
