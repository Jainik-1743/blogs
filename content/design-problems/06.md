> **In one line:** autocomplete must feel instant. The frontend job is to **send fewer, smarter requests** (debounce, cache, cancel stale ones) and be **keyboard- and screen-reader-friendly**; the backend job is to answer a prefix query in **milliseconds** from a **precomputed structure** (a trie or a search index) ranked by popularity.

This is a "frontend system design" classic and a great fit for your background: half of the interesting decisions are in the browser.

## 1. Requirements

**Functional**

- As the user types, show a short list (5 to 10) of suggestions matching the **prefix** (or fuzzy match).
- Select with mouse or **keyboard**; pressing Enter submits the search.
- Highlight the matched part; show recent or popular searches when the box is empty and focused.

**Non-functional**

- **Latency:** suggestions should appear within ~100 to 200 ms of the keystroke; total perceived response under 300 ms.
- **Scale:** a million users, each typing several characters per search: tens of thousands of requests per second without smart client behaviour.
- **Relevance:** rank by popularity, recency, personalisation.
- **Accessibility, resilience, correctness** (never show results for a stale query).

## 2. Frontend design

### State and data flow

```text
keystroke ─▶ (min length?) ─▶ debounce 150–300 ms ─▶ cache hit? ─yes─▶ show
                                                         │no
                                                         ▼
                                          abort previous request ─▶ fetch /suggest?q=… ─▶ store in cache ─▶ show
```

### Fewer requests

- **Minimum length:** do not query for 0 or 1 characters (huge result sets, low value). Often start at 2 or 3, or show **recent/popular searches** for empty input from local data.
- **Debounce** (about 150 to 300 ms): wait for a pause in typing so "react" triggers one request, not five. A shorter delay feels snappier but sends more traffic; tune with data.
- **Cache per query:** a `Map` (or LRU) of `prefix → results`. When the user backspaces from "reac" to "rea", the answer is instant. Even better, **reuse a longer prefix's cache**: if "re" returned *all* matches (fewer than the page size) you can filter locally for "rea".
- **HTTP caching:** make `GET /suggest?q=rea` cacheable (`Cache-Control: public, max-age=60`) so the CDN and the browser share popular prefixes ([Browser Contract, Lesson 05](/browser/lesson-5)).
- **Prefetch** likely next characters only if data shows it pays off (usually not).

### Correctness: always show results for the latest input

Responses can arrive out of order ([Debugging, Lesson 05](/debugging/lesson-5)). Abort stale requests and ignore their results:

```tsx
function useSuggestions(query: string) {
  const [state, setState] = useState<{ items: string[]; loading: boolean }>({ items: [], loading: false });
  const cache = useRef(new Map<string, string[]>());

  useEffect(() => {
    const q = query.trim().toLowerCase();
    if (q.length < 2) { setState({ items: [], loading: false }); return; }
    const hit = cache.current.get(q);
    if (hit) { setState({ items: hit, loading: false }); return; }

    const controller = new AbortController();
    setState((s) => ({ ...s, loading: true }));
    const timer = setTimeout(async () => {                       // debounce
      try {
        const res = await fetch(`/api/suggest?q=${encodeURIComponent(q)}`, { signal: controller.signal });
        const items: string[] = await res.json();
        cache.current.set(q, items);
        setState({ items, loading: false });
      } catch (e) {
        if ((e as Error).name !== "AbortError") setState({ items: [], loading: false });
      }
    }, 200);

    return () => { clearTimeout(timer); controller.abort(); };   // a newer keystroke cancels this one
  }, [query]);

  return state;
}
```

### IME composition

Users typing Chinese, Japanese or Korean (and some mobile keyboards) use an **input method** that composes characters in several steps. Firing a search on every intermediate composition state is wrong. Listen for `compositionstart` and `compositionend`, and only query when composition is finished (or treat `onChange` during composition as "not yet").

### Keyboard interaction and accessibility

Autocomplete is a classic **combobox** pattern. Use the ARIA combobox roles so screen readers announce it correctly:

```tsx
<input
  role="combobox"
  aria-expanded={open}
  aria-controls="suggest-list"
  aria-autocomplete="list"
  aria-activedescendant={activeIndex >= 0 ? `opt-${activeIndex}` : undefined}
  value={query}
  onChange={(e) => setQuery(e.target.value)}
  onKeyDown={handleKeys}
/>
<ul id="suggest-list" role="listbox">
  {items.map((s, i) => (
    <li key={s} id={`opt-${i}`} role="option" aria-selected={i === activeIndex} onMouseDown={() => choose(s)}>
      <Highlight text={s} query={query} />
    </li>
  ))}
</ul>
<div aria-live="polite" className="sr-only">{items.length} suggestions available</div>
```

Keyboard behaviour to implement:

| Key | Action |
|---|---|
| **↓ / ↑** | Move the active option (wrap around); keep focus in the input (`aria-activedescendant` points at the option) |
| **Enter** | Choose the active option, or submit the typed text if none is active |
| **Escape** | Close the list (second press clears the input) |
| **Tab** | Accept or move on, per your design |
| **Home / End** | Keep default text-cursor behaviour in the input |

Also: use `onMouseDown` (not `onClick`) on options so the input's `blur` does not close the list before the click registers; announce result counts politely; support touch; ensure sufficient contrast for the highlight; do not trap focus.

### UI states

Design each state: **empty** (recent/popular), **loading** (subtle, avoid flicker: show a spinner only after ~150 ms), **no results**, **error** (degrade to plain search, do not block submission), and **offline**.

### Safe highlighting (security)

Highlighting matched text often tempts people to use `dangerouslySetInnerHTML` with `<mark>`. Do not: suggestion text from a database can contain markup. Split the string into matched and unmatched **text segments** and render `<mark>` elements with React, so everything is escaped ([Browser Contract, Lesson 07](/browser/lesson-7)).

## 3. Backend design: answering prefix queries fast

The access pattern is **"give me the top 10 completions for this prefix"**. Options:

### Option A: a database `LIKE 'prefix%'`

```sql
CREATE INDEX queries_prefix ON search_queries (lower(text) text_pattern_ops);
SELECT text FROM search_queries WHERE lower(text) LIKE 'rea%' ORDER BY popularity DESC LIMIT 10;
```

A B-tree with a pattern-ops index can serve a prefix match, but sorting by popularity across all matches can be expensive for short prefixes. Fine for small datasets and internal tools.

### Option B: a search engine

**Elasticsearch/OpenSearch** (completion suggester, edge n-grams), **Typesense** or **Algolia** provide prefix matching, ranking, typo tolerance and filters out of the box. Good when you need fuzzy matching and rich ranking without building it.

### Option C: a trie in memory (the classic answer)

A **trie** (prefix tree) stores strings character by character; every path from the root spells a prefix. To answer "completions of `rea`", walk 3 nodes, then collect the best words below. Each node can store its **top-k suggestions by popularity precomputed**, making lookups **O(length of prefix)**, independent of dataset size.

```js
class Trie {
  constructor(k = 5) { this.root = { next: new Map(), top: [] }; this.k = k; }

  insert(word, score) {
    let node = this.root;
    this._bump(node, word, score);
    for (const ch of word) {
      if (!node.next.has(ch)) node.next.set(ch, { next: new Map(), top: [] });
      node = node.next.get(ch);
      this._bump(node, word, score);          // every prefix node remembers its best completions
    }
  }

  _bump(node, word, score) {
    const i = node.top.findIndex((e) => e.word === word);
    if (i >= 0) node.top[i].score = score; else node.top.push({ word, score });
    node.top.sort((a, b) => b.score - a.score || a.word.localeCompare(b.word));
    if (node.top.length > this.k) node.top.length = this.k;
  }

  suggest(prefix) {
    let node = this.root;
    for (const ch of prefix) {
      node = node.next.get(ch);
      if (!node) return [];
    }
    return node.top.map((e) => e.word);        // already ranked: O(prefix length)
  }
}

const t = new Trie(3);
[["react", 90], ["reactive", 40], ["read", 70], ["real", 60], ["redux", 80], ["red", 20]]
  .forEach(([w, s]) => t.insert(w, s));

console.log(t.suggest("rea").join(","));    // react,read,real
console.log(t.suggest("re").join(","));     // react,redux,read
console.log(t.suggest("red").join(","));    // redux,red
console.log(t.suggest("zzz").length);       // 0
```

**Memory:** a plain trie of millions of strings is large (many small nodes). Use a **compressed (radix) trie**, store only the **top-k per node** (not every completion), keep only reasonably popular queries, or use a **finite state transducer** (what Lucene uses). A **hash map from every prefix to its top-k** list is the simplest "precomputed" variant and works well if you limit prefix length (for example 20).

### How the data gets there

Suggestions come from **query logs** (what people actually search) and catalogue data (product names).

```text
search logs ─▶ stream/batch aggregation (count queries, decay by recency, filter spam/PII/offensive)
            ─▶ build trie or prefix map offline (hourly/daily; incremental updates for trending terms)
            ─▶ publish snapshot ─▶ suggestion servers load it in memory (swap atomically)
```

- Do **not** update the trie on every search; aggregate and rebuild periodically, and add a small "trending" layer for fast-moving terms.
- **Remove sensitive or inappropriate queries** (personal data, offensive terms).
- **Personalisation:** blend global popularity with the user's history by re-ranking a larger candidate set on the server or client.

### Ranking

Score = popularity (decayed over time) × relevance to context (category, location, language) + personalisation boosts, with a small randomness or exploration factor. Keep it explainable and testable.

### Typos and fuzziness

Exact prefix match fails on "raect". Options: **edit-distance** matching (limited to 1 to 2 edits), **n-gram** indexes, phonetic keys, a **BK-tree**, or the search engine's fuzzy suggester. Apply fuzziness only when exact matches are few, since it costs more.

## 4. Scaling and delivery

- **CDN and cache:** popular prefixes are extremely repetitive. `GET /suggest?q=re` with `Cache-Control: public, max-age=300` is served from the CDN for most traffic; the origin sees mostly the long tail.
- **Stateless suggestion servers** hold the in-memory structure; scale horizontally behind a load balancer. For very large data, **shard by first characters** or by language/tenant, and route accordingly.
- **Hot prefixes** ("a", "the") are cached forever and handled at the edge.
- **Rate limit** per client and per IP ([Lesson 02](/design-problems/lesson-2)); the debounce reduces legitimate load, limits stop abuse.
- **Latency budget:** network 30 ms + server 5 ms + render 10 ms: easy when the lookup is in memory.
- **Failure:** if the service is slow or down, **degrade gracefully**: hide suggestions and let the user type and submit normally; add timeouts (a few hundred ms) on the client.
- **Privacy:** do not log full keystroke streams tied to identities; log completed searches; treat the suggest endpoint's logs carefully.

## 5. API

```http
GET /v1/suggest?q=rea&limit=8&lang=en
→ 200 OK
Cache-Control: public, max-age=300
{ "query": "rea", "suggestions": [ { "text": "react", "highlight": [0, 3] }, { "text": "read", "highlight": [0, 3] } ] }
```

Return the original `query` so the client can verify it matches the current input; validate and cap `q` length and `limit`; respond `400` for abuse inputs.

## Common mistakes

1. **A request on every keystroke** with no debounce, cache or minimum length.
2. **No abort/ignore of stale responses**, so results flicker or show the wrong query.
3. **Ignoring IME composition**, breaking CJK users.
4. **Using `onClick` for options**, losing to the input's blur.
5. **Highlighting with `dangerouslySetInnerHTML`.**
6. **No ARIA combobox semantics or keyboard support.**
7. **Scanning the database with `LIKE '%…%'`** for every query.
8. **Updating the suggestion index synchronously on every search**, and logging sensitive queries into suggestions.
9. **No graceful degradation** when the suggestion service fails.

## Interview questions

### Q1. How do you avoid sending a request on every keystroke?

Combine a minimum query length, a debounce of roughly 150 to 300 ms, and a client-side cache keyed by prefix (including reuse of results for shorter or longer related prefixes). On the server side, make popular prefix responses cacheable at the CDN. Together they reduce traffic by an order of magnitude.

### Q2. How do you show results only for the latest query?

Abort the previous request with `AbortController` (or ignore stale results) whenever the input changes, key cached results by query, and have the server echo the query so the client can verify the response matches the current input. Debounce lowers request volume but does not by itself prevent out-of-order responses.

### Q3. How do you make it accessible?

Use the ARIA combobox pattern: `role="combobox"` with `aria-expanded`, `aria-controls` and `aria-activedescendant` on the input, a `listbox` of `option`s with `aria-selected`, keyboard handling for arrows, Enter and Escape with focus staying in the input, a polite live region announcing the number of results, sufficient contrast, and `onMouseDown` on options so blur does not swallow clicks.

### Q4. Where would a trie help?

On the backend, to answer prefix queries in O(prefix length) by storing precomputed top-k suggestions at each node, so latency does not depend on dataset size. Build it offline from aggregated query logs, load it into memory on stateless servers, and compress it (radix trie or prefix map with limited depth) to control memory.

### Q5. How would you rank suggestions?

By popularity (counts decayed for recency), contextual relevance (language, location, category) and optionally personalisation from the user's history, computed offline into the index and lightly re-ranked at request time. Filter spam, sensitive and offensive queries before they become suggestions.

### Q6. Trie vs database vs search engine?

A database `LIKE 'prefix%'` with the right index is fine for small data. A search engine gives prefix matching, typo tolerance and ranking with little custom code, and scales well. A custom in-memory trie or prefix map gives the lowest latency and cost for a focused, high-traffic suggestion service when you control the data pipeline.

### Q7. How do you handle IME input?

Track `compositionstart` and `compositionend` and avoid querying on intermediate composition states; trigger the search when composition ends (or use the finalised value). Without it, East Asian users trigger meaningless queries mid-composition.

### Q8. What happens if the suggestion service is down?

The input must still work: set short timeouts, hide the dropdown on failure and let the user submit the search normally. Cache recent results, monitor error rates and avoid retry storms with backoff.

### Q9. Scenario: autocomplete suggests offensive or private queries. How do you handle it?

Filter at the source: build suggestions from aggregated, anonymised query logs with a minimum count, exclude personal data patterns (emails, phone numbers) and apply blocklists and classifiers for offensive content before terms enter the index. Offer a takedown path with a fast purge, avoid personalised suggestions leaking one user's history to another, and review the top suggestions regularly.

### Q10. Scenario: at peak the suggestion latency spikes and results arrive after the user typed more characters. What do you change?

On the client, abort stale requests and ignore late responses so wrong results never show, keep a prefix cache, and set a short timeout with a graceful fallback to plain search. On the server, serve popular prefixes from the CDN and in-memory structures, add replicas near users, rate-limit abuse, and measure p95 per prefix length to find the slow path.

## Key takeaways

- **Frontend:** minimum length, debounce, cache by prefix, abort stale requests, handle IME, full keyboard and ARIA combobox support, safe highlighting, graceful states.
- **Backend:** precompute **top-k per prefix** (trie or prefix map), build from aggregated logs offline, serve from memory, cache popular prefixes at the CDN.
- Use **search engines** for fuzzy/typo-tolerant needs; add fuzziness sparingly.
- Rank by decayed popularity and context; filter sensitive terms; protect with rate limits and fall back gracefully.
