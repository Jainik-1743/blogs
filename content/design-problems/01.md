> **In one line:** a URL shortener maps a short **code** to a long URL. The design is easy; the interview is won in the details: **how you generate unique codes**, **why Base62**, **how collisions are handled**, **301 vs 302**, and **how you serve 100x more reads than writes** from a cache.

Follow the six steps from [Lesson 00](/design-problems/lesson-0): clarify, estimate, API, data, core design, scale and failure.

## 1. Requirements

**Functional**

- Create a short link for a long URL. Optional: **custom alias**, **expiry date**.
- Following a short link **redirects** to the long URL.
- Optional: per-link **click analytics**; users can list or delete their links.

**Non-functional**

- **Redirects are fast** (tens of ms) and highly available, because every click depends on them.
- **Read-heavy**: assume reads outnumber writes about 100 to 1.
- Short codes must be **unique** and not trivially collide.
- Durability: a link must not silently disappear.
- Abuse resistance (spam, phishing, scraping).

## 2. Estimates

```text
100M new links / month           → ~40 writes/s (peak ~200)
Read:write 100:1                 → ~4,000 reads/s (peak ~20,000)
Keep 5 years: 6 billion links × ~500 B → ~3 TB
Hot-set cache (20% of daily URLs) → ~10 GB: fits in one Redis node
```

Code length: with Base62 (`0-9a-zA-Z`), **7 characters give 62⁷ ≈ 3.5 trillion** possible codes, comfortably more than 6 billion (about 0.17% used). 6 characters give ≈ 56.8 billion, also enough, but leave less headroom; 7 is the usual answer.

## 3. API

```http
POST /v1/links
Authorization: Bearer …
Content-Type: application/json

{ "url": "https://example.com/some/very/long/path?x=1", "alias": "launch-2026", "expiresAt": "2027-01-01T00:00:00Z" }

→ 201 Created
Location: /v1/links/Xk3p9Qa
{ "code": "Xk3p9Qa", "shortUrl": "https://sho.rt/Xk3p9Qa", "longUrl": "…", "expiresAt": "…" }

# Errors: 400/422 invalid URL, 409 alias already taken, 429 rate limited

GET /Xk3p9Qa
→ 302 Found
Location: https://example.com/some/very/long/path?x=1
# 404 unknown code, 410 expired or removed
```

Notes: only `http`/`https` URLs are accepted; the create endpoint is **authenticated and rate-limited** ([Lesson 02](/design-problems/lesson-2)); the redirect endpoint is **public and extremely hot**, so keep it as lean as possible.

## 4. Data model

```sql
CREATE TABLE links (
  code        varchar(16)  PRIMARY KEY,         -- the short code; the hot lookup key
  long_url    text         NOT NULL,
  user_id     uuid,
  created_at  timestamptz  NOT NULL DEFAULT now(),
  expires_at  timestamptz,
  is_active   boolean      NOT NULL DEFAULT true
);
CREATE INDEX links_user_created ON links (user_id, created_at DESC);
```

The main access pattern is **lookup by `code`**: a pure key-value read. PostgreSQL with a primary-key index handles that well at this scale; if volume demanded it, the same model moves to a key-value store such as DynamoDB (partition key = code) or is sharded by a hash of the code. Click events go to a **separate append-only store** ([analytics section](#analytics-without-slowing-the-redirect)).

## 5. The core problem: generating unique short codes

Four common approaches.

### Option A: hash the URL, encode, truncate

`code = base62(md5(longUrl + salt)).slice(0, 7)`

- **Pro:** stateless, no coordination; the same URL gives the same code (natural deduplication).
- **Con:** **truncation causes collisions.** Two different URLs can share the first 7 characters. You must check the database and handle a collision (re-hash with a counter or salt, retry).
- **Con:** the same long URL from two users maps to one code, which is wrong if each user wants their own stats or expiry.
- The classic [system-design-primer](https://github.com/donnemartin/system-design-primer) solution uses MD5 over IP and timestamp, Base62, and the first 7 characters; it is a good starting answer if you also explain the collision handling.

### Option B: random code with collision retry

Generate 7 random Base62 characters; insert with the code as primary key; if the insert hits a **unique violation**, generate another and retry.

- With 6 billion codes in a space of 3.5 trillion, the probability that a random code is already taken is about **0.17%**, so retries are rare (expected 1.002 attempts).
- **Pro:** simple, no central coordinator, unguessable-ish codes.
- **Con:** collisions grow as the space fills (at 50% full, half of the inserts retry), so monitor occupancy and add length before then. The database must enforce uniqueness (a primary key does).

```ts
async function createLink(longUrl: string, userId: string) {
  for (let attempt = 0; attempt < 5; attempt++) {
    const code = randomBase62(7);
    try {
      return await prisma.link.create({ data: { code, longUrl, userId } });
    } catch (e) {
      if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === "P2002") continue; // unique violation → try again
      throw e;
    }
  }
  throw new Error("Could not allocate a unique code");
}
```

### Option C: a counter encoded in Base62

Keep a global **counter**; the code is the counter value in Base62 (counter 125 → `21`). Uniqueness is guaranteed by construction, **no collision handling needed**.

- **Pro:** zero collisions; codes are as short as possible (small counters give short codes).
- **Con:** the counter is a **coordination point and potential bottleneck/single point of failure**. Mitigations: an atomic database sequence, Redis `INCR`, or **range allocation**: each app server reserves a block (say 100,000 IDs) from a coordinator and hands them out locally with no network call per ID. If a server crashes, its unused range is wasted, which is fine (we have trillions).
- **Con:** codes are **sequential and guessable**, so anyone can enumerate other people's links. Fix by **scrambling** the counter before encoding (a reversible permutation such as a Feistel network or multiplying by a large number coprime to the space, modulo 62⁷), so codes look random but remain unique.

### Option D: a key-generation service (KGS) with pre-generated keys

A separate service pre-generates unique random codes and stores them in two tables, **unused** and **used**. App servers fetch **batches** of unused keys into memory and consume them locally; the KGS moves them to "used".

- **Pro:** instant, no collisions at request time, short critical path.
- **Con:** extra component to run, a possible single point of failure (run it replicated), and keys held in a crashed server's memory are lost (acceptable).

### Comparison

| Approach | Collisions | Coordination | Guessable | Complexity |
|---|---|---|---|---|
| Hash + truncate | Yes, must handle | None | Not really | Low |
| Random + retry | Rare, handled by retry | None (DB uniqueness) | No | **Low** |
| Counter + Base62 | None | Counter/range service | **Yes** unless scrambled | Medium |
| KGS | None | A service | No | Higher |

**A defensible answer:** "At this scale I'd use random 7-character Base62 codes with an insert-retry on collision: simple, stateless and enough headroom. If we needed guaranteed uniqueness without retries or shorter codes, I'd use a scrambled counter with range allocation per server. If collisions or latency became a concern at much larger scale, I'd move to a key-generation service."

## Why Base62, not Base64?

- **Base64** uses `A-Z a-z 0-9 + /` (and `=` padding). `+` and `/` have **special meaning in URLs** (`/` is a path separator; `+` can mean a space in query strings), so you must further escape them. Base64url swaps in `-` and `_` and drops padding, which is URL-safe but still includes punctuation.
- **Base62** uses only `0-9 a-z A-Z`: **alphanumeric, URL-safe, easy to read out and copy**, no escaping.

Encoding a number in Base62:

```js
const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

function toBase62(n) {
  n = BigInt(n);
  if (n === 0n) return ALPHABET[0];
  let out = "";
  while (n > 0n) {
    out = ALPHABET[Number(n % 62n)] + out;
    n /= 62n;
  }
  return out;
}

function fromBase62(s) {
  let n = 0n;
  for (const ch of s) n = n * 62n + BigInt(ALPHABET.indexOf(ch));
  return n;
}

console.log(toBase62(125));            // 21
console.log(fromBase62("21"));         // 125n
console.log(toBase62(62n ** 7n - 1n)); // ZZZZZZZ   (the largest 7-character code)
console.log(62n ** 7n);                // 3521614606208n  (about 3.5 trillion codes)
```

Check the size claim: 62⁷ = 3,521,614,606,208, and 62⁶ = 56,800,235,584.

## The redirect: 301 or 302?

Both redirect the browser; the difference is **caching**.

| | `301 Moved Permanently` | `302 Found` (temporary) |
|---|---|---|
| **Browser caching** | Cached aggressively; the browser may go straight to the long URL next time and **never hit your server** | Not cached by default; every click comes to your server |
| **Server load** | Lower | Higher |
| **Analytics** | **Lost** for repeat clicks from the same browser | **Every click is counted** |
| **Changing or disabling a link later** | Hard: cached redirects linger in browsers and intermediaries | Easy: takes effect immediately |
| **SEO** | Passes link equity to the target (treated as permanent) | Treated as temporary |

**Answer:** if you offer **click analytics, expiry, editing or deactivation**, use **302** (or 307, which also preserves the method). If links are permanent and you want to minimise load, use **301**. Most commercial shorteners use 302-style redirects precisely for the analytics ([HTTP semantics](/browser/lesson-6)). Always set an explicit `Cache-Control` rather than relying on defaults.

```ts
app.get("/:code", async (req, res) => {
  const target = await resolve(req.params.code);   // cache → DB
  if (!target) return res.status(404).send("Not found");
  if (target.gone) return res.status(410).send("Link expired");
  recordClick(req, req.params.code);               // fire-and-forget, never awaited on the hot path
  res.redirect(302, target.longUrl);
});
```

## Serving 100x more reads than writes

1. **Cache-aside with Redis:** look up `code → longUrl` in Redis first; on a miss, read the database and populate the cache with a TTL. With the 80/20 rule, a ~10 GB cache serves most reads.

```ts
async function resolve(code: string) {
  const cached = await redis.get(`l:${code}`);
  if (cached) return JSON.parse(cached);
  const row = await prisma.link.findUnique({ where: { code } });
  if (!row) { await redis.set(`l:${code}`, "null", "EX", 60); return null; }   // short negative cache vs. scanners
  const value = { longUrl: row.longUrl, gone: !row.isActive || (row.expiresAt && row.expiresAt < new Date()) };
  await redis.set(`l:${code}`, JSON.stringify(value), "EX", 3600);
  return value;
}
```

2. **Read replicas** for the database; the hot path rarely hits it.
3. **CDN or edge caching** for permanent links, if using 301 or `Cache-Control` on 302s.
4. **Keep the redirect path minimal:** no auth, no heavy logging, no synchronous analytics.
5. **Protect against cache stampedes and hot keys** (a viral link): coalesce concurrent misses, keep popular entries warm, replicate hot keys across cache nodes.
6. **Negative caching** of unknown codes protects the database from scanners probing random codes.

## Analytics without slowing the redirect

Never write a click row to the database inside the redirect request. Instead:

```text
redirect handler ──(non-blocking)──▶ queue / log stream (Kafka, SQS, Kinesis)
                                          │
                                          ▼
                              stream processor / batch job
                                          │
                       aggregates (per link, per day, per country) ──▶ analytics store (columnar DB / time-series)
```

Raw events: `code, timestamp, ip (hashed or truncated), user-agent, referrer`. Aggregate asynchronously; the stats endpoint reads the aggregates. Filter obvious **bots** and de-duplicate if "unique clicks" matter. Mind privacy: hash or truncate IPs and honour regional rules.

## Custom aliases and expiry

- **Custom alias:** validate length and characters, reject **reserved words** (`api`, `admin`, `login`, `v1`), check uniqueness via the same primary key (the insert fails with a unique violation, returned as `409`). Aliases and generated codes share one namespace, so generated codes cannot collide with aliases.
- **Expiry:** store `expires_at`; the redirect checks it (also in the cache value, with a TTL no longer than the remaining life). A background job **deletes or archives** expired rows and reclaims codes if desired. Return `410 Gone` for expired links so crawlers drop them.

## Abuse prevention and security

- **Validate the destination:** allow only `http`/`https`, enforce a maximum length, and normalise. Check against **malware and phishing blocklists** (Google Safe Browsing or similar) at creation, and re-scan periodically since a clean page can turn malicious.
- **Rate limit creation** per user, API key and IP, and require authentication or CAPTCHA for anonymous creation ([Lesson 02](/design-problems/lesson-2)).
- **Prevent SSRF** if you ever fetch the destination (to show a preview or title): block private IP ranges, metadata endpoints and redirects to them.
- **Report-and-takedown flow:** a way to deactivate a link (`is_active = false`) that takes effect immediately; this is another reason to prefer 302.
- **Enumeration:** sequential codes let people scan for other users' links. Use random or scrambled codes, and remember that short links are **not secret** by themselves; do not put sensitive content behind an unauthenticated short link.
- **Open redirect abuse:** shorteners are inherently redirectors; warn on suspicious destinations, show an interstitial for flagged domains, and monitor.

## Scaling the storage

At 3 TB and 20,000 reads per second, caches carry the reads; the write rate is small. If you outgrow one primary:

- **Shard by a hash of the code**, so lookups are routed to one shard. Use **consistent hashing** or a lookup service to add shards without remapping everything.
- Or use a **managed key-value store** (DynamoDB, Cassandra) that shards automatically.
- Keep **per-user listing** (`user_id, created_at`) in a secondary index or table, since the code-based sharding does not serve it.

## Failure modes

- **Redis down:** fall back to the database (slower but correct), with rate limiting to protect it; consider a local in-process cache as a second layer.
- **Database primary down:** promote a replica; reads continue from replicas; creation briefly fails and clients retry (creation is idempotent per request ID or alias).
- **Duplicate create requests:** use an idempotency key so a retry does not allocate a second code ([Backend, Lesson 02](/backend/lesson-2)).
- **Region outage:** replicate across regions, with routing at DNS or the edge.

## Common mistakes

1. **Hash-and-truncate with no collision handling.**
2. **Base64 codes** with `+` and `/` in URLs.
3. **301 redirects when analytics or editing are required.**
4. **Writing analytics synchronously** in the redirect path.
5. **Sequential IDs** that expose and allow enumeration of all links.
6. **No caching**, so every redirect hits the database.
7. **No abuse controls** (phishing, spam creation, SSRF).
8. **Forgetting expiry and deactivation** semantics (`410`).

## Interview questions

### Q1. Why Base62 over Base64?

Base62 uses only letters and digits, which are safe in URLs and easy to copy and say aloud. Base64's `+` and `/` need escaping in URLs (and `=` padding is awkward); even the URL-safe variant adds punctuation. Seven Base62 characters give about 3.5 trillion codes, ample for billions of links.

### Q2. How do you handle collisions with a truncated MD5 hash?

Treat the hash as a starting point: truncate to 7 characters, attempt the insert with the code as primary key, and on a unique violation re-hash with an added counter or salt and retry. The database constraint is the source of truth. Alternatively, avoid hashing and use random codes with insert-retry or a counter, which handle uniqueness more directly.

### Q3. Sequential IDs are guessable. Does that matter, and how would you mitigate it?

It matters if links may reveal private content or users' activity, because anyone can enumerate codes. Mitigate by scrambling the counter with a reversible permutation before Base62 encoding, or by using random codes; and never rely on obscurity for sensitive links; require authentication where privacy matters.

### Q4. 301 or 302, and why does analytics change the answer?

A 301 is cached by browsers, so repeat clicks may never reach the server, losing analytics and making edits or deactivation slow to take effect. A 302 is not cached by default, so each click hits the server, enabling accurate counts, expiry and immediate changes at the cost of more load, which a cache and CDN absorb. With analytics or editing requirements I choose 302.

### Q5. How do you scale when reads outnumber writes 100 to 1?

Cache-aside with Redis for hot codes (including negative caching), read replicas for the database, CDN or edge caching where redirects are permanent, a minimal hot path with asynchronous analytics, protection against hot keys and stampedes, and sharding by a hash of the code if storage or throughput outgrows one primary.

### Q6. How would you generate IDs across many servers without collisions or a bottleneck?

Range allocation: a coordinator hands each server a block of counter values; the server issues them locally, so there is no per-request coordination, and a lost block simply wastes some of a huge space. Scramble the values to avoid guessable sequences. Or use random codes with database uniqueness as the arbiter.

### Q7. How do you stop the service being used for phishing?

Validate and normalise URLs, check them against threat-intelligence lists at creation and periodically afterwards, rate-limit and authenticate creation, provide reporting and instant deactivation, show warnings for flagged domains, and monitor abuse patterns.

### Q8. How would you implement custom aliases?

Validate format and reserved words, use the same unique primary key namespace as generated codes so conflicts surface as a unique violation returned as `409`, and apply the same expiry and abuse controls. Optionally restrict custom aliases to authenticated or paid users.

## Key takeaways

- Estimate first: ~40 writes/s, ~4,000 reads/s, ~3 TB; **7 Base62 characters** (≈3.5 trillion) is plenty.
- **Code generation:** random + unique-constraint retry (simple), scrambled counter with range allocation (no collisions), or a KGS (no request-time work). Hashing needs collision handling.
- **Base62** is URL-safe and readable; Base64 is not.
- **302 for analytics and control, 301 for permanence and load.**
- **Cache aggressively**, keep the redirect path lean, record clicks **asynchronously**.
- Plan for **expiry (410), abuse, enumeration, failures and sharding**.
