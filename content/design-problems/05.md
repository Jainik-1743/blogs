> **In one line:** a notification system is **events in, decisions in the middle, deliveries out**. Services publish events; a notification service decides *who gets what on which channel*; queues fan out to channel workers; a realtime gateway pushes to connected browsers. Reliability comes from **queues, retries and idempotency**, not from hoping the provider works.

This problem touches almost every backend topic: queues, retries, deduplication, real-time connections, preferences and database design. It also has a frontend half: the bell icon.

## 1. Requirements

**Functional**

- Send notifications through multiple **channels**: in-app (the bell), web/mobile push, email, SMS.
- Triggered by **events** (a comment, a payment, a shipped order) or by schedules and broadcasts.
- Users have **preferences** (per channel and per type, quiet hours) and can mark notifications **read**.
- Show an **unread count** and a list that updates **in real time** while the user is online.

**Non-functional**

- **Reliable delivery**: do not lose important notifications (at least once), but also **avoid duplicates** (an effectively-once experience).
- **Low latency** for in-app (seconds), tolerant for email.
- **Scalable**: spikes (a broadcast to a million users), isolation between channels, and graceful handling of provider outages.
- Respect **rate limits** of providers and **user fatigue**.
- Observable and auditable.

## 2. Estimates

```text
10 million users, 20% daily active → 2 million DAU
Avg 10 notifications per DAU per day  → 20 million in-app notifications / day ≈ 230 per second (peak ~2,000)
Concurrent online users (SSE/WebSocket): ~5% of DAU at peak ≈ 100,000 open connections
Storage: 20M/day × 365 × 500 B ≈ 3.6 TB/year → keep 90 days hot, archive the rest
```

Conclusion: the event pipeline is moderate; the interesting scaling problem is **holding 100,000+ long-lived connections**, and **fan-out spikes** for broadcasts.

## 3. Choosing the real-time transport

How does the server tell a browser something happened?

| Technique | How | Pros | Cons |
|---|---|---|---|
| **Polling** | Client requests `/notifications` every N seconds | Trivial; works everywhere | Wasteful (most responses are empty); latency up to N seconds; load grows with users |
| **Long polling** | Request stays open until there is news, then client re-requests | Lower latency, simple infra | A connection per client anyway; reconnect overhead; awkward ordering |
| **Server-Sent Events (SSE)** | One long-lived HTTP response streaming `text/event-stream`; **server to client only** | Built into browsers (`EventSource`), **automatic reconnect**, `Last-Event-ID` for resuming, works over plain HTTP/2, easy to proxy | One-way; per-origin connection limits on HTTP/1.1 (about 6) unless using HTTP/2 |
| **WebSocket** | Full-duplex connection after an HTTP upgrade | Two-way, low overhead, binary support | More infrastructure (sticky routing, heartbeats), reconnect and resume logic is yours |

**For notifications, SSE is usually the right answer**: the data flows one way (server to client), the browser reconnects automatically, and resuming from `Last-Event-ID` is built in. Choose **WebSocket** when you also need frequent client-to-server messages (chat, collaborative editing). Use polling as a **fallback** and for simple low-volume cases.

## 4. Architecture

```text
 ┌───────────┐  events   ┌──────────────────┐   ┌─────────────────────┐
 │ Services  │──────────▶│  Event bus       │──▶│ Notification service │
 │ (orders,  │ (Kafka /  │  (Kafka/SNS/SQS) │   │  • resolve recipients│
 │ comments) │ SQS/SNS)  └──────────────────┘   │  • check preferences │
 └───────────┘                                   │  • dedupe / throttle │
                                                 │  • render templates  │
                                                 └───────────┬─────────┘
                                                             │ one message per (user, channel)
                    ┌───────────────┬─────────────┬──────────┴───────┐
                    ▼               ▼             ▼                  ▼
              In-app queue     Push queue    Email queue         SMS queue
                    │               │             │                  │
              store + realtime   FCM/APNs/     SES/SendGrid     Twilio/SNS
                    │            Web Push
                    ▼
        Realtime gateway (SSE/WebSocket) ──▶ connected browsers
```

Principles:

- **Decouple with queues.** Producers publish an *event* (`comment.created`) and move on; they do not call email or SMS providers. A slow provider cannot slow checkout.
- **One queue per channel** so a failing email provider does not delay in-app delivery, with its own scaling, rate limits and retry rules.
- **Notification service** turns an event into zero or more *notification jobs*: it looks up recipients (a post's followers), applies **preferences** and **quiet hours**, **dedupes**, and renders content (templates, localisation).
- **Workers** per channel call providers with **retries and backoff**, and write delivery status.

## 5. Data model

```sql
CREATE TABLE notifications (
  id          uuid PRIMARY KEY,
  user_id     uuid        NOT NULL,
  type        text        NOT NULL,                  -- 'comment.reply', 'order.shipped'
  payload     jsonb       NOT NULL,                  -- ids and data needed to render; avoid copying large objects
  dedupe_key  text,                                  -- e.g. 'comment.reply:post42:user9'
  created_at  timestamptz NOT NULL DEFAULT now(),
  read_at     timestamptz,
  UNIQUE (user_id, dedupe_key)                       -- idempotency: the same event cannot create two rows
);
CREATE INDEX notif_user_created ON notifications (user_id, created_at DESC, id DESC);       -- the list, cursor-paginated
CREATE INDEX notif_user_unread  ON notifications (user_id) WHERE read_at IS NULL;            -- small partial index for unread

CREATE TABLE notification_preferences (
  user_id uuid, channel text, type text, enabled boolean NOT NULL DEFAULT true,
  quiet_start time, quiet_end time, PRIMARY KEY (user_id, channel, type)
);

CREATE TABLE push_subscriptions (user_id uuid, platform text, token text, last_seen timestamptz, PRIMARY KEY (user_id, token));
CREATE TABLE deliveries (notification_id uuid, channel text, status text, attempts int, provider_id text, error text, PRIMARY KEY (notification_id, channel));
```

- **List** the bell with cursor pagination ([Lesson 03](/design-problems/lesson-3)).
- **Unread count:** `SELECT count(*) … WHERE user_id = $1 AND read_at IS NULL` is cheap with the partial index for most users. For very large unread numbers, cache a counter per user (in Redis) updated on create and read, and cap the display ("99+").
- **Read state:** `PATCH /notifications/{id}` with `{ read: true }`, and `POST /notifications/read-all`. Idempotent updates.
- **Retention:** delete or archive old rows (partition by month; drop partitions).

## 6. Delivering in-app notifications in real time

### The connection gateway

A fleet of **gateway** servers holds the open SSE or WebSocket connections. The notification system must be able to reach *whichever gateway holds user 42's connection*.

```text
Browser ──SSE──▶ Gateway instance 3          Redis: user:42 → [gateway-3:conn-9, gateway-5:conn-2]
                         ▲
In-app worker ──publish "user:42" event──▶ Redis Pub/Sub (or NATS/Kafka) ──▶ gateways subscribed for connected users
```

- On connect, the gateway **authenticates** (cookie or token), and **subscribes** to that user's channel; it removes the subscription when the connection drops.
- To deliver, the worker **publishes** to `user:{id}` on a pub/sub system; any gateway holding a connection for that user pushes it.
- **Do not hold business logic in the gateway.** It is a thin fan-out layer, scaled by connection count (tens of thousands of connections per well-tuned node, because idle connections are cheap), with load balancer settings for long-lived connections and **heartbeats** (a comment line every 15 to 30 seconds) so proxies do not drop idle streams.

### SSE endpoint (server) and client

```ts
// Express SSE endpoint
app.get("/v1/notifications/stream", requireAuth, (req, res) => {
  res.set({ "Content-Type": "text/event-stream", "Cache-Control": "no-cache, no-transform", Connection: "keep-alive", "X-Accel-Buffering": "no" });
  res.flushHeaders();

  const lastId = req.header("Last-Event-ID");                       // the browser sends this on reconnect
  if (lastId) replayMissed(req.user.id, lastId).forEach((n) => send(n));   // catch up from the DB

  const send = (n: Notification) => res.write(`id: ${n.id}\nevent: notification\ndata: ${JSON.stringify(n)}\n\n`);
  const unsubscribe = bus.subscribe(`user:${req.user.id}`, send);
  const heartbeat = setInterval(() => res.write(": ping\n\n"), 25_000);

  req.on("close", () => { clearInterval(heartbeat); unsubscribe(); });
});
```

```ts
// Browser
const es = new EventSource("/v1/notifications/stream", { withCredentials: true });
es.addEventListener("notification", (e) => {
  const n = JSON.parse((e as MessageEvent).data);
  addToList(n); incrementBadge();
});
es.onerror = () => { /* the browser reconnects automatically and sends Last-Event-ID */ };
```

Because every event has an **`id`**, a reconnecting client sends `Last-Event-ID` and the server **replays what was missed** from the database. That is how you get reliability on top of a flaky connection: the DB is the source of truth; the stream is just a fast path.

## 7. Reliability: at least once, plus idempotency

Queues deliver **at least once**: a worker may crash after sending an email but before acknowledging the message, so the message is delivered again. To make the *user* experience effectively once:

- **Deduplicate at creation:** each notification has a deterministic **`dedupe_key`** (for example `order.shipped:{orderId}:{userId}`); the `UNIQUE (user_id, dedupe_key)` constraint makes inserting the same event twice a no-op.
- **Idempotent senders:** record `(notification_id, channel)` delivery status *before/while* sending; skip if already `SENT`; pass an **idempotency key** to providers that support it.
- **Retry transient failures** with exponential backoff and jitter; use a **dead-letter queue** for messages that keep failing, and alert on it ([Lesson 07](/design-problems/lesson-7)).
- **Honour provider limits**: throttle workers (token buckets, [Lesson 02](/design-problems/lesson-2)) so a burst does not cause `429`s from the email or push provider.
- **Ordering:** per-user ordering matters little for notifications; if it does, partition the queue by `user_id`.
- **Provider failover:** a secondary email/SMS provider for critical messages.

## 8. User preferences, batching and fatigue

- **Preferences** by channel and type; always allow critical messages (security alerts, receipts) regardless; respect legal requirements (unsubscribe links, SMS opt-in).
- **Quiet hours** per user time zone: delay push or email until morning.
- **Batching and digests:** "5 people liked your post" instead of five pushes. Collapse by key in a short window (a "debounce for notifications"): hold the first, coalesce the rest, send one summary.
- **Frequency caps** per user per hour/day, and priority tiers (urgent skips batching).
- **Channel selection and fallback:** send in-app first; if unread after N minutes, send an email; do not push to a device the user is actively using (presence).

## 9. Scenario: a user has 3 tabs open. How many connections do you hold?

Naively, **three SSE connections** (one per tab), each receiving every notification. Fine at small scale; at 100,000 users it means 300,000 connections. Options:

1. **Accept it:** idle connections are cheap and it is simple.
2. **Leader tab:** tabs coordinate with `BroadcastChannel` or a `SharedWorker` so only one tab holds the connection and relays events to the others.
3. **Multiplex over HTTP/2** to avoid browser per-origin connection limits (the six-connection limit on HTTP/1.1 is a real problem with several tabs and SSE).
4. Cap connections per user on the gateway and close the oldest.

Also make **read state server-side** so marking read in one tab updates the others (through the same stream or a `BroadcastChannel`).

## 10. Scenario: broadcast to a million users

Fan-out creates a million rows and a million jobs. Strategies:

- **Fan-out on write:** insert one row per user (fast reads, heavy write spike) via **batched, paginated workers** that process users in chunks; rate-limit to protect the database.
- **Fan-out on read:** store **one** broadcast record and merge it into each user's feed at read time (cheap writes; reads need a merge and per-user read-state).
- A **hybrid**: fan-out on write for normal notifications, on read for large broadcasts and "celebrity" accounts.
- Use **topics** for push (FCM/APNs topic messaging) instead of per-device sends where possible.
- **Throttle** and stagger to avoid thundering herds when everyone opens the app at once.

## 11. Offline users

- In-app notifications are persisted, so they appear on next load or reconnect (via `Last-Event-ID` replay or the list endpoint).
- **Push notifications** (Web Push via service workers and VAPID, FCM, APNs) reach users who are not on the page. Handle **token lifecycle**: remove invalid tokens when providers return "unregistered" errors; refresh on each app open; ask for permission at a meaningful moment, not on first load.
- **Email/SMS** as longer-latency fallbacks.

## 12. The frontend: the bell

- Fetch the **list** (paginated) and **unread count** on load; subscribe to the stream; merge new items; keep the badge in sync.
- **Optimistic read:** mark as read in the UI immediately, send the request, roll back on failure.
- **Group and truncate** long lists; show relative times; link each notification to its target.
- **Accessibility:** `aria-live="polite"` for new notification announcements (not too chatty), keyboard-reachable dropdown, focus management.
- **Fallbacks:** if the stream fails repeatedly, fall back to **polling with backoff**; pause when the tab is hidden; do not hammer the server ([Debugging, Lesson 05](/debugging/lesson-5)).

## Observability

Track: events in, notifications created, deliveries by channel and status, end-to-end latency (event to delivered), queue depth and age, provider error and bounce rates, DLQ size, open connections, reconnect rate, unread backlog. Log with the notification ID and dedupe key ([Backend, Lesson 05](/backend/lesson-5)).

## Common mistakes

1. **Calling providers synchronously** from business code, coupling checkout to an email API.
2. **No idempotency**, so retries send duplicates.
3. **One shared queue** for all channels, so one slow provider blocks the rest.
4. **Polling every second** from every client.
5. **Treating the stream as the source of truth** (no replay on reconnect).
6. **Ignoring preferences, quiet hours and batching**, causing notification fatigue and opt-outs.
7. **Fan-out per recipient inside the request** for broadcasts.
8. **Never pruning dead push tokens** or old notifications.

## Interview questions

### Q1. SSE or WebSocket for notifications?

SSE is usually the better fit: communication is server to client, browsers reconnect automatically and resume with `Last-Event-ID`, it runs over plain HTTP (and HTTP/2) and is simple to operate. WebSocket is appropriate when you also need frequent client-to-server messages. Either way I persist notifications and replay missed ones, with polling as a fallback.

### Q2. How do you avoid sending duplicates?

Assume at-least-once delivery and make processing idempotent: a deterministic dedupe key with a unique constraint when creating notifications, delivery records checked before sending, idempotency keys with providers, and safe retries with backoff. The user sees at most one notification even if a job runs twice.

### Q3. Scenario: a user has 3 tabs open. How many connections do you hold?

By default one per tab. To reduce load, elect a leader tab with `BroadcastChannel` or a `SharedWorker` that holds the single connection and relays events, use HTTP/2 to avoid per-origin limits, and cap connections per user on the gateway. Keep read state on the server so tabs stay consistent.

### Q4. How do you handle offline users?

Persist every in-app notification so it appears on the next load or reconnect (replay from `Last-Event-ID` or the list endpoint), send push notifications through service workers, FCM or APNs for users away from the page, and use email or SMS as slower fallbacks according to preferences. Maintain push token health.

### Q5. How would you deliver a broadcast to 10 million users?

Avoid doing it inline: enqueue a broadcast job and fan out in batches through workers with rate limiting, or store one broadcast record and merge it at read time, or use push topics. Often a hybrid works. Throttle and stagger to protect the database and providers, and handle read state per user.

### Q6. How do you store and display the unread count efficiently?

A partial index on unread rows per user makes the count cheap; for heavy users or hot paths cache a per-user counter in Redis updated on create and read, and cap the display (for example "99+"). Mark-all-read is a single idempotent update.

### Q7. Why one queue per channel?

Isolation and independent control: each channel has different providers, rate limits, latency needs and failure modes. A slow or failing email provider should not delay in-app delivery, and each queue can scale, retry and alert separately.

### Q8. How do you prevent notification fatigue?

Honour per-type and per-channel preferences and quiet hours, batch or digest similar events, apply frequency caps, set priorities (security alerts bypass batching), avoid pushing to devices the user is actively using, and measure opt-out and engagement to tune the rules.

## Key takeaways

- **Events in, decisions in the middle, deliveries out**, decoupled with queues and one queue per channel.
- **SSE** (with `Last-Event-ID` replay) is the pragmatic real-time channel for server-to-client notifications; the database is the source of truth.
- **At-least-once + idempotency** (dedupe keys, delivery records, provider keys) gives an effectively-once experience; use DLQs and backoff.
- Scale the **connection gateway** separately; connect it to workers through pub/sub keyed by user.
- Design for **preferences, batching, quiet hours**, broadcast fan-out and offline users.
