> **In one line:** a notification system is **events in, decisions in the middle, deliveries out**. Services publish events. A notification service decides *who gets what on which channel*. Queues pass the work to channel workers. A realtime gateway pushes messages to browsers that are connected. The system stays reliable because of **queues, retries and idempotency** (safe repeats), not because we hope the provider always works.

This problem touches almost every backend topic: queues, retries, removing duplicates, real-time connections, user settings and database design. It also has a frontend part: the bell icon.

## 1. Requirements

**Functional**

- Send notifications through many **channels**: in-app (the bell), web or mobile push, email and SMS.
- Start a notification from an **event** (a comment, a payment, a shipped order), from a schedule, or from a broadcast to many users.
- Users have **preferences** (per channel and per type, plus quiet hours). They can mark notifications as **read**.
- Show an **unread count** and a list. Both update in **real time** while the user is online.

**Non-functional**

- **Reliable delivery**: do not lose important notifications (send them at least once). Also **avoid duplicates**, so the user feels it was sent exactly once.
- **Low latency** for in-app (a few seconds). Email can be slower.
- **Scalable**: handle spikes (a broadcast to a million users), keep channels separate from each other, and cope when a provider is down.
- Respect the **rate limits** of providers (the most requests they allow per time period) and avoid **user fatigue** (too many messages).
- Easy to watch and audit.

## 2. Estimates

```text
10 million users, 20% daily active → 2 million DAU
Avg 10 notifications per DAU per day  → 20 million in-app notifications / day ≈ 230 per second (peak ~2,000)
Concurrent online users (SSE/WebSocket): ~5% of DAU at peak ≈ 100,000 open connections
Storage: 20M/day × 365 × 500 B ≈ 3.6 TB/year → keep 90 days hot, archive the rest
```

What this tells us: the event pipeline is a medium load. The hard scaling problems are **holding 100,000+ long-lived connections** and **fan-out spikes** (one message turning into many) for broadcasts.

## 3. Choosing the real-time transport

How does the server tell a browser that something happened?

| Technique | How | Pros | Cons |
|---|---|---|---|
| **Polling** | The client asks `/notifications` every N seconds | Very simple; works everywhere | Wasteful (most answers are empty); delay of up to N seconds; load grows with users |
| **Long polling** | The request stays open until there is news, then the client asks again | Lower delay, simple setup | Still one connection per client; reconnect cost; order of messages is awkward |
| **Server-Sent Events (SSE)** | One long HTTP response that streams `text/event-stream`; **server to client only** | Built into browsers (`EventSource`), **reconnects by itself**, `Last-Event-ID` lets you resume, works over plain HTTP/2, easy to proxy | One-way only; on HTTP/1.1 a browser allows only about 6 connections per origin (HTTP/2 removes this limit) |
| **WebSocket** | A two-way connection that starts as an HTTP upgrade | Two-way, low overhead, supports binary data | More infrastructure (sticky routing, heartbeats); you write the reconnect and resume logic yourself |

**For notifications, SSE is usually the best choice.** The data goes one way (server to client). The browser reconnects by itself. Resuming from `Last-Event-ID` is built in. Choose **WebSocket** when the client also sends messages often (chat, shared editing). Use polling as a **fallback** and for simple, low-volume cases.

## 4. Architecture

```text
 ┌───────────┐  events   ┌──────────────────┐   ┌─────────────────────┐
 │ Services  │──────────▶│  Event bus       │──▶│ Notification service │
 │ (orders,  │ (Kafka /  │  (Kafka/SNS/SQS) │   │  • resolve recipients│
 │ comments) │ SQS/SNS)  └──────────────────┘   │  • check preferences │
 └───────────┘                                   │  • dedupe / throttle │
                                                 │  • render templates  │
                                                 └───────────┬─────────┘
                                                             │ one message per (user, channel)
                    ┌───────────────┬─────────────┬──────────┴───────┐
                    ▼               ▼             ▼                  ▼
              In-app queue     Push queue    Email queue         SMS queue
                    │               │             │                  │
              store + realtime   FCM/APNs/     SES/SendGrid     Twilio/SNS
                    │            Web Push
                    ▼
        Realtime gateway (SSE/WebSocket) ──▶ connected browsers
```

Main ideas:

- **Use queues to separate the parts.** A queue is a waiting line for jobs. A producer publishes an *event* (`comment.created`) and moves on. It does not call email or SMS providers itself. So a slow provider cannot slow down checkout.
- **Use one queue per channel.** Then a failing email provider does not delay in-app messages. Each queue has its own scaling, rate limits and retry rules.
- **The notification service** turns one event into zero or more *notification jobs*. It finds the recipients (for example, the followers of a post). It applies **preferences** and **quiet hours**. It **removes duplicates**. It builds the message text (templates and translations).
- **Workers** (one group per channel) call the providers. They use **retries and backoff** (waiting longer after each failed try). They also save the delivery status.

## 5. Data model

```sql
CREATE TABLE notifications (
  id          uuid PRIMARY KEY,
  user_id     uuid        NOT NULL,
  type        text        NOT NULL,                  -- 'comment.reply', 'order.shipped'
  payload     jsonb       NOT NULL,                  -- ids and data needed to render; avoid copying large objects
  dedupe_key  text,                                  -- e.g. 'comment.reply:post42:user9'
  created_at  timestamptz NOT NULL DEFAULT now(),
  read_at     timestamptz,
  UNIQUE (user_id, dedupe_key)                       -- idempotency: the same event cannot create two rows
);
CREATE INDEX notif_user_created ON notifications (user_id, created_at DESC, id DESC);       -- the list, cursor-paginated
CREATE INDEX notif_user_unread  ON notifications (user_id) WHERE read_at IS NULL;            -- small partial index for unread

CREATE TABLE notification_preferences (
  user_id uuid, channel text, type text, enabled boolean NOT NULL DEFAULT true,
  quiet_start time, quiet_end time, PRIMARY KEY (user_id, channel, type)
);

CREATE TABLE push_subscriptions (user_id uuid, platform text, token text, last_seen timestamptz, PRIMARY KEY (user_id, token));
CREATE TABLE deliveries (notification_id uuid, channel text, status text, attempts int, provider_id text, error text, PRIMARY KEY (notification_id, channel));
```

- **The list:** show the bell list with cursor pagination (loading one page at a time, see [Lesson 03](/design-problems/lesson-3)).
- **Unread count:** `SELECT count(*) … WHERE user_id = $1 AND read_at IS NULL` is cheap for most users because of the small partial index (an index that only covers unread rows). If a user has a very large unread number, keep a counter per user in Redis. Update it when a notification is created or read. Cap the display at "99+".
- **Read state:** use `PATCH /notifications/{id}` with `{ read: true }`, and `POST /notifications/read-all`. These updates are idempotent (doing them twice gives the same result as doing them once).
- **Retention (how long to keep data):** delete or archive old rows. Split the table by month (partitions) and drop old partitions.

## 6. Delivering in-app notifications in real time

### The connection gateway

A group of **gateway** servers holds the open SSE or WebSocket connections. The notification system must be able to reach *the gateway that holds user 42's connection*.

```text
Browser ──SSE──▶ Gateway instance 3          Redis: user:42 → [gateway-3:conn-9, gateway-5:conn-2]
                         ▲
In-app worker ──publish "user:42" event──▶ Redis Pub/Sub (or NATS/Kafka) ──▶ gateways subscribed for connected users
```

- When a user connects, the gateway **checks who they are** (cookie or token). Then it **subscribes** to that user's channel. When the connection drops, it removes the subscription.
- To deliver a message, the worker **publishes** it to `user:{id}` on a pub/sub system (a system where publishers send messages and subscribers receive them). Any gateway that holds a connection for that user then pushes the message.
- **Keep business logic out of the gateway.** It should only pass messages along. Scale it by the number of connections. A well-tuned server can hold tens of thousands, because idle connections are cheap. Set the load balancer for long-lived connections. Send **heartbeats** (a small comment line every 15 to 30 seconds) so proxies do not close idle streams.

### SSE endpoint (server) and client

```ts
// Express SSE endpoint
app.get("/v1/notifications/stream", requireAuth, (req, res) => {
  res.set({ "Content-Type": "text/event-stream", "Cache-Control": "no-cache, no-transform", Connection: "keep-alive", "X-Accel-Buffering": "no" });
  res.flushHeaders();

  const lastId = req.header("Last-Event-ID");                       // the browser sends this on reconnect
  if (lastId) replayMissed(req.user.id, lastId).forEach((n) => send(n));   // catch up from the DB

  const send = (n: Notification) => res.write(`id: ${n.id}\nevent: notification\ndata: ${JSON.stringify(n)}\n\n`);
  const unsubscribe = bus.subscribe(`user:${req.user.id}`, send);
  const heartbeat = setInterval(() => res.write(": ping\n\n"), 25_000);

  req.on("close", () => { clearInterval(heartbeat); unsubscribe(); });
});
```

```ts
// Browser
const es = new EventSource("/v1/notifications/stream", { withCredentials: true });
es.addEventListener("notification", (e) => {
  const n = JSON.parse((e as MessageEvent).data);
  addToList(n); incrementBadge();
});
es.onerror = () => { /* the browser reconnects automatically and sends Last-Event-ID */ };
```

Every event has an **`id`**. When the client reconnects, it sends `Last-Event-ID`. Then the server **replays the messages the client missed** from the database. This is how you get reliability on top of a connection that can break. The database is the source of truth (the place we trust). The stream is only the fast path.

## 7. Reliability: at least once, plus idempotency

Queues deliver **at least once**. A worker may crash after it sends an email but before it confirms the message. Then the queue sends the same message again. To make the *user* feel it was sent exactly once, do these things:

- **Remove duplicates when you create the notification.** Give each notification a **`dedupe_key`** that is always the same for the same event (for example `order.shipped:{orderId}:{userId}`). The `UNIQUE (user_id, dedupe_key)` rule means that inserting the same event twice does nothing.
- **Make senders idempotent.** Save the delivery status for `(notification_id, channel)` *before or while* you send. Skip the send if the status is already `SENT`. Pass an **idempotency key** to providers that support it.
- **Retry temporary failures** with exponential backoff (the wait doubles each time) and jitter (a small random extra wait). Use a **dead-letter queue** (a separate queue for messages that keep failing) and set an alert on it ([Lesson 07](/design-problems/lesson-7)).
- **Respect provider limits.** Slow your workers down with token buckets ([Lesson 02](/design-problems/lesson-2)). Then a burst does not cause `429` errors (too many requests) from the email or push provider.
- **Order:** the order of notifications per user usually does not matter much. If it does, split the queue by `user_id`.
- **Provider failover:** keep a second email or SMS provider for critical messages.

## 8. User preferences, batching and fatigue

- **Preferences** by channel and type. Always allow critical messages (security alerts, receipts), whatever the user chose. Follow the law (unsubscribe links, SMS opt-in).
- **Quiet hours** use the user's own time zone. Delay push or email until the morning.
- **Batching and digests:** send "5 people liked your post" instead of five pushes. Group messages with the same key in a short time window (like a "debounce for notifications"). Hold the first one, collect the rest, then send one summary.
- **Frequency caps** limit messages per user per hour or day. **Priority levels** let urgent messages skip batching.
- **Channel choice and fallback:** send in-app first. If it is still unread after N minutes, send an email. Do not push to a device the user is using right now (check presence, meaning whether they are online).

## 9. Scenario: a user has 3 tabs open. How many connections do you hold?

The simple answer is **three SSE connections**, one per tab. Each one receives every notification. This is fine at small scale. With 100,000 users it means 300,000 connections. Your options:

1. **Accept it.** Idle connections are cheap and it is simple.
2. **Leader tab:** the tabs talk to each other with `BroadcastChannel` or a `SharedWorker`. Only one tab holds the connection and passes events to the other tabs.
3. **Use HTTP/2** to avoid the browser limit per origin. The six-connection limit on HTTP/1.1 is a real problem when several tabs use SSE.
4. Set a maximum number of connections per user on the gateway and close the oldest one.

Also keep the **read state on the server**. Then marking a notification as read in one tab updates the other tabs (through the same stream or a `BroadcastChannel`).

## 10. Scenario: broadcast to a million users

A broadcast creates a million rows and a million jobs ("fan-out" means one message spreading to many users). Ways to handle it:

- **Fan-out on write:** insert one row per user. Reads are fast, but the writes spike. Use **batched workers that go through users page by page**, and limit their speed to protect the database.
- **Fan-out on read:** store **one** broadcast record. Merge it into each user's feed when the user reads the feed. Writes are cheap. Reads need a merge and a read-state for each user.
- A **hybrid**: use fan-out on write for normal notifications. Use fan-out on read for large broadcasts and for "celebrity" accounts (accounts with huge numbers of followers).
- For push, use **topics** (FCM/APNs topic messaging) instead of sending to each device, where you can.
- **Throttle** and spread out the sends. This avoids a thundering herd (everyone opening the app at the same moment).

## 11. Offline users

- In-app notifications are saved. They show up on the next page load or reconnect (through the `Last-Event-ID` replay or the list endpoint).
- **Push notifications** (Web Push with service workers and VAPID, FCM, APNs) reach users who are not on the page. Take care of the **token lifecycle**. Remove invalid tokens when a provider returns an "unregistered" error. Refresh the token each time the app opens. Ask for permission at a good moment, not on the first page load.
- **Email and SMS** are slower fallbacks.

## 12. The frontend: the bell

- On load, fetch the **list** (one page) and the **unread count**. Subscribe to the stream. Merge new items into the list. Keep the badge in sync.
- **Optimistic read:** show the item as read in the UI right away, then send the request. If the request fails, undo the change.
- **Group and shorten** long lists. Show relative times ("5 min ago"). Link each notification to the thing it is about.
- **Accessibility:** use `aria-live="polite"` so screen readers announce new notifications (without being too noisy). Make the dropdown reachable with the keyboard. Manage focus.
- **Fallbacks:** if the stream keeps failing, switch to **polling with backoff**. Pause when the tab is hidden. Do not overload the server ([Debugging, Lesson 05](/debugging/lesson-5)).

## Observability

Observability means being able to see what the system is doing. Track these numbers: events in, notifications created, deliveries by channel and status, end-to-end latency (from event to delivered), queue depth and age, provider error and bounce rates, DLQ size, open connections, reconnect rate and unread backlog. Put the notification ID and dedupe key in every log line ([Backend, Lesson 05](/backend/lesson-5)).

## Common mistakes

1. **Calling providers directly** from business code. This ties checkout to an email API.
2. **No idempotency**, so retries send duplicates.
3. **One shared queue** for all channels, so one slow provider blocks the rest.
4. **Polling every second** from every client.
5. **Treating the stream as the source of truth**, with no replay on reconnect.
6. **Ignoring preferences, quiet hours and batching.** Users get tired of the messages and opt out.
7. **Fan-out per recipient inside the request** for broadcasts.
8. **Never removing dead push tokens** or old notifications.

## Interview questions

### Q1. SSE or WebSocket for notifications?

I usually pick SSE. The data goes one way, from server to client. Browsers reconnect by themselves and resume with `Last-Event-ID`. It runs over plain HTTP (and HTTP/2), so it is simple to run. I would use WebSocket if the client also had to send messages often. In both cases I save notifications and replay the missed ones. I keep polling as a fallback.

### Q2. How do you avoid sending duplicates?

I assume messages are delivered at least once, so I make the processing idempotent. First, each notification gets a dedupe key that is always the same for the same event, with a unique rule in the database. Second, I check the delivery record before I send. Third, I pass idempotency keys to providers. Fourth, retries with backoff are safe. So the user sees at most one notification, even if a job runs twice.

### Q3. Scenario: a user has 3 tabs open. How many connections do you hold?

By default, one per tab. To reduce the load, I pick a leader tab with `BroadcastChannel` or a `SharedWorker`. That tab holds the one connection and passes events to the others. I also use HTTP/2 to avoid the limit per origin, and I set a maximum per user on the gateway. The read state lives on the server, so all tabs stay in sync.

### Q4. How do you handle offline users?

I save every in-app notification. It appears on the next page load or reconnect, through the `Last-Event-ID` replay or the list endpoint. For users who are away from the page, I send push notifications with service workers, FCM or APNs. I use email or SMS as slower fallbacks, based on the user's preferences. I also keep the push tokens clean.

### Q5. How would you deliver a broadcast to 10 million users?

I would not do it inside the request. I put a broadcast job in a queue. Workers then fan it out in batches with rate limits. Another option is to store one broadcast record and merge it when the user reads the feed. A third option is push topics. A hybrid often works best. I slow down and spread out the sends to protect the database and the providers. I also keep the read state for each user.

### Q6. How do you store and display the unread count efficiently?

A partial index on the unread rows of each user makes the count cheap. For heavy users or hot paths, I keep a counter per user in Redis. I update it when a notification is created or read. I cap the display, for example at "99+". "Mark all as read" is one idempotent update.

### Q7. Why one queue per channel?

Each channel needs its own control. Each has different providers, rate limits, speed needs and ways to fail. A slow or failing email provider should not delay in-app messages. Each queue can also scale, retry and raise alerts on its own.

### Q8. How do you prevent notification fatigue?

I follow the user's preferences for each type and channel, and their quiet hours. I batch similar events into a digest. I set frequency caps and priorities (security alerts skip batching). I do not push to a device the user is using right now. I also watch opt-out and engagement numbers to tune the rules.

## Key takeaways

- **Events in, decisions in the middle, deliveries out.** Use queues to separate the parts, with one queue per channel.
- **SSE** (with `Last-Event-ID` replay) is a practical real-time channel for server-to-client notifications. The database is the source of truth.
- **At-least-once plus idempotency** (dedupe keys, delivery records, provider keys) gives the feeling of exactly-once. Use DLQs and backoff.
- Scale the **connection gateway** on its own. Connect it to the workers with pub/sub keyed by user.
- Plan for **preferences, batching, quiet hours**, broadcast fan-out and offline users.
