> **In one line:** four small designs that interviewers love because each one hides a precise trick: an **LRU cache** (hash map + doubly linked list for O(1)), **idempotent payments** (a key and a state machine), **retries** (exponential backoff with jitter, plus a dead-letter queue) and **feature flags** (stable hashing for percentage rollouts).

Each is short enough to write on a whiteboard, and each connects to production patterns you have used. Code samples below are runnable JavaScript.

## 1. An LRU cache

**Requirement:** a fixed-capacity cache. `get(key)` and `put(key, value)` both in **O(1)**. When full, evict the **least recently used** entry.

### The data structure

- A **hash map** gives O(1) lookup from key to node.
- A **doubly linked list** orders entries by recency: most recent at the head, least recent at the tail. Moving a node to the head or removing the tail is O(1) *because you already have the node and its neighbours*.

```text
map: key → node
list: head ⇄ (most recent) ⇄ … ⇄ (least recent) ⇄ tail

get(k):  find node via map → move to head → return value
put(k):  if exists: update, move to head
         else: create node at head; if size > capacity: remove tail, delete its key from the map
```

A singly linked list cannot remove an arbitrary node in O(1) (you need the previous pointer), which is why the list is **doubly** linked.

```js
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map();
    this.head = { prev: null, next: null };   // sentinels simplify edge cases
    this.tail = { prev: null, next: null };
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }
  _remove(node) { node.prev.next = node.next; node.next.prev = node.prev; }
  _addToFront(node) {
    node.next = this.head.next; node.prev = this.head;
    this.head.next.prev = node; this.head.next = node;
  }
  get(key) {
    const node = this.map.get(key);
    if (!node) return undefined;
    this._remove(node); this._addToFront(node);
    return node.value;
  }
  put(key, value) {
    let node = this.map.get(key);
    if (node) { node.value = value; this._remove(node); this._addToFront(node); return; }
    node = { key, value, prev: null, next: null };
    this.map.set(key, node);
    this._addToFront(node);
    if (this.map.size > this.capacity) {
      const lru = this.tail.prev;             // least recently used
      this._remove(lru);
      this.map.delete(lru.key);
    }
  }
}

const c = new LRUCache(2);
c.put("a", 1); c.put("b", 2);
console.log(c.get("a"));        // 1   (a is now most recent)
c.put("c", 3);                  // evicts b, the least recently used
console.log(c.get("b"));        // undefined
console.log(c.get("c"));        // 3
c.put("a", 10);                 // update moves a to the front
c.put("d", 4);                  // evicts c
console.log(c.get("c"), c.get("a"), c.get("d")); // undefined 10 4
```

### The JavaScript shortcut

A JavaScript `Map` **preserves insertion order**, so deleting and re-inserting a key moves it to "most recent":

```js
class TinyLRU {
  constructor(cap) { this.cap = cap; this.m = new Map(); }
  get(k) {
    if (!this.m.has(k)) return undefined;
    const v = this.m.get(k);
    this.m.delete(k); this.m.set(k, v);                  // refresh recency
    return v;
  }
  put(k, v) {
    this.m.delete(k); this.m.set(k, v);
    if (this.m.size > this.cap) this.m.delete(this.m.keys().next().value);   // oldest key
  }
}

const t = new TinyLRU(2);
t.put("a", 1); t.put("b", 2); t.get("a"); t.put("c", 3);
console.log([...t.m.keys()].join(","));                  // a,c
```

Mention both: the explicit linked list shows you know why it is O(1); the `Map` version is what you would ship in a small utility.

### Production considerations

- **Thread/async safety** (in Node a single thread makes this simple; in multi-threaded languages you need locks or sharding).
- **TTL** on top of LRU; **size by bytes**, not entries, when values vary.
- **Variants:** LFU (least frequently used), 2Q/ARC, TinyLFU (what many modern caches use) to resist scans that pollute LRU.
- Redis implements approximate LRU/LFU with the `maxmemory-policy` setting (`allkeys-lru`, `allkeys-lfu`), sampling a few keys rather than tracking exact order.

## 2. Idempotent payments

**Problem:** a network timeout leaves the client unsure whether the payment went through. Retrying must **not charge twice**. (Developed in [Backend, Lesson 02](/backend/lesson-2) and [Debugging, Lesson 05](/debugging/lesson-5).)

### Design

1. The client generates an **idempotency key** (a UUID) **once per payment attempt** and sends it as `Idempotency-Key`. Retries reuse the same key.
2. The server has a table with a **unique constraint** on `(account_id, key)`.
3. On each request: try to **insert** the key with status `IN_PROGRESS` and a **fingerprint of the request** (hash of the body).
   - **Insert succeeds** → this request owns the work: call the payment provider **with the same key**, store the result, mark `COMPLETED`.
   - **Key exists, COMPLETED, same fingerprint** → return the **stored response** (no new charge).
   - **Key exists, IN_PROGRESS** → return `409` (or wait briefly): another request is working on it.
   - **Key exists, different fingerprint** → return `422`: the key was reused for a different request.
4. Pass the key to the **payment provider** (Stripe and others support idempotency keys), so even if your server crashes between calling the provider and saving the result, a retry cannot create a second charge.
5. Expire keys after a window (for example 24 hours) and clean up.

```sql
CREATE TABLE idempotency_keys (
  account_id   uuid NOT NULL,
  key          text NOT NULL,
  request_hash text NOT NULL,
  status       text NOT NULL,              -- IN_PROGRESS | COMPLETED | FAILED
  response     jsonb,
  created_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (account_id, key)
);
```

### The payment as a state machine

```text
CREATED ──authorize──▶ AUTHORIZED ──capture──▶ CAPTURED ──refund──▶ REFUNDED
   │                        │
   └───fail───▶ FAILED      └──void──▶ VOIDED
```

Only legal transitions are allowed, enforced with a conditional update (`UPDATE payments SET status = 'CAPTURED' WHERE id = $1 AND status = 'AUTHORIZED'`, check the affected row count), so repeated or concurrent attempts cannot corrupt state. Record every transition in an **append-only ledger** and use **double-entry** bookkeeping for money movements. Use **minor units (integers)** for amounts.

### Reliability extras

- **Reconciliation job:** compare your records with the provider's daily settlement; fix mismatches.
- **Webhooks** from the provider are also at-least-once: dedupe them by event ID.
- **Timeouts:** treat a timeout as **unknown**, never as failure; resolve by querying the provider with the key.

## 3. Retries with exponential backoff and jitter

**Rule:** retry only **transient** failures (timeouts, connection resets, `429`, `502/503/504`) and only **idempotent** operations (or ones protected by an idempotency key). Never retry `400`/`401`/`403`/`422`.

### Why not retry immediately?

If a dependency is overloaded and 1,000 clients retry at once, you make it worse (a **retry storm**). **Exponential backoff** spaces retries out (1 s, 2 s, 4 s, 8 s…), and **jitter** (randomness) stops clients from retrying in lockstep (the **thundering herd**).

**Full jitter** (a widely used strategy):

```text
delay = random(0, min(cap, base × 2^attempt))
```

```js
function backoffDelay(attempt, { base = 100, cap = 5000 } = {}) {
  const ceiling = Math.min(cap, base * 2 ** attempt);
  return Math.random() * ceiling;              // full jitter: anywhere between 0 and the ceiling
}

async function retry(fn, { retries = 4, base = 100, cap = 5000, isRetryable = () => true } = {}) {
  let lastError;
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await fn(attempt);
    } catch (e) {
      lastError = e;
      if (attempt === retries || !isRetryable(e)) break;
      await new Promise((r) => setTimeout(r, backoffDelay(attempt, { base, cap })));
    }
  }
  throw lastError;
}

// Demo: fails twice, then succeeds
let calls = 0;
const result = await retry(async () => {
  calls++;
  if (calls < 3) throw Object.assign(new Error("503"), { transient: true });
  return "ok after " + calls + " calls";
}, { base: 5, cap: 20, isRetryable: (e) => e.transient });
console.log(result);                                          // ok after 3 calls

// The delay ceiling doubles but never exceeds the cap
const ceilings = [0, 1, 2, 3, 4, 5, 6].map((a) => Math.min(5000, 100 * 2 ** a));
console.log(ceilings.join(","));                              // 100,200,400,800,1600,3200,5000
```

Production practices:

- **Honour `Retry-After`** when the server provides it.
- **Cap total time** (a deadline), not only the attempt count; propagate the deadline downstream.
- **Retry budgets:** limit retries to a fraction of traffic (for example 10%) so retries cannot multiply load.
- **Circuit breaker:** after repeated failures, "open" the circuit and fail fast for a cool-down, then probe with a few requests ("half-open"). Prevents wasting resources on a dead dependency ([Backend, Lesson 04](/backend/lesson-4)).
- **Do not retry at every layer:** with 3 layers × 3 attempts you create 27 calls. Retry at one layer, usually the outermost caller that understands idempotency.
- **Log and measure** attempts, final outcomes and retry rate.

### Job queues with retries

For background jobs (emails, webhooks, image processing):

```text
queue ─▶ worker takes job (it becomes invisible for a "visibility timeout")
          ├─ success → delete the job
          └─ failure → job reappears after the timeout (or is re-enqueued with a delay = backoff)
                       after N attempts → move to the dead-letter queue (DLQ) + alert
```

- **At-least-once delivery**, so consumers must be **idempotent** (use the job ID as an idempotency key, or check state first).
- **Visibility timeout** longer than the job's typical run time, with heartbeats for long jobs.
- **Poison messages** (always failing) must not block the queue: the DLQ isolates them for inspection and replay.
- **Delayed retries:** native delay queues or scheduled messages; store `attempts` and `nextRunAt`.
- **Ordering and concurrency:** limit parallelism per tenant to avoid noisy neighbours.

## 4. Feature flags

**Requirement:** turn features on or off, or roll them out to a **percentage** of users, **without redeploying**, with **targeting** (internal staff first, then 5%, then 50%) and an instant **kill switch**.

### Flag types

- **Release flags:** hide unfinished or risky code; short-lived.
- **Experiment flags:** A/B tests with a consistent assignment.
- **Ops flags / kill switches:** disable a feature under load or incident.
- **Permission flags:** entitlements by plan or customer.

### Evaluation

```text
isEnabled(flagKey, user):
  1. flag disabled globally?            → false
  2. user in an explicit deny/allow list? → that answer
  3. rule matches (country = IN, plan = pro, internal staff…)? → rule's answer
  4. percentage rollout: bucket = hash(flagKey + userId) mod 100; enabled if bucket < percent
  5. otherwise default
```

The crucial detail is **stable hashing**: the same user must get the **same** answer every time (no flicker between enabled and disabled), and raising the percentage from 10 to 20 must **keep** the original 10% enabled (only add users). Hashing `flagKey + userId` achieves both, and including the flag key makes different flags roll out to **different** random slices, avoiding "the same unlucky 5% see every new feature".

```js
// A small, fast, deterministic 32-bit hash (FNV-1a)
function hash32(str) {
  let h = 0x811c9dc5;
  for (let i = 0; i < str.length; i++) {
    h ^= str.charCodeAt(i);
    h = Math.imul(h, 0x01000193) >>> 0;
  }
  return h >>> 0;
}

const bucket = (flag, userId) => hash32(`${flag}:${userId}`) % 100;

function isEnabled(flag, user) {
  if (!flag.enabled) return false;
  if (flag.denyUsers?.includes(user.id)) return false;
  if (flag.allowUsers?.includes(user.id)) return true;
  if (flag.rules?.some((r) => user[r.attr] === r.equals)) return true;
  return bucket(flag.key, user.id) < (flag.percent ?? 0);
}

const flag = { key: "new-checkout", enabled: true, percent: 10, allowUsers: ["staff-1"], rules: [{ attr: "plan", equals: "enterprise" }] };

// Stable: same user, same answer, every time
console.log(isEnabled(flag, { id: "u42" }) === isEnabled(flag, { id: "u42" }));   // true
// Monotonic: raising 10% → 25% never turns anyone OFF
const users = Array.from({ length: 5000 }, (_, i) => ({ id: "u" + i }));
const at10 = users.filter((u) => isEnabled({ ...flag, percent: 10 }, u));
const at25 = users.filter((u) => isEnabled({ ...flag, percent: 25 }, u));
console.log(at10.every((u) => at25.includes(u)));                                   // true
// Roughly the right size
console.log(Math.abs(at10.length / 5000 - 0.10) < 0.02);                            // true
console.log(isEnabled(flag, { id: "staff-1" }), isEnabled(flag, { id: "x", plan: "enterprise" })); // true true
```

### Architecture

```text
Admin UI ─▶ Flag service (DB + audit log) ─▶ publishes changes
                                                  │
        SDK in each app: loads all flag rules, caches in memory, subscribes to updates (SSE/polling),
        evaluates LOCALLY (no network call per check)
```

- **Evaluate locally** from cached rules: a flag check on every request must not add a network hop.
- **Safe defaults:** if the flag service is unreachable, use the last known rules, or a hard-coded default per flag (usually "off" for new features, "on" for kill switches protecting the old behaviour).
- **Consistency across frontend and backend:** evaluate on the server and send resolved values to the client (so the client does not need rules and cannot be tampered with), or use an SDK on both with the same hash.
- **Audit log** of who changed what and when; **permissions** for who can flip production flags.
- **Flag hygiene:** every release flag has an **owner and an expiry**; remove the flag and dead code after rollout (stale flags are tech debt and a source of bugs); test both branches.
- **Rollout practice:** staff → 1% → 10% → 50% → 100% while watching error rates and latency, and keep the kill switch ready.
- **Do not use flags for authorization**; entitlements and security belong in your access control logic.

## Common mistakes

1. **LRU with a singly linked list** (O(n) removals) or without moving on `get`.
2. **Idempotency keys generated per click or per retry**, not per attempt.
3. **Treating a payment timeout as a failure** and retrying with a new key.
4. **Retrying immediately with no backoff or jitter**, and retrying non-idempotent calls.
5. **Retries at every layer** multiplying load.
6. **No DLQ**, so a poison message blocks the queue forever.
7. **Random (not hashed) percentage rollouts** that flicker per request.
8. **Flag checks over the network on every request**, and flags that never get cleaned up.

## Interview questions

### Q1. Implement an LRU cache with O(1) operations.

Use a hash map from key to node plus a doubly linked list ordered by recency. `get` moves the node to the front; `put` inserts or updates at the front and, if over capacity, removes the tail node and its map entry. Because the map gives the node directly and the list is doubly linked, every operation is O(1). In JavaScript a `Map` that deletes and reinserts keys can serve as a compact implementation.

### Q2. Make a payment endpoint idempotent.

Require a client-generated idempotency key per attempt, store it with a unique constraint and a request fingerprint, return the stored response for repeats, reject key reuse with different content, serialise concurrent duplicates with the constraint, and pass the key to the payment provider. Model payments as a state machine with conditional updates, and treat timeouts as unknown, resolving via the provider.

### Q3. Design retries with exponential backoff and jitter.

Retry only transient failures of idempotent operations; compute each delay as a random value between zero and `min(cap, base × 2^attempt)` (full jitter) to avoid synchronised retries; honour `Retry-After`; cap attempts and total time; add a retry budget and circuit breaker; retry at one layer only; send exhausted jobs to a dead-letter queue.

### Q4. How would you implement feature flags safely?

Store flag rules in a service with audit and permissions, distribute them to SDKs that cache and evaluate locally, use a stable hash of flag key plus user ID for percentage rollouts so users do not flicker and increases only add users, provide targeting rules and a kill switch, use safe defaults when the service is unavailable, evaluate server-side where possible and clean up flags after rollout.

### Q5. Why does a percentage rollout hash the flag key together with the user ID?

Hashing only the user ID would put the same users in the early percentage buckets of every flag. Combining the flag key makes assignment independent across flags, while remaining deterministic per user and flag so the same user always gets the same result.

### Q6. What is the thundering herd and how does jitter help?

When many clients fail at the same time and retry on the same schedule, their retries arrive together and overload the recovering service again. Randomising the delay spreads the retries over time so load ramps up gently.

### Q7. How do you stop a poison message from blocking a queue?

Limit the number of delivery attempts; after the maximum, move the message to a dead-letter queue and alert, so the main queue continues. Operators inspect and replay or discard the message once fixed. Consumers must also be idempotent because delivery is at least once.

### Q8. LRU vs LFU?

LRU evicts the entry unused for the longest time, favouring recency; LFU evicts the least frequently used, favouring popularity. LRU is simple and good for temporal locality but can be polluted by one-time scans; LFU resists scans but can keep stale popular items. Modern caches often combine both ideas (TinyLFU, ARC).

### Q9. Scenario: your retry logic amplified a dependency outage into a full outage. How do you fix it?

Retries at several layers multiplied the load. Retry in one layer only, use exponential backoff with full jitter, respect `Retry-After`, cap attempts and total time, add a retry budget (for example at most 10% of traffic), and put a circuit breaker in front of the dependency so callers fail fast. Make non-idempotent calls safe with idempotency keys before retrying them.

### Q10. Scenario: after a nightly batch job scanned the whole dataset, your LRU cache hit rate collapsed. What happened?

A scan pollution problem: one pass over many keys evicted the genuinely hot entries. Mitigate by bypassing the cache for batch reads, using an admission policy or a scan-resistant algorithm (TinyLFU, ARC, 2Q), partitioning the cache, or warming it after the job. Monitor hit ratio so a drop is noticed.

## Key takeaways

- **LRU:** hash map + doubly linked list = O(1) get and put; in JS a `Map` can do it with delete-and-reinsert.
- **Idempotent payments:** key per attempt, unique constraint, fingerprint, stored response, key passed to the provider, state machine, timeouts are "unknown".
- **Retries:** transient and idempotent only, **exponential backoff with full jitter**, deadlines, budgets, circuit breakers, DLQs, idempotent consumers.
- **Feature flags:** local evaluation, **stable hashing** of flag key + user for percentage rollouts, targeting, kill switch, safe defaults, audit and cleanup.
