> **In one line:** a remote is just another copy of your repository, usually on GitHub. You send commits with `push`, get new ones with `fetch` (safe) or `pull` (fetch plus merge), and on GitHub you ask for your work to be joined through a pull request that others review.

So far everything lived on one computer. Real work is shared. This lesson covers the Git side (clone, remote, fetch, pull, push, upstream tracking, forks) with real runs, and then the GitHub side (the pull request flow, writing a good description and reviewing), which I describe from the GitHub docs but did not run.

The review part is about code and the Git tools. For the human side of reviewing (tone, size, what to look for), read [Team Lead Lesson 3](/team-lead/lesson-3).

> [!note] **What I ran / checked.** Git commands ran with **git version 2.43.0** on Linux. **GitHub itself was not reachable for pushes**, so I used a **local bare repository** as the "remote". A bare repository is a repository with no working files, only the history, and it is what a server keeps. `git push` and `git fetch` to a folder path behave like they do to a GitHub URL, but everything that is special to GitHub (pull requests, reviews, forks as a button, branch protection, Actions) was **not run**. I describe those from the `github/docs` repository (and from general knowledge for details I did not find there, such as the "Compare & pull request" banner and the `Fixes #123` keyword): `content/communities/using-templates-to-encourage-useful-issues-and-pull-requests/creating-a-pull-request-template-for-your-repository.md`, `content/pull-requests/reference/pull-request-merges.md` and `content/repositories/.../about-code-owners.md`. For the fork simulation I used two more local bare repositories. For repeatable output I used the names "Ada Lovelace" and "Bob" and fixed dates; your hashes will differ.

## Words used in this lesson

- **A remote** is another copy of the repository, kept on a server or in another folder. Its short name is often `origin`.
- **`origin`** is the default name Git gives to the place you cloned from.
- **To clone** is to copy a whole repository, with all history, and set up `origin`.
- **A remote-tracking branch** is your local, read-only note of where a remote branch was the last time you talked to it. It looks like `origin/main`.
- **Upstream (tracking) branch** is the remote branch that your local branch is linked to. It decides what a plain `git push` and `git pull` do.
- **To fetch** is to download new commits and update `origin/*`. Your own branches and files do not change.
- **To pull** is `fetch` followed by a merge (or rebase) into your current branch.
- **To push** is to send your commits to a remote branch.
- **A fork** is your own copy of someone else's repository on GitHub.
- **A pull request (PR)** is a request on GitHub to merge one branch into another, with a page for discussion and review.
- **A review** is when another person reads your change and approves it or asks for changes.

## Remotes

A remote is only a name plus a URL. I start with a bare repository as the "server" and a normal repository for Ada:

```bash
git -c init.defaultBranch=main init --bare -q origin.git
git -c init.defaultBranch=main init -q ada && cd ada
echo "# Notes" > README.md && git add . && git commit -qm "Add README"
git remote -v
```

(The `git remote -v` printed nothing: a new repository has no remotes.) Add one and push:

```bash
git remote add origin ../origin.git
git remote -v
git push origin main
git push -u origin main
git branch -vv
```

```text
origin	../origin.git (fetch)
origin	../origin.git (push)
To ../origin.git
 * [new branch]      main -> main
Everything up-to-date
branch 'main' set up to track 'origin/main'.
* main 80dc38d [origin/main] Add README
```

With GitHub the URL would look like `https://github.com/you/repo.git` or `git@github.com:you/repo.git` (the second form uses an SSH key). Everything else is the same. The `-u` (long form `--set-upstream`) tells Git to link local `main` to `origin/main`. `git branch -vv` shows the link in brackets. The link is stored in the repository config:

```text
[remote "origin"]
	url = ../origin.git
	fetch = +refs/heads/*:refs/remotes/origin/*
[branch "main"]
	remote = origin
	merge = refs/heads/main
```

### Clone

Bob joins the project. He does not set up a remote by hand. `git clone` copies everything and sets up `origin`:

```bash
git clone origin.git bob
cd bob
git branch -a
```

```text
Cloning into 'bob'...
done.
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/main
```

Bob has a local `main` and a remote-tracking branch `remotes/origin/main`, and `main` is already linked to it. Clone also sets `origin/HEAD`, the remote's default branch.

## Fetch, pull and push

Bob makes a commit and pushes. Because `main` has an upstream, plain `git push` is enough:

```bash
echo "bob line" >> README.md && git commit -qam "Bob adds a line"
git push
```

```text
To .../origin.git
   80dc38d..322fd66  main -> main
```

Ada does not know yet. Her `origin/main` is only a note from her last talk with the server:

```bash
git status
git fetch
git status
```

```text
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
From ../origin
   80dc38d..322fd66  main       -> origin/main
On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

nothing to commit, working tree clean
```

The first `status` says "up to date" because Git never contacts the server by itself. After `git fetch` it knows Bob's commit exists. **Fetch is safe**: it only updates `origin/*`. It never touches her files or her branch. She can look before she decides:

```bash
git log --oneline --all --graph --decorate
git diff main origin/main --stat
git merge origin/main
```

```text
* 322fd66 (origin/main) Bob adds a line
* 80dc38d (HEAD -> main) Add README
 README.md | 1 +
 1 file changed, 1 insertion(+)
Updating 80dc38d..322fd66
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
```

That is exactly what `git pull` does, in one step:

```text
git pull  =  git fetch  +  git merge origin/main   (or a rebase, if you configure it)
```

```explainer
git-github-3-fetch-and-merge
```

| Command | Changes my branch? | Safe to run any time? |
|---|---|---|
| `git fetch` | No (only `origin/*`) | Yes |
| `git pull` | Yes (merge or rebase) | Mostly, but may stop on a conflict |
| `git push` | No (changes the remote) | Rejected if the remote moved |

### The rejected push

Now both edit and Bob pushes first. Ada has an unpushed commit and tries to push:

```text
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '../origin.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
```

This is not a bug. It protects Bob's work: Git only lets a push **fast-forward** the remote branch. The fix is to bring Bob's commit into Ada's history first. Then I ran `git pull`, and this Git version stopped:

```text
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
fatal: Need to specify how to reconcile divergent branches.
```

The histories have **diverged** (each side has a commit the other lacks), so Git asks which strategy you want. I chose merge:

```bash
git config pull.rebase false
git pull --no-edit
git push
git log --oneline --graph
```

```text
Merge made by the 'ort' strategy.
 bob.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 bob.txt
To ../origin.git
   25f3b1d..5216c83  main -> main
*   5216c83 Merge branch 'main' of ../origin
|\
| * 25f3b1d Bob adds bob.txt
* | ab8a3f9 Ada line 2
|/
* 322fd66 Bob adds a line
* 80dc38d Add README
```

(I removed trailing spaces from the graph lines.) Rebase (`pull.rebase true`) would give a straight line instead of a merge commit. Many teams prefer that; lesson 5 compares them. If you want to be safe, `git pull --ff-only` refuses to do anything except a fast-forward, so you can never get a surprise merge.

### New branches and upstream tracking

```bash
git switch -c feature/greeting
echo hi > greet.txt && git add greet.txt && git commit -qm "Add greeting"
git push
```

```text
fatal: The current branch feature/greeting has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin feature/greeting
```

Git does not guess where a new branch should go. Do what it says once:

```bash
git push -u origin feature/greeting
git branch -vv
```

```text
 * [new branch]      feature/greeting -> feature/greeting
branch 'feature/greeting' set up to track 'origin/feature/greeting'.
* feature/greeting 5ad154f [origin/feature/greeting] Add greeting
  main             5216c83 [origin/main] Merge branch 'main' of ../origin
```

From now on, plain `git push` and `git pull` on this branch know where to go. Git also has a setting `push.autoSetupRemote` that does this for you the first time.

To delete the remote branch (for example after the PR is merged):

```bash
git push origin --delete feature/greeting
git fetch --prune
```

```text
 - [deleted]         feature/greeting
```

`git fetch --prune` also removes your stale `origin/*` notes for branches that no longer exist on the server.

## Forks

On GitHub you often cannot push to a project (you are not a member). So you make a **fork**: your own copy under your account. You push to your fork, then open a PR from the fork to the original ("upstream") repository. You keep two remotes:

- `origin`: your fork (you can push)
- `upstream`: the original project (you only fetch)

I simulated this with two bare repositories on disk (`upstream.git` for the project, `fork.git` for my fork). GitHub's Fork button did not run here.

```bash
git clone -q fork.git mine && cd mine
git remote add upstream ../upstream.git
git remote -v
```

```text
origin	.../fork.git (fetch)
origin	.../fork.git (push)
upstream	../upstream.git (fetch)
upstream	../upstream.git (push)
```

The maintainers then commit to the project. I bring that into my fork:

```bash
git fetch upstream
git merge --ff-only upstream/main
git push origin main
```

```text
From ../upstream
 * [new branch]      main       -> upstream/main
 M.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 M.txt
   5216c83..7b62051  main -> main
```

(I show only the last lines of the merge and push output.) That is the standard way to keep a fork current: fetch from `upstream`, fast-forward your `main`, push it to `origin`. For your own work, make a branch from the updated `main`. Never commit on your fork's `main`, or it will drift from the project.

## The pull request flow on GitHub

Not run. This is from the GitHub docs and from how teams work.

1. **Branch.** From an up-to-date `main`, make a branch with a clear name: `git switch -c fix/cart-rounding`.
2. **Commit** in small steps (lesson 1).
3. **Push** the branch: `git push -u origin fix/cart-rounding`. GitHub shows a banner offering "Compare & pull request".
4. **Open the PR.** Choose the *base* branch (where the change goes, usually `main`) and the *compare* branch (your branch). Write the title and description. You can open it as a **draft** if it is not ready; code owners are not asked to review a draft until you mark it ready.
5. **Automatic checks run** (tests, lint) if the repository has them (lesson 5).
6. **Review.** People comment on lines, ask for changes or approve.
7. **Update.** You push more commits to the same branch and the PR updates by itself.
8. **Merge** with one of three methods, then delete the branch.

The GitHub docs describe the three merge methods like this:

| Method | Result | Choose when |
|---|---|---|
| Merge commit | Keeps every commit and adds a merge commit | History of the branch is meaningful |
| Squash and merge | All commits become one commit on the base branch | One logical change, lots of "fix typo" commits |
| Rebase and merge | Each commit is added without a merge commit; linear history | Commits are already clean |

The same docs warn that squash merging works best for short-lived branches: if you keep working on the same branch after a squash merge, later PRs can contain commits that were already squashed, and conflicts become likelier. That is one more reason to delete the branch after merging and start the next change from a fresh `main`.

### A PR from a fork

The steps are the same, except the compare side is `your-name:branch` on your fork and the base is the project's `main`. Usually there is a checkbox "Allow edits by maintainers". A repository can have a **PR template** (`.github/pull_request_template.md`) that pre-fills the description. The GitHub docs list the places it can live: the root, `docs/` or `.github/`; it is used when it is on the default branch.

## Writing a good PR description

The reviewer has not been inside your head for three days. Give them the context. A simple template:

```text
## What
Round discount amounts to two decimals on the order page.

## Why
Orders showed 89.99999999999999 (see issue #123).

## How
round() on the final amount only, so rates still add up exactly.

## How I tested it
- New unit test for 0%, 10% and 33% discounts
- Checked the order page by hand with a 3-item cart

## Notes for reviewers
- Please look at cart.py:discount(); the rest is test code.
- Not in this PR: changing the tax rounding (separate ticket).
```

Good habits:

- **Small.** A PR you can review in 15 minutes gets a real review. A 1,500-line PR gets "looks good".
- **One topic.** If the title needs "and", split it.
- **Say what you did not do** and what you want help with.
- **Link the issue.** Writing `Fixes #123` in the description closes the issue when the PR merges into the default branch.
- **Show it** (screenshot, before and after, or the output of a command) if it changes something visible.
- **Self-review first.** Read your own diff in the PR page before asking anyone. You will find leftovers.
- **Keep CI green.** Do not ask for review on a red build unless you say why.

## Reviewing a PR

When you are the reviewer:

1. **Read the description first**, then the tests, then the code. Tests tell you what the author thinks the code should do.
2. **Check the big things first:** is this the right change? Does it break something? Are there missing tests, security risks, or data changes?
3. **Be clear which comments block.** Many teams mark small ideas as `nit:` (optional).
4. **Ask questions** instead of giving orders: "What happens when the list is empty?"
5. **Run it** when the change is risky. `git fetch origin pull/123/head:pr-123` (GitHub offers this special ref; I did not run it) or check out the branch.
6. **Decide:** *Comment* (no verdict), *Approve*, or *Request changes*.

When you are the author: answer every comment (fix it, or explain why not), push the fix, then mark the conversation resolved. Do not take comments personally; they are about the code. For tone, size and speed of reviews on a team, see [Team Lead Lesson 3](/team-lead/lesson-3).

> [!warn] **Never put secrets in a PR.** Even if you remove them in a later commit, they stay in the branch history and in the PR page. If it happens, rotate the secret first.

## Try it

Use two folders on your own computer. No GitHub account needed.

1. Make a bare repository with `git -c init.defaultBranch=main init --bare shared.git`. Clone it twice into `alice` and `bob`. (Git will warn that you cloned an empty repository. That is fine.)
2. In `alice`, create a commit and push it with `git push -u origin main`. If you get an error about the branch name, check `git branch` and use that name.
3. In `bob`, run `git pull`. What happens?
4. Now both of them commit different files. Bob pushes first. Alice pushes second. What error does Alice get and how does she fix it?
5. Alice runs `git fetch` instead of `git pull`. Use `git log --oneline --all --graph` to see the difference between `main` and `origin/main`.
6. Make a branch `feature/x` in Alice's clone. Push it without `-u`. Read the error and fix it.
7. Write a PR description for a change you made, using the What/Why/How/Testing template.

### Answers

1. `git clone shared.git alice` and `git clone shared.git bob`. The warning "You appear to have cloned an empty repository" is expected.
2. After the push, `git branch -vv` shows `[origin/main]`.
3. Bob gets Alice's commit. If his own branch is empty (nothing committed), pull just creates his `main` from the remote.
4. Alice's push is rejected with `! [rejected] main -> main (fetch first)`. She runs `git pull` (merge, rebase or `--ff-only`, depending on config; she may be asked to choose), tests the result, then `git push`.
5. `origin/main` is ahead (or has a different commit) while `main` stays where it was, and her files did not change.
6. `fatal: The current branch feature/x has no upstream branch.` and Git prints `git push --set-upstream origin feature/x`. Use that, or `git push -u origin feature/x`.
7. Example: see the template above. A good answer has all four parts and states what the change does **not** cover.

## Interview questions

### Q1. What is the difference between `git fetch` and `git pull`? (Must know)

`fetch` downloads new commits and updates my remote-tracking branches like `origin/main`. It never changes my own branches or files, so it is always safe. `pull` is `fetch` followed by a merge (or a rebase if I configure that) into the current branch, so it can change my files and stop on a conflict. I often fetch first, look at `git log main..origin/main`, and then decide.

### Q2. Why was my push rejected? (Must know)

The remote branch has commits that I do not have. Git only allows a push that fast-forwards the remote, so nobody's work gets lost silently. I fetch, bring the remote work into my branch (merge or rebase), run the tests, and push again. I do not use `--force` to "fix" it, because that would delete my teammate's commits from the remote branch.

### Q3. What is `origin`? What is `origin/main`? (Must know)

`origin` is the default name of the remote I cloned from. `origin/main` is a remote-tracking branch: my local record of where `main` was on `origin` at the last fetch. It is read-only, and it only moves when I fetch, pull or push. That is why `git status` can say "up to date" while the server has something new.

### Q4. What does `git push -u` do? (Must know)

It pushes the branch and also sets the upstream, so my local branch is linked to the remote one. After that, `git push` and `git pull` work without arguments, and `git status` can tell me how many commits I am ahead or behind. I can check with `git branch -vv`.

### Q5. What is a fork, and how is it different from a clone and a branch? (Must know)

A clone is a copy on my computer. A branch is a label inside one repository. A fork is a GitHub feature: a full copy of a repository under my account on the server. I use a fork when I cannot push to the original. I clone my fork (`origin`), add the original as `upstream`, push branches to my fork and open a PR from the fork to the original.

### Q6. How do you keep a fork up to date? (Senior signal)

`git fetch upstream`, then on `main` `git merge --ff-only upstream/main` (or rebase), then `git push origin main`. I never commit directly on my fork's `main`; I make a branch for each change. If `--ff-only` fails, it means I committed on `main` by accident, and I need to move that work to a branch first.

### Q7. What makes a good pull request? (Must know)

It is small, on one topic, with a title and description that explain what, why and how I tested it. It links the issue. The checks are green and I reviewed my own diff first. It says what is not included. The aim is that a reviewer can understand it in about 15 minutes without asking me for context.

**Follow-up: "What do you do with a 2,000-line change?"** I split it into steps that each work alone (for example, refactor first, then the feature) and open them in order, or I stack small PRs. If the change is truly big, I talk to the reviewer first and add a design note.

### Q8. How do you review a pull request? (Senior signal)

I read the description and the tests first. Then I check the design and risk (is this the right change, what can break, security, data), then the details. I separate blocking comments from optional ones (`nit:`), ask questions instead of ordering, and run the branch when the change is risky. I always say something good as well; reviews are about the code, not the person. For team practice I follow my team's agreed rules.

### Q9. Squash, merge commit or rebase and merge? Which would you pick? (Senior signal)

It depends on what the team wants from history. Squash gives one commit per PR, a clean `main` and easy reverts, at the cost of losing the small steps. A merge commit keeps all steps and a record of the branch. Rebase and merge gives a linear history with the original commits, and it only makes sense if the commits are already clean. I would ask the team, and I would choose one and use it everywhere. For short-lived branches I like squash.

### Q10. A teammate says "my branch is behind origin". What does that mean and what do you do? (Trap)

It means `origin/<branch>` (as of their last fetch) has commits that their local branch lacks. They should run `git fetch` first because the information can be old, then `git pull` (or `git pull --rebase`). If they also have local commits, the branch is *diverged*, not just behind, and they need to merge or rebase. They must not force push to "fix" it.

## Key takeaways

- A remote is a name plus a URL. `git clone` sets up `origin`. `git remote -v` lists them.
- `origin/main` is your local note of the remote. `git fetch` updates the note and is always safe. `git pull` is fetch plus merge or rebase.
- A rejected push means the remote has work you lack. Integrate first, then push. Do not force.
- `git push -u origin branch` links a branch to its upstream once.
- Fork when you cannot push to the project. Keep `origin` (fork) and `upstream` (project). Fetch from `upstream` to stay current.
- A good PR is small, has one topic, explains what/why/how tested, and links the issue.
- Reviews are about the code. Say which comments block, and ask questions.
- GitHub features (PRs, forks, reviews) are described here from the docs; I ran only the Git part against local bare repositories.
