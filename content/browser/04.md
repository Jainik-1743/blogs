> **In one line:** CORS is a **browser** rule that lets a server say "yes, that other origin may *read* my response." It protects users from malicious pages. It is not a firewall for your API, and it does not stop requests from being **sent**.

CORS errors are among the most common frontend problems and the most commonly misunderstood. Once you know the two ideas underneath (the same-origin policy, and the preflight), every error message becomes readable.

## Origins and the same-origin policy

An **origin** is the combination of **scheme + host + port**.

| URL | Same origin as `https://app.example.com`? |
|---|---|
| `https://app.example.com/page` | Yes (path does not matter) |
| `http://app.example.com` | No (scheme differs) |
| `https://api.example.com` | No (host differs, even as a subdomain) |
| `https://app.example.com:8443` | No (port differs) |

The **same-origin policy (SOP)** says: a page may *send* requests to other origins in many cases, but scripts may **not read the responses** unless the other server opts in. Without it, any website you visit could use your logged-in session to read your email from another tab.

**CORS (Cross-Origin Resource Sharing)** is the opt-in mechanism: the response carries headers that tell the browser which origins are allowed to read it.

> [!warn] Two facts to say out loud in an interview. (1) CORS is enforced by the **browser**; `curl`, Postman and server-to-server calls ignore it. (2) For many requests, the browser **sends** the request first and only **hides the response** from your script if the headers do not allow it. The side effect on the server already happened.

## Simple requests

A request is "simple" (no preflight) if **all** of these hold:

- Method is `GET`, `HEAD` or `POST`.
- Only CORS-safelisted headers are set manually (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`, and a few others).
- `Content-Type` is one of `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`.

The browser sends it directly with an `Origin` header, and checks the response:

```http
GET /api/products HTTP/2
Origin: https://app.example.com

HTTP/2 200
Access-Control-Allow-Origin: https://app.example.com
```

If `Access-Control-Allow-Origin` matches the origin (or is `*` for non-credentialed requests), JavaScript may read the body. Otherwise the browser blocks access and logs a CORS error.

## Preflighted requests

Anything else is **preflighted**: before the real request, the browser sends an `OPTIONS` request asking permission.

Common triggers:

- Methods like `PUT`, `PATCH` or `DELETE`
- `Content-Type: application/json` (JSON is **not** in the simple list, so almost every modern API call is preflighted)
- Custom headers such as `Authorization` or `X-Request-Id`

```http
OPTIONS /api/orders HTTP/2
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
```

The server must answer with permission:

```http
HTTP/2 204
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 600
Vary: Origin
```

Only if that check passes does the browser send the real `POST`. The result is cached for `Access-Control-Max-Age` seconds (browsers cap it, for example a couple of hours in Chrome), so you are not paying an extra round trip every time. A missing or low `Max-Age` doubles your request count.

The sequence:

```text
Browser                          API server
  │── OPTIONS (preflight) ───────────▶│
  │◀─ 204 + Allow-* headers ──────────│   ← permission check, no cookies, no body
  │── POST /orders (real request) ───▶│
  │◀─ 201 + Allow-Origin ─────────────│   ← the response must ALSO carry Allow-Origin
```

## Credentials

By default, cross-origin `fetch` does **not** send cookies or HTTP auth. You opt in on the client, and the server must opt in too:

```js
fetch("https://api.example.com/me", { credentials: "include" });
```

```http
Access-Control-Allow-Origin: https://app.example.com   ← must be the exact origin
Access-Control-Allow-Credentials: true
```

Rules interviewers love:

- With credentials, `Access-Control-Allow-Origin: *` is **not allowed**. You must echo a specific origin.
- The same goes for `Allow-Headers: *` and `Allow-Methods: *`: wildcards do not count for credentialed requests.
- When you echo the request's origin dynamically, add `Vary: Origin`, or a cache may serve one origin's response to another.
- The cookie itself must still be sendable: a cross-site cookie needs `SameSite=None; Secure`, and third-party cookie restrictions may block it ([Lesson 03](/browser/lesson-3)).

## Reading response headers

By default, JavaScript can read only a short list of "safe" response headers. To expose others (a `Location`, a pagination `X-Total-Count`, a `RateLimit-Remaining`), the server must list them:

```http
Access-Control-Expose-Headers: X-Total-Count, Location
```

## A correct server setup (Express)

```ts
import cors from "cors";

const allowed = new Set(["https://app.example.com", "https://staging.example.com"]);

app.use(
  cors({
    origin(origin, cb) {
      // no Origin header = non-browser client (curl, server-to-server): CORS does not apply
      if (!origin || allowed.has(origin)) return cb(null, true);
      cb(new Error("Origin not allowed"));
    },
    credentials: true,
    methods: ["GET", "POST", "PUT", "PATCH", "DELETE"],
    allowedHeaders: ["Content-Type", "Authorization"],
    exposedHeaders: ["X-Total-Count"],
    maxAge: 600,
  }),
);
```

Use an **allow-list**, never reflect any origin blindly with credentials enabled: that is equivalent to disabling the protection.

## Why "it works in Postman but not in the browser"

Postman, `curl` and your backend are not browsers. They send the request and show you the response; there is no same-origin policy to enforce. The browser, on the other hand, checks the CORS headers *after* the response arrives and refuses to give the response to your script. The fix is on the **server's response headers**, not in your frontend code.

## Debugging checklist

1. **Read the exact console message.** It usually names the missing header or the failed rule.
2. **Open the Network tab.** Look at the `OPTIONS` request first: status, headers. Then the real request.
3. **Is the preflight failing?** It must return a **2xx** (commonly 204) with the right `Allow-*` headers. If your auth middleware runs before CORS and rejects the unauthenticated `OPTIONS` with `401`, CORS fails. **Put CORS middleware first.** Preflights carry no cookies or Authorization header.
4. **Does the *error response* lack CORS headers?** A `500` or a proxy `502` generated outside your app has no `Allow-Origin`, so the browser reports a **CORS error** even though the real problem is a server crash. Check the server logs.
5. **Redirects:** a preflight must not be redirected; a redirect on the real request to a different origin also needs CORS headers.
6. **Credentials:** `include` on the client and a specific origin plus `Allow-Credentials: true` on the server.
7. **Different in production than locally?** Check the production origin is in the allow-list (including `www`, scheme and port), and that a CDN, load balancer or API gateway is not stripping or caching the headers (add `Vary: Origin`).

## Is CORS a security control for your API?

**No.** An attacker's own script, `curl` or a server ignores CORS entirely. CORS protects **users' browsers** from other sites reading authenticated responses. Your API still needs real authentication and authorization on every request. Also, CORS is **not** CSRF protection: a simple cross-site `POST` still arrives with cookies attached ([Lesson 03](/browser/lesson-3)).

## Common mistakes

1. **`Access-Control-Allow-Origin: *` together with credentials.** Browsers reject it.
2. **Reflecting the `Origin` header for everything** while allowing credentials, which lets any site read user data.
3. **CORS middleware registered after auth**, so preflights get `401`.
4. **"Fixing" CORS in the frontend** (setting headers on the request, or a `no-cors` mode that returns an unreadable opaque response).
5. **Forgetting `Vary: Origin`** when the response differs per origin.
6. **No `Max-Age`**, so every call is preceded by a preflight.
7. **Believing CORS blocks the request.** It blocks *reading the response*; the server may already have acted.

## Interview questions

### Q1. What is an origin?

The tuple of scheme, host and port. `https://app.example.com` and `https://api.example.com` are different origins, as are `http` vs `https` and different ports.

### Q2. When does the browser send an OPTIONS preflight?

When a cross-origin request is not "simple": methods other than `GET`, `HEAD` or `POST`, custom headers like `Authorization`, or a `Content-Type` other than the three form types (so `application/json` triggers it). The preflight asks the server whether the real method and headers are allowed.

### Q3. Why does the request work in Postman but fail in the browser?

CORS is enforced only by browsers. Postman has no same-origin policy. The browser blocks your script from reading the response because the server did not send the right `Access-Control-Allow-*` headers. Fix the server's headers.

### Q4. Scenario: cookies aren't sent on a cross-origin fetch. List three causes.

1. The client did not set `credentials: "include"`.
2. The server did not send `Access-Control-Allow-Credentials: true`, or used `*` instead of the exact origin.
3. The cookie's `SameSite` is `Lax`/`Strict`, or `None` without `Secure`, so the browser will not send it cross-site.
4. Bonus: third-party cookie blocking, a `Domain`/`Path` mismatch, or the cookie was never set because `Set-Cookie` was ignored in a CORS response without credentials.

### Q5. Is CORS a security control for your API?

No. It protects users' browsers from malicious sites reading authenticated responses. Anyone can call your API directly with a script or `curl`, so you still need authentication, authorization, validation and rate limiting server-side.

### Q6. Why can't you combine `Allow-Origin: *` with credentials?

Because a wildcard plus cookies would let any website make authenticated reads on the user's behalf. The spec requires an explicit origin when credentials are allowed. Maintain an allow-list and echo the matching origin (with `Vary: Origin`).

### Q7. A server error shows up in the console as a CORS error. How can that be?

Error responses produced by a crash, a gateway or a proxy often have no CORS headers. The browser sees a response lacking `Allow-Origin` and reports a CORS failure, hiding the real status. Inspect the Network tab and server logs to find the underlying `5xx`.

### Q8. How do you avoid preflights altogether?

Make the API **same-origin** (serve it under your domain or proxy it through your Next.js server), or keep requests simple. In practice, same-origin proxying or a BFF is cleaner than loosening headers, and you gain first-party cookies as well.

### Q9. Scenario: CORS works for `GET` and `POST` but `PUT` fails in staging. Where do you look?

`PUT` triggers a preflight, so check the `OPTIONS` response: `Access-Control-Allow-Methods` must include `PUT`, `Access-Control-Allow-Headers` must list the custom headers you send, and the preflight must return a 2xx without being blocked by auth or a gateway rule. Also confirm a proxy or load balancer in staging is not stripping the headers or caching a preflight response without `Vary: Origin`.

## Key takeaways

- **Origin = scheme + host + port.** CORS lets a server allow other origins to *read* its responses.
- JSON, `Authorization` and non-simple methods trigger an **OPTIONS preflight**; cache it with `Access-Control-Max-Age`.
- Credentials need `credentials: "include"`, an **exact** origin, `Allow-Credentials: true`, and a cookie that can travel cross-site.
- Put CORS middleware **before** auth, always send `Vary: Origin` when echoing, and use an **allow-list**.
- CORS is **not** a firewall and **not** CSRF protection. Same-origin proxying avoids most pain.
