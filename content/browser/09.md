> **In one line:** Core Web Vitals are three user-centred metrics measured on **real users' devices**: **LCP** (how fast the main content appears), **INP** (how fast the page responds to interaction) and **CLS** (how much the layout jumps). A page "passes" when all three are good at the **75th percentile**.

Performance conversations at senior level are about **metrics, thresholds and causes**, not "it feels slow." These three give you a shared language, and they feed directly into the debugging playbooks in the [Scenario Debugging series](/debugging).

## The three metrics and their thresholds

| Metric | Measures | Good | Needs improvement | Poor |
|---|---|---|---|---|
| **LCP**: Largest Contentful Paint | Loading: when the largest visible content element is rendered | **≤ 2.5 s** | 2.5 to 4 s | > 4 s |
| **INP**: Interaction to Next Paint | Responsiveness: how long the page takes to visually respond to clicks, taps and key presses | **≤ 200 ms** | 200 to 500 ms | > 500 ms |
| **CLS**: Cumulative Layout Shift | Visual stability: unexpected movement of content | **≤ 0.1** | 0.1 to 0.25 | > 0.25 |

**"At the 75th percentile":** collect the metric from real page loads, sort them, and look at the value below which 75% of visits fall. A page passes a metric if that value is "good", evaluated separately for mobile and desktop. This means your slowest quarter of users matter, so averages hide problems.

### Why INP replaced FID

**FID (First Input Delay)** measured only the **delay before** the browser started handling the **first** interaction. It missed slow handlers, later interactions and the time to show the result. **INP** looks at **all** interactions during a visit and measures from the user's action until the next frame is painted, reporting (roughly) the worst one. INP officially replaced FID as a Core Web Vital on **12 March 2024**.

## LCP in depth

**What counts as the LCP element:** the largest of an `<img>`, an `<svg>` image, a `<video>` poster, an element with a CSS `background-image` loaded through `url()`, or a block of text. Usually it is the hero image or the main heading.

LCP is the sum of four parts, and finding which part is large tells you what to fix:

| Part | What is slow | Fixes |
|---|---|---|
| **TTFB** (time to first byte) | The server or network | CDN, caching, streaming HTML, faster backend, fewer redirects ([Lesson 00](/browser/lesson-0)) |
| **Resource load delay** | The browser found the image late (CSS background, JS-injected, lazy-loaded hero) | Put the image in the HTML as `<img>`, **preload** it, add `fetchpriority="high"`, never lazy-load the LCP image |
| **Resource load duration** | A big file on a slow connection | Modern formats (AVIF/WebP), correct dimensions with `srcset`/`sizes`, compression, CDN |
| **Element render delay** | The browser had the file but could not paint (render-blocking CSS or JS, client-side rendering waiting for JS) | Inline critical CSS, defer scripts, **server-render** the content, reduce main-thread work |

```html
<!-- A good hero: discoverable early, high priority, correctly sized, never lazy -->
<img
  src="/hero-1200.avif"
  srcset="/hero-600.avif 600w, /hero-1200.avif 1200w, /hero-2000.avif 2000w"
  sizes="100vw"
  width="1200" height="630"
  fetchpriority="high"
  alt="…"
/>
```

In Next.js, `next/image` with the `priority` prop on the LCP image does much of this for you.

### Scenario: LCP is poor only on mobile

Typical causes: a **huge image** served to a small screen (no `srcset`), slow mobile networks making the **resource load duration** long, **heavy JavaScript** delaying render on weaker CPUs, **client-side rendering** where content appears only after a big bundle runs, and a **far-away server**. Compare the four sub-parts in field data to see which dominates.

## INP in depth

An interaction's latency has three parts:

1. **Input delay:** the main thread was busy, so the event handler could not start.
2. **Processing time:** your event handlers (and what they trigger) running.
3. **Presentation delay:** rendering the result after handlers finish (layout, paint).

| Cause | Fix |
|---|---|
| Long tasks blocking the thread | Break them up, `scheduler.yield()`, Web Workers ([Lesson 08](/browser/lesson-8)) |
| Heavy handlers | Do the minimum synchronously (update the UI), defer the rest |
| Large re-renders in React | Memoise, split components, virtualise lists, `startTransition`, `useDeferredValue` |
| Large DOM (thousands of nodes) | Virtualise; `content-visibility`; simplify |
| Third-party scripts | Defer, load after interaction, remove |
| Layout thrashing | Batch reads and writes |

The rule: **respond visually fast** (acknowledge the click with some UI change), then do slow work after the next frame.

## CLS in depth

A **layout shift** happens when a visible element changes position between frames without user input. The score for one shift is **impact fraction × distance fraction**: how much of the viewport was affected, multiplied by how far things moved. CLS reports the worst "session window" of shifts during the page's life. Shifts within 500 ms after a user input (like opening a menu) are excluded.

| Cause | Fix |
|---|---|
| Images, video or iframes without dimensions | Set `width` and `height` attributes or CSS `aspect-ratio` so space is reserved |
| Ads, embeds, banners injected late | Reserve a fixed-size slot (`min-height`) |
| Content inserted **above** existing content (cookie banners, "related" bars) | Insert below the fold, or overlay with `position: fixed` / `transform` |
| Web fonts swapping and changing text size | `font-display: swap` plus a size-matched fallback (`size-adjust`, `ascent-override`), or `font-display: optional`; preload key fonts |
| Animations that change layout properties | Animate `transform` instead |
| Skeletons that do not match the final size | Match the skeleton to the real content dimensions |

```css
/* Reserve space for an image or video before it loads */
.card-img { aspect-ratio: 16 / 9; width: 100%; background: #e5e7eb; }

/* A slot for a late-loading ad */
.ad-slot { min-height: 250px; }
```

## Field data vs lab data

| | Field data (RUM) | Lab data |
|---|---|---|
| **Source** | Real users on real devices and networks | A controlled test (Lighthouse, WebPageTest) on a simulated device |
| **Examples** | **CrUX** (Chrome UX Report, used by PageSpeed Insights and Search Console), your own RUM via the `web-vitals` library | Lighthouse in DevTools or CI |
| **Good for** | **What users actually experience**; what Google's page-experience signals use | **Reproducing and debugging**: repeatable, shows a waterfall, works before release |
| **Weakness** | Cannot tell you *why*; needs traffic; delayed | May not match real conditions; **cannot measure INP** without interaction (Lighthouse uses TBT as a proxy) |

**Which one matters for search ranking?** Field data (CrUX) is what Google uses, though it is only one small signal among many. **Which one do you use to fix things?** Both: field data tells you **whether and where** there is a problem; lab data lets you **reproduce and verify** a fix.

### Collecting your own field data

```ts
import { onLCP, onINP, onCLS } from "web-vitals";

function send(metric: { name: string; value: number; id: string; rating: string }) {
  navigator.sendBeacon("/analytics/vitals", JSON.stringify(metric));
}

onLCP(send);
onINP(send);
onCLS(send);
```

`sendBeacon` is used because it survives the page being closed. Aggregate by route, device type and connection to find the worst offenders, and look at the **75th percentile**, not the mean.

## Related metrics worth knowing

| Metric | Meaning | Note |
|---|---|---|
| **TTFB** | Time to first byte | Server and network; a component of LCP; good is roughly under 0.8 s |
| **FCP** | First Contentful Paint | First text or image; good is 1.8 s or less |
| **TBT** | Total Blocking Time | Lab proxy for responsiveness: the sum of the blocking portion of long tasks between FCP and interactive |
| **TTI** | Time to Interactive | Largely retired from Lighthouse scoring |

## Common mistakes

1. **Quoting averages** instead of the 75th percentile.
2. **Optimising the Lighthouse score** while real users (field data) still suffer.
3. **Lazy-loading the LCP image**, or using it as a CSS background.
4. **Talking about FID** in a new interview. The answer is INP.
5. **Missing image dimensions**, then wondering why CLS is high.
6. **Fixing only the desktop** when the 75th percentile is dominated by mid-range phones.
7. **Adding a heavy third-party tag** (chat, analytics, A/B testing) without measuring its INP cost.

## Interview questions

### Q1. Why did INP replace FID?

FID captured only the input delay of the first interaction, ignoring processing time, presentation delay and every later interaction. INP measures the full latency (input delay + handlers + next paint) across all interactions during a visit and reports roughly the worst one, which reflects how responsive the page feels throughout. It became a Core Web Vital on 12 March 2024.

### Q2. Lab vs field data: which one matters for search ranking?

Field data, specifically the CrUX data at the 75th percentile for real users. Lab tools like Lighthouse are for diagnosing and reproducing problems, and they cannot directly measure INP. Use field data to decide *what* to fix and lab data to find and verify *how*.

### Q3. Scenario: LCP is poor only on mobile. What are the likely causes?

Oversized images with no `srcset`, slow mobile networks inflating load duration, a heavy JS bundle or client-side rendering that delays paint on slow CPUs, render-blocking CSS, late discovery of the hero image, or a distant origin and cold cache. Break LCP into TTFB, load delay, load duration and render delay to see which dominates.

### Q4. How do you prevent layout shift from images or ads that load late?

Reserve space: set `width`/`height` or `aspect-ratio` on media, give ad and embed slots a fixed `min-height`, insert dynamic content below existing content or as an overlay, use size-matched font fallbacks, and animate with `transform`.

### Q5. What are the thresholds and how are they evaluated?

LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 are "good", evaluated at the 75th percentile of real page loads, separately for mobile and desktop. A page passes the Core Web Vitals assessment when all three are good.

### Q6. What are the four sub-parts of LCP and why do they matter?

TTFB, resource load delay, resource load duration and element render delay. Splitting LCP into them turns a vague "slow" into a specific cause: server, discovery, file size or rendering blockage, each with a different fix.

### Q7. How would you improve INP in a React app?

Find the slow interaction in the Performance panel or via `web-vitals` attribution, break up long tasks, keep handlers light, reduce re-render scope (memoisation, state colocation, virtualisation), mark non-urgent updates with `startTransition` or `useDeferredValue`, and defer or remove heavy third-party scripts.

### Q8. Why shouldn't you lazy-load the LCP image?

Lazy loading delays fetching until the browser decides the image is near the viewport, which pushes the LCP later. The hero should be discoverable in the initial HTML, fetched with high priority and, in Next.js, marked `priority`.

## Key takeaways

- **LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1** at the **75th percentile**; INP replaced FID in March 2024.
- Break **LCP** into TTFB, load delay, load duration and render delay; **INP** into input delay, processing and presentation; **CLS** is almost always about **reserved space**.
- **Field data** says what users feel; **lab data** says why. You need both.
- Measure in production with **`web-vitals`**, report percentiles by route and device, and test on throttled hardware.
