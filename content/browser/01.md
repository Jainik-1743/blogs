> **In one line:** a browser gives you five places to keep data. They differ in *how long it lives*, *who can read it* and *whether the server sees it automatically*. Pick by those three questions, not by habit.

"Where should I store this?" is a daily decision and a favourite interview question, because a wrong answer leaks tokens, loses a user's cart, or sends 4 KB of junk on every request. This lesson gives you the properties of each store and a table you can recite.

## The five stores at a glance

| | Cookies | `localStorage` | `sessionStorage` | IndexedDB | Cache API / Service Worker |
|---|---|---|---|---|---|
| **Lifetime** | Session, or until `Expires` / `Max-Age` | Until cleared by user, code or the browser | Until the **tab** closes (survives reload) | Until cleared | Until cleared or evicted |
| **Scope** | Domain + path (+ subdomains if `Domain` is set) | **Origin** | Origin **and** tab | Origin | Origin |
| **Sent to server automatically?** | **Yes**, on every matching request | No | No | No | No |
| **Readable by JavaScript?** | Yes, unless `HttpOnly` | Always | Always | Always | Always |
| **Size** | About 4 KB per cookie | About 5 MB per origin | About 5 MB per origin | Large (quota based on disk, often hundreds of MB or more) | Large (same quota pool) |
| **API** | `document.cookie` or `Set-Cookie` header | Synchronous, strings only | Synchronous, strings only | **Asynchronous**, structured data and blobs | Asynchronous, request/response pairs |
| **Works in Web Workers?** | No | No | No | **Yes** | **Yes** |

Memorize the first three rows: **lifetime, scope, automatically sent**. Most interview answers are built from them.

## Cookies

A cookie is a small piece of text the **server** asks the browser to remember, and the browser then **sends back on later requests** to that site.

```http
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; Max-Age=3600; Path=/; Secure; HttpOnly; SameSite=Lax
```

Every later request to that site carries it:

```http
GET /api/me HTTP/2
Cookie: session_id=abc123
```

### What each attribute does

| Attribute | Meaning | Why you care |
|---|---|---|
| `Expires` / `Max-Age` | When the cookie dies. No value means a **session cookie**, which lasts until the browser closes (and browsers that restore sessions may keep it longer). | Controls how long a login lasts. Browsers cap very long values (Chrome caps at 400 days). |
| `Domain` | Which hosts receive it. **Omit it** and only the exact host gets the cookie. Set `Domain=example.com` and *all subdomains* get it too. | Setting `Domain` widens exposure. A compromised `blog.example.com` can then read or overwrite cookies meant for `app.example.com`. |
| `Path` | URL prefix the cookie applies to. | A convenience, **not** a security boundary. Other paths on the same origin can still read it through script. |
| `Secure` | Only sent over HTTPS. | Prevents leaking on plain HTTP. Always set in production. |
| `HttpOnly` | JavaScript cannot read it (`document.cookie` hides it). | Stops an XSS payload from *stealing* the cookie. It does **not** stop the payload from *using* the session. |
| `SameSite` | `Strict`, `Lax` or `None`: whether the cookie is sent on cross-site requests. | Your main CSRF defence ([Lesson 03](/browser/lesson-3)). Modern browsers treat a missing value as `Lax`. `None` requires `Secure`. |
| `Partitioned` | Keys a third-party cookie to the top-level site (CHIPS). | The replacement for classic third-party cookies in embedded widgets. |

### Cookie name prefixes

Prefixes make the browser *enforce* rules:

- `__Secure-` requires the `Secure` attribute.
- `__Host-` requires `Secure`, `Path=/`, **and no `Domain`**. This locks the cookie to the exact host, so a sibling subdomain cannot overwrite it. Use `__Host-` for session cookies when you can.

### Why cookies are special

They are the only store the **server receives automatically**. That makes them the natural home for a session ID, and also the reason for CSRF: the browser attaches them even when the request was triggered by another site. They also cost bandwidth: a 3 KB cookie on a domain that serves 60 assets adds roughly 180 KB of upload traffic to a page load. Keep cookies small, and serve static assets from a cookieless domain or path where it matters.

### Reading and writing from JavaScript

```js
// Writing (cannot set HttpOnly this way, only the server can)
document.cookie = "theme=dark; Max-Age=31536000; Path=/; SameSite=Lax; Secure";

// Reading gives ONE string of every non-HttpOnly cookie
console.log(document.cookie); // "theme=dark; locale=en-IN"
```

The `document.cookie` API is awkward (one string, manual parsing), so libraries or the newer **Cookie Store API** are used where available.

## `localStorage`

A key-value store of **strings**, scoped to the **origin** (scheme + host + port), persisting until someone clears it.

```js
localStorage.setItem("theme", "dark");
localStorage.getItem("theme");          // "dark"
localStorage.setItem("prefs", JSON.stringify({ density: "compact" }));
JSON.parse(localStorage.getItem("prefs") ?? "{}");
localStorage.removeItem("theme");
```

Properties worth knowing:

- **Synchronous.** A large read or write blocks the main thread. Avoid storing megabytes of JSON you re-parse on every render.
- **Strings only.** Everything goes through `JSON.stringify` / `JSON.parse`.
- **Shared by all tabs of the origin.** A change in one tab fires a `storage` event in the *other* tabs, which is how you sync a logout or theme across tabs:

```js
window.addEventListener("storage", (e) => {
  if (e.key === "theme") applyTheme(e.newValue);
});
```

- **Shared by all scripts on the origin**, including your analytics snippet, chat widget and any compromised dependency. There is no per-script permission. This is the root of the token-storage warning in [Lesson 03](/browser/lesson-3).
- **Not sent to the server.** Nothing in `localStorage` costs bandwidth, but nothing is available to server rendering either (it does not exist on the server, which is why Next.js components that read it must run on the client after mount).
- **Not guaranteed to persist.** Users clear site data; browsers evict under storage pressure; Safari's tracking prevention can delete script-written storage for sites a user has not interacted with for about seven days.

## `sessionStorage`

The same API as `localStorage`, but scoped to the **browsing context (a tab)** and cleared when the tab closes.

- It survives a page **reload** and navigation within the tab.
- Each tab has its **own copy**. Open the same site in a second tab by typing the URL and that tab starts empty. (Opening a link with `target="_blank"` may copy the opener's values at that moment, then the two diverge, so do not rely on it for sharing.)
- It does **not** fire cross-tab `storage` events, because tabs do not share it.

Good uses: a multi-step form draft, a wizard's progress, a one-time redirect target, "have I shown this banner in this visit?".

## IndexedDB (and friends)

IndexedDB is a transactional, **asynchronous** object database in the browser. It stores structured data (objects, arrays, `Blob`s, `File`s), supports indexes and queries by key range, and is available in Web Workers and Service Workers. Use it when you have **a lot of data** or **non-string data**: an offline-first app's records, cached API collections, drafts with attachments.

```js
// Minimal raw usage (in practice you would wrap it with a small library such as idb)
const open = indexedDB.open("app", 1);
open.onupgradeneeded = () => open.result.createObjectStore("drafts", { keyPath: "id" });
open.onsuccess = () => {
  const tx = open.result.transaction("drafts", "readwrite");
  tx.objectStore("drafts").put({ id: 1, body: "Hello", updatedAt: Date.now() });
};
```

The **Cache API** (used with Service Workers) stores `Request` → `Response` pairs, which is exactly what an offline shell or cached assets need.

**Quota and eviction:** browsers allot a share of disk space per origin. `navigator.storage.estimate()` reports usage and quota, and `navigator.storage.persist()` asks the browser not to evict your data under pressure. Anything you store may disappear, so treat it as a **cache of something recoverable**, not as the only copy.

## Decision table: where does this data belong?

| Data | Best home | Why |
|---|---|---|
| Session ID / auth cookie | **Cookie**: `HttpOnly; Secure; SameSite`, preferably `__Host-` | The server needs it on every request; JS should not read it |
| Access token for an API | In **memory** (a JS variable), refreshed via an HttpOnly cookie | Storage that JS can read is exposed to XSS ([Lesson 03](/browser/lesson-3)) |
| Theme, language, density | `localStorage` (or a cookie if the server must render with it) | Non-sensitive, should persist; a cookie avoids a flash of the wrong theme on SSR |
| "Shown the welcome banner this visit" | `sessionStorage` | Per-tab, dies with the tab |
| Multi-step checkout form progress | `sessionStorage` (or server-side draft) | Scoped to one flow in one tab |
| Shopping cart for logged-in users | **Server** (database) | Must follow the user across devices |
| Cart for anonymous users | Cookie ID + server cart, or `localStorage` | Needs to survive tabs and restarts |
| Large offline dataset, drafts with files | **IndexedDB** | Big, structured, async |
| Static assets for offline use | **Cache API** via a Service Worker | Request/response storage |
| Secrets (API keys, passwords) | **Nowhere in the browser** | Anything shipped to the client is public |

> [!warn] The rule of thumb for authentication: if JavaScript can read it, so can an attacker's JavaScript. OWASP's guidance is explicit that session identifiers and tokens should not live in `localStorage` or `sessionStorage`. [Lesson 03](/browser/lesson-3) explains the trade-offs and the patterns that hold up.

## A safe storage wrapper

Storage can throw: private modes, blocked cookies, quota exceeded, or an iframe without access. Never assume it works.

```ts
type Json = string | number | boolean | null | Json[] | { [k: string]: Json };

export const safeStorage = {
  get<T extends Json>(key: string, fallback: T): T {
    try {
      const raw = localStorage.getItem(key);
      return raw === null ? fallback : (JSON.parse(raw) as T);
    } catch {
      return fallback; // storage blocked, or corrupted JSON
    }
  },
  set(key: string, value: Json): boolean {
    try {
      localStorage.setItem(key, JSON.stringify(value));
      return true;
    } catch {
      return false; // QuotaExceededError, SecurityError, ...
    }
  },
};
```

In Next.js, also remember that **server components and the first server render have no `localStorage`**. Read it in an effect after mount, or you will cause a hydration mismatch.

## Common mistakes

1. **Storing JWTs or session IDs in `localStorage`.** Any XSS, including one in a third-party script, can read and exfiltrate it.
2. **Using `localStorage` for data the server needs on first render** (theme, locale). The server cannot see it, so the page flashes the wrong theme. Use a cookie for that.
3. **Putting big objects in cookies.** They are sent on every request, including images. Store an ID in the cookie and the data on the server.
4. **Setting `Domain` on a cookie "to be safe."** It does the opposite: it shares the cookie with every subdomain.
5. **Assuming storage is permanent.** Treat browser storage as a cache that can vanish.
6. **Believing `Path` is security.** It only scopes sending; any page on the same origin can still read the cookie through script (unless `HttpOnly`) or an iframe.
7. **Forgetting `try/catch`** around storage calls.

## Interview questions

### Q1. When would you choose `sessionStorage` over `localStorage`?

When the data should be **scoped to a single tab and a single visit**: wizard progress, a draft, a one-time flag. `sessionStorage` is isolated per tab and cleared on close, so two tabs cannot clobber each other and nothing lingers afterwards. Use `localStorage` when the data should persist across visits and be visible in every tab, such as a theme.

### Q2. What do `HttpOnly`, `Secure`, `SameSite`, `Domain` and `Path` each do?

- `HttpOnly`: hides the cookie from JavaScript, so XSS cannot read it.
- `Secure`: send only over HTTPS.
- `SameSite`: controls whether it is sent on cross-site requests (`Strict`, `Lax`, `None`), a CSRF defence.
- `Domain`: which hosts get it. Omitted means the exact host only; set means subdomains too.
- `Path`: limits which URL paths send it, but it is a convenience, not a security boundary.

### Q3. Why is `localStorage` shared by every script on an origin, and why does that matter?

Storage is partitioned by **origin**, not by script. Your own code, the analytics tag, a chat widget and any compromised npm package all run with the same origin and can read all of it. That is why secrets and tokens do not belong there: one malicious or buggy script leaks everything.

### Q4. Scenario: a user's cart disappears when they open the site in a new tab. Which storage choice caused it?

The cart is in `sessionStorage`, which is per-tab. The new tab has its own empty copy. Move the cart to `localStorage` for anonymous users, or, better, store it on the server tied to the user or a cookie-based anonymous ID so it also follows them across devices.

### Q5. How would you sync a logout across all open tabs?

Write a flag to `localStorage` on logout (for example `localStorage.setItem("logout", Date.now())`) and listen for the `storage` event in every tab, then clear in-memory state and redirect. A `BroadcastChannel` does the same thing without touching storage.

### Q6. Why are cookies sent with every request, and how do you limit the cost?

The browser attaches every cookie whose domain and path match, including to image and script requests. Limit cost by keeping cookies tiny (store an ID, not data), setting precise `Path`/host scope, avoiding `Domain` when unnecessary, and serving static assets from a cookieless hostname or a CDN on a different domain.

### Q7. When is IndexedDB the right answer?

When the data is large, structured or binary, needs queries or indexes, must be accessed asynchronously, or must be available in a worker: offline-first apps, drafts with attachments, large cached collections. `localStorage` is synchronous, string-only and about 5 MB, so it is the wrong tool there.

### Q8. Is browser storage a safe place to keep the only copy of important data?

No. Users clear data, browsers evict under storage pressure, private modes discard it and some browsers expire script-written storage after a period of inactivity. Keep the source of truth on the server and treat the browser copy as a cache.

### Q9. Scenario: Safari users complain that their saved preferences disappear after about a week away. Why, and what do you do?

Safari's tracking prevention caps the lifetime of script-written storage (cookies set with `document.cookie` and `localStorage`) for sites a user has not interacted with for a period, around seven days. Treat browser storage as a cache: keep important preferences on the server for logged-in users, set cookies from the server with `Set-Cookie` where appropriate, and re-create local defaults gracefully when storage is empty.

## Key takeaways

- Choose a store by **lifetime, scope, and whether the server needs it automatically**.
- Cookies are the only store sent to the server automatically. Their attributes (`HttpOnly`, `Secure`, `SameSite`, no `Domain`) are your security controls.
- `localStorage` is origin-wide, synchronous, string-only and readable by every script. Never keep secrets there.
- `sessionStorage` is per-tab and ends with the tab.
- Use IndexedDB for big or structured data, and always wrap storage access in `try/catch`.
