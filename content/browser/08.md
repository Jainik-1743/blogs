> **In one line:** the browser has **one main thread**. It runs your JavaScript *and* draws every frame. If your code keeps the thread busy for too long, the page cannot respond or paint. A smooth UI comes from short tasks and the cheapest kind of rendering work.

The event loop and the rendering pipeline are two halves of one story. Interviewers like this topic because one simple model explains jank (stuttering), laggy scrolling and "why does my animation stutter?"

## The frame budget

Most screens refresh 60 times a second. So the browser has about **16.7 ms per frame** (8.3 ms at 120 Hz) to run your code **and** make the pixels. If anything holds the main thread longer than that, a frame is dropped.

A task that runs for more than **50 ms** is called a **long task**. Long tasks make clicks feel slow to answer. This is measured by the INP metric in [Lesson 09](/browser/lesson-9).

## The rendering pipeline

The pipeline is the list of steps the browser follows to turn your code into pixels. Think of a factory line with five stations:

```text
JavaScript ─▶ Style ─▶ Layout ─▶ Paint ─▶ Composite
 (your code)  (which   (size and  (fill     (combine layers,
              CSS      position   pixels)    usually on the GPU)
              applies) of boxes)
```

| Stage | What it does | Triggered by changing… |
|---|---|---|
| **Style** | Works out which CSS rules apply to each element | Classes, attributes, `:hover` states |
| **Layout (reflow)** | Works out the geometry: where every box goes | `width`, `height`, `top`, `margin`, `font-size`, adding or removing nodes |
| **Paint** | Draws text, colours, borders and shadows into layers | `color`, `background`, `box-shadow`, `border-radius` |
| **Composite** | Moves and blends layers that are already painted | `transform`, `opacity` (and some `filter` effects) |

The cost goes **down** as you move to the right. A change that only needs **composite** skips layout and paint. So it can stay smooth even when the main thread is busy.

| Change | Pipeline work | Cost |
|---|---|---|
| `transform: translateX()` / `opacity` | Composite only | Cheap |
| `background-color`, `box-shadow` | Paint + composite | Medium |
| `width`, `height`, `top`, `left`, `margin` | Layout + paint + composite | **Expensive**, and can affect many other elements |

This is why you animate with `transform` and `opacity`, and not with `left` and `width`.

> [!note] **Reflow vs repaint.** *Reflow (layout)* works out the geometry again, and it often forces a repaint. *Repaint* draws the pixels again without changing the geometry. Reflow costs more. Changes that only use the compositor avoid both.

## The event loop in one page

JavaScript runs on one thread. So work waits in queues, and the browser handles it in a loop. Think of a single cashier with a line of customers. Each person is served fully before the next one.

1. Take one **task** (a macrotask) from the task queue. A task can be a click handler, a `setTimeout` callback, a network response or a message.
2. Run it until it finishes.
3. Run **all microtasks** until the microtask queue is empty. Microtasks are promise callbacks, `queueMicrotask` and `MutationObserver`.
4. If it is time to render (about every 16.7 ms), run the **animation frame callbacks** (`requestAnimationFrame`). Then run **style, layout and paint**.
5. Repeat.

```js
console.log("1 sync");

setTimeout(() => console.log("4 timeout (task)"), 0);

Promise.resolve().then(() => console.log("3 promise (microtask)"));

requestAnimationFrame(() => console.log("5 rAF (just before the next paint)"));

queueMicrotask(() => console.log("3b microtask"));

console.log("2 sync");

// Typical order in Chrome: 1 sync, 2 sync, 3 promise, 3b microtask, 4 timeout, 5 rAF
// Microtasks ALWAYS come right after the current script and before anything else.
// The order of the timeout and the rAF callback is NOT guaranteed: a 0 ms timer usually fires
// first, but if a frame is due, rAF can run before it. Never write code that depends on it.
```

What this means for you:

- **Microtasks run before the browser can render.** A promise chain that keeps adding microtasks can **starve rendering** (and input). Starving means the browser never gets a turn.
- **`setTimeout(fn, 0)` makes a new task.** So rendering can happen before it runs. This is how you **yield** (give the browser a turn).
- **Rendering happens between tasks**, never in the middle of one. A 300 ms synchronous loop means no paint and no input handling for 300 ms.
- **`requestAnimationFrame`** callbacks run right before the next paint. This is the right place to read or write values that affect layout during an animation.

(The JavaScript series explains the loop in more depth. Here we only look at how it shapes rendering.)

## Layout thrashing

The browser normally **batches** layout. You change several things, and it works out the layout once. But there is a problem if you **read a layout value** (`offsetHeight`, `getBoundingClientRect()`, `scrollTop`, `getComputedStyle`) **after a write that made the layout out of date**. The browser must work out the layout **right now** to give you a correct answer. If you read, write, read, write in a loop, you force a full layout on every round. This is called layout thrashing.

```js
// ❌ Layout thrashing: each iteration writes then reads
for (const el of items) {
  el.style.width = box.offsetWidth / 2 + "px"; // read (forces layout), then write (invalidates it)
}

// ✅ Batch: all reads first, then all writes
const w = box.offsetWidth / 2;                  // one read
for (const el of items) el.style.width = w + "px"; // writes only, one layout later
```

Fixes:

- **Batch reads and writes.** Read everything first. Then write everything.
- Do the writes in **`requestAnimationFrame`**.
- Use **`ResizeObserver`** and **`IntersectionObserver`**. Do not check sizes and positions again and again (polling) in scroll handlers.
- Avoid `getBoundingClientRect()` in loops that run often. Save the result.
- In React, measure once in `useLayoutEffect`. Do not measure each item during render.

## Why scrolling and input get janky

### Scroll handlers

```js
// ❌ Heavy work on every scroll event
window.addEventListener("scroll", () => {
  const top = el.getBoundingClientRect().top; // layout read
  el.style.transform = `translateY(${top / 2}px)`;
  updateStickyHeader(); // plus more work
});
```

Scroll events can fire more than once per frame. Here is a fix:

```js
let ticking = false;
window.addEventListener(
  "scroll",
  () => {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => {
      update();            // at most once per frame
      ticking = false;
    });
  },
  { passive: true },      // tell the browser you won't call preventDefault(), so it can scroll without waiting for you
);
```

- Use **`{ passive: true }`** on `touchstart`, `touchmove`, `wheel` and `scroll` listeners.
- Use **`IntersectionObserver`** instead of scroll math that asks "is it visible?"
- Use CSS when you can: `position: sticky`, `scroll-snap` and scroll-driven animations.

### Long tasks and input delay

A click that arrives during a 200 ms task must wait 200 ms. So break the work into small pieces:

```js
async function processInChunks(items, doItem) {
  let last = performance.now();
  for (const item of items) {
    doItem(item);
    if (performance.now() - last > 12) {              // keep each slice short
      await (globalThis.scheduler?.yield?.() ?? new Promise((r) => setTimeout(r, 0)));
      last = performance.now();
    }
  }
}
```

Other tools:

- **`scheduler.yield()`** (where it exists) or `setTimeout(0)` gives input a turn.
- **`requestIdleCallback`** is for work that is really low priority.
- **Web Workers** move heavy CPU work (parsing, sorting, diffing) **off the main thread completely**.
- **`startTransition`** in React marks an update as one that can be interrupted ([Frontend Depth](/frontend-depth)).

## Layers, `will-change` and `content-visibility`

- The browser puts some elements on their **own compositor layer**. These are elements with a `transform` or `opacity` animation, `will-change`, video or canvas. Such an element can move without repainting the others.
- **`will-change: transform`** is a hint. It is not a magic speed-up. Every layer uses memory. Add it just before an animation and remove it afterwards. Do not put it on everything.
- **`content-visibility: auto`** lets the browser skip layout and paint for sections that are off screen. It does the work only when they come near the viewport. Use it with `contain-intrinsic-size` to avoid jumps in the scrollbar. It is great for long pages and feeds.
- **`contain: layout paint`** tells the browser that a part of the page does not affect the rest. This limits the damage of a change.

## How to debug it

1. **Chrome DevTools, Performance panel:** record while you reproduce the jank. Look for **long tasks** (red corners), the **Main** thread flame chart, and the purple **Layout** blocks and green **Paint** blocks.
2. Look for repeated **"Recalculate Style" and "Layout"** inside a loop. That is thrashing. DevTools may show "Forced reflow."
3. Turn on **Rendering > Paint flashing** and **Layout Shift Regions** to see what repaints.
4. **Layers** and **Rendering > FPS meter** show compositing problems.
5. Use **CPU throttling (4x slowdown)**. Your laptop hides problems that mid-range phones show.

## Common mistakes

1. **Animating `top`, `left`, `width` or `height`** instead of `transform` or `opacity`.
2. **Mixing reads and writes** in loops and event handlers (layout thrashing).
3. **Heavy synchronous work in event handlers.** The UI freezes until it ends.
4. **Scroll and touch listeners that are not passive.**
5. **Overusing `will-change`** and making hundreds of layers.
6. **Thinking `Promise` means "async" and so "does not block."** The callback still runs on the main thread. A long chain of microtasks still blocks rendering.
7. **Testing only on a fast desktop.**

## Interview questions

### Q1. Reflow vs repaint?

Reflow (layout) works out the size and position of elements again, and it usually causes a repaint. Repaint draws the pixels again without changing the geometry. Reflow costs more and can spread to other elements. Changes to `transform` and `opacity` can avoid both and only need compositing.

### Q2. Why does reading `offsetHeight` in a loop hurt?

If styles were changed earlier in the loop, the browser must run layout right away to give a correct value. If reads and writes are mixed, layout runs on every round. This is layout thrashing. I do all the reads first and then all the writes, ideally inside `requestAnimationFrame`.

### Q3. Which CSS properties can animate on the compositor?

`transform` and `opacity` (and some `filter` effects in many browsers). They need no layout or paint when the element is on its own layer. So they stay smooth even if the main thread is busy.

### Q4. Scenario: a scroll handler causes jank. Fix it.

I mark the listener `passive`. I limit the work to once per frame with `requestAnimationFrame`. I avoid layout reads inside it. I move visibility checks to `IntersectionObserver`. I use CSS (`sticky`, `scroll-snap`) where I can. Then I profile in the Performance panel to confirm that the long task or forced reflow is gone.

### Q5. Where do microtasks, tasks and `requestAnimationFrame` fit in the event loop?

One task runs. Then all microtasks run until none are left. Then, if a frame is due, the animation-frame callbacks run, followed by style, layout and paint. Then the next task starts. So microtasks always run before rendering, and a long chain of microtasks can delay paint.

### Q6. What is a long task and why does it matter?

A long task is a task that runs for more than 50 ms. While it runs, the main thread cannot handle input or paint. So users feel a delay. Long tasks cause a poor INP score. I break them up, yield with `scheduler.yield` or timeouts, or move the work to a Web Worker.

### Q7. Does `will-change` make things faster?

Only when it is a targeted hint that an element is about to be animated. It lets the browser prepare a layer. If you use it too much, it wastes memory and can make things slower. I add it just before the animation and remove it afterwards.

### Q8. Why can a Promise-heavy loop freeze the UI?

Promise callbacks are microtasks. All microtasks run before the browser may render or take the next task. If each callback adds another one, the queue never becomes empty, and rendering is starved. I use `setTimeout` or `scheduler.yield` to give control back to the browser.

### Q9. Scenario: scrolling is janky only on a page with a sticky header and a parallax hero. How do you diagnose it?

I record the scroll in the Performance panel with CPU throttling. I look for long frames, and for layout and paint work on each scroll event. Common causes are a scroll handler that reads layout, and a parallax effect that animates `top` or `background-position` instead of `transform`. Others are large areas that get repainted, and listeners that are not passive. I move the effect to `transform`, limit updates with `requestAnimationFrame`, mark listeners passive, and promote only the layers that animate.

## Key takeaways

- One main thread runs your JavaScript and the rendering pipeline. Keep tasks under **50 ms** and frames within about **16 ms**.
- Prefer animations that only need **composite** (`transform`, `opacity`) over properties that trigger layout.
- **Batch reads before writes** to avoid layout thrashing.
- Use `requestAnimationFrame`, passive listeners and observers instead of heavy scroll handlers.
- Move heavy work to **Web Workers**, and **yield** inside long loops.
- Measure with the **Performance panel** and CPU throttling. Do not guess.
