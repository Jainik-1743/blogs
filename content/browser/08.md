> **In one line:** the browser has **one main thread** that runs your JavaScript *and* builds every frame. If your code holds it for too long, the page cannot respond or paint. Smooth UIs come from keeping tasks short and doing the cheapest kind of rendering work.

The event loop and the rendering pipeline are two halves of the same story. Interviewers like it because it explains jank, laggy scrolling and "why did my animation stutter" with one mental model.

## The frame budget

Most screens refresh 60 times a second, so the browser has about **16.7 ms per frame** (8.3 ms at 120 Hz) to run your code **and** produce pixels. Anything that holds the main thread for longer causes a dropped frame.

A task that runs for more than **50 ms** is called a **long task**. Long tasks are what make clicks feel delayed (the INP metric in [Lesson 09](/browser/lesson-9)).

## The rendering pipeline

```text
JavaScript ─▶ Style ─▶ Layout ─▶ Paint ─▶ Composite
 (your code)  (which   (size and  (fill     (combine layers,
              CSS      position   pixels)    usually on the GPU)
              applies) of boxes)
```

| Stage | What it does | Triggered by changing… |
|---|---|---|
| **Style** | Computes which rules apply to each element | Classes, attributes, `:hover` states |
| **Layout (reflow)** | Computes geometry: where every box goes | `width`, `height`, `top`, `margin`, `font-size`, adding or removing nodes |
| **Paint** | Draws text, colours, borders, shadows into layers | `color`, `background`, `box-shadow`, `border-radius` |
| **Composite** | Moves and blends already-painted layers | `transform`, `opacity` (and some `filter` effects) |

The cost goes **down** as you go right. A change that only needs **composite** skips layout and paint entirely, so it can run smoothly even when the main thread is busy.

| Change | Pipeline work | Cost |
|---|---|---|
| `transform: translateX()` / `opacity` | Composite only | Cheap |
| `background-color`, `box-shadow` | Paint + composite | Medium |
| `width`, `height`, `top`, `left`, `margin` | Layout + paint + composite | **Expensive**, and can affect many other elements |

This is why you animate with `transform` and `opacity`, not `left` and `width`.

> [!note] **Reflow vs repaint.** *Reflow (layout)* recalculates geometry and often forces a repaint. *Repaint* redraws pixels without changing geometry. Reflow is the costlier one; both are avoided entirely by compositor-only changes.

## The event loop in one page

JavaScript runs on one thread, so work is queued and processed in a loop:

1. Take one **task** (macrotask) from the task queue: a click handler, a `setTimeout` callback, a network response, a message.
2. Run it to completion.
3. Run **all microtasks** (promise callbacks, `queueMicrotask`, `MutationObserver`) until the microtask queue is empty.
4. If it is time to render (about every 16.7 ms), run **animation frame callbacks** (`requestAnimationFrame`), then **style, layout, paint**.
5. Repeat.

```js
console.log("1 sync");

setTimeout(() => console.log("5 timeout (task)"), 0);

Promise.resolve().then(() => console.log("3 promise (microtask)"));

requestAnimationFrame(() => console.log("4 rAF (before next paint)"));

queueMicrotask(() => console.log("3b microtask"));

console.log("2 sync");

// Order: 1 sync, 2 sync, 3 promise, 3b microtask, 4 rAF*, 5 timeout
// (*rAF usually runs before the next paint; its position relative to the timeout
//  depends on when that paint opportunity comes, but microtasks always come first)
```

Key consequences:

- **Microtasks run before the browser can render.** A promise chain that keeps queuing microtasks can **starve rendering** (and input).
- **`setTimeout(fn, 0)` is a new task**, so rendering can happen before it. It is how you **yield** to the browser.
- **Rendering happens between tasks**, never in the middle of one. A 300 ms synchronous loop means no paint and no input handling for 300 ms.
- **`requestAnimationFrame`** callbacks run right before the next paint: the right place to read or write layout-affecting values for animation.

(The JavaScript series covers the loop in more depth; here we care how it shapes rendering.)

## Layout thrashing

The browser normally **batches** layout: you change several things, and it recalculates once. But if you **read a layout value** (`offsetHeight`, `getBoundingClientRect()`, `scrollTop`, `getComputedStyle`) **after a write that invalidated layout**, the browser must recalculate layout **immediately** to give you a correct answer. Alternate read, write, read, write in a loop and you force a full layout on every iteration.

```js
// ❌ Layout thrashing: each iteration writes then reads
for (const el of items) {
  el.style.width = box.offsetWidth / 2 + "px"; // read (forces layout), then write (invalidates it)
}

// ✅ Batch: all reads first, then all writes
const w = box.offsetWidth / 2;                  // one read
for (const el of items) el.style.width = w + "px"; // writes only, one layout later
```

Fixes:

- **Batch reads and writes**: read everything, then write everything.
- Do the writes in **`requestAnimationFrame`**.
- Use **`ResizeObserver`** and **`IntersectionObserver`** instead of polling geometry in scroll handlers.
- Avoid `getBoundingClientRect()` in hot loops; cache results.
- In React, measure in `useLayoutEffect` once, not per item in render.

## Why scrolling and input get janky

### Scroll handlers

```js
// ❌ Heavy work on every scroll event
window.addEventListener("scroll", () => {
  const top = el.getBoundingClientRect().top; // layout read
  el.style.transform = `translateY(${top / 2}px)`;
  updateStickyHeader(); // plus more work
});
```

Scroll events can fire more than once per frame. Fixes:

```js
let ticking = false;
window.addEventListener(
  "scroll",
  () => {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => {
      update();            // at most once per frame
      ticking = false;
    });
  },
  { passive: true },      // tell the browser you won't call preventDefault(), so it can scroll without waiting for you
);
```

- Use **`{ passive: true }`** on `touchstart`, `touchmove`, `wheel` and `scroll` listeners.
- Replace "is it visible?" scroll math with **`IntersectionObserver`**.
- Use CSS where possible: `position: sticky`, `scroll-snap`, scroll-driven animations.

### Long tasks and input delay

A click that arrives during a 200 ms task waits 200 ms. Break up work:

```js
async function processInChunks(items, doItem) {
  let last = performance.now();
  for (const item of items) {
    doItem(item);
    if (performance.now() - last > 12) {              // keep each slice short
      await (globalThis.scheduler?.yield?.() ?? new Promise((r) => setTimeout(r, 0)));
      last = performance.now();
    }
  }
}
```

Other tools:

- **`scheduler.yield()`** (where available) or `setTimeout(0)` to give input a turn.
- **`requestIdleCallback`** for truly low-priority work.
- **Web Workers** to move CPU-heavy work (parsing, sorting, diffing) **off the main thread entirely**.
- **`startTransition`** in React to mark an update as interruptible ([Frontend Depth](/frontend-depth)).

## Layers, `will-change` and `content-visibility`

- The browser promotes some elements (`transform`/`opacity` animation, `will-change`, video, canvas) to their **own compositor layer**, so they can move without repainting others.
- **`will-change: transform`** is a hint, not a magic speedup: every layer costs memory. Add it right before an animation and remove it afterwards; do not put it on everything.
- **`content-visibility: auto`** lets the browser skip layout and paint for off-screen sections until they are near the viewport. Pair it with `contain-intrinsic-size` to avoid scrollbar jumps. Great for long pages and feeds.
- **`contain: layout paint`** tells the browser that a subtree does not affect the rest of the page, which narrows the damage of a change.

## How to debug it

1. **Chrome DevTools, Performance panel:** record while reproducing the jank. Look for **long tasks** (red corners), the **Main** thread flame chart, and purple **Layout** and green **Paint** blocks.
2. Look for repeated **"Recalculate Style" and "Layout"** inside a loop (thrashing). DevTools may flag "Forced reflow."
3. Enable **Rendering > Paint flashing** and **Layout Shift Regions** to see what repaints.
4. **Layers** and **Rendering > FPS meter** show compositing problems.
5. Check **CPU throttling (4x slowdown)** because your laptop hides problems that mid-range phones expose.

## Common mistakes

1. **Animating `top`/`left`/`width`/`height`** instead of `transform`/`opacity`.
2. **Read/write interleaving** in loops and event handlers (layout thrashing).
3. **Heavy synchronous work in event handlers**, which makes the UI freeze until it ends.
4. **Non-passive scroll and touch listeners.**
5. **Overusing `will-change`** and creating hundreds of layers.
6. **Assuming `Promise` means "async" and therefore "non-blocking."** The callback still runs on the main thread, and a long microtask chain still blocks rendering.
7. **Testing only on a fast desktop.**

## Interview questions

### Q1. Reflow vs repaint?

Reflow (layout) recomputes element sizes and positions and usually triggers a repaint. Repaint redraws pixels without changing geometry. Reflow is more expensive and can cascade to other elements. Changes to `transform` and `opacity` can avoid both and only composite.

### Q2. Why does reading `offsetHeight` in a loop hurt?

If styles were changed earlier in the loop, the browser must run a synchronous layout to return an accurate value. Interleaving reads and writes forces a layout on every iteration (layout thrashing). Batch all reads first, then all writes, ideally inside `requestAnimationFrame`.

### Q3. Which CSS properties can animate on the compositor?

`transform` and `opacity` (and some `filter` effects in many browsers). They need no layout or paint when the element is on its own layer, so they stay smooth even if the main thread is busy.

### Q4. Scenario: a scroll handler causes jank. Fix it.

Mark the listener `passive`, throttle work to once per frame with `requestAnimationFrame`, avoid layout reads inside it, move visibility checks to `IntersectionObserver`, and use CSS (`sticky`, `scroll-snap`) where possible. Profile in the Performance panel to confirm the long task or forced reflow is gone.

### Q5. Where do microtasks, tasks and `requestAnimationFrame` fit in the event loop?

One task runs, then all microtasks run to exhaustion, then (if a frame is due) animation-frame callbacks run, followed by style, layout and paint. Then the next task is taken. Microtasks therefore always run before rendering, and long microtask chains can delay paint.

### Q6. What is a long task and why does it matter?

A task running longer than 50 ms. While it runs, the main thread cannot handle input or paint, so users experience delay. Long tasks drive poor INP. Break them up, yield with `scheduler.yield` or timeouts, or move work to a Web Worker.

### Q7. Does `will-change` make things faster?

Only as a targeted hint that an element is about to be animated, letting the browser prepare a layer. Overuse wastes memory and can hurt performance. Apply it just before the animation and remove it afterwards.

### Q8. Why can a Promise-heavy loop freeze the UI?

Promise callbacks are microtasks, and all microtasks run before the browser may render or handle the next task. If each callback queues another, the queue never empties and rendering is starved. Use `setTimeout`/`scheduler.yield` to hand control back to the browser.

## Key takeaways

- One main thread runs your JS and the rendering pipeline; keep tasks under **50 ms** and frames within about **16 ms**.
- Prefer **composite-only** animation (`transform`, `opacity`) over layout-triggering properties.
- **Batch reads before writes** to avoid layout thrashing.
- Use `requestAnimationFrame`, passive listeners and observers instead of heavy scroll handlers.
- Move heavy computation to **Web Workers**, and **yield** inside long loops.
- Profile with the **Performance panel** and CPU throttling, not by guessing.
