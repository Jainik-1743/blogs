> **In one line:** HTTP caching lets a response be reused instead of re-fetched. `Cache-Control` says **how long it is fresh and who may store it**; validators (`ETag`) let the browser ask "has it changed?" cheaply. Get it right and pages are instant; get it wrong and users see yesterday's site.

Caching is where performance and correctness collide. This lesson gives you the directives, the two mechanisms (freshness and validation), the standard recipe for a modern web app, and a debugging method for "users see stale data after a deploy."

## The two mechanisms

### 1. Freshness: "use it without asking"

If a stored response is still **fresh**, the browser serves it immediately with **no network request**.

```http
Cache-Control: max-age=3600
```

Fresh for one hour. In that hour the response is reused straight from cache.

### 2. Validation: "ask whether it changed"

When a response is **stale** (or must always be checked), the browser sends a **conditional request** with a validator, and the server replies either "still good" or the new body.

```http
# First response
HTTP/2 200
ETag: "a1b2c3"
Cache-Control: no-cache

# Later request
GET /data.json
If-None-Match: "a1b2c3"

# Server: nothing changed — no body sent
HTTP/2 304 Not Modified
```

A `304` saves the **download** (bandwidth) but still costs a **round trip** (latency). Two validators exist:

| Validator | Sent back as | Notes |
|---|---|---|
| `ETag` (a fingerprint of the content) | `If-None-Match` | Precise. Weak ETags (`W/"..."`) mean "semantically equal" |
| `Last-Modified` (a date) | `If-Modified-Since` | Coarse (one-second resolution) |

## The `Cache-Control` directives you must know

| Directive | Meaning |
|---|---|
| `max-age=N` | Fresh for N seconds (browser **and** shared caches) |
| `s-maxage=N` | Like `max-age` but **only for shared caches** (CDNs, proxies); overrides `max-age` there |
| `public` | Any cache may store it, even if normally not cacheable (for example when `Authorization` is present) |
| `private` | Only the **user's own browser** may store it, not a shared cache. Use for personalized responses |
| `no-cache` | **Store it, but revalidate before every reuse.** Does *not* mean "don't cache" |
| `no-store` | **Do not store it anywhere.** For sensitive data |
| `must-revalidate` | Once stale, don't serve it without revalidating (no "serve stale on error" shortcuts) |
| `immutable` | The content will **never** change at this URL, so skip revalidation even on reload |
| `stale-while-revalidate=N` | After it goes stale, serve the stale copy for up to N seconds **while refreshing in the background** |
| `stale-if-error=N` | If the origin errors, serve the stale copy for up to N seconds |

> [!warn] **`no-cache` and `no-store` are the most-confused pair.** `no-cache` = *cache it, but check with the server before using it* (a cheap `304` is possible). `no-store` = *never keep a copy*. Sensitive pages (account details, banking, anything with a session) should use `no-store`; OWASP asks for it so that the Back button and shared computers do not reveal them.

### Where a response is stored

- **Browser (private) cache:** one per user.
- **Shared caches:** CDN edge, reverse proxy, corporate proxy. Many users share one stored copy, which is why personalized content must be `private` or `no-store`.

## What happens when there is no `Cache-Control`?

Browsers apply **heuristic freshness**: if a response has `Last-Modified` but no explicit lifetime, a browser may treat it as fresh for a fraction (often 10%) of its age. That is how an un-configured server produces confusing "sometimes stale" behaviour. **Always send explicit `Cache-Control`.**

## The standard recipe for a modern web app

| Resource | Header | Why |
|---|---|---|
| Hashed build assets (`app.8f3a1c.js`, `style.4b2d.css`, `/_next/static/…`) | `Cache-Control: public, max-age=31536000, immutable` | The file name changes whenever the content changes, so it can be cached for a year safely |
| HTML documents | `Cache-Control: no-cache` (or `max-age=0, must-revalidate`) | Always check, so users get the new HTML that points to the new asset names; `304` keeps it cheap |
| Images with stable URLs | `max-age=86400` + `stale-while-revalidate=604800` | Fast, refreshes quietly |
| API GET responses, public data | `public, s-maxage=60, stale-while-revalidate=300` | The CDN absorbs traffic; clients still see data within a minute or so |
| API responses, per user | `private, no-cache` (or `no-store` if sensitive) | Never let a shared cache store someone's data |
| Responses that set cookies or carry secrets | `no-store` | Must not be reused |

**Cache busting** means changing the **URL** when content changes (a content hash in the file name), not trying to expire caches. Build tools such as Webpack, Vite and Next.js do this for you. Query-string versions (`app.js?v=3`) work in browsers but some proxies refuse to cache URLs with query strings, so a hash in the file name is more reliable.

```ts
// Next.js: custom headers in next.config.ts
export default {
  async headers() {
    return [
      { source: "/_next/static/:path*", headers: [{ key: "Cache-Control", value: "public, max-age=31536000, immutable" }] },
      { source: "/api/me", headers: [{ key: "Cache-Control", value: "private, no-store" }] },
    ];
  },
};
```

```nginx
# nginx
location ~* \.(js|css|woff2|png|jpg|webp|svg)$ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}
location / {
  add_header Cache-Control "no-cache";
}
```

## The `Vary` header

If the response depends on a request header, say so. `Vary: Accept-Encoding` tells caches to store gzip and Brotli versions separately; `Vary: Origin` is needed when CORS headers differ per origin ([Lesson 04](/browser/lesson-4)). A missing `Vary` can serve the wrong variant. `Vary: Cookie` or `Vary: *` effectively disables shared caching, which is sometimes exactly what you want for personalised pages.

## How reload and navigation behave

| Action | What the browser does |
|---|---|
| Normal navigation / link click | Uses the cache as normal (fresh = no request) |
| **Reload** (F5) | Revalidates the main document and often its subresources |
| **Hard reload** (Ctrl+Shift+R) | Bypasses the cache for everything |
| Back / Forward | Prefers cached copies, even stale ones (and bfcache may restore the whole page) |
| DevTools "Disable cache" | Only while DevTools is open; remember users do not have it |

## Scenario: users see stale data after a deploy

Debug it as a chain of caches, from the browser outward:

1. **Is the HTML cached with a long `max-age`?** Then browsers keep the *old HTML*, which references *old* bundle file names. Fix: HTML must be `no-cache`.
2. **Is the CDN caching the HTML?** Purge it on deploy, or use short `s-maxage` plus `stale-while-revalidate`, and make your pipeline invalidate the changed paths.
3. **Are asset names hashed?** If you ship `app.js` with a long `max-age`, nothing will update it. Use hashed names.
4. **Do old chunks still exist?** Users on the old HTML will request old chunk files. If your deploy deletes them, they hit 404s ("ChunkLoadError"). Keep the previous build's assets available for a while.
5. **Is a Service Worker serving an old shell?** It can pin an old version indefinitely until updated. Ensure it updates and calls `skipWaiting`/prompts a refresh deliberately.
6. **Check `Age` and cache-status headers** (`x-cache`, `cf-cache-status`) in the response: they show whether a CDN served a stored copy and how old it is.
7. **Is the API response cached too aggressively?** Check `Cache-Control` on the data endpoints.

## What a shared CDN must never cache

- Responses with `Set-Cookie` or personal data, unless you key the cache on the user (usually don't).
- Anything tied to an `Authorization` header (do not add `public`).
- Anything marked `private` or `no-store` (CDNs should respect it, but **verify your CDN config**, since rules sometimes override headers).
- Error pages that would be served to everyone for minutes (`5xx` cached by mistake).

## Common mistakes

1. **Long `max-age` on HTML** (users stuck on an old version).
2. **Confusing `no-cache` with `no-store`.**
3. **Caching personalised API responses at the CDN** (one user sees another's data: a serious incident).
4. **Not hashing asset names**, then fighting "clear your cache" support requests.
5. **Relying on heuristic caching** because no header was set.
6. **Deleting old assets immediately on deploy.**
7. **Forgetting `Vary`.**
8. **Treating `304` as free:** it still costs a round trip. For static assets, prefer `immutable` and a long `max-age`.

## Interview questions

### Q1. What's the difference between `no-cache` and `no-store`?

`no-cache` allows storing the response but requires revalidation with the server before each reuse (often resulting in a cheap `304`). `no-store` forbids storing it at all. Use `no-store` for sensitive data and `no-cache` for HTML you want fresh but still cheap to check.

### Q2. How do ETag and `If-None-Match` work, and what is a 304?

The server sends an `ETag` fingerprint with the response. On the next request the browser sends `If-None-Match` with that value. If the content is unchanged, the server returns `304 Not Modified` with no body and the browser reuses its stored copy. It saves bandwidth but still needs a round trip.

### Q3. How do you cache-bust a JS bundle safely?

Put a content hash in the file name (`main.8f3a1c.js`) and serve it with `Cache-Control: public, max-age=31536000, immutable`. When the content changes, the name changes, so the browser fetches the new file. The HTML that references it must be revalidated (`no-cache`) so users learn the new name.

### Q4. Scenario: users see stale data after a deploy. Diagnose it.

Walk outward: HTML `max-age` too long, CDN serving cached HTML (check `Age`/`x-cache`), non-hashed assets, deleted old chunks, a Service Worker pinning the old shell, or cached API responses. Fix the HTML to `no-cache`, hash assets, purge the CDN on deploy, keep old assets briefly, and set explicit API cache headers.

### Q5. What should a shared CDN never cache?

Personalised or authenticated responses (`Set-Cookie`, `Authorization`, user data), anything marked `private` or `no-store`, and transient error responses. A mistake here can serve one user's data to another.

### Q6. What is `stale-while-revalidate` and when is it useful?

It lets a cache serve a stale response immediately while it fetches a fresh one in the background. Users get instant responses and data is refreshed for the next request. Great for dashboards, product listings and public API data where a few minutes of staleness is acceptable.

### Q7. What is the difference between `max-age` and `s-maxage`?

`max-age` applies to all caches including the browser. `s-maxage` applies only to **shared** caches and overrides `max-age` there. It lets you cache at the CDN for longer or shorter than in browsers, for example `max-age=0, s-maxage=300`.

### Q8. Why does `Vary` matter?

It tells caches which request headers change the response (such as `Accept-Encoding` or `Origin`). Without it, a cache could serve a gzip response to a client that cannot decode it, or one origin's CORS headers to another.

## Key takeaways

- **Freshness** (`max-age`) skips the network; **validation** (`ETag`, `304`) saves the download.
- **`no-cache` = revalidate; `no-store` = never keep.**
- The recipe: **hashed assets** `immutable` for a year, **HTML** `no-cache`, **personal data** `private`/`no-store`, **public API data** `s-maxage` + `stale-while-revalidate`.
- Cache-bust by **changing the URL**, not by hoping caches expire.
- Debug stale content by walking the cache chain: browser, Service Worker, CDN, origin.
