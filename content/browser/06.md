> **In one line:** the HTTP method says **what you want to do**, the status code says **what happened**, and the redirect code says **where to go next and whether to keep the method**. Interviewers use these to see if you design APIs deliberately or by habit.

This is vocabulary, but it is vocabulary with consequences: retries, caching, redirects and error handling in the frontend all depend on it. Learn the three properties of methods, the status-code families, and the redirect matrix.

## Methods: safe, idempotent, cacheable

Three properties define how a method behaves:

- **Safe:** it does not change server state (read-only in intent). Crawlers and prefetchers may call safe methods freely.
- **Idempotent:** doing it **once or many times has the same effect on server state**. Safe to retry after a timeout.
- **Cacheable:** a response may be stored and reused.

| Method | Typical use | Safe | Idempotent | Cacheable |
|---|---|---|---|---|
| `GET` | Read a resource | Yes | Yes | Yes |
| `HEAD` | Like GET, headers only | Yes | Yes | Yes |
| `OPTIONS` | Ask what is allowed (CORS preflight) | Yes | Yes | No |
| `PUT` | **Replace** a resource with the body | No | **Yes** | No |
| `DELETE` | Remove a resource | No | **Yes** | No |
| `POST` | Create, or run an action | No | **No** | Rarely |
| `PATCH` | **Partially** modify | No | **Not guaranteed** | No |

### What "idempotent" really means

It is about the **effect on the server**, not the response. `DELETE /orders/7` returns `204` the first time and `404` the second, but the end state ("order 7 does not exist") is the same, so it is idempotent. `PUT /users/5` with the same full body five times leaves the same user.

`POST /orders` creates a **new** order every time, so a retry after a timeout can create a duplicate. That is why payment and order endpoints use an **idempotency key**: the client generates a unique key, sends it as a header, and the server stores the result of the first processing and returns it for repeats.

```http
POST /payments HTTP/2
Idempotency-Key: 3d1c0b6e-6a9e-4c4e-9f0a-1a2b3c4d5e6f
Content-Type: application/json

{ "amount": 4999, "currency": "INR" }
```

### Is `PATCH` idempotent?

Not by definition. `PATCH { "views": 10 }` (set a value, as in JSON Merge Patch) is naturally idempotent, while `PATCH { "op": "increment" }` or a JSON Patch that appends to an array is not. Say: "it depends on the patch semantics, so design it to be idempotent when you can, or use an idempotency key."

### `PUT` vs `POST` for creating

`PUT /users/42` means "make the resource at this URL look like this" (the **client** chooses the ID; repeatable). `POST /users` means "create a new one and the **server** chooses the ID" (not repeatable without a key).

## Status codes by family

| Family | Meaning | Examples you must know |
|---|---|---|
| **1xx** | Informational | `101` Switching Protocols (WebSocket upgrade), `103` Early Hints |
| **2xx** | Success | `200` OK, `201` Created (+ `Location`), `202` Accepted, `204` No Content |
| **3xx** | Redirection | `301`, `302`, `303`, `304`, `307`, `308` |
| **4xx** | The **client** got it wrong | `400`, `401`, `403`, `404`, `405`, `409`, `410`, `412`, `415`, `422`, `429` |
| **5xx** | The **server** failed | `500`, `502`, `503`, `504` |

### Success codes

- `200 OK`: the request worked and there is a body.
- `201 Created`: a resource was created; include a `Location` header with its URL.
- `202 Accepted`: **work is queued, not finished** (a video transcode, a report). Return a status URL the client can poll.
- `204 No Content`: success with no body (typical for `DELETE` and some `PUT`s).

### Client errors that get confused

| Code | Use when | Notes |
|---|---|---|
| `400 Bad Request` | The request is **malformed** (invalid JSON, missing required parameter) | Generic; prefer a more specific code if one fits |
| `401 Unauthorized` | **Not authenticated**: no credentials or invalid ones | The name is misleading. Should include a `WWW-Authenticate` header. The fix: log in |
| `403 Forbidden` | Authenticated, but **not allowed** | Logging in again will not help |
| `404 Not Found` | The resource does not exist | Also used to **hide** that a resource exists (so a user cannot probe for other people's IDs) |
| `405 Method Not Allowed` | The URL exists but not for this method | Send an `Allow` header |
| `409 Conflict` | The request conflicts with the **current state** (duplicate unique value, edit conflict) | Common for optimistic-concurrency failures |
| `410 Gone` | It existed and is permanently removed | Stronger than `404` for SEO |
| `412 Precondition Failed` | An `If-Match` / `If-Unmodified-Since` condition failed | The standard way to implement optimistic locking with ETags |
| `415 Unsupported Media Type` | You sent a `Content-Type` the server cannot handle | |
| `422 Unprocessable Content` | Well-formed but **semantically invalid** (an email without `@`, a negative quantity) | Commonly used for validation errors. Some APIs use `400`; be **consistent** |
| `429 Too Many Requests` | Rate limit hit | Include `Retry-After` |

**401 vs 403 in one line:** `401` = "I don't know who you are." `403` = "I know who you are, and the answer is no."

### Server errors

- `500 Internal Server Error`: an unexpected bug.
- `502 Bad Gateway`: a proxy or gateway got an invalid response from the upstream server.
- `503 Service Unavailable`: overloaded or in maintenance; can send `Retry-After`.
- `504 Gateway Timeout`: the proxy waited too long for the upstream.

Clients may retry `502/503/504` and `429` (with backoff) for idempotent requests. They should not blindly retry `400`/`422`: the same request will fail again.

## Redirects: the 301 / 302 / 303 / 307 / 308 matrix

Two questions describe every redirect: **is it permanent?** and **must the method and body be preserved?**

| Code | Permanent? | Method on the follow-up request | Cached by default? |
|---|---|---|---|
| `301 Moved Permanently` | Yes | May change `POST` to `GET` (historical behaviour) | **Yes** |
| `302 Found` | No (temporary) | May change `POST` to `GET` (historical behaviour) | No (needs explicit freshness) |
| `303 See Other` | No | **Always** becomes `GET` | No |
| `307 Temporary Redirect` | No | **Preserved** (a `POST` stays a `POST` with the same body) | No |
| `308 Permanent Redirect` | Yes | **Preserved** | **Yes** |

Why do `307` and `308` exist? Early browsers turned a `POST` into a `GET` on `301`/`302` redirects, and the specification later acknowledged that practice. `307` and `308` were added so that "temporary/permanent **and keep the method**" has an unambiguous code.

Rules of thumb:

- **Permanent URL change for GET pages (SEO):** `301` (or `308`).
- **Temporary redirect (A/B test, maintenance):** `302` or `307`.
- **After a form `POST`, send the user to a result page** (the **Post/Redirect/Get** pattern, so refresh does not resubmit): `303`.
- **A `POST` endpoint moved and clients must resend the body:** `307` (temporary) or `308` (permanent).

> [!warn] **301 and 308 are cached aggressively.** Once a browser has cached a permanent redirect, it can keep following it without asking your server, even after you remove it. If you are not sure it is permanent, use `302` or `307` first. This is also why URL shorteners that need click analytics often prefer a temporary redirect ([Practical Design Problems, Lesson 01](/design-problems/lesson-1)).

## Other HTTP details worth a sentence

- **Content negotiation:** `Accept`, `Accept-Language`, `Accept-Encoding` ask for a representation; the server answers with `Content-Type` and `Content-Language`. `406` means "I can't produce what you accept."
- **Conditional requests:** `If-None-Match` (caching, `304`) and `If-Match` (safe updates, `412`).
- **Range requests:** `Range: bytes=0-1023` returns `206 Partial Content`, which is how video seeking and resumable downloads work.
- **Errors:** return a consistent machine-readable body. A common standard is "problem details" (`type`, `title`, `status`, `detail`).

## Common mistakes

1. **`200 OK` with `{ "error": ... }` in the body.** Clients, monitors and caches rely on status codes. Use the right 4xx/5xx.
2. **Using `401` for "forbidden."** Use `403`.
3. **Creating resources with `GET`**, or deleting with a link that a prefetcher can follow.
4. **Calling `POST` idempotent**, then retrying payments blindly.
5. **Returning `500` for client mistakes** (bad input).
6. **Permanent redirects (`301`) as a testing tool**, then being unable to undo them in users' browsers.
7. **Redirecting `POST` with `301`/`302`** and losing the body.

## Interview questions

### Q1. Is PUT idempotent? Is PATCH?

`PUT` is idempotent by definition: sending the same full replacement repeatedly leaves the same state. `PATCH` is not guaranteed to be; it depends on the operation. Setting fields to values is idempotent, while "increment" or "append" is not. Make non-idempotent operations safe to retry with an idempotency key.

### Q2. 401 vs 403?

`401` means the request lacks valid authentication (the client should authenticate, and the response should say how via `WWW-Authenticate`). `403` means the client is authenticated but not permitted. Re-authenticating will not change a `403`.

### Q3. Why do 307/308 exist when 301/302 already did?

Because browsers historically changed `POST` to `GET` on `301` and `302`, so there was no code for "redirect and keep the method and body." `307` (temporary) and `308` (permanent) guarantee the method is preserved.

### Q4. Scenario: a POST endpoint has moved. Which redirect keeps the request body?

`308` if the move is permanent, `307` if temporary. `301`/`302` may convert the request to `GET` and drop the body. For a form submission that should end on a results page, use `303` instead.

### Q5. When should you return 202?

When the server accepted the request but the work is not complete: report generation, video processing, bulk imports. Return `202` with a `Location` to a status resource or a job ID the client can poll (or be notified through a webhook).

### Q6. What is the difference between 400 and 422?

`400` signals a malformed request (bad JSON, missing parameter, wrong type). `422` means the request was understood and well-formed but violates business or validation rules. Many APIs use `400` for everything; what matters is documenting it and staying consistent.

### Q7. What is "safe" vs "idempotent"?

Safe methods do not change server state (GET, HEAD, OPTIONS), so they can be prefetched and called freely. Idempotent methods may change state, but repeating them has no additional effect (PUT, DELETE), so they can be retried. Every safe method is idempotent; not every idempotent method is safe.

### Q8. What does 304 mean and what must the server do?

`304 Not Modified` is the answer to a conditional request (`If-None-Match` / `If-Modified-Since`): the stored copy is still valid. The server sends no body, and should repeat the relevant headers like `ETag` and `Cache-Control`.

## Key takeaways

- **Safe** = no state change; **idempotent** = repeatable with no extra effect; know the table by heart.
- Use **the status code to carry the outcome**: `401` = authenticate, `403` = not allowed, `409` = state conflict, `422` = validation, `429` = slow down.
- Redirects are a 2×2: **permanent or temporary** × **method preserved or not**. `307`/`308` keep the method; `303` forces `GET`.
- Make retries safe with **idempotency keys** and by choosing methods deliberately.
