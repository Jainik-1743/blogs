> **In one line:** a **session** is a ticket number that the server looks up in its own records. A **JWT** is a signed note that the client carries, and the server can check it without looking anything up. "Stateless" (the server keeps no records) helps you scale, but it makes instant logout hard.

"Sessions or JWT?" is rarely about which one is *better*. The real questions are: **who holds the data**, how fast you must be able to say "this user is logged out *now*", and what happens when a credential leaks. This lesson gives you the words and a simple rule to decide.

## The two models

### Server-side session (stateful)

"Stateful" means the server remembers things about each user. Think of a cloakroom: you hand in your coat and get a numbered ticket. The ticket is just a number. The coat stays in the cloakroom.

1. The user logs in with a password.
2. The server creates a **session record** (user ID, roles, created time, expiry time). It keeps the record in a store, such as Redis or a database table.
3. The server sends back a random, unguessable **session ID** in a cookie.
4. On every request, the browser sends the cookie. The server **looks up** the record and knows who the user is.

```text
Browser ──Cookie: sid=9f3a…──▶ Server ──lookup sid──▶ Redis { userId: 42, role: "admin" }
```

The cookie holds **no information** about the user. It is only a key. If you delete the record, the key stops working at once.

### JSON Web Token (stateless)

"Stateless" means the server keeps no record. The token itself carries the information. Think of a signed concert wristband: the guard can see it is real just by looking at it. The guard does not need to call the box office.

1. The user logs in.
2. The server builds a **claims** object (`sub`, `exp`, `role` and so on). A claim is one piece of information about the user. The server **signs** the object with a secret or a private key, and sends back the token.
3. The client sends the token on each request (in a header or a cookie).
4. The server **checks the signature and the claims**. It does not need a database lookup. The token itself carries the identity.

```text
Browser ──Authorization: Bearer eyJhbGciOi…──▶ Server ──verify signature──▶ { sub: 42, role: "admin" }
```

## What a JWT actually is

A JWT is three base64url strings joined by dots. (Base64url is just a way to write data as plain text. It is not secret.)

```text
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiI0MiIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTc1MDAwMDAwMH0 . <signature>
        header                                         payload (claims)                              signature
```

Decoded:

```json
{ "alg": "RS256", "typ": "JWT" }
{ "sub": "42", "role": "admin", "iss": "https://auth.example.com", "aud": "my-api", "iat": 1749996400, "exp": 1750000000 }
```

> [!warn] **A signed JWT is not encrypted.** Anyone who has it can base64-decode it and read the payload. The signature only proves two things: the token **was not changed**, and who issued it. Never put secrets, passwords or sensitive personal data in a standard (JWS) token. Encrypted tokens (JWE) exist, but most apps use signed ones.

### Registered claims you must understand

| Claim | Meaning | Check that… |
|---|---|---|
| `iss` | **Issuer**: who created the token | It is the issuer you expect |
| `sub` | **Subject**: the user | It matches a real, active user |
| `aud` | **Audience**: who the token is for | Your API is in the list (this stops a token for service A from working on service B) |
| `exp` | **Expiry** time (Unix seconds) | It is in the future (allow a small difference between clocks, called clock skew) |
| `nbf` | Not valid **before** this time | That time has arrived |
| `iat` | Issued at | The time looks reasonable, if you limit the maximum age |
| `jti` | A unique token ID | It is not on a deny list, if you keep one |

### Signing algorithms

| Type | Algorithms | Who can verify | Typical use |
|---|---|---|---|
| **Symmetric** (one shared secret) | HS256 | Anyone with the secret. They can also **forge** tokens | One service that signs and checks its own tokens |
| **Asymmetric** (a pair of keys) | RS256, ES256, EdDSA | Anyone with the **public** key. Only the holder of the private key can sign | One auth service issues tokens and many services check them (the public keys are published at a JWKS endpoint) |

### JWT attacks interviewers expect you to name

- **`alg: none`**: some simple libraries accepted tokens with no signature. Always set the **allowed algorithms** when you verify.
- **Algorithm confusion**: an attacker changes `RS256` to `HS256` and signs with the *public* key (which everyone can get). A library that trusts the algorithm in the token header will accept it. The fix is the same: fix the expected algorithm for each key.
- **Weak HS256 secrets** can be guessed offline by trying many values (brute force). Use long random secrets (32 or more random bytes) or asymmetric keys.
- **Using `decode` instead of `verify`.** Decoding does not check the signature.
- **Not checking `exp`, `aud` and `iss`.** A valid signature for the wrong audience is still wrong.
- **`kid` header injection**: if you use the key ID to pick a file or run a query, treat it as untrusted input.

```ts
// Verify with explicit expectations (jose library)
import { jwtVerify, createRemoteJWKSet } from "jose";

const jwks = createRemoteJWKSet(new URL("https://auth.example.com/.well-known/jwks.json"));

export async function verifyAccessToken(token: string) {
  const { payload } = await jwtVerify(token, jwks, {
    issuer: "https://auth.example.com",
    audience: "my-api",
    algorithms: ["RS256"], // pin it
  });
  return payload; // exp is checked automatically
}
```

## Head-to-head comparison

| | Server session | JWT |
|---|---|---|
| **Where the data lives** | On the server (Redis or a database) | In the token the client holds |
| **Cost per request** | A lookup in the store | A signature check (uses CPU, no I/O) |
| **Log out or revoke now** | **Easy**: delete the record | **Hard**: the token is valid until `exp`, unless you add a deny list |
| **Role or permission change** | Works on the next request | Old values stay until the token expires or is refreshed |
| **Many servers** | Needs a shared store (Redis) or sticky sessions (the same user always goes to the same server) | Any server can check the token with the key |
| **Size** | A tiny ID | Hundreds of bytes up to kilobytes, sent on every request |
| **Use across services or by third parties** | Awkward (everyone needs access to the store) | **Natural**: pass the token and check it with the public key |
| **If a credential leaks** | Revoke the session | Valid until it expires, so keep it short-lived |
| **Typical fit** | First-party web apps | APIs, service-to-service calls, mobile, third-party access |

## Making JWTs workable: short access tokens plus refresh tokens

You cannot easily take a JWT back. So you make it **expire quickly**. Then you give the user a second, longer-lived credential that can get new tokens.

| | Access token | Refresh token |
|---|---|---|
| Lifetime | Minutes (5 to 15) | Days to weeks |
| Sent to | Your API on every request | **Only** the auth endpoint |
| Stored | In memory, or in a cookie | In an HttpOnly cookie, **and recorded on the server** |
| Can be revoked | Not one by one (it just expires) | **Yes** (delete or flag the record) |

**Refresh token rotation:** each time a refresh token is used, you issue a **new** one and cancel the old one. If someone shows the old token again, it was stolen. Then you revoke the whole token family and force a new login. A quiet theft now becomes something you can detect.

```text
Login ─▶ access (10 min) + refresh R1
...
Access expires ─▶ send R1 ─▶ new access + refresh R2   (R1 now invalid)
Attacker replays R1 ─▶ reuse detected ─▶ revoke R2 and the family ─▶ everyone re-logs in
```

Notice what this really is. The refresh token works like a **server-side session**. Many "stateless" systems quietly bring state back exactly where they need control.

## How to log a user out when you use JWTs

You cannot "delete" a token that is already in someone's hand. These are the practical options:

1. **Delete it on the client** and **revoke the refresh token** on the server. The access token still works until its short expiry. This is often fine.
2. **Deny list** by `jti` in Redis, with a TTL (time to live) equal to the token's remaining life. Now you do a lookup on every request. That is the state you wanted to avoid.
3. **Token version**: store a `tokenVersion` on the user. Put it in the token. When you verify, compare it with the stored value. Adding 1 to it makes every token of that user invalid. This needs one cached lookup.
4. **Use sessions** for that part of the system.

## Choosing: a decision rule

- **First-party web app (Next.js with its own backend), one domain family, and you need instant logout and permission changes:** use **server sessions** in an HttpOnly cookie. This is simpler and safer by default. Libraries such as Auth.js (database sessions) or iron-session fit here.
- **Public API, mobile clients, third-party integrations, or microservices that check a token from a central auth service:** use **short-lived JWT access tokens** (signed with asymmetric keys) plus rotating refresh tokens.
- **Both:** a common pattern is a **session cookie in the browser**. It talks to a **backend-for-frontend** (a server you own that sits between the browser and other APIs). This server holds the tokens and calls other APIs for the user ([Lesson 03](/browser/lesson-3)).

> [!ok] "JWT" and "session" are not opposites in a cookie. You can store a JWT *inside* an HttpOnly cookie. A session ID is also "just a cookie". The real questions are **who holds the state** and **how revocation works**.

## Common mistakes

1. **Choosing JWT because it sounds "modern" or "scalable"** for a single-domain web app. Sessions would be simpler and safer.
2. **Long-lived access tokens** (days or weeks) with no way to revoke them.
3. **Putting sensitive data in the payload.** People forget that anyone can read it.
4. **Skipping `aud` and `iss` checks**, or accepting any `alg` that the token names.
5. **Storing the token in `localStorage`** ([Lesson 03](/browser/lesson-3)).
6. **Putting roles in the token and trusting them for too long.** A demoted admin keeps admin powers until the token expires.
7. **Sequential or guessable session IDs.** Session IDs must come from a cryptographically secure random generator with plenty of entropy (randomness). OWASP recommends at least 64 bits.

## Interview questions

### Q1. How do you log out a user with a JWT?

Delete the token on the client. Revoke the refresh token on the server, so no new access tokens can be made. The access token then dies at its short `exp`. If you need to cancel it at once, keep a deny list of `jti` values (or a token version for each user) and check it on every request. This brings back some state, and you should say so.

### Q2. Is a JWT encrypted?

No. A standard signed JWT (JWS) is only **encoded** and **signed**. Anyone can read the payload by base64-decoding it. The signature only proves that the token is unchanged and who made it. Do not put secrets in it. Use JWE if you need privacy. Or keep sensitive data on the server and put only an ID in the token.

### Q3. Which claims must you validate?

Check `exp` (not expired), `iss` (the issuer you expect), `aud` (made for your API), and `nbf` if it is present. Also check the signature itself, with a fixed algorithm. You can also check that `sub` matches an active user and that `jti` is not revoked.

### Q4. Scenario: a token leaks. What limits the damage?

Several things help. Use a short access-token lifetime. Use refresh-token rotation with reuse detection. Be able to revoke refresh tokens or raise a user's token version. Use narrow scopes and audiences, so the token only works for what it was made for. Watch for strange use. If the signing key itself leaked, rotate (replace) the key.

### Q5. When would you pick sessions for a Next.js app?

Pick sessions when it is a first-party app on your own domain, and the browser talks to your own backend. They are also good when you want simple, instant logout and permission changes. Use an HttpOnly, `Secure`, `SameSite` cookie that holds a random session ID. Back it with Redis or a database. This is hard to misuse, and you do not handle tokens in client code.

### Q6. What is the difference between HS256 and RS256, and why does it matter?

HS256 uses one shared secret to sign and to verify. So every service that can verify can also forge tokens. RS256 uses a private key to sign and a public key to verify. So many services can verify tokens without being able to make them. For systems with many services, prefer asymmetric signing and publish the public keys at a JWKS endpoint.

### Q7. What is refresh-token rotation?

Each time a refresh token is used, the server issues a new one and cancels the old one. If a refresh token that was already used shows up again, it means theft (or a replay). Then the server revokes that token family and forces a new login. This makes stolen refresh tokens easy to detect and limits how long they work.

### Q8. Why is "stateless" often a half-truth?

Some jobs need records on the server: logging out, revoking, rotating refresh tokens, blocking hacked accounts, or changing permissions fast. These records are refresh-token tables, deny lists and token versions. Real systems are stateless for the **hot path** (checking access tokens). They are stateful for **control** (refresh and revocation).

### Q9. Scenario: the product wants a "log out of all devices" button, but auth is JWT-only. How do you build it?

Pure stateless tokens cannot be revoked, so you add a little state. Keep a `tokenVersion` for each user (or a session table) and put the version in the token. "Log out everywhere" adds 1 to the version. Then every older token fails verification the next time it is used. Also revoke refresh tokens on the server, and keep access tokens short-lived so the leftover time is small.

## Key takeaways

- A session is an **opaque key** (it means nothing by itself) to data on the server. A JWT is **signed data** that the client carries.
- JWTs are **readable** and **not encrypted**. Check the signature, `exp`, `iss` and `aud`, with a fixed algorithm.
- The price of stateless checking is **hard revocation**. Reduce the pain with short access tokens, rotating refresh tokens and token versions.
- For a first-party web app, **sessions are usually the simpler and safer default**. JWTs work well across services and for third-party access.
