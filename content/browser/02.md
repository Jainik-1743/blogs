> **In one line:** a **session** is a ticket number the server looks up in its own records; a **JWT** is a signed note the client carries that the server can verify without looking anything up. "Stateless" buys scalability and costs you instant revocation.

"Sessions or JWT?" is rarely about which is *better*. It is about **who holds the state**, how fast you must be able to say "this user is logged out *now*," and what happens when a credential leaks. This lesson gives you the vocabulary and a decision rule.

## The two models

### Server-side session (stateful)

1. The user logs in with a password.
2. The server creates a **session record** (user ID, roles, created time, expiry) in a store, such as Redis or a database table.
3. The server returns a random, unguessable **session ID** in a cookie.
4. On every request, the browser sends the cookie, the server **looks up** the record and knows who this is.

```text
Browser ──Cookie: sid=9f3a…──▶ Server ──lookup sid──▶ Redis { userId: 42, role: "admin" }
```

The cookie contains **no information** about the user. It is only a key. Delete the record and the key becomes useless instantly.

### JSON Web Token (stateless)

1. The user logs in.
2. The server builds a **claims** object (`sub`, `exp`, `role`…), **signs** it with a secret or private key, and returns the token.
3. The client sends the token on each request (in a header or cookie).
4. The server **verifies the signature and claims** with no database lookup. The token itself carries the identity.

```text
Browser ──Authorization: Bearer eyJhbGciOi…──▶ Server ──verify signature──▶ { sub: 42, role: "admin" }
```

## What a JWT actually is

A JWT is three base64url strings joined by dots:

```text
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiI0MiIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTc1MDAwMDAwMH0 . <signature>
        header                                         payload (claims)                              signature
```

Decoded:

```json
{ "alg": "RS256", "typ": "JWT" }
{ "sub": "42", "role": "admin", "iss": "https://auth.example.com", "aud": "my-api", "iat": 1749996400, "exp": 1750000000 }
```

> [!warn] **A signed JWT is not encrypted.** Anyone holding it can base64-decode and read the payload. The signature only proves it **was not modified** and who issued it. Never put secrets, passwords or sensitive personal data in a standard (JWS) token. Encrypted tokens (JWE) exist, but most apps use signed ones.

### Registered claims you must understand

| Claim | Meaning | Validate that… |
|---|---|---|
| `iss` | **Issuer**: who created it | It is the issuer you expect |
| `sub` | **Subject**: the user | It maps to a real, active user |
| `aud` | **Audience**: who it is for | Your API is in the list (stops a token for service A working on service B) |
| `exp` | **Expiry** (Unix seconds) | It is in the future (allow small clock skew) |
| `nbf` | Not valid **before** | The time has arrived |
| `iat` | Issued at | Reasonable, if you enforce max age |
| `jti` | Unique token ID | Not on a deny list, if you keep one |

### Signing algorithms

| Type | Algorithms | Who can verify | Typical use |
|---|---|---|---|
| **Symmetric** (shared secret) | HS256 | Anyone with the secret, who can then also **forge** tokens | One service signing and verifying its own tokens |
| **Asymmetric** (key pair) | RS256, ES256, EdDSA | Anyone with the **public** key; only the private-key holder can sign | An auth service issues tokens, many services verify them (published via a JWKS endpoint) |

### JWT attacks interviewers expect you to name

- **`alg: none`**: some naive libraries accepted unsigned tokens. Always pin the **allowed algorithms** on verification.
- **Algorithm confusion**: an attacker changes `RS256` to `HS256` and signs with the *public* key (which is public). A library that trusts the token's header will accept it. Again: pin the expected algorithm per key.
- **Weak HS256 secrets** can be brute-forced offline. Use long random secrets (32+ random bytes) or asymmetric keys.
- **Using `decode` instead of `verify`.** Decoding does not check the signature.
- **Not validating `exp`, `aud`, `iss`.** A valid signature on the wrong audience is still wrong.
- **`kid` header injection**: if you use the key ID to select a file or query, treat it as untrusted input.

```ts
// Verify with explicit expectations (jose library)
import { jwtVerify, createRemoteJWKSet } from "jose";

const jwks = createRemoteJWKSet(new URL("https://auth.example.com/.well-known/jwks.json"));

export async function verifyAccessToken(token: string) {
  const { payload } = await jwtVerify(token, jwks, {
    issuer: "https://auth.example.com",
    audience: "my-api",
    algorithms: ["RS256"], // pin it
  });
  return payload; // exp is checked automatically
}
```

## Head-to-head comparison

| | Server session | JWT |
|---|---|---|
| **State lives** | On the server (Redis/DB) | In the token the client holds |
| **Per-request cost** | A store lookup | A signature check (CPU, no I/O) |
| **Logout / revoke now** | **Easy**: delete the record | **Hard**: valid until `exp` unless you add a deny list |
| **Role or permission change** | Takes effect on the next request | Stale until the token expires or is refreshed |
| **Scaling across servers** | Needs a shared store (Redis) or sticky sessions | Any server can verify with the key |
| **Token size** | Tiny ID | Hundreds of bytes to kilobytes, sent on every request |
| **Cross-service / third-party use** | Awkward (everyone needs store access) | **Natural**: pass the token, verify with the public key |
| **Leaked credential** | Revoke the session | Valid until expiry, so keep it short-lived |
| **Typical fit** | First-party web apps | APIs, service-to-service calls, mobile, third-party access |

## Making JWTs workable: short access tokens plus refresh tokens

Because you cannot easily take a JWT back, you make it **expire quickly** and issue a second, longer-lived credential to get new ones.

| | Access token | Refresh token |
|---|---|---|
| Lifetime | Minutes (5 to 15) | Days to weeks |
| Sent to | Your API on every request | **Only** the auth endpoint |
| Stored | In memory, or a cookie | HttpOnly cookie, **and recorded server-side** |
| Revocable | Not individually (it just expires) | **Yes** (delete or flag the record) |

**Refresh token rotation:** every time a refresh token is used, issue a **new** one and invalidate the old. If an old token is presented again, someone has stolen it: revoke the whole token family and force a login. This turns a quiet theft into a detectable event.

```text
Login ─▶ access (10 min) + refresh R1
...
Access expires ─▶ send R1 ─▶ new access + refresh R2   (R1 now invalid)
Attacker replays R1 ─▶ reuse detected ─▶ revoke R2 and the family ─▶ everyone re-logs in
```

Notice what this really is: the refresh token behaves like a **server-side session**. Most "stateless" systems quietly reintroduce state exactly where they need control.

## How to log a user out when you use JWTs

You cannot "delete" a token already in someone's hand. The practical options:

1. **Delete it from the client** and **revoke the refresh token** server-side. The access token still works until its short expiry. Often acceptable.
2. **Deny list** by `jti` in Redis with a TTL equal to the token's remaining life. You now do a lookup per request, which is the state you were avoiding.
3. **Token version**: store `tokenVersion` on the user. Put it in the token; on verification compare it with the stored value. Incrementing it invalidates every token for that user (needs one cached lookup).
4. **Use sessions** for that part of the system.

## Choosing: a decision rule

- **First-party web app (Next.js with its own backend), one domain family, need instant logout and permission changes:** use **server sessions** in an HttpOnly cookie. It is simpler and safer by default. Libraries such as Auth.js (database sessions) or iron-session fit here.
- **Public API, mobile clients, third-party integrations, microservices verifying a token issued by a central auth service:** use **short-lived JWT access tokens** (signed asymmetrically) plus rotating refresh tokens.
- **Both:** a common pattern is a **session cookie in the browser** talking to a **backend-for-frontend** that holds tokens and calls downstream APIs on the user's behalf ([Lesson 03](/browser/lesson-3)).

> [!ok] "JWT" and "session" are not opposites in a cookie. You can store a JWT *inside* an HttpOnly cookie, and a session ID is also "just a cookie." The real questions are **who holds the state** and **how revocation works**.

## Common mistakes

1. **Choosing JWT because it is "modern" or "scalable"** for a single-domain web app that would be simpler and safer with sessions.
2. **Long-lived access tokens** (days or weeks) with no revocation path.
3. **Putting sensitive data in the payload**, forgetting it is readable.
4. **Skipping `aud` and `iss` checks**, or accepting whatever `alg` the token declares.
5. **Storing the token in `localStorage`** ([Lesson 03](/browser/lesson-3)).
6. **Putting roles in the token and trusting them for long.** A demoted admin keeps admin powers until expiry.
7. **Sequential or guessable session IDs.** Session IDs must come from a cryptographically secure random generator with plenty of entropy (OWASP recommends at least 64 bits).

## Interview questions

### Q1. How do you log out a user with a JWT?

Delete it on the client and revoke the refresh token on the server, so no new access tokens can be minted; the access token then dies at its short `exp`. If you need immediate invalidation, keep a deny list of `jti` values (or a per-user token version) and check it on each request, accepting that this reintroduces some state.

### Q2. Is a JWT encrypted?

No. A standard signed JWT (JWS) is only **encoded** and **signed**. Anyone can read the payload by base64-decoding it; the signature just proves integrity and origin. Do not put secrets in it. Use JWE if you need confidentiality, or keep sensitive data on the server and put only an ID in the token.

### Q3. Which claims must you validate?

`exp` (not expired), `iss` (expected issuer), `aud` (meant for your API), and `nbf` if present, plus the signature itself with a pinned algorithm. Optionally check `sub` maps to an active user and `jti` is not revoked.

### Q4. Scenario: a token leaks. What limits the damage?

A short access-token lifetime, refresh-token rotation with reuse detection, the ability to revoke refresh tokens or bump a user's token version, narrow scopes and audiences so the token only works for what it was issued for, and monitoring for anomalous use. Rotate signing keys if the key itself leaked.

### Q5. When would you pick sessions for a Next.js app?

When it is a first-party app on your own domain, the browser talks to your own backend, and you want simple, instant logout and permission changes. An HttpOnly, `Secure`, `SameSite` cookie holding a random session ID, backed by Redis or a database, is hard to misuse and avoids token handling in client code.

### Q6. What is the difference between HS256 and RS256, and why does it matter?

HS256 uses one shared secret for signing and verifying, so every verifier could also forge tokens. RS256 uses a private key to sign and a public key to verify, so you can let many services verify tokens without giving them the power to mint them. For multi-service systems, prefer asymmetric signing and publish the public keys via a JWKS endpoint.

### Q7. What is refresh-token rotation?

Each time a refresh token is exchanged, the server issues a new one and invalidates the old. If an already-used refresh token appears again, it indicates theft (or a replay), so the server revokes that token family and forces re-authentication. It makes stolen refresh tokens detectable and limits their lifetime.

### Q8. Why is "stateless" often a half-truth?

To log out, revoke, rotate refresh tokens, block compromised accounts or change permissions quickly, you need server-side records: refresh-token tables, deny lists, token versions. Real systems are stateless for the **hot path** (verifying access tokens) and stateful for **control** (refresh and revocation).

## Key takeaways

- A session is an **opaque key** to server state; a JWT is **signed data** the client carries.
- JWTs are **readable** and **not encrypted**. Validate the signature, `exp`, `iss` and `aud`, with a pinned algorithm.
- The price of stateless verification is **hard revocation**. Mitigate with short access tokens, rotating refresh tokens and token versions.
- For a first-party web app, **sessions are usually the simpler and safer default**. JWTs shine across services and for third-party access.
