> **In one line:** there is no perfectly safe place for a browser credential. `localStorage` exposes it to **XSS**; a cookie exposes you to **CSRF**. A senior answer picks a pattern, names what it still leaves open, and says what mitigates the rest.

This is the lesson that separates "I store the JWT in localStorage because the tutorial did" from "here is the threat model and the trade-off." You need two attacks and four patterns.

## The two attacks

### XSS: cross-site scripting

The attacker gets **their JavaScript to run on your origin**: through unsanitised user content, a vulnerable dependency, a compromised third-party script or a DOM sink you forgot. From that moment the script is *you* as far as the browser is concerned.

What it can do:

- **Read anything JavaScript can read**: `localStorage`, `sessionStorage`, non-HttpOnly cookies, tokens held in variables, the DOM (including personal data on screen).
- **Act as the user**: call your API with `fetch`; the browser attaches the session cookie automatically, **HttpOnly or not**.
- **Rewrite the page**: show a fake login form and capture the password.

### CSRF: cross-site request forgery

The attacker does **not** run code on your site. They get the **victim's browser to send a request to your site from somewhere else**, and the browser helpfully attaches the cookies.

```html
<!-- On evil.example, while the victim is logged in to bank.example -->
<form action="https://bank.example/transfer" method="POST" id="f">
  <input name="to" value="attacker" /><input name="amount" value="5000" />
</form>
<script>document.getElementById("f").submit()</script>
```

The attacker can **cause** an action but cannot **read** the response (the same-origin policy blocks that). So CSRF targets state-changing endpoints that rely only on "the cookie is present."

> [!note] **Bearer tokens in an `Authorization` header are not sent automatically.** Code must attach them, so a forged cross-site request has no token. That is why the localStorage-plus-header pattern has no CSRF problem, and why its whole risk concentrates on XSS.

## What each storage choice exposes

| Where the credential lives | Stolen by XSS? | Used by XSS (acting as the user)? | Vulnerable to CSRF? |
|---|---|---|---|
| `localStorage` / `sessionStorage` token | **Yes**, and reusable from the attacker's own machine | Yes | No (not auto-sent) |
| Non-HttpOnly cookie | **Yes** | Yes | Yes |
| **HttpOnly** cookie | **No** (cannot be read) | **Yes** (browser attaches it to the script's requests) | Yes, unless defended |
| JS variable in memory | Harder, but a script on the page can still call the same API path | Yes | No |

Read the HttpOnly row carefully. It is the most misunderstood fact in this topic: **HttpOnly prevents token theft, not account abuse.** An XSS payload cannot walk away with the cookie, so the attacker loses the ability to use it later from elsewhere, but it can still perform actions *while the victim's tab is open*. HttpOnly limits the blast radius; **preventing XSS** is the real control.

## Defending against CSRF (when you use cookies)

Layer these; none is the single answer.

1. **`SameSite` cookies.**
   - `Lax`: the cookie is **not** sent on cross-site `POST`, `fetch`, iframes or images, but **is** sent on top-level cross-site navigations that use safe methods (clicking a link to your site).
   - `Strict`: never sent on cross-site requests, including a click on a link from another site (the user can look logged out on arrival).
   - `None`: always sent; requires `Secure`; use only when you truly need cross-site cookies.
2. **CSRF tokens.** The server issues an unpredictable token tied to the session and requires it on state-changing requests, in a header or a hidden form field. The attacker's site cannot read it (same-origin policy), so it cannot forge the request. Variants: synchronizer token (stored server-side) and signed double-submit cookie.
3. **Verify `Origin` (and `Referer`)** on unsafe requests. Browsers set `Origin` on cross-site `POST`s and attackers cannot forge it from a browser.
4. **Fetch Metadata headers** (`Sec-Fetch-Site`): reject state-changing requests where it says `cross-site`.
5. **Require a custom header** (for example `X-Requested-With`) for JSON APIs. A cross-site page cannot add custom headers without triggering a CORS preflight that your server refuses.
6. **Never change state on `GET`.** A `<img src="/delete?id=3">` would otherwise work under `Lax`.

### Where `SameSite=Lax` falls short

- **Same-site is not same-origin.** `a.example.com` and `b.example.com` are the **same site**. XSS (or a subdomain takeover) on a sibling subdomain can send authenticated requests to yours with the cookie attached.
- **`GET` requests with side effects** still ride along on top-level navigations.
- **Browser quirks:** some browsers allow a short grace window for cookies with no explicit `SameSite` on top-level cross-site `POST`. Set it **explicitly**.
- **Older or non-supporting clients** ignore it. Keep a CSRF token for sensitive operations.

## Defending against XSS (when anything is exposed)

- **Escape output by default.** React escapes interpolated values. The danger zones are `dangerouslySetInnerHTML`, `innerHTML`, `href` / `src` values from users (`javascript:` URLs), and unsanitised markdown ([Lesson 07](/browser/lesson-7)).
- **Sanitise** HTML you must render (an allow-list sanitiser such as DOMPurify).
- **Content Security Policy** to block inline and untrusted scripts, so injected markup cannot execute.
- **Trusted Types** to make dangerous DOM sinks reject plain strings.
- **Vet dependencies and third-party scripts.** A compromised script is XSS you invited.

## Four patterns that hold up

### Pattern 1: HttpOnly session cookie (the strong default for first-party apps)

```http
Set-Cookie: __Host-sid=…; Path=/; Secure; HttpOnly; SameSite=Lax
```

- Token theft by XSS: **blocked**.
- CSRF: handled by `SameSite` plus a CSRF token or Origin check on unsafe requests.
- Server renders and API calls are authenticated the same way. Simplest to reason about.

### Pattern 2: short-lived access token in memory plus HttpOnly refresh cookie (SPA talking to an API)

```text
Page load ─▶ POST /auth/refresh (refresh cookie sent automatically, SameSite + CSRF check)
          ◀─ { accessToken }  (kept in a JS variable, never persisted)
API calls ─▶ Authorization: Bearer <accessToken>
Reload    ─▶ the access token is gone, so call /auth/refresh again
```

- The refresh cookie cannot be read by XSS and is only sent to the auth endpoint (scope it with `Path=/auth`).
- The access token is not in storage, so stealing it requires code running at that moment, and it expires in minutes.
- Cost: a refresh call on every page load; some complexity around concurrent requests.

### Pattern 3: backend-for-frontend (BFF)

The browser never sees an access token. It holds only a session cookie to **your own backend**, which keeps the tokens and calls downstream APIs on the user's behalf.

```text
Browser ──session cookie──▶ Next.js server (BFF) ──Bearer token──▶ Resource APIs
                               │
                               └─ tokens stored server-side (encrypted session / Redis)
```

- XSS cannot steal tokens, because there are none in the browser.
- One place to handle refresh, scopes and logging. It is the pattern the OAuth browser-app guidance recommends for most cases.
- In Next.js, route handlers or server actions act as the BFF; the downstream API stays private.

### Pattern 4: bearer token in `localStorage` (and when it is defensible)

Simple, no CSRF, works across domains. But any XSS exfiltrates a reusable credential. Defensible only for low-risk apps, when paired with **short expiry**, strict CSP, minimal third-party scripts, and an accepted risk. OWASP's guidance is that session identifiers and tokens should not be kept in `localStorage` or `sessionStorage`. In an interview, if you choose it, say so *and* state the exposure.

| Pattern | XSS steals token? | CSRF risk | Complexity | Good for |
|---|---|---|---|---|
| HttpOnly session cookie | No | Needs defence | Low | Most first-party web apps |
| Memory access + HttpOnly refresh | Hard | Refresh endpoint needs defence | Medium | SPAs with a separate API |
| BFF | No tokens in browser | Session cookie needs defence | Medium | Sensitive apps, many downstream APIs |
| `localStorage` bearer | **Yes** | None | Low | Low-risk apps, accepted trade-off |

## Scenario: the SPA calls an API on another domain

The frontend is on `app.example.com` and the API is on `api.otherdomain.com`. What now?

1. **Best:** make it same-site. Put the API behind your own domain (`api.example.com`) or proxy it through your Next.js server (a rewrite or BFF). Then cookies are first-party and `SameSite=Lax` works.
2. If it must be cross-site: the cookie needs `SameSite=None; Secure`, the request needs `credentials: "include"`, the API must send `Access-Control-Allow-Origin: <exact origin>` plus `Access-Control-Allow-Credentials: true` ([Lesson 04](/browser/lesson-4)), you **must** add CSRF tokens, and you will fight third-party cookie blocking in browsers.
3. Or use bearer tokens with the memory-plus-refresh or BFF pattern and accept the extra moving parts.

## Common mistakes

1. **"HttpOnly makes us safe from XSS."** It only prevents *reading* the cookie.
2. **"We use JWT in a cookie, so no CSRF."** A cookie is sent automatically, so CSRF applies no matter what is inside it.
3. **Relying on `SameSite=Lax` alone** while sibling subdomains host user content.
4. **State-changing `GET` endpoints.**
5. **CORS used as CSRF protection.** CORS restricts *reading* responses; a simple cross-site `POST` is still sent.
6. **Putting the refresh token in `localStorage`.** It is the longest-lived, most valuable secret.
7. **Skipping logout cleanup:** not revoking the refresh token server-side.

## Interview questions

### Q1. Why does OWASP say not to put JWTs in localStorage?

Because `localStorage` is readable by any JavaScript on the origin. One XSS bug, or one compromised third-party script, lets an attacker copy the token and reuse it from anywhere until it expires. There is also no way to restrict it the way an `HttpOnly` cookie can be restricted from script access.

### Q2. Does an HttpOnly cookie stop XSS?

No. It stops **cookie theft**, not **session abuse**. Injected script can still call your API and the browser will attach the cookie. HttpOnly narrows the damage (no long-term theft), but you still must prevent XSS with escaping, sanitisation and CSP.

### Q3. How does `SameSite=Lax` mitigate CSRF, and where does it fall short?

It withholds the cookie from cross-site subrequests such as `POST`, `fetch`, images and iframes, which covers the classic forged form. It falls short for same-site (sibling subdomain) attackers, for state-changing `GET` requests that arrive via top-level navigation, and in clients with different or older behaviour. Pair it with a CSRF token or Origin check for sensitive actions.

### Q4. Scenario: your SPA calls an API on another domain. How do you store auth safely?

Prefer making the API same-site through your domain or a proxy and using an HttpOnly `Lax` session cookie. Otherwise use a BFF that holds tokens server-side, or keep a short-lived access token in memory with an HttpOnly refresh cookie scoped to the auth path. If you must use cross-site cookies, add `SameSite=None; Secure`, exact-origin CORS with credentials and CSRF tokens.

### Q5. What is a backend-for-frontend and why use one for auth?

A server component you own that sits between the browser and downstream APIs. The browser holds only a session cookie to the BFF; the BFF stores and refreshes the OAuth tokens and calls APIs for the user. Tokens never reach JavaScript, which removes the main XSS-theft path and centralises security logic.

### Q6. How does a CSRF token work, and why can't the attacker's page read it?

The server generates an unpredictable value bound to the user's session and embeds it in the page or returns it in a response. State-changing requests must send it back (header or field). Another origin cannot read your pages or API responses because of the same-origin policy, so it cannot learn the value and cannot forge a valid request.

### Q7. Is CORS a CSRF defence?

No. CORS controls whether a page may **read** a cross-origin response. A cross-site `POST` form submission is sent regardless. Preflight-triggering custom headers can incidentally block some forged requests, but you should not rely on CORS for CSRF protection.

### Q8. Is JWT-in-a-cookie vulnerable to CSRF?

Yes. Cookies are attached automatically, so any cookie-based authentication needs CSRF defences, regardless of what the cookie contains.

## Key takeaways

- **XSS** runs the attacker's code as you; **CSRF** makes your browser send requests you did not intend. They need different defences.
- `localStorage` tokens: no CSRF, but **stolen by XSS**. HttpOnly cookies: **not stealable**, but need **CSRF defences**, and XSS can still *use* the session.
- Strong defaults: **HttpOnly session cookie** (first-party), **memory access token + HttpOnly refresh cookie** (SPA + API), or a **BFF** (sensitive apps).
- Make cross-domain APIs **same-site** when you can.
- Always layer: escape and sanitise, CSP, `SameSite`, CSRF tokens or Origin checks, short token lifetimes.
