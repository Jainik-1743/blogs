> **In one line:** The browser works out *where* the page lives, opens a *secure connection* to it, *asks* for it, and *turns* the response into pixels. Caches can skip almost every step along the way.

A junior answer to this question is "DNS lookup, then the server sends HTML." A senior answer walks through each layer, says **where time is spent**, says **where caching skips work**, and says **which tool shows it**. This lesson builds that answer step by step. Every other lesson in this series zooms into one part of this map.

## The map (memorize this first)

```text
You press Enter
  │
  ├─ 1. Input handling      → Is it a URL or a search? Normalize it.
  ├─ 2. Before the network  → HSTS, Service Worker, HTTP cache, bfcache
  ├─ 3. DNS                 → domain name  → IP address
  ├─ 4. Connection          → TCP handshake (or QUIC for HTTP/3)
  ├─ 5. TLS                 → encryption and certificate check
  ├─ 6. HTTP request        → GET / with headers and cookies
  ├─ 7. Server work         → CDN → load balancer → app → DB → response
  ├─ 8. Response            → status, headers, compressed HTML
  ├─ 9. Parsing             → HTML → DOM, CSS → CSSOM, JS execution
  ├─ 10. Rendering          → style → layout → paint → composite
  └─ 11. After load         → hydration, lazy resources, interactivity
```

Keep this map in your head during the interview and walk it top to bottom. You can then zoom into whichever layer the interviewer cares about.

## Step 1: Input handling

When you type into the address bar, the browser first decides **what you meant**:

- `react.dev` looks like a domain, so it is treated as a URL.
- `how to use useState` is treated as a search query and sent to your default search engine.
- `localhost:3000` is treated as a URL with a port.

It then **normalizes** the URL: it adds a scheme if you left it out, lowercases the host, and converts international domain names to Punycode (for example, `मेरा.com` becomes an `xn--` form).

**Why seniors mention it:** autocomplete and *prediction* start work early. Chrome may already be resolving DNS or preconnecting while you type, because it predicts you will press Enter. That is why a site you visit often feels faster than its raw numbers suggest.

## Step 2: Before the network (the shortcuts)

This is where senior answers stand out. Several layers can answer the request **without touching the network at all**.

### 2a. HSTS: forcing HTTPS

If the domain sent a `Strict-Transport-Security` header before, or is on the browser's **HSTS preload list**, the browser upgrades `http://` to `https://` internally. No insecure request is sent. (Chrome shows this as a `307 Internal Redirect` in DevTools.)

> **Interview angle:** without HSTS, the very first `http://` request can be intercepted on public Wi-Fi before the server's redirect to HTTPS arrives. HSTS closes that gap.

### 2b. Service Worker

If the site registered a Service Worker, it can **intercept the request** and answer from its own cache. This is how PWAs work offline. It runs before the normal HTTP cache.

### 2c. HTTP cache

The browser checks its disk and memory cache using the rules in `Cache-Control`:

- **Fresh** (still within `max-age`): served instantly with no network request.
- **Stale but has an `ETag` or `Last-Modified`**: the browser asks the server "has it changed?" and gets a cheap `304 Not Modified` if it has not.

HTML is usually *not* cached for long. Hashed assets like `main.a1b2c3.js` often are (`max-age=31536000, immutable`). [Lesson 05](/browser/lesson-5) goes deep on this.

### 2d. Back/forward cache (bfcache)

When you press Back, the browser can restore the **entire page from memory**, including its JavaScript state, so it appears instantly. An `unload` event listener or `Cache-Control: no-store` can make a page ineligible.

## Step 3: DNS (name to IP address)

Computers connect to IP addresses, not names. DNS resolution checks a chain of caches, from closest to farthest:

1. **Browser DNS cache**
2. **OS cache** (and the `/etc/hosts` file)
3. **Recursive resolver**: your ISP, or something like `1.1.1.1` or `8.8.8.8`
4. If the resolver does not have it cached, it asks a **root server** ("who handles `.dev`?"), then the **TLD server** ("who handles `react.dev`?"), then the **authoritative server** ("`react.dev` is at `76.76.21.21`")

Each answer comes with a **TTL** (time to live) that says how long it may be cached. (The DevOps series covers this in its DNS lesson.)

**Senior details:**

- A cold DNS lookup can take tens to hundreds of milliseconds. A cached one is close to zero.
- `<link rel="dns-prefetch" href="https://api.example.com">` resolves a third-party domain early.
- Modern browsers may use **DNS over HTTPS (DoH)** so the lookup is encrypted.
- With a CDN, DNS often returns the IP of the **nearest edge server**, not your origin. Geography is decided here.

## Step 4: Connection (TCP or QUIC)

### HTTP/1.1 and HTTP/2: TCP

TCP needs a **three-way handshake** before any data is sent:

```text
Browser → SYN       → Server
Browser ← SYN-ACK   ← Server
Browser → ACK       → Server     (1 round trip spent)
```

One **round trip (RTT)** is the time for a packet to reach the server and come back. A user in Ahmedabad hitting a server in the US might have an RTT of about 250 ms, so the handshake *alone* costs 250 ms. This is why CDNs matter: they bring the server physically closer.

### HTTP/3: QUIC over UDP

HTTP/3 runs on **QUIC**, which is built on UDP. QUIC combines the transport and TLS handshakes, so a new connection is ready after about **1 RTT instead of 2**. It also avoids TCP's **head-of-line blocking**: one lost packet no longer stalls every stream on the connection.

**Senior detail:** connections are **reused**. HTTP/2 and HTTP/3 send many requests over one connection (multiplexing), so the handshake cost is usually paid once per origin. That is why spreading assets across many domains ("domain sharding") was an HTTP/1.1 trick that now *hurts*.

## Step 5: TLS (the padlock)

For HTTPS, the browser and server negotiate encryption. With **TLS 1.3**:

1. The browser says hello, lists the ciphers it supports, and sends its key share.
2. The server responds with its key share and its **certificate**.
3. The browser **verifies the certificate**: is it signed by a trusted Certificate Authority, valid for this domain, and not expired?
4. Both sides derive the same session keys, and encrypted HTTP can begin.

TLS 1.3 needs **1 RTT** (TLS 1.2 needed 2). Resumed sessions can use **0-RTT**, which sends data immediately but is replayable, so it is only safe for idempotent requests.

**Running total for a cold HTTPS visit over TCP:** DNS + 1 RTT (TCP) + 1 RTT (TLS) before the first byte of the request is even sent. On a 250 ms RTT, that is **500 ms or more of pure setup**.

> **Fix in the interview:** `<link rel="preconnect" href="https://cdn.example.com">` does DNS + TCP + TLS early for an origin you know you will need.

## Step 6: The HTTP request

Now the browser sends the actual request:

```http
GET / HTTP/2
Host: react.dev
User-Agent: Mozilla/5.0 ...
Accept: text/html,application/xhtml+xml
Accept-Encoding: gzip, br, zstd
Accept-Language: en-IN,en;q=0.9
Cookie: session_id=abc123
```

**Senior details:**

- **Cookies are attached automatically** for that domain, subject to `SameSite`, `Secure` and `Domain` rules. That is the root of CSRF ([Lesson 03](/browser/lesson-3)).
- `Accept-Encoding` tells the server the browser can decompress Brotli or gzip.
- For a *navigation*, the browser also sends headers like `Sec-Fetch-Mode: navigate` that servers can use for security decisions.

## Step 7: Server work (the TTFB story)

The request rarely goes straight to "the server." A typical production path:

```text
Browser → CDN edge → (cache hit? return now) → Load balancer → App server
        → (auth, business logic) → DB / Redis / external APIs → render HTML → back
```

The time from sending the request to receiving the first byte of the response is **TTFB (Time to First Byte)**. It includes the network trip *and* all server work.

For a Next.js app, what happens here depends on the rendering mode:

| Mode | What the server does | TTFB |
|---|---|---|
| Static (SSG) | Serves pre-built HTML from the CDN | Very low |
| ISR | Serves cached HTML and revalidates in the background | Low |
| SSR (dynamic) | Runs data fetching and the React render per request | Depends on the slowest data call |
| Streaming SSR | Sends the shell immediately, streams the rest | Low first byte, content arrives progressively |

**Senior detail:** `103 Early Hints` lets a server tell the browser "start fetching these CSS files and fonts" *before* the final response is ready, using think-time that would otherwise be wasted.

## Step 8: The response

```http
HTTP/2 200
Content-Type: text/html; charset=utf-8
Content-Encoding: br
Cache-Control: no-cache
Set-Cookie: theme=dark; Path=/; Secure; SameSite=Lax
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'
```

The browser:

- reads the **status** (a `301` or `302` sends it back to Step 3 with a new URL; this redirect chain is a hidden performance cost),
- **decompresses** the body,
- stores any cookies,
- applies security headers (HSTS, CSP),
- and starts **parsing immediately**. It does not wait for the full HTML to download. HTML is streamed.

## Step 9: Parsing (HTML to DOM, CSS to CSSOM)

### Building the DOM

The HTML parser reads bytes, then characters, then tokens, then nodes, and ends with the **DOM tree**.

### The preload scanner

While the main parser is busy (or blocked), a **preload scanner** looks ahead in the raw HTML and starts downloading `<img>`, `<link>` and `<script>` resources early. This is a big reason why resources declared in HTML load faster than ones injected later by JavaScript.

### CSS is render-blocking

The browser will not paint until it has the **CSSOM**, because painting without styles would show a flash of unstyled content. A large or slow CSS file therefore delays the first paint.

### JavaScript is parser-blocking (by default)

A plain `<script src="app.js">` **stops HTML parsing** until the script is downloaded *and* executed, because the script might call `document.write` or read the DOM.

| Script type | Download | Executes | Blocks parsing? | Order kept? |
|---|---|---|---|---|
| `<script>` | Immediately | Immediately when downloaded | **Yes** | Yes |
| `<script async>` | In parallel | As soon as downloaded | Only while executing | **No** |
| `<script defer>` | In parallel | After parsing finishes, before `DOMContentLoaded` | No | Yes |
| `<script type="module">` | In parallel | Deferred by default | No | Yes |

> **Rule of thumb:** use `defer` for app code that needs the DOM, and `async` for independent scripts like analytics.

## Step 10: Rendering (the critical rendering path)

Once the browser has a DOM and a CSSOM:

1. **Style:** combine them into the **render tree** (only visible nodes; `display: none` is excluded).
2. **Layout (reflow):** calculate the exact position and size of every box.
3. **Paint:** fill in pixels: text, colors, borders, images, shadows.
4. **Composite:** combine painted layers in the right order, often on the GPU.

**Key milestones:**

- **FCP (First Contentful Paint):** the first text or image appears.
- **LCP (Largest Contentful Paint):** the main content (hero image or heading) appears. This is a Core Web Vital, and "good" is 2.5 s or less ([Lesson 09](/browser/lesson-9)).

**Senior detail:** animating `transform` and `opacity` can skip layout and paint and only composite, which is why they are smooth. Animating `width`, `top` or `height` triggers layout on every frame ([Lesson 08](/browser/lesson-8)).

## Step 11: After the load (where React apps spend their time)

For a React or Next.js app, "the page is painted" is *not* the end:

- **Hydration:** React downloads the JS bundle, runs your components again on the client, and attaches event handlers to the server-rendered HTML. Until hydration finishes, the button is *visible but not clickable*.
- **Lazy resources:** images below the fold (`loading="lazy"`), code-split chunks and fonts.
- **API calls** from `useEffect` or React Query start, often triggering **more renders**.
- **Interactivity:** how quickly the page responds to clicks is measured by **INP**, which replaced FID as a Core Web Vital in March 2024.

This is why "the HTML arrived fast but the app *feels* slow" is a classic senior scenario (see [Scenario Debugging, Lesson 01](/debugging/lesson-1)).

## Worked example: a cold visit to a Next.js e-commerce site from Ahmedabad

| Step | Time (approx.) | What is happening |
|---|---|---|
| DNS | 40 ms | Resolver lookup, CDN returns the Mumbai edge IP |
| TCP | 15 ms | 1 RTT to the Mumbai edge |
| TLS 1.3 | 15 ms | 1 RTT, certificate verified |
| Request to TTFB | 600 ms | CDN miss, request goes to the origin in Virginia, SSR waits on a product API |
| HTML download | 50 ms | Streamed and Brotli-compressed |
| CSS (blocking) | 120 ms | One 80 KB stylesheet |
| FCP | about 850 ms | Header and skeleton visible |
| Hero image | 400 ms | Discovered late because it is a CSS background |
| LCP | about 1.4 s | Product image painted |
| JS bundle and hydration | 900 ms | 400 KB of JS on a mid-range Android phone |
| Interactive | about 2.3 s | "Add to cart" actually works |

**Where a senior would look:** the 600 ms TTFB (cache the HTML at the edge, or stream it), the late-discovered hero image (use an `<img>` with `fetchpriority="high"` or preload it), and the 900 ms hydration (ship less JS, use Server Components).

The numbers are illustrative. The point is to **break the time down by layer** instead of saying "it's slow."

## Where caching skips steps (summary)

| Cache | Skips | Controlled by |
|---|---|---|
| bfcache | Everything | Avoid `unload` handlers and `no-store` |
| Service Worker | Network entirely | Your service worker code |
| HTTP cache (fresh) | DNS, TCP, TLS, request, server | `Cache-Control: max-age` |
| HTTP cache (revalidate) | Body download | `ETag` or `Last-Modified`, answered with `304` |
| DNS cache | DNS lookup | TTL |
| Connection reuse | TCP and TLS handshakes | HTTP/2 and HTTP/3, keep-alive |
| CDN cache | Origin server work | `Cache-Control: s-maxage`, CDN rules |
| App cache (Redis) | Database work | Your backend |

## Common mistakes in interviews

1. **Starting at "DNS" and stopping at "server sends HTML."** You have skipped the caches before the network and everything after the response, which is where most user-facing time goes in React apps.
2. **Saying "the server responds" with no detail.** Mention the CDN, TTFB and what drives it.
3. **Saying JavaScript is "loaded at the end."** Explain *parser-blocking* versus `defer` and `async`.
4. **Forgetting redirects.** `http` to `https` to `www` can add a full extra round trip or more.
5. **Treating "loaded" as "usable."** Bring up hydration and INP.
6. **No numbers.** Say "on a 250 ms RTT, the TCP and TLS handshakes cost about 500 ms before the first request byte." Numbers signal seniority.

## How to answer in an interview (the 2-minute version)

> "First the browser decides whether the input is a URL, then checks the shortcuts: HSTS to force HTTPS, a Service Worker, the HTTP cache, or bfcache for back navigation. If it has to go to the network, it resolves DNS through browser, OS and resolver caches, opens a TCP connection (or QUIC for HTTP/3), and completes a TLS 1.3 handshake, which costs about two round trips on TCP. It sends the GET request with cookies attached; it likely hits a CDN and maybe an origin server, and the time until the first byte is TTFB. As HTML streams in, the parser builds the DOM while a preload scanner fetches resources early. CSS blocks rendering, and plain scripts block parsing unless they are `defer` or `async`. Then style, layout, paint and composite produce the first paint and LCP. For a React app, hydration makes it interactive, which we measure with INP. When debugging, I would break the time down by these layers in the DevTools network waterfall and Performance panel."

Then **pause and let the interviewer pick a layer to zoom into.**

## Interview questions

### Q1. Walk me through what happens after pressing Enter.

Use the 11-step map above, and keep it in order: input handling, the shortcuts before the network (HSTS, Service Worker, HTTP cache, bfcache), DNS, TCP or QUIC, TLS, the request, server work, the response, parsing, rendering and finally hydration. Mention the caches **before** DNS and hydration **after** paint, since those are the two places weak answers stop short.

### Q2. Where can caching short-circuit this flow?

bfcache, the Service Worker, the HTTP cache (fresh means no request at all; stale means a cheap `304`), the DNS cache, connection reuse, the CDN and a server-side cache such as Redis. See the summary table above for what each one skips.

### Q3. Why does a `<script>` in `<head>` delay first paint, and how do `defer` and `async` differ?

A classic script blocks HTML parsing until it is downloaded and executed, so the DOM is not ready and paint is delayed. `defer` downloads in parallel and runs in order after parsing finishes. `async` downloads in parallel and runs as soon as it is ready, in no guaranteed order. Module scripts behave like `defer` by default.

### Q4. Scenario: TTFB is 1.8 s. What do you check first?

Split network time from server time using DevTools (the Timing tab, "Waiting for server response") and server logs or traces. Then check:

- Is the CDN missing its cache (look for `x-cache` or `cf-cache-status` headers)?
- Are there redirects?
- Is SSR waiting on a slow API or database query?
- Is it a serverless cold start?
- Is the origin far from the user?

Fixes: cache at the edge, stream the HTML, parallelize data fetching, add indexes or a cache layer, and move the region closer to users.

### Q5. What is the difference between DNS prefetch, preconnect and preload?

`dns-prefetch` resolves only the domain. `preconnect` does DNS, TCP and TLS. `preload` actually downloads a specific resource that the current page needs.

### Q6. HTTP/2 vs HTTP/3: what changed and why does it matter?

HTTP/2 multiplexes many requests over one TCP connection, but one lost packet still stalls all of them (TCP head-of-line blocking). HTTP/3 uses QUIC over UDP: streams are independent, and the transport and TLS handshakes are combined, so connection setup is faster.

### Q7. The HTML arrived in 200 ms, but users cannot click "Buy" for 3 seconds. Why?

The JS bundle is too large, hydration is slow on a weak CPU, or long tasks are blocking the main thread. Fix it by shipping less JS (code splitting, Server Components), deferring non-critical scripts and breaking up long tasks. Measure with INP and the Performance panel.

### Q8. What does the browser check in a TLS certificate?

That it chains to a trusted Certificate Authority, matches the domain, is within its validity dates, and has not been revoked.

## Key takeaways

- The journey has **network** costs (DNS, TCP, TLS, TTFB) and **rendering** costs (parsing, CSS blocking, JS, layout, hydration). Seniors cover both.
- **Caching happens at almost every layer.** Name them.
- **Round trips are the hidden tax.** CDNs, connection reuse, HTTP/3 and preconnect all exist to cut them.
- **CSS blocks rendering, JavaScript blocks parsing.** Know `defer` vs `async` cold.
- For React apps, **"painted" is not "interactive."** Hydration and INP finish the story.
- In interviews, **break the time down by layer and use numbers.**
