> **In one line:** a stream moves data **in small pieces** instead of all at once, so a program can handle a 5 GB file with a few dozen megabytes of memory. **Backpressure** is the rule that keeps this safe: a fast source must **slow down when the slow destination says "I am full"**. If you ignore that rule, the pieces pile up in memory, and streams lose their whole point.

In [lesson 2](/nodejs/lesson-2) we read files with `readFile` and saw it loads everything into memory. That is fine for a config file and a disaster for a log file, a video or a database export. Streams are Node's answer, and they sit under `fs`, `http`, `zlib`, `crypto` and child processes. In this lesson we first feel the problem with real memory numbers, then learn the four kinds of streams, then measure backpressure with and without respect for it, then use `pipeline`, the safe way to connect streams. The next lesson, [An HTTP Server From Scratch](/nodejs/lesson-4), uses streams for the request and response.

> [!note] **What I ran / checked.** All code ran on Linux (4 cores, 16 GB RAM) with **Node.js v22.22.0**. I generated a CSV file of 10,000,000 lines, **302 MB** (316,686,660 bytes), and every memory figure comes from `process.memoryUsage().rss` (resident memory) sampled every 5 to 10 ms while the code ran, so the peaks are close, not exact. Timings vary a lot between runs and machines. **Sources I read** (in my own words): the Node.js `stream` API docs (raw markdown from `nodejs/node`, v22.x branch), including the sections on `highWaterMark`, `pipeline`, `finished`, and the backpressure notes under `writable.write()`; the Node.js `http` docs for streaming responses; the libuv design page (for the file thread pool); and the `goldbergyoni/nodebestpractices` README. **Could not read:** the long "Backpressuring in Streams" learn guide on nodejs.org was not fetched, so I rely on the API docs and my own measurements. **Not tested:** web streams (`ReadableStream`) beyond one `fetch` body read, `Duplex` sockets with real network slowness, and Windows. I did not verify any GitHub star counts.

## Words used in this lesson

- **Stream** is an object that sends or receives data in pieces over time.
- **Chunk** is one piece of data in a stream. For files it is a `Buffer`; for text streams with an encoding it is a string; in object mode it is any JavaScript value.
- **Readable** is a source of data you read from (a file, an HTTP request body).
- **Writable** is a destination you write to (a file, an HTTP response, a socket).
- **Duplex** is both readable and writable, like a network socket.
- **Transform** is a duplex stream whose output is a changed version of its input, like gzip or an upper-case filter.
- **Pipe** means connecting the output of one stream to the input of the next.
- **Backpressure** is the signal from a slow reader or writer to a fast one that says "wait, I am full".
- **`highWaterMark`** is the size at which a stream's internal buffer counts as full. It is a hint, not a hard limit.
- **Buffering** means holding chunks in memory while waiting for the other side.
- **`drain` event** is what a writable emits when its buffer has emptied and it is ready for more.
- **Object mode** means a stream carries any JavaScript value instead of bytes or strings.
- **RSS (resident set size)** is the amount of RAM the operating system has given your process right now.

## The problem: reading everything at once

The task is simple: count the lines in the CSV that end with `,2026-01-15`. I wrote the same task two ways. The first reads the whole file as a string and splits it:

```js
import { readFile } from "node:fs/promises";
const text = await readFile(process.argv[2], "utf8");
let count = 0;
for (const line of text.split("\n")) { if (line.endsWith(",2026-01-15")) count++; }
```

The second reads a stream, line by line, with the built-in `readline` module:

```js
import { createReadStream } from "node:fs";
import { createInterface } from "node:readline";
const rl = createInterface({ input: createReadStream(process.argv[2]), crlfDelay: Infinity });
let count = 0;
for await (const line of rl) { if (line.endsWith(",2026-01-15")) count++; }
```

Both scripts sampled the process memory in the background and printed the peak. I ran each twice:

```text
readFile + split: 357143 matches, 8041 ms, peak rss 881 MB
stream + readline: 357143 matches, 4052 ms, peak rss 82 MB
readFile + split: 357143 matches, 6943 ms, peak rss 853 MB
stream + readline: 357143 matches, 3874 ms, peak rss 82 MB
```

Same answer: 357,143 matches. But the whole-file version needed **about 850 to 880 MB** of memory for a 302 MB file, and the stream version needed **82 MB**, and that is nearly the same as an empty Node process plus some buffers (an empty process was about 42 MB on this machine). The stream version was also faster here, because splitting a 300 MB string into ten million line strings is heavy work. Do not take the speed ratio as a law; take the memory result seriously.

It gets worse. A server usually has a memory limit. I ran the whole-file script with the heap limited to 64 MB (`node --max-old-space-size=64`):

```text
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
```

It crashed. The stream version, with the same 64 MB limit, finished normally: `stream + readline: 357143 matches, 3673 ms, peak rss 83 MB`.

If you have 100 users each downloading a file at the same time and you read each file whole, you need 100 times the file size in RAM. With streams you need roughly 100 times a few chunks. That is the reason streams exist.

> [!warn] **A buffer is not limited by the heap setting.** In lesson 2 we saw that `readFile` without an encoding stores the bytes outside the JavaScript heap. The crash above happened because I asked for a *string* of 300 MB plus ten million line strings, which do live on the heap. A raw 302 MB buffer would not hit the heap limit, but it would still use 302 MB of RAM. Streams fix both.

## The four kinds of streams

| Kind | You do | Examples |
|---|---|---|
| Readable | read from it | `fs.createReadStream`, an incoming HTTP request, `process.stdin` |
| Writable | write to it | `fs.createWriteStream`, an HTTP response, `process.stdout` |
| Duplex | read and write (two independent sides) | a TCP socket (`net.Socket`) |
| Transform | write in, read the changed result out | `zlib.createGzip()`, `crypto.createHash()` |

A good picture is a river of water pipes. A Readable is a tap. A Writable is a sink. A Transform is a filter in the middle of the pipe. Water flows, but only as fast as the narrowest pipe can take it.

### Reading: a stream gives you chunks

The easiest way to read a stream today is `for await`:

```js
import { createReadStream } from "node:fs";
let bytes = 0, chunks = 0, peak = 0;
const s = createReadStream("/tmp/lab-nodejs/big.csv");
const timer = setInterval(() => { peak = Math.max(peak, process.memoryUsage().rss); }, 5);
const t0 = performance.now();
for await (const chunk of s) { bytes += chunk.length; chunks++; }
clearInterval(timer);
console.log(`chunks: ${chunks}, first chunk size ${s.readableHighWaterMark} bytes (highWaterMark), total ${(bytes/1048576).toFixed(0)} MB, ${(performance.now()-t0).toFixed(0)} ms, peak rss ${(peak/1048576).toFixed(0)} MB`);
```

```text
chunks: 4833, first chunk size 65536 bytes (highWaterMark), total 302 MB, 639 ms, peak rss 76 MB
```

The 302 MB file arrived as 4,833 chunks of up to 64 KiB each (65,536 bytes). The Node docs say 64 KiB is the default `highWaterMark` for streams of bytes in this version, and 16 for object mode streams. I checked in code:

```text
Writable 65536 Readable 65536 objectMode 16 fs read 65536 fs write 65536
```

Peak memory was 76 MB: the loop touches one chunk at a time. You can pick another chunk size. With `highWaterMark: 1024 * 1024` and an `end` limit of 5 MiB I got exactly 5 chunks of 1 MiB.

There is also the older event style, still common in tutorials and library code:

```js
import { createReadStream } from "node:fs";
const r = createReadStream("/etc/hostname", { encoding: "utf8" });
r.on("data", (c) => console.log("data event, typeof", typeof c, JSON.stringify(c)));
r.on("end", () => console.log("end event"));
r.on("close", () => console.log("close event"));
```

```text
data event, typeof string "vm\n"
end event
close event
```

`data` fires for each chunk, `end` fires when there is no more data, and `close` fires when the underlying file is released. Adding a `data` listener switches the stream to "flowing" mode: it starts pushing chunks to you as fast as it can. Note `{ encoding: "utf8" }` turned chunks into strings. That also fixes the split-character problem from lesson 2, because the stream keeps unfinished bytes for the next chunk.

### Writing: `write()` answers a question

A writable has a method `write(chunk)`. Its **return value** matters more than most beginners think. I made a writable with a tiny `highWaterMark` of 10 bytes and a slow `write` (it finishes each chunk in a later turn of the loop):

```js
const w = new Writable({ highWaterMark: 10, write(c, e, cb) { setImmediate(cb); } });
console.log("write 4 bytes ->", w.write("1234"),
            "| write 4 more ->", w.write("1234"),
            "| write 4 more (12 > 10) ->", w.write("1234"));
console.log("writableLength", w.writableLength, "needDrain", w.writableNeedDrain);
w.on("drain", () => console.log("drain event, length now", w.writableLength));
```

```text
write 4 bytes -> true | write 4 more -> true | write 4 more (12 > 10) -> false
writableLength 12 needDrain true
drain event, length now 0
```

`write()` returns `true` while the stream's internal buffer is below `highWaterMark`. When the buffer goes past it (12 bytes queued, mark is 10), it returns **`false`**. That `false` means: "I have taken your data, but please stop writing until I tell you I am ready". When the buffer is empty again, the stream emits `drain`. That is the whole backpressure mechanism on the writing side: **a `false`, then a pause, then a `drain`**.

Important: a `false` from `write()` does not lose your data. The chunk is accepted and queued. The danger is what happens if you **keep writing anyway**.

## Backpressure, measured

Here is an experiment with a fast producer and a slow consumer. The consumer is a writable that finishes each chunk in a later loop turn (a stand-in for a slow disk or a slow network client). The producer writes 20,000 chunks of 32 KiB each, 625 MiB in total, in a loop. The two versions differ in one thing: whether the loop obeys `write()`.

```js
import { Writable } from "node:stream";
import { once } from "node:events";
const mode = process.argv[2];           // "ignore" or "respect"
const CHUNKS = 20000, SIZE = 32 * 1024;

let consumed = 0;
const slowSink = new Writable({
  write(chunk, enc, cb) { consumed += chunk.length; setImmediate(cb); }
});

for (let i = 0; i < CHUNKS; i++) {
  const ok = slowSink.write(Buffer.alloc(SIZE, 97));
  if (!ok && mode === "respect") await once(slowSink, "drain");   // the only difference
}
```

```text
$ node bp.mjs ignore
ignore: write() returned false 19999 times, waited for drain 0 times
ignore: all chunks handed over after 4547 ms, peak rss so far 685 MB, bytes the sink had finished: 0 MB, buffered inside the writable: 625 MB
ignore: finished at 4634 ms, peak rss 685 MB

$ node bp.mjs respect
respect: write() returned false 10000 times, waited for drain 10000 times
respect: all chunks handed over after 224 ms, peak rss so far 83 MB, bytes the sink had finished: 625 MB, buffered inside the writable: 0 MB
respect: finished at 225 ms, peak rss 83 MB
```

This is the whole lesson in two blocks.

- **Ignoring** `false`: the loop handed over all 625 MB first. The sink had processed **0 MB** by then, because the loop never gave it a turn. Everything, 625 MB, sat in the writable's internal queue. Peak memory: **685 MB**. This is the "memory leak" people describe when a stream-based program uses more and more RAM.
- **Respecting** `false`: the loop paused 10,000 times and waited for `drain`. The sink kept up. Peak memory: **83 MB**, only a little more than an empty process, and the sink finished all 625 MB.

(Why did the ignoring version take 4.5 seconds and the respecting one only 0.2 seconds? My guess is that allocating and holding 625 MB of buffers costs time, but I did not profile it, and I would not claim this speed gap holds on every machine. The memory gap is the reliable lesson.)

One more detail from the output: in the ignoring run `write()` returned `false` 19,999 times, that is for every chunk except the first, because the queue was past the mark from then on. In the respecting run it returned `false` 10,000 times and the loop waited for `drain` every time. I did not dig into why the second count is exactly half.

Now the same thing with a real reader. Here the source is a file stream and the destination a slow writable that takes 2 ms per chunk. First with `pipeline` (which respects backpressure for you):

```js
const src = createReadStream("/tmp/lab-nodejs/big.csv", { end: 50 * 1024 * 1024 - 1 });   // first 50 MiB
const slow = new Writable({
  write(chunk, enc, cb) { /* record src.readableLength and slow.writableLength */ setTimeout(cb, 2); },
});
await pipeline(src, slow);
```

```text
wrote 50 MB in 800 chunks, 1889 ms
most bytes ever waiting inside the reader: 0, inside the writer: 65536
peak rss 66 MB
```

The file reader paused whenever the writer was busy. At most 64 KiB sat inside the writer. The reading side held 0 bytes at the sampled moments. Memory stayed at 66 MB, and the speed was set by the slow writer (about 800 chunks at 2 ms each, 1.9 s). The flow of the whole pipeline matched its slowest member.

And now the broken version, where I read with a `data` event and call `write` without checking:

```js
src.on("data", (chunk) => { slow.write(chunk); });   // ignores the return value, never pauses
src.on("end", () => console.log(`reader finished while the writer still had ${(slow.writableLength / 1048576).toFixed(0)} MB queued`));
```

```text
reader finished while the writer still had 43 MB queued; rss 99 MB
```

The reader finished its 50 MB long before the writer; **43 MB** were still queued in memory, and resident memory had already risen to 99 MB. Scale this to a 3 GB file and a slow client and you get an out-of-memory crash.

**Rule: a `data` handler that writes somewhere must stop when `write()` returns `false`, or you should let `pipeline` do it for you.** The easiest correct design is to not write this code yourself at all.

## `pipe` versus `pipeline`

`readable.pipe(writable)` is the classic way to connect streams. It does handle backpressure, but it has a problem with **errors**. Here is a test: the destination fails on the first chunk, and I look at the source afterwards.

```js
// pipe(): when the destination fails, the source is NOT cleaned up
const src1 = createReadStream(FILE);
const bad1 = new Writable({ write(c, e, cb) { cb(new Error("disk full")); } });
bad1.on("error", (e) => console.log("pipe(): dest error:", e.message));
src1.pipe(bad1);
await sleep(300);
console.log("pipe(): source destroyed?", src1.destroyed, "| closed?", src1.closed);

// pipeline(): everything is destroyed
const src2 = createReadStream(FILE);
const bad2 = new Writable({ write(c, e, cb) { cb(new Error("disk full")); } });
try { await pipeline(src2, bad2); } catch (e) { console.log("pipeline(): rejected with:", e.message); }
await sleep(100);
console.log("pipeline(): source destroyed?", src2.destroyed, "| closed?", src2.closed);
```

```text
pipe(): dest error: disk full
pipe(): source destroyed? false | closed? false
pipeline(): rejected with: disk full
pipeline(): source destroyed? true | closed? true
```

With `pipe`, the destination errored, but the **source file stayed open** (`destroyed: false`). In a server that serves many requests, each failed pipe leaves a file descriptor open. After a while you hit `EMFILE`, too many open files. With `pipeline`, the error went to one place (a rejected promise), and **every stream in the chain was destroyed and closed**.

Use `pipeline` from `node:stream/promises`. It does three jobs: it respects backpressure, it forwards errors to one handler, and it cleans up all streams when anything fails or finishes. The `stream.finished()` helper is useful too, but the Node docs warn that it leaves some event listeners hanging after the callback, so use `pipeline` where you can.

You can cancel a pipeline with an `AbortSignal`. I started a pipeline over the 302 MB file with a slow writer and aborted after 50 ms:

```text
AbortError | bytes handled before abort: 2490368 | source destroyed: true
```

It stopped after about 2.4 MB and the source was destroyed. This is useful to stop work when a client disconnects.

### Compressing a file with a pipeline

Here is the typical real use: read, transform, write.

```js
import { createReadStream, createWriteStream } from "node:fs";
import { pipeline } from "node:stream/promises";
import { createGzip } from "node:zlib";

await pipeline(
  createReadStream("/tmp/lab-nodejs/big.csv"),
  createGzip(),
  createWriteStream("/tmp/lab-nodejs/big.csv.gz"),
);
```

```text
gzip done in 7026 ms; peak rss 73 MB
original 302 MB -> gz 53 MB
```

A 302 MB file was compressed to 53 MB with a peak memory of 73 MB. The compression work runs off the main JavaScript thread, so the event loop stays free while it works. I did not measure loop lag during this run, so take that as the documented design, not as my measurement. Reading it back is the mirror image with `createGunzip()`.

## Writing your own Transform

A Transform takes input chunks, does something, and pushes output chunks. Three ways to write one. The class way:

```js
import { Readable, Writable, Transform } from "node:stream";
import { pipeline } from "node:stream/promises";

const source = Readable.from(["apple\n", "banana\n", "cherry\n"]);
const upper = new Transform({
  transform(chunk, enc, cb) { cb(null, chunk.toString().toUpperCase()); }
});
const out = [];
const sink = new Writable({ write(chunk, enc, cb) { out.push(chunk.toString()); cb(); } });
await pipeline(source, upper, sink);
console.log(out);
```

```text
[ 'APPLE\n', 'BANANA\n', 'CHERRY\n' ]
```

`Readable.from(iterable)` turns an array or generator into a readable stream. In `transform`, you call `cb(error, output)` when done with the chunk.

The modern way is an **async generator** inside `pipeline`. It is much shorter and respects backpressure automatically (the generator is only asked for the next value when downstream is ready):

```js
async function* numbered(src) { let n = 1; for await (const chunk of src) yield `${n++}: ${chunk}`; }
const out2 = [];
await pipeline(Readable.from(["a\n", "b\n"]), numbered, async function (src) { for await (const c of src) out2.push(c); });
console.log(out2);
```

```text
[ '1: a\n', '2: b\n' ]
```

**Object mode** streams carry JavaScript objects instead of bytes. Set `objectMode: true` on the sides that need it:

```js
const objs = Readable.from([{ id: 1 }, { id: 2 }, { id: 3 }]);
const doubled = new Transform({ objectMode: true, transform(o, e, cb) { cb(null, { ...o, twice: o.id * 2 }); } });
const got = [];
await pipeline(objs, doubled, new Writable({ objectMode: true, write(o, e, cb) { got.push(o); cb(); } }));
console.log(got);
```

```text
[ { id: 1, twice: 2 }, { id: 2, twice: 4 }, { id: 3, twice: 6 } ]
```

In object mode the `highWaterMark` counts objects (16 by default, as we saw), not bytes.

### The classic bug: chunks are not lines

A chunk boundary can fall in the **middle of a line**. If you split each chunk on `\n` and count, you get the wrong answer. I tested it on the 10,000,000-line file:

```js
// WRONG: treat each chunk as a list of whole lines
let naive = 0;
for await (const chunk of createReadStream(FILE, { encoding: "utf8" })) naive += chunk.split("\n").filter(Boolean).length;

// RIGHT: keep the unfinished last piece for the next chunk
class LineSplitter extends Transform {
  constructor() { super({ readableObjectMode: true }); this.rest = ""; }
  _transform(chunk, enc, cb) {
    const parts = (this.rest + chunk.toString()).split("\n");
    this.rest = parts.pop();                 // the last piece may be unfinished
    for (const p of parts) this.push(p);
    cb();
  }
  _flush(cb) { if (this.rest) this.push(this.rest); cb(); }
}
```

```text
true line count (wc -l): 10000000
naive chunk.split count : 10004536
LineSplitter count      : 10000000
```

The naive count was off by 4,536. The file has 4,832 chunk boundaries, and almost every one fell in the middle of a line. A cut line is counted as two pieces, so each cut adds one. The `LineSplitter`, which saves the unfinished tail and finishes it with the next chunk, got exactly 10,000,000. In real code, use `readline` (as in the first test) or a tested library for lines. The lesson is the idea: **a chunk is a piece of the stream, not a unit of your data**. The same is true for JSON: you cannot `JSON.parse` a chunk.

## Streams in HTTP

An HTTP server's request is a Readable and its response is a Writable. So you can stream a big file to a client without loading it:

```js
http.createServer(async (req, res) => {
  if (req.url === "/whole") { const data = await readFile(FILE); res.setHeader("content-length", data.length); res.end(data); }
  else if (req.url === "/stream") { res.setHeader("content-type", "text/csv"); await pipeline(createReadStream(FILE), res).catch(() => {}); }
  // ...
}).listen(3102);
```

I started a fresh server for each route, downloaded the 302 MB file with `curl`, then asked the server for the peak memory it had seen (the base before any request was 54 MB):

```text
== whole (fresh server)
peak rss so far: 54 MB
downloaded 316686660 bytes in 0.886968s
peak rss so far: 358 MB

== stream (fresh server)
peak rss so far: 54 MB
downloaded 316686660 bytes in 0.788890s
peak rss so far: 97 MB
```

Both sent all 316,686,660 bytes in about the same time. The whole-file route grew the server by 304 MB (one copy of the file) **per request in flight**. The streaming route grew by 43 MB. With ten simultaneous downloads the first would need over 3 GB.

When the client disconnects midway, `pipeline` is built to destroy the file stream, as in the failing-writable test above, so no file handle is left open. I did not run a disconnect test against this server. That is why I used `pipeline` and not `pipe` there. The `.catch(() => {})` is only there because I do not want an unhandled rejection for a client that left. In a real server, you would log the error.

Also notice that the streaming response has no `content-length` header: Node sends it with `Transfer-Encoding: chunked`. The headers I got from `curl -D -` on the `/stream` route:

```text
HTTP/1.1 200 OK
content-type: text/csv
Date: Sun, 11 Oct 2026 18:51:42 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked
```

No `Content-Length`, because the size is not known when the headers go out. The client reads chunk by chunk until the server says it is finished. We saw this in action in lesson 4, where I read a response with three parts spaced 200 ms apart and got them as they arrived.

## When not to use streams

Streams add code and complexity. Do not use them everywhere.

- **Small data.** A 2 KB config file: `readFile` is simpler and just as good.
- **Formats that need all the data.** `JSON.parse` needs the full text. For big JSON, switch the format to one JSON object per line (NDJSON) and read it with the line approach, or use a streaming parser from npm.
- **Random access.** If you need the middle of a file, use `FileHandle.read` with a position (lesson 2), not a full stream.

And remember the size of the problem: if the whole data fits easily in memory, and there are few users, the simple code is the correct choice. If the data is unbounded or user-controlled (uploads, exports, logs), use streams.

## Web streams, in one paragraph

Browsers have their own stream API (`ReadableStream`, `WritableStream`) and Node has it too. `fetch()` returns a body that is a web `ReadableStream`; in lesson 4 I read it with `for await (const chunk of r.body)` and it worked. The Node docs list `Readable.fromWeb`, `Readable.toWeb` and similar helpers to convert between the two kinds. The ideas (chunks, backpressure) are the same. This series uses Node streams, because that is what `fs`, `http` and `zlib` give you.

### Answers

1. In my 10-million-line test, `readFile` gave about 850 MB peak and `readline` about 82 MB. Your numbers differ, but the 10x ratio should look similar.
2. Use `createReadStream`, an async generator `async function* (src) { for await (const c of src) yield c.toString().toUpperCase(); }`, `createGzip()` and `createWriteStream("out.txt.gz")`. To read back, `createReadStream`, `createGunzip()`, then in the last step print `chunk.toString().slice(0, 100)` for the first chunk only and stop.
3. Without waiting you will see a large `writableLength` (all strings, close to the total size you wrote). With `await once(w, "drain")` after each `false`, it stays near 100.
4. Even with an `error` listener on the source, `pipe` does not destroy the other streams when one fails, so the source stays open (as in the output above). Only `pipeline` (or manual `destroy` calls) cleans up.
5. `async function* dropEmpty(src) { for await (const line of src) if (line.trim() !== "") yield line; }`. Place it between a line source and the destination.
6. Calling `ac.abort()` in the signal handler makes `pipeline` reject with `AbortError` and destroy all streams. The output file is closed but contains whatever was written before the abort, so delete or rename a partial file in a `catch`.

## Interview questions

### Q1. What is a stream and why would you use one instead of `readFile`? (Must know)

A stream delivers data in chunks over time instead of as one big value. I use it when the data is large or unbounded, so memory use stays small. In my test, counting lines in a 302 MB file with `readFile` plus `split` peaked at about 850 MB, while a stream with `readline` peaked at 82 MB, and the first one crashed with a 64 MB heap limit. For a tiny file `readFile` is simpler, and I would keep it.

### Q2. What is backpressure? (Must know)

It is the way a slow consumer tells a fast producer to wait. For a writable, `write()` returns `false` when its internal buffer is over `highWaterMark`. The producer should stop writing and resume when the writable emits `drain`. If the producer ignores this, the chunks pile up in memory. In my test, ignoring it with a slow sink queued 625 MB in memory (peak 685 MB), and respecting it kept peak memory at 83 MB for the same work.

### Q3. What does `highWaterMark` do, and what is its default? (Must know)

It is the size at which a stream's internal buffer is considered full. For a readable it controls how much it reads ahead and the chunk size for file streams. For a writable it decides when `write()` starts returning `false`. It is a threshold for signalling, not a hard cap: in my test, a writable with a mark of 10 accepted 12 bytes and just returned `false`. The default is 64 KiB for byte streams in this Node version (I checked it in code) and 16 objects in object mode.

### Q4. Why prefer `stream.pipeline` over `.pipe()`? (Must know)

`pipeline` forwards an error from any stream to one callback or promise and destroys every stream in the chain when something fails or ends. With `pipe`, errors are not forwarded, and in my test the source file stayed open after the destination failed. In a server that leaks file descriptors on every failed request until `EMFILE`. `pipeline` also accepts async generators and an `AbortSignal`.

### Q5. How do you read a huge file line by line? (Must know)

I use `readline.createInterface({ input: createReadStream(file) })` with `for await (const line of rl)`. That keeps memory flat. I would not split chunks on `\n` myself, because chunk boundaries can cut a line. In my test, naive splitting of each chunk counted 10,004,536 lines in a file with exactly 10,000,000.

### Q6. What is the difference between a Transform and a Duplex stream? (Senior signal)

Both are readable and writable. A Duplex has two independent sides, like a TCP socket where what you send is unrelated to what you receive. A Transform links them: the readable output is computed from the writable input, like gzip or an upper-case filter. For a Transform, I implement `transform(chunk, enc, cb)`; for a Duplex I implement `read` and `write` separately.

### Q7. How would you send a 4 GB file in an HTTP response without crashing the server? (Must know)

I stream it: `await pipeline(createReadStream(file), res)`. Memory use per request stays at a few chunks, and `pipeline` stops reading when the client is slow, and closes the file if the client disconnects. In my measurement, sending a 302 MB file with `readFile` grew the server by about 304 MB per request, and streaming grew it by 43 MB. I would also set `content-type` and, if I know the size, `content-length` (using `stat`).

### Q8. What does it mean if `write()` returns `false`? Is data lost? (Trap)

No data is lost. The chunk is accepted and queued. `false` is only a request to stop writing until the `drain` event. The mistake is to keep writing anyway, which grows the internal queue and uses more and more memory. The correct approach is `await once(stream, "drain")` before the next write, or use `pipeline` so I do not manage it.

### Q9. A Node process reading a file slowly grows memory until it dies. What do you check? (Senior signal)

I check for a reader that writes somewhere without respecting backpressure: a `data` handler calling `write()` and ignoring the result, or a loop pushing into a stream. I look at `writableLength` of the destination. I also check for `Buffer` accumulation (like `chunks.push(chunk)` for a whole body), and for `pipe()` chains where an error leaves streams open. In my own test, a `data` event handler without a pause left 43 MB queued when the reader had already finished.

### Q10. Can you `JSON.parse` each chunk of a streamed JSON file? (Trap)

No. A chunk is a piece of bytes, not a unit of data. It can end in the middle of a key, a number or a multi-byte character. I either collect the full body when I know it is small and bounded, use a streaming JSON parser for large input, or use a line-based format such as NDJSON where each line is a complete JSON value and I split on newlines with a line reader.

### Q11. How do you stop a stream pipeline when the client disconnects or a timeout fires? (Senior signal)

I pass an `AbortSignal` to `pipeline`, or rely on `pipeline`'s handling of a destroyed destination, which destroys the source as well. In my test, an aborted pipeline rejected with `AbortError` after about 2.4 MB, and the source stream was destroyed. I make sure to handle the rejection so that it does not become an unhandled rejection, and to remove half-written output files.

### Q12. Why does async iteration (`for await (const chunk of stream)`) respect backpressure automatically? (Senior signal)

Because the stream is only asked for the next chunk when the loop body has finished with the previous one. While my loop body is busy or awaiting something slow, the stream stops reading further ahead than its `highWaterMark`. An async generator in a `pipeline` works the same way: the generator is resumed only when downstream wants more. That is why generators are a safer way to write transforms than manual `data` handlers.

## Key takeaways

- Streams process data in chunks, so memory use depends on the chunk size, not the data size: 82 MB versus about 850 MB for a 302 MB file, and a crash under a 64 MB heap limit for the non-stream version.
- `write()` returning `false` means "wait for `drain`". Ignoring it makes the data pile up: 625 MB queued and a 685 MB peak in my test, against 83 MB when respected.
- Use `pipeline` from `node:stream/promises`. It handles backpressure, forwards errors, destroys all streams on failure and supports `AbortSignal`. `pipe()` left the source open when the destination failed.
- Chunks are not lines and not JSON values. Use `readline`, a `LineSplitter`, or an encoding on the stream. The naive version miscounted by 4,536 lines.
- Async generators are the shortest way to write a transform inside `pipeline`.
- In HTTP, stream big responses: about 43 MB extra versus about 304 MB extra for one 302 MB download.
- Do not use streams for tiny data or formats that need all of the data at once.
