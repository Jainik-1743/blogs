> **In one line:** **Prisma** is a tool that turns your database tables into typed TypeScript code, and **SQL** is the language the database itself understands. A 4+ year engineer must know both: how Prisma 7 is set up, how its migrations and transactions behave, where it hides traps, and which SQL tools (joins, window functions, CTEs, locks) it cannot write for you.

This lesson does not repeat [Backend, Lesson 07](/backend/lesson-7) (indexes, `EXPLAIN`, ACID, isolation levels) or [Backend, Lesson 08](/backend/lesson-8) (the N+1 problem, DataLoader, connection pool basics). Read those first if you need them. Here we go to the things interviewers ask next: the Prisma 7 setup, the migration workflow, modeling, extensions, safe raw SQL, and the SQL features that separate a junior from a senior.

> [!note] **Which Prisma?** Every example here ran on **Prisma 7.10** with PostgreSQL 16. Prisma 7 is the stable line. A newer **Prisma 8** is a *release candidate* (a nearly final test version) at the time of writing, and `npm install prisma` may already install it. Pin the major version in a real project: `npm i prisma@7 @prisma/client@7`. Prisma 8 renames files and commands and does not yet have `$extends`, so old and new advice is easy to mix up. See the last section.

## Words used in this lesson

- **An ORM (object-relational mapper)** is a library that lets you read and write database rows as objects in your language. Prisma is one. Think of it as a translator between TypeScript and SQL.
- **A schema file** (`schema.prisma`) is the text file where you describe your models (tables), fields (columns) and relations. Prisma reads it to build the database changes and the typed client.
- **A migration** is a saved, ordered SQL file that changes the database structure, such as "add a column". Together the files form the *migration history*.
- **A driver adapter** is a small package that connects Prisma Client to a database driver, such as `pg` for PostgreSQL. In Prisma 7 you always pass one.
- **A transaction** is a group of database steps that either all succeed or all roll back.
- **Schema drift** means the real database no longer matches what your migration files say it should be.
- **A shadow database** is a temporary empty database that Prisma creates and deletes to check your migrations.
- **A window function** is an SQL function that calculates over a set of related rows *without* collapsing them into one row (like a running total next to each row).
- **A CTE (common table expression)** is a named sub-query written with `WITH name AS (...)`. Think of it as a temporary variable for a query.

## Setting up Prisma 7

Prisma 7 changed the setup. Three things surprise people who learned Prisma 5 or 6.

**1. The database URL moved to `prisma.config.ts`.** The `datasource` block in `schema.prisma` now only names the provider.

```prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}
```

```ts
// prisma.config.ts
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: { path: "prisma/migrations", seed: "tsx prisma/seed.ts" },
  datasource: { url: env("DATABASE_URL") },
});
```

**2. `.env` is not loaded for you.** I removed the `dotenv` line and the CLI stopped with `Cannot resolve environment variable: DATABASE_URL`. Load it yourself.

**3. The client needs a driver adapter and a generated folder.** The `prisma-client` generator requires an `output` path. It writes plain TypeScript into your project, not into `node_modules`. You import from that folder.

```ts
import { PrismaClient } from "./generated/prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
export const prisma = new PrismaClient({ adapter });
```

For SQLite use `PrismaBetterSqlite3` from `@prisma/adapter-better-sqlite3` with `{ url: "file:./dev.db" }`. I ran both. The CLI reported `Query Compiler: enabled`: Prisma 7 plans queries in TypeScript/WASM and the driver runs them, instead of the old Rust query-engine binary.

> [!warn] **Outdated advice.** Many articles say "`migrate dev` also runs `generate` and your seed". That was true before version 7. In Prisma 7, `migrate dev` and `migrate reset` run neither. Run `npx prisma generate` and `npx prisma db seed` yourself. A `postinstall` script for `generate` is common.

## Modeling: relations, enums, JSON, indexes

A **relation** links two models. Prisma stores it as a foreign key (a column that points to another table's row).

| Kind | How you write it | What the database gets |
|---|---|---|
| One-to-one | `userId Int @unique` on one side, `Profile?` on the other | Foreign key with a unique constraint |
| One-to-many | `authorId Int` + `author User @relation(...)` on the many side, `posts Post[]` on the one side | Foreign key on the "many" table |
| Many-to-many, **implicit** | `tags Tag[]` on `Post`, `posts Post[]` on `Tag` | Prisma creates a hidden table `_PostToTag` with columns `A` and `B` |
| Many-to-many, **explicit** | Your own model `PostCategory` with two relations and `@@id([postId, categoryId])` | A normal table you control |

```prisma
model Profile {
  id     Int  @id @default(autoincrement())
  userId Int  @unique
  user   User @relation(fields: [userId], references: [id], onDelete: Cascade)
}

model PostCategory {
  postId     Int
  categoryId Int
  assignedAt DateTime @default(now())
  post       Post     @relation(fields: [postId], references: [id])
  category   Category @relation(fields: [categoryId], references: [id])

  @@id([postId, categoryId])
}
```

**Implicit or explicit?** I use implicit when the link has no data of its own (a post and its tags). I use explicit as soon as the link needs a column (`assignedAt`, `role`, `quantity`), or when I want to query the link table directly. Moving from implicit to explicit later needs a data migration, so I decide early.

**Referential actions** say what the database does when a parent row is deleted. If you write nothing, the defaults are `onDelete: Restrict` for required relations (`SetNull` for optional ones) and `onUpdate: Cascade`. I checked the generated SQL: `Post_authorId_fkey ... ON DELETE RESTRICT ON UPDATE CASCADE`. Deleting a user who still has posts fails with Prisma error `P2003`. The profile above uses `Cascade`, so it disappears with its user.

**Enums, JSON and indexes:**

```prisma
enum Role { USER ADMIN }

model User {
  id       Int   @id @default(autoincrement())
  email    String @unique
  role     Role  @default(USER)
  settings Json?

  @@index([settings], type: Gin)
}

model Post {
  authorId  Int
  createdAt DateTime @default(now())
  @@index([authorId, createdAt])
}
```

- An `enum` becomes a native PostgreSQL enum type (`CREATE TYPE "Role" AS ENUM ...`). Adding a value later is easy; removing one is not.
- `Json` becomes `jsonb`. You can filter inside it with `where: { settings: { path: ["theme"], equals: "dark" } }` (I ran this on PostgreSQL). A `Gin` index (Generalized Inverted Index, built for values with many parts) helps such searches.
- Prisma does **not** index foreign keys in PostgreSQL. Add `@@index([authorId])` yourself ([Backend, Lesson 07](/backend/lesson-7)).
- **Full-text search** on PostgreSQL still needs `previewFeatures = ["fullTextSearchPostgres"]` in the generator. Then `where: { body: { search: "fox & quick" } }` works. For serious search (typo tolerance, ranking) I use a search engine such as Meilisearch rather than the database.

## The migration workflow

Prisma Migrate compares your schema file with your migration history and writes SQL. The commands differ by where you run them.

| Command | Use it | What it does |
|---|---|---|
| `prisma migrate dev` | Local only | Uses the shadow database, applies pending migrations, creates a new one from schema changes, may ask to reset |
| `prisma migrate deploy` | CI and production | Applies pending migration files. Never resets, never creates files, **no shadow database needed** |
| `prisma migrate reset` | Local only | Drops the database, re-applies all migrations. In v7 it does not seed |
| `prisma migrate status` | Anywhere | Compares the history with the `_prisma_migrations` table |
| `prisma db push` | Quick prototypes | Pushes the schema straight to the database with **no migration file** |
| `prisma db pull` | Existing database | Reads the database and writes models (introspection) |
| `prisma migrate resolve` | Fixing history | Marks a migration as applied or rolled back without running it |

### The shadow database and drift

When you run `migrate dev`, Prisma creates a temporary **shadow database**, replays all your migration files in it, and compares the result with your real development database. If they differ, you have **drift**. After it finishes, the shadow database is deleted. The user in your connection string therefore needs the right to create databases locally. Hosted databases often need a manual `shadowDatabaseUrl`.

I created drift on purpose: I ran `ALTER TABLE "Post" ADD COLUMN views ...` by hand. Then:

- `prisma migrate status` said **"Database schema is up to date!"**. It only compares migration *files* with the history table. It does not look at the real tables.
- `prisma migrate dev` said **"Drift detected ... Added column `views`"** and offered a reset.

I fixed it without losing data. I added `views` to the schema, wrote the matching `ALTER TABLE` into a new migration folder by hand, and ran `prisma migrate resolve --applied <folder>`. Then `migrate dev` said "Already in sync". In production I never want a reset, so this "write it down, then mark as applied" path matters.

### Baselining an existing database

**Baselining** means giving a database that already exists, and holds real data, a starting migration that is marked as "already applied". I ran this flow on a database made with plain SQL:

```bash
npx prisma db pull                      # write models from the existing tables
mkdir -p prisma/migrations/0_init
npx prisma migrate diff --from-empty --to-schema prisma/schema.prisma \
  --script > prisma/migrations/0_init/migration.sql
npx prisma migrate resolve --applied 0_init   # do NOT run it, just record it
npx prisma migrate deploy               # "No pending migrations to apply."
```

New developers get the real `0_init` SQL when they build a fresh local database. Production skips it. Later, `migrate dev` generated only the new `ALTER TABLE`.

> [!ok] Edit a generated migration before you apply it when you need something Prisma cannot express: `CREATE INDEX CONCURRENTLY`, a data backfill, or a safe two-step column rename. Use `--create-only` to write the file without applying it. Never edit a migration that is already applied elsewhere: its checksum is stored, and Prisma will complain.

### Seeding

Put the command in `prisma.config.ts` (`migrations.seed`) and run `npx prisma db seed`. Write seeds with `upsert` so you can run them many times. I ran mine twice and got no duplicates.

## Reading and writing data

### `select`, `include`, `omit`

`select` lists the fields you want. `include` adds relations to all default fields. `omit` removes fields from the default set. You cannot use `select` and `include` together at the same level (I got: "Please either use `include` or `select`, but not both"). You *can* nest them: `select` a relation, and `select` inside it.

```ts
const user = await prisma.user.findFirst({
  select: { id: true, email: true, posts: { select: { title: true }, take: 1 } },
});
const safe = await prisma.user.findFirst({ omit: { settings: true, deletedAt: true } });
```

`omit` is the clean way to keep a `passwordHash` out of API responses.

### `relationLoadStrategy`

A **load strategy** says how Prisma fetches relations. With `include: { posts: true }` I counted the SQL statements:

| Setup | Statements for `findMany({ include: { posts: true } })` |
|---|---|
| Default, no preview flag | **2** (one for users, one for posts with `IN (...)`) |
| `previewFeatures = ["relationJoins"]`, default | **1** (`LEFT JOIN LATERAL` with `JSONB_AGG`) |
| flag on, `relationLoadStrategy: "query"` | 2 |
| flag on, `relationLoadStrategy: "join"` | 1 |

Without the flag, passing `relationLoadStrategy` is a validation error ("Unknown argument"). Some articles say `join` is the default. That is only true after you turn the feature on. The docs still call it a preview feature in 7.x. One join query means fewer round trips but repeated parent data inside JSON. Two queries are often better for wide parents with big lists. I measure on real data.

### Nested writes

A **nested write** creates or links related rows in one call, and Prisma wraps it in a transaction.

```ts
await prisma.user.create({
  data: {
    email: "a@x.com",
    profile: { create: { bio: "hi" } },
    posts: { create: [{
      title: "P1",
      tags: { connectOrCreate: [{ where: { name: "js" }, create: { name: "js" } }] },
    }] },
  },
  include: { posts: { include: { tags: true } } },
});
```

`connectOrCreate` links to a tag if it exists, or creates it. For an implicit many-to-many, `tags: { set: [] }` removes every link (I ran it).

### Pagination

**Offset pagination** uses `skip` and `take`. **Cursor pagination** (also called keyset) remembers the last row you saw:

```ts
const page1 = await prisma.post.findMany({ take: 3, orderBy: { id: "asc" } });
const page2 = await prisma.post.findMany({
  take: 3, skip: 1, cursor: { id: page1.at(-1)!.id }, orderBy: { id: "asc" },
});
```

`skip: 1` skips the cursor row itself. The generated SQL uses `WHERE id >= (SELECT id ... = $1) ... OFFSET 1`. On a 300,000-row table in PostgreSQL I measured the same idea in plain SQL: `OFFSET 250000` read 250,020 index entries in about 24 ms, while `WHERE id > 250000 LIMIT 20` read 20 entries in 0.05 ms. The cursor needs a unique, ordered column. See [Practical Design Problems, Lesson 03](/design-problems/lesson-3).

## Transactions

Prisma has two forms.

```ts
// 1. Sequential: an array of queries, run in order in one transaction
const [count, posts] = await prisma.$transaction([
  prisma.user.count(),
  prisma.post.findMany({ take: 1 }),
]);

// 2. Interactive: a function; you can read, decide, then write
await prisma.$transaction(async (tx) => {
  const u = await tx.user.findUniqueOrThrow({ where: { email: "a@x.com" } });
  await tx.post.create({ data: { title: "in-tx", authorId: u.id } });
}, { maxWait: 3000, timeout: 8000, isolationLevel: "Serializable" });
```

| | Sequential `[...]` | Interactive `async (tx) => ...` |
|---|---|---|
| Can use results of earlier steps | No | Yes |
| Holds a connection | Briefly | For the whole function |
| Time limits | — | `timeout` 5000 ms and `maxWait` 2000 ms by default |
| Use when | Independent writes that must succeed together | Read, check, then write |

I forced a duplicate email as the second item of a sequential transaction. It threw `P2002` and the first user was **not** saved. I held an interactive transaction open for 5.5 seconds and got `P2028` after about 5.5 seconds. Inside `tx` you must use `tx`, not the outer `prisma`; the outer client runs *outside* the transaction. Many simple cases need no transaction at all: `update ... data: { views: { increment: 1 } }` is already atomic (it compiles to `SET views = views + $1`).

## Raw queries, safely

Use `$queryRaw` (returns rows) and `$executeRaw` (returns the number of changed rows) when Prisma cannot express the query, such as window functions.

```ts
const evil = "x' OR '1'='1";

await prisma.$queryRaw`SELECT id FROM "User" WHERE email = ${evil}`;               // 0 rows: safe
await prisma.$queryRawUnsafe(`SELECT id FROM "User" WHERE email = '${evil}'`);       // ALL rows: injected!
await prisma.$queryRawUnsafe(`SELECT id FROM "User" WHERE email = $1`, evil);        // 0 rows: safe
```

I ran all three on 5 users: the second returned 5 rows. The tagged template (`` $queryRaw`...` ``) turns each `${value}` into a bound parameter ($1, $2). The `Unsafe` version is safe only when you pass values as parameters and never join strings. More facts I saw:

- Calling `$queryRaw("SELECT 1")` like a normal function fails: it is a *tag* function.
- A table or column name cannot be a parameter. `` SELECT * FROM ${"User"} `` failed with `P2010` (syntax error near `$1`). Check names against an allow-list in code.
- Lists: `` WHERE id IN (${Prisma.join(ids)}) `` with `Prisma.sql` works.
- `count(*)` comes back as a `bigint`. Cast it (`::int`) or convert it, or JSON serialization will fail.

## Extensions replace middleware

**Middleware** (`prisma.$use`) is gone in Prisma 7: `typeof prisma.$use` is `undefined`. Its replacement is **client extensions**, added with `$extends`. An extension can change queries (`query`), add model methods (`model`), add computed fields (`result`) or add client methods (`client`).

### Soft delete, and why it leaks

**Soft delete** means marking a row as deleted (`deletedAt`) instead of removing it. This is the classic extension:

```ts
const xprisma = prisma.$extends({
  query: {
    user: {
      async findMany({ args, query }) {
        args.where = { deletedAt: null, ...args.where };
        return query(args);
      },
    },
  },
});
```

I tested it. `findMany` and `findFirst` hid the deleted user. But:

- `findUnique` still returned the deleted user.
- `count()` still counted them.
- `include: { author: true }` on posts still loaded the deleted author.

The extension only covers the operations you list, on the model you list. Soft delete is easy to start and hard to finish. Alternatives I weigh: a database **view** that shows only live rows, row-level security, or hard deletes plus an audit table. Also remember unique columns: a soft-deleted email still blocks a new signup unless you use a partial unique index (`WHERE deleted_at IS NULL`, written in a hand-edited migration).

## Errors, types, testing

**Error codes** to know: `P2002` unique constraint failed, `P2003` foreign key failed, `P2025` record not found (also thrown by `update` and `findUniqueOrThrow`), `P2028` transaction API error (such as a timeout), `P2010` raw query failed. Check them with `error.code`, or `instanceof Prisma.PrismaClientKnownRequestError`. Map them to HTTP codes in one place ([Backend, Lesson 04](/backend/lesson-4)): `P2002` to `409`, `P2025` to `404`.

**Type safety.** The client types depend on what you ask for. If you `select` only `id` and `email`, then `user.name` is a compile error. To name a result type, use `satisfies` and `GetPayload`:

```ts
import { Prisma } from "./generated/prisma/client";

const postWithAuthor = {
  include: { author: { select: { id: true, name: true } } },
} satisfies Prisma.PostDefaultArgs;

type PostWithAuthor = Prisma.PostGetPayload<typeof postWithAuthor>;
```

I compiled this with `tsc`. The older `Prisma.validator` helper is **not present** in the Prisma 7 generated client, so `satisfies` is the way now.

**Testing.** I test against a real database, not a mock, because the behaviours above (constraints, cascades, error codes) live in the database. A mock would hide them. My pattern with the built-in Node test runner:

```ts
beforeEach(async () => {
  await prisma.$executeRaw`TRUNCATE "User" RESTART IDENTITY CASCADE`;
});

test("unique email is enforced", async () => {
  await prisma.user.create({ data: { email: "t@x.com" } });
  await assert.rejects(
    prisma.user.create({ data: { email: "t@x.com" } }),
    (e: any) => e.code === "P2002",
  );
});
```

Use a separate test database and run `migrate deploy` once before the suite. Mock Prisma only for pure unit tests of business logic, and keep that logic away from the client with a small repository layer.

## Pooling, serverless and Accelerate

In Prisma 7 the **pool** (the set of reusable database connections) belongs to the driver. For `pg` through `PrismaPg`, the defaults are `max: 10` connections and `connectionTimeoutMillis: 0`, which means **wait forever**. I tested with `max: 1` while one transaction held the only connection. A second query was still waiting after 1.5 seconds. With `connectionTimeoutMillis: 500` it failed after about 540 ms with "timeout exceeded when trying to connect". A request that hangs forever is worse than an error, so I always set a timeout.

For serverless, keep the pool small per instance, reuse one client per process, and put a pooler (PgBouncer or your provider's pooler) in front. Use a direct URL for migrations. Details are in [Backend, Lesson 08](/backend/lesson-8).

> [!warn] **Prisma Accelerate** is Prisma's hosted connection pool and cache (`cacheStrategy: { ttl: 60, swr: 10 }`). The current Prisma docs say Accelerate, including hosted Accelerate connections for Prisma Postgres, **will be retired on 1 December 2026**. Many tutorials still recommend it. For new work, use your database provider's pooler and your own cache.

## Core SQL that Prisma will not write for you

Run these in `psql`. I ran every one on PostgreSQL 16 with small tables: `users(id, name, manager_id)` and `orders(id, user_id, total, status, created_at)`.

### Join traps

- **Anti-join (find rows with no match).** `LEFT JOIN ... WHERE o.id IS NULL` and `WHERE NOT EXISTS (...)` both returned the 2 users with no orders.
- **`NOT IN` and `NULL`.** One order had `user_id = NULL`. `WHERE id NOT IN (SELECT user_id FROM orders)` returned **0 rows**, because comparing with `NULL` is "unknown". Use `NOT EXISTS`.
- **A `WHERE` on the right table undoes a `LEFT JOIN`.** `... LEFT JOIN orders o ON o.user_id = u.id WHERE o.status = 'paid'` returned 3 users (the unmatched ones vanished). Moving the test into `ON ... AND o.status = 'paid'` returned all 5.
- **Fan-out.** Join an order with 3 item rows and `sum(total)` gives 300 for an order worth 100. Aggregate first, then join, or use `count(DISTINCT ...)`.
- `count(*)` counts rows (6); `count(user_id)` skips `NULL` (5).

### Window functions

```sql
SELECT user_id, created_at, total,
  sum(total)  OVER (PARTITION BY user_id ORDER BY created_at) AS running,
  row_number() OVER (PARTITION BY user_id ORDER BY total DESC) AS rn,
  lag(total)  OVER (PARTITION BY user_id ORDER BY created_at) AS prev
FROM orders WHERE user_id IS NOT NULL;
```

`PARTITION BY` splits rows into groups. `ORDER BY` inside `OVER` orders inside each group. With ties on values 10, 10, 20: `row_number` gave 1,2,3; `rank` gave 1,1,3 (it skips); `dense_rank` gave 1,1,2 (no gaps). "Top order per user" is `row_number() = 1`, or in PostgreSQL `SELECT DISTINCT ON (user_id) ... ORDER BY user_id, total DESC`, which gave the same rows.

> [!warn] **Frame gotcha.** When a window has `ORDER BY`, the default frame ends at the *current row*. So `last_value(total) OVER (ORDER BY created_at)` returned the current row's value (100, then 50). Add `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` to get the true last value (50 on both rows).

### CTEs, recursion and LATERAL

A recursive CTE walks a tree such as an org chart:

```sql
WITH RECURSIVE tree AS (
  SELECT id, name, 0 AS depth, name::text AS path FROM users WHERE manager_id IS NULL
  UNION ALL
  SELECT u.id, u.name, t.depth + 1, t.path || ' > ' || u.name
  FROM users u JOIN tree t ON u.manager_id = t.id
) SELECT * FROM tree ORDER BY path;   -- Ann > Bob > Di
```

In PostgreSQL 12 and later, a simple CTE is **inlined**: `EXPLAIN` showed one `Seq Scan` with both filters. Write `WITH c AS MATERIALIZED (...)` and it became a separate `CTE Scan`. So "CTEs are an optimization fence" is old advice. **`LATERAL`** lets a sub-query use columns of the row to its left. `CROSS JOIN LATERAL (SELECT ... WHERE o.user_id = u.id ORDER BY created_at DESC LIMIT 1)` gives the latest order for each user, which is a "top N per group" tool.

### Locking in practice

`SELECT ... FOR UPDATE` locks rows ([Backend, Lesson 07](/backend/lesson-7)). Two more options matter:

- **`FOR UPDATE SKIP LOCKED`** skips rows another transaction holds. It is how you build a job queue. I held jobs 1 and 2 in one session. A second session ran the same query and got jobs 3 and 4, with no waiting.
- **`NOWAIT`** fails at once instead of waiting: `ERROR: could not obtain lock on row`.

### One `EXPLAIN` note

On 300,000 rows, `WHERE created_at::date = current_date` used a `Parallel Seq Scan`, because the function on the column hides the index. Compare the column to a range instead (`created_at >= today AND created_at < tomorrow`).

## Prisma 7 and the Prisma 8 release candidate

The Prisma docs say Prisma 8 is a release candidate, with general availability expected in October 2026. In it the schema file is called a *contract* (`contract.prisma`), and the command that makes types is `contract emit`. The docs also list what is *not* available yet, including `$extends`, most nested writes and transaction isolation levels. Prisma 7 keeps getting fixes for 18 months after Prisma 8 is final. So I stay on 7 for production, and I check the version of every article I read.

## Common mistakes

1. Letting `npm install prisma` float to a new major version.
2. Creating a `PrismaClient` per request, or never setting a pool timeout.
3. Using `$queryRawUnsafe` with string concatenation.
4. Trusting `migrate status` as proof of no drift, or running `migrate dev` or `db push` on production.
5. Calling the outer `prisma` inside an interactive transaction.
6. Assuming a soft-delete extension covers `findUnique`, `count` and relations.

## Interview questions

### Q1. What changed in Prisma 7 setup compared with Prisma 5 or 6? (must know)

Four things. The database URL moved from `schema.prisma` to `prisma.config.ts`. The default generator is `prisma-client`, and it needs an `output` folder with plain TypeScript. The client needs a driver adapter, such as `PrismaPg`. And `.env` is not loaded for me, so I import `dotenv/config`. Also `migrate dev` no longer runs `generate` or the seed. I ran a project with the dotenv line removed and the CLI stopped with "Cannot resolve environment variable".

### Q2. What is the difference between `migrate dev`, `migrate deploy` and `db push`? (must know)

`migrate dev` is for my laptop. It creates migration files, uses a shadow database to detect drift, and can reset the database. `migrate deploy` is for CI and production: it only applies files that already exist, never resets, and needs no shadow database. `db push` syncs the schema straight to the database with no migration file. I use it for throwaway prototypes only, because it leaves no history and may drop data.

### Q3. What is the shadow database and when do you need to configure it? (must know)

It is a temporary database Prisma creates during `migrate dev`. Prisma replays all migrations in it and compares the result with my real dev database to find drift and to check data loss. It is deleted afterwards. Locally it just works if my user may create databases. On managed cloud databases I often cannot create one, so I make an empty database myself and set `shadowDatabaseUrl`. Production never needs it.

### Q4. Your teammate changed a column by hand in the dev database. What happens and how do you fix it? (senior signal)

`migrate dev` reports drift, lists the difference, and offers a reset. `migrate status` can still say "up to date", because it only compares migration files with the history table. To fix it without a reset, I put the change into the schema, write the matching SQL into a new migration folder, and run `migrate resolve --applied`. I also ask why someone edited the database by hand.

### Q5. How do you add Prisma Migrate to a database that already has data? (senior signal)

I baseline it. I run `db pull`, create `0_init` with `migrate diff --from-empty --to-schema ... --script`, and run `migrate resolve --applied 0_init`. Production then sees nothing pending, while a fresh database gets the full `0_init` SQL. I test the flow on a copy of production first.

### Q6. Implicit or explicit many-to-many? (must know)

Implicit means Prisma hides the join table (`_PostToTag`, columns `A` and `B`). It suits simple links like tags. Explicit means I write the join model. I choose it when the link needs its own data (`assignedAt`, `role`) or I want to query it directly. Switching later needs a data migration, so I decide early.

### Q7. What is the difference between `select`, `include` and `omit`? Can you use `select` and `include` together? (must know)

`select` lists exactly the fields I want. `include` returns all fields plus chosen relations. `omit` returns all fields except those I name. At one level, `select` and `include` together throw a validation error, but I can nest them. I prefer `select` for API responses, and `omit` to keep fields like `passwordHash` out.

### Q8. Does `include` solve N+1? What is `relationLoadStrategy`? (senior signal)

Yes: instead of one query per row, `include` loads the relation in one extra query (two statements total) or, with the join strategy, in one statement. I counted: 2 statements by default. With the `relationJoins` preview feature on, the default becomes one statement with `LEFT JOIN LATERAL` and `JSONB_AGG`. Then `relationLoadStrategy: "query"` or `"join"` picks per call. Without the flag, the option is rejected. Join means fewer round trips but repeated data; I measure both.

### Q9. Sequential `$transaction([...])` or interactive `$transaction(async tx => ...)`? (must know)

Sequential is an array of queries that run in order and roll back together. It cannot use the result of one step in the next. Interactive gives me a `tx` client, so I can read, decide and write. But it holds a connection for the whole function and has a default 5-second run limit (error `P2028`), and 2 seconds to wait for a connection. I keep interactive transactions short, never call external APIs inside them, and always use `tx`, not the outer `prisma`.

### Q10. How do you stop two requests from overselling the last item in Prisma? (senior signal)

I make the check and the change one step. `updateMany({ where: { id, stock: { gte: 1 } }, data: { stock: { decrement: 1 } } })` and then I check `count`. If it is 0, the item is out of stock. That compiles to a single atomic `UPDATE`. For more complex logic I use an interactive transaction with `SELECT ... FOR UPDATE` through `$queryRaw`, or `Serializable` isolation with retries. A `CHECK (stock >= 0)` constraint is my last safety net. See [Backend, Lesson 07](/backend/lesson-7).

### Q11. How do you write raw SQL safely in Prisma? (must know)

I use the tagged template, `` prisma.$queryRaw`... ${value}` ``, which binds each value as a parameter. With an injection string it returned 0 rows, but `$queryRawUnsafe` with string concatenation returned **all** rows. If I must use the unsafe function, I pass values as `$1` parameters. Table and column names cannot be parameters, so I check them against a fixed list.

### Q12. Middleware is gone. How do you add behaviour to every query now? (must know)

With client extensions: `prisma.$extends({ query, model, result, client })`. `query` wraps operations (soft delete, audit, tenant filters), `model` adds methods, `result` adds computed fields. `$use` is `undefined` in Prisma 7. An extension returns a new client, so I export the extended one and use it everywhere.

### Q13. You added a soft-delete extension. A bug report says deleted users still appear. Why? (trap)

I only wrapped `findMany` and `findFirst`. I tested the same extension: `findUnique`, `count` and nested `include` of a relation still returned the deleted row. Fixes: cover every read operation, including `findUnique`, `count`, `aggregate` and `groupBy`; filter relations through the related model; or use a database view or row-level security so the rule lives in one place. Also a soft-deleted email still blocks a new signup unless I add a partial unique index with `WHERE deleted_at IS NULL`.

### Q14. A serverless function sometimes hangs for a long time under load. What do you check? (trap)

In Prisma 7 with `pg`, the default pool size is 10 and `connectionTimeoutMillis` is 0, so a request waits forever when the pool is empty. I reproduced it with `max: 1`. I set `connectionTimeoutMillis`, size `max` small per instance, reuse one client, and put a pooler in front of the database. I also check for long interactive transactions that hold connections. I do not depend on Prisma Accelerate for new work because the docs say it retires on 1 December 2026.

### Q15. How do you use Prisma error codes in an API? (must know)

I catch `PrismaClientKnownRequestError` in one place and map the code: `P2002` (unique) to `409 Conflict`, `P2025` (not found) to `404`, `P2003` (foreign key) to `409` or `400`. `P2028` is a transaction problem, so it is a `5xx` and I log it. I never return Prisma's raw message to clients, because it can leak table and column names.

### Q16. How do you test code that uses Prisma? (senior signal)

I run integration tests against a real database of the same type as production, because constraints, cascades and error codes are database behaviour. I run `migrate deploy` once, then truncate tables in `beforeEach`. I use a mock only for pure business logic, kept behind a small repository.

### Q17. `NOT IN` returns no rows when it should return some. Why? (trap)

The sub-query contains a `NULL`. Comparing a value with `NULL` is "unknown", so `NOT IN` can never be true. I reproduced this: one order had `user_id = NULL` and `NOT IN` returned 0 rows, while `NOT EXISTS` and `LEFT JOIN ... IS NULL` returned the right 2 users. I use `NOT EXISTS`.

### Q18. Explain `row_number`, `rank` and `dense_rank`, and get the top order per user. (must know)

All three number rows inside a window. With values 10, 10, 20: `row_number` gives 1,2,3 (always unique), `rank` gives 1,1,3 (ties share a number, then a gap), `dense_rank` gives 1,1,2 (no gap). For the top order per user I use `row_number() OVER (PARTITION BY user_id ORDER BY total DESC)` in a sub-query and filter `rn = 1`. In PostgreSQL `DISTINCT ON (user_id)` is shorter and gave the same result. A gotcha: with `ORDER BY` in the window, the default frame ends at the current row, so `last_value` does not return the real last value unless I widen the frame.

### Q19. When would you use a CTE, and are CTEs slow? (senior signal)

I use CTEs to name steps in a long query, and recursive CTEs for trees such as org charts or category paths. In PostgreSQL 12 and later a simple CTE is inlined, so it is not an optimization fence. My `EXPLAIN` showed one scan for the plain CTE and a separate `CTE Scan` only after I wrote `MATERIALIZED`. The old advice "CTEs are always slow in Postgres" is outdated. I add `MATERIALIZED` on purpose when the CTE is expensive and used twice.

### Q20. How do you build a safe job queue in SQL? (senior signal)

I select jobs with `FOR UPDATE SKIP LOCKED` inside a transaction, mark them as taken, and commit. Workers never block each other, and no two get the same job. In my test one session held jobs 1 and 2, and the second got 3 and 4 at once. Plain `FOR UPDATE` would make it wait, and `NOWAIT` would make it fail. I add a retry count and a "locked until" time so jobs from a crashed worker come back.

## Key takeaways

- Pin Prisma to **7** for now. Check the version of every tutorial: `migrate dev` no longer generates or seeds, `$use` and `Prisma.validator` are gone, and the URL lives in `prisma.config.ts`.
- `migrate dev` is local and uses a shadow database; `migrate deploy` is for production. `migrate status` does not detect drift.
- Baseline existing databases with `migrate diff --from-empty`, then `migrate resolve --applied`.
- Use the tagged `$queryRaw`. `$queryRawUnsafe` with string joins is an injection hole.
- Extensions replace middleware, but a soft-delete extension must cover every read path.
- Set a pool timeout. In Prisma 7 with `pg`, the default is to wait forever.
- Know the SQL traps: `NOT IN` with `NULL`, `LEFT JOIN` plus `WHERE`, join fan-out, window frames, `SKIP LOCKED`.
