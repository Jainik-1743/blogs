> **In one line:** test what a **user can see and do**, not how your code is organised. Query by role and text, mock the **network** instead of your own modules, keep end-to-end tests for the few journeys that must never break, and treat tests that break on every refactor as a design smell in the tests.

Backend testing is covered in [Backend, Lesson 11](/backend/lesson-11). This is the frontend half: React components, pages and flows.

## The testing trophy

```text
            ▲  E2E            a handful: login, checkout, the revenue paths
           ███  Integration    the bulk: pages/features with real components, mocked network
          █████  Unit          pure logic: formatters, reducers, hooks with tricky logic
        ███████  Static        TypeScript + ESLint catch a whole class of bugs for free
```

The "trophy" (as opposed to a strict pyramid) puts most effort into **integration tests**: render a feature the way a user meets it, with real child components, real state management and a **fake network**. They give the best confidence per test, because bugs usually live in the *wiring* between pieces.

| Level | Tools | Tests | Speed |
|---|---|---|---|
| **Static** | TypeScript, ESLint (`react-hooks`, `jsx-a11y`) | Types, hook rules, accessibility lint | Instant |
| **Unit** | Vitest or Jest | Pure functions, reducers, selectors, custom hooks | Milliseconds |
| **Integration / component** | Vitest or Jest + **React Testing Library** + **MSW** | Features and pages from the user's point of view | Tens of ms each |
| **End-to-end** | **Playwright** (or Cypress) | Full app in a real browser | Seconds each |

## React Testing Library's guiding principle

> The more your tests resemble the way your software is used, the more confidence they can give you.

That means:

- **Query like a user (or a screen reader) would**, in this order of preference: `getByRole` (with an accessible name), `getByLabelText`, `getByPlaceholderText`, `getByText`, `getByDisplayValue`, then `getByAltText`/`getByTitle`, and `getByTestId` only as a **last resort**.
- **Interact like a user**: `@testing-library/user-event` simulates typing, clicking and tabbing realistically (focus, key events, pointer events), unlike calling handlers directly.
- **Assert on what the user perceives**: text on screen, enabled/disabled, `aria-*` states, navigation, not component state or private functions.
- **Avoid testing implementation details**: internal state, hook return values of a component, which child received which prop, class names.

`getByRole` has a bonus: if you cannot find your element by role and name, a screen-reader user probably cannot either, which is a real accessibility bug ([Lesson 06](/frontend-depth/lesson-6)).

### A component test

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LoginForm } from "./LoginForm";

test("shows a validation error and then submits valid credentials", async () => {
  const user = userEvent.setup();
  const onSubmit = vi.fn();
  render(<LoginForm onSubmit={onSubmit} />);

  await user.click(screen.getByRole("button", { name: /sign in/i }));
  expect(await screen.findByText(/email is required/i)).toBeInTheDocument();      // async UI: findBy waits
  expect(onSubmit).not.toHaveBeenCalled();

  await user.type(screen.getByLabelText(/email/i), "ada@example.com");
  await user.type(screen.getByLabelText(/password/i), "correct horse");
  await user.click(screen.getByRole("button", { name: /sign in/i }));

  expect(onSubmit).toHaveBeenCalledWith({ email: "ada@example.com", password: "correct horse" });
});
```

Notes: `findBy*` (async, retries) for things that appear later; `queryBy*` to assert absence (`expect(screen.queryByText("x")).not.toBeInTheDocument()`); `getBy*` for things that must exist now. Use `waitFor` sparingly, and never put side effects inside it.

## Mock the network, not your own code

Mocking your own modules and hooks (`vi.mock("./useOrders")`, shallow rendering, replacing child components) couples tests to *how* the code is built. Instead mock at the **boundary you do not control: HTTP**. **MSW (Mock Service Worker)** intercepts requests and returns responses, so your components, hooks, data library and error handling all run for real.

```tsx
import { http, HttpResponse } from "msw";
import { setupServer } from "msw/node";

const server = setupServer(
  http.get("/api/orders", () => HttpResponse.json([{ id: "o1", total: 4999, status: "paid" }])),
);
beforeAll(() => server.listen({ onUnhandledRequest: "error" }));   // fail on requests you forgot to mock
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test("lists orders from the API", async () => {
  render(<OrdersPage />, { wrapper: AppProviders });                 // real router, query client, theme…
  expect(await screen.findByRole("row", { name: /o1/ })).toBeInTheDocument();
});

test("shows an error state when the API fails", async () => {
  server.use(http.get("/api/orders", () => new HttpResponse(null, { status: 500 })));   // per-test override
  render(<OrdersPage />, { wrapper: AppProviders });
  expect(await screen.findByRole("alert")).toHaveTextContent(/couldn't load orders/i);
});
```

Benefits: the same handlers work in tests, Storybook and local development; error and loading paths are easy to cover; refactoring the fetching layer (React Query to SWR) does not break tests. Keep a **custom `render`** that wraps providers (router, query client with retries off, theme, i18n).

When to mock more: third-party widgets that need a browser you do not have (maps, charts), time (`vi.useFakeTimers()`), randomness, `IntersectionObserver`/`matchMedia` shims in jsdom, and anything non-deterministic.

## Testing hooks and logic

- **Pure logic** (formatters, validation, reducers, selectors): plain unit tests with table-driven cases.
- **Custom hooks** with real complexity: `renderHook` from Testing Library; but prefer testing the **component that uses the hook**, which also proves the integration.
- **Reducers/state machines:** test transitions from state + event to new state.

```ts
test.each([
  [{ status: "idle" }, { type: "fetch" }, { status: "loading" }],
  [{ status: "loading" }, { type: "ok", data: [1] }, { status: "success", data: [1] }],
])("reducer %j + %j → %j", (state, action, expected) => {
  expect(reducer(state as State, action as Action)).toEqual(expected);
});
```

## End-to-end with Playwright

E2E tests drive a real browser against a real (or staging) stack. They are the slowest and most fragile, so spend them on **critical journeys**: sign up, log in, search → add to cart → pay, and anything that loses money or trust.

```ts
import { test, expect } from "@playwright/test";

test("a signed-in user can place an order", async ({ page }) => {
  await page.goto("/products/blue-shirt");
  await page.getByRole("button", { name: "Add to cart" }).click();
  await page.getByRole("link", { name: "Cart (1)" }).click();
  await page.getByRole("button", { name: "Checkout" }).click();
  await page.getByLabel("Card number").fill("4242 4242 4242 4242");
  await page.getByRole("button", { name: "Pay" }).click();
  await expect(page).toHaveURL(/\/orders\/\w+/);
  await expect(page.getByRole("heading", { name: "Thank you" })).toBeVisible();
});
```

Playwright's **locators auto-wait** and web-first assertions (`expect(locator).toBeVisible()`) retry, which removes most sleep-based flakiness.

### How do you test an auth flow end to end?

1. **Test the login UI once** end to end (form, errors, redirect).
2. For every other test, **log in programmatically** (call the login API or create a session in setup) and **reuse the resulting `storageState`** (cookies and local storage) so each test starts authenticated without repeating the UI flow. In Playwright, a setup project saves `storageState` to a file that other projects load.
3. Seed test users and data through an API or database fixture, with a **separate test environment** and isolated data (unique emails per run).
4. Mock or sandbox third parties (payment providers' test modes, a fake email inbox such as Mailpit).
5. Cover **negative paths** in lower-level tests (wrong password, locked account) to keep E2E small.
6. Also test **authorization** boundaries: a logged-out user is redirected, a user cannot see another's data ([Backend, Lesson 06](/backend/lesson-6)).

## Snapshot tests: useful or noise?

A snapshot test stores output (serialised DOM or a value) and fails when it changes.

- **Useful:** small, stable, *meaningful* outputs: a formatted string, a generated config, an API response shape, a serialised data structure, an error message set.
- **Noise:** large DOM snapshots of whole components. They break on every harmless markup change, reviewers click "update" without reading, and they assert structure rather than behaviour. Prefer explicit assertions.
- **Good practice:** keep snapshots small, use **inline snapshots** so the expectation is visible in the test, and review diffs deliberately.

Other tools: **visual regression** (Playwright screenshots, Chromatic) for UI appearance, with tolerance and a stable environment; **accessibility checks** (`jest-axe`, `@axe-core/playwright`) in tests; **component stories** (Storybook) with interaction tests.

## What to skip

- **Implementation details**: internal state, private helpers, which function was called, props passed to children.
- **Third-party libraries**: do not test that React Query caches or that `date-fns` formats; trust and pin them.
- **Trivial components** with no behaviour (a styled wrapper).
- **Styling and exact markup** (class names, pixel values), except via visual tests.
- **Everything at 100% coverage.** Coverage shows what was *executed*, not what was *verified*; aim for confidence on critical paths and edge cases.
- **Duplicating the same behaviour at every level.** Test a rule at the lowest level that gives confidence, and prove the integration once higher up.

## Scenario: tests break on every refactor. What's wrong?

The tests are coupled to **implementation**, not behaviour. Typical culprits and fixes:

| Smell | Fix |
|---|---|
| Asserting on internal state or hook return values | Assert on what renders and what the user can do |
| Shallow rendering or mocking child components | Render the real tree |
| `vi.mock` of your own modules and hooks | Mock the network (MSW) at the boundary |
| Selectors by class name, DOM structure or index (`container.querySelector(".btn-primary > span")`) | `getByRole`/`getByLabelText` with accessible names |
| Large DOM snapshots | Targeted assertions |
| Asserting `toHaveBeenCalledTimes` on internals | Assert on observable outcomes |
| One giant test per component | Several small behaviour-focused tests |

A healthy test suite lets you **rewrite a component's internals completely** (class to hooks, Redux to React Query) and stay green as long as behaviour is unchanged.

## Keeping the suite healthy

- Run tests in **CI** on every pull request; fail the build on red; keep the main suite **fast** (under a few minutes).
- **Treat flaky tests as bugs**: find the race (usually a missing `await`/`findBy`, shared state or time), fix or delete.
- **Isolate tests**: no shared mutable state, reset handlers, clean up (RTL auto-cleanup), unique data in E2E.
- **Name tests by behaviour** ("shows an error when the API fails").
- **Test the unhappy paths:** loading, empty, error, offline, permission denied.
- **Control time and randomness** (`vi.useFakeTimers`, seeded values, fixed locale and timezone).
- Use **TDD** where it helps (logic-heavy code, bug reproduction first), not as a religion.

## Common mistakes

1. **Testing implementation details** (state, props passed down, method calls).
2. **`getByTestId` everywhere** instead of role/label queries.
3. **Mocking your own modules** instead of the network.
4. **Giant snapshots** that nobody reads.
5. **Too many E2E tests** (slow, flaky) and none lower.
6. **Not awaiting async UI**, then adding `setTimeout` hacks.
7. **Testing only the happy path.**
8. **Chasing coverage numbers.**

## Interview questions

### Q1. What do you test in a React component?

Behaviour a user can observe: what renders for given props and data, how it responds to typing, clicks and keyboard input, loading, empty and error states, accessibility roles and names, and the outcomes it triggers (a request sent, navigation, a callback invoked). I do not assert on internal state or structure.

### Q2. Scenario: tests break on every refactor. What's wrong?

They are coupled to implementation: shallow rendering, mocked internals, class-name or DOM-structure selectors, internal state assertions, large snapshots. I would rewrite them to query by role and text, mock only the network, assert on visible outcomes and keep snapshots small, so a refactor that preserves behaviour keeps the tests green.

### Q3. How do you test an auth flow end to end?

Test the login UI path once in E2E, then log in programmatically in setup and reuse the saved `storageState` for other tests; seed isolated test data, sandbox third parties, cover negative cases and authorisation boundaries at lower levels, and keep the E2E suite focused on critical journeys.

### Q4. Are snapshot tests useful or noise?

Both: small, stable, meaningful outputs benefit from snapshots (inline preferably), but large DOM snapshots mostly add noise, break on harmless changes and get approved without review. Prefer explicit assertions for behaviour, and visual regression tools for appearance.

### Q5. Why mock the network instead of modules?

Mocking at the HTTP boundary lets the real components, hooks, caching library and error handling run, so tests exercise the integration and survive refactors of the data layer. Module mocks tie tests to internal structure and can hide integration bugs.

### Q6. `getByRole` vs `getByTestId`?

`getByRole` (with an accessible name) reflects how users and assistive technology find elements and doubles as an accessibility check. `getByTestId` is a last resort for elements with no accessible role, because it is invisible to users and encourages tests detached from real behaviour.

### Q7. How do you handle async UI in tests?

Use `findBy*` queries or `waitFor` to wait for elements to appear, `await` user-event actions, mock network responses deterministically with MSW, use fake timers for timed behaviour and avoid arbitrary sleeps. Playwright's auto-waiting locators and web-first assertions handle this in E2E.

### Q8. What belongs in E2E tests?

Only critical user journeys that must never break and that depend on the full stack (sign-in, search, checkout and payment), a few smoke checks per deployment and cross-browser essentials. Detailed logic and edge cases belong in faster unit and integration tests.

### Q9. Scenario: a test passes locally but fails in CI. How do you investigate?

Look for timing, environment and shared-state differences: a missing `await` or `findBy` (CI is slower), time zone or locale differences, randomised or order-dependent tests, leaked state between tests, different Node or browser versions and resource limits. Reproduce with the same container, run the test repeatedly and in isolation, use traces or videos, fix the root cause and avoid sleeps.

## Key takeaways

- **Trophy:** static checks, lots of **integration tests**, some unit tests, a few **E2E**.
- Query by **role/label/text**, use **user-event**, assert on **user-visible behaviour**.
- **Mock the network (MSW)**, not your own modules; use a custom render with providers.
- Auth in E2E: test login once, then reuse **`storageState`**; seed isolated data.
- **Small, meaningful snapshots only;** skip implementation details, third-party internals and coverage chasing.
- Refactor-proof tests are **behaviour-focused**; flaky tests are bugs.
