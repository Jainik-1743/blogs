> **In one line:** hooks let a function component keep state and synchronise with the outside world. Two ideas explain nearly every hook bug: **closures capture the values of the render they were created in** (stale closures), and **effects are for synchronising with external systems, not for reacting to your own state**.

You use hooks daily. The senior-level questions are about *why* the rules exist, how stale values arise, and how often an effect is the wrong tool.

## Why the Rules of Hooks exist

Two rules: call hooks **at the top level** (not in loops, conditions or nested functions) and **only from React functions** (components or custom hooks).

Why? React does not know hooks by name. It stores each component's hook state in an **ordered list** and matches calls to list positions **by call order** on every render:

```tsx
function Form({ editing }: { editing: boolean }) {
  const [name, setName] = useState("");        // slot 0
  if (editing) {
    const [draft, setDraft] = useState("");    // ❌ slot 1 only sometimes
  }
  const ref = useRef(null);                    // slot 1 or slot 2? React gets confused
}
```

If the number or order of hook calls changes between renders, React hands the wrong state to the wrong hook. The lint rule (`react-hooks/rules-of-hooks`) catches this. Put conditions *inside* the hook (`useEffect(() => { if (editing) … })`) or split into components.

## `useState`

```tsx
const [count, setCount] = useState(0);
const [user, setUser] = useState(() => readFromStorage());   // lazy initialiser: runs once, not on every render
setCount((c) => c + 1);                                       // updater form for "based on previous" updates
```

- State updates **replace** the value (unlike class `setState`, objects are not merged): `setUser({ ...user, name })`.
- Never mutate state (`user.name = "x"; setUser(user)`): React compares by reference and will not re-render.
- State is a **snapshot** per render ([Lesson 00](/frontend-depth/lesson-0)).

## `useEffect`: synchronising with external systems

An effect runs **after render** to keep something *outside React* in sync with your component: a subscription, a timer, a network request, a third-party widget, the document title.

```tsx
useEffect(() => {
  const conn = createConnection(serverUrl, roomId);   // setup: connect
  conn.connect();
  return () => conn.disconnect();                      // cleanup: disconnect
}, [serverUrl, roomId]);                               // re-synchronise when these change
```

Think "**synchronise**", not "run when X changes". The dependency array lists **every reactive value the effect reads**: props, state, and anything derived from them. When a dependency changes, React runs the cleanup of the previous effect and then the effect again with new values.

- `[]`: set up on mount, clean up on unmount.
- No array: runs after **every** render (rarely wanted).
- **Do not lie about dependencies.** Suppressing the lint rule creates stale closures. Fix the code instead.
- **Objects, arrays and functions created during render are new on every render**, so using them as dependencies re-runs the effect every time. Move them outside the component, into the effect, or stabilise them with `useMemo`/`useCallback`.

### Strict Mode and effects

In development, Strict Mode mounts → unmounts → remounts once, to verify that your setup and cleanup are symmetrical. If you see duplicated behaviour (two connections, two requests), your cleanup is incomplete ([Debugging, Lesson 05](/debugging/lesson-5)).

## Stale closures

A function captures the variables from the render in which it was created. An effect or handler created in render 1 keeps seeing render 1's values.

**Scenario: an interval keeps logging an old count.**

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);             // ❌ always 0: this callback closed over count from the first render
      setCount(count + 1);            // ❌ always sets 1
    }, 1000);
    return () => clearInterval(id);
  }, []);                             // empty deps: the effect (and its closure) never refreshes

  return <p>{count}</p>;
}
```

Fixes, in order of preference:

```tsx
// 1) Functional update: no need to read count from the closure
useEffect(() => {
  const id = setInterval(() => setCount((c) => c + 1), 1000);
  return () => clearInterval(id);
}, []);

// 2) Honest dependencies: re-create the interval when count changes (fine for infrequent changes)
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]);

// 3) A ref holding the latest value (when the callback must stay stable)
const latest = useRef(count);
useEffect(() => { latest.current = count; });
useEffect(() => {
  const id = setInterval(() => console.log(latest.current), 1000);
  return () => clearInterval(id);
}, []);
```

React 19.2 added **`useEffectEvent`** as a stable API: a purpose-built way to read the latest props and state inside an effect without making them dependencies (on older React versions use a ref).

The same snapshot behaviour explains "stale state in async handlers": a `setTimeout` or a `fetch().then` created in an earlier render sees that render's values.

## `useRef`: a mutable box that does not trigger renders

```tsx
const inputRef = useRef<HTMLInputElement>(null);       // DOM access
const timerId = useRef<number | undefined>(undefined); // any mutable value that must survive renders
const prevValue = useRef(value);                       // "previous value" pattern
```

| | `useState` | `useRef` |
|---|---|---|
| Changing it | Triggers a re-render | **Does not** trigger a re-render |
| Reading during render | Safe, expected | **Avoid** reading or writing `ref.current` during render (not pure) |
| Use for | Anything that affects the output | DOM nodes, timers, "latest value" boxes, non-visual instance values |

If the screen should change when the value changes, it is state, not a ref. Refs are an **escape hatch**. In React 19, function components receive `ref` as an ordinary prop, so `forwardRef` is no longer needed for new code.

## `useLayoutEffect`

Runs after DOM mutations but **before paint**; use it to measure DOM and synchronously adjust (tooltip position, preventing flicker). It blocks painting, so keep it light, and it does not run on the server (use `useEffect` or guard it in SSR code to avoid warnings).

## `useMemo`, `useCallback`, `useReducer`, and friends

- **`useMemo(fn, deps)`** caches a computed value; **`useCallback(fn, deps)`** caches a function identity. Use them for expensive calculations or to keep identities stable for memoised children and effect dependencies, not by default ([Debugging, Lesson 03](/debugging/lesson-3)). They are performance hints, not semantic guarantees: React may discard cached values.
- **`useReducer`** centralises complex state transitions in a pure `(state, action) => state` function, easier to test and reason about than many `useState` calls; the dispatch function is stable.
- **`useId`** generates stable IDs for accessibility attributes (consistent between server and client).
- **`useSyncExternalStore`** subscribes to external stores safely (used by state libraries).
- **`use`** (React 19) reads a promise or context during render, integrating with Suspense.

## "You might not need an effect"

The most important modern lesson: many effects are bugs waiting to happen because they add an extra render pass and make data flow hard to follow. Prefer these alternatives.

### 1. Derive values during render instead of syncing state

```tsx
// ❌ Effect that copies props into state, causing an extra render and a flash of stale data
const [fullName, setFullName] = useState("");
useEffect(() => { setFullName(first + " " + last); }, [first, last]);

// ✅ Just compute it
const fullName = first + " " + last;                       // cheap
const visible = useMemo(() => filter(items, q), [items, q]);  // expensive: memoise
```

### 2. Handle user events in event handlers

```tsx
// ❌ A POST triggered by an effect reacting to state set by a click
useEffect(() => { if (submitted) post(form); }, [submitted]);

// ✅ The click is the cause: do the work in the handler
function handleSubmit() { post(form); }
```

If code runs *because the user did something*, put it in the handler. Effects are for code that runs *because the component was shown* or *because a value it synchronises with changed*.

### 3. Reset state with a `key`, not an effect

```tsx
// ❌ useEffect(() => { setComment(""); }, [userId]);
// ✅
<Profile key={userId} userId={userId} />       // fresh state per user
```

### 4. Don't chain effects that set state to trigger other effects

A cascade of effects (A sets state, B reacts, C reacts) causes multiple renders and is brittle. Compute everything in an event handler or a reducer.

### 5. Data fetching

Fetching in an effect is legitimate (it synchronises with a server) but needs cleanup for races ([Debugging, Lesson 05](/debugging/lesson-5)). Better: a data library (TanStack Query, SWR) or framework data loading (Server Components, loaders), which provide caching, deduplication, retries and no waterfalls.

### 6. Notify parents in the handler, not an effect

```tsx
// ❌ useEffect(() => { onChange(value); }, [value]);
// ✅ call onChange inside the same event handler that sets value
```

### What effects ARE for

Subscriptions (WebSocket, resize, `matchMedia`), timers, imperative third-party widgets (charts, maps), analytics page views, focusing an element after display, syncing `document.title`, and fetching when no better tool exists.

## Custom hooks

A custom hook is a function starting with `use` that calls other hooks, extracting reusable stateful logic (not shared state: each call gets its own state).

```tsx
function useOnlineStatus() {
  return useSyncExternalStore(
    (cb) => { window.addEventListener("online", cb); window.addEventListener("offline", cb); return () => { window.removeEventListener("online", cb); window.removeEventListener("offline", cb); }; },
    () => navigator.onLine,
    () => true,                     // server snapshot
  );
}
```

Good custom hooks have a clear purpose, return a minimal API, and hide effect and cleanup details.

## Scenario walkthroughs

### "An interval keeps logging an old count. Fix it."

Explain the stale closure (the interval callback captured `count` from the first render because the effect had empty dependencies). Fix with a functional update for setting state, honest dependencies if the interval can be re-created, or a ref/`useEffectEvent` for reading the latest value while keeping the interval stable. Mention that the lint rule would have flagged the missing dependency.

### "Derived state: an effect or a plain computation?"

A plain computation during render (with `useMemo` if it is expensive). An effect that copies props or state into other state adds a render, can show an inconsistent intermediate UI, and creates sync bugs. Use a `key` to reset state when identity changes.

## Common mistakes

1. **Conditional hooks** or hooks inside loops.
2. **Suppressing the exhaustive-deps lint rule** instead of fixing the closure.
3. **Objects and functions in dependency arrays** that change every render.
4. **Using effects to derive state** or to respond to events.
5. **Mutating state or refs during render.**
6. **Missing cleanup** (listeners, timers, subscriptions), exposed by Strict Mode.
7. **Using a ref when the UI should update** (it will not re-render).
8. **Fetching in an effect without handling races** or using a data library.

## Interview questions

### Q1. Why must hooks be called in the same order on every render?

React stores a component's hook state in an ordered list and associates each hook call with its slot by call order. Conditional or looped hook calls change the order, so React would give state to the wrong hook. Hence hooks must be called unconditionally at the top level.

### Q2. Scenario: an interval keeps logging an old count. Fix it.

The effect's callback closed over `count` from the render where the effect ran, and an empty dependency array never refreshed it. Use a functional state update (`setCount(c => c + 1)`), list `count` as a dependency so the effect re-runs, or read the latest value through a ref or `useEffectEvent`, and keep the exhaustive-deps lint rule on.

### Q3. When do you use `useLayoutEffect`?

When you must read layout or adjust the DOM synchronously before the browser paints, such as positioning a tooltip based on measured size, to avoid a visible flicker. Otherwise prefer `useEffect`, since layout effects block painting and do not run during server rendering.

### Q4. Derived state: an effect or a plain computation?

A plain computation during render, memoised with `useMemo` if it is costly. Copying data into state through an effect causes an extra render, transient inconsistent UI and synchronisation bugs. If the source identity changes, reset state with a `key`.

### Q5. What is the difference between `useRef` and `useState`?

Updating state triggers a re-render and its value is part of the rendered output; updating `ref.current` does not trigger a render and is meant for values that do not affect rendering: DOM nodes, timer IDs, "latest value" holders. Avoid reading or writing refs during render.

### Q6. What are effects for, and when should you avoid them?

Effects synchronise a component with external systems: subscriptions, timers, imperative widgets, network requests. Avoid them for deriving state, responding to user events, resetting state, notifying parents or chaining state updates; use render-time computation, event handlers, keys and reducers instead.

### Q7. Why does an object in the dependency array re-run the effect every render?

Dependencies are compared by reference with `Object.is`. An object, array or function created during render is a new reference each time, so React sees a change. Move it outside the component, create it inside the effect, or memoise it with `useMemo`/`useCallback` when it truly must be passed in.

### Q8. What is a custom hook and does it share state?

A function whose name starts with `use` that calls other hooks to reuse stateful logic. It shares logic, not state: every component that calls it gets its own independent state and effects.

### Q9. Scenario: a component renders in an endless loop after adding an effect. What do you look for?

An effect that sets state which is also in its dependency list, or an object, array or function created during render used as a dependency so it changes every render. Check the exhaustive-deps lint warning, derive values during render instead of syncing them with an effect, stabilise dependencies (move them out, `useMemo`, `useCallback`) and use functional updates so the effect does not need the state as a dependency.

## Key takeaways

- Hooks are matched **by call order**, hence the rules.
- **Closures capture each render's values**: stale values come from missing or lying dependencies, fixed with functional updates, honest deps, refs or `useEffectEvent`.
- Effects **synchronise with external systems** and need **cleanup**; Strict Mode checks that.
- **You might not need an effect**: derive during render, use event handlers, reset with `key`, fetch with a library or on the server.
- `useRef` is a non-rendering mutable box; `useLayoutEffect` runs before paint; memoisation hooks are performance tools, not defaults.
