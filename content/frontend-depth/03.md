> **In one line:** stop asking "Redux or Zustand?" and start asking "**what kind of state is this?**" Server data, URL state, form state, shared UI state and local state each have a natural home. Most state-management pain comes from putting the wrong kind in the wrong place.

Senior interviews ask this to see whether you can classify state and pick the *least powerful* tool that solves each case.

## The five kinds of state

| Kind | Examples | Natural home |
|---|---|---|
| **Local UI state** | Is this dropdown open? Which tab is active? Hover state | `useState` / `useReducer` in the component that needs it |
| **Shared client state** | Theme, current user session info, a multi-step wizard, a cart before checkout, sidebar collapsed | Lifted state, Context (for low-frequency values) or a small store (Zustand, Redux Toolkit, Jotai) |
| **Server state** | Products, orders, profile data, anything that **lives on the server** and you merely display and cache | A server-state library (**TanStack Query, SWR, RTK Query, Apollo**) or framework data loading (Server Components) |
| **URL state** | Search text, filters, sort order, page number, selected tab, open modal ID | The **URL** (`searchParams`, route params) |
| **Form state** | Field values, validation errors, touched/dirty flags, submission status | A form library (React Hook Form, TanStack Form) with a schema (Zod), or native form actions |

Add two derived categories:

- **Derived state:** anything computable from other state (a filtered list, a total, a full name). **Don't store it**; compute it during render ([Lesson 01](/frontend-depth/lesson-1)).
- **Persistent state:** survives reloads (preferences, drafts) → `localStorage`/IndexedDB/cookies/server, synced deliberately ([Browser Contract, Lesson 01](/browser/lesson-1)).

## Server state is not client state

The biggest conceptual shift of the last years: **data from an API is a cache of something you do not own.** It can become stale, be changed by other users, fail to load, need revalidation, deduplication, pagination, retries and optimistic updates. Hand-rolling this in `useState`/`useEffect` (or copying it into Redux) is a bug factory.

A server-state library gives you, out of the box:

- **Caching by key** and **deduplication** (five components asking for the same data share one request).
- **Background revalidation** (stale-while-revalidate), refetch on focus or reconnect.
- **Loading and error states**, retries, and cancellation.
- **Mutations** with cache invalidation and **optimistic updates**.
- **Pagination and infinite queries**, prefetching.
- Garbage collection of unused data (a memory-safety bonus; see [Debugging, Lesson 04](/debugging/lesson-4)).

```tsx
function useProduct(id: string) {
  return useQuery({ queryKey: ["product", id], queryFn: ({ signal }) => api.getProduct(id, signal), staleTime: 60_000 });
}

function ProductHeader({ id }: { id: string }) { const { data } = useProduct(id); /* … */ }
function ProductPrice({ id }: { id: string }) { const { data } = useProduct(id); /* … same key: one request, shared cache */ }
```

In an App Router app, much server state can simply be fetched in **Server Components** and passed down, with the client cache needed only for interactive, frequently updated or mutated data.

### Scenario: five components each fetch the same data. Design the fix.

1. **Diagnose:** the Network tab shows the same request five times; each component has its own `useEffect` + `useState`.
2. **Fix:** put the fetch behind **one query hook keyed by the resource** (`["user", id]`); the library dedupes in-flight requests and shares the cache, so all five read the same data and update together on refetch. Or fetch once in a **Server Component or loader** and pass the data down.
3. **Tune:** set `staleTime` to match how fresh the data must be; prefetch on route navigation; invalidate the key after mutations.
4. **Avoid:** copying the result into a global store, which duplicates the cache and creates synchronisation bugs.

## URL state

Anything that defines **what the user is looking at** should usually live in the URL:

- **Shareable and bookmarkable** (send a colleague the filtered view).
- **Back/forward buttons work.**
- **Survives refresh.**
- **Server-renderable:** the server can read `searchParams` and render the right data.

```tsx
// Next.js: filters live in the URL, not in useState
"use client";
import { useRouter, useSearchParams, usePathname } from "next/navigation";

function useQueryParam(name: string) {
  const sp = useSearchParams(); const router = useRouter(); const pathname = usePathname();
  const set = (value: string) => {
    const next = new URLSearchParams(sp);
    value ? next.set(name, value) : next.delete(name);
    router.replace(`${pathname}?${next}`, { scroll: false });
  };
  return [sp.get(name) ?? "", set] as const;
}
```

> [!warn] In the Next.js App Router, a Client Component that calls `useSearchParams` should be wrapped in a `<Suspense>` boundary. On a prerendered route, the tree up to the nearest boundary is otherwise rendered on the client, which can undo the benefit of prerendering.

**Should filters live in the URL?** Yes for list/search/report pages: it gives deep links and server rendering. Keep ephemeral UI state (a tooltip, an open dropdown) out of the URL. Debounce text input before writing to the URL.

## Form state

Forms have their own complexity: validation, touched/dirty tracking, async submit, error mapping, performance with many fields.

- Use a **form library** (React Hook Form and a Zod resolver; TanStack Form) rather than one `useState` per field plus ad-hoc validation.
- **Uncontrolled inputs under the hood** (React Hook Form) avoid re-rendering the whole form on every keystroke ([Debugging, Lesson 08](/debugging/lesson-8)).
- **Validate with the same schema as the backend** ([Backend, Lesson 03](/backend/lesson-3)); map server field errors back onto fields.
- With Server Actions/forms in the App Router, use `useActionState`/`useFormStatus` for pending and result state, and `useOptimistic` for optimistic UI.
- Drafts that must survive reloads: persist locally or server-side.

## Shared client state: Context, or a store?

Not everything shared is server state. Genuinely client-owned shared state (theme, wizard progress, selected rows across components, a global "command palette is open") needs a home.

### Context

Good for **low-frequency, app-wide** values: theme, locale, current-user object, feature flags, dependency injection (a router, a query client). **Context is not a state management library**; it is a way to avoid prop drilling.

**When is Context the wrong tool?**

- The value changes **frequently** (every keystroke, mouse move, timer tick): every consumer re-renders ([Debugging, Lesson 03](/debugging/lesson-3)).
- The value is a **big object** where consumers need different parts: any change re-renders all consumers; no built-in selectors.
- You need **fine-grained subscriptions, middleware, devtools, persistence** or computed values.

Mitigations: split contexts by update frequency; memoise the value; separate state and dispatch contexts; or use a store.

### Stores with selectors

Libraries like **Zustand, Redux Toolkit, Jotai and Valtio** hold state outside React and let components **subscribe to slices**, re-rendering only when their slice changes.

```tsx
import { create } from "zustand";

const useCart = create<{ items: Item[]; add: (i: Item) => void }>((set) => ({
  items: [],
  add: (i) => set((s) => ({ items: [...s.items, i] })),
}));

const count = useCart((s) => s.items.length);        // re-renders only when the length changes
const add   = useCart((s) => s.add);                 // stable
```

| Tool | Character | Choose when |
|---|---|---|
| `useState`/`useReducer` + lifting | Built in, explicit | State is used by a few nearby components |
| **Context** | Built in, no selectors | Rarely changing, app-wide values |
| **Zustand / Jotai** | Tiny, minimal boilerplate, selectors/atoms | Shared client state without ceremony |
| **Redux Toolkit** | Structured, devtools, middleware, strong conventions | Large teams, complex client state with many interactions, auditability needs |
| **State machines (XState)** | Explicit states and transitions | Complex flows (checkout, wizards, media players) with many invalid combinations |

Redux itself is not "wrong"; using it for server data, form fields and everything else is the anti-pattern.

## Principles for placing state

1. **Colocate:** keep state as close as possible to where it is used; lift it only when two components genuinely need to share it ([Debugging, Lesson 03](/debugging/lesson-3)).
2. **Single source of truth:** each piece of data lives in one place; other places derive from it.
3. **Don't store derived data**; compute during render (memoise if costly).
4. **Don't duplicate server data in client state.**
5. **Prefer the URL for navigational state.**
6. **Normalise** large shared collections (by ID) if you must keep them client-side; but prefer the server-state cache.
7. **Use the least powerful tool** that works; move up the ladder only when pain appears.
8. **Make impossible states impossible:** model status as a union (`"idle" | "loading" | "success" | "error"`) or a reducer/state machine, not several booleans (`isLoading && isError`).

```ts
// ❌ Booleans that can contradict each other
{ isLoading: boolean; isError: boolean; data?: T }

// ✅ A discriminated union
type State<T> = { status: "idle" } | { status: "loading" } | { status: "error"; error: Error } | { status: "success"; data: T };
```

## A decision flow

```text
Does the data come from a server and can change without you?  → server-state library / Server Component
Does it describe what the user is looking at (filter, page, tab)? → URL
Is it a form's field/validation/submit state?                  → form library
Is it computed from other state?                               → derive during render
Is it only used by one component or its children?              → useState / useReducer
Used by distant components and changes rarely?                  → Context
Used by distant components and changes often?                   → store with selectors
A complex flow with many states and transitions?               → reducer or state machine
Must survive a reload?                                         → persist (URL, storage, server)
```

## Common mistakes

1. **Copying API responses into Redux/Context** and writing manual refetch logic.
2. **Everything in one global store**, including form fields and UI toggles.
3. **A single giant Context** for rapidly changing state.
4. **Storing derived values** and syncing them with effects.
5. **Filters in local state**, losing deep links, back-button behaviour and SSR.
6. **Multiple booleans for status** instead of a union.
7. **Prop drilling avoided with the wrong tool** (Context for hot state).
8. **Over-engineering** early: reaching for a heavyweight store before state is actually shared.

## Interview questions

### Q1. When is Context the wrong tool?

When the value changes frequently or is a large object with consumers needing different slices: every consumer re-renders on any change and there are no selectors. Context fits rarely changing values like theme, locale or the current user. For hot shared state, use a store with selectors or restructure so state is colocated.

### Q2. Server state vs client state?

Server state lives remotely, can be changed by others and so can go stale; it needs caching, deduplication, revalidation, retries and invalidation, which a library such as TanStack Query handles. Client state is owned by the UI (open modals, wizard steps, theme) and changes only through user actions in the app. Mixing them leads to duplicated, inconsistent data.

### Q3. Scenario: five components each fetch the same data. Design the fix.

Wrap the request in a shared keyed query (or load it once in a Server Component/loader and pass it down) so requests are deduplicated and the cache is shared across components, set an appropriate stale time, invalidate after mutations and avoid copying the data into a global store.

### Q4. Should filters live in the URL?

For list, search and report pages yes: it makes views shareable and bookmarkable, supports back/forward, survives refresh and allows server rendering. Debounce text input updates, and keep ephemeral UI state out of the URL.

### Q5. How do you decide between `useState`, Context and a store?

Start with `useState` colocated with its users; lift state when siblings need it. Use Context for rarely changing app-wide values. Use a store with selectors for shared state that changes often or needs middleware and devtools. Choose the least powerful tool that solves the problem.

### Q6. How do you model loading and error states?

As a discriminated union (`idle`, `loading`, `success` with data, `error` with the error) or via a library's status, so contradictory combinations like loading and error simultaneously cannot occur.

### Q7. Why avoid storing derived state?

It duplicates a source of truth and has to be kept in sync (usually with effects), causing extra renders and bugs. Computing it during render (memoised if expensive) keeps one source of truth and consistent output.

### Q8. When would you choose Redux Toolkit over Zustand?

When the team and application benefit from Redux's strict conventions, mature devtools, middleware ecosystem, predictable action logs and RTK Query integration, typically in large codebases with complex client-side state and many contributors. For smaller or simpler needs, Zustand or Jotai offers less boilerplate.

### Q9. Scenario: a global store holds 200 fields and every update re-renders half the app. How do you fix it?

Components subscribe to the whole state or to large objects. Select narrow slices with selectors, split the store by domain, keep server data out of it (use a query cache), derive instead of storing computed values and avoid creating new objects in selectors. Profile the store updates and move high-frequency data to local or ref-based state.

## Key takeaways

- **Classify state first:** local, shared client, **server**, **URL**, form, derived, persistent.
- **Server state belongs in a cache library or Server Components**, not Redux or `useState`.
- **Navigational state belongs in the URL**; forms deserve a form library and a shared schema.
- Context is for **low-frequency** values; use **stores with selectors** for hot shared state.
- **Colocate, single source of truth, derive don't store,** model status with unions, and use the least powerful tool.
