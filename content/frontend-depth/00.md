> **In one line:** React works in two phases. **Render** calls your components to describe what the UI *should* be (pure calculation, no side effects). **Commit** applies the minimum DOM changes and runs effects. In between, **reconciliation** compares the new description with the previous one, using **element type and key** to decide what to keep, update or throw away.

Most "weird React bugs" (state in the wrong row, stale values, duplicated work) disappear once you can say exactly what happens in each phase. This lesson builds the model interviewers probe.

## What "render" means

**Rendering is React calling your component functions** to find out what to show. It is *not* "updating the screen" and does not necessarily touch the DOM.

```text
Trigger  ──▶  Render (call components, build the new element tree)  ──▶  Commit (update the DOM, run layout effects, then effects)
```

1. **Trigger:** the first render (`root.render(<App />)`) or a state update (`setState`, a context change, a store update that re-renders a subscribed component).
2. **Render phase:** React calls the component whose state changed, and **recursively every child component** (unless a child is skipped by `memo` or the "same element" optimisation; [Debugging, Lesson 03](/debugging/lesson-3)). The result is a tree of React **elements** (plain objects like `{ type: "li", props, key }`).
3. **Reconciliation:** React compares the new element tree with the previous one to compute what changed.
4. **Commit phase:** React applies the changes to the DOM, attaches refs, and runs effects.

> [!note] **Render ≠ DOM update.** If a component re-renders but returns the same output, React touches nothing in the DOM. The cost of a wasted render is the function call and the comparison, not a repaint.

### Rendering must be pure

During the render phase your component must behave like a pure function of its **props, state and context**: same inputs, same output, **no side effects** (no mutating external variables, no network calls, no subscriptions, no `Math.random()`/`Date.now()` in the output). Why? React may **call render more than once, pause it, discard it or restart it** (concurrent rendering, Strict Mode's double render in development). Impure render code produces duplicated or inconsistent results.

```tsx
// ❌ Mutates something outside the component during render
let count = 0;
function Badge() { count++; return <span>{count}</span>; }   // double render in Strict Mode: shows 2, then 4…

// ✅ Pure: derived only from its inputs
function Badge({ count }: { count: number }) { return <span>{count}</span>; }
```

Side effects belong in **event handlers** (in response to a user action) or **effects** (to synchronise with the outside world), covered in [Lesson 01](/frontend-depth/lesson-1).

## State is a snapshot

Each render sees a **fixed snapshot** of state, props and handlers. Calling `setState` does not change the variable in the current render; it schedules a **new render** with the new value.

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    console.log(count);          // still 0: the snapshot of this render
  }
  // result after one click: count is 1, not 3 — all three calls used count = 0

  function handleClickRight() {
    setCount((c) => c + 1);      // updater function: "take the latest pending value and add 1"
    setCount((c) => c + 1);
    setCount((c) => c + 1);      // result: 3
  }
  return <button onClick={handleClickRight}>{count}</button>;
}
```

Rule: if the next state depends on the previous state, use the **updater form** (`setX(prev => …)`).

## Batching

React groups multiple state updates that happen in the same event (and, since React 18, **also in timeouts, promises and native handlers**: "automatic batching") into **one re-render**.

```tsx
async function save() {
  setSaving(true);
  setError(null);
  await api.save();
  setSaving(false);   // updates after an await are still batched with each other (React 18+)
  setSaved(true);
}
```

Batching means fewer renders and a consistent UI (you never see `saving=false` with `saved=false` for one frame). In rare cases you need the DOM updated immediately; `flushSync(() => setState(...))` forces a synchronous flush, at a performance cost.

## Reconciliation: how React decides what changed

Comparing two arbitrary trees optimally is expensive, so React uses two **heuristics**:

1. **Elements of different types produce different trees.** If a `<div>` becomes a `<section>`, or `<Profile>` becomes `<Settings>`, React **destroys the old subtree and builds a new one** (state in it is lost, effects clean up and re-run).
2. **Keys identify children across renders.** Within a list, an element's `key` tells React "this is the same item as last time", even if it moved.

### Same type at the same position: update, keep state

```tsx
// Render 1:  <Counter />   Render 2:  <Counter />  (same type, same position)
// → React UPDATES the existing instance: its state is preserved.
```

State is not stored "in the component function"; it is attached to the **position of the component in the tree** (to its Fiber node). If a component of the same type renders at the same position, its state survives, even if you think of it as "a different thing".

```tsx
function Page({ userId }: { userId: string }) {
  return <Profile />;   // same type, same position for every userId
}
// <Profile> keeps its state (a half-typed form) when userId changes. Often a bug!

// Fix: change the key to reset state when the identity changes
<Profile key={userId} />    // new key → React treats it as a different instance → fresh state
```

**`key` as a reset button** is the idiomatic way to discard state when an entity changes (a form for a different user, a different video).

### Different type at the same position: reset

```tsx
{isEditing ? <EditForm /> : <ReadOnlyView />}   // different types: switching unmounts one and mounts the other
```

### Don't define components inside components

```tsx
function Parent() {
  function Child() { return <input />; }       // ❌ a NEW function (new type) on every render
  return <Child />;                            // React sees a different type each time → remounts → input loses focus/state
}
```

Define components at module level.

## Keys in lists

```tsx
{todos.map((todo) => <TodoItem key={todo.id} todo={todo} />)}
```

A good key is **stable** (the same item has the same key across renders) and **unique among siblings**. Use a database ID, never `Math.random()` (a new key each render means remounting everything).

### Why index keys are risky

```tsx
{todos.map((todo, index) => <TodoItem key={index} todo={todo} />)}
```

Index keys identify *positions*, not *items*. They are fine only for static lists that are never reordered, inserted into or deleted from. Otherwise:

**Scenario: after deleting a list item, its state "jumps" to another row.**

```text
Items:  [A, B, C]  keys by index: 0:A  1:B  2:C       Each row has an uncontrolled <input> (local state).
User types "hello" into B's input (index 1).
User deletes A. New list: [B, C]   keys by index: 0:B  1:C
React compares by key: key 0 (was A) → now B: same type, so it UPDATES the instance, keeping the old input value
                       key 1 (was B, holding "hello") → now C: keeps "hello"!   ← C appears to have B's text
                       key 2 → removed.
```

The state stayed attached to the **position**, not the **item**. With `key={todo.id}` the instance for B is matched to B wherever it moves, and the instance for A is destroyed. The same problem causes wrong animations, lost focus and incorrect memoisation when lists reorder.

## What happens in the commit phase

After render and reconciliation, React commits in this order:

1. **Mutation:** apply DOM changes (insert, update, remove nodes). Old refs are detached; new refs attached.
2. **Layout effects** (`useLayoutEffect`) run **synchronously**, after the DOM is updated but **before the browser paints**. Use them to measure DOM or adjust layout without a visible flicker. They block painting, so keep them tiny.
3. The browser **paints**.
4. **Passive effects** (`useEffect`) run **after paint** (in most cases), so they do not delay what the user sees.

```tsx
useLayoutEffect(() => {
  const h = ref.current!.getBoundingClientRect().height;   // read layout right after DOM mutation
  setHeight(h);                                            // causes a synchronous re-render before paint
}, []);

useEffect(() => {
  const id = subscribe(onChange);      // synchronise with an external system after paint
  return () => unsubscribe(id);        // cleanup runs before the next effect and on unmount
}, []);
```

**Cleanup order:** when dependencies change, React runs the **previous effect's cleanup** and then the **new effect**. On unmount, it runs cleanups.

## Under the hood: Fiber and concurrent rendering

React represents your tree as **Fiber** nodes (units of work). In **concurrent rendering** the render phase is **interruptible**: React can render in small chunks, pause to let urgent work (typing, clicking) go first, resume or discard in-progress work. The **commit phase is not interruptible**: once React starts mutating the DOM it finishes. That is why render must be pure (it may run, stop and run again) and why transitions work ([Lesson 02](/frontend-depth/lesson-2)).

## Putting it together: an interview-ready walk-through

> "When state changes, React schedules a render. In the render phase it calls my components, which must be pure, to produce a new tree of elements, re-rendering children by default. It reconciles that against the previous tree: different element types are torn down and rebuilt, the same type at the same position is updated and keeps its state, and keys identify list items so state follows the item. In the commit phase it applies the minimal DOM changes, runs layout effects before paint and passive effects after. Updates in the same tick are batched into one render."

## Common mistakes

1. **Believing re-render means DOM update**, then over-optimising.
2. **Impure render:** mutating variables, reading `Date.now()` or random values, or fetching during render.
3. **Index (or random) keys** on dynamic lists.
4. **Defining components inside other components**, causing remounts.
5. **Expecting `setState` to update the variable immediately**; not using the updater form.
6. **Forgetting that state survives when type and position are unchanged**, and not using `key` to reset it.
7. **Reading layout in `useEffect`** and causing a flash (use `useLayoutEffect`), or the opposite: heavy work in `useLayoutEffect` blocking paint.

## Interview questions

### Q1. Render phase vs commit phase?

The render phase calls components to compute the next UI description and is pure and interruptible; nothing is visible yet. The commit phase applies the minimal DOM changes, attaches refs and runs layout effects (before paint) and passive effects (after paint); it runs to completion without interruption.

### Q2. Why are index keys risky?

Keys tie state to a position rather than an item. When items are inserted, deleted or reordered, React matches instances by index, so component state and DOM state (focus, input values) stay at the old position while the data moves, causing wrong values and bugs. Use stable unique IDs.

### Q3. What does reconciliation compare?

The previous and next element trees, level by level, using two heuristics: elements of different types produce different trees (the old subtree is unmounted and the new one mounted), and elements of the same type at the same position are updated in place; keys let React match list children across renders.

### Q4. Scenario: after deleting a list item, its state "jumps" to another row. Why?

The list uses index keys, so after deletion the instances are matched by position: each remaining row inherits the local state (input text, expanded state) of the instance that previously occupied that position. Using a stable ID as the key attaches state to the item and fixes it.

### Q5. How do you reset a component's state when a prop identity changes?

Give it a `key` derived from that identity (`<Profile key={userId} />`). A new key makes React treat it as a different instance: the old one unmounts and a fresh one mounts with initial state.

### Q6. What does batching do?

It combines multiple state updates from the same event, timeout, promise or other source into a single re-render, avoiding intermediate inconsistent UI and wasted work. React 18 applies automatic batching almost everywhere; `flushSync` opts out when a synchronous DOM update is needed.

### Q7. `useLayoutEffect` vs `useEffect`?

`useLayoutEffect` runs synchronously after DOM mutations and before the browser paints, so it suits measurements and layout adjustments that must not flicker, but it blocks painting. `useEffect` runs after paint and is the default for synchronising with external systems.

### Q8. Why must render be pure?

Because React may call it multiple times, pause it, discard it or run it concurrently, and Strict Mode intentionally double-invokes it in development. Side effects during render would be duplicated or leave inconsistent state; they belong in event handlers and effects.

## Key takeaways

- **Render** = call components (pure) to describe the UI; **commit** = apply DOM changes and run effects. Render is not a DOM update.
- **State is a snapshot** per render; use the **updater form** when depending on previous state. Updates are **batched**.
- **Reconciliation:** type changes reset, same type + position preserves state, **keys** carry identity in lists. Use `key` to deliberately reset state.
- **Stable unique keys**, never index or random for dynamic lists; never define components inside components.
- **Layout effects before paint, passive effects after.** The render phase is interruptible; the commit phase is not.
