> **In one line:** accessibility is mostly **using the right HTML and not breaking the keyboard**. Native elements come with roles, focus and keyboard behaviour for free; ARIA only patches what HTML cannot express, and **bad ARIA is worse than none**.

Accessibility (a11y) is a legal requirement in many places, a quality signal in interviews and, more practically, it makes your product better for everyone using a keyboard, a small screen, bright sunlight or a slow day. This lesson covers what senior frontend interviews check and how to verify it.

## The first rule: use semantic HTML

The browser already knows how to expose a `<button>` to assistive technology: it is focusable, activates with Enter **and** Space, has the role "button" and announces its label. A `<div onClick>` has none of that.

```tsx
// ❌ Looks like a button, behaves like nothing for keyboard and screen-reader users
<div className="btn" onClick={save}>Save</div>

// ✅ One native element does everything
<button type="button" onClick={save}>Save</button>

// If you truly cannot use <button> (rare), you must re-implement everything:
<div role="button" tabIndex={0} onClick={save}
     onKeyDown={(e) => (e.key === "Enter" || e.key === " ") && save()}>Save</div>
```

| Need | Use | Not |
|---|---|---|
| An action | `<button>` | `<div onClick>` or `<a onClick>` |
| Navigation to a URL | `<a href>` | `<button onClick={navigate}>` |
| Text input | `<input>`/`<textarea>` with a `<label>` | A `contenteditable` div |
| Choose one option | `<select>`, radio group (`<fieldset>`/`<legend>`) | A styled div list (unless you build a full pattern) |
| Page structure | `<header> <nav> <main> <footer> <section> <h1…h6>` | A tower of `<div>`s |
| Lists | `<ul>`/`<ol>`/`<li>` | Line-broken text |
| Tabular data | `<table>` with `<th scope>`, `<caption>` | Div grids faking a table |
| Modal | `<dialog>` with `showModal()` | A positioned div |

**Document structure matters:** one `<h1>` per page, headings in order without skipping levels (screen-reader users navigate by headings), landmarks (`main`, `nav`) so users can jump around, and a **skip link** ("Skip to main content") as the first focusable element.

## Names for everything interactive

Every control needs an **accessible name** (what a screen reader announces):

- Visible label text: `<label htmlFor="email">Email</label><input id="email" />` (or wrap the input).
- Buttons: their text content. **Icon-only buttons** need a name: `<button aria-label="Close dialog"><XIcon aria-hidden="true" /></button>`.
- Images: **meaningful `alt` text** that conveys purpose; **`alt=""`** for decorative images so they are skipped.
- Links: text that makes sense out of context ("Read the pricing guide", not "click here").
- Groups: `<fieldset><legend>Shipping method</legend>…</fieldset>`.
- Extra description: `aria-describedby` pointing at hint or error text.

A placeholder is **not** a label (it disappears and has poor contrast).

## Keyboard support

Everything a mouse can do, a keyboard must do.

- **All interactive elements reachable with Tab** in a **logical order** (DOM order should match visual order; avoid positive `tabindex` values).
- **Visible focus indicator**: never `outline: none` without a replacement. Use `:focus-visible` for keyboard-only rings.
- **No keyboard traps**: users must be able to leave every component (except an intentional modal, where Escape closes it).
- **Standard keys:** Enter/Space activate buttons; Enter follows links; Escape closes popups; arrow keys move within composite widgets (tabs, menus, listboxes, radio groups); Home/End jump to ends.
- Test it: unplug your mouse and use the app for five minutes.

### Roving tabindex (composite widgets)

A tab list or toolbar should be **one Tab stop**, with arrow keys moving inside it:

```tsx
// Only the active tab is tabbable; arrows move focus and selection
<div role="tablist" aria-label="Account">
  {tabs.map((t, i) => (
    <button key={t.id} role="tab" id={`tab-${t.id}`} aria-selected={i === active} aria-controls={`panel-${t.id}`}
            tabIndex={i === active ? 0 : -1} onKeyDown={(e) => onArrow(e, i)} onClick={() => setActive(i)}>
      {t.label}
    </button>
  ))}
</div>
<div role="tabpanel" id={`panel-${tabs[active].id}`} aria-labelledby={`tab-${tabs[active].id}`}>…</div>
```

## Focus management (the modal case)

When content appears or disappears dynamically, you are responsible for where focus goes.

**A modal dialog must:**

1. **Move focus into the dialog** when it opens (to the first focusable element or the dialog heading).
2. **Keep focus inside** while open (**focus trap**): Tab and Shift+Tab wrap within the dialog.
3. **Make the rest of the page inert** (`aria-hidden`/`inert` on the background) so assistive technology and clicks cannot reach it.
4. **Close on Escape**, and via a visible close button.
5. **Return focus** to the element that opened it when it closes.
6. Have an accessible name (`aria-labelledby` pointing at the title) and `aria-modal="true"`.

```tsx
// The native element gives you most of this: focus moves in, Escape closes, the background is inert,
// and focus returns to the trigger on close.
function Confirm({ open, onClose, children }: { open: boolean; onClose: () => void; children: React.ReactNode }) {
  const ref = useRef<HTMLDialogElement>(null);
  useEffect(() => {
    const d = ref.current!;
    if (open && !d.open) d.showModal();
    if (!open && d.open) d.close();
  }, [open]);
  return (
    <dialog ref={ref} aria-labelledby="confirm-title" onClose={onClose}>
      <h2 id="confirm-title">Delete this project?</h2>
      {children}
      <button onClick={onClose}>Cancel</button>
    </dialog>
  );
}
```

Prefer the native `<dialog>` or a well-tested library (Radix UI, React Aria, Headless UI) over rolling your own focus trap.

Other focus rules: after a **route change** in a single-page app, move focus to the new page's heading (or announce the change), since there is no page load; after **deleting an item**, move focus to a sensible neighbour; after a **form submission error**, move focus to the error summary or the first invalid field.

## ARIA: when and when not

**ARIA** (Accessible Rich Internet Applications) attributes add semantics HTML cannot express. The five rules in short:

1. **Do not use ARIA if a native HTML element or attribute can do the job.**
2. **Do not change native semantics** (`<h2 role="button">`): use the right element.
3. **All interactive ARIA controls must be keyboard operable.**
4. **Do not use `role="presentation"` or `aria-hidden="true"` on focusable elements.**
5. **All interactive elements must have an accessible name.**

**First rule of ARIA: no ARIA is better than bad ARIA.** ARIA changes **what is announced**, not **what the element does**: `role="button"` on a div does not add focus or key handling.

### When ARIA is harmful

- `role="button"` on a div **without** `tabIndex` and key handlers (announced as a button, impossible to use).
- `aria-label` that **contradicts** the visible text, so voice-control users who say what they see fail to activate it.
- `aria-hidden="true"` on a focusable element or on content users need (focus lands on something silent).
- `aria-expanded` that is not updated when the state changes (wrong announcements).
- Redundant roles (`<button role="button">`, `<nav role="navigation">`) add noise.
- Wrong or invented roles, or roles missing their required parts (a `listbox` without `option`s).

### ARIA that is genuinely useful

| Attribute | Use |
|---|---|
| `aria-label` / `aria-labelledby` | Name controls with no visible text, or label regions |
| `aria-describedby` | Link a control to hint or error text |
| `aria-expanded`, `aria-controls` | State of disclosure buttons, menus, accordions |
| `aria-current="page"` | The current item in navigation |
| `aria-invalid="true"` + `aria-describedby` | Form field errors |
| `aria-live`, `role="status"`, `role="alert"` | Announce dynamic changes (toasts, results count, form errors) |
| `aria-busy` | A region is loading |
| `aria-hidden="true"` | Hide purely decorative content (icons) from assistive technology |
| `aria-selected`, `aria-checked`, `aria-pressed` | State in custom widgets |

**Live regions:** use `role="status"` (polite) for non-urgent updates ("12 results") and `role="alert"` (assertive) sparingly for errors that need immediate attention. The region must exist in the DOM **before** its content changes.

## Forms and errors

```tsx
<label htmlFor="email">Email</label>
<input id="email" type="email" autoComplete="email" required
       aria-invalid={!!error} aria-describedby={error ? "email-error" : "email-hint"} />
<p id="email-hint">We'll never share it.</p>
{error && <p id="email-error" role="alert">{error}</p>}
```

- Every input has a **visible label**; use correct `type` and `autoComplete`.
- **Errors:** describe what is wrong and how to fix it in text (not only a red border), associate with the field, and move focus to the first error (or an error summary) after a failed submit.
- Mark required fields in text, not colour alone.
- Do not disable the submit button as the only feedback; explain what is missing.

## Colour, contrast and motion

- **Contrast (WCAG AA):** at least **4.5:1** for normal text, **3:1** for large text (about 24 px, or 19 px bold) and for **UI components and meaningful graphics** (input borders, icons, focus rings).
- **Do not rely on colour alone** to convey information (error states, charts, status): add text, icons or patterns.
- **Respect user preferences:** `prefers-reduced-motion` (reduce or remove animation), `prefers-color-scheme`, and allow text zoom to 200% and reflow at 320 px width without horizontal scrolling. Use relative units (`rem`), not fixed pixel text.
- **Target size:** make touch targets comfortably large (WCAG 2.2 sets a minimum of 24 by 24 CSS px; around 44 px is a common comfortable target).
- **Time limits and auto-moving content** (carousels) need pause controls.

```css
@media (prefers-reduced-motion: reduce) {
  * { animation-duration: 0.01ms !important; animation-iteration-count: 1 !important; transition-duration: 0.01ms !important; scroll-behavior: auto !important; }
}
:focus-visible { outline: 3px solid currentColor; outline-offset: 2px; }
```

## Custom widgets: follow established patterns

Dropdowns/comboboxes, menus, tabs, accordions, date pickers, tree views and data grids are **hard to make accessible**. Options, best first:

1. **Use the native element** (`<select>`, `<details>/<summary>`, `<input type="date">`, `<dialog>`) when its look and behaviour are acceptable.
2. **Use an accessible headless/UI library** (Radix UI, React Aria, Headless UI, Ariakit) that implements the keyboard and ARIA patterns correctly.
3. **Implement the WAI-ARIA Authoring Practices pattern** exactly (roles, states, keys). Do not improvise.

### Scenario: a custom dropdown doesn't work with screen readers. Fix it.

1. **Diagnose:** try it with keyboard only, then a screen reader (VoiceOver, NVDA). Typical findings: the trigger is a `div` (not focusable, no role), options are unlabeled divs, arrow keys do nothing, the open state is not announced, selection is not announced, Escape does not close, focus is lost.
2. **Decide:** can a native `<select>` do it? If yes, use it (and style it modestly). If you need custom UI (search, rich options), use a library's `Select`/`Combobox` or implement the **combobox/listbox pattern**.
3. **Implement the pattern:** a button or input with `role="combobox"`, `aria-expanded`, `aria-controls`, `aria-haspopup="listbox"`, and `aria-activedescendant` while focus stays on the trigger; a popup `role="listbox"` containing `role="option"` items with `aria-selected`; keys: Enter/Space/ArrowDown open, arrows move, Home/End jump, type-ahead, Enter selects, Escape closes and returns focus; announce the selected value.
4. **Verify** with keyboard, a screen reader and automated checks; add regression tests ([Lesson 05](/frontend-depth/lesson-5)). The autocomplete lesson shows this pattern in code ([Practical Design Problems, Lesson 06](/design-problems/lesson-6)).

## Testing accessibility

- **Static:** `eslint-plugin-jsx-a11y` catches missing alt text, invalid ARIA, click handlers on divs.
- **Automated:** `axe-core` via `jest-axe`, `@axe-core/playwright` or the axe DevTools extension; Lighthouse's accessibility audit. They catch roughly a third to a half of issues (contrast, missing labels, invalid roles), **not** keyboard flow or screen-reader experience.
- **Manual:** keyboard-only pass (Tab order, focus visibility, traps, Escape), zoom to 200%, a screen reader on key flows, high-contrast mode, reduced-motion preference.
- **Query by role in tests**: if `getByRole("button", { name: "Save" })` cannot find it, assistive technology likely cannot either.
- **In CI:** run axe on main pages; fail on serious or critical violations; track regressions.

## Common mistakes

1. **Clickable `div`s and `span`s** instead of buttons and links.
2. **Removing focus outlines** with no replacement.
3. **Missing labels** (placeholder-only inputs, icon buttons with no name).
4. **ARIA used to paper over bad HTML** (and wrong or redundant ARIA).
5. **Modals without focus management** (no trap, no restore, background still reachable).
6. **Colour as the only signal; low contrast.**
7. **No focus management after route changes or dynamic updates.**
8. **Relying only on automated tools**, skipping keyboard and screen-reader testing.

## Interview questions

### Q1. When is ARIA harmful?

When it misdescribes the element or adds semantics without behaviour: `role="button"` on a div with no keyboard support, `aria-label` that conflicts with visible text, `aria-hidden` on focusable content, stale state attributes like `aria-expanded`, or redundant roles. ARIA changes announcements, not behaviour, so native HTML should be used first; no ARIA is better than bad ARIA.

### Q2. How do you trap focus inside a modal?

Prefer the native `<dialog>` opened with `showModal()`, which moves focus in, makes the background inert, closes on Escape and restores focus. If building it manually: move focus to the dialog on open, wrap Tab and Shift+Tab within its focusable elements, set `aria-modal` and an accessible name, mark the background inert or `aria-hidden`, close on Escape and return focus to the trigger.

### Q3. Scenario: a custom dropdown doesn't work with screen readers. Fix it.

Check keyboard and screen-reader behaviour, then replace it with a native `<select>` if suitable, or a proven accessible component library, or implement the WAI-ARIA combobox/listbox pattern: correct roles and states (`aria-expanded`, `aria-controls`, `aria-activedescendant`, `aria-selected`), full keyboard support, focus handling and announcements. Verify with a screen reader and add automated and regression tests.

### Q4. What are the contrast requirements?

WCAG AA requires 4.5:1 for normal text, 3:1 for large text, and 3:1 for UI components and graphical objects such as input borders, icons and focus indicators. Also avoid conveying information by colour alone.

### Q5. Why use a `<button>` instead of a clickable `div`?

A native button is focusable, activates with Enter and Space, exposes the button role and name to assistive technology, supports disabled and form behaviour and works with browser features, all by default. A div needs `role`, `tabIndex`, key handlers and styling to approximate this, and usually gets something wrong.

### Q6. How do you handle focus after a route change in a single-page app?

There is no page load to reset focus or announce the change, so move focus to the new page's main heading (or a wrapper with `tabIndex={-1}`) or announce the title via a live region, and update `document.title`. Frameworks like Next.js provide a route announcer, but test it.

### Q7. How do you announce dynamic content to screen readers?

Use a live region that exists before the update: `role="status"` or `aria-live="polite"` for non-urgent messages like result counts and saved confirmations; `role="alert"` for urgent errors. Keep messages short and avoid over-announcing.

### Q8. What can automated accessibility testing not catch?

Keyboard flow and focus order, whether labels make sense, the quality of alt text, screen-reader announcements of dynamic updates, logical heading structure and the overall usability of custom widgets. Automation finds a portion of issues (missing names, contrast, invalid ARIA); the rest needs manual keyboard and assistive-technology testing.

## Key takeaways

- **Semantic HTML first**: native elements give roles, focus and keyboard behaviour for free.
- Everything interactive needs an **accessible name** and **keyboard operability** with a **visible focus indicator**.
- **Manage focus** for modals, route changes, deletions and errors; prefer native `<dialog>` or proven libraries.
- **ARIA patches gaps**; wrong ARIA does harm. Know the useful attributes and the five rules.
- Meet **contrast** (4.5:1 text, 3:1 large/UI), do not rely on colour, respect **reduced motion** and zoom.
- Test with **lint, axe, keyboard and a screen reader**, and use `getByRole` in tests.
