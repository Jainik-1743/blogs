> **In one line:** modern React splits work by **priority** (urgent input vs background updates), lets components **wait** declaratively (Suspense), and moves non-interactive components to the **server** (Server Components) so they send **no JavaScript**. Next.js builds on all three with streaming and selective hydration.

This lesson gives you the mental model for the App Router era: what runs where, what crosses the boundary, and what causes hydration errors.

## Concurrent rendering and transitions

In React 18+, rendering can be **interruptible**. React can start rendering an update, pause when something more urgent arrives (a keystroke), and continue or restart later ([Lesson 00](/frontend-depth/lesson-0)).

You tell React which updates are **urgent** (typing, clicking, pressing) and which are **transitions** (a screen change or heavy list update that can lag a little):

```tsx
const [isPending, startTransition] = useTransition();

function onTabClick(next: string) {
  startTransition(() => setTab(next));      // non-urgent: React may interrupt or defer this render
}

return (
  <>
    <Tabs onSelect={onTabClick} />
    {isPending && <Spinner />}              // optional feedback while the transition is in progress
    <TabPanel tab={tab} />
  </>
);
```

- **`startTransition` / `useTransition`** marks state updates as transitions. If the user acts again, the in-progress transition render is abandoned.
- **`useDeferredValue(value)`** gives a lagging copy of a value so an expensive part of the UI updates later, while the urgent part stays in sync ([Debugging, Lesson 01](/debugging/lesson-1)).

### `startTransition` vs debounce

| | Debounce | `startTransition` |
|---|---|---|
| **Mechanism** | Delay a callback by N ms | Lower the priority of a React update |
| **Fixed delay** | Yes (user waits at least N ms) | **No**: it renders as soon as the browser is free |
| **Interruptible** | No | **Yes**: a newer interaction cancels the stale render |
| **Reduces network calls** | **Yes** | No (it is about rendering, not requests) |
| **Use for** | Limiting requests (typeahead fetches) | Keeping the UI responsive during heavy re-renders |

They are complementary: debounce the **fetch**, transition the **render**.

## Suspense

**Suspense** lets a component "wait" for something (code, data) and shows a **fallback** until it is ready, declaratively:

```tsx
<Suspense fallback={<ProductSkeleton />}>
  <Product id={id} />        {/* this subtree may suspend while it loads */}
</Suspense>
```

What can suspend: lazy-loaded components (`React.lazy`), data read with the `use` hook or through Suspense-aware libraries and frameworks, and (in Next.js) async Server Components.

- **Boundaries decide the loading experience.** Place them around independent sections so fast parts show immediately and slow parts show skeletons ("waterfall of one big spinner" is the anti-pattern).
- With transitions, React can **keep showing the old UI** while the new content suspends (instead of replacing it with the fallback), which avoids flicker on navigation.
- Combine with **error boundaries** to handle failures: Suspense handles *waiting*, error boundaries handle *throwing*.

## Streaming SSR and selective hydration

Classic SSR: the server renders **all** the HTML, then sends it, then the client downloads all the JS and hydrates **everything**, so one slow data call blocks the whole page.

With Suspense, React supports:

1. **Streaming:** the server sends the HTML **shell immediately** and **streams** the rest as each suspended part resolves; placeholders are replaced in place. TTFB and FCP improve because slow data no longer blocks fast content.
2. **Selective hydration:** React hydrates Suspense boundaries **independently and in priority order**. If the user clicks something inside a not-yet-hydrated boundary, React hydrates that part first.

```text
Server: [header + nav + main shell] ──flush──▶ browser paints now
        ... recommendations query finishes ...  ──stream──▶ replaces the skeleton
Client: hydrates header, then main, then recommendations as their JS arrives; clicks bump priority.
```

This is what makes `loading.tsx` and `<Suspense>` in the Next.js App Router valuable: loading states and streaming come "for free" from the file structure.

## Server Components (RSC)

**React Server Components** are components that run **only on the server** (at build time or per request). Their code never ships to the browser.

```tsx
// app/products/[id]/page.tsx — a Server Component by default in the Next.js App Router
import { db } from "@/lib/db";
import { AddToCart } from "./AddToCart";            // a Client Component

export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await db.product.findUnique({ where: { id } });   // direct data access: no API, no client JS
  return (
    <article>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <AddToCart productId={product.id} price={product.price} />    {/* interactive leaf */}
    </article>
  );
}
```

### What Server Components can and cannot do

| Server Components | Client Components |
|---|---|
| Can be `async` and `await` data, query databases, read files and secrets | Can use `useState`, `useEffect`, event handlers (`onClick`) |
| **Send no component JavaScript** to the browser (smaller bundles, less hydration) | Run in the browser (and are also pre-rendered to HTML on the server) |
| **Cannot** use state, effects, browser APIs or event handlers | Can use browser APIs (`window`, `localStorage`) |
| Can render Client Components | Cannot import Server Components, but can **receive them as `children` or props** |

### The `"use client"` boundary

`"use client"` at the top of a file marks the **boundary**: that module and everything it imports become part of the **client bundle**. Everything else stays on the server by default.

```tsx
"use client";
import { useState } from "react";

export function AddToCart({ productId, price }: { productId: string; price: number }) {
  const [qty, setQty] = useState(1);
  return <button onClick={() => addToCart(productId, qty)}>Add {qty} (₹{price * qty})</button>;
}
```

Guidance: keep the boundary **as low as possible**, at interactive **leaves** (buttons, forms, widgets), so large static parts stay on the server.

**Composition pattern:** a Client Component can render server-rendered content passed as `children`:

```tsx
// ClientShell is a client component (e.g. has open/close state); it does not import ServerList
<ClientShell>
  <ServerList />       {/* rendered on the server, passed through as already-rendered content */}
</ClientShell>
```

### The serialisation rule

Props passed from a Server Component to a Client Component must be **serialisable** (strings, numbers, booleans, plain objects and arrays, dates, promises, and a few more). **Functions, class instances and event handlers cannot cross** the boundary (except **Server Actions**, which are special references). Passing `onClick={() => …}` from a server component to a client component is an error.

### Server Actions

Functions marked `"use server"` run on the server but can be called from the client (forms, handlers), replacing hand-written API endpoints for mutations. Treat them as **public endpoints**: authenticate, authorise and validate inputs inside ([Backend, Lessons 03 and 06](/backend/lesson-3)).

```tsx
"use server";
export async function addToCart(productId: string, qty: number) {
  const user = await requireUser();
  const input = schema.parse({ productId, qty });
  await db.cartItem.upsert(/* … */);
  revalidateTag("cart");
}
```

### Data fetching and caching notes

- **Fetch where you need the data** in Server Components; identical `fetch` GET requests with the same URL and options are **memoised within one server render pass**, so several components can request the same data without extra calls. For non-`fetch` work (database calls), wrap functions with React's `cache`.
- Fetch **in parallel** (`Promise.all`) to avoid server-side waterfalls.
- Cross-request caching behaviour has **changed between Next.js versions** (for example, newer versions use the explicit `"use cache"` model); read the documentation for your version rather than relying on memory.

## Hydration and why mismatches happen

**Hydration** is React attaching event handlers to server-rendered HTML and reusing the DOM. For that to work, the **first client render must produce the same output as the server's HTML**. If it differs, React warns ("Hydration failed because the server rendered HTML didn't match the client") and may discard the server HTML and re-render on the client, losing the benefit.

Common causes and fixes:

| Cause | Example | Fix |
|---|---|---|
| **Non-deterministic values** in render | `Date.now()`, `Math.random()`, `new Date().toLocaleString()` | Compute on the server and pass as a prop; or render the client-only value after mount in an effect |
| **Browser-only APIs** in render | `window.innerWidth`, `localStorage`, `navigator.language` | Read them in `useEffect` (state starts with a server-safe default) or use `useSyncExternalStore` with a server snapshot |
| **Locale/timezone differences** | Server formats dates in UTC, browser in IST | Use explicit locale and timezone options, or format on the client |
| **Invalid HTML nesting** | `<div>` inside `<p>`, `<a>` inside `<a>`, `<tr>` outside `<tbody>` | Correct the markup (browsers auto-fix it, causing a mismatch) |
| **Third-party and extensions** | Browser extensions injecting nodes into the DOM | Use `suppressHydrationWarning` on the affected element sparingly |
| **Conditional rendering on client-only state** | `typeof window !== "undefined" ? <A/> : <B/>` | Render the same on first pass; switch after mount |

```tsx
function ClientTime({ iso }: { iso: string }) {
  const [text, setText] = useState(iso);                       // identical on server and first client render
  useEffect(() => setText(new Date(iso).toLocaleString()), [iso]);   // localised after hydration
  return <time dateTime={iso}>{text}</time>;
}
```

## Scenario: a Client Component pulls a heavy library into the server render. What are the consequences?

Remember that **Client Components are also rendered to HTML on the server** (for the first paint) *and* shipped to the browser. A heavy library imported by a Client Component therefore:

1. **Increases the JS bundle** the browser must download, parse and execute: slower LCP and INP, especially on mid-range phones.
2. **Increases hydration cost**: more client code to run before the page is interactive.
3. **Costs server render time** too: the library executes during SSR for every request (or at build time for static pages), adding to TTFB, and may break if it touches `window` during SSR.
4. **Spreads**: every module imported by the `"use client"` file also joins the client bundle.

Fixes:

- **Keep the heavy work in a Server Component** and pass only the **results** as props (for example, render Markdown, syntax-highlight, format dates or process data on the server).
- **Move the `"use client"` boundary down** to the smallest interactive component.
- **Lazy-load** truly client-only widgets with `next/dynamic` (and `ssr: false` only when it needs the browser and is not needed for first paint), or load on interaction ([Debugging, Lesson 06](/debugging/lesson-6)).
- **Replace** the library with a lighter one, and enforce a bundle budget.
- Mark server-only modules with `import "server-only"` so they cannot be accidentally imported into client code.

## Common mistakes

1. **Putting `"use client"` at the top of large components or the root layout**, shipping everything to the browser.
2. **Passing functions (non-actions) or class instances** from server to client components.
3. **Using hooks, state or browser APIs in a Server Component.**
4. **Hydration mismatches** from dates, random values, `window` and invalid HTML.
5. **One big Suspense boundary** (or none), so the slowest query blocks all content.
6. **Server-side waterfalls** (sequential awaits for independent data).
7. **Treating Server Actions as private**: they are public endpoints needing auth and validation.
8. **Assuming caching defaults** from an older Next.js version.

## Interview questions

### Q1. What problem do Server Components solve?

They let non-interactive components run only on the server, so their code and dependencies never reach the browser, reducing bundle size and hydration cost. They can access databases and secrets directly, fetch data close to the source and stream results, while interactive pieces remain Client Components.

### Q2. What causes hydration mismatches?

The first client render producing different output than the server HTML: non-deterministic values (dates, random numbers), browser-only APIs during render, locale or timezone differences, invalid HTML nesting, extensions modifying the DOM, or client-only conditional rendering. Fix by making the first render deterministic and updating client-specific values after mount.

### Q3. `startTransition` vs debounce?

Debounce delays an action by a fixed time and reduces how often work (like a network call) happens. `startTransition` keeps the update immediate but marks its render as low priority and interruptible so urgent input stays responsive; it does not reduce network calls. Use debounce for requests and transitions for heavy rendering, often together.

### Q4. Scenario: a Client Component pulls a heavy library into the server render. What are the consequences?

The library enlarges the client bundle and hydration cost and also runs during server rendering, slowing TTFB and risking `window` errors; everything the client module imports ships to the browser. Move heavy computation into Server Components and pass results as props, lower the client boundary, lazy-load client-only widgets, replace the library and set bundle budgets.

### Q5. How does streaming SSR improve performance?

The server sends the HTML shell immediately and streams slower Suspense sections as they resolve, so users see content sooner and slow data no longer blocks the whole page. Selective hydration then hydrates boundaries independently, prioritising ones the user interacts with.

### Q6. What can cross the server-to-client boundary?

Serialisable data: primitives, plain objects and arrays, dates, promises and some other supported types, plus Server Action references and rendered server content passed as children. Arbitrary functions, class instances and event handlers cannot.

### Q7. Where should the `"use client"` boundary go?

As deep as possible: at interactive leaf components (forms, buttons, widgets). Keeping parents as Server Components minimises client JavaScript, and Client Components can still render server-rendered content passed in as children.

### Q8. Why are Server Actions a security concern?

They are callable over the network, so they are effectively public endpoints. Each must authenticate the caller, authorise access to the specific resource, validate and sanitise input and handle errors safely, exactly like an API route.

## Key takeaways

- **Concurrent React:** urgent vs transition updates; `useTransition`/`useDeferredValue` keep input responsive and are interruptible, unlike debounce.
- **Suspense** gives declarative loading states; **streaming + selective hydration** show content early and hydrate by priority.
- **Server Components** send no JS and can access data directly; **`"use client"`** marks interactive leaves; props must be **serialisable**.
- **Hydration mismatches** come from non-deterministic or browser-only render output; keep first renders identical and update after mount.
- Keep heavy libraries on the server, move boundaries down, lazy-load, parallelise fetches and check caching docs for your Next.js version.
