> **In one line:** advanced TypeScript is about making **illegal states unrepresentable** and letting types **flow** from one source of truth. Master generics with constraints, narrowing (especially discriminated unions), mapped and conditional types, and the one habit that fixes most API bugs: **derive types from schemas** instead of writing them twice.

Interviews rarely ask for type-level gymnastics for their own sake. They ask whether you can type a reusable function correctly, model a state machine safely, and keep frontend types in sync with a backend you do not fully control.

## `unknown` vs `any`

- **`any`** turns off type checking for that value. It spreads silently (a value derived from `any` is `any`).
- **`unknown`** means "a value I know nothing about yet". You **cannot use it** until you **narrow** it. It is the type-safe counterpart of `any`, ideal for data from outside your program (`JSON.parse`, `fetch().json()`, `catch (e)`).

```ts
{
  function parse(json: string): unknown { return JSON.parse(json); }

  const v = parse('{"id": 1}');
  // v.id            // ❌ error: 'v' is of type 'unknown'
  if (typeof v === "object" && v !== null && "id" in v) {
    console.log((v as { id: unknown }).id);   // ✅ after narrowing
  }
}
```

Use `unknown` at boundaries and validate with a schema ([below](#keeping-api-types-in-sync)). Enable `strict` (and `noUncheckedIndexedAccess`) in `tsconfig`.

## Generics

A generic is a **type parameter**: a function or type that works for many types while preserving their relationship.

```ts
{
  // The return type depends on the input type: no information is lost
  function first<T>(items: readonly T[]): T | undefined { return items[0]; }
  const n = first([1, 2, 3]);        // number | undefined
  const s = first(["a", "b"]);       // string | undefined
}
```

### Constraints: `extends`

Say what the type parameter must at least look like:

```ts
{
  function byId<T extends { id: string }>(items: T[]): Map<string, T> {
    return new Map(items.map((i) => [i.id, i]));
  }
  byId([{ id: "a", name: "Ada" }]);      // ✅ T inferred as { id: string; name: string }
  // byId([{ name: "x" }]);              // ❌ missing 'id'
}
```

### `keyof` and indexed access

```ts
{
  function pluck<T, K extends keyof T>(obj: T, key: K): T[K] {   // return type is the exact property type
    return obj[key];
  }
  const user = { id: 1, name: "Ada" };
  const name = pluck(user, "name");        // string
  // pluck(user, "age");                    // ❌ "age" is not a key of the object
}
```

### Defaults and inference

```ts
{
  type ApiResult<T = unknown, E = Error> = { ok: true; data: T } | { ok: false; error: E };
  const r: ApiResult<number> = { ok: true, data: 1 };
}
```

Let TypeScript **infer** type arguments from usage; add them explicitly only when it cannot.

## Narrowing

TypeScript refines a value's type inside a branch based on checks it understands:

| Technique | Example |
|---|---|
| `typeof` | `typeof x === "string"` |
| `instanceof` | `err instanceof Error` |
| `in` | `"radius" in shape` |
| Truthiness / equality | `if (x)`, `x === null`, `x !== undefined` |
| **Discriminant property** | `shape.kind === "circle"` |
| **User-defined type guard** | `function isUser(x: unknown): x is User` |
| Assertion function | `function assertDefined<T>(x: T): asserts x is NonNullable<T>` |

### Discriminated unions

Give every variant a literal tag (the **discriminant**); narrowing on the tag gives access to that variant's fields.

```ts
{
  type Shape =
    | { kind: "circle"; radius: number }
    | { kind: "rect"; width: number; height: number }
    | { kind: "square"; size: number };

  function area(s: Shape): number {
    switch (s.kind) {
      case "circle": return Math.PI * s.radius ** 2;
      case "rect": return s.width * s.height;
      case "square": return s.size ** 2;
      default: {
        const _exhaustive: never = s;          // compile error if a new variant is added and not handled
        return _exhaustive;
      }
    }
  }
}
```

**Exhaustive checks:** assigning the leftover value to `never` makes the compiler fail when a new variant (`"triangle"`) is added without handling it. That is how discriminated unions "enable exhaustive checks".

This is also the right way to model async state, replacing booleans ([Lesson 03](/frontend-depth/lesson-3)):

```ts
{
  type Remote<T> =
    | { status: "idle" }
    | { status: "loading" }
    | { status: "success"; data: T }
    | { status: "error"; error: Error };

  function label(r: Remote<string[]>): string {
    switch (r.status) {
      case "idle": return "Not started";
      case "loading": return "Loading…";
      case "success": return `${r.data.length} items`;   // data exists only here
      case "error": return r.error.message;              // error exists only here
    }
  }
}
```

### Type guards

```ts
{
  type User = { id: string; name: string };

  function isUser(x: unknown): x is User {
    return typeof x === "object" && x !== null
      && typeof (x as Record<string, unknown>).id === "string"
      && typeof (x as Record<string, unknown>).name === "string";
  }

  function handle(input: unknown) {
    if (isUser(input)) console.log(input.name.toUpperCase());   // narrowed to User
  }
}
```

Be careful: a type guard is a promise *you* make; a wrong guard is a lie the compiler believes. Prefer schema validation for real data.

## Utility types

| Utility | Meaning |
|---|---|
| `Partial<T>` / `Required<T>` | All properties optional / required |
| `Readonly<T>` | All properties read-only |
| `Pick<T, K>` / `Omit<T, K>` | Keep / remove certain keys |
| `Record<K, V>` | An object with keys `K` and values `V` |
| `Exclude<U, X>` / `Extract<U, X>` | Remove / keep union members assignable to `X` |
| `NonNullable<T>` | Remove `null` and `undefined` |
| `ReturnType<F>` / `Parameters<F>` | A function's return / parameter types |
| `Awaited<T>` | Unwrap a `Promise` type |

```ts
{
  type User = { id: string; name: string; email: string; passwordHash: string };
  type PublicUser = Omit<User, "passwordHash">;                    // never leak the hash in a response type
  type UserPatch = Partial<Pick<User, "name" | "email">>;          // PATCH body
  type ById = Record<User["id"], User>;
}
```

## Mapped types

Transform every property of a type with `{ [K in keyof T]: … }`:

```ts
{
  type Mutable<T> = { -readonly [K in keyof T]: T[K] };            // remove readonly
  type Nullable<T> = { [K in keyof T]: T[K] | null };
  type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };   // key remapping + template literal types

  type Person = { name: string; age: number };
  type PersonGetters = Getters<Person>;     // { getName: () => string; getAge: () => number }
}
```

## Conditional types and `infer`

`T extends U ? X : Y` chooses a type based on a relationship; `infer` captures a part of a type inside the condition.

```ts
{
  type IsString<T> = T extends string ? true : false;
  type A = IsString<"x">;   // true
  type B = IsString<1>;     // false

  // Extract the element type of an array, and unwrap a Promise
  type ElementOf<T> = T extends readonly (infer U)[] ? U : never;
  type Unwrap<T> = T extends Promise<infer U> ? U : T;

  type E = ElementOf<string[]>;          // string
  type P = Unwrap<Promise<number>>;      // number

  // Conditional types distribute over unions
  type ToArray<T> = T extends unknown ? T[] : never;
  type X = ToArray<string | number>;     // string[] | number[]
}
```

(The built-in `ReturnType`, `Parameters` and `Awaited` are written with `infer`.)

## Implementing `DeepPartial<T>`

A classic interview question: make every property, at every depth, optional.

```ts
{
  type DeepPartial<T> =
    T extends (...args: never[]) => unknown ? T                       // leave functions alone
    : T extends readonly (infer U)[] ? DeepPartial<U>[]               // arrays: partial elements
    : T extends object ? { [K in keyof T]?: DeepPartial<T[K]> }       // objects: recurse
    : T;                                                              // primitives: unchanged

  type Settings = { theme: { dark: boolean; accent: string }; tags: string[]; save: () => void };

  const patch: DeepPartial<Settings> = { theme: { dark: true } };     // ✅ nested partial
  // const bad: DeepPartial<Settings> = { theme: { dark: "yes" } };  // ❌ error: string is not boolean (uncomment to see)
}
```

Explain the pieces: a conditional type for each category, recursion for objects and arrays, and a base case for primitives and functions.

## `as const` and `satisfies`

```ts
{
  // as const: literal types and readonly
  const ROLES = ["admin", "editor", "viewer"] as const;
  type Role = (typeof ROLES)[number];              // "admin" | "editor" | "viewer"

  // satisfies: check against a type WITHOUT widening the inferred type
  type Route = { path: string; auth: boolean };
  const routes = {
    home: { path: "/", auth: false },
    admin: { path: "/admin", auth: true },
  } satisfies Record<string, Route>;

  routes.home.path;                                 // type is string, and the keys "home" | "admin" are preserved
  // a typo like { pth: "/" } would be an error, but routes keeps its precise shape
}
```

`satisfies` validates a value against a contract while keeping the most specific inferred type: unlike a type annotation (`const routes: Record<string, Route> = …`), which would lose the known keys.

## `type` vs `interface`

Both describe object shapes; differences are small:

| | `interface` | `type` |
|---|---|---|
| Extends | `extends`; **declaration merging** (same name merges) | Intersection `&` |
| Can express | Object shapes, class contracts | Objects **and** unions, tuples, primitives, mapped/conditional types |
| Errors | Often clearer on extension conflicts | |
| Convention | Public library object types | Unions, utilities, anything computed |

A common stance: use **`interface`** for object-like public APIs you want to be extendable, and **`type`** for everything else; consistency in a codebase matters more than the choice.

## Branded (nominal-ish) types

Prevent mixing up values that share a primitive type:

```ts
{
  type Brand<T, B extends string> = T & { readonly __brand: B };
  type UserId = Brand<string, "UserId">;
  type OrderId = Brand<string, "OrderId">;

  const asUserId = (s: string) => s as UserId;
  function loadUser(id: UserId) { /* … */ }

  const oid = "o_1" as OrderId;
  // loadUser(oid);                // ❌ OrderId is not assignable to UserId
  loadUser(asUserId("u_1"));        // ✅
}
```

The brand exists only at compile time (no runtime cost); create branded values in one validated place.

## Keeping API types in sync

**Scenario: frontend API types drift out of sync with the backend.** The backend renames a field; the frontend's hand-written interface still says the old name; TypeScript is happy and production breaks. Types you write by hand are **assumptions**, not facts. Options, strongest first:

1. **One schema, many consumers.** Define a runtime schema (Zod, Valibot, ArkType) in a shared package; derive types from it; validate responses at the boundary.

```ts
{
  // With Zod: const OrderSchema = z.object({ id: z.string(), totalMinor: z.number().int(), status: z.enum(["pending", "paid"]) });
  type Parser<T> = { parse(input: unknown): T };
  type OrderShape = { id: string; totalMinor: number; status: "pending" | "paid" };
  const OrderSchema: Parser<OrderShape> = { parse: (input) => input as OrderShape };   // stand-in: a real schema checks every field
  type Order = ReturnType<typeof OrderSchema.parse>;     // with Zod you would write z.infer<typeof OrderSchema>

  async function getOrder(id: string): Promise<Order> {
    const res = await fetch(`/api/orders/${id}`);
    return OrderSchema.parse(await res.json());          // unknown → validated Order; throws if the API drifted
  }
}
```

2. **Generate types from an OpenAPI/GraphQL schema** (`openapi-typescript`, GraphQL Code Generator) in CI. A breaking change becomes a compile error; add a breaking-change check on the spec ([Backend, Lesson 11](/backend/lesson-11)).
3. **End-to-end typed RPC** (tRPC, or typed server actions in a TypeScript monorepo): the client imports the server's types directly.
4. **Contract tests** as a safety net.

Whichever you choose: **never trust `res.json()` as a typed value.** It returns `any` (or `unknown` if you type it so); validate at the edge so types describe reality.

## Overloads, tuples and other tools worth recognising

```ts
{
  // Function overloads: precise return types per call shape
  function parseId(id: string): string;
  function parseId(id: number): number;
  function parseId(id: string | number) { return id; }

  // Tuples with labels: fixed-length arrays with positions
  type Range = [start: number, end: number];

  // Generic components/hooks: relate props to a value
  function useList<T extends { id: string }>(items: T[]) { return new Map(items.map((i) => [i.id, i] as const)); }
}
```

Also be able to explain: **structural typing** (compatibility is by shape, not name), **variance** basics (why `Array<Dog>` assignable to `Array<Animal>` is allowed but unsound for mutation), **`readonly`**, the **`never`** type, and that **types are erased at runtime**: they cannot validate data.

## Common mistakes

1. **Using `any` as a shortcut**, losing all safety downstream.
2. **Type assertions (`as Foo`) to silence the compiler** instead of validating.
3. **Trusting `fetch().json()`** as typed API data.
4. **Several booleans instead of a discriminated union.**
5. **Missing the `never` exhaustiveness check** in switches over unions.
6. **Hand-maintained API interfaces** that drift.
7. **Over-engineering types** nobody can read: prefer simple, well-named types.
8. **Forgetting that TypeScript types disappear at runtime.**

## Interview questions

### Q1. `unknown` vs `any`?

`any` disables type checking and infects everything it touches. `unknown` is the safe top type: a value of any kind that must be narrowed (by `typeof`, `instanceof`, type guards or schema validation) before use. Prefer `unknown` for external data and catch variables.

### Q2. Implement `DeepPartial<T>`.

A recursive conditional type: leave functions as they are, map arrays to arrays of `DeepPartial` elements, map objects with `{ [K in keyof T]?: DeepPartial<T[K]> }`, and return primitives unchanged.

### Q3. How do discriminated unions enable exhaustive checks?

Each variant has a literal discriminant property, so narrowing on it gives access to the right fields. In a `switch` over the discriminant, a `default` branch can assign the remaining value to `never`; if a new variant is added and not handled, the assignment fails to compile, forcing you to update the code.

### Q4. `type` vs `interface`?

Both describe object shapes. Interfaces support declaration merging and read well for extendable object contracts; type aliases can also express unions, tuples, primitives and mapped or conditional types. Pick a convention (for example `interface` for public object shapes, `type` otherwise) and stay consistent.

### Q5. Scenario: frontend API types drift out of sync with the backend. How do you prevent it?

Derive types from a single source of truth: shared runtime schemas (for example Zod) used by both sides, or types and clients generated from OpenAPI/GraphQL schemas in CI, or end-to-end typed RPC. Validate responses at the boundary instead of asserting types, and add breaking-change checks and contract tests so drift fails the build.

### Q6. What is the difference between `satisfies` and a type annotation?

An annotation widens the value to the declared type (losing specific keys or literals). `satisfies` checks that the value conforms to the type but keeps its more precise inferred type, so you get validation without losing information.

### Q7. What does `infer` do?

Inside a conditional type it declares a type variable that TypeScript infers from the matched position, letting you extract parts of a type (an array's element, a Promise's resolved value, a function's return type).

### Q8. How do generics with constraints help in a reusable function?

They let a function accept many types while guaranteeing certain properties and preserving the exact input type in the output. For example, `function byId<T extends { id: string }>(items: T[])` can use `id` safely while returning the original element type rather than a loose base type.

### Q9. Scenario: `any` keeps creeping into the codebase. How do you stop it?

Make it expensive and visible: enable `strict` and the lint rule against explicit `any`, ban unchecked `as` casts at API boundaries, validate external data with schemas so types are real, prefer `unknown` plus narrowing, and ratchet in CI so the count of `any` can only go down. Review the reasons people reach for `any`; often a missing generic or a missing schema.

## Key takeaways

- Use **`unknown` at boundaries**, narrow or **validate**, avoid `any` and unchecked `as`.
- **Generics with `extends`/`keyof`** keep types connected; learn mapped and conditional types with `infer`.
- **Discriminated unions + `never` checks** make illegal states unrepresentable and updates safe.
- `as const` and **`satisfies`** keep precision while validating.
- **Types are erased:** keep API types honest with **shared schemas, generated types or typed RPC**, and validate at runtime.
